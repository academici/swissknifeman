# Verify Claims — не решай по устаревшему знанию, верифицируй внешний факт

Знание модели имеет порог и может быть неполным/ошибочным по конкретной теме. Поэтому **классифицируй
заявление перед тем, как на нём строить решение/вердикт** — и внешние staleness-чувствительные факты
до-проверяй через RAG, а не утверждай по памяти.

## Классификация заявления (главное)

| Тип | Источник истины | Верифицировать? |
|---|---|---|
| **Repo/code-grounded** — есть в коде/конфиге ЭТОГО репо | прочитать код (он авторитетен для репо) | НЕТ |
| **Стабильное общее знание** — синтаксис языка, устоявшиеся алгоритмы, математика | — | НЕТ |
| **Внешнее + staleness-чувствительное** — версии/API библиотек, «ещё актуально/поддерживается», best practice, рынок, возможности чужого сервиса/сервера/MCP, цены, security | **RAG (лестница ниже) + цитата + confidence** | **ДА** |

## Когда верификация ТРЕБУЕТСЯ (конкретные ситуации)

- **Ревью аудита/плана:** любой вердикт/**отказ**, опирающийся на внешний факт («библиотека Y это уже умеет»,
  «это deprecated», «современный способ — Z», «сервер X уже отдаёт это») — **даже если аудит выглядел полным**.
  Repo-grounded вердикты (прочитал код — реализовано/нет) — исключение, проверять не надо.
- **Большое планирование/дизайн (формирование плана):** выбор стека, архитектура, выбор библиотеки/сервиса/интеграции
  — проверь текущие версии/API/SLA/цены/«поддерживается ли» ДО фиксации. **План на 100% стоит на свежих данных**;
  завершай его footer'ом «Проверка» (ниже): что проверено, что осталось непроверенным → повторный проход.
- **Утверждение «current best practice» / «это стандарт» / «так больше не делают»** — проверь, что всё ещё актуально.
- **Рекомендация/внедрение зависимости, инструмента, MCP-сервера** — проверь, что существует, поддерживается,
  делает заявленное, и какое имя пакета/команда актуальны.
- **Любое post-cutoff / time-sensitive** (релизы, цены, депрекейты после порога знаний).

Правило широты: всё, что **не** чистая реализация уже-спланированного-и-проверённого ТЗ, подкрепляй данными.
Дешевле перепроверить, чем зафиксировать неверный вердикт.

## Когда НЕ требуется (узкие исключения)

- Repo/code-grounded — проверено чтением кода/конфига.
- Стабильное общее знание (синтаксис, устоявшиеся паттерны, математика).
- Чистая реализация уже-спланированного-и-верифицированного ТЗ («за тебя спланировали — реализуй»).

## Лестница движков (дешёвый/надёжный — первым)

1. **Факт про библиотеку/фреймворк/API** (есть ли метод, текущая сигнатура, опция конфига, поведение версии)?
   → **сначала context7** — живые версионные доки, самый дешёвый и авторитетный для библиотек:
   `resolve-library-id` → `query-docs`. Если есть подключённая дока проекта — сначала она.
   **Библиотеки/API нет в context7** (не проиндексирована / пустой ответ) → фолбэк на **`perplexity-web`** (п.2),
   НЕ на WebSearch.
2. **Факта нет в доках библиотек** (best practice, «ещё рекомендуется/поддерживается», рынок, сравнение,
   недавнее изменение, security-advisory, «какой пакет/команда сейчас») → **Perplexity — агрессивный дефолт**:
   - есть `PERPLEXITY_API_KEY` → **native Perplexity MCP** (точнее/быстрее, инструменты `perplexity_ask`/`perplexity_research`);
   - нет ключа → **`perplexity-web`** (keyless-мост: `mcp__perplexity-web__search` / `search_advanced` / `search_deep`).
   **Почему агрессивно:** `perplexity-web` — keyless, через браузерный профиль по **flat-rate подписке** (не жрёт
   API-токены) и возвращает **компактный синтез** вместо сырых страниц. Выгружай retrieval+синтез на него **по
   максимуму** — это дешевле по контекст-токенам, чем тянуть выдачу через WebSearch/WebFetch (сырьё в контекст).
3. **Одна известная страница/URL, тривиальная проверка** → **WebFetch/WebSearch** (Claude-native) — **последний
   фолбэк**: тянут сырьё в контекст (дороже по токенам). Бери их только под конкретный known-URL или когда
   Perplexity недоступен.
4. **Глубокий/высокоставочный** (нужен синтез + кросс-чек источников) → эскалация в скилл `research/research`
   (deep-research, source-tiers, faithfulness-check).

Принцип экономии: context7 для точного API библиотек; всё остальное — агрессивно через `perplexity-web`
(flat-rate, компактный синтез); WebSearch/WebFetch — узкий known-URL/фолбэк; не пали deep-research зря.

## Делегирование: не ронять ступень

Лестница — обязательство на РЕЗУЛЬТАТ, не только порядок движков. RAG-ступень выполняется там, где
приоритетный движок ДОСТУПЕН (обычно — основной контекст). **Прежде чем делегировать «проверь X»
субагенту — убедись, что у него в тулсете есть `perplexity-web` (и `context7`).** Топикально-подходящий
агент (напр. «по Claude Code») часто WebSearch-only → делегируя туда, ты МОЛЧА роняешь лестницу до
WebSearch. Если у делегата нет приоритетного движка: (а) держи проверку в основном контексте; (б) дай
субагенту сам движок `perplexity-web`; (в) пусть субагент вернёт, ЧТО проверить, а лестницу прогони
сам. Делегировать верификацию МОЖНО (напр. `research/research` фанит осознанно) — нельзя лишь молча
ронять ступень. Если ступень всё же прошла урезанной — это отказ движка: в footer «Непроверено →
ПОВТОРНЫЙ ПРОХОД».

## Цитирование и confidence

- Указывай **источник + дату** факта в выводе.
- Помечай **confidence**: `high` (первичные/официальные доки, кросс-чек ≥2 источников) · `medium` (один
  первичный источник) · `low` (только вторичные/форумы). Один источник Tier-низко — провизорно.
- Внешнее решение на `low` confidence — **не финализируй без явного флага** «требует подтверждения».
- Противоречие источников → не выбирай молча: покажи расхождение и спроси/эскалируй.

## Footer «Проверка» (низ плана/дизайна/вердикта)

Любой план/дизайн/вердикт, где были внешние факты, завершай блоком **«Проверка»** — чтобы владелец видел, на
чём план стоит, и мог дать команду **повторного прохода**, если данные не добрались:

```
## Проверка (verification status)
- RAG: <движки + N запросов + успех/деградация> (напр. «perplexity-web ×3 OK, context7 ×1 OK»)
- Непроверено → ПОВТОРНЫЙ ПРОХОД: <факт> — <движок был недоступен: lock/timeout/MCP down>
- Обходки/[POSSIBLE-DEFECT]: <что решено костылём без реального решения — честно>
```

- Движок был недоступен/деградировал (`perplexity-web` залочен/`TIMEOUT`, MCP лёг, `context7` пусто) и факт
  остался непроверенным → **не маскируй, не финализируй молча**: вынеси в «Непроверено → ПОВТОРНЫЙ ПРОХОД».
- Пустые секции пиши явно («непроверенного нет», «обходок нет») — тишина ≠ «всё проверено».

## Честность: не правки ради правок, костыль называй костылём

- Верификация показала, что правка **не нужна** (факт уже верен, «библиотека это уже умеет») → **убери её из
  плана**, не фиксируй ради активности.
- Реального решения нет, остаётся обходка → пометь `[POSSIBLE-DEFECT]` / «обходка, реального решения нет» и
  вынеси в footer «Проверка». **Не выдавай костыль за решение.**

## Ревью аудита — спец-клауза

Разбирая чужой аудит/план, для КАЖДОГО пункта реши: вердикт repo-grounded или внешний?
- repo-grounded («уже в файле Y», «модуль это делает») → подтверди чтением кода, без RAG.
- внешний («библиотека/сервер/рынок уже это умеет», «это устарело») → **до-проверь по лестнице ДО финализации**,
  даже если уверен и даже если аудит «полный». Лучше подстраховаться, чем отклонить пункт по устаревшему знанию.

## Чеклист качества

- [ ] Каждое решение-несущее заявление классифицировано (repo-grounded / стабильное / внешнее-staleness).
- [ ] Внешние факты проверены по лестнице (context7 для API → **агрессивно `perplexity-web`** → websearch фолбэк → research), не по памяти.
- [ ] Синтез/beyond-docs выгружен на `perplexity-web` (flat-rate, токен-дёшево), а не тянут сырьём через WebSearch/WebFetch.
- [ ] Источник + дата + confidence указаны; `low`-факты помечены «требует подтверждения».
- [ ] План/дизайн/вердикт с внешними фактами несёт footer «Проверка» (RAG + непроверенное→повторный проход + обходки).
- [ ] В ревью аудита внешне-мировые вердикты до-проверены, repo-grounded — подтверждены кодом.

## Связанные скиллы

- `mcp-advisor` (general) — комплементарен: тот про **что подключить** к проекту (context7/perplexity/web как
  серверы), этот про **когда** доставать факт. Перед верификацией убедись, что нужный движок подключён.
- `research/query-craft` — про **как сформулировать** запрос к движку (детализация: версия/стек/режим
  search·advanced·deep/источники; надёжность keyless-моста perplexity-web). Подключается ПОСЛЕ решения «надо
  проверить»: эта тройка (mcp-advisor=что · verify-claims=когда · query-craft=как) — единая RAG-дисциплина.
- `research/research` — глубокий RAG: source-tiers, faithfulness-check, многошаговый deep-research; сюда эскалирует п.4 лестницы.
- `general/grill-with-docs` — частный тяжёлый случай: разбор ТРЕБОВАНИЙ против кода+внешних спек (API/RFC/банк) с glossary+ADR.
- `general/anti-drift` — дисциплина итераций; этот скилл — дисциплина знания (не утверждать устаревшее).
- `general/context-economy` — каждый RAG-движок стоит контекста/permissions; не держи неиспользуемые подключёнными.
