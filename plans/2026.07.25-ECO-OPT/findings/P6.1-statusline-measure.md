# P6.1 — замеры statusline context-notify (2026-07-28)

Четыре доказательства из ТЗ item'а: дельта бюджета первого хода, латентность рендера,
таблица полос порога офлайн, ноль подпроцессов-сирот. Всё снято на дереве
`packages/harness` с внесённым item'ом; сырые прогоны — во временном каталоге сессии
(в репозиторий не коммитятся, как и требует «`git status --porcelain` чист от временных
файлов»).

Машина замера: Linux 7.0.0-28-generic, bash 5.x, `jq` из системы, `python3` только как
секундомер вокруг скрипта (в горячем пути python отсутствует).

---

## 1. Дельта `skiller budget --first-turn` = 0 ток

Ожидание было записано **до** прогона (D54: statusline не тратит контекст-токенов вовсе,
«The status line runs locally and does not consume API tokens»; пять источников гейта —
`skills`/`agents`/`claude_md`/`hooks`/`mcp` — statusline не включают). Гейт прогнан как
**доказательство нуля**, а не как замер.

Цель — чистый временный проект (`.claude/` без прочих артефактов), чтобы дельту не
маскировали чужие источники.

```bash
skiller budget --first-turn --target <tmp-проект> --json          # ДО
harness hooks --target <tmp-проект> --statusline context          # включение
skiller budget --first-turn --target <tmp-проект> --json          # ПОСЛЕ
```

| Прогон | skills | agents | claude_md | hooks | mcp | **total** | verdict |
|:--|--:|--:|--:|--:|--:|--:|:--|
| ДО включения | 2547 | 0 | 0 | 0 | 0 | **2547** | OK |
| ПОСЛЕ включения | 2547 | 0 | 0 | 0 | 0 | **2547** | OK |

**Дельта `total` = 0 ток.** Ненулевая дельта трактовалась бы как ошибка монтажа (механизм
зацепили за SessionStart-хук) — этой ветки не случилось.

## 2. Латентность рендера — медиана 5.4 мс, максимум 6.9 мс

Порог приёмки из ТЗ (не двигался под результат): **медиана ≤ 50 мс, максимум ≤ 150 мс**
на 50 прогонах.

Методика: 50 последовательных прогонов `bash context-notify.sh` на записанном образце JSON
(`used_percentage: 42`, `context_window_size: 1000000`), состояние сессии предварительно
создано прогревочным прогоном — меряется **steady-state рендер**, а не ветка старта сессии.
Секундомер — `time.perf_counter()` вокруг `subprocess.run`, то есть в число входит и запуск
самого bash (пессимистично в нашу сторону).

| Метрика | Значение | Порог |
|:--|--:|--:|
| минимум | 4.8 мс | — |
| **медиана** | **5.4 мс** | ≤ 50 мс ✅ |
| p90 | 5.8 мс | — |
| **максимум** | **6.9 мс** | ≤ 150 мс ✅ |

Запас порядка ×9 к медианному порогу. Он куплен правилом «ровно один внешний вызов на
рендер» (`jq` одним выражением): `git`/`curl`/`python3`/сеть в горячем пути отсутствуют,
`mkdir`/`mv`/`find` возможны только на редких ветках (старт сессии, смена полосы).

**`[UNVERIFIED]` из `findings/P6-context-hygiene-facts.md` §1.4 остаётся `[UNVERIFIED]`:**
дока не называет таймаута statusline-скрипта, и наблюдать «что будет, если скрипт висит
минуту» на этом item'е было нечем — скрипт не висит. Бюджет времени по-прежнему
самодисциплина, а не гарантия рантайма; приводить его к наблюдённому значению не
понадобилось.

## 3. Таблица полос — офлайн-прогон `null→5→79→81→85→91→30→95`

Пороги `80,90`; доставка подменена фейковым `NOTIFY_CMD` (пишет payload в лог), поэтому
прогон офлайновый и повторяемый. Ожидаемый список уведомлений зафиксирован **до** прогона
и вынесен в юнит-тест `tests/test_statusline.py` (`test_band_sequence_without_cooldown`,
`test_cooldown_suppresses_and_does_not_lose_alert`).

### 3.1 `COOLDOWN_MIN=0` — чистая семантика полосы

| % | Строка статуса | Уведомление | Состояние после |
|:--|:--|:--:|:--|
| `null` | `Opus 5 · proj` (бара нет) | — | файла нет (решение НЕ принимается) |
| 5 | `[----------] 5%` | — | `BAND=0` |
| 79 | `[#######---] 79%` | — | `BAND=0` |
| **81** | `[########--] 81%` | **+1** (порог 80%) | `BAND=1` |
| 85 | `[########--] 85%` | — (та же полоса) | `BAND=1` |
| **91** | `[#########-] 91%` | **+1** (порог 90%) | `BAND=2` |
| 30 | `[###-------] 30%` | — (падение) | `BAND=0` — сброс вниз |
| **95** | `[#########-] 95%` | **+1** (порог 90%) | `BAND=2` |

**Итог: ровно 3 уведомления** — по одному на пересечение полосы вверх, включая «второе
после падения и нового подъёма». Ветка «уведомляет каждый раз» (была бы 5) и ветка «не
уведомляет второй раз после компакта» (была бы 2) закрыты числом, а не рассуждением.

### 3.2 `COOLDOWN_MIN=15` (дефолт) — троттлинг, при котором алерт не теряется

| % | Уведомление | Состояние после |
|:--|:--:|:--|
| `null`, 5, 79 | — | `BAND=0` |
| **81** | **+1** | `BAND=1`, `LAST_NOTIFY=<epoch>` |
| 85 | — | `BAND=1` |
| 91 | — (кулдаун) | `BAND=1` — **полоса НЕ повышена** |
| 30 | — | `BAND=0` |
| 95 | — (кулдаун) | `BAND=0` |

**Итог: 1 уведомление.** Ключевое свойство: подавленный кулдауном переход **не съедается** —
полоса в состоянии остаётся прежней, поэтому первый же рендер после истечения кулдауна
уведомит (проверено тестом: тот же 91% при `COOLDOWN_MIN=0` даёт уведомление).

### 3.3 `null` — отдельно

`used_percentage: null` (начало сессии и после `/compact`, пока следующий вызов API не
заполнит поле): бар не рисуется, состояние не пишется, решение о пороге не принимается.
Трактовка `null` как `0%` сбрасывала бы полосу вниз на каждом старте — это и есть дефект,
который контракт `// empty` (а не `// 0`) закрывает.

## 4. Ноль подпроцессов-сирот + живая доставка

- Офлайн-серия (§3, обе конфигурации, 16 рендеров): `pgrep -P 1 -f fake-notify.sh` — **пусто**.
- Юнит-тест `test_no_orphan_notifier_processes` держит это свойство в регрессе.
- Живой прогон РЕАЛЬНОГО `hooks/notify/notify.sh` (один переход 40% → 81%): уведомление
  доставлено, `DEBUG=true` записал `notify: отправлено «Контекст 81% — пройден порог 80%…»`,
  `pgrep -P 1 -f 'notify\.sh'` — **пусто**, процесс доставки к моменту проверки завершён.
- Отмена in-flight (первый режим отказа практики) наблюдать на этом item'е было нечем:
  рендер занимает ~5 мс против 300 мс дебаунса — окно, в котором рантайм отменяет скрипт,
  на такой длительности не воспроизводится. Свойство закрыто **конструкцией**, а не
  наблюдением: доставка отсоединена (`setsid … &`), состояние пишется атомарно (`tmp`+`mv`),
  и тест `test_state_is_per_session_and_atomic` проверяет отсутствие `*.tmp`-остатков.
  Формулировать это как «проверено на живой отмене» было бы неправдой.

## 5. Что осталось за границей замера

- Латентность снята на ОДНОЙ машине — «на моей машине быстро» замером не является для
  чужих машин; порог приёмки поэтому и держится в ТЗ, а не выводится из результата.
- Поведение desktop-бэкендов кроме Linux `notify-send` не проверялось: доставка
  переиспользует существующий `notify.sh`, чья кросс-платформенная ветка (macOS/WSL) была
  написана и проверена ранее и этим item'ом не менялась.
