# Roadmap: красная валидация не должна автоматически запускать redesign

**Статус:** ⬜ к внедрению. **Дата инцидента:** 2026-08-14.
**Источник:** owner feedback в `insiders`; полевой запуск `task:plan-run`.
**Владельцы:** `packages/task` (канонические команды, classifier и journal),
`packages/skiller` (провайдерские проекции и parity).

## Что произошло

В проекте `/home/vostrikov/sibintek/projects/insiders` запускался план
`2026.07.30-SITE-HARDENING`, item `P6.5` — перенос решения о версиях ПДн из
`InsiderStoreRepository` в два Action. Его собственная реализация уже была в
commit `3e2f6811`, а дополнительный guard закрытых полей — в `07b7ca94`.

Declared feature-тесты, task regression gate, repository scan и Pint были зелёными.
Полный PHPStan обнаружил десять ошибок в другом vertical slice: `P6.4` commit
`1a0ca495` добавил PHPDoc `array<int, Role>` в
`CreateUserData`/`UpdateUserData` без import `App\\Enums\\User\\Role`, а два
Filament mapper-а оставили невыводимый тип `collect()`.

Это четыре локализованных PHP-файла и детерминированная типовая правка: нет
изменения schema, public/frozen contract, прав доступа, зависимости, generated asset,
архитектурной границы или acceptance. Тем не менее исполнитель записал
`local-repair`, затем ошибочно рекомендовал `task:plan-design ... P6.4` и оставил
`P6.5` незавершённым. Результат — ложный stop, лишняя холодная сессия и задержка
уже проверенного product item.

## Полная decision trace

1. `P6.5` был запущен в `task:plan-run` с provider-bound маршрутом
   `implementation/high`; Task Contract вернул `pre_mutation=allow`.
2. Изолированная тестовая БД `insiders_test` была проверена; declared tests дали
   `7 passed, 2 skipped`, domain regression gate — `10 passed`, Pint — green.
3. `vendor/bin/phpstan analyse --memory-limit=1G` вернул десять ошибок, все в
   `app/Dto/Users/{CreateUserData,UpdateUserData}.php` и
   `app/Filament/Resources/Users/Pages/{CreateUser,EditUser}.php`.
4. `git blame` связал первичный дефект с `1a0ca495` (`fix(filament): сделать
   mapper ролей чистым (P6.4)`), а не с P6.5. Ошибка воспроизводима и имеет
   узкий repair.
5. `packages/task/commands/plan-exec.md` уже требует
   `observe → minimal reproduce → classify → act → verify`; для
   `unrelated-pre-existing` предписаны safe fallback/local reversible repair в
   том же attempt. Раздел Validation требует local repair и повтор исходного
   carrier, а `plan-design` оставляет только для authority/frozen/public contract,
   неясной архитектуры, security/data boundary, migration либо изменённой acceptance.
6. Исполнитель ошибочно превратил `path ∉ Files` в необходимость redesign. Это
   противоречит канону и записи
   [`2026.08.11-local-repair-vs-escalation-classifier.md`](2026.08.11-local-repair-vs-escalation-classifier.md),
   где `Files` — не автоматический terminal gate.

## Что хочет получить владелец

Если declared validation нашла малый, локальный и безопасный defect, агент должен
сам довести исходную задачу до зелёного результата в том же authoritative root.
Нужно сохранить честную полную валидацию, provenance и видимость факта repair, но
не создавать `Blocked`, отдельный design loop или требовать повторного owner decision
из-за опечатки, import-а, узкой типизации либо другого доказуемо bounded repair.

`plan-design` остаётся исключением: он нужен только когда repair действительно
меняет решение/контракт/границу либо его безопасность и acceptance нельзя доказать
локально. «Файл принадлежит закрытому соседнему item» сам по себе таким основанием не является.

## Варианты решения

### A. Только уточнить prose

Явно добавить в `plan-exec.md`/`plan-run.md`: bounded repair может касаться
локализованного файла вне текущего `Files`; его выполнение не требует redesign.

Плюс: дешёво. Минус: текущая команда уже несёт эту семантику, поэтому prose-only не
защищает от повторного неверного вывода исполнителя.

### B. Structured repair classifier и исполнимый continuation gate — рекомендовано

Ввести `validation-repair/v1`: signal, affected paths, provenance, material-surface
checklist, original carrier, pre/post result и bounded diff. Когда все predicates
зелёные, reducer выдаёт exact action `repair-in-current-attempt`; launch/handoff не
могут печатать `plan-design`. После repair обязательно повторяется тот же carrier.

Для изменения за пределами `Files` record остаётся process provenance, а closing
status определяет только фактический material diff; ответственность закрытого
соседнего item фиксируется attribution, но не останавливает текущий product work.

### C. Scoped baseline для PHPStan

Сравнивать результат с сохранённым baseline и не блокировать на старых ошибках.

Не рекомендовано как единственная мера: baseline легко скрывает регрессии. Допустим
лишь как diagnostic complement к варианту B, если новые ошибки надёжно отделены от
исторических и original carrier всё равно запускается полностью.

### D. Автоматически чинить любой внешний файл

Отклонено: это сняло бы scope guard и позволило бы замаскировать material change.
Автоматизировать можно только classification и exact continuation, не произвольное
расширение mutations.

## Acceptance

- Fixture, эквивалентная incident P6.5: green item validation кроме четырёх
  PHPStan type errors из committed соседнего slice. Classifier выбирает
  `repair-in-current-attempt`, repair выполняется, тот же PHPStan carrier green и
  item закрывается без `plan-design`/`Blocked`.
- Import/annotation/локальный generic repair вне `Files` проходит только с
  evidence всех predicates и оставляет journal provenance; repair с migration,
  policy, public/frozen API, generated asset или security semantics продолжает
  fail-closed escalation path.
- Canonical command, Codex/Claude projections, installed package и launch-block
  имеют одинаковую семантику; parity test ловит старую формулировку или
  `plan-design` recommendation для qualified local repair.
- Regression: красный original carrier никогда не заменяется baseline-only зеленью;
  после repair повторяется ровно исходная команда и сохраняется её фактический output.

## Критерий внедрения

Следующий item, меняющий `packages/task/commands/plan-exec.md`, `plan-run.md`,
repair reducer либо provider projections, обязан реализовать вариант B и его
fixtures. До этого каждый такой incident исправляется продолжением текущего item,
а не redesign по одному факту красного static-analysis carrier.

## Повторный полевой инцидент: swissknifeman P6.2, 2026-08-16

`2026.08.02-PROVIDER-CONTRACT-LOCALE` P6.2 завершил свой product candidate и получил
green Core, Skiller, mAInd и focused Harness checks. Полный объявленный Harness carrier
воспроизвёл пять одинаковых `TERMINAL_EVIDENCE_REQUIRED` ошибок в
`packages/harness/tests/test_run_journal.py`. Тот же набор `20 tests / 5 errors`
воспроизвёлся на чистом `HEAD`, то есть evidence уже доказывал
`unrelated-pre-existing`, а не регрессию P6.2.

Несмотря на это executor записал capsule с
`signal_class=acceptance-failure`, `scope_coverage=outside-scope`. Существующий reducer
детерминированно вернул для него `terminal-block`; distinct reviewer подтвердил уже
переданную ему неверную premise. Если в том же capsule заменить только signal class на
доказанный evidence класс `unrelated-pre-existing`, тот же
`task.plan_blocking.evaluate()` возвращает `continue-local-repair` /
`LOCAL_REPAIR_REQUIRED`. После terminal append executor дополнительно, уже вне reducer,
сам выбрал handoff `task:plan-design ... P6.2`.

Это уточняет остаток реализации:

1. `block-candidate/v1` сейчас валидирует enum и форму, но не согласованность
   `signal_class` с baseline/provenance evidence. Clean-HEAD reproduction не может быть
   превращена в `acceptance-failure` только из-за того, что общий carrier обязателен.
2. `terminal-block` означает лишь доказанное право остановить текущий write boundary. Он
   не является автоматическим доказательством, что следующий шаг — redesign.
3. Перед `design-item|design-phase` handoff нужен отдельный
   `design-justification/v1` из
   [`2026.08.15-checkpoint-repair-without-redesign.md`](2026.08.15-checkpoint-repair-without-redesign.md):
   новый decision surface, evidence gap, alternatives и expected decision artifact.
   Без него continuation остаётся `repair-in-current-attempt`/`continue-root`.
4. Reviewer обязан проверять не только наличие boundary evidence, но и соответствие
   выбранного signal/scope class наблюдаемому baseline. Подтверждение capsule не делает
   ошибочную классификацию независимым фактом.

### Дополнительная приёмка по P6.2

- Fixture загружает P6.2-style evidence: полный carrier red, focused item checks green,
  тот же failure fingerprint воспроизводится на чистом `HEAD`. Единственный допустимый
  исход до bounded repair — `repair-in-current-attempt`, не `terminal-block`.
- Schema/reducer отвергают либо нормализуют сочетание clean-baseline reproduction с
  `signal_class=acceptance-failure`, если нет доказанного candidate delta.
- `terminal-block` без отдельного `design-required` carrier не может породить
  `plan-design` handoff; lint/delivery отвергают такую recommendation.
- Harness driver/Task journal compatibility repair повторяет исходный полный Harness
  carrier. Изменение старых driver result mappings не расширяет P6.2 product contract и
  не требует отдельного design item.
