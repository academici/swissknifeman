# Рабочий процесс «Лучшие практики Vue»

Используйте этот скилл как набор инструкций. Следуйте рабочему процессу по порядку, если только пользователь явно не попросит другой порядок.

## Основные принципы
- **Делайте состояние предсказуемым:** один источник истины, всё остальное выводите из него.
- **Делайте поток данных явным:** в большинстве случаев — пропсы вниз, события вверх (Props down, Events up).
- **Предпочитайте маленькие, сфокусированные компоненты:** их легче тестировать, переиспользовать и сопровождать.
- **Избегайте лишних перерисовок:** разумно используйте вычисляемые свойства (computed) и наблюдатели (watcher).
- **Читаемость важна:** пишите ясный, самодокументируемый код.

## 1) Подтвердите архитектуру до написания кода (обязательно)

- Стек по умолчанию: Vue 3 + Composition API + `<script setup lang="ts">`.
- Если проект явно использует Options API, загрузите скилл `vue-options-api-best-practices`, если он доступен.
- Если проект явно использует JSX, загрузите скилл `vue-jsx-best-practices`, если он доступен.

### 1.1 Обязательные к прочтению основные справочники (обязательно)

- Перед реализацией любой задачи на Vue обязательно прочитайте и примените эти основные справочники:
  - `references/reactivity.md`
  - `references/sfc.md`
  - `references/component-data-flow.md`
  - `references/composables.md`
- Держите эти справочники в активном рабочем контексте на протяжении всей задачи, а не только когда возникает конкретная проблема.

### 1.2 Спланируйте границы компонентов до написания кода (обязательно)

Для любой нетривиальной фичи перед реализацией составьте краткую карту компонентов.

- Определите единственную зону ответственности каждого компонента одним предложением.
- По умолчанию держите входной/корневой компонент и компоненты-представления уровня маршрута как поверхности композиции (composition surfaces).
- Выносите UI фичи и логику фичи из входного/корневого/представляющего компонентов, если только задача намеренно не является крошечным однофайловым демо.
- Определите контракты props/emits для каждого дочернего компонента в карте.
- Предпочитайте раскладку по папкам фич (`components/<feature>/...`, `composables/use<Feature>.ts`), когда добавляете больше одного компонента.

## 2) Примените базовые основы Vue (обязательно)

Это базовые, обязательные к знанию основы. Применяйте их все в каждой задаче на Vue, используя основные справочники, уже загруженные в разделе `1.1`.

### Реактивность

- Обязательный справочник из `1.1`: [reactivity](references/reactivity.md)
- Держите исходное состояние минимальным (`ref`/`reactive`), всё возможное выводите через `computed`.
- При необходимости используйте наблюдатели (watcher) для побочных эффектов.
- Избегайте повторного выполнения дорогой логики в шаблонах.

### Структура SFC и безопасность шаблонов

- Обязательный справочник из `1.1`: [sfc](references/sfc.md)
- Держите секции SFC в таком порядке: `<script>` → `<template>` → `<style>`.
- Держите ответственность SFC сфокусированной; разбивайте большие компоненты.
- Держите шаблоны декларативными; перенесите ветвления/вывод значений в скрипт.
- Применяйте правила безопасности шаблонов Vue (`v-html`, рендеринг списков, выбор способов условного рендеринга).

### Держите компоненты сфокусированными

Разбивайте компонент, когда у него **более одной чёткой зоны ответственности** (например, оркестрация данных + UI, или несколько независимых секций UI).

- Предпочитайте **меньшие компоненты + композаблы** одному «мега-компоненту».
- Выносите **секции UI** в дочерние компоненты (пропсы внутрь, события наружу).
- Выносите **состояние/побочные эффекты** в композаблы (`useXxx()`).

Применяйте объективные триггеры для разбиения. Разбивайте компонент, если истинно **любое** из условий:

- Он владеет одновременно оркестрацией/состоянием и существенной презентационной разметкой для нескольких секций.
- В нём 3+ различных секций UI (например: форма, фильтры, список, футер/статус).
- Блок шаблона повторяется или мог бы стать переиспользуемым (строки элементов, карточки, записи списка).

Правило для входного/корневого компонента и представления маршрута:

- Держите входной/корневой компонент и представления маршрута тонкими: оболочка/лейаут приложения, подключение провайдеров и композиция фич.
- Не размещайте полные реализации фич во входном/корневом/представляющем компонентах, когда эти фичи содержат независимые части.
- Для CRUD/списочных фич (todo, таблица, каталог, входящие) разбивайте как минимум на:
  - компонент-контейнер фичи
  - компонент ввода/формы
  - компонент списка (и/или элемента)
  - компонент футера/действий или фильтра/статуса
- Допускайте однофайловую реализацию только для очень маленьких одноразовых демо; если выбрана она — явно обоснуйте, почему разбиение не нужно.

### Поток данных в компонентах

- Обязательный справочник из `1.1`: [component-data-flow](references/component-data-flow.md)
- Используйте «пропсы вниз, события вверх» как основную модель.
- Используйте `v-model` только для настоящих двунаправленных контрактов компонента.
- Используйте provide/inject только для зависимостей в глубине дерева или общего контекста.
- Держите контракты явными и типизированными с помощью `defineProps`, `defineEmits` и `InjectionKey` по мере необходимости.

### Композаблы

- Обязательный справочник из `1.1`: [composables](references/composables.md)
- Выносите логику в композаблы, когда она переиспользуется, содержит состояние или насыщена побочными эффектами.
- Держите API композаблов маленьким, типизированным и предсказуемым.
- Отделяйте логику фичи от презентационных компонентов.

## 3) Рассматривайте опциональные возможности только когда их требуют требования

### 3.1 Стандартные опциональные возможности

Не добавляйте их по умолчанию. Загружайте соответствующий справочник только когда требование существует.

- Слоты: родителю нужно управлять содержимым/лейаутом дочернего компонента -> [component-slots](references/component-slots.md)
- Сквозные атрибуты (fallthrough): обёрточные/базовые компоненты должны безопасно пробрасывать атрибуты/события -> [component-fallthrough-attrs](references/component-fallthrough-attrs.md)
- Встроенный компонент `<KeepAlive>` для кэширования представлений с состоянием -> [component-keep-alive](references/component-keep-alive.md)
- Встроенный компонент `<Teleport>` для оверлеев/порталов -> [component-teleport](references/component-teleport.md)
- Встроенный компонент `<Suspense>` для границ запасного содержимого асинхронного поддерева -> [component-suspense](references/component-suspense.md)
- Возможности, связанные с анимацией: выбирайте простейший подход, соответствующий нужному поведению движения.
  - Встроенный компонент `<Transition>` для эффектов появления/исчезновения -> [transition](references/component-transition.md)
  - Встроенный компонент `<TransitionGroup>` для анимированных изменений списка -> [transition-group](references/component-transition-group.md)
  - Анимация на основе классов для эффектов, не связанных с появлением/исчезновением -> [animation-class-based-technique](references/animation-class-based-technique.md)
  - Анимация, управляемая состоянием, для анимации, управляемой пользовательским вводом -> [animation-state-driven-technique](references/animation-state-driven-technique.md)

### 3.2 Менее распространённые опциональные возможности

Используйте их только при наличии явной продуктовой или технической необходимости.

- Директивы: поведение специфично для DOM и плохо ложится на композабл/компонент -> [directives](references/directives.md)
- Асинхронные компоненты: тяжёлый/редко используемый UI следует загружать лениво -> [component-async](references/component-async.md)
- Render-функции — только когда шаблоны не могут выразить требование -> [render-functions](references/render-functions.md)
- Плагины — когда поведение должно устанавливаться на уровне всего приложения -> [plugins](references/plugins.md)
- Паттерны управления состоянием: общее для всего приложения состояние пересекает границы фич -> [state-management](references/state-management.md)

## 4) Выполняйте оптимизацию производительности после того, как поведение стало корректным

Работа над производительностью — проход после реализации функциональности. Не оптимизируйте до того, как основное поведение реализовано и проверено.

- Узкие места рендеринга больших списков -> [perf-virtualize-large-lists](references/perf-virtualize-large-lists.md)
- Статические поддеревья перерисовываются без необходимости -> [perf-v-once-v-memo-directives](references/perf-v-once-v-memo-directives.md)
- Чрезмерная абстракция на горячих путях списков -> [perf-avoid-component-abstraction-in-lists](references/perf-avoid-component-abstraction-in-lists.md)
- Дорогие обновления срабатывают слишком часто -> [updated-hook-performance](references/updated-hook-performance.md)

## 5) Финальная самопроверка перед завершением

- Основное поведение работает и соответствует требованиям.
- Все обязательные к прочтению справочники были прочитаны и применены.
- Модель реактивности минимальна и предсказуема.
- Соблюдены структура SFC и правила шаблонов.
- Компоненты сфокусированы и хорошо разложены, с разбиением там, где это нужно.
- Входной/корневой компонент и представления маршрута остаются поверхностями композиции, если нет явного исключения для маленького демо.
- Решения о разбиении компонентов явны и обоснованны (границы ответственности чёткие).
- Контракты потока данных явны и типизированы.
- Композаблы используются там, где это оправдано переиспользованием/сложностью.
- Состояние/побочные эффекты вынесены в композаблы, если применимо.
- Опциональные возможности используются только когда их требуют требования.
- Изменения производительности применены только после того, как функциональность была завершена.
