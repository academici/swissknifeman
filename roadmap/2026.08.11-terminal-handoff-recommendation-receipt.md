# Roadmap: terminal handoff recommendation receipt

**Статус:** 🟡 Task receipt и provider contract реализованы планом
`2026.08.12-№1-TASK-RESILIENCE`; остаток — runtime/harness проверка фактического final transcript.
**Владельцы:** `packages/task`, provider adapters и runtime/harness, который видит финальный
ответ. **Не владелец:** только prompt-текст отдельного проекта.

## Симптом

Исполнитель записал корректный `plans/<ID>/handoff.md`, включая `Next` и полный native Codex
launch-block для P3.3. Финальный ответ сообщил лишь «P3.1/P3.2 done; Next P3.3» и не вынес
результат-зависимую рекомендацию, причину следующего шага или копипастопригодную команду.
Владелец получил формальное закрытие без управляемого продолжения.

Это не дефект результата P3.1/P3.2: свежий runtime был принят владельцем. Дефект — разрыв
между durable handoff и chat terminal delivery.

## Точная причина

1. `handoff.md` и plan-lint проверяют сохранённое состояние плана, но не содержимое финального
   сообщения агента.
2. `plan-exec` уже требовал launch-block в expected output, однако это был prompt-only контракт:
   нет receipt, связывающего terminal response с только что сохранённым `handoff.Next`.
3. Provider renderer добавлял статичное правило native launch-block, но не предписывал
   перечитывание фактического handoff непосредственно перед `final`.
4. Краткий финал агента therefore может опустить рекомендацию, не ломая ни commit, ни plan-lint.

## Решение

Ввести provider-neutral `terminal-handoff-recommendation@v1` и машинный receipt.

1. После final handoff write команда строит structured record из **сохранённого** `handoff.md`:
   plan ID, closed subject, status, exact `Next`, launch command/prompt, route, rationale
   (Remaining/Open risks/Known Deviations/Pending Work), commit SHA и handoff digest.
2. Terminal response обязан вывести отдельную метку `Рекомендация следующего шага:` и exact
   recommendation из record; bare `Next Pn.m` запрещён. Для terminal plan допустим только
   явно записанный owner-selected next step.
3. Provider projections Codex и Claude получают один canonical contract; native Codex block
   остаётся дополнительным представлением той же recommendation, а не второй истиной.
4. Runtime/harness, который получает final transcript, валидирует receipt against handoff digest.
   Отсутствие, stale digest или отличие Next дают `HANDOFF_RECOMMENDATION_MISSING` и не позволяют
   пометить run completed.
5. Контракт применяется ко **всем** terminal outcomes task-команд: green, deviation, blocked,
   phase close и terminal plan/archive (последнему — с допустимой owner-choice формой).

## Приемка

- fixtures для green, deviation, blocked, phase close и terminal plan доказывают, что receipt
  содержит exact handoff `Next`, корректный route/command и результат-зависимую причину;
- missing, stale или mismatched Next даёт `HANDOFF_RECOMMENDATION_MISSING`;
- transcript fixture с кратким «Next Pn.m» без recommendation не проходит;
- Codex и Claude generated projections содержат одинаковый provider-neutral contract;
- `plan-lint` продолжает проверять durable handoff, а новый runtime check проверяет delivery;
- архивный terminal plan не выдумывает новую команду: receipt явно сообщает, что следующий план
  выбирает владелец.

## Первые точки изменения

- `packages/task/commands/plan-exec.md`, `plan-close.md`, `plan-design.md`, `plan-audit.md`;
- `packages/task/lib/task/command_render.py` и provider projection tests;
- task run-report / harness terminal-transcript seam, который способен проверить фактический
  final response, а не только prompt;
- fixtures plan handoff и `packages/task/scripts/validate.sh`.

## Доказательства

- Agelto commits `70a28a7a` (P3.1) и `a7d6f93d` (P3.2);
- `agelto/plans/2026.08.09-RELEASE-READINESS/handoff.md` после P3.2 содержит native Codex
  launch-block P3.3;
- до этой записи source contract не связывал final response с persisted handoff, поэтому
  успешные plan checks не могли обнаружить пропуск.

## Реализовано 2026-08-12

`task.plan_delivery` строит и проверяет receipt с exact persisted `Next`, route, result-dependent
recommendation, terminal status, commit SHA и handoff/state/closure digests. Missing/stale/mismatch
даёт `HANDOFF_RECOMMENDATION_MISSING` или `STALE_TERMINAL_RECEIPT`; пять canonical команд,
Claude golden и Codex projections требуют точную метку `Рекомендация следующего шага:`.

Остался один внешний seam: harness/provider должен сопоставить фактический final transcript с
receipt до run-completed. До появления такого lifecycle hook prompt/Task-уровень доказан, но
transport-level acceptance «краткий final не проходит» честно не считается закрытым.
