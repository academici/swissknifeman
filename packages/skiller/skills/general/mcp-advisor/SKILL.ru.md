# MCP Advisor — обоснованный подбор MCP-серверов под проект

Профили и онбординг прикручивают MCP **статично** (почти всем — только `context7`, фронту — ещё
`playwright`). Этот скилл закрывает пробел: при добавлении/синке проекта **проанализировать сигналы и
предложить** недостающие серверы (или явно сказать «не нужно») — а не подключать всё подряд.

## Когда активировать

- Онбординг/добавление проекта в экосистему: `maind onboard`, `skiller integrate`, шаг настройки MCP.
- Синхронизация/ресинк проекта; правка `.mcp.json`; вопрос «какие MCP подключить этому проекту».
- Смена стека или характера задач (появился UI → нужен браузер; пошла работа с GitHub → нужен gh/github).

## Принцип: каждый сервер не бесплатен

MCP-сервер — это **постоянный налог**, не «бесплатная фича»:
- его **схема инструментов грузится в КАЖДЫЙ запрос** (контекст-токены), даже если не используется;
- требует **permissions** (доступ к сети/ФС/токенам) — поверхность риска;
- многие тянут **Node/uvx-зависимость** (`npx`/`uvx` ставят пакет при первом запуске).

Правило: подключай **по доказанной необходимости**, не «на всякий случай». Неиспользуемый 7+ дней —
отключай (см. `context-economy` §5). Где хватает CLI (`gh`, `git`) — предпочитай CLI серверу.

## Алгоритм подбора

1. **Собери сигналы проекта:** тип/стек (laravel · node-frontend · python-backend · package · vault ·
   standalone), роль (backend · frontend · maintainer/reviewer · author), типы задач (UI/E2E · работа с
   GitHub · свежие внешние доки/API · сложное многошаговое планирование · экосистемная память/граф).
2. **Пройди по карте** ниже: для каждого сервера — нужен / не нужен / решить, с одной строкой обоснования.
3. **Выдай memo «MCP план подключения»:** три списка — **Рекомендуется** (с причиной), **Не нужно** (с
   причиной), **Решить** (зависит от ответа пользователя). Для рекомендованных укажи способ подключения:
   профиль skiller (`mcp[]`) → раздаётся `harness`, либо ручная запись в `.mcp.json` проекта.
4. **Подтверди у пользователя** перед записью — подключение MCP меняет окружение и permissions.

## Карта серверов (меню = каталог harness + хаб maind)

| Сервер | Транспорт | Подключать когда | Зачем | НЕ нужен когда | Цена |
|---|---|---|---|---|---|
| **context7** | http | почти любой кодовый проект с фреймворком/библиотеками | живые доки версий библиотек (вместо устаревшего знания) | vault, чистая инфра без кода | низкая (http, без локальных deps) |
| **playwright** | npx `@playwright/mcp --headless` | фронт с UI, E2E-тесты, скриншоты страниц | управление браузером, проверка верстки | backend/CLI/библиотека без UI | Node + загрузка браузеров |
| **github** | http | активная работа с GitHub: PR/issue/Actions/releases, роль maintainer/reviewer | богатая интеграция платформы как инструменты | проект не на GitHub; рутинный review (хватает `gh` CLI — дешевле, см. `gh-review`) | auth-токен + permissions |
| **fetch** | uvx `mcp-server-fetch` | нужны свежие веб-доки/внешние API, не покрытые context7 | загрузка URL/страниц в контекст | context7 уже покрывает доки | uvx-deps, сеть |
| **perplexity** | npx `@perplexity-ai/mcp-server` (+`PERPLEXITY_API_KEY`) | верификация «текущих фактов/рынка/ещё-актуально/современный подход» вне доков библиотек; research | веб-поиск с синтезом и цитатами | хватает context7 (доки) или известного URL (fetch); нет ключа → keyless `perplexity-web` (демон v1.3.0: параллельные вкладки, изоляция проектов через `--pool=<проект>`) | Node + API-key |
| **sequential-thinking** | npx | сложное многошаговое планирование/ризонинг | структурный «блокнот рассуждения» | рутинные/короткие задачи | Node + токены на каждый вызов |
| **filesystem** | npx | редкий случай: мульти-рут/особый доступ к ФС | расширенный доступ к файлам | **обычно избыточен** — у Claude Code родной доступ к ФС | Node |
| **memory (generic)** | npx `server-memory` | **в экосистеме academici — НЕ использовать** | — | всегда: память идёт через хаб `maind` | конфликт с каноном памяти |
| **maind (хаб)** | per-project, из `.mcp.json` онбординга | онбордженные проекты экосистемы | память (scope-изоляция) + граф связей + проекты/links | разовый внешний проект без онбординга | уже стоит после `maind onboard` |

**Важный нюанс памяти.** В экосистеме academici память и граф идут **через сервер `maind`**
(`MODE=maind`, инструменты `maind_memory_*` / `maind_graph_*`), а **не** через сырой `memory`-MCP и не
через прямой agentmemory. Generic `memory` не предлагать — он дублирует/конфликтует с хабом.

**GitHub: `gh` CLI vs `github` MCP.** Для рутинного review/handoff дешевле `gh` CLI (минимальный срез:
`gh pr diff`, `gh pr view --comments`) — см. `oss-dev/gh-review`. Полноценный `github` MCP — когда нужна
именно инструментальная интеграция платформы в агенте (массовые операции, Actions, секреты).

## Профильные дефолты (отправная точка, не потолок)

Профили skiller сейчас дают: `context7` — всем кодовым типам; `+playwright` — `node-frontend`. Адвайзер
**дополняет** под роль/задачи: `github` — для oss/maintainer и пакетов; `fetch` — где нужна свежая внешняя
дока/API; `sequential-thinking` — под сложные задачи. Базовый набор оставляй минимальным.

## Прополка резидентного MCP (аудит уже подключённого)

Подбор (выше) — про добавление. Симметричный ритуал — про то, что УЖЕ висит в `.mcp.json` проекта:

1. **Аудит:** `skiller budget --first-turn --target <path>` → строка MCP отчёта (список серверов + ток
   по eager-модели `budget.py::_measure_mcp`). Каждый резидентный сервер сверяй с картой выше: подключён
   по сигналу проекта (стек/роль/задачи) или «раньше подключили, сигнал сейчас не выполняется»?
2. **Правило «1–2 сервера на задачу».** Типовая сессия использует 1–2 MCP из подключённого набора
   (остальные — молчаливый резидентный «налог» на все запросы). Больше 4–5 серверов у некрупного
   проекта без явного мульти-доменного стека — сигнал для ревью владельца, не автоматическое отключение.
3. **Caveat про tool search:** first-party Claude Code CLI держит tool search / deferred MCP-loading
   **включённым по умолчанию** — резидентны summaries + per-server instructions, не полные tool-схемы;
   `_measure_mcp` считает EAGER-потолок (полные схемы), это **не** факт резидента на типовом прогоне.
   Не заявляй экономию прополки на eager-числе («отключение сервера X сэкономит N ток») — цифра честная
   только как верхняя граница при выключенном/недоступном tool search. Прополка не бесполезна (сервер
   всё равно = summary-строка + permissions-поверхность + Node/uvx-деп), но ROI ниже заявленного eager-
   потолком.
4. **Кандидат на отключение** — сервер, для которого ни один сигнал карты («Подключать когда») не
   выполняется 7+ дней подряд (см. `context-economy` §5) — предложи владельцу проекта отключение с
   причиной, не отключай молча.

## Чеклист качества

- [ ] Собраны сигналы: стек, роль, типы задач — рекомендация обоснована ими, а не «по умолчанию всё».
- [ ] Каждый рекомендованный сервер имеет причину; каждый отклонённый — причину отказа.
- [ ] Учтена цена: схема в каждом запросе + permissions + Node/uvx-деп; «на всякий случай» не подключается.
- [ ] Память/граф — через `maind`; generic `memory`-MCP не предложен.
- [ ] Для рутинного GitHub-review предложен `gh` CLI, а не тяжёлый `github` MCP без нужды.
- [ ] Перед записью в `.mcp.json` — подтверждение пользователя.

## Связанные скиллы

- `context-economy` (general) — обратная сторона: аудит/обрезка уже подключённого (неиспользуемый MCP →
  отключить; схема грузится в каждый запрос). Этот скилл — про **подбор**, тот — про **сокращение**.
- `oss-dev/gh-review` — `gh`-driven review: когда GitHub-операции дешевле через CLI, чем через `github` MCP.
- `ai/ai-agents` — когда задача не «подключить готовый MCP», а **спроектировать собственный** MCP-сервер.
- `security/security` — ревью конфигов MCP-инструментов на инъекции/эксфильтрацию перед подключением.
- `architect/figma-mcp-core` — доменный частный случай (Figma Dev Mode MCP), вне общего подбора.
- `verify-claims` (general) — комплементарен: этот скилл про *что подключить* к проекту, тот про *когда и как доставать/верифицировать факт* через подключённые движки (context7/perplexity/web).
