## Selected forward fix

P3.4 becomes the forward owner of the narrow native-tool projection while preserving terminal
P3.1/P3.2/P3.3 history. The later item may edit both adapter modules and their unit tests because
their native argv construction is the only lawful home for provider semantics; the scheduler and
runner receive only typed admission-derived controls and never patch argv after the mapper.
RAG:— (repo-grounded: D34/D36/D74/D77 and current adapter/scheduler boundaries).

The activity binding passes the exact, ordered admission `permissions.tools` as a separate
provider-native control outside the closed `worker-envelope-v1` request. It does not add a field to
the frozen neutral envelope and cannot obtain tools from ambient config, prompt text or a provider
default. Each adapter validates the control before argv construction:

- Claude: the empty tuple maps to literal `--tools ""`; `--allowedTools` is omitted because there
  is nothing to auto-approve. Any non-empty list not already proven by a later owner-bound business
  contract refuses instead of being guessed during P3.4.
- Codex: the exact empty tuple returns `CAPABILITY_UNSUPPORTED` before process launch. `read-only`,
  `features.shell_tool=false`, a prompt prohibition or an untrusted transient hook cannot substitute
  for a documented global no-tool availability boundary.

RAG:✅ 2026-08-04 exact installed/first-party CLI evidence in
`findings/P3.4-native-no-tool-verification-2026-08-04.md`.

## Readiness versus item completion

The two indexed admissions must each produce one minimized readiness row. A row may be non-green
for `CAPABILITY_UNSUPPORTED`, `MAPPING_UNKNOWN`, missing binary/auth/quota or another frozen exit;
that is the measured capability result, not a validation relaxation. The item is complete only if
the runner/activity implementation, fake-binary fault/privacy suite, exact pre-launch refusal,
project-delta proof, two-row aggregate and all upstream validators are green. Neither provider is
called when its preflight is non-green. Capability maturity and item status remain separate.
RAG:— (repo-grounded: plan-protocol status/maturity split, P3.4 acceptance and D74 evidence goal).

The installed Claude version is `2.1.221`, while terminal P3.2 pins `2.1.220`. P3.4 must record
`MAPPING_UNKNOWN`/non-green readiness and zero process for that drift. Repinning would require a new
provider probe/parity decision and is outside this remediation; accepting the newer help as proof
for the older mapper would be evidence laundering. RAG:✅ 2026-08-04 local version evidence in the
finding above.

## Rejected alternatives

- Widen D77/P1.6 tools to `Read,Glob,Grep`: changes frozen owner authority to fit implementation.
- Strip or rewrite argv in `worker.py`: duplicates provider semantics outside the adapter.
- Treat Codex `read-only` as no-tool: it still permits reads and does not prove tool unavailability.
- Disable a guessed list of Codex feature flags: absence of a global closed inventory leaves a
  fail-open remainder.
- Repin Claude to the current binary inside P3.4: invalidates terminal probe/version evidence
  without the owning P0/P3 parity pass.

## DoR consequences

`Not started`, P3 returns to `In progress`, and the next executable step is the existing
manual `implementation/high` item. P1/P2 contracts, tasks, grants, admissions and terminal item
histories remain byte- and status-stable.
