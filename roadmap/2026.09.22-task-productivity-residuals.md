# Roadmap: остаток аудита производительности Task после быстрого ремонта

**Статус:** 🟡 отложенные изменения требуют измерений или продуктового решения владельца.

**Источник:** `audits/2026-09-22-perplexity-2.md`.

**Формат:** это обычный roadmap-carrier, а не Task plan. Он не активирует Task workflow,
не задаёт порядок исполнения и не требует довести перечисленные идеи до реализации одним
пакетом.

## Зачем сохранён этот остаток

В сессии 2026-09-22 были напрямую реализованы изменения с понятной локальной выгодой:
убраны повторная подготовка и лишний snapshot на normal path, запись generated carriers
перенесена после admission, terminal reconciliation перестала перестраивать всю закрытую
историю, сокращён двойной write pass design finalization, review и `plan-run` упрощены,
Phase Assurance получила неявный default, неизвестные `risk_tags` разрешены, exact final
rendering стал условным, а PR-матрица Python сокращена до 3.9/3.11/3.13.

Ниже перечислено только то, что сознательно не сделано. Общий критерий возврата к этим
темам: есть измеримый повторяющийся расход или полевой сбой, который нельзя дешевле устранить
локальной правкой. Само наличие рекомендации во внешнем аудите таким триггером не является.

## 1. Полностью in-memory admission и design finalization

### Что не сделано

Normal path больше не выполняет раннюю materialization до admission и не повторяет полный
recovery prepare. Design finalization больше не выполняет второй полный rebuild states и
bundles. Однако runtime всё ещё не умеет представить все candidate states, bundles, status,
decisions и receipt как один неизменяемый объект, проверить его без файлов и затем записать
весь набор ровно одним проходом.

Не добавлен и предложенный аудитом публичный `PreparedAdmission` с полным набором digests.
Существующий flow передаёт только те данные, которые уже нужны текущим контрактам.

### Почему не сделано

Текущие lint, compiler и delivery paths местами читают канонические файлы. Полностью
in-memory flow потребует параллельных render/check API почти для каждой projection. Это
крупная архитектурная работа ради остатка стоимости, величина которого пока не измерена.
Кроме того, «одна запись» не будет настоящей транзакцией: journal и несколько projection
files нельзя атомарно зафиксировать одним filesystem operation.

### Сложности, которые придётся решить

- Единый versioned candidate format для state, status, decisions, bundles и receipt.
- Lint и handoff validation, принимающие bytes/objects без обязательной записи на диск.
- Digest, который связывает candidate с прочитанными journal, specs и route evidence.
- Повторная проверка candidate под lock без полного пересчёта.
- Порядок записи journal и projections при падении процесса посередине.
- Recovery, который различает допустимую незавершённую materialization и повреждение.
- Совместимость существующих CLI, тестовых fixtures и provider projections.

### Нужно обсудить

1. Какой фактический бюджет normal-path materialization считаем проблемой: wall time, число
   reads/writes или prompt/tool overhead?
2. Нужен ли общий candidate API либо достаточно точечно научить lint проверять ожидаемые bytes?
3. Считаем ли journal единственным durable commit point, после которого projections всегда
   разрешено лениво восстановить?
4. Оправдан ли новый `PreparedAdmission`, если он не устраняет filesystem transaction gap?

### Критерий запуска

Профиль минимум трёх реальных plan executions показывает, что оставшийся pre/post-event
projection pass входит в два крупнейших источника wall time или filesystem I/O.

## 2. Persistent incremental reconciliation index и dependency cache

### Что не сделано

Terminal reconciliation теперь локально перестраивает текущий item, но не создаёт предложенный
аудитом on-disk index с `journal_offset`, `latest_positions`, `state_input_digests` и
`reverse_dependencies`. `materialize_next_ready()` по-прежнему может разбирать specs и
зависимости при поиске следующего frontier.

### Почему не сделано

Durable cache сам становится состоянием, для которого нужны schema version, atomic update,
invalidation, recovery и правила конкурентного доступа. Без профиля длинных планов это может
добавить больше процедур и дефектов, чем сэкономить. Journal уже является источником истины;
второй authoritative-looking carrier повышает риск рассинхронизации.

### Сложности, которые придётся решить

- Явно определить, derived это cache или часть durable protocol.
- Версионировать schema и мигрировать либо безопасно удалять старые indexes.
- Обновлять offset и позиции атомарно относительно append-only journal.
- Обнаруживать truncation, rewrite, corrupt tail и concurrent append.
- Инвалидировать dependency graph при изменении phase/spec, Required Reads, Files и Deliverables.
- Обрабатывать rename/remove item и изменение plan layout.
- Определить порог, после которого выгоднее полный rebuild.
- Доказать, что cache miss/corruption всегда приводит к безопасной реконструкции, а не к
  ошибочному ready frontier.

### Нужно обсудить

1. Индекс должен жить в plan directory, machine-local cache или только в памяти процесса?
2. Можно ли всегда удалить индекс без потери поведения?
3. Нужны ли reverse dependencies постоянно или достаточно memoization на один invocation?
4. Какой размер плана и journal реально встречается во флоте?
5. Нужна ли отдельная recovery-команда или transparent rebuild достаточно?

### Критерий запуска

На реальном плане минимум с 30 terminal items время одного последующего closure либо число
повторных phase parses растёт заметно с длиной истории и превышает согласованный бюджет.

## 3. Дополнительное сокращение design context

### Что не сделано

Не введены dependency-closure filtering для baseline diagnostics, агрегат
`foreign_baseline_count/digest/details_command` и отдельное представление prose без item fields.
Также сохранена проверка lint при finalization, даже если lint уже запускался при получении
design context.

### Почему не сделано

В Layout v2 полный phase prose находится в `Pn.md`, а структурированные item contracts — в
отдельных `Pn.m.md`; это не буквальная двойная передача одного Markdown, как утверждает аудит.
Фильтрация diagnostics требует надёжно классифицировать global, current, dependency и foreign
ошибки. Ошибка фильтрации скроет actionable defect. Повторный lint после редактирования проверяет
уже другие входные bytes и потому не является автоматически лишним.

### Сложности, которые придётся решить

- Стабильная классификация lint diagnostics по ownership и dependency closure.
- Компактный response contract, который не теряет global authority/schema errors.
- Команда детализации, привязанная к digest агрегированных ошибок.
- Инвалидация baseline после любого изменения specs или routing.
- Измерение реальных bytes/tokens по частям context, а не только размера файлов.
- Гарантия, что prose, необходимый для интерпретации item, не исчезает при фильтрации.

### Нужно обсудить

1. Что именно доминирует в context: phase prose, item specs, handoff, routing или diagnostics?
2. Допустимо ли по умолчанию скрывать foreign diagnostics за digest?
3. Можно ли переиспользовать lint только при точном совпадении input digest?
4. Нужна ли model-facing details command либо достаточно файла с полным результатом?

### Критерий запуска

Замер минимум пяти design invocations показывает, что design context систематически превышает
согласованный бюджет, а один из перечисленных компонентов даёт не менее трети объёма.

## 4. Route ranges и owner budget

### Что не сделано

Не добавлен общий контракт `minimum/preferred/ceiling/owner_budget`, не реализованы правила
overshoot/undershoot внутри диапазона и миграция старых exact routes. Вместо этого default
`task:review` переведён на более дешёвый implementation/high route.

### Почему не сделано

Ranges меняют command-routing schema, catalog, route evidence, renderers, provider adapters,
fixtures, документацию и сохранённые Task contracts. Model class и reasoning effort — две
разные оси; простое сравнение «между minimum и ceiling» неоднозначно. Новый cost envelope
может сам стать тяжёлой политикой, которую приходится объяснять и подтверждать при каждом вызове.

### Сложности, которые придётся решить

- Полный порядок model classes и efforts, включая неизвестные будущие модели.
- Разница между advisory preferred и обязательными minimum/ceiling.
- Поведение `plan-run`, наследующего attested route.
- Provider-specific mapping, когда одинаковые классы моделей отсутствуют.
- Backward compatibility exact route в старых plans, receipts и journal events.
- Представление owner budget без выдуманной точности стоимости.
- Правила добровольного более дешёвого route и доказательство достаточности capabilities.
- Семантика overshoot, если более мощная модель уже запущена и дополнительной оплаты не требует.

### Нужно обсудить

1. Осталась ли реальная проблема после удешевления review и явного opt-in?
2. Должен ли `preferred` быть только подсказкой без admission semantics?
3. Нужен ли единый диапазон всем командам или достаточно risk modes для review/design?
4. Кто и где задаёт owner budget: invocation, project config или fleet default?
5. Как мигрировать существующие exact route receipts без переписывания истории?

### Критерий запуска

Есть минимум три полевых случая, где exact route либо вызвал измеримый лишний расход, либо
заблокировал достаточный доступный route, и локальная смена default не решает класс проблемы.

## 5. Явные режимы review

### Что не сделано

Не введены отдельные публичные modes `quick`, `standard`, `adversarial` с автоматическим выбором.
Review prompt и route стали легче, но остаются одной командой с адаптацией по фактическому риску.

### Почему не сделано

Три режима добавляют ещё один выбор, правила его вывода, override и тестовую матрицу. Для
маленького diff это может заменить прежнюю review-церемонию новой классификационной церемонией.
Сначала нужно проверить, достаточно ли текущей короткой risk-based инструкции.

### Сложности, которые придётся решить

- Наблюдаемые признаки режима без чтения всего репозитория заранее.
- Поведение при смешанном diff, например docs плюс migration.
- Право владельца ограничить время без ослабления hard boundary.
- Независимый verifier только там, где его вклад окупается.
- Совместимость command routing и provider capabilities.

### Нужно обсудить

1. Режим должен быть явным аргументом, автоматическим выводом или только внутренней эвристикой?
2. Какие surfaces безусловно переводят review в adversarial?
3. Нужен ли quick mode как отдельный контракт, если обычный review уже может закончиться одним
   проходом?

### Критерий запуска

Накоплены реальные reviews обоих типов: слишком дорогой для малого diff и недостаточный для
hard-risk diff. Для каждого известен конкретный пропущенный либо лишний этап.

## 6. Классы Validation: must, risk, diagnostic, live

### Что не сделано

Не расширен синтаксис Validation и не добавлены классы обязательности. Все существующие
declared validation carriers по-прежнему являются closure contract.

### Почему не сделано

Классификацию пишет design agent. Ошибочно помеченная `diagnostic` проверка может молча убрать
реальный acceptance gate, а ошибочный `must` лишь тратит время и заметен владельцу. Значит,
расширение без строгих правил создаёт асимметричный риск. Кроме того, исторические plans содержат
plain Validation, и для них нужен однозначный default.

### Сложности, которые придётся решить

- Grammar для fenced commands, prose checks и provider/live boundaries.
- Backward compatibility: вероятный безопасный default для plain entries — `must`.
- Связь `risk[...]` с фактическим impact текущего change set.
- Identity и evidence freshness для `live[...]`.
- Terminal admission: какие классы входят в обязательный receipt.
- Lint, projections, fixtures и migration без переписывания plan history.
- Право понизить уже объявленный `must` и видимость такого решения владельцу.
- Поведение diagnostics при красном результате: warning, finding или hard stop по содержанию?

### Нужно обсудить

1. Достаточно ли более простого optional marker для diagnostics вместо четырёх классов?
2. Кто может менять класс после design: исполнитель, владелец или только явная contract edit?
3. Должен ли failed diagnostic автоматически эскалироваться, если он показывает acceptance defect?
4. Как представить live check, который невозможно безопасно выполнить до deploy?

### Критерий запуска

Минимум три реальных plan items содержат широкую полезную проверку, которая стала дорогим
необязательным closure gate, и их нельзя исправить точечным редактированием Validation.

## 7. Настоящее наследование prompt для plan-run

### Что не сделано

`plan-run` сокращён, но не превращён в машинно-декларативный alias вида `extends: plan-exec`.
Общая часть всё ещё поддерживается как текстовые source/projection surfaces.

### Почему не сделано

`extends` потребует определить merge semantics, порядок overrides, циклы, renderer behavior и
проверку provider parity. Ради двух команд это новый мини-язык. Короткий явный prompt сейчас
дешевле и понятнее.

### Сложности, которые придётся решить

- Какие frontmatter и sections наследуются, заменяются или добавляются.
- Детерминированный render во всех provider projections.
- Ошибки при циклическом или отсутствующем base command.
- Объяснимый итоговый prompt для отладки и аудита.
- Совместимость с route `inherit-attested`, который отличается от `plan-exec`.

### Нужно обсудить

1. Есть ли второй и третий реальный consumer общего command fragment?
2. Достаточно ли генератора shared fragments без публичного `extends`?
3. Как измерять выигрыш: source maintenance, provider drift или input tokens?

### Критерий запуска

Повторный drift между plan execution prompts вызывает дефект либо появляется минимум три
команды с одной и той же крупной алгоритмической частью.

## 8. Разделение Task CI

### Что не сделано

PR matrix сокращена до Python 3.9, 3.11 и 3.13, но каждый matrix leg всё ещё вызывает полный
`packages/task/scripts/validate.sh`. Static/generated/provider checks не вынесены в один job;
полная пятиверсионная проверка не перенесена в nightly/release workflow.

### Почему не сделано

`validate.sh` сейчас является единым локальным и CI entrypoint. Механическое разрезание создаст
риск, что разработчик запускает одну комбинацию, CI другую, а release третью. Нужны явные modes
и тест того, что их объединение эквивалентно полной проверке.

### Сложности, которые придётся решить

- Разделить runtime tests, Ruff, compile, frontmatter, conflicts и generated projections.
- Сохранить один авторитетный полный локальный command.
- Добавить `--runtime-only`/`--static-only` либо отдельные стабильные scripts.
- Исключить повторную установку зависимостей и корректно настроить caches.
- Определить nightly/release trigger для 3.10 и 3.12.
- Не заявлять поддержку версии, которая редко или никогда не проверяется.
- Проверить path filters: изменения shared `core/` должны запускать нужные jobs.

### Нужно обсудить

1. Достаточна ли трёхверсионная PR matrix без nightly пяти версий?
2. Какие проверки действительно version-independent по реализации, а не по предположению?
3. Должен ли release gate всегда запускать полный пятиверсионный набор?
4. Какой текущий CI wall time и какая его доля приходится на повторяемые static checks?

### Критерий запуска

Несколько CI runs показывают, что static/generated часть составляет значимую долю каждого leg,
а общее время Task job остаётся выше принятого бюджета после сокращения matrix.

## 9. Progressive governance levels

### Что не сделано

Не введены `Direct`, `Tracked`, `Governed`, `Protected`, их автоматический выбор, переходы и
сохранение уровня в carriers. Идея остаётся концепцией аудита.

### Почему не сделано

Четыре уровня — это новый control plane. Для них понадобятся правила выбора, override,
переходов и обратной совместимости. Это прямо увеличивает число понятий, хотя цель текущей
работы — уменьшить procedure tax. Обычная работа уже отделена explicit opt-in, а hard boundaries
могут включаться по наблюдаемому риску без отдельного публичного уровня.

### Сложности, которые придётся решить

- Однозначный selection по observable risks без эвристики «много файлов = Governed».
- Повышение уровня посередине работы и судьба уже созданных evidence/carriers.
- Понижение уровня и authority владельца на такое решение.
- Совместимость старых plans без level field.
- Граница между level и уже существующими assurance, lifecycle, routing и authority.
- Prompt/runtime parity: level не должен быть лишь словом без механического эффекта.
- UX, в котором агент не тратит время на постоянное объяснение выбранного уровня.

### Нужно обсудить

1. Какой конкретный полевой дефект не решается existing opt-in и hard-risk checks?
2. Нужны ли уровни как public contract или достаточно внутренней таблицы выбора механизмов?
3. Можно ли начать с двух состояний: обычное и protected boundary?
4. Какие механизмы реально включаются/выключаются на каждом уровне?

### Критерий запуска

Есть минимум три разнотипных field incidents, где существующая модель либо включила слишком
много процедур, либо не включила необходимую защиту, и причины стабильно группируются в уровни.

## 10. Invocation metrics и observability

### Что не сделано

Не добавлены постоянные counters для tokens, tool calls, files/bytes read, journal scans, phase
parses, state/bundle builds, snapshots, validation runs и wall time. Не создан telemetry carrier
на каждый invocation.

### Почему не сделано

Измерительный слой легко становится ещё одним обязательным write path и источником схем,
миграций и проверок. Некоторые метрики принадлежат provider runtime и недоступны библиотеке без
monkeypatching или приблизительных оценок. Persisted prompts/transcripts также создают лишний
privacy и retention риск. Пока нет потребителя, который автоматически принимает решения по этим
данным.

### Сложности, которые придётся решить

- Сбор counters без вмешательства во все filesystem/provider operations.
- Отличие точной метрики от estimate и маркировка отсутствующих значений.
- Opt-in либо выключенное по умолчанию хранение.
- Стабильная schema и совместимость версий.
- Агрегация без сохранения raw prompts, transcript content и абсолютных путей.
- Retention, расположение machine-local данных и удаление.
- Низкий overhead самого измерения.
- Тестирование instrumentation без brittle exact-count fixtures.

### Нужно обсудить

1. Какие три метрики реально изменят решение разработчика?
2. Достаточен ли отдельный benchmark harness вместо telemetry в production path?
3. Где должны жить данные: stdout одного запуска, machine-local JSONL или агрегат CI?
4. Какой overhead допустим и как его измерять?
5. Какие SLO являются actionable, а не просто интересной статистикой?

### Критерий запуска

Есть назначенный consumer данных и конкретное решение, которое он будет принимать. До этого
для сравнения реализаций используется локальный benchmark/profile без изменения normal path.

## Общие вопросы владельцу

Перед продвижением любого пункта нужно принять несколько продуктовых решений:

1. Что оптимизируем первым: wall time, model cost, число tool calls, объём prompt или число
   изменяемых carriers? Эти показатели могут требовать разных решений.
2. Какой измеримый бюджет считается нормальным для одного малого plan item и одной design phase?
3. Какие contracts считаются публичными и требуют миграции, а какие derived caches можно просто
   удалить и восстановить?
4. Какие hard boundaries нельзя ослаблять даже ради скорости: owner authority, release/deploy,
   secrets, payments, destructive migrations, public compatibility и shared durable state?
5. Должно ли новое поведение быть opt-in pilot сначала на одном consumer project?
6. Какой из пунктов можно закрыть решением «не делать», если field trigger не сработает до
   следующего крупного пересмотра Task?

## Рекомендуемая диспозиция без нового плана

- Считать R-01/R-02/R-04 достаточно исправленными до появления профиля остаточной стоимости.
- Не строить durable reconciliation cache заранее; сначала измерить длинный plan.
- Проверить эффект уже сделанного review/route упрощения до проектирования ranges и modes.
- Не вводить Validation classes без owner-решения о downgrade authority.
- Сначала собрать CI timings существующих jobs; только затем разрезать `validate.sh`.
- Progressive governance оставить отклонённой по умолчанию гипотезой, пока field incidents не
  докажут необходимость нового публичного control plane.
- Для performance work использовать временный benchmark harness; permanent telemetry добавлять
  только вместе с известным потребителем и retention policy.
