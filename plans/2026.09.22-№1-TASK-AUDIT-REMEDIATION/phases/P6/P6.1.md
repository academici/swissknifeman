### P6.1 — Синхронизировать semantics и доказать non-code changes на real projects

**Intent:** Завершить аудитную программу единой runtime/prompt/docs/provider semantics и принять только те non-code changes, чьё поведение подтверждено на реальных repository tasks.
**Why:** RAG:— Audit требует typed refusals и может требовать changes в prompts/docs, но textual consistency не доказывает agent behavior. D1 поэтому требует real-project paired evidence и допускает honest `no-change` при отсутствии causal candidate.
**Scope Included:** Confirmed reason-code and non-code candidates from P1–P5; canonical Task commands and plan-protocol sources; owned docs and generated provider/runtime/registry projections; one actual task per corex/agentools/edufy; paired baseline/candidate runs in isolated worktrees; runtime security/integration smoke; final result matrix and independent review.
**Scope Excluded:** Synthetic prompt/microtask benchmarks as behavioral evidence; tuning on test wording; writes/checkouts/stash/reset/clean in source consumer trees; merging experiment worktrees; package release, marketplace publish, consumer rollout, deployment or branch protection.

**Implementation Rules:** Build a candidate ledger first. Each reason-code/non-code row names confirmed defect evidence, causal mechanism, exact source owner, proposed semantic delta, affected providers, real task(s), success/regression gates and rollback. No row means no corresponding change. Canonical source changes precede deterministic regeneration; generated projections are never hand-edited. Reason codes remain machine-distinct through CLI/JSON and are mapped to concise user-facing messages without leaking sensitive evidence. Resolve consumer paths from topology, pin exact commits and snapshot source worktree status; create separate temporary worktrees/agent state for baseline and candidate, never reuse conversation/session state, secrets or produced files across arms. Select actual pending or historically executed repository tasks with real acceptance from each project, not invented exercises. Hold task, commit, route/model/effort, tools and budget constant. Structural lint/golden tests prove only distribution/form. Behavioral evidence comes from task outcome, gate honesty, false-green/bypass count, validation execution/receipt, unnecessary owner interruptions, completion turns/time/tokens where available and reviewer-rated scope adherence. Predeclare invalid-run rules and do not replace failed runs with easier prompts. Retain a candidate only when all security/acceptance gates stay GREEN and the intended behavior improves or remains equivalent under the P1 threshold; otherwise revert that candidate. Delete temporary worktrees only after evidence is safely summarized and source states rechecked.
**Code Guidance:** Keep taxonomy small and tied to recovery action: `schema-invalid`, `evidence-missing`, `evidence-stale`, `evidence-forged`, `policy-denied` only where confirmed; avoid an enum migration with no consumer. For prompts, state observable requirements and recovery, not internal implementation trivia. Field report contains per-project task identity/commit, baseline/candidate route, artifact digests, acceptance results, invalidations and limitations; never store raw transcripts, chain-of-thought, secrets or full tool payloads. Use anonymized/minimized evidence summaries. A candidate that merely changes prose style with no observed behavior is dropped.
**Validation:** 1) Reconcile the Corex, Agentools and Edufy smoke records already produced by P2/P3/P5; rerun only a project whose relevant implementation changed afterward; 2) retain a prompt/docs/policy change only when a real task showed an observable improvement; 3) source HEAD/status snapshots remain unchanged; 4) `bash packages/task/scripts/validate.sh` plus validators for actually changed packages are GREEN; 5) `findings/P6-field-results.md` and `research/P6-final-reconciliation.md` give every claim one concise outcome and boundary; 6) plan bundle/lint/conflict/citation checks and `git diff --check` GREEN. No synthetic benchmark, exhaustive replay or independent review is required without a new concrete risk.
**Deliverables:** Minimal typed reason-code changes; only field-proven canonical prompt/docs/policy changes and regenerated projections; three-project paired field report; final 17-claim reconciliation, compatibility/rollback/release note and independent review; unchanged consumer source trees and no release/rollout.
