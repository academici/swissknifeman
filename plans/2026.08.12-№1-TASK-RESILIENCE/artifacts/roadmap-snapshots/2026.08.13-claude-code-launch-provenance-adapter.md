# Roadmap: launch-provenance adapter для провайдера `claude-code`

**Статус:** ⬜ к внедрению. Критерий сработал: Edufy, `2026.08.06-EDUFY-BUILD` P0.10–P0.13,
P0.16, P0.15 — **шесть** воспроизводимых случаев, 2026-08-13.
**Владельцы:** `packages/task` (route evidence) и Claude Code provider adapter.
**Не владелец:** скилл, model prompt, план-потребитель.

## Симптом

`task:plan-run` в проекции для **Claude Code** предписывает получать launch provenance
через `task.route_evidence_codex.capture_current(...)`. Модуля
`task.route_evidence_claude` в `packages/task/lib/task/` **не существует вовсе** —
каталог несёт ровно два файла: `route_evidence.py` и `route_evidence_codex.py`.

Воспроизводимый замер в Claude Code (Opus 5, `/effort high`), cwd `~/projects/edufy`:

```python
from task import route_evidence_codex as rec
rec.capture_current(expected_invocation="$ task:plan-run 2026.08.06-EDUFY-BUILD P0.15",
                    expected_cwd="/home/vostrikov/projects/edufy")
# RouteEvidenceError: ROUTE_LAUNCH_UNAVAILABLE: CODEX_THREAD_ID is absent or invalid
```

Codex-адаптер идёт по ancestor process chain до owning **Codex** process и читает его
argv (`-m`, `-c model_reasoning_effort=...`). В Claude-сессии такого процесса нет по
конструкции, поэтому единственный документированный путь возвращает
`ROUTE_LAUNCH_UNAVAILABLE` **всегда**, независимо от того, верен маршрут или нет.

Следствие вниз по цепочке — write-site Task Contract:

```python
actual = route_evidence.capture_actual(None, None, source="self-attested")
task_contract.evaluate(task_contract.build("plans/2026.08.06-EDUFY-BUILD", "P0.15",
                                           actual_route=actual))
# {'pre_mutation': 'block:ROUTE_UNDERSHOOT', 'pre_final': 'n/a', ...}
```

`block:ROUTE_UNDERSHOOT` здесь выведен из **unknown**-осей, а не из реального недобора:
фактический маршрут исполнения — `opus/high`, предписанный §3 Routing — `frontier/high`,
то есть **exact**. Предикат не различает «маршрут ниже требуемого» и «маршрут не
наблюдаем», и оба схлопывает в один реальный код отказа.

## Почему это отдельная запись, а не часть codex-observability

[`2026.08.11-codex-effective-route-observability.md`](2026.08.11-codex-effective-route-observability.md)
описывает **качество** evidence у существующего Codex-адаптера: платформа не отдаёт
effective route работающего thread, поэтому adapter вынужден принимать self-attestation.
Его Приёмка одной строкой упоминает, что «Codex и Claude adapters соблюдают один
provider-neutral schema contract» — но владельца у Claude-стороны нет ни в одной записи.

Здесь дефект другого класса: **provider coverage gap**. Не «evidence слабое», а
«канала evidence не существует», при том что канонический текст команды его требует и
`plan-run` рендерится для этого провайдера. Починка codex-observability не создаёт
claude-адаптер, а создание claude-адаптера не решает codex-проблему наблюдаемости.

## Incident record — 2026-08-13, Edufy `2026.08.06-EDUFY-BUILD`

Шесть items одного плана прошли через один и тот же ложный красный write-site:

| Item | Предписано §3 Routing | Фактический маршрут | Исход |
|:--|:--|:--|:--|
| P0.10 | frontier/high | opus/high | закрыт по авторизации владельца |
| P0.11 | frontier/high | opus/high | закрыт по авторизации владельца |
| P0.12 | frontier/high | opus/high | закрыт по авторизации владельца |
| P0.13 | frontier/high | opus/high | закрыт по авторизации владельца |
| P0.16 | implementation/high | sonnet/high | закрыт по авторизации владельца |
| P0.15 | frontier/high | opus/high | routing-rejected → авторизация владельца |

Ни в одном случае маршрут не был ниже предписанного. Каждый прогон вынужден:

1. писать nonterminal `routing-rejected` / `routing-blocked` в append-only
   `journal.jsonl` до старта продуктовой работы;
2. получать **разовую** авторизацию владельца репликой в чате (что сам протокол
   `DecisionRequest` не признаёт каналом approval);
3. нести строку `write-site: pre_mutation: block:ROUTE_UNDERSHOOT · pre_final: n/a`
   в Completion Notes закрытого 🟢/🟠 item'а.

Третий пункт имеет механическое следствие: `_lint_write_site_codes_44` требует **оба**
кода строго `allow`, поэтому `plan-lint --baseline HEAD` даёт стабильный `+1 ERROR` на
каждом закрытии — шесть ложных ERROR, неотличимых линтером от настоящих.

Это evidence инцидента, а не попытка объявить operator correction доказательством
маршрута. Владельцем починки остаётся `packages/task`, не план-потребитель: Edufy
фиксирует расхождение и продолжает, а не самоправит чужой пакет.

## Решение

1. Добавить `task/route_evidence_claude.py` с `capture_current(*, expected_invocation,
   expected_cwd)` — **симметрично** codex-адаптеру по сигнатуре, кодам ошибок
   (`ROUTE_LAUNCH_UNAVAILABLE` / `ROUTE_LAUNCH_MISMATCH`) и форме возвращаемой записи
   (concrete `model`, provider-neutral `model_class`, `effort`, session binding, ts,
   `source`/version).
2. Источник осей — **не** `config.toml`-аналог и не актор: session-bound runtime
   identity провайдера (`CLAUDE_CODE_SESSION_ID` уже читает
   `task/session_context_claude.py`) плюс резолв selector→класс через committed
   `command-routing.json` `mappings.claude-code` (`frontier → opus`, `high → high`).
   Ось, которую провайдер не отдаёт, возвращается `unknown` — не подставляется.
3. Ввести резолвер провайдера поверх двух адаптеров (`route_evidence.capture_launch`
   либо аналог), чтобы каноническая команда звала **один** provider-neutral вход, а не
   называла codex-адаптер поимённо в тексте, рендеримом для всех провайдеров.
4. Развести в предикате `unknown` и реальный недобор: отсутствие evidence обязано давать
   nonterminal `ROUTE-UNVERIFIABLE`, а не `block:ROUTE_UNDERSHOOT`. Сегодня один код
   покрывает оба случая, и линтер красит ложный ERROR наравне с настоящим.

## Приемка

- в Claude-сессии `capture_current` с effective `opus/high` проходит routing
  `frontier/high` без self-attestation и без обращения к codex-адаптеру;
- fixture с реальным недобором (`haiku/low` против `frontier/high`) даёт nonterminal
  routing rejection, а provenance несёт provider source и session binding;
- отсутствие provider evidence даёт `ROUTE-UNVERIFIABLE`, **не**
  `block:ROUTE_UNDERSHOOT`: два кода различимы в `plan_lint` и в write-site строке;
- каноническая команда `plan-run` не называет codex-адаптер поимённо — обе проекции
  ходят через один provider-neutral резолвер;
- regression fixture воспроизводит инцидент Edufy: exact-маршрут в Claude-сессии больше
  не порождает ни `routing-blocked` event, ни `+1 ERROR` линтера.

## Доказательства

- `packages/task/lib/task/` — каталог несёт `route_evidence.py` и
  `route_evidence_codex.py`; `route_evidence_claude.py` отсутствует.
- `packages/task/lib/task/route_evidence_codex.py` — `ROUTE_LAUNCH_UNAVAILABLE` при
  отсутствии `CODEX_THREAD_ID`.
- `packages/task/lib/task/session_context_claude.py` — Claude-адаптер session identity
  уже существует (`CLAUDE_CODE_SESSION_ID`), то есть провайдер-специфичный слой в пакете
  предусмотрен; route-ось для него просто не написана.
- Edufy `plans/2026.08.06-EDUFY-BUILD/handoff.md` Open risk 1 (унаследован P0.10→P0.16) и
  `journal.jsonl` — шесть записей `routing-rejected` / `routing-blocked`.
