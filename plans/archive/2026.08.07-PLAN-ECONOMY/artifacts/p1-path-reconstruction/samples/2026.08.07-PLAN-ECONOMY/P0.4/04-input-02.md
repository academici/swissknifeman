# findings/16 — Зонд учёта корней в `plan-weight.py sweep` (2026-08-07)

**Класс:** репро/диагноз собственного инструмента (слой 1). **Повод:** эскалация P0.4 —
Validation-команда item'а не выполнима против реального CLI. **Инструмент:**
`packages/task/scripts/plan-weight.py` на дереве `0d32ac8f` (HEAD на момент зонда). Четыре файла,
от которых зависит наблюдение, — `lib/task/plan_weight.py`, `lib/task/plan_lint.py`,
`scripts/plan-weight.py`, `tests/test_plan_weight.py` — проверены `git status --porcelain`: диффа
рабочего дерева нет, наблюдение снято ровно на `0d32ac8f`. Оговорка о том, что в дереве ЕСТЬ
посторонний дифф соседних файлов пакета (в том числе `packages/task/commands/plan-exec.md` —
источник литералов обязательного пути), — в §3. **Кто:** сессия
`plan-design 2026.08.07-PLAN-ECONOMY P0.4`, claude-opus-5[1m]/high.

Зонд отвечает ровно на один вопрос: **что делает `sweep` с корнем, который ему передали, в каждом
классе доступности корня** — потому что на этом стоит условие закрытия P0.4 («каждый корень либо
померян, либо явно помечен недоступным»).

## 1. Что предполагала Validation P0.4 и что есть на самом деле

| Предположение ТЗ | Факт |
|:--|:--|
| `sweep <fleet-roots.json>` — CLI читает JSON-манифест корней | `p_sweep.add_argument("roots", nargs="+")` (`plan_weight.py:770`); каждый элемент уходит в `plan_lint.discover_plan_dirs(Path(root))` (`:579`) как ПУТЬ КАТАЛОГА, JSON не читается нигде |
| envelope несёт top-level `unreadable_roots` | Ключа нет вовсе: `sweep` возвращает `{"plans", "errors", "totals"}` (`:589–597`), `envelope()` добавляет только `schema`/`calibration`/`limits`/`session_model_id`/`dense_ascii_min_run` (`:601–619`) |
| `GAP_UNREADABLE_ROOT` — про корень входа | `GAP_UNREADABLE_ROOT` — пробел ПУНКТА: проверяется `repo_root` конкретного плана внутри `measure_item` (`:423–427`), к аргументам `sweep` отношения не имеет |

Следствие для двух команд Validation P0.4 (обе не выполнимы как написаны): первая — манифест как
единственный корень не резолвится в каталог, дамп получается пустым (`plans: []`), а `&& echo
sweep-ok` печатает зелёное; вторая — `KeyError: 'unreadable_roots'`.

## 2. Три класса корня — наблюдения зонда

Стенд: `<scratch>/probe2/noread` (каталог `chmod 000`), `<scratch>/probe2/empty` (пустой каталог),
`<scratch>/probe2/nope` (не существует). Команда — `python3 packages/task/scripts/plan-weight.py
sweep <корень>`.

**O1. Корень существует, но недоступен на чтение → НЕПЕРЕХВАЧЕННОЕ исключение, прогон падает
целиком.** Дословно (хвост трейсбека):

```
  File ".../plan_weight.py", line 579, in sweep
    discovered = plan_lint.discover_plan_dirs(Path(root))
  File ".../plan_lint.py", line 2343, in discover_plan_dirs
    if (root / "plan.md").is_file():
PermissionError: [Errno 13] Permission denied: '<scratch>/probe2/noread/plan.md'
```

Код возврата процесса — `1`, на stdout ничего. **O2. Падение уносит и остальные корни:**
`sweep <noread> <empty> plans` (третьим — живой корень этого репозитория, 19 планов) даёт тот же
трейсбек и код `1`, ноль измеренного вывода. То есть один недоступный корень флота уничтожает весь
замер флота — при том, что докстрока самой функции обещает обратное: «План, который не удалось
разобрать, попадает в `errors` и НЕ роняет прогон» (`plan_weight.py:575–577`).

**O3. Корень существует, читается, планов не содержит → тишина.** Вывод —
`итого: планов 0, пунктов 0, пробелов 0 (…)`; в `errors` пусто, в машинном выводе следа корня нет
вообще. Корень, отданный инструменту, исчезает из отчётности бесследно.

**O4. Корень не существует / не каталог → штатная запись.** `errors` получает
`{"root": …, "error": "корень не существует или не каталог"}`, человеческая печать —
`НЕ ИЗМЕРЕН: <root>: корень не существует или не каталог`. Это единственный из трёх классов,
который сегодня отчитывается.

**O5. Причина O1 и O3 — общая: у `sweep` нет понятия «корень входа» как учётной единицы.**
`discover_plan_dirs` возвращает `None` только для «не каталог» (`plan_lint.py:2345–2346`), а
`PermissionError` летит из `stat()` ещё до этой проверки; успешный же вызов возвращает список,
длина которого нигде не сопоставляется с фактом «корень был во входе».

**O6. Позиция `errors` не различает два разных факта** — «корень не удалось резолвить» (ключи
`root`, `error`) и «конкретный план не удалось разобрать» (ключи `root`, `plan_dir`, `error`).
Различие несёт только присутствие ключа `plan_dir`.

## 3. Что зонд НЕ проверял

Не воспроизводился класс «корень доступен, планы есть, `measure_plan` падает» — он уже наблюдался
штатным прогоном P0.3 на живом дереве: `plans/.claude` и `plans/__pycache__` распознаются
`discover_plan_dirs` как каталоги планов и дают две строки `НЕ ИЗМЕРЕН` (пре-существующий дефект
среды, зафиксирован в `handoff.md` Open risks и в Completion Notes P0.2/P0.3). Не измерялась
доступность конкретных чужих корней флота из этой сессии — это работа самого P0.4, а не зонда.

**Названо прямо, потому что задевает прогон P0.4.** Рабочее дерево на момент зонда несёт
посторонний дифф, принадлежащий другой параллельной работе (зафиксирован в `handoff.md` при
закрытии P0.3), и в нём — `packages/task/commands/plan-exec.md`. Именно из §1 этого файла тест
P0.3 грепает четыре литерала обязательного пути. Зонд к этому файлу не обращался и его не
трогал, но исполнитель P0.4 обязан считаться с тем, что тест `plan_weight` может покраснеть от
ЧУЖОГО диффа: класс отказа тогда — не его правка, и чинится он не подгонкой теста (см. Code
Guidance P0.4).
