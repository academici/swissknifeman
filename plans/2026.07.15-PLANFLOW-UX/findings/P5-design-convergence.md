# P5 — RAG-верификация: методология сходимости итеративного дизайна (анти-клинч)

**Дата:** 2026-07-16 · **Движок:** perplexity-web (`mcp__perplexity-web__search`) · **Модель дизайна:** opus/high
**Запрос (суть):** best-practice сходимости при итеративном рефайне плотно-связанной спеки, где фикс
одной секции рябит в другую (ripple); «батч-фиксы → одна консолидация» vs «фикс-и-реверификация каждого»;
LRM / set-based design / design freeze / критерий остановки. Таймфрейм 2024–2025.

## Вердикт (CONFIRMED)

Между двумя крайностями — **средний путь**:

- **Не** «фикс-и-реверификация каждого изменения» (per-change) — при высокой связности/неопределённости
  даёт **thrash** (ранние допущения ещё нестабильны → каждый локальный фикс вскрывает рассогласование).
- **Не** «большой батч → одна консолидация в конце» (big-bang) — прячет несовместимости до поздна,
  болезненные конфликтующие правки.
- **✅ Средние когерентные батчи вокруг ОДНОГО дизайн-вопроса/хотспота**: сгруппировать правки вокруг
  одной связной темы (coupling-hotspot), применить во ВСЕ затронутые секции, прогнать **стандартную
  интеграционную валидацию** (DoR/тесты/ревью) — и лишь потом двигаться дальше.

**Несущие концепты (перекладываются на наш plan-protocol 1-в-1):**

| Концепт (внешний) | Что значит | Наш механизм-носитель |
|:--|:--|:--|
| **Set-Based Design (SBD/SBCE)** | держать несколько вариантов для hotspot'а, сходиться пересечением feasible-set, а не полировкой одного point-solution; пустое пересечение → **удалить вариант, не патчить вокруг** | развилка `## Обсуждение` (варианты) + D# (что выбрано) |
| **Last Responsible Moment (LRM)** | замораживать решение, когда цена НЕ-решения превысила цену решения; до LRM — держать опции открытыми | скелет-фаза (не терминальна до детализации) + reconcile-правило P4.1 |
| **Progressive / partial design freeze** | стабилизированные секции → «закрыты для структурных изменений», только косметика/непрорывные детали; дальнейшее — через change-control/ADR, не «рефайн» | контракт-блок P4.1 (заморозка интерфейса фазы) + потолок раундов аудита plan-audit.md |
| **Medium-batch around one design question** | не микро-твики, не big-bang; батч вокруг одного риска/хотспота | батчинг подфаз P4.2 (`Batch` колонка §3) |
| **Явный критерий остановки** | стоп-правило: нет открытых high-severity рассогласований между секциями, все LRM пройдены, дальше — только редакторские правки | DoR-гейт §7 (0 маркеров) + порог severity plan-audit |

## Прямой ответ на вопрос дизайна P5.1

Наш измеренный клинч (`2026.07.13-PLAN-PROTOCOL-GAP`: P2 реопенился ×3; recon §2.2) — это **point-based
рефайн плотно-связанного SSOT БЕЗ явного критерия сходимости**. Ремедиация:

1. **RECOVERY-дисциплина в §7 refine-цикл** (сейчас: `design → self-audit → правка → повтор до 0 маркеров`
   — НЕТ анти-ripple слоя): когда фикс рябит (клинч), рефайнить **средним батчем вокруг ОДНОГО
   coupling-hotspot'а** (не per-change, не big-bang), после батча — интеграционная валидация (DoR по всем
   затронутым фазам); **финальная консолидация — единый проход в конце**, а не полный re-design N раз.
2. **Прогрессивная заморозка**: стабилизированную фазу морозим контракт-блоком (P4.1) — дальше только
   детали, не новые контракты; при структурном клинче (feasible-set пуст) — **удалить вариант** (SBD),
   а не патчить (эскалация к Perplexity на стратегию декомпозиции — RAG-делегирование CLAUDE.md).
3. **Достаточность анти-клинч-канона:** AUDIT-петля УЖЕ закрыта (`plan-audit.md` L24–35: потолок 2 раунда,
   severity находки ≠ вердикт фазы, follow-up вместо реопена — D44/2.7). **Пробел — DESIGN-рефайн-петля**:
   у неё нет консолидационно-батчевой дисциплины и явного критерия остановки. P5.1 закрывает именно её.
