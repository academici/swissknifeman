# P15.03. Измерения производительности и покрытия recovery

Пороговые числа в таблице — допущения для проектирования одной инсталляции, не SLA. Измерения относятся к одному хосту и указанной конфигурации. Процессы описаны в [обзоре архитектуры](architecture/overview.md).

## Стенд

- Исходная ревизия `643f1f2e5c692ba4b99187c6862cff06f6b95f0a`, SKM `2.0.0.dev0`, прогоны 19–20 ноября 2026 г. Хост Ubuntu 24.04.5 LTS, Linux 7.0.0-31-generic, x86-64, Intel Xeon E5-2683 v4 2.10 ГГц, 16 физических ядер и 32 логических CPU, 31,2 GiB RAM. Диск Samsung SSD 970 EVO 250 GB, рабочее дерево на ext4.
- Python 3.12.3, uv 0.13.1, pytest 9.1.1, pytest-xdist 3.8.0, coverage 7.17.0, psycopg 3.3.6, psycopg-pool 3.3.3, Starlette 0.52.1, Uvicorn 0.54.0, HTTPX 0.28.1, Git 2.43.0.
- PostgreSQL 16.4, Docker-образ `postgres:16.4` (`sha256:e62fbf9d3e2b49816a32c400ed2dba83e3b361e6833e624024309c35d334b412`), один изолированный контейнер на `127.0.0.1:54339`. `shared_buffers=128MB`, `max_connections=200`, `max_wal_size=512MB`, `fsync=on`, `synchronous_commit=on`, `full_page_writes=on`, UTC. Данные PG на отдельном tmpfs 13 GiB, временные файлы, локальные blobs и архив на `/dev/shm/skm-pg`. Для логического архива использован клиент PG 16.15. Условия записи и backup на NVMe требуют отдельного измерения.
- HTTP, SSE и upload используют один реальный процесс `skm serve` на сценарий с локальным blob store и штатными фоновыми службами. Авторизация и worker/scheduler идут через реальные PG-репозитории тестовой композиции. Пул embedded fixture ограничен 8 соединениями, HTTP запускается с `api.threadpool.size=16` и штатным расчётом пула. Нагрузочные результаты и baseline тестов получены на общем хосте. Полный perf-прогон распределён по файлам между тремя процессами pytest-xdist. Каждый HTTP/SSE сценарий использует свой процесс serve и свою одноразовую БД.

## Воспроизведение

```sh
export TMPDIR=/dev/shm/skm-pg
export SKM_TEST_DATABASE_URL=postgresql://skm:skm_dev@127.0.0.1:54339/skm_test
export SKM_REQUIRE_PG=1
uv sync --frozen
uv run --frozen pytest -q -m perf tests/perf -n 3 --dist loadfile \
  --perf-results="$TMPDIR/p15-perf.jsonl"
make test
make test-affected AFFECTED_ARGS='--module integrations'

export COVERAGE_FILE="$TMPDIR/p15-recovery.coverage"
uv run --frozen coverage run --branch -m pytest -q tests/recovery
uv run --frozen coverage report \
  --include='*/adapters/postgres/*,*/application_bus/*,*/modules/execution/*' \
  --skip-covered --sort=cover
uv run --frozen coverage json \
  --include='*/adapters/postgres/*,*/application_bus/*,*/modules/execution/*' \
  -o "$TMPDIR/p15-recovery.json"
```

Набор создаёт одноразовые БД из текущих миграций. Для history доступен отдельный тестовый сервер через `--perf-history-dsn`. Для полного объёма нужно место под данные, индексы, WAL и архив. `--perf-results` дописывает JSON Lines с сырыми значениями и метаданными, в том числе перед проверкой бюджета. Перцентили вычислены по исходным значениям. p50 — медиана, p95 — элемент с рангом `ceil(0.95 × n)`. Показанные сырые значения округлены до трёх знаков.

Scheduler прекращает повторные замеры после первого превышения жёсткого предела. Его p50 и p95 отражают один завершённый тик. Загрузка событий в строках 6 и 8 идёт отдельно от HTTP API, чтобы измерение фоновой доставки начиналось с доменной записи. Тест использует синтетические валидные `WorkspaceCreated` события одного workspace. Приложение читает их штатным SSE. Для outbox каждый замер откатывает транзакцию после claim и сохраняет одинаковую исходную очередь. Timeline вызывает production PostgreSQL-репозиторий. Прежний замер audit фильтровал SQL proxy только по `recorded_at`. Исправленный SQL использует курсор `(recorded_at, id)` с тем же убывающим порядком. Отдельная проверка в PostgreSQL проходит три страницы с совпадающим `recorded_at` по обе стороны границы страницы. Задержка исправленного SQL на 10 млн строк в этом проходе не измерялась. Backup измеряет `pg_dump --format=custom` и проверяет оглавление через `pg_restore --list`. Для backup одна выборка, p50 и p95 равны 98,767 с.

## Предложения ADR и задачи владельцам

1. **Scheduler, владелец execution.** Измерить число SQL-вызовов и CPU на тех же десяти DAG. Во время тика PostgreSQL показывал повторяющиеся чтения attempts и run tasks. Вызов `require_future_admission` для зависимой задачи снова перебирает попытки для всех задач run. Проверить пакетную загрузку задач, попыток и назначений на run, а также раннее исключение задач с неудовлетворёнными зависимостями и однократное построение карты зависимостей. Замерить снова на той же форме графа под конкурирующими изменениями. Сохранить порядок блокировок K5 и гарантию сериализации.
2. **Claim и renew, владельцы execution и storage.** Замерить отдельно ожидание пула, блокировки run/assignment/worker и обработку команды. Сопоставить текущий пул из восьми соединений с конфигурацией одного HTTP serve, распределив 32 lease по нескольким worker. Сохранять fencing, точную выдачу и повторяемость receipt при любом варианте.
3. **Запуск outbox relay и учёт переполнений, владельцы bootstrap и application bus.** `OutboxRelayService` реализован, а `BACKGROUND_SERVICES` его не регистрирует. Подключить сервис в `serve`, добавить серверный счётчик закрытий из-за переполнения SSE-очереди и проверить его на намеренно замедленном клиенте с возобновлением по `Last-Event-ID`. Повторить профиль 50 событий/с и 50 клиентов с подтверждённой доставкой через LISTEN, измерить end-to-end relay lag и сверить счётчик. Отдельно проверить fallback polling. Текущий замер курсора покрывает fallback, а `OutboxStore.claim` измеряет операцию PostgreSQL.
4. **Audit и backup, владельцы audit и эксплуатации.** Добавить замер штатного чтения после появления поверхности audit. Провести backup на NVMe с локальным blob store и реалистичной шириной событий. Сохранить проверки курсоров и восстановления целостного снимка. Для решения о разбиении истории использовать измерение действующей инсталляции. История остаётся append-only; см. [модель данных](architecture/data-model.md).
5. **Скорость тестов, владельцы tooling.** Оставить полную проверку в CI. Локальная цель `test-affected` экономит время между полными запусками. Отдельно снять `--durations` с полного прогона и профилировать collection и медленные группы, поскольку замер выбранного модуля также выше 60 с.
6. **Холодный старт skm-hook, владелец integrations.** Снять `-X importtime` и фазовый профиль запуска на каждом target. Сравнить стоимость старта интерпретатора, поиска root/cache и проверки digest на неизменившихся четырёх входах. Держать существующие проверки native-решения и отсутствия backend-импортов.
7. **Сброс PostgreSQL в тестах, владелец tooling.** Оставить текущий `TRUNCATE … RESTART IDENTITY CASCADE` со сбросом migration seed и `seed_instance()` перед каждым тестом. Цель 30 мс превышена на 1,729 мс по p50 и 6,919 мс по p95. Шаблонная БД на модуль могла бы амортизировать миграции, но добавляет клонирование, переподключение пулов и удаление клонов. Общий клон на модуль всё равно требует очистки между тестами. Рассматривать переход после сравнения общего времени PG-набора с учётом этих затрат. Шаблон должен содержать только состояние свежих миграций, клоны должны быть изолированы между workers, а регрессия `test_clean_database.py` должна подтверждать совпадение seed после каждого сброса со свежей БД.
