## Pass 1 — does an OSS repo already do the whole construction?

**Query (abridged):** OSS repos 2025–2026 running Codex CLI (`codex exec`) and/or Claude Code CLI
(`claude -p`, headless) as non-interactive batch workers under a supervisor, with disposable git
worktree per task, machine-readable task spec, enforced JSON output schema, tool/permission
allowlists + network-off, wall-clock/token caps, automatic diff acceptance against a declared
file scope, and crash/resume idempotency — and specifically **how each composes the prompt**.

**Answer, condensed:**

- **No single OSS repo hits all six criteria** around a raw `codex exec` / `claude -p` worker.
  The closest concrete studies are `anthropics/claude-code-action`, `OpenHands/openhands` +
  `OpenHands/software-agent-sdk`, and SWE-bench-style harnesses.
- `anthropics/claude-code-action`: one agent run per workflow invocation (fresh process per task
  ✔), isolation at the CI-runner/checkout level rather than git-worktree-per-task; supports
  `--output-format json` / `--json-schema` / `--max-turns`; OS sandboxing (seatbelt/bubblewrap)
  with filesystem/network boundaries; **prompt = full issue/PR/comment text plus repo context**,
  with the file/diff list as *additional* context, never the sole content. No built-in
  scope-based diff rejector and no crash/resume idempotency — those need an external
  orchestrator.
- OpenHands SDK / benchmarks: task spec is machine-readable and the prompt is *"system prompt +
  full issue/PR/task description + repo/file context"*. Documented failure modes include *agent
  claims success but tests fail*, *agent produces no diff or only documentation*, *timeouts /
  budget exhaustion*, and explicitly **"under-specified prompts leading to partial fixes."**
- Codex CLI in CI is a documented recipe (`codex exec "<natural-language instruction>" --full-auto`
  in a disposable container, `AGENTS.md` for repo context), not a packaged orchestrator.

## Pass 2 — per-repo source-level analysis of the named candidates

**Query (abridged):** for `stravu/crystal`, `devflowinc/uzi`, `smtg-ai/claude-squad`,
`BloopAI/vibe-kanban`, `dagger/container-use`, worktree-fleet managers,
`All-Hands-AI/OpenHands` evaluation harness, `princeton-nlp/SWE-agent`, and the official
SWE-bench harness: how is the per-task prompt actually built in code; worktree/container
lifecycle; JSON schema; how the diff is extracted and judged; what happens on **success with an
empty diff**; which budgets are enforced runner-side. **Does ANY of them ever dispatch a coding
task with only a file list and no natural-language description, and what is the observed outcome
of under-specified prompts?**

**The load-bearing answer, verbatim in substance:**

> "Almost none implement a pure 'file list, no natural language' task dispatch, and when they do
> under-specify prompts the observed outcome is typically either a no-op/empty diff that is still
> marked 'success' or a stuck agent that needs manual intervention."

Cross-cutting conclusions stated by the research pass:

1. **No benchmark or orchestrator surveyed dispatches a task as a file list without a
   natural-language description.** For SWE-bench-lineage harnesses this is definitional — the
   benchmark *requires* the issue text in context.
2. **Under-specification reliably produces a no-op/empty diff that the agent itself labels
   success.** Orchestrators without test adjudication record it as `+0/-0` and move on; harnesses
   with test adjudication count it as failure.
3. **Serious harnesses never trust the agent's self-reported success** — they apply the patch and
   run tests. Our `validate-repository-pilot.py` follows the same discipline (it judged
   `accepted:false` on real evidence rather than trusting `reason_code: OK`).
4. **Runner-side hard budgets are precedented** (SWE-agent step budgets, harness container
   timeouts, `--max-turns`), but token/cost caps are generally left to the provider — matching
   D112's finding that the Codex CLI exposes no money cap.

## What this establishes for this plan

- **The construction is feasible and precedented.** Every individual property Artifex requires —
  headless CLI worker, worktree/container per task, enforced JSON schema, tool allowlist +
  network-off, runner-side wall-clock/step budgets, test/scope-based diff adjudication,
  fresh-process idempotency — exists in shipped OSS. Artifex is a *superset assembly* of
  precedented parts, not an unproven construction. What is genuinely rare is combining all of
  them in one auditable harness, which is this plan's contribution, not its risk.
- **Our 0/3 matches the documented signature of an under-specified prompt, not of an incapable
  provider or a broken seam.** Two zero-diff `success` records is precisely the failure mode every
  surveyed system reports for that input class.
- **No reference system would have dispatched our admission.** Passing a file list with no problem
  statement is outside the practice of every harness examined.

Limitations, stated plainly: this is a synthesized survey, not a first-party read of each repo's
source. Line-level claims about specific functions in those repos are `[UNVERIFIED]` and are not
load-bearing here — the load-bearing claim (no file-list-only dispatch; under-specification →
no-op success) is corroborated independently across nine projects and two benchmark harnesses.
