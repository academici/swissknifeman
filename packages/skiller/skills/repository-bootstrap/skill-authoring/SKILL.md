# Registry skill authoring

Internal skill (not exported). **Procedure** for working with skills; the package map is in
[package-architecture], the canonical process is `CONTRIBUTING.md` (only rules not covered there
live here).

[package-architecture]: ../package-architecture/SKILL.md
[release-discipline]: ../release-discipline/SKILL.md
[docs-maintenance]: ../docs-maintenance/SKILL.md

## When to activate

- Creating, editing, moving, or removing any `skills/<bucket>/<name>/SKILL.md`, its
  `SKILL.ru.md`, snippets/, references/, adapters/, or upstream.json.
- **Editing `SKILL.ru.md`** (the Russian source) — regenerating `SKILL.md` is MANDATORY
  afterward (see "Bilingual model").
- Editing internal `.claude/skills/` skills (the "no overlap" rule applies to them too).
- Root-bootstrap identities (class A, `skills/repository-bootstrap/<id>/`) — same bilingual
  model and completeness requirement; the projections `.claude/skills/<id>/`+
  `.agents/skills/<id>/` are generated by `skiller registry` and never hand-edited (P1.2, D31).

## Step 0 — overlap check (mandatory BEFORE creating)

1. Search `skills.json`: name, description, tags for the new skill's topic.
2. `grep -ri` over `skills/` for topic keywords.
3. Check `references/` — an import may already be planned.

**Decision:** an overlap in content found → extend the existing skill, don't create a new one.
The same name within one bucket is a validator error; across buckets — a warning (a collision
when vendoring), allowed only deliberately.

## Bilingual model: `SKILL.ru.md` (source) → `SKILL.md` (EN canon)

EVERY local registry skill is bilingual:
- **`SKILL.ru.md`** — the full Russian SOURCE. Human-edited, this is the SSOT: full context,
  the "why", examples.
- **`SKILL.md`** — the compact English CANON, **generated** from RU. Only this is loaded by the
  agent; Russian never enters context.

**Creation:** write `SKILL.ru.md` first (full, per the "Completeness requirement" below) →
generate `SKILL.md` with the prompt
`packages/skiller/prompts/generate/claude-canon-from-ru.md` (compact EN, preserves EVERY
rule/condition/threshold/code/path; frontmatter is copied, only `description` is translated) →
`bash packages/skiller/scripts/check-translations.sh --stamp`.

**Editing:** edit ONLY `SKILL.ru.md` → regenerate `SKILL.md` with the same prompt → `--stamp`.
**Do NOT edit `SKILL.md` directly** — it will be overwritten from RU and the edit lost.

**Control:** `check-translations.sh` (no flags) → lists "EN stale" (RU edited, EN not
regenerated). Freshness is stamped as `<!-- ru-source-sha256 -->` at the end of `SKILL.md`.
`*.ru.md` files are committed, but NOT vendored into projects.

**External (upstream) skills — exception:** their `SKILL.md` (EN) comes from upstream and is NOT
generated from RU; their `SKILL.ru.md` is only a human reference, the canon is left untouched.

## Local skill

1. Fill in the **full** frontmatter (in `SKILL.ru.md`; copied when EN is generated): `name`
   (kebab-case, == directory name), `bucket`, `version`, `description`,
   `risk: read|draft|write|external`, `persona`, `tags`, `requires`, `produces_for`, `outputs`,
   `snippets`, `adapters`, `sha256: ""`.
2. Lists — inline syntax only `[a, b]`: multiline YAML lists parse neither in sync nor in the
   validator.
3. A new bucket → mandatory entry in `buckets.json` (description/category/tags).
4. A nested SKILL.md inside a skill is invisible to plugin discovery — expand it into a sibling
   directory `<parent>-<child>`.

## Granularity and placement philosophy (doctrine)

Full version — [skill-taxonomy.md](../../../../../packages/skiller/docs/guide/skill-taxonomy.md).
Briefly — **where** a skill should live and **how much** it's split:

1. **One skill = one capability; a bucket = a broad role area.** Don't dump unrelated things
   into one skill; don't spawn a bucket per skill.
2. **`general` is cross-stack only.** It's part of **CORE** (distributed to EVERY project,
   always loaded) → must be minimal and universal. Stack-specific content (PHP/Laravel/Node/Vue)
   in `general` is **forbidden**: it belongs in `php`/`devops`/`frontend`.
3. **Project-specific → project-local, NOT in the registry.** A specific project's business
   logic (domain class names, enums, `App\…`) lives in `<project>/.claude/skills/`, not the
   shared registry (the universality rule, see "Skill review").
4. **init-only ≠ always-loaded.** A skill needed once (choosing a stack/packages at init) is not
   kept in permanent distribution — mark it init-only (frontmatter `lifecycle: init`), don't put
   it in CORE/default profiles.
5. **Lean SKILL.md.** Body is an entry point (guideline ≤150 lines): what it is, when, the key
   algorithm. Details/long examples/tables → `references/`/`snippets/` (progressive disclosure).
   `validate.sh` softly warns on bloated bodies. Channel: connect = whole bucket (coarse), vendor
   = per-skill (fine) — tune fine-grained via vendor.

## `SKILL.md` body size — no platform cap (OQ-4, D27)

The provider reads a selected skill's body **in full** — Codex first-party states the
discovery budget applies "only to the initial skills list", no cap on `SKILL.md` size
itself; same fact for Claude Code. The real constraint is the **discovery listing**
(name+description of every active skill, resident every request), not the file — see
`docs/guide/budget.md`. So **no body-size cap is introduced** (`2026.07.29-HARNESS-AGNOSTIC`
D27, OQ-4 closed negative) — don't trim long bodies against an imagined platform limit.
The only limiter stays the existing soft `validate.sh` warn on non-empty body line count
(see "Lean SKILL.md" above) — that's about readability (progressive disclosure), not the
platform.

## Completeness requirement ("maximally complete" skill)

A skill must contain:

1. **Explicit activation criteria** — a "When to activate" section, and the frontmatter
   `description` works as a router (triggers named explicitly).
2. **A complete algorithm** — no stubs or "see elsewhere" for key steps.
3. **A quality checklist** — checkable boolean items.

Snippets: anonymized (`namespace App\...`, `// Source: {project}/{file} (anonymized)`), listed in
`snippets/index.json`. Adapter differences only live in `adapters/`, never a duplicated
SKILL.md.

## Eval-first: behavioral skill tests (evals/)

Structural validation doesn't answer the main question — *does the skill work and trigger at the
right time?* So every authored (non-upstream) skill gets an `evals/` folder beside SKILL.md
(scaffold: `skiller eval <bucket>/<name> --scaffold`):

- **`evals.json`** — cases `{id, prompt, assertions[]}`; assertions are ONLY deterministic
  (`contains`/`not_contains`/`regex`/`not_regex`/`file_exists`/`file_absent`/`min_words`) — the
  grade is reproducible without an LLM judge. Prompts are in the user's real language, concrete.
- **`pressure.json`** — temptation scenarios (from the "TDD for documentation" method): what
  tempts the agent to skip the skill, with assertions on compliance/violation.
- **`triggers.json`** — `should_trigger` / `should_not` queries for the precision of the
  `description` trigger (tier-0). Optimization: `skiller eval … --triggers` proposes a
  description ≤150 chars; edits go into `SKILL.ru.md` → EN regeneration.

Running `skiller eval <bucket>/<name>` (with-skill vs `--baseline`) writes
`evals/benchmark.json`. Needs the `claude` CLI; without it — offline format validation. `evals/`
is NOT vendored (like `*.ru.md`) and isn't part of the content hash. Coverage is shown by an
`evals coverage:` line in `validate.sh`. Canon — `docs/guide/evals.md`.

## External/derived skill → upstream.json mandatory

Any skill borrowed or derived from an external source must have `upstream.json` beside
SKILL.md:

- `schema_version: 1`; `source: github|http|file` (file — local fixtures/tests only);
  `strategy`:
  - `replace` — mirror (upstream has valid frontmatter, auto-updated);
  - `notify` — adapted copy (upstream only reported);
  - `fork` — a fork with our own edits (pristine mirror in `files[].path`; on drift
    `review_pending=true` blocks distribution — manual transfer, then `--resolve`);
  - `merge` — a **composite of ≥2 external sources** assembled into one whole skill.
- `files[]` — each with `path`/`url`/`sha256`/`fetched_at` (YYYY-MM-DD); `notes`.

**Composite (`strategy: merge`) — a skill made of several sources.** When a skill is actually
assembled from two+ external skills, record provenance with roles in `origins[]`:

```json
{
  "schema_version": 1, "source": "github", "strategy": "merge",
  "origins": [
    {"repo": "antfu/skills", "role": "base", "url": "…", "ref": "main",
     "sha256": "…", "fetched_at": "2026-06-26", "note": "took the structure and core"},
    {"repo": "onmax/nuxt-skills", "role": "supplement", "url": "…",
     "sha256": "…", "fetched_at": "2026-06-26", "suggest": "added SEO/module sections"}
  ],
  "merge": {"review_pending": false, "last_review": "2026-06-26"},
  "files": [ … ]
}
```

- Roles: exactly one `base` (the taken-as-base source) + ≥1 `supplement` (an augmenting
  "suggest" source; what it added — in `note`/`suggest`).
- **Sync is manual, agent-managed.** On drift of any `origin`, set `merge.review_pending=true` —
  this blocks `validate.sh`/`registry`/release until the agent re-merges sources into SKILL.md by
  hand and clears the gate (`scripts/update-upstreams.sh --resolve --skill <id>`). Auto-overwrite
  for merge is forbidden.
- Workflow: create the directory → upstream.json with empty sha values →
  `./scripts/update-upstreams.sh --apply --skill <bucket>/<name>` → status in
  `references/<source>.md` → imported.
- Reference example: `skills/php/laravel-best-practices/upstream.json` (multi-file, notify).

**An external resource used as a reference → `docs/reference.md`.** If you used an external
resource (repo, framework, someone else's skill, article, spec) while designing —
**even purely as a reference/inspiration, without copying files** — record it in the root
`docs/reference.md`: a table row (what · maturity · verdict adopt/reference/skip · what was
taken), a card if significant. `upstream.json` is the provenance passport of a SPECIFIC vendored
file; `docs/reference.md` is the unified provenance catalog of ALL external influences.

## requires / produces_for

- Only existing frontmatter `name`s; no self-reference; no cycles via `requires`. The pair `A
  requires B` + `B produces_for A` is legal.

## Skill review (acceptance standard, for reviewer and author)

A registry skill must be **universal** and must not overlap existing skills:

1. **Universality.** No project-specific business logic and **no names of concrete
   projects/packages** in the body/snippets (use generic terms: "consumer project", "the
   dependent package"). Project attachment → belongs in the project's `.ai/skills/`, not the
   shared registry; parameterize specifics into `snippets/`.
2. **No duplicate.** Step 0 was performed: a `skills.json` search (name/description/tags) and a
   `grep -ri skills/` on the topic came up clean, or an existing skill was extended.
3. **Frontmatter completeness.** All fields, inline lists, `name` == directory, valid
   `risk`/`persona`/`bucket`, a new bucket is in `buckets.json`.
4. **Triggers in `description`.** Concrete activation scenarios (when to include), not an
   abstract topic description — `description` works as a router.
5. **Snippets.** Anonymized, listed in `snippets/index.json`, carry value (not a body retelling).

## Closing out

Edited `SKILL.ru.md` → regenerate `SKILL.md` (prompt `claude-canon-from-ru.md`) →
`scripts/check-translations.sh --stamp` → `./scripts/validate.sh` → `skiller registry` → commit
`SKILL.ru.md` + the regenerated `SKILL.md` + `skills.json`, `.claude-plugin/*`,
`docs/guide/graph.md`/`budget.md` together with the change → then follow [release-discipline].

## Quality checklist

- [ ] Step 0 done, no overlaps found (or an existing skill was extended).
- [ ] Bilingual: `SKILL.ru.md` (source) updated; `SKILL.md` regenerated from it (NOT hand-edited);
      `check-translations.sh` reports no staleness.
- [ ] Full frontmatter, name == directory, inline lists.
- [ ] Has "When to activate", a complete algorithm, a checklist.
- [ ] External skill — upstream.json with filled sha256/fetched_at.
- [ ] External resources/references used while designing are recorded in `docs/reference.md`.
- [ ] requires/produces_for valid; a new bucket is in buckets.json.
- [ ] validate is green, registry is regenerated and committed.
