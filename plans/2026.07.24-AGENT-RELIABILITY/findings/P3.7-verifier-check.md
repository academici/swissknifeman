# P3.7 — read-only `--check` mode for `verify_result_manifest.py`

RAG:— (repo-grounded: every number below is recomputed by this item's own commands
against committed `plans/2026.07.24-AGENT-RELIABILITY/artifacts/P2.5/*` inputs).

## 1. What was built

`artifacts/P2.5/verify_result_manifest.py` gets a `--check` flag (D84). It builds the
exact same `manifest_payload` the writing path builds (no second implementation), then:

- strips `content_hash` (top-level) and `input_provenance.tree_anchor` from both the
  committed `--manifest` and the recomputed payload;
- if the two stripped payloads are byte-identical → `rc=0`, prints whether
  `tree_anchor` itself also matched or differed (`tree_anchor differs (<committed> →
  <current>), payload identical` vs `identical, tree_anchor matches too`);
- otherwise → `rc=1`, one `ОШИБКА: input drift at <dotted.field.path>` line per
  divergent field (never a generic "mismatch").

`--check` performs zero writes on any path, including full agreement — the same
`fail()`/`return 0` structure as the rest of the script, no new I/O primitive.

## 3. Finding: the verifier's own self-hash is not `tree_anchor`-shaped drift

`manifest_payload["files"]["verify_result_manifest.py"] = file_hash(__file__)` hashes
the verifier script's own bytes — unchanged logic from before this item. Editing this
same script to add `--check` necessarily changes that hash forever after, for any
future edit including this one. Measured: the committed `result-manifest.json`'s
`files.verify_result_manifest.py` (`6c1458de5edfe7fa1b9bc8fed4fb51addf89c72388d0d68f8
7d278d82fdeb5c7`) equals the pre-edit script at `HEAD` (`14bd1c86`); the post-edit
script hashes to a different value. This is the **only** field beyond
`tree_anchor`/`content_hash` that ever diverges in (2) and (5) — confirmed by running
both against the same committed manifest and by the negative test in § 2.4 isolating
exactly the intentionally-corrupted fields when the self-hash is held constant.

Per this item's own Code Guidance, an unanticipated divergent field is a **finding to
report, not a reason to widen the benign list**: `files.verify_result_manifest.py` is
correctly classified `input-drift` (the verifier genuinely changed — that is real
information, not noise), so `rc=1` on (2)/(5) is the honest, structurally inevitable
answer, not a bug in `--check`. It also means the literal Validation line's predicted
`rc=0` cannot hold for *this specific edit* against the pre-edit manifest — any future
edit to `verify_result_manifest.py` that runs `--check`/(5) against a manifest sealed
before that edit will reproduce the same single-field drift.

**Not fixed here** (Scope Excluded forbids widening the benign list and forbids
regenerating `result-manifest.json`/bumping `SCHEMA_VERSION`, D84): a genuine fix would
require a deliberate, owner-level decision on whether the verifier's own hash should
ever be benign-classified (it would blunt the field's only real purpose — catching an
unnoticed edit to the grading path) — a new D# for `plan-design`, not a silent
addition here.
