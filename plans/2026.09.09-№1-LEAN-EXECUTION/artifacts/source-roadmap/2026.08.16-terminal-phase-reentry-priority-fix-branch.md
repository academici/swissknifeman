# Roadmap: terminal phase не переоткрывается без доказанного trigger

**Статус:** ⬜ к внедрению. **Дата инцидента:** 2026-08-16.
**Источник:** `2026.08.02-PROVIDER-CONTRACT-LOCALE` P7.1, `task:plan-run`.
**Владельцы:** `packages/task` (dispatch, journal, plan gates, lint и provider projections);
плановый producer/consumer contract.

## Короткий вердикт

Терминальная фаза — это immutable consumption checkpoint, а не приглашение снова аудитировать
её при каждом downstream сигнале. Consumer обязан сначала проверить named producer carrier и
классифицировать факты. Если нужен ограниченный correction, он выполняется в current item либо
через отдельный приоритетный fix branch с точным return target. Re-open предыдущей фазы разрешён
только typed evidence о новом decision/authority/safety/contract boundary; прозы, пустого файла,
старого статуса или неудачной интерпретации недостаточно.

## Воспроизводимая трассировка

### Симптом

P7.1 увидел пустой P5 WAL и ошибочно вывел «absent terminal producer», сформировав handoff на
`task:plan-design … P5`. Это был бы возврат в уже закрытую P5 без изменения P5 bytes, решения,
authority или acceptance contract.

### Минимальный feedback loop

```bash
python3 plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/artifacts/p5-consumer-reconcile.py \
  verify-results \
  --manifest plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/artifacts/P5/fleet-action-manifest.json \
  --approval plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/artifacts/P5/fleet-action-approval.md \
  --recovery-contract plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/root/contracts/provider-recovery-gates-v1.md \
  --all-action-sets \
  --journal plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/artifacts/P5/fleet-transaction-log.jsonl \
  --results plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/artifacts/P5/P5.4-results.json \
  --convergence plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/artifacts/P5/fleet-convergence.json
```

Наблюденный результат: `P5 fleet results verified: 3 action sets; 0 durable events`.
P5 Phase Handoff и D83 объясняют его: action sets намеренно пусты, все 13 421 rows —
`no-op-unresolved`, rollout не авторизован. Следовательно, нулевой WAL — approved terminal
no-op, а не missing producer.

Диагностический вид тоже был снят:

```bash
PYTHONPATH=packages/task/lib python3 packages/task/scripts/plan-views.py returns \
  --plan-dir plans/2026.08.02-PROVIDER-CONTRACT-LOCALE --json
```

Он выдал 236 journal entries, 14 return events и ноль `over_cap_subjects`. Это полезный
плановый baseline, но не поймал этот incident: неверный переход был отменён до terminal
`plan-design` event и остался двумя `local-repair` observations P7.1. Новый policy carrier
должен покрывать такой pre-terminal routing decision, а не полагаться только на return-loop.

### Проверенные гипотезы

| Гипотеза | Проверка | Вердикт |
|:--|:--|:--|
| WAL повреждён или terminal result утрачен | exact `verify-results --all-action-sets` | отвергнута |
| P5 нуждается в новой live migration | D83, P5 Phase Handoff, approved empty action sets | отвергнута |
| `complete verified journal` означает «непустой» | verifier принимает 0 events как complete no-write result | отвергнута |
| Consumer не классифицирует producer mode до re-entry handoff | P7.1 сформировал `plan-design P5` до exact verifier | подтверждена |
| Runtime не хранит typed justification для возврата в terminal phase | `returns` наблюдает terminal returns, но не pre-terminal consumer re-entry proposal | подтверждена |

## Policy: terminal checkpoint first

Перед любым handoff на `task:plan-design <PLAN> <closed-phase>` runtime строит
`phase-reentry-justification/v1`:

| Поле | Смысл |
|:--|:--|
| `detected_by`, `closed_phase`, `consumer_item` | кто и где увидел сигнал |
| `producer_anchor` | terminal receipt/commit/spec digest и exact named verifier |
| `observed_mode` | `approved-no-op`, `valid-output`, `stale-derived`, `missing-or-corrupt`, `contract-conflict` |
| `impact` | affected paths, acceptance and dependency closure |
| `proposed_route` | `continue-current`, `priority-fix`, `reopen-phase`, `owner-decision` |
| `trigger` | closed enum ниже; не prose |
| `resume_target` | original item/phase и exact recheck carrier |

`approved-no-op` и `valid-output` запрещают re-open. `stale-derived` сначала регенерируется
у владельца generated carrier; `missing-or-corrupt` проходит bounded repair classification.

### Единственные триггеры `reopen-phase`

1. `owner-decision-change` — новая D# явно меняет frozen decision/contract предыдущей фазы.
2. `terminal-evidence-invalid` — named verifier доказывает повреждение terminal evidence,
   которое нельзя восстановить как bounded derived-carrier repair.
3. `safety-or-authority-boundary` — security, irreversible external state или authority
   требует изменить прошлый фазовый contract, а isolated repair не способен сохранить его
   смысл.

Любой trigger содержит конкретный verifier output, affected invariant и reason, почему
`continue-current`/priority fix недостаточны. Его отсутствие даёт
`PHASE_REENTRY_UNJUSTIFIED` до смены handoff или статуса.

## Маршруты correction без re-open

| Класс | Маршрут | Лог и возврат |
|:--|:--|:--|
| Неверная интерпретация, stale generated view, missing proof run | `continue-current` | `local-repair` с pre/post carrier; original item resumes |
| Ограниченный defect, нужный текущему outcome и в scope current item | `continue-current` | один fix commit, recheck исходного carrier |
| Ограниченный defect лежит у другого owner, но не меняет frozen semantics | `priority-fix` | append-only `fix-branch/v1`: origin, owner, scope, priority, rollback, exact resume target; после green автоматически возвращает consumer |
| Требует новой product surface, но не меняет terminal phase semantics | новый priority fix item/phase в конце master plan | routing явно разрешает внечисловой priority dispatch; после close resume target возвращает первоначальный поток |
| Один из трёх re-entry triggers | `reopen-phase` | только тогда четыре обязательных шага phase re-open и новый phase audit/close |

`priority-fix` — не скрытый rewrite прошлого item. Он имеет свой `Files`, validation,
terminal evidence и relationship `repairs=<origin>`. Плановый journal и status projection
должны показывать его отдельно, чтобы history читалась без вывода из prose.

Выбор current root versus fresh fix root принадлежит
[`2026.08.15-owner-decision-same-session-continuity.md`](2026.08.15-owner-decision-same-session-continuity.md):
`priority-fix` не создаёт новую сессию автоматически. Controller сравнивает required route,
remaining bounded work и cold-start cost; fresh root разрешён только по его typed verdict.

## Требуемые изменения

1. Добавить `phase-reentry-justification/v1` в `packages/task`; canonical commands и обе
   provider projections обязаны вызвать его до handoff на closed phase.
2. Добавить `fix-branch/v1` и priority dispatcher: ветка может быть запланирована в конце
   master plan, но получить explicit priority route сейчас; phase/item numeric order не
   подменяет dependency/priority graph.
3. Расширить `plan-views returns` отдельной метрикой `reentry_proposals` и outcome counters;
   не считать только terminal negative events.
4. `plan-lint` запрещает смену Next на closed phase без valid justification, а также
   `priority-fix` без origin/resume/rollback/validation/owner carrier.
5. Связать с
   [`2026.08.15-empty-producer-ledger-must-continue-first.md`](2026.08.15-empty-producer-ledger-must-continue-first.md):
   producer mode определяется exact verifier, а не пустотой/счётчиком.

## Acceptance

1. Fixture P5→P7: approved empty action set и zero-record verified WAL дают
   `approved-no-op` + `continue-current`; `plan-design P5` запрещён.
2. Неподписанный пустой/повреждённый WAL даёт `missing-or-corrupt`; bounded repair выбирает
   current/fix branch, если не меняет frozen semantics.
3. Новая D# меняет P5 contract: только теперь `reopen-phase` допускается и требует полный
   `phase-reentry-justification/v1`.
4. Fix в другом owner path получает отдельный priority branch, логируется с origin/resume и
   после green возвращает P7.1; P5 state/closure не меняются.
5. `returns --json` показывает pre-terminal proposal/route outcome; attempts без terminal
   return не становятся невидимыми.
6. Claude/Codex canonical/projection parity fixtures получают одинаковые diagnosis code и
   route для всех пяти классов.

## Границы и критерий внедрения

Это не разрешает обходить owner decision, переписывать closed phase задним числом или лечить
security/external-state risk без escalation. Это также не требует нового audit только потому,
что consumer прочитал старый результат: audit запускается лишь по material candidate/trigger.

**Критерий уже сработал:** P7.1 сформировал ложный re-entry proposal для P5, хотя exact
producer verifier был green. Следующая содержательная правка Task lifecycle, plan dispatch,
return diagnostics или producer/consumer readiness должна реализовать эту запись совместно с
existing producer-ledger direction; отдельный новый audit loop не создавать.
