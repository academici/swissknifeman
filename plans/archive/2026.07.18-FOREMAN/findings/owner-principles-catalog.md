## §1. Бинарная классификация (ядро D13)

### 1.1 Мета-принцип владельца

> **«Идеальные системы — главный козырь; всё чисто под себя, под единую структуру» —
> улучшение качества никогда не блокируется.**
> Прецедент: `2026.07.18-FOREMAN P0.5 D13`; `brief/01-refinements.md §5`.

Из мета-принципа следует **асимметрия** качества-атрибутов: *усиление* строгости/надёжности/
изоляции — свободно; *ослабление* — стоп + эскалация (см. free-принцип #2).

### 1.2 «Требует согласования» (эскалация супервизора)

Межпроектные/межпакетные концептуальные взаимодействия, публичные контракты, SemVer-breaking,
новые абстракции в чужом (2+ потребителя) пакете.

| # | Принцип | Прецеденты (план · D#) |
|:--|:--|:--|
| A1 | Расхождение с замороженным фундаментом/каноном/frozen-контрактом → явная эскалация в Decision Log, **никогда** молчаливая самоправка | EDUFY · Exec Rules; EDUFY-CORE · Exec Rules; FLEXCRM-W2 · Exec Rules; REGHUB · D22–D23; VLT-REL · §2 |
| A2 | После аудита схема/фундамент замораживается — только additive-only (nullable/новые таблицы), никаких breaking rename/drop; остаток → эскалация с маркером | EDUFY · D3, D22; EDUFY-CORE · D6 |
| A3 | Reuse-gate / vendor-vs-build: перед build-new — проверка радара экосистемы; политика 100% fit→берём / частично→свой пакет поверх / иначе минимальная своя база | ECOSYSTEM · D7, Context; FLEX-2 · D12; REGHUB · P1 findings |
| A4 | Дизайн-волна отделена от dev-волны: сначала все repo-планы до design-complete + замороженные **кросс-пакетные** контракты, реализация — единым фронтом по гейту «Запускай» | ECOSYSTEM · D21, Handoff |
| A5 | Владелец делегирует детали реализации при зафиксированной архитектуре, но **удерживает контроль над контрактами и breaking** | AZGUARD-STABLE · D28; VLT-REL · D13, D14 |
| A6 | Breaking changes — осознанное арх-решение с D#/обоснованием; pre-1.0 breaking легальны в MINOR | AZGUARD-STABLE · D14; COREX-CORE · P1-premortem (D17) |
| A7 | Package-граница закреплена трёхзвенно (домен-core ↔ cross-products ↔ standalones) с явной развязкой доменов | REGHUB · boundary.md D1–D4; ECOSYSTEM P5 · SocKit |
| A8 | Новые межпроектные связи / переиспользуемые компоненты требуют RAG-верификации первоисточником, приоритет GitHub API над памятью/веб-поиском | ECOSYSTEM P5 · SocKit; SKM референсы 2026-07-18 |
| A9 | Contract-first + frozen gates: заморозить контракты до кода; RAG-источники метить `RAG:✅` датой; проверять **семантическую** согласованность цепочек контрактов, не только API | ECOSYSTEM · cross-contract-audit; AXIOMA-ORCHESTRA · bitrix-d7; AZGUARD-STABLE · D20 |

### 1.3 «Свободно без вопросов» (автономно)

Внутрипакетное чистое улучшение, один потребитель, не ломает публичный контракт.

| # | Принцип | Прецеденты (план · D#) |
|:--|:--|:--|
| F1 | Качество и простота (fluent API, расширяемость, конфигурируемость, надёжность) улучшаются свободно, **пока не тронут контракт**; межпроектное/концептуальное → согласование | FOREMAN · D13 (мета + бинарь) |
| F2 | Fail-closed по умолчанию до 1.0: из развилки берётся строгий/идеальный вариант, ничего не ослабляется. **Асимметрия:** усиление — free; *ослабление* изоляции/breach → стоп+эскалация | AZGUARD-STABLE · D10, D27, P1.md:97; AUDIT-VLT · D15; AZGUARD-STABLE · refinements |

## §3. Класс решений ВНЕ бинаря — находка для D13

> **Находка (If-then Code Guidance P0.5 / D13).** Корпус выявил, что фактические принципы
> владельца **выходят за бинарь** «согласование vs свободно». Бинарь D13 описывает **ось
> изменения кода** (что в пакете можно менять свободно vs что требует согласования). Но
> ~2/3 извлечённых принципов лежат на **ортогональной оси процесс-governance**: как ведутся
> планы, роутинг моделей, пороги эскалации, дисциплина скоупа/handoff/git. Классификация
> **не расширена самовольно** — вынесено сюда как D13-находка для решения владельца
> (нужен ли отдельный класс/ось в policy-схеме P0.3).

Эти принципы — прямой сид **rulebook супервизора (P5.3)** и **скилла P3.3**: большинство —
готовые правила «когда эскалировать / когда действовать / что проверять».

| O4 | Open questions наследуются явно вниз по слоям и трекаются реестром; молчаливая потеря вопроса — дефект плана | FLEXCRM-W2 · Exec Rules; AZGUARD-STABLE · OQ, P1-audit |
