Условно я бы сначала проверил CAO как заменяемый backend исполнения, оставив план, порядок стадий и учёт у вас. Но это не «готовый runtime поверх вашего менеджера без перекрытий»: в актуальном CAO уже есть Python workflow tier, run journal, replay/resume, провайдеры Claude Code, Codex и Grok Build, а также live-наблюдение. ## Что уже умеет CAO

- Это локальный сервер и оркестрация CLI-агентов в изолированных tmux-терминалах; агенты используют собственные CLI и аутентификацию. В текущем README перечислены Claude Code, Codex и Grok Build; это соответствует вашему набору CLI.
- CAO — уже не только supervisor, делегирующий задачи по усмотрению модели. В релизных заметках v2.5 указаны script-tier workflows, async submit и live event following, durable run journal, Python replay и frozen execution manifest/plan approval. Это прямо пересекается с детерминированным плановым исполнением.
- Есть видимый в терминале запуск, tmux-сессии и Web UI; API включает live terminal streaming. Это сильная готовая часть, если под «видимостью» вы имеете в виду наблюдение за живыми CLI, а не только журнал этапов.
- Важно не трактовать «replay» как доказанную гарантию exactly-once для любого произвольного Python workflow. В issue CAO описан незакрытый на момент документации риск: Python resume может повторно исполнять завершённые вызовы run_step; предлагается проверка step fingerprint и возврат сохранённого результата. Это issue, а не подтверждение текущего поведения каждого релиза — но достаточная причина проверить именно ваш сценарий.

## Где будет дублирование

Считать нужно по владельцам ответственности, а не по наличию одноимённых функций. Сохраните собственные plan schema, зависимости, переходы статусов и детерминированные решения. В CAO передавайте уже разрешённый план исполнения; не позволяйте его supervisor’у повторно выбирать порядок стадий или самостоятельно менять статус канонического плана. Иначе появятся два планировщика и два источника истины.
Затем определите, кому принадлежат retry/resume, идентичность и журнал запуска, отмена, статус задачи и итоговые записи. Если CAO владеет durable run lifecycle, а ваш runtime параллельно хранит несовместимое состояние выполнения, возникнет двойной учёт и риск расхождения после сбоя. Для собственной реализации аналогичный риск есть между существующим runtime и новым workflow runner: сохранение менеджера планов не означает, что его текущий runtime можно оставить без явных границ.
Ваши контекст-сбор, опциональный design/review, проверки команд и bookkeeping — не следует считать отсутствующими в CAO или вашем проекте без проверки. Это требования к адаптеру и контракту: передавать этапу prompt/context, профиль и provider; собирать структурированный результат; запускать проверки как недоверенные к модели команды; записывать результат в существующий менеджер. CAO даёт терминалы, provider-интеграции и workflow-субстрат, но его наличие само по себе не доказывает соответствие этим конкретным контрактам.

## Реальная цена миграции

Это не нулевая миграция ни в одном направлении. CAO сокращает потенциальную работу вокруг CLI-процессов и live-терминалов, но может добавить интеграционную поверхность: отдельный сервер, workflow/run lifecycle, преобразование данных и границу между двумя журналами. Расширение своего runtime экономит эту интеграцию, но не гарантирует меньшую суммарную стоимость: вы становитесь владельцем и тонких provider-адаптеров, и отказных случаев терминалов. Надёжную оценку трудозатрат можно дать только после инвентаризации вашего кода и прохождения пилота — имеющихся сведений для чисел недостаточно.

## Обратимость и пилот

Сделайте backend заменяемым за узким интерфейсом, например start_step / observe / wait / cancel / result, с вашим plan ID и step ID, фиксированным рабочим каталогом и нормализованными exit/result. Канонический план и bookkeeping пусть остаются вашими; вывод и run ID CAO храните как внешние ссылки. Тогда возврат к своему исполнителю — смена адаптера, а не миграция планов. Это архитектурное предложение, не утверждение о готовом API CAO.
Пилот на нескольких реальных задачах — с локально зафиксированной версией CAO и CLI — должен пройти все ворота:
- Семантика: сбой и resume после каждой стадии не повторяют завершённые side effects; изменённый prompt/profile/provider или план обнаруживается как divergence, а не молча продолжается.
- Детерминизм: опциональные design и review действительно пропускаются по плану; verification всегда запускается кодом; bookkeeping не делегируется модели.
- Наблюдаемость: видны живой вывод, текущий шаг, ошибки, остановка и восстановление; не требуется полагаться на текстовые догадки supervisor’а.
- Интеграция: тесты подтверждают запуск всех трёх ваших CLI через CAO с вашей аутентификацией, передачу skills/context и ожидаемую работу в нужном репозитории.
- Обратимость: на середине задачи можно заменить backend или продолжить собственным runner’ом без потери канонического плана и без двойной записи статуса.
Провал любого из первых двух или последнего ворот — основание не отдавать CAO lifecycle плана: оставьте его только терминальным/backend-слоем, если интерфейс это позволяет, иначе расширяйте своё исполнение. Если ворота пройдены, CAO рационален как backend, но не как владелец ваших планов и бизнес-правил.
