## 3. The three rules, as predicates

**(1) Provider-structural inclusion.** A metric field the declared provider does not report
*separately* because it is definitionally contained in another reported field is a MEASURED `0`
carrying a mandatory `inclusion_bases` entry keyed by that field's exact JSON pointer and closed to
`provider` / `contained_field` / `containing_field` / `evidence_ref`. The permitted instantiations
are a declared set closed at exactly one row —
`claude-code:reasoning_tokens:output_tokens` — and the rule binds in both directions: an entry
outside the set, on a field the pointer does not name, on a non-zero value, naming a null
containing field, or attributing the measurement to a provider other than
`provider_scope.provider` is invalid; and a bare `0` in that one field, under that one provider, in
an envelope that is not a rule-(2) structural zero and carries no entry, is *also* invalid. Cost is
absent from the set by construction, so a `cost_microunits` derived from tokens times a rate cannot
be declared through this rule (D25 unchanged).

**(2) Structural zero envelope.** An envelope of a component that makes no model call is a measured
all-zero envelope carrying a mandatory `zero_bases` entry keyed by that envelope's exact JSON
pointer and closed to `component` / `path` / `statement`, where `path` is a repository-relative
committed path that must resolve in the tree the adjudication runs against. The eligible components
are a declared set closed at exactly `coordinator`: a `worker` envelope is the model call itself
and is never a structural zero, and a component that *could* call a model but did not stays
`unknown`. Reverse direction: an all-zero `coordinator` envelope with no entry is invalid — an
undeclared all-zero envelope is indistinguishable from "we did not look".

**(3) Single-provider economic scope.** `single-provider` + a provider from the closed set + a
non-empty Owner D# is a COMPLETE economic scope: no scope penalty, no disabled branch, every
threshold/formula/floor/reason code unchanged, and no new reason code. It is never rendered as
parity: the parity shape under `single-provider` stays ineligible exactly as in v1, and no evidence
entry may attribute a measurement to another provider. `inclusion_bases` is admissible *only* under
`single-provider` — the inclusion rule can never quietly rescue a parity claim, which is precisely
why codex (no cost surface at all) stays outside the economic lane under D126.

## 4. Why the v2 verdict cannot drift from v1's

`validate-economy-evidence.py`'s v2 path does not re-implement adjudication. It gates the two v2
carriers and then calls the **v1 `adjudicate` function** over the *v1 view* of the v2 input (the
two carriers removed, the two version strings restored). Every threshold, formula, denominator,
branch and reason code is therefore the same code object that P1.5 froze — divergence is
structurally impossible, not merely tested. The v1 argument list and the v1 code path are
untouched; `--contract-version` defaults to `1.0.0`, and `--v1-cases`/`--tree-root` are refused
outside `2.0.0`.

## 7. The v1 regression assertion, and why it is mechanical

The v2 run does not hand-copy the twenty v1 cases. It loads the frozen
`economy-evidence-cases-v1.json`, lifts its `base_input` by exactly four operations — the two
version strings and two empty carriers — **asserts that the lift changed nothing else**
(`set(lifted) - set(base) == {inclusion_bases, zero_bases}` and the only differing pre-existing
keys are `schema_version`/`contract_version`, or the run fails), applies each v1 case's own
mutations unchanged, adjudicates through the v2 path, and requires each v1 expectation to hold
byte-for-byte. All twenty hold. No v1 verdict, eligible-branch list, reason-code list or asserted
metric moved.

Why the two new rules do not fire on any v1 case, checked case by case: the v1 base input is
`parity` scope (rule (1) is single-provider-only), its two single-provider cases both declare
`codex` (outside the one instantiation row, whose provider is `claude-code`), and no v1 envelope is
all-zero (the base coordinators carry non-zero input/output/cost/duration/turns —
`100/0/100/0/200/200/1` on candidate and baseline, `150/0/150/0/300/300/2` on workflow — and no v1
mutation zeroes one), so rule (2)'s reverse direction never triggers. This is a property of the
frozen fixtures, not an exemption in the rules.
