# Roadmap: declared execution batch must be authoritative at item selection

**Статус:** ⬜ к внедрению. **Критерий сработал:** Agelto,
`2026.08.09-RELEASE-READINESS`, B3-READINESS (`P3.1–P3.5`), 2026-08-11.
**Владельцы:** `packages/task` (canonical plan protocol, selection/preflight, linter, generated
provider commands). **Не владелец:** конкретный план Agelto, память агента или только его
финальная проза.

## Что было проигнорировано

`plans/2026.08.09-RELEASE-READINESS/roadmap.md` дважды объявляет один обязательный batch:

| Носитель | Норма |
|:--|:--|
| «Матрица решений по группировке», строка P3 | `P3.1–P3.5` → `B3-READINESS`, один runtime context; root-cause escalation останавливает серию |
| «Карта исполнения», строка P3.1 | единственный запуск: `task:plan-run … P3.1-P3.5` |
| Строки P3.2–P3.5 | `↑`: не самостоятельные launch targets, а продолжение B3-READINESS |
| `phases/P3/P3.md`, Sequence and orchestration | строгая evidence→fix→readiness→E2E→recovery цепь с общим Docker/Composer/docs hotspot |

Несмотря на это, запрос и фактическое выполнение были сведены к `P3.1`, затем к `P3.2`.
Это нарушило не product scope каждого item, а **декларированную единицу исполнения**: batch должен
был выбрать один root, продолжить связанные manual items в общем контексте и остановиться только
на его собственном escalation/owner gate.

## Наблюдаемая причинная цепочка

1. Владелец вызвал `$ task:plan-run 2026.08.09-RELEASE-READINESS P3.1`.
2. `task:plan-run` принимает одиночный аргумент (`argument-hint: <PLAN-ID> Pn.m [Pn.k]`) и
   наследует read path `plan-exec`.
3. Для Layout v2 обязательные пять слотов — `plan.md`, phase context, item spec, bundle, state.
   `roadmap.md` не входит в этот preflight-read set. Команда не обязана открыть batch map до
   начала работы.
4. Runtime получает выбранный item, но не имеет parser/contract, который сопоставляет `P3.1` с
   `B3-READINESS`, его полным ordered membership и canonical invocation `P3.1-P3.5`.
5. Поэтому direct single-item invocation не получает `ROADMAP_BATCH_REQUIRED`; он исполняется как
   легальный standalone item. После закрытия handoff строит локальный Next для P3.2, а не
   continuation receipt исходного batch.
6. Правило в `plan-exec.md` о том, что launch-block сверяется с `roadmap.md` и выбирает команду
   группы, находится в **expected output после выполнения**. Оно не защищает начальный выбор и
   слишком поздно предотвращать already-split batch.
7. Агент дополнительно отнёс roadmap к необязательной «подсказке», хотя сам план называл её
   «Карта исполнения», а задача `plan-run` по определению исполняет именно её. Это ошибка
   интерпретации, которую существующая модель данных позволила, а не причина, которой можно
   оправдать нарушение.

## Почему существующие гейты этого не поймали

- `plan-lint` валидирует item spec/state, handoff и внутреннюю согласованность, но не доказывает,
  что requested subset совпадает с declared batch membership;
- `task_contract.build(plan_dir, item_id)` строит контракт для одного item и routing row, не
  возвращает execution-group identity;
- semantic `Next` уже поддерживает несколько item IDs, но они не извлекаются из project roadmap
  и не сравниваются с входом команды;
- roadmap — свободный Markdown с таблицами/стрелкой `↑`, без versioned machine-readable schema;
- provider projection предписывает launch-block, но не обладает durable selection receipt,
  связывающим invocation, roadmap digest и факт исполнения всех членов группы;
- пользовательский direct argument имеет неявный приоритет над группой, потому что явный
  precedence rule отсутствует.

## Требуемое решение

Ввести отдельный versioned carrier `execution-batches@v1`; Markdown roadmap остаётся его
человеческим представлением, но не единственной парсируемой истиной.

1. План хранит machine-readable batch map (например, `execution-batches.json` или строго
   schema-validated section `roadmap.md`): ID, ordered items, exact canonical command, required
   route/review, context boundary, stop conditions, owner gates, source digest.
2. До mutation `plan-run`/`plan-exec`/`plan-close` читают batch map и резолвят requested item(s).
   Выбор `P3.1` при membership B3-READINESS не начинает работу, а возвращает
   `ROADMAP_BATCH_REQUIRED` с единственной canonical command `task:plan-run <ID> P3.1-P3.5`.
3. Разрешены только: точный весь batch, declared solo, или explicit resume-subset после durable
   batch checkpoint/stop condition. Частичный direct invocation не является resume сам по себе.
4. Batch run сохраняет `batch_id`, ordered membership, invocation digest, completed prefix,
   stop disposition и handoff digest в journal/run receipt. Handoff после P3.1 обязан сохранить
   continuation B3-READINESS, а не молча редуцировать её до P3.2.
5. Любое расхождение между roadmap batch map, phase sequence, Routing и item states fail-closed:
   `ROADMAP_BATCH_AMBIGUOUS`/`ROADMAP_BATCH_STALE`, без эвристического выбора. Владелец либо
   `plan-design` явно реопенит карту.
6. `plan-lint` validates both directions: every non-solo map item has exactly one batch, every
   batch has contiguous ordered members and one canonical invocation, and `↑` has no independent
   command. Renderer derives provider-neutral and native launch blocks from the resolved batch.
7. Existing plans migrate forward-only. Пока карты нет, режим legacy explicitly reports
   `batch-map=absent` и не притворяется, что одиночный запуск одобрен roadmap; migration may
   create only owner-reviewed map, never infer it from prose.

## Приемка

- fixture, эквивалентный Agelto B3, делает direct `P3.1` RED до journal/mutation с
  `ROADMAP_BATCH_REQUIRED` и точной командой `P3.1-P3.5`;
- exact `P3.1-P3.5` создаёт один batch receipt и последовательно допускает P3.1…P3.5,
  сохраняя item-level commits/validation/handoffs;
- root-cause escalation после P3.1 останавливает batch, materializes permitted resume target и
  не выдаёт P3.2 как unconditional Next;
- no-op/green P3.1 сохраняет batch continuation; P3.2 не может быть запущен отдельно без
  checkpoint, созданного тем же batch;
- mismatch phase sequence ↔ map, non-contiguous range, duplicate member, `↑` with command,
  route mismatch и stale digest fail closed;
- plan-lint, state/status/decisions и both provider projections pass against green fixture;
- regression test asserts that roadmap consultation happens **before** item state becomes
  in-progress, not only when final launch-block is rendered.

## Evidence and implementation loci

- `agelto/plans/2026.08.09-RELEASE-READINESS/roadmap.md:17,46–50` — B3 declaration and exact
  canonical range;
- `agelto/plans/2026.08.09-RELEASE-READINESS/phases/P3/P3.md` — strict coupled sequence and
  common hotspot;
- `packages/task/commands/plan-run.md` — single-item admission plus v2 delegated read path;
- `packages/task/commands/plan-exec.md` — late, output-only roadmap consultation;
- `packages/task/lib/task/task_contract.py`, `command_render.py`, journal/state and plan-lint
  seams — present single-item/Next machinery that needs an explicit batch contract.

## Non-goals and safety

This change must not turn every adjacent item into a batch, remove item-level validation/commits,
or let a batch bypass owner gates, routing or escalation. Its only authority is a plan-declared,
validated execution group. If that declaration is absent or ambiguous, the tool asks for plan
design rather than deciding from conversational context.
