**Implementation Rules:** Live registry data may resolve a root only; before any observation the runner recomputes the sealed stable project identity and rejects missing, duplicate, moved-to-different-repository or preimage-drift rows. RAG:— (repo-grounded: D26 and P0.1 revised locator boundary) Classification and action are separate exact enums: `ambiguous` only permits `no-op-unresolved`; `local-override` permits `preserve` or owner-approved `register-override`; destructive action requires `skm-managed` proof plus a separately approved exact preimage/rollback. RAG:— (repo-grounded: D28 and P0.2 gates) Each transaction ID is derived from manifest hash, destination item, stable project ID, ordered action IDs and frozen source/contract identities. Before mutation the runner append-writes canonical `before`, flushes, `fsync`s, reopens and verifies the entire ordinal/`prev_event_sha256` chain. It appends each later boundary similarly and derives aggregate results only from terminal `accepted|rolled-back` states. Acceptance is project-atomic after all selected-provider readbacks; a partial state never advances the cursor. Resume validates the chain and frozen inputs, selects the first non-terminal manifest transaction, then: exact planned postimage → fresh readback and `accepted`; failed/partial planned postimage → rollback and exact-preimage `rolled-back`; exact preimage → reconciled `rolled-back`; any third state/missing backup/mixed image/source drift → refuse all remaining actions. RAG:— (repo-grounded: D47 and `research/05-p5-consumer-migration-design.md`) The runner only sequences terminal P3/P4 public plan/apply/readback calls and validates evidence; it must not render, infer ownership, edit provider targets directly or translate output.
