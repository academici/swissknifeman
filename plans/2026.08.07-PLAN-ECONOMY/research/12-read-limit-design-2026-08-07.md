# 12 — Лимит одного чтения: модель среды, форма артефакта, процедура зонда (2026-08-07)

Слой 2 (авторский синтез). Сырьё — `findings/15-read-limit-probe-2026-08-07.md` (семь наблюдений
собственного зонда). Документ **замещает `research/02-p0-measurement-design.md` §4** в части единицы
лимита, формы артефакта и процедуры зонда; всё остальное `research/02-…` остаётся в силе. Решения,
принятые владельцем по этому синтезу, — D107, D108, D109 плана.

## 1. Что понадобилось решить

`research/02-…` §4 писал процедуру под ОДИН лимит в токенах, читаемый из текста отказа. Зонд
исполнения (P0.2, `plan-exec`) получил отказ в байтах и остановился по Code Guidance — правильно, но
предпосылка item'а действительно оказалась неполной. Собственный зонд этой сессии показал, что среда
несёт **два независимых гейта**, а «расхождение» было наблюдением двух разных из них.

## 2. Модель среды: два гейта

| | Гейт A — размер файла | Гейт B — содержимое чтения |
|:--|:--|:--|
| Единица | байты файла на диске | токены счётчика харнеса по ОТРЕНДЕРЕННОМУ выводу |
| Значение (2026-08-07) | 262144 (сообщается как `256KB`, KiB) | 25000 |
| Поведение | жёсткий отказ, ноль контента | три формы, см. §2.1 |
| Область | только чтение файла ЦЕЛИКОМ | любой возвращаемый срез |
| Обход | `offset`/`limit` снимает гейт | не снимается: срез тоже меряется |
| Проверяется | первым | вторым |

Порядок доказан O1: файл, превышающий оба порога, дал байтовое сообщение.

**Величины не конвертируются друг в друга.** На русском markdown плана 25000 токенов ≈ 66–78 КБ (по
парам §5 `findings/15-…`), то есть гейт B срабатывает НАМНОГО раньше гейта A; на плотном ASCII
(hex/base64) соотношение обратное — 262144 байта дают порядка 170к токенов, и первым срабатывает
всё равно B, но по совсем другому коэффициенту. Фиксированного множителя между гейтами нет, поэтому
один из них вывести из другого нельзя — это и есть содержательная причина держать оба.

### 2.1 Три формы гейта B

1. **Постраничная обрезка** (многострочный файл, чтение целиком): выдаётся префикс строк + маркер
   `showing lines 1-N of M total (T tokens, cap 25000)`. Отказа НЕТ — есть тихая частичная выдача.
2. **Посимвольная обрезка** (файл с очень длинными строками): выдаётся первый префикс символов +
   маркер `showing the first N of M characters (T tokens, cap 25000); … cannot be paginated by line`.
3. **Жёсткий отказ** (`offset`/`limit`, срез которого сам превышает кап):
   `File content (T tokens) exceeds maximum allowed tokens (25000)` — ровно та форма, которую
   `findings/00-…` §7 наблюдал и под которую `research/02-…` §4 писал процедуру.

Формы 1–2 — и есть дефект КОРРЕКТНОСТИ, ради которого заведён план: исполнитель получает подмножество
файла и штатный текст «дочитай сам», а гарантия «всё нужное несёт план» не выполняется молча.

## 3. Форма артефакта `packages/task/configs/read-limit.json`

Оба гейта — отдельными типизированными полями (D107). Поле `limit_tokens` из `research/02-…` §4
не сохраняется даже как синоним: одно скалярное поле в среде с двумя гейтами обязано соврать.

```json
{
  "version": "1.0.0",
  "measured_at": "<ISO-8601 UTC>",
  "environment": {
    "platform": "linux",
    "harness": "claude-code",
    "harness_version": "<если доступна>",
    "model_id": "<модель сессии зонда>"
  },
  "tool": "Read",
  "limits": {
    "size_bytes": {
      "value": 262144,
      "unit": "bytes",
      "reported_as": "256KB",
      "severity": "refusal",
      "scope": "whole_file_read"
    },
    "tokens": {
      "value": 25000,
      "unit": "tokens",
      "counter": "harness-read-counter",
      "severity": ["refusal", "truncation"],
      "scope": "rendered_read_output"
    }
  },
  "binding_for_plan_prose": "tokens",
  "probe": {
    "size_gate": {
      "path": "<путь пробного файла>",
      "bytes": 306751,
      "call": "Read(<path>)",
      "refusal_message": "<дословный текст>"
    },
    "token_gate": {
      "path": "<путь пробного файла>",
      "bytes": 128001,
      "chars": 128001,
      "lines": 1,
      "call": "Read(<path>, limit=1)",
      "tool_reported_tokens": 82901,
      "refusal_message": "<дословный текст>"
    }
  },
  "cross_check": {
    "note": "счётчик среды чтения ≠ токенизатор калибровки P0.1 (D15); только перекрёстная проверка",
    "pairs": [
      {"chars": 128001, "content_class": "dense_ascii_hex",
       "tool_reported_tokens": 82901, "token_estimate": 41095, "true_over_estimate": 2.017}
    ]
  }
}
```

Обязательные инварианты формы:

- `limits.*.value` — целые > 0; отсутствие любого из двух гейтов = невалидный артефакт (fail closed,
  D15 без изменений).
- `severity` гейта B — список, потому что одна и та же величина проявляется и отказом, и обрезкой;
  потребитель обязан считать обе формы нарушением условия (D108).
- `probe.*.refusal_message` — дословный текст, а не пересказ; он и есть доказательство замера.
- `cross_check` НЕ является калибровочным входом и потребителями калибровки не читается (D15).

## 4. Процедура зонда — дешёвая и воспроизводимая

Ключевое свойство, найденное зондом: **счёт среды и кап можно получить, не заплатив за контент**.
Форма 3 гейта B (§2.1) возвращает ноль контента и при этом называет оба числа. Отсюда процедура из
двух обязательных шагов, каждый стоит нисколько:

1. **Гейт A.** Взять существующий файл > 256 КБ (годится крупный `plan.md` флота) и прочитать его
   ЦЕЛИКОМ. Записать дословный отказ, размер файла в байтах и заявленный кап. Единица «KB» — KiB:
   `байты / 1024` обязано совпасть с числом в сообщении, иначе среда считает иначе и это отмечается.
2. **Гейт B.** Сгенерировать однострочный плотный файл заведомо выше капа и прочитать его с
   `limit=1`:

   ```python
   import hashlib, pathlib
   pathlib.Path("/tmp/read-limit-probe.txt").write_text(
       "".join(hashlib.sha256(str(i).encode()).hexdigest() for i in range(2000)) + "\n")
   ```

   Отказ вернёт и счёт файла средой, и кап. Записать дословно; сюда же берётся пара `cross_check`
   (символы файла → счёт среды → оценка `task.token_estimate` на том же тексте).

Формы 1–2 гейта B (обрезка) в exec-прогоне **не воспроизводятся намеренно**: каждая стоит полной
страницы (до 25000 токенов контекста), а нового числа не даёт — кап уже получен шагом 2. Их
наблюдения зафиксированы в `findings/15-…` O3/O4 как поведение среды и цитируются справкой.

Бисекция границы не нужна ни для одного гейта — среда называет оба числа сама.

**Признак смены среды** (для справки `read-limit-probe.md`): любое расхождение с записанным
артефактом — другое число капа, другая единица в сообщении, исчезновение одной из форм, появление
третьего гейта. Реакция — перезамер и новая версия артефакта, а не правка числа руками.

## 5. D2(б) читается строго (D108)

```
pass(f) = bytes(f) ≤ limits.size_bytes.value  AND  est_tokens(f) ≤ limits.tokens.value
```

Обязательный к чтению файл обязан читаться ЦЕЛИКОМ ОДНИМ вызовом. Постраничное дочитывание условие
НЕ удовлетворяет: именно тихая частичная выдача (§2.1, формы 1–2) и есть дефект корректности,
названный `findings/00-…` §7 — исполнитель видит подмножество на своё усмотрение, и ни линтер, ни
аудит этого не ловят.

Токенная сторона проверяется ОЦЕНКОЙ СВЕРХУ (артефакт калибровки P0.1), а не счётом среды: счёт среды
наблюдаем только в момент срабатывания капа (O6), то есть в CI недоступен. Направление ошибки при
этом безопасное — пока оценка не занижает (см. §6).

Последствия, названные прямо:

- Собственный `plan.md` этого плана (306751 байт) не проходит ОБА гейта; `phases/P*.md` (72–172 КБ,
  оценка 25–60к токенов) не проходят гейт B. Это не новость и не новая работа: расщепление носителей
  — предмет фазы P2, а условие D2(б) ровно его и требует.
- Гейт B — связывающий для прозы планов; гейт A остаётся вторым условием и ловит класс, который
  токенный гейт пропускает: токен-разрежённый крупный файл (длинные пути, повторы, машинный дамп).

## 6. Граница оценщика P0.1 — корпус-условна (D109)

Пары `findings/15-…` §5: на плотном ASCII оценщик занижает счёт среды примерно ВДВОЕ (1.972 и 2.017),
на реальной прозе плана граница держится. Причина — класс контента: калибровочный корпус P0.1 состоит
из 14 файлов планов флота (проза, таблицы, эмодзи-статусы), ставка `ascii_word` = 0.295 токена на
символ, тогда как случайный hex токенизируется примерно 1 токен на 1.5 символа.

Реокалибровка сейчас НЕ производится, и на то две причины, а не одна:

1. **Формальная.** Наблюдение снято счётчиком СРЕДЫ ЧТЕНИЯ, а D15 прямо запрещает калибровать по нему
   оценщик — это разные измерители. Как cross-check наблюдение законно; как калибровочная точка —
   нет. Реокалибровка потребовала бы прогона дифференциального харнесса P0.1 на расширенном корпусе,
   то есть реопена P0.1.
2. **Содержательная.** Неизвестно, встречается ли плотный ASCII на ОБЯЗАТЕЛЬНЫХ путях чтения флота и
   в какой доле. Реокалибровать «на всякий случай» — назначить работу до измерения, ровно то, что
   план себе запретил.

Поэтому измерение встраивается в уже запланированные items:

- **P0.3** считает и печатает по каждому файлу `dense_ascii_share` — долю символов файла, входящих в
  непрерывные прогоны длиной ≥ 32 символов из `[0-9A-Za-z+/=]` без пробельных разделителей; величина
  попадает в `--json`. Порог здесь НЕ вводится: пороги замораживает P0.5.
- **P0.4** добавляет в отчёт раздел о распределении `dense_ascii_share` по обязательным путям флота:
  сколько файлов и в каких долях, и попадают ли такие файлы в `Required Reads` вообще.
- **P0.5** получает это распределение как вход и принимает владельческое решение: нужна ли
  реокалибровка P0.1 с пятым классом (реопен P0.1) или ограничение фиксируется в контракте
  `read-budget` как названная граница применимости.

До этого решения ограничение существует явно: **свойство «оценка не занижает» доказано на корпусе
прозы планов и не доказано на плотном ASCII.** Формулировка обязана попасть в контракт `read-budget`
независимо от исхода — как условие применимости числа, а не как сноска.

## 8. Что рассматривалось и отвергнуто

- **Только токены** (сохранить D15 дословно). Отвергнуто: теряется класс «жёсткий отказ на
  токен-разрежённом файле > 256 КБ», а он наблюдён первым же зондом.
- **Только байты.** Отвергнуто замером: для прозы планов связывающий гейт — токенный, байтовый почти
  никогда не срабатывает первым.
- **Конвертировать один гейт в другой коэффициентом.** Отвергнуто: коэффициент «байты → токены»
  меняется вдвое между классами контента (§2), фиксированного множителя нет.
- **Считать пагинацию выполнением D2(б).** Отвергнуто владельцем (D108): это сохранило бы ровно тот
  сценарий, который план назвал дефектом корректности.
- **Реокалибровать P0.1 немедленно.** Отвергнуто (§6): нарушило бы D15 как источник калибровки и
  назначило бы работу до измерения её нужности.
- **Воспроизводить формы обрезки в exec-прогоне.** Отвергнуто: стоит до 25000 токенов контекста и не
  даёт числа, которого не даёт дешёвый шаг 2 (§4).
