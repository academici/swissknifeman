## 1. Критерий (сформулирован ДО просмотра списка, записан также в
`packages/skiller/docs/guide/skill-taxonomy.md` §«context: fork — критерий отбора»)

Процедурный скилл с задачей, НЕ справочник:

1. Тело даёт исполнимую процедуру (пронумерованные шаги/алгоритм) с итоговым артефактом или
   проверяемым результатом — не только конвенции/best practices.
2. Задача самодостаточна: не требует истории разговора текущей сессии и не читает состояние
   самой сессии.
3. Побочный эффект — локальный (файлы репозитория, git-состояние worktree), не запись во
   внешнюю систему без возможности безопасно проверить срабатывание на стенде.
4. Скилл, несущий канон для ОСНОВНОЙ сессии (стоячие инструкции, читаемые многократно за
   сессию — `plan-protocol`, весь контур `task:plan-*`, CORE-девятка), форку не подлежит.
5. Сомневаешься в классе — не форкать (fail-safe: ложный форк = пустой ответ субагента в
   проде; ложный отказ = только неполученная экономия).

## 2. Прогон критерия по реестру (229 скиллов)

## 5. Честная граница и побочные находки (Pending Work — НЕ чинится этим item'ом)

- **`resolving-merge-conflicts` заблокирован на permission-gate записи файла** в headless
  `-p`-режиме без интерактивного апрува (Write/Edit denied) — это поведение sandboxing
  `-p`-режима, НЕ дефект `context: fork`: модель корректно провела ВЕСЬ анализ (нашла
  `MERGE_HEAD`, верно синтезировала обе стороны конфликта) и остановилась именно на записи,
  как и положено при отсутствии гранта. Ось B (непустой содержательный результат) этим не
  опровергается — задача выполнена до последнего шага, отчёт о блокере содержателен.
- **`db-test-preflight`: попутно найдены 3 реальных дефекта в собственных `snippets/`**
  (`composer-scripts.json:8` — неэкранированный `$c` ломает PHP-скрипт; `preflight.sh:82-91`
  — падение миграции проглатывается `|| echo`, противоречит шагу 8 самого скилла;
  `preflight.sh:33-35` — источник имени тестовой БД не учитывает `tests/bootstrap.php`) —
  ЗАПИСАНО, НЕ исправлено (вне Scope Included этого item'а — правка snippets отдельного
  скилла не входит в задачу «простановка `context: fork`»; Implementation Rules плана:
  «улучшить бы заодно» → Pending Work, не делать).
- **Кандидаты, требующие отдельного стенд-режима для безопасной проверки внешних
  side-effects** (`to-issues`, `issue-triage` — пишут в GitHub tracker) — не форкнуты в этом
  заходе; структурный критерий пере-открытия: способ проверить «форк сработал» БЕЗ реального
  постинга (мок `gh` или аналог).
- **`quality/tech-debt-audit`** — правдоподобный кандидат, не разобран поштучно в этом заходе
  (проход держит запрет батча) — адрес пере-открытия: следующий проход по этому же критерию.

## 6. Находки методики стенда (не про сами скиллы — про артефакт этого item'а)

- Первая версия `p3-4-fork-selection-bench.sh` деплоила `.claude/skills/<bucket>/<name>/` (по
  образцу пути реестра) — REAL explicit-путь дал `Unknown command` для всех 4 кандидатов.
  Причина: реальная раскладка флота ПЛОСКАЯ (`skillset.py` — `.claude/skills/<name>/`, bucket
  отбрасывается при физическом sync). Исправлено на плоскую раскладку — explicit заработал
  для всех 4 (§4). Названо явно, т.к. это отдельный урок методики стенда, не наблюдение о
  скиллах.
- Фикстура git-конфликта для `resolving-merge-conflicts` требует identity-env
  (`GIT_AUTHOR_NAME`/`GIT_COMMITTER_NAME`+email) на КАЖДОМ git-вызове, включая сам `merge` —
  на одном прогоне без identity на вызове `merge` git падает `rc=128 «unable to auto-detect
  email»` ДО создания `MERGE_HEAD`, и конфликт молча не создаётся (ложный «пустой» стенд).
  Исправлено: identity-env закреплён на всех вызовах, `git_conflict_repo()` теперь
  ассертит `MERGE_HEAD` существует после `merge` (fail loud, не тихий пропуск).
- `refactoring-plan` auto-путь занимает ~250–300с (генерирует полный 10-шаговый план) —
  таймаут артефакта поднят с 180 до 420с; дефолт `eval.py` (180с) для содержательных
  генеративных задач тесен, отдельно от синтетических zz-фикстур P3.1.
