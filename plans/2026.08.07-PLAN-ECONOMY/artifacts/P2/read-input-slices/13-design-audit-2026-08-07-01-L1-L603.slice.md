### F1 · Blocker · confidence high · issue · `packages/task/lib/task/task_contract.py:511`

**Компилятор Pre-mutation/Pre-final — обязательный гейт закрытия КАЖДОГО item'а — не покрыт ни одной
фазой плана и жёстко зашит на раскладку v1.**

`plan-exec.md:53` («ОБЯЗАТЕЛЬНЫЙ шаг, не условный», шаг 2), `plan-exec.md:140` (Pre-final, шаг 7) и
`plan-close.md:61` (шаг 4) зовут `task_contract.build("plans/<PLAN-ID>", "<Pn.m>")`, а гейт закрытия
БИНАРЕН: `pre_mutation == "allow" and pre_final == "allow"`. Строка 511 модуля:

```python
phase_path = plan_dir / "phases" / f"{phase_token}.md"
```

Это не резолвер — это литеральный путь v1, ровно тот класс дефекта, который `phases/P2.md`
Phase Context называет своим первым предметом для `plan_lint` («сегодняшний линтер ищет фазы как
`phases/*.md` нерекурсивным глобом и каталог `phases/P2/` не увидит вовсе»). Для `plan_lint`,
`plan_weight`, `verify-citations.py` и `cross-plan-files.py` переход на резолвер назначен (P2.1,
D74); для `task_contract` — нет: строка `task_contract` не встречается ни в одном `Files`, ни в
одном `Производит`/`Границы` контракт-блока, ни в D82, ни в реестре диспозиций P3.6 (он покрывает
проверки `plan_lint`, не компилятор контракта), ни в P6.1/P6.2 (путь чтения и производство записей).

**Воспроизведено.** Копия этого плана, у которой `phases/P0.md` превращён в `phases/P0/P0.md` +
`phases/P0/P0.1.md` (форма v2 по P2.3):

```
BUILD FAILED: TaskContractBuildError P0.1: item: no item block found in <tmp>/phases/P0.md
--- контроль: та же сборка на v1-раскладке ---
BUILD OK (v1)
```

**failure_scenario.** P2.8 мигрирует план на v2 (Deliverable, необратимо, «до неё дерево чистое»).
Исполнитель P3.1 обязан начать с шага 2 `plan-exec`: `task_contract.build` резолвит `phases/P3.md`,
которого больше нет, и поднимает `TaskContractBuildError`. По собственной таблице `plan-exec.md`
это класс «структурный» → «СТОП: D#-запись, реопен-кандидат P2.6 (владелец `build`), НЕ тихая
правка здесь». Владелец механизма — фаза P2, уже терминальная: чинить придётся реопеном §3 либо
внеплановой правкой чужого модуля. Альтернативный исход хуже: исполнитель молча пропускает
write-site, и тогда каждый из 30 items (P3.1–P6.9) закрывается без напечатанных кодов обеих границ
— по правилам `plan-audit` это находка **Major на каждый item**, тридцать раз подряд.

Ещё два входа компилятора меняются той же миграцией и в плане не разобраны: пять полей исхода
уезжают в генерируемую проекцию (D33), а `Version`/`Status`/`Last Updated` — в `status.md` (D32),
тогда как `build` читает `plan.md` через `plan_lint.parse_plan_md` (`task_contract.py:510`).
