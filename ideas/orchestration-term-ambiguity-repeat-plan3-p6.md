# Идея: слово «оркестрация» читается двояко; тот же сбой повторился в PLAN3 P6 (vaulter), и кондуктор после переноса планов в workspace не стартует

Статус: идея, не реализовано. Источник: сессия оркестрации PLAN3 (vaulter), фаза P6, 2026-10-18.
Связано: `orchestrator-session-bypasses-conductor.md` (тот же сбой на P4.5–P5.3 — повтор, а не новая находка),
`conductor-ignores-plan-review-policy.md`, `plan-must-not-prescribe-executor-workflow.md`,
`conductor-adopt-and-write-set-mismatch.md`, `plan7-bridge-research-outside-checkout.md`.

## Что произошло

Поручение владельца: «работай по 6й фазе в режиме оркестрации, используй настройки ревью и батчинга».

1. Сессия (Sonnet 5.5 medium) прочитала `knowledge/orchestration` плана и исполнила его буквально: секция `#how` говорит
   «Исполнитель — нативный субагент (Agent, `general-purpose`)», «цикл пункта: `plan.py next/start/finish/commit`
   вызывает оркестратор». Пункты P6.1–P6.7 и три fix-коммита (RC-P6-1, RC-P6-2, красные тесты) выполнены субагентами
   инструмента Agent; `plan.py` вызывался самой сессией; ревью — ручной `codex exec`.
2. Кондуктор (`orch conduct run`) не запускался вообще. «Настройки ревью и батчинга» сессия поняла как таблицы плана
   (`item-map-p6`, батчи B1–B8, `review-map-p6`), а не как опции кондуктора (`--batch`, `review.*`, `reviewer`).
3. Владелец остановил запуск P6.8 (агент уже работал): «кто тебе разрешил вызывать агента не через оркестрацию».
   Сессия честно ответила «никто, я так понял `orchestration#how`», остановила агента, нашла `orch conduct`.
4. Первые два запуска кондуктора: `CLAIM_BLOCKED` (`ITEM_OWNED` — пункты уже начаты вручную `plan.py start`).
   Для освобождения пришлось `finish --status blocked` + `reopen` (иного способа снять `in_progress` нет).
5. Третий: `CLAIM_BLOCKED` / `ROUTE_UNDERSHOOT` (P6.8 — frontier, кондуктор по умолчанию даёт sonnet/implementation).
   Помог `--options` с `stages[{role: executor, model_class: frontier}]` (проверено `--dry-run`).
6. Четвёртый: `BRIEF_REFUSED` / `WORK_SOURCE_FAILED`: мост `planner-orch brief` падает
   `ValueError: '<home>/workspaces/axioma/projects/vaulter/local/state/artifacts/sha256/…' is not in the subpath of …`.
   Артефакт брифа лежит в portable workspace, проверка «путь внутри проекта» (`relative_to(project_root)`) его отвергает.
   Следствие переноса планов в workspace (маркер `.swissknifeman/project.json`: `plans_store: workspace`; коммиты vaulter
   `a6b68cca`, `67dda924`). Кондуктор для такого проекта не стартует вообще: ни один пункт не пройдёт.

Итог: 7 пунктов и 3 fix-коммита сделаны не кондуктором, две стороны (владелец и сессия) понимали «оркестрацию» по-разному;
на момент записи P6.8 и P6.9 сброшены в `todo`, кондуктор заблокирован багом п. 6.

## Почему так вышло

1. **«Оркестрация» — три разные вещи в одном проекте, и нигде не сказано, какая главная:** `orch conduct run` (кондуктор),
   `planner:plan-run` (ручная команда плана), цикл «оркестратор + Agent-субагенты» из `knowledge/orchestration#how`.
   Для сессии, у которой всегда есть инструмент Agent, третий вариант — путь наименьшего сопротивления.
2. **План описывает ручной цикл** (`#how`) — ровно та проблема, что в `plan-must-not-prescribe-executor-workflow.md`.
   Документ плана, который сессия обязана прочитать, содержит инструкцию «как исполнять» и перекрывает слово владельца.
3. **Знание уже было записано, но не дошло до сессии.** Идея `orchestrator-session-bypasses-conductor.md` описывает тот же
   сбой и лежит в `swissknifeman/ideas/`. В контекст vaulter-сессии она не попала: `CLAUDE.md` проекта и `AGENTS.md` про
   `orch conduct` молчат (п. 7 той идеи — «одна строка в CLAUDE.md» — не сделан), `plan.py next` по-прежнему печатает
   `run-items: planner:plan-run …`, команды `/orch` нет. Идея без реализации = тот же сбой на следующей фазе.
4. **Сессия не сверилась с историей:** не посмотрела, как выполнялись P1–P5 (`.swissknifeman/orch/reports`, `orch-artifacts`
   с запусками кондуктора), и не переспросила владельца при неоднозначном слове. Два сигнала были на виду.
   Уточнение владельца: «не прочитала нужный файл» — не объяснение. Вся работа P6.1–P6.7 шла через Agent с первого пункта,
   P6.8 был тем же способом, а не новым выбором; единственная инструкция сессии — слово «оркестрация» в запросе, и оно
   было прочитано как схема `orchestration#how`. Исправление должно действовать на самое слово, а не на «чтение документов».
5. **Формулировка «настройки ревью и батчинга» не привязана к конфигу:** у кондуктора это `--batch/--no-batch`, `review.*`,
   `reviewer` (по умолчанию grok-4.7, выключено в `solo`); у плана — `batches[]`, `review-map`. Сессия выбрала план.
6. **Стоимость разворота скрыта:** ручной `plan.py start` до запуска кондуктора делает пункты «чужими» для кондуктора, а
   вернуть их можно только обходным `finish blocked` + `reopen`; это отбивает охоту возвращаться.
7. **Баг workspace-режима не покрыт тестом:** кондуктор + `plans_store: workspace` + бриф с артефактом, путь которого вне
   корня проекта (`plan7-bridge-research-outside-checkout.md` — того же класса: код предполагает, что всё под корнем).

## Как исправить в SKM

1. **Один термин.** В `docs/agent-mode.md` и в CLAUDE.md-блоке `project init`: «оркестрация = `orch conduct`». Ручной цикл
   `plan.py`+Agent называется «ручное исполнение» и разрешён только как явный fallback с `plan.py log --type deviation`.
2. **Слово «оркестрация» в запросе владельца приводит к одному действию** — загрузке `/orch` (команда/скилл из п. 8 прежней
   идеи): `orch conduct run --plan P --ready --batch [--adopt] [--debug] [--options …]` + наблюдение `status/observe`.
   Без обходных запусков Agent для ролей кондуктора. Текст команды не оставляет выбора «или так, или так».
3. **План не описывает «как исполнять»:** `knowledge/orchestration#how` (цикл, «исполнитель — Agent») заменяется ссылкой
   на кондуктор; `planner:plan-new`/audit помечает документ плана, предписывающий субагентов/`plan.py`-цикл, как дефект
   (развитие `plan-must-not-prescribe-executor-workflow.md`). Модель/effort/ревью — из `route`/`review` пункта и options.
4. **`plan.py next` печатает `conduct: orch conduct run --plan … --items … --batch`** первой строкой; `run-items: plan-run`
   — только если `orch` недоступен.
5. **Нельзя случайно «увести» пункт от кондуктора:** `plan.py start` без `--manual` в проекте с включённым кондуктором
   печатает предупреждение «пункт будет закрыт вручную, кондуктор его не возьмёт»; `plan.py release <item>`
   (или `orch conduct adopt`) возвращает `in_progress` в `todo` без `finish blocked`+`reopen` и без записи ложного
   `blocked` в историю.
6. **`ITEM_OWNED`/`ROUTE_UNDERSHOOT` называют готовую команду:** для `ITEM_OWNED` — `plan.py release …` / `--adopt`;
   для `ROUTE_UNDERSHOOT` — готовый `--options` либо кондуктор сам берёт `model_class` из `route` пункта (он его знает).
7. **Исправить мост `planner-orch brief` для `plans_store: workspace`:** артефакты брифа проверять относительно корня
   хранилища планов/workspace (или хранить в `<project>/.swissknifeman/orch-artifacts`), а не `project_root`. Тест: проект
   с `plans_store: workspace`, пункт с брифом, `orch conduct run --dry-run` и реальный `run` до стадии `brief`.
8. **`plan.py stats` помечает `engine: manual-agent|conductor`** для каждого закрытого пункта — доля ручных видна
   владельцу без разбора журнала.
9. **Спорное слово — вопрос, а не догадка:** в промпте оркестратора/`/orch` правило: если в запросе «оркестрация» и в
   проекте есть и кондуктор, и план с ручным циклом, сессия печатает одну строку «запускаю orch conduct run …» и идёт
   дальше (без вопроса «можно ли»), но НЕ выбирает Agent-цикл молча.

## Критерии приёмки

- В проекте с `orch` фраза «работай в режиме оркестрации» всегда приводит к `orch conduct run`; в журнале сессии нет
  Agent-запусков ролей executor/reviewer.
- `orch conduct run` стартует (до стадии executor) в проекте с `plans_store: workspace`.
- `plan.py release` возвращает пункт без `finish blocked`.
- `plan.py next` называет кондуктор; `CLAUDE.md` проекта после `project init` содержит правило «исполнение плана — `orch conduct`».
- `plan.py stats` показывает долю пунктов по `engine`.
