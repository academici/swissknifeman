# Политика полезной памяти: bounded writes, TTL и проверяемая очистка

**Статус:** ⬜ отложено до подтверждённой пользы. Это не задача на включение
автодайджеста: для consumer-проектов базовым режимом остаётся `MODE=manual`.

**Источник:** аудит `project:corex` 2026-09-26. В проектном scope было 15
фактов: полезный `active-handoff` смешан с историей фаз, тестовыми счётчиками
и routing-rejected попытками. Такой журнал плохо возвращается поиском и не
должен становиться контекстом на каждом запуске.

## Проблема и границы

Память нужна для cross-session continuity, межпроектных связей и решений,
которые нельзя надёжно восстановить из кода, Git или плана. Она не является
вторым Git, журналом сессии или хранилищем планов.

Текущий `maind` уже делает две правильные вещи:

- отклоняет `progress`, `plan-progress`, `checkpoint` и `session-log` в
  `store_managed()`;
- хранит один заменяемый `active-handoff` на scope.

Но произвольные `fact` остаются бессрочными: нативного TTL, фильтрации
истёкших фактов и проверяемой уборки пока нет. Нельзя объявлять срок жизни
только текстовым правилом — его должен исполнять memory port.

## Целевая политика записи

| Kind | Допустимое содержимое | Retention |
|---|---|---|
| `active-handoff` | Один текущий continuation: ссылка на план/Git, следующий шаг, блокер | singleton; истекает через 5 суток без refresh |
| `plan-context` | Невосстановимое из репозитория временное ограничение активного плана | 5 суток; требует `plan_ref` |
| `decision` | Долгоживущая причина решения с канонической ссылкой | без TTL только при `source_ref`; иначе 30 суток |
| `ecosystem-link` | Подтверждённая межпроектная связь и область видимости | без TTL, пока связь валидна |

Запрещены: пересказ исходников, состояние фазы, результаты тестов, команды,
модель/route, неудачные повторы и любые данные, уже живущие в плане, issue,
ADR, handoff-файле или Git. Запись без kind и provenance должна отклоняться,
а не превращаться в вечный `fact`.

## Предлагаемый контракт

Расширить memory port до явных метаданных:

```text
store(scope, kind, text, metadata, expires_at?) -> {id, expires_at}
recall(scopes, query, limit, now) -> live records only
prune(scope?, before, dry_run) -> {matched, deleted, skipped}
```

`metadata` минимально содержит `source_ref` для durable facts, `plan_ref` для
плановых и `created_at`/`expires_at`, назначаемые сервером. Клиент не может
передать бесконечный TTL для временного kind. Удаление идемпотентно и
аудитируемо по `id`, но audit хранит метаданные операции, не удалённый текст.

## Последовательность без ложной автоматики

1. Добавить allowlist kind, обязательные ссылки и серверное вычисление expiry;
   покрыть CLI, MCP и прямой `store_managed()` единым валидатором.
2. На `recall` скрывать истёкшие факты; добавить `prune --dry-run` и
   детерминированный отчёт, затем плановый idempotent prune.
3. Мигрировать старые facts только через dry-run классификацию: оставить
   links/доказанные decisions, удалить plan-journal и устаревшие handoff.
4. Проверить field-результат на нескольких consumer-проектах: число выдач,
   долю использованных recall, размер digest и first-turn tokens. Без такого
   результата не включать SessionStart digest.

## Критерии запуска

Работа становится исполняемым plan item, когда одновременно есть:

1. не менее двух project scopes с повторяемым шумом от устаревших плановых
   facts либо ручной cleanup занимает заметное время;
2. подтверждённый владелец retention-политики и миграции существующих записей;
3. field-метрика, по которой можно доказать улучшение recall или снижение
   контекста без потери нужного handoff.

До этого consumer-проекты используют `MODE=manual`, один
`active-handoff` и repository-first continuity. Это даёт пользу памяти без
стоимости постоянной автозагрузки.
