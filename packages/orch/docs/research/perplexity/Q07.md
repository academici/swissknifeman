## Краткий вывод

Нет: CAO не гарантирует, что каждый этап действительно запущен на выбранном «economy/frontier» классе модели и с запрошенным reasoning effort, и не описывает сквозную проверку фактически применённых значений. CAO умеет передать некоторые настройки конкретному CLI, но модельный каталог, доступность аккаунта, применение effort и биллинг остаются на стороне CLI/провайдера. Документация Grok, например, описывает grok_cli, а не grok_build; такого идентификатора в рассмотренных официальных страницах CAO нет.

## Поля модели и effort

- Claude Code (claude_code). Профиль CAO документирует поле model, но в описании запуска не указано отдельное поле CAO для reasoning effort. Запрос конкретной модели сам по себе не подтверждает, что она доступна или фактически выбрана: это зависит от Claude Code и учётных данных.
- Codex (codex). Текущая документация CAO задаёт настройки на профильном уровне через codexConfig, который передаётся Codex как -c key=value. Примеры включают model_reasoning_effort: "xhigh" и модельные/скоростные параметры; CLI-override применяется поверх Codex profile. В более общей формулировке документации CAO настройки модели, timeout и approval принадлежат Codex CLI, а не CAO. Ни один вариант не означает, что effort поддержан выбранной моделью или будет принят без ошибки.
- Grok Build (grok_cli). Документированный профиль задаёт model: grok-4.5; --model при запуске переопределяет его. В описанной форме команды и полях профиля нет CAO-поля reasoning effort. CAO советует сверять доступные конкретному аккаунту ID через grok models.
Отсюда: если «по этапам» означает разные supervisor/worker-профили, CAO позволяет задать им разные профильные параметры там, где провайдер их поддерживает. Но это передача настройки, а не доказательство фактически использованной модели или effort.

## Auth и оплата

- Claude: CAO описывает Anthropic API key или Claude subscription как способы аутентификации Claude Code. Это не равнозначно API-кредитам: документация CAO не обещает, что подписка превращается в API-баланс или оплачивает API-запросы. Используется конфигурация аутентификации установленного Claude Code.
- Codex: CAO перечисляет OpenAI API key и ChatGPT subscription/login; провайдер опирается на существующую авторизацию Codex CLI. Подписка ChatGPT и API-биллинг — разные основания оплаты; CAO не гарантирует наличие конкретного права доступа для текущего аккаунта.
- Grok: интеграция использует уже выполненный вход Grok Build либо XAI_API_KEY; CAO повторно использует имеющуюся авторизацию, но не выполняет login автоматически. Сам факт существования интеграции не гарантирует, что у пользователя есть Grok-доступ, нужная модель или подписка/квота. Проверять — в grok login и grok models.

## Разрешения: существенно разные

То есть одинаковое название профиля или allowlist не означает одинаковую границу безопасности: особенно рискованен Codex-дефолт --yolo, который делает sandbox неработающим; у Claude дефолт также пропускает проверки разрешений.

## Парсинг, версии и no-op

CAO определяет статусы и извлекает ответы разбором интерактивного TUI — это не подтверждение выбранной модели/effort. Codex-документация отдельно описывает версионные различия футера и spinner; Grok указывает тестирование на конкретных версиях и необходимость перепроверять поведение после обновлений.
Особенно важно: у Codex codexConfig передаётся как -c key=value, но CAO-документация не обещает, что каждый ключ валиден для каждой версии/модели. Неподдерживаемое значение нельзя считать «применённым» лишь потому, что CAO сформировал команду. Версионную совместимость следует проверять на установленном CLI и по его фактическому выводу/настройкам; CAO описывает статус-мониторинг терминала, а не верификатор фактического backend-маршрута.
Практический итог: используйте отдельные профили и явные настройки там, где они документированы; для Codex задавайте codexConfig.model и model_reasoning_effort, для Grok проверяйте доступность через grok models, а для Claude проверяйте выбранную модель средствами самого Claude Code. Не трактуйте CAO как гарантирующий маршрутизатор «economy/frontier» или аудит применения effort.
