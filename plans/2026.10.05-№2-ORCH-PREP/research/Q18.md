# Q18

Запрос (perplexity-web-mcp stdio, default pool; search):

```text
Python stdlib-only monorepo (several packages, each with its own CLI, plus shared root configs/ JSON files read by multiple packages). Answer in Russian, prose, max 500 words, with URLs to primary sources (PEPs, official docs of tools, well-known engineering blogs):
1) When a JSON config file has two drifted copies (root configs/X.json and packages/owner/configs/X.json) and a resolver prefers the root copy with fallback to the package copy, what are recommended patterns to consolidate to a single owner without breaking external readers: delete-and-redirect in the resolver, symlink, generated copy with --check gate, or a deprecation window? Pros/cons of each.
2) What lightweight mechanisms exist to enforce that every config file in a repo has a declared owner and at least one consumer (orphan config detection): CODEOWNERS, an inventory manifest checked by a unit test, grep-based reference tests, Bazel/Pants ownership? Which is proportionate for a small repo without build system?
3) For released config surfaces consumed by users (example files, presets discovered by glob), what is a sane deprecation policy (keep path, CHANGELOG Deprecated section per Keep a Changelog, removal in next major under SemVer 0.x)?
```

Ответ (как вернул сервис, 2026-10-07):

Для небольшого stdlib-only монorepo рекомендую канонический файл у пакета-владельца, временную совместимость старого публичного пути и JSON-инвентарь с проверкой через unittest. Это проектная рекомендация, а не требование Python: единственный редактируемый источник важнее единственного физического файла.

## 1. Устранение двух копий

Сначала разберите различия: сейчас root-копия определяет поведение resolver, поэтому переключение на package-копию без согласования содержимого само по себе меняет контракт. Владелец отвечает за содержание; расположение файла — отдельное решение.
Delete-and-redirect: удалить root-копию и направить resolver к владельцу. Плюсы — минимум механизмов, отсутствие рассинхронизации. Минус — совместимость сохраняется только для вызывающих resolver; прямой open("configs/X.json") и внешний glob сломаются. Подходит для внутренних путей после проверки потребителей.
Symlink: старый путь указывает на файл владельца. Обычно сохраняет прямое чтение без генерации. Недостатки — переносимость checkout и упаковки: Git for Windows требует подходящих настроек/прав, иначе ссылка может оказаться обычным файлом с текстом пути. Поэтому не выбирал бы его по умолчанию для публичных JSON. .
Generated copy с --check: package-файл редактируется вручную, root-файл генерируется. Плюсы — обычный JSON по старому пути, переносимость; минусы — две физические копии, дополнительный шаг. Предлагаемый gate должен ничего не исправлять, а завершаться ошибкой при несовпадении; генерация выполняется отдельно. Проверяйте также поставляемый артефакт.
Deprecation window — не альтернативный способ хранения, а политика поверх ссылки/генерируемой копии. Плюс — время миграции; минус — временная поддержка двух путей. Нельзя утверждать, что resolver-warning уведомляет прямых внешних читателей.

## 2. Владельцы и потребители

CODEOWNERS назначает людей/команды для ответственности и review, но не описывает runtime-потребителей и сам по себе не обнаруживает orphan configs. .
Соразмерный вариант — manifest с path, owner, consumers, canonical_path для совместимых копий. Тест сравнивает inventory с файлами в явно заданной области конфигов, требует ровно одного владельца, непустой список потребителей и существующие ссылки. Потребителем может быть CLI, тест, документация или внешняя пользовательская поверхность; последнюю нельзя доказать поиском по репозиторию. Добавьте smoke-тест загрузки: декларация потребителя ещё не доказывает использование.
Grep полезен как вспомогательная эвристика: комментарии дают ложные совпадения, динамические пути/glob — пропуски.
Bazel/Pants моделируют файлы и зависимости targets; Bazel позволяет искать обратные зависимости. Это не тождественно ответственному владельцу и работает лишь для представленных в графе связей. Вводить build system только ради этой проверки несоразмерно. , .

## 3. Публичная депрекация

Сохраняйте старый путь, валидность JSON и discovery-поведение; новый alias может увеличить число presets в glob — проверяйте это отдельно. Публикуйте замену, инструкцию миграции и точную версию удаления: Deprecated при объявлении, Removed при удалении. .
При SemVer 0.x «следующий major» означает 1.0.0, не 0.следующий-minor. SemVer разрешает нестабильность до 1.0; разумная собственная политика — минимум один выпущенный цикл предупреждения, затем удаление в заранее названном minor либо 1.0.0, без breaking patch. .
