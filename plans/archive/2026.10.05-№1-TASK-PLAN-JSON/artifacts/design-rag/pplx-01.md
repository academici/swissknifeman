# Query

Open-source tools (2025-2026) that store AI coding agent task plans as structured JSON/JSONL/YAML with JSON Schema and render Markdown views for humans: compare Taskmaster AI (tasks.json), steveyegge beads (JSONL issue tracker for agents), Backlog.md, GitHub Spec Kit, OpenSpec, Kiro specs. For each: data model fields (status, dependencies, files, test strategy, subtasks), how agents mutate it (CLI/API vs editing files), and lessons learned.

# Answer

Короткий вывод: из перечисленных инструментов только Task Master прямо хранит подробный task-план как JSON-объекты с зависимостями, подзадачами и отдельным testStrategy. Beads — уже не просто JSONL-трекер: в актуальной версии JSONL служит экспортом, а источником истины является Dolt; остальные решения в основном хранят спецификации и планы в Markdown, а не в JSON Schema-валидируемой модели. Ни у одного из шести я не подтвердил полноценный встроенный контракт, который одновременно описывает все поля задачи через JSON Schema и гарантированно генерирует из него Markdown-представление.

## Сравнение форматов и полей

Важно о формулировке про схемы. “Structured” не означает “JSON Schema”. У Task Master есть структурированная JSON-модель, но доступная документация описывает поля, а не подтверждает опубликованный JSON Schema-контракт. У Spec Kit, OpenSpec и Kiro структура прежде всего Markdown-шаблонная; у Backlog.md — Markdown с YAML metadata; у Beads — типизированная база данных с экспортом JSONL.

## Как агенты меняют данные

- Task Master: через CLI/MCP-команды для чтения, статусов, разбиения и обновления задач; ручная правка tasks.json тоже возможна. Документация отдельно предупреждает регенерировать task-файлы после изменений JSON, чтобы представления не разошлись. Обновление metadata через MCP выключено по умолчанию; при включении изменения сливаются с существующей metadata.
- Beads: преимущественно через bd CLI и интеграции агентов. Это принципиально отличает его от подхода «агент переписывает JSONL»: JSONL сейчас экспорт, а не live storage. CLI закрывает цикл с ready/claim/close, зависимостями и синхронизацией базы.
- Backlog.md: через backlog task ..., MCP и Web UI; эти интерфейсы обновляют Markdown-файлы. Документация рекомендует использовать их вместо прямого редактирования, чтобы сохранять корректные типы и metadata.
- Spec Kit: агент проходит последовательность skills вроде specify → plan → tasks → implement/converge и пишет Markdown-файлы. Человек может просмотреть и поправить артефакты; инструментарий не требует отдельного task API.
- OpenSpec: агент создаёт и редактирует Markdown-артефакты через workflow-команды; apply обрабатывает незавершённые пункты, archive переносит согласованные изменения в постоянные specs. Формат рассчитан на итеративную правку, а не на редактирование типизированной задачи через API.
- Kiro: задачи обновляются в task-execution интерфейсе Kiro; пользователь запускает отдельные задачи или набор задач, система отслеживает прогресс и волны выполнения. Пользовательские изменения обычно делаются через сам spec workflow и соответствующие файлы.

## Что полезно перенять

- Разделить модель задачи и представление. Task Master показывает пользу явных полей status, dependencies, subtasks, testStrategy; Markdown-вывод удобен для чтения, но не должен быть вторым независимо редактируемым источником истины. Если нужны и JSON, и Markdown, лучше определить один канонический формат и генерировать второе представление.
- Не называть экспорт источником истины. Beads — наглядный урок: наличие issues.jsonl в репозитории не означает, что JSONL является основным хранилищем. Зафиксируйте явно, какая запись авторитетна, как выглядит экспорт и как обнаруживаются конфликты.
- CLI/API нужны не только для удобства. Backlog.md и Beads ограничивают мутации интерфейсами, которые могут проверять зависимости, статусы и связи. Если разрешить агенту произвольно править файлы, нужны валидация схемы, проверка ссылок/циклов и форматирование на commit/CI.
- Спецификация и исполнение — разные слои. Spec Kit, OpenSpec и Kiro хорошо покрывают “что строим и почему”; Task Master и Beads сильнее как исполняемый task ledger. Связка может быть полезнее попытки уместить требования, дизайн, тест-план, файловый scope и runtime-состояние в один документ.
- Тесты должны быть частью задачи, а не пожеланием в чате. Среди сравниваемых решений самое явное task-level поле — testStrategy у Task Master. В Markdown-подходах стоит договориться о проверяемом формате: например, acceptance criteria плюс команды/тесты, ожидаемый результат и признак завершения.
- Зависимости для параллелизма требуют семантики. Kiro документирует волны исполнения, Spec Kit — маркировку [P], Beads — граф связей. Для собственной модели лучше различить “блокирует”, “родитель/подзадача” и “можно параллелить”, а не полагаться только на порядок строк или чекбоксы.
Практический вывод: если приоритет — формальные машинные задачи, бери за основу модель Task Master, но добавь версионируемую JSON Schema, явный files/scope и генерацию Markdown из канонического JSON. Если важнее команда, зависимости и надёжные переходы состояния — изучай Beads, учитывая, что его текущая архитектура не JSONL-first. Если главный актив — долговечные требования и дизайн, OpenSpec/Spec Kit/Kiro решают соседнюю, но не ту же задачу: они хранят спецификации и планы в Markdown, а не полноценную типизированную модель исполнения.
