# Roadmap: workflow-craft — активация конструктора workflow + fleet-синтез накопленных скриптов

**Статус:** ⬜ к внедрению — критерий сработал (field-case 2026-07-10, vaulter).
**Дом:** пак `task` (конструктор уже там: `packages/task/workflows/`) + `analyst` (fleet-синтез).

## Проблема (измеренная)

Field-case 2026-07-10, пакет vaulter: владелец попросил Opus-сессию «составить workflow по
полной разработке». Проект подключён к skiller (`task@swissknifeman` включён), канонический
конструктор существует (`packages/task/workflows/` — 4 шаблона, в `wf-dev-slice.js` ревью
встроено обязательной risk-адаптивной стадией). **Модель всё равно собрала workflow с нуля
и забыла обязательное code review.**

Причина — не контент, а активация: свободная формулировка «составь workflow» не матчится
ни на один скилл-триггер. `task:dev`/`task:dev-slice` описаны как «задача РАЗРАБОТКИ»,
а не как «авторинг workflow-скрипта» — модель не узнала в запросе повод открыть конструктор
и сочинила оркестрацию из общего описания Workflow-инструмента. Тот же класс мисроута, что
у `/task:*` (см. `agent-command-router-hook.md` — там триггер сработал и хук внедрён).

## Часть 1: активация конструктора (скилл `workflow-craft`)

Тонкий скилл-указатель в паке `task`, триггеры: «составь/напиши/сгенерируй workflow»,
«оркестрация субагентов», «мультиагентный прогон», авторинг `*.js` для Workflow-tool.
Содержание — НЕ копия шаблонов, а дисциплина:

1. Сначала матчинг на 4 канонических шаблона (`README.md` конструктора: research-fanout /
   author-by-spec / audit-adversarial / dev-slice) — копировать шаблон и заполнять слоты,
   не изобретать оркестрацию.
2. **Обязательные стадии по типу задачи**: dev-workflow без review-стадии не существует
   (risk-адаптивная глубина из `wf-dev-slice.js`); авторинг-workflow — без self-check;
   audit — без adversarial verify. Чек-лист «что должно быть» до написания первой строки.
3. Правила слотов (embedded-конфиг vs args-строка, structured-summary у каждого agent(),
   judge-panel только high-stakes) — ссылкой на README, не дублировать.
4. RAG-опция: при нестандартной оркестрации — поиск best practices (query-craft), с
   маркерами RAG:✅/[UNVERIFIED] в комментарии скрипта.

Дополнительно прошить ссылку на конструктор в `requires`/текст скиллов, которые порождают
workflow (task:dev, task:plan-exec, task:design) — прецедент: `ecosystem-reuse-gate`
прошит в `new-project`/`tech-stack-selection` (ECOSYSTEM P2.4).

## Часть 1.5: команда-гейт с выходным ревьюером (идея Owner 2026-07-10)

Авторинг workflow — через специальную команду (рабочее имя `/task:make-workflow`), а не
свободной формулировкой. Контур:

1. **Вход:** команда принимает тип задачи и грузит соответствующие скиллы-требования
   («как должно быть»): матчинг на шаблон, обязательные стадии, правила слотов.
2. **Чек-лист наводящих вопросов** — не «что должно быть» (review-фаза обязательна всегда,
   это не вопрос), а уточнения по шаблону типа: какие гейты между срезами, какой risk у
   каждого среза, что замораживается контрактом, нужен ли judge-panel (high-stakes?),
   какие пути абсолютные. Прецедент механики — скилл `spec-interview` (один вопрос за раз,
   агент сам читает кодовую базу, предлагает рекомендуемый ответ).
3. **Выход:** по завершении формирования автоматически запускается **ревьюер-агент**,
   который проверяет готовый скрипт на соответствие критериям входных скиллов
   (стадии на месте, слоты — константы, схемы structured-summary, embedded-конфиг,
   review/verify не выпилены). Вход скиллы показывают «как надо», выход — контроль,
   что так и сделано. Красный вердикт = скрипт не выдаётся без фикса.

**Два разных типа workflow — два разных набора требований** (не смешивать):

| Тип | Шаблоны-основа | Обязательные стадии | Чего НЕТ |
|:--|:--|:--|:--|
| **Проектирование** (design-only) | research-fanout, audit-adversarial | RAG-research → дизайн (main loop дорогой модели) → adversarial-аудит/DoR-гейт → фиксы → re-audit | кода, тестов, semver |
| **Разработка** (dev) | dev-slice, author-by-spec | срез → impl → tests-to-green → risk-адаптивное review → гейты между срезами → коммит | дизайн-решений на дешёвой модели (эскалация в main loop) |

Полевые прототипы обоих типов уже есть: `wf-design-fleet.js` (ECOSYSTEM P4, design) и
`wf-agentools-drive.js` (AGENTOOLS, dev с designOnly-флагом) — использовать как эталоны
при синтезе команды.

## Часть 2: fleet-синтез накопленных workflow

Workflow-скрипты копятся по проектам (`plans/*/workflows/*.js` в vault Brain: ECOSYSTEM
wf-design-fleet, AGENTOOLS wf-agentools-drive, P5-пайплайны; плюс скрипты в проектных
репо). Это полевой материал, который конструктор не видит:

1. `analyst`-скан по реестру maind: собрать все `*.js` с `export const meta`, извлечь
   структуру (фазы, модели, схемы, наличие review/verify-стадий).
2. Синтез: повторяющиеся паттерны, отсутствующие в 4 шаблонах (например «делегат-workflow
   c designOnly-флагом», «билинговая цепочка с frozen-контрактами» из wf-design-fleet) →
   кандидаты в новые шаблоны или слоты существующих; анти-паттерны (workflow без review) →
   находки для владельцев планов.
3. Выход — доклад + PR в `packages/task/workflows/` (новые шаблоны только по Rule of Three:
   паттерн в 3+ полевых скриптах).

Прецедент механики: `analyst digest → promote` (self-learning-memory), `maind doctor --audit`.

## Критерий внедрения

Часть 1 — сработал (кейс vaulter: канон есть, подключён, не активировался — прямая потеря
качества workflow). Часть 2 — по накоплению: 10+ полевых скриптов в флоте ИЛИ второй случай
«изобрели оркестрацию, которая уже была шаблоном».
