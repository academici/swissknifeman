# Roadmap: хаб-как-сервис — память с авторизацией по scope и назначение конфигов

**Статус:** 🧭 Deferred by decision (владелец, 2026-07-25) — в скоуп плана `2026.07.25-ECO-OPT`
НЕ входит. Текущая фаза P4 того плана делает только **подготовку** (см. §11), тяжёлая часть
живёт здесь до срабатывания критериев активации (§12).

**Происхождение:** диалог владельца с агентом 2026-07-25 при разборе `OQ-7` плана
`2026.07.25-ECO-OPT` (cross-machine память). Замеры субстрата — этот же заход, воспроизводимы
(§3). Уточняет и расширяет более ранний стаб `roadmap/cross-machine-memory.md` (D12 плана
`2026.07.12-CONTEXT-ECONOMY`): тот ставил вопрос «как синхронизировать две машины», этот — «как
устроить память и раздачу конфигов, когда машин и людей станет много».

**Дом при реализации:** `packages/maind` (порт памяти + клиент), плюс новый сервисный компонент
(прослойка) — вероятно отдельный пакет/деплой, решается в ADR при активации.

## 1. Что произошло и почему запись появилась

Разбор `OQ-7` начинался как выбор транспорта для варианта «единственный демон на always-on хосте
+ клиенты» (D4). По ходу выяснились три вещи, которые меняют не транспорт, а постановку:

1. **Субстрат оказался крошечным** — вся память экосистемы это 251 запись и 226 КБ текста, а
   поиск в ней лексический (BM25), не векторный. Инфраструктура, которую мы проектировали
   (секрет, ACL, tailnet, бэкап-политика, офлайн-деградация), несоразмерна объекту.
2. **Целевой режим изменился.** Владелец обозначил рост: компания, много машин, много людей.
   Решение, оптимальное для «две машины, один человек», под этот режим не годится — и наоборот.
3. **Есть дыра, которую транспорт не чинит:** у движка **один глобальный секрет** и нет
   изоляции по namespace; кто получил доступ — видит память всех проектов сразу. Для компании
   это блокер, и он не решается ни VPN, ни TLS.

Владелец решил: тяжёлую часть в текущий план не брать, но спроектировать так, чтобы прийти к ней
было дёшево. Эта запись фиксирует, к чему именно мы готовимся.

## 2. Ближайшая реальность (3–4 месяца)

Две машины **в одной локальной сети**, один оператор. Допустимы простые механизмы вплоть до
скрипта. Требование владельца — «несколько механизмов», то есть выбор транспорта не должен быть
зашит в код.

Важный факт: клиентский режим **уже поддержан конфигом** — `memory.resolve_ports()` берёт URL из
`AGENTMEMORY_URL` → `config.memory.url` → дефолт `http://127.0.0.1:<порт>`
(`packages/maind/lib/maind/memory.py`). То есть «вторая машина ходит в демон первой по LAN»
сегодня требует не кода, а конфигурации + предохранителей (см. §11).

| Величина | Факт |

## 4. Два режима и почему ответ разный

| | Режим A: 1–2 машины, один человек | Режим B: компания, N машин, M людей |
|:--|:--|:--|
| Что дефицитно | простота, офлайн | контроль доступа, отзыв, аудит |
| Git как субстрат памяти | **работает** — офлайн, история, бэкап бесплатно | **не работает** — репозиторий это «всё или ничего», нельзя выдать 3 проекта из 15 и нельзя отозвать доступ, не переписав историю; плюс дисциплина синка ложится на всех |
| Сервис | избыточен: новая зависимость доступности и контур доверия ради 226 КБ | **необходим**: единая точка авторизации, отзыва и аудита |
| Общий секрет движка | терпимо (один оператор) | **блокер** — секрет = доступ ко всей памяти всех проектов |

Вывод, который надо помнить при возврате: **вариант «git-память» не отвергнут как плохой — он
отвергнут как решение не той задачи.** Для одиночной машины/офлайн-режима он остаётся лучшим
кандидатом (см. §10).

## 5. Несущая идея: разделить порт и бэкенд

Сегодня архитектура **склеена с движком**: `maind` ходит прямо в HTTP-контракт `agentmemory`
(`POST /memories {namespace,type,text}` · `GET /search?namespace=&q=`), а изоляция достигается
тем, что `maind` подмешивает scope-маркер в текст. Значит замена движка = переписывание
потребителей, а изоляция держится на соглашении, а не на структуре.

Целевая форма — узкий **порт памяти** внутри `maind`:

```
store(scope, kind, text, meta) -> id
recall(scopes[], query, limit) -> [{id, scope, text, score}]
forget(scope, id) -> ok
links(scope) -> [...]
```

Ключевое отличие от сегодняшнего: **`scope` — параметр вызова, а не подстрока в контенте.**

Что это даёт:
- бэкенд становится сменным (agentmemory / файловый / сервисный) без правки потребителей;
- изоляция перестаёт зависеть от того, не забыл ли кто-то маркер (сегодня забыли в 9 записях);
- появляется место, где позднее встанет авторизация, — без переписывания вызовов.

## 6. Дыра, которую не чинит транспорт: авторизация по scope

Факты (проверены при разборе OQ-7):
- `AGENTMEMORY_SECRET` — **глобальный middleware**: 401 на всё без токена, и полный доступ с ним.
- Namespace в 0.9.x движком **игнорируется** (единый пул) — поэтому изоляцию и делает `maind`
  маркером в контенте.
- Значит: **любой, кто получил секрет, читает память всех проектов.** Ни tailnet, ни TLS, ни
  firewall этого не меняют — они защищают канал, а не разграничивают содержимое.

Вывод для целевой архитектуры: **авторизация обязана жить в нашем слое**, потому что в движке её
нет. Это и есть та «прослойка на сервере», о которой говорил владелец, — только её первая работа
не конфиги, а идентичность и права.

## 7. Слои целевой архитектуры

```
агент/клиент (Claude Code, Codex, скрипт)
        │  MCP-инструменты maind_memory_*
        ▼
maind (порт памяти)              ← scope как параметр; единственный вход
        │  HTTP
        ▼
ПРОСЛОЙКА (сервис)               ← идентичность · права по scope · аудит · rate-limit
        │  loopback
        ▼
бэкенд хранения                  ← agentmemory сегодня; сменяем завтра
```

Свойства, ради которых так:
- движок **перестаёт быть публичным** — он слушает loopback, наружу смотрит только прослойка;
- политика прав живёт **как данные** (кому какие scope), а не как настройка движка;
- аудит становится нашим и полным (сегодня audit-лог движка — 5 805 записей, но он не знает,
  *кто* спрашивал, потому что субъект один);
- смена движка не трогает ни клиентов, ни политику.

## 8. Конфиги: сервер назначает, репозиторий определяет

Идея владельца «управлять конфигами с сервера» правильная по цели и опасная по форме. Если
сервер станет **редактором** конфигов, появится второй источник истины рядом с репозиторием — то
есть прямое нарушение рамки репо («манифесты генерируются, не правятся руками»; «детерминированная
доставка»).

Рабочая форма:

| Слой | Кто владеет | Что содержит |
|:--|:--|:--|
| **Определение** | репозиторий `swissknifeman` | пресеты, бакеты, профили, agent-packs, инструкционный каталог — как сейчас |
| **Назначение** | сервис (прослойка) | «этой машине — такой профиль», «этому проекту — такой набор бакетов», «этому человеку — такие scope памяти» |
| **Применение** | `maind`/`harness` на машине | тянет назначение и применяет существующим провижинингом |

Побочная выгода: это чинит найденный 2026-07-25 дефект, при котором `maind sync --only mcp`
красный на **всём** флоте (`unmanaged-target` — артефакты создавались до введения lock'а и никем
не «усыновлены», `core/provider_lock.py:_classify`). При централизованном назначении артефакт
управляем по построению. Отдельный вопрос владельца об исполнителе этой починки — `OQ-9` плана
`2026.07.25-ECO-OPT`.

## 9. Brain, машинная память и obsidian-mind

Гибрид, который советует внешняя практика, **у нас уже реализован**, только разделение проходит
не там, где его ищут:

- **Brain (Obsidian, git)** — курируемое человеком знание: доки, заметки, программные планы.
  Меняется медленно, читается людьми, git ему естественен.
- **память `maind`** — операционные факты, которые пишет агент: решения, связи, «что уже
  пробовали». Пишется машинами, читается по запросу, 251 запись.

`obsidian-mind` предлагает свернуть вторую половину в первую (машинную память сделать
git-валтом). Для одного оператора это работает; для компании это ровно тот режим, где git-память
ломается (§4). Поэтому вердикт **skip остаётся в силе** (D8/D4 плана `2026.07.25-ECO-OPT`), а
ответ «можно комбинировать» верен в смысле «держать обе половины на своих ролях», а не «слить в
одну».

## 10. Механизмы по масштабу (несколько, как просил владелец)

| Масштаб | Механизм | Что нужно |
|:--|:--|:--|
| **1 машина** | локальный демон, как сейчас | ничего |
| **2 машины в LAN** (ближайшие 3–4 мес.) | одна держит демон, вторая ходит по LAN | `role` в конфиге + URL + секрет + fail-soft (§11) — кода почти нет |
| **2+ машины вне LAN** | тот же демон, доступ через tailnet (`tailscale serve` на loopback-бэкенд) | смена одной строки конфигурации, не кода |
| **офлайн-машина / автономный ноут** | файловый бэкенд порта (запись = файл, синк — git) | реализация файлового бэкенда порта; годится как dev/офлайн-режим |
| **компания** | прослойка с авторизацией + arendованный хост | §6–§7, отдельный план |

Смысл таблицы: **все механизмы — это разные бэкенды/деплои одного порта.** Если порт есть,
переход между строками не переписывает систему.

## 11. Что план `2026.07.25-ECO-OPT` делает сейчас (подготовка), а чего НЕ делает

**Делает (дёшево, разблокирует будущее):**
1. `memory.role` явным полем (`standalone` | `host` | `client`), и при `role=client` подъём
   локального демона **запрещён кодом**, а не документацией (D27 того плана). Без этого «сейчас
   подниму локально, потом синхронизирую» произойдёт само и родит второго писателя.
2. Заголовки в `core.http` (аддитивно) + секрет из `secret_file`, и починка `ping`, который
   сегодня трактует 401 как «жив» (D29) — иначе включённый секрет даёт зелёный `doctor` при
   поголовно падающих вызовах.
3. Fail-soft при недоступности памяти с честным сообщением; никакого локального кэша/outbox.
4. **Инвентарь потребителей памяти** — кто ходит в движок мимо `maind` (health-дайджест, хуки,
   узел Brain). Порт имеет смысл, только если вход единственный; инвентарь нужен раньше порта.
5. Миграция scope из текста в структуру — **если** окажется дешёвой; иначе фиксируется здесь как
   первый шаг при активации. Она же чинит 9 записей без маркера и мусорный `project:p`.

**НЕ делает (живёт в этой записи):** прослойку-сервис, авторизацию по scope, отзыв доступа,
серверное назначение конфигов, файловый/git бэкенд, смену движка, мультипользовательский аудит.

## 12. Критерии активации (когда возвращаться сюда)

Любой из:
1. **Появился второй человек**, которому нужна память экосистемы. Это жёсткий триггер: с общим
   секретом он получает доступ ко всем проектам сразу.
2. **Машин стало больше двух** или появилась машина вне LAN/tailnet.
3. **Потребовалось разграничение по проектам** (например заказчик/NDA-проект, чью память нельзя
   показывать остальному флоту).
4. Объём памяти вырос настолько, что BM25 нашего бэкенда перестал давать нужный recall
   (сегодняшний ориентир — 251 запись; порядок величины для пересмотра — тысячи).

До срабатывания — не реализуем: философия репо, «фичу внедряем по факту измеренной проблемы».

## 13. Риски и что проверить ДО реализации

| Что | Почему важно | Как проверить |
|:--|:--|:--|
| Полный список потребителей движка | порт бессмыслен при втором входе | грепом по репо + инвентарь хуков/шаблонов |
| Есть ли у свежих версий движка per-namespace авторизация | если появилась — прослойка упрощается | прямое чтение исходника версии, не README |
| Качество нашего ранжирования против BM25 движка | замена бэкенда без замера = деградация recall втихую | фиксированный набор ~30 запросов + эталон «что обязано найтись»; переключаемся, только если не хуже |
| Стоимость прослойки в эксплуатации | сервис надо обновлять, мониторить, чинить | оценить при ADR; для одного оператора она может не окупаться никогда |
| Хранение памяти всех проектов на арендованном хосте | это контекст решений по коммерческим проектам | решение владельца, фиксируется в ADR явно |
| Аудит без субъекта | сегодня «кто спрашивал» неизвестно — субъект один | появляется вместе с идентичностью, раньше не имеет смысла |
