## Что важно проверить перед выбором

Harness adapters помечены как experimental: AI SDK предупреждает о breaking changes между релизами. Адаптер Grok — не просто запись в таблице: документация описывает пакет @ai-sdk/harness-grok-build, ACP-интеграцию через @ai-sdk/harness-acp и pinned CLI @xai-official/grok@1.0.5 для установки в sandbox. Однако это подтверждает документированный путь, но не доказывает совместимость с произвольной локальной средой или произвольной версией Grok CLI. Перед внедрением фиксируйте версии и проверяйте фактически опубликованный пакет/lockfile, а не только список adapters.
Resume не переносится автоматически между слоями. Grok headless хранит named sessions в ~/.grok/sessions; Harness session управляет runtime, sandbox и своим resume state; CAO сохраняет живые процессы в tmux. Нельзя считать эти сессии взаимозаменяемыми или переносимыми: выбирайте владельца состояния и отдельно тестируйте restart/resume при завершении процесса, перезапуске supervisor и пересоздании sandbox.
И ни нативная авторизация CLI, ни наличие адаптера не гарантируют подписочную тарификацию. Harness прямо допускает native subscription только как fallback, если подходящие credential variables отсутствуют и не выбран AI Gateway; доступность подписки, биллинг и лимиты зависят от маршрута авторизации и аккаунта. Проверяйте фактический auth route, а не выводите его из факта использования CLI.

## Условная рекомендация

Для локальной multi-agent работы на нескольких CLI — CAO, если устраивают tmux и TUI-надёжность; его Grok-путь уже реализован, но это именно TUI-адаптер. Для собственного локального supervisor с надёжно наблюдаемым потоком — Python runner, предпочтительно ACP для длительных сессий и streaming-json для линейного сценария. Для TypeScript-продукта, которому нужны AI SDK streams и Harness API, — HarnessAgent, если допустим экспериментальный API и sandbox; не выбирайте его автоматически для локального runtime без проверки конкретного локального sandbox-пути.
