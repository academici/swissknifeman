# P2.8 redesign — stage-aware admission без ослабления бюджета

## 1. Основание

Исходный P2.8 смешал три разных утверждения: корректность миграции, экономию carrier-path и
готовность каждого будущего execution input. Первые два можно доказать сразу после миграции;
третье зависит от outputs P3–P6 и не может быть истинным до их производителей.

Источник наблюдения — `findings/21-p2.8-read-admission-diagnosis-2026-08-08.md`; численные
границы — frozen `root/contracts/read-budget-v1.md`. Внешних факт-классов redesign не вводит.
RAG:— (repo-grounded: указанные файлы и `brief/01-refinements.md` — RED-долг не принимается,
технический способ закрытия делегирован агенту).

## 2. Целевая модель admission

У item есть ровно одно из трёх состояний относительно бюджетного гейта:

| Состояние | Условие | Семантика |
|:--|:--|:--|
| `historical-pre-v2` | item терминален до активации Layout v2 | измеряется и сохраняется как baseline/evidence; закрытое ТЗ не переписывается |
| `pending-producer` | item ещё не ready, а отсутствующий вход адресован конкретному более раннему producer item | не считается зелёным и не считается нулём; producer id обязателен, generic missing запрещён |
| `ready` | item является следующим исполнимым по phase-first и все producer gates терминальны | до pre-mutation обязан пройти D2(a) и D2(b), иначе hard block |

Переход `pending-producer → ready` детерминирован Status Board + объявленными связями producer;
ручного warning-mode, baseline-исключения и path allowlist нет. Порог `100000`, лимиты
`262144/25000`, квалифицированная единица и anti-displacement не меняются.

## 3. Декомпозиция

### P2.8 — миграция и честный baseline

P2.8 доказывает: converter deterministic/idempotent; inventory lossless; v2 consumers собираются;
собственный ready-path P2.8 проходит оба бюджета; полный плановый отчёт печатает ВСЕ классы gaps и
не выдаёт forecast за pass. Наличие будущих проблем — вход следующего item, а не молчаливый зелёный.

### P2.9 — contract + machine admission + bounded task carriers

P2.9 уточняет публичный контракт stage-aware семантикой, учит `plan_weight` различать три состояния,
и механически разделяет oversized `plan_lint.py`/`test_plan_lint.py` по ответственностям при
дословной parity диагностик. Это устраняет первый общий hotspot, который сейчас ломает D2(b) у
P3.3/P3.6/P6.4/P6.5.

### P2.10 — пересборка read graph и self-host proof

P2.10 заменяет aggregate views точечными immutable decisions, связывает будущие файлы с producer
items, создаёт проверяемые bounded projections для канона/audit/cross-plan resume и переснимает
полный self-host report. Финальный гейт: ни одного intrinsic oversized/unresolved входа; отсутствующие
будущие outputs представлены только `pending-producer` с существующим более ранним producer;
текущий ready item проходит hard gate; aggregate не вырос и anti-displacement answer отрицательный.

## 4. Почему не один гигантский item

P2.9 меняет публичную семантику и код пакета `task`; P2.10 применяет уже замороженный механизм к
живому плану и его read graph. Их Validation различна, а P2.10 потребляет P2.9. Слияние вернуло бы
тот же дефект P2.8: acceptance формулируется реализацией, которую должен проверять.
