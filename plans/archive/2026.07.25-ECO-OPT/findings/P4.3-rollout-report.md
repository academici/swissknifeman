# P4.3 — rollout вторая машина: шесть гейтов (2026-07-28)

**Честная граница исполнения (анти-самообман, Code Guidance item'а):** второй физической машины
в этой сессии исполнения НЕТ. Гейты, требующие клиента/внешней-к-LAN точки, **не прогнаны** — не
помечены зелёным по рассуждению. Что реально сделано и проверено на ЭТОЙ (host) машине —
зафиксировано ниже с командами и выводом.

## Гейт 1 — на клиенте нет юнита/pidfile/порта

**НЕ ПРОГНАН.** Требует физического клиента (`role=client`), которого нет. Код-часть (роль-осознанная
ступень 5 `bootstrap-machine.sh`, не поднимающая демон при `role=client`) проверена smoke-тестом
ниже («Смоук ступени 5»), но это НЕ замена гейта — смоук проверяет только ветвление скрипта.

## Гейт 2 — `maind health --strict` зелёный round-trip с клиента

**НЕ ПРОГНАН.** Требует физического клиента.

## Гейт 3 — `loginctl show-user <user> --property=Linger` = `yes` на хосте

**ПРОГНАН, зелёный.** Единственный из шести гейтов, чей субъект — сама текущая (host) машина, не
клиент.

```
$ loginctl show-user "$USER" --property=Linger
Linger=yes
```

## Гейт 4 — сервис недоступен из-за пределов подсети LAN, доступен с клиента

**НЕ ПРОГНАН.** Требует машину вне подсети LAN (или контролируемый firewall-эксперимент на клиенте).

## Гейт 5 — бэкап снят app-level экспортом и проверен восстановлением в изолированную копию

**НЕ ЗАВЕРШЁН — инцидент при попытке, устранён, задокументирован как находка.** Метод по ADR
(app-level `GET /agentmemory/export` + restore в изолированную копию + smoke-чтение) не требует
второй физической машины — попытка предпринята на этой сессии.

**Что сделано:**
1. Экспорт с ЖИВОГО хоста (read-only, безопасно): `GET /agentmemory/memories?namespace=` →
   254 записи (`live-export.json`, не коммитится — рабочий артефакт сессии).
2. Поднята ИЗОЛИРОВАННАЯ копия демона: отдельный каталог (`config.json`/`iii-config.yaml` с
   ДРУГИМ портом 4311/4312, host=`127.0.0.1`, симлинк на существующий `node_modules` — без
   переустановки).
3. **Находка F1 (существенная):** `curl http://127.0.0.1:4111/agentmemory/health` (ЖИВОЙ хост)
   после подъёма изолированного инстанса вернул health-ответ, в котором `workers[]` содержал
   ДВА воркера — PID живого демона И PID только что поднятого изолированного демона.
   Т.е. движок `@agentmemory/agentmemory@0.9.27` подключает НОВЫЙ локальный процесс к ОБЩЕЙ
   mesh/discovery-группе НЕЗАВИСИМО от отдельного каталога данных/порта — свойство, ранее
   зафиксированное как «есть встроенный mesh-sync» (`findings/P4-cross-machine-facts.md` §3,
   D31 «не используем»), но НЕ было известно, что оно активируется просто фактом второго
   локального процесса, а не явным конфигом mesh. **Это прямая угроза инварианту «один
   писатель»**, ради которого выбран вариант 1 — попытка «изолированной копии для теста
   восстановления» сама по себе технически создаёт второго локального писателя.
4. Реплей экспортированных записей (`store()`) в изолированный порт вернул `HTTP 404
   /agentmemory/remember` — маршрут restore не подтверждён (демон, возможно, не успел поднять
   REST-воркер к моменту вызова).
5. Изолированный инстанс остановлен НЕМЕДЛЕННО (`maind memory stop` под изолированным root)
   при первом подозрении на кросс-влияние; обнаружен ОСИРОТЕВШИЙ дочерний процесс
   `~/.agentmemory/bin/iii --config .../drill/...` (PID пережил `memory stop` родительского
   node-обёртки) — убит вручную (`kill`).
6. **Побочный простой продакшн-памяти:** последующий `maind memory stop` + `maind memory start`
   на ЖИВОМ хосте (проверка целостности) поднял демон на конфиге, УЖЕ несущем LAN-bind
   (`iii-config.yaml` правился в P4.2, но живой процесс с Jul27 не перезапускался с тех пор) —
   новый процесс стал слушать ТОЛЬКО `192.168.31.93:4111`, а `config.json` (гитигнорённый,
   локальный) НЕ нёс `memory.url`/`memory.role` → `maind health`/CLI по умолчанию били в
   `127.0.0.1:4111` → полный локальный простой памяти (`round-trip: FAIL`, `HTTP 404`).
   **Найдена и устранена корневая причина:** `config.json` дополнен `memory.role="host"` +
   `memory.url="http://192.168.31.93:4111"` (см. `docs/deploy.md` «Вторая машина», пункт 2)
   — после правки `maind health --cwd` зелёный, round-trip зелёный, число записей ДО/ПОСЛЕ
   инцидента совпадает: **254/254** (проверено тем же `GET /agentmemory/memories?namespace=`).
   Данные не потеряны; простой — только доступности локальных проверок этой сессии.

**Вывод по гейту 5:** восстановление в изолированную копию НЕ подтверждено как рабочий
протокол — находка F1 показывает, что «изолированная копия» на ОДНОЙ машине технически не
изолирована от mesh-discovery движка, то есть заявленный ADR-метод верификации бэкапа
нуждается в пересмотре (кандидат: тест на ВТОРОЙ физической машине, а не втором локальном
процессе — тогда mesh-discovery ограничена сетевым обнаружением, а не общим localhost).
**Roadmap/Pending Work**, не чинится в этом item'е (Scope Excluded — `lib/maind`).

## Гейт 6 — `maind doctor` на клиенте не считает отсутствие локального Node/agentmemory ошибкой

**НЕ ПРОГНАН** (требует клиента) — и **находка F2**: чтение `packages/maind/lib/maind/doctor.py`
(строки 246-253) показывает, что проверки `node в PATH` и `agentmemory установлен` идут
БЕЗУСЛОВНО, без ветвления по `memory.role`. На клиенте (`role=client`, локальный Node/agentmemory
намеренно не устанавливаются per ADR) `doctor` сегодня закономерно покажет эти два `FAIL` —
требование гейта 6 («не считает ошибкой») **кодом не реализовано**. Правка — `lib/maind/doctor.py`,
явно вне `Scope Included`/`Files` этого item'а (`Scope Excluded`: «любые правки `lib/maind` и `core`
— это P4.2»). Зафиксировано как долг, НЕ чинится здесь.
