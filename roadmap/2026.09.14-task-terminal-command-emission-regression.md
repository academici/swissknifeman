# Roadmap: Task обязан выводить native command в каждом user-facing terminal ответе с runnable Next

**Статус:** 🔥 trigger сработал; owner-prioritized (Edufy, 2026-09-14).

**Критерий запуска:** немедленно — после закрытия
`2026.08.06-EDUFY-BUILD P5.2` terminal handoff корректно содержал готовый Codex launch-block
для `P5.3`, однако user-facing ответ завершился фразой «Next plan item: P5.3» без команды.

## Field incident

В `plans/2026.08.06-EDUFY-BUILD/handoff.md` после terminal event были записаны точный semantic
Next, маршрут `implementation/high`, metadata-таблица и единственная команда:

```bash
codex -C /home/vostrikov/projects/edufy -m gpt-5.6-terra -c 'model_reasoning_effort="high"' -a never -s danger-full-access '$ task:plan-run 2026.08.06-EDUFY-BUILD P5.3'
```

`plan_delivery.build_terminal_receipt()` и `plan_delivery.required_final_message()` успешно
собрали этот fragment. Но executor не вызвал renderer/terminal-admission перед ответом и не
перенёс fragment в chat final. Владельцу пришлось отдельно запросить команду новой сессии.

## Причина

1. **Неправильное исполнение канона.** Я прочитал `continue-root` как запрет на любой final и,
   закончив ответ на явно ограниченном owner item `P5.2`, не применил альтернативный обязательный
   путь: вывести уже построенный delivery fragment.
2. **Soft guard вместо write-site enforcement.** `command_render._codex_native_launch_rule()`
   предписывает требуемый блок текстом, однако нет обязательного runtime-вызова, который перед
   final проверяет, что `plan_delivery.required_final_message(receipt)` присутствует в proposed
   user-facing text.
3. **Неверная граница правила.** «Не финализировать» верно только пока executor действительно
   продолжает совместимый ready batch. Если он всё же возвращает user-facing ответ — например,
   потому что owner запросил ровно один item или явно просит команду новой сессии, — runnable Next
   нельзя скрывать за `continue-root`; должен быть выведен exact native launch-block.
4. **Опциональный adapter не закрыл разрыв.** `terminal_admission.evaluate()` умеет сравнить
   proposed fragment с receipt, но применяется только при установленном lease. В Edufy lease не
   был установлен, поэтому сохранённый receipt не стал запретом на голую сводку.

Это не противоречит архивному carrier
[`2026.09.13-task-final-launch-block-parity.md`](archive/2026.09.13-task-final-launch-block-parity.md):
тот описывает ту же обещанную семантику и её прежнюю реализацию, а этот фиксирует подтверждённую
полевую регрессию — обещание пока не стало обязательным на фактическом пути финального ответа.

## Граница исправления

- Не менять `plan_delivery` semantic Next, Routing, readiness или owner gates.
- Не печатать команду закрытого item и не выводить второй provider command.
- `continue-root` сохраняет обычное значение: при продолжающемся compatible batch агент не
  заканчивает ответ. Новый hard guard срабатывает **только если** он собирается завершить
  user-facing ответ с runnable successor.
- При явном запросе владельца «команду новой сессии» выводить native command независимо от
  `continue-root`; это запрошенная session boundary, а не разрешение обходить scope следующего item.

## Предложение реализации

1. Вынести из provider guidance обязательный `terminal finalization` seam: plan-команда после
   `build_terminal_receipt()` получает `required_final_message(receipt)` и передаёт его в один
   renderer final-ответа.
2. Этот renderer принимает только active-provider mapping и exact receipt. Для runnable Next он
   добавляет целиком `required_final_message(receipt)`; для terminal Next команды не добавляет.
   Никакой ручной сборки model/effort/argv в агентском тексте.
3. Сделать admission обязательным и без внешнего lease: перед выходом plan command сравнивает
   proposed final fragment с `terminal_admission.required_final_message(receipt)`. Lease остаётся
   дополнительным transport-level доказательством, а не единственной защитой.
4. Уточнить `plan-run` и Codex projection: после `continue-root` допустимы только два исхода:
   продолжить compatible admitted batch без final **или**, если создаётся final owner-facing
   boundary, вывести exact receipt fragment. Формулировку «do not finalise» нельзя оставлять без
   этого else-правила.
5. Добавить regression tests для `plan-exec` и `plan-run`: (a) continue-root без финала продолжает
   допустимый batch; (b) terminal response с runnable Next без receipt fragment отклоняется;
   (c) ответ с `cold-start-root`, `waiting-*` и явным запросом новой сессии содержит ровно один
   active-provider native command c `-C`, `-m`, effort, `-a never`, `-s danger-full-access`;
   (d) terminal Next не получает launch-block.

## Acceptance

- Владелец, закрывший один item и попросивший команду новой сессии, получает в том же ответе
  копируемую команду текущего provider, не открывая `handoff.md`.
- Голая completion summary при runnable Next не проходит terminal finalization.
- Continuous batch не дробится: пока agent продолжает его в текущем root, финального ответа и
  нового процесса нет.
- Проверки покрывают `plan-run`, `plan-exec`, `continue-root`, `cold-start-root`, `waiting-*` и
  terminal Next; один final никогда не содержит команд обоих providers.
