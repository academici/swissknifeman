# Roadmap: доказуемая поставка релиза до cache, проектов и новой сессии

**Статус:** 🔥 owner-prioritized, trigger сработал 2026-09-11.  
**Формат:** подтверждённый incident carrier; перед реализацией перенести целиком в одно
ограниченное задание. Не запускать массовую перезапись consumer-проектов из этого документа.

## Результат расследования

В FlexCRM сейчас не старая поставка. Umbrella-релиз `v0.15.2` публикует независимые units
`task@0.13.4` и `core@0.13.2`; локальный Codex cache и project-contained bundles совпадают
с исходниками релиза. Номер `0.13.*`, показанный Codex, — версия unit, а не umbrella-тега.

Проблема всё равно реальна и состоит не в одном отображении версии:

1. в `v0.15.0` и `v0.15.1` Task/Core менялись без bump их unit versions, поэтому разные
   байты могли жить под одним `(unit, version)` и старый cache выглядел актуальным;
2. `skiller update --all` обновляет project projections, но не machine-global Codex cache;
3. открытая сессия не перечитывает поставку сама — нужен новый разговор/перезапуск;
4. последняя fleet-поставка обновила 19 проектов, но четыре остались на старых units;
5. `maind` при обычном provider deploy способен удалить из общего lock записи `skiller`;
   следующий `skiller update` после этого безопасно, но без пути восстановления блокируется;
6. существующая installed-проверка Task ошибочно считает provider-generated
   `migrated-command-skills` посторонними файлами;
7. release/tag, machine install, fleet update, readback и session activation не образуют
   одной проверяемой поставки и не оставляют единого durable receipt.

Следовательно, утверждение «релиз опубликован» сейчас не доказывает «этот агент в этом проекте
исполняет байты этого релиза». Нужна сквозная аттестация, а не принудительное равенство всех
номеров версий.

## Измеренный инцидент

| `v0.15.0` | `0.13.3` | `0.13.1` | оба installable tree изменились без bump |
| `v0.15.1` | `0.13.3` | `0.13.1` | оба tree снова изменились без bump |
| `v0.15.2` | `0.13.4` | `0.13.2` | versions bumped; FlexCRM совпадает с этими bytes |

Tree OID подтверждают повторное использование immutable tuple:

- Task: `6f460755…` → `5187f5bf…` → `9543ad99…` при неизменном `0.13.3`;
- Core: `33c5aa5e…` → `1180dd89…` → `95d939a6…` при неизменном `0.13.1`;
- в `v0.15.2`: Task `2843dbe1…` / `0.13.4`, Core `e32223e2…` / `0.13.2`.

Это нарушает уже принятый контракт
[`generated-artifact-version-v1`](../plans/archive/2026.07.24-AGENT-RELIABILITY/root/contracts/generated-artifact-version-v1.md):
один `(name, version)` обязан однозначно определять tree bytes.

### Текущее состояние машины и FlexCRM

- `codex plugin list --json` показывает `task@0.13.4` и `core@0.13.2` из локального
  marketplace Swissknifeman;
- source, cache и `v0.15.2` имеют одинаковые manifest и managed-file digests;
- FlexCRM bundles также совпадают с source; отдельные cache-only файлы
  `migrated-command-skills` принадлежат самому Codex;
- поэтому видимое `0.13.*` здесь — проблема наблюдаемости, не фактический stale runtime.

### Fleet

В registry найдено 23 уникальных root:

- 17 project-contained bundles уже на Task `0.13.4` / Core `0.13.2`;
- 4 остались на Task `0.13.3` / Core `0.13.1`:
  `dterema/app`, `packages/agentools`, `packages/botkit`, `vintera/vintera`;
- 2 root не имеют contained bundle; это отдельное состояние, а не автоматически ошибка.

Delivery-отчёт в
[`tasks/2026.09.11-task-execution-cost`](../tasks/2026.09.11-task-execution-cost/README.md)
правильно перечисляет 19 подтверждённых поставок и четыре
`SPUB_OWNERSHIP_CONFLICT`, но его заголовок и обзорные roadmap-формулировки одновременно
говорят, что consumer install не выполнялся. Такая внутренняя противоречивость отчёта сама
является дефектом delivery projection.

### Потеря ownership

`skiller` и `maind` пишут один `.swissknifeman/provider-artifacts.lock.json`.

- `packages/skiller/lib/skiller/publication.py` сохраняет чужие записи через
  `retain_unexpected_records=True`;
- обычные вызовы `plan_artifact_lock()` в
  `packages/maind/lib/maind/provider_deploy.py` используют default
  `retain_unexpected_records=False`;
- lock четырёх заблокированных проектов содержит только две записи
  `maind.provider-deploy`, хотя managed bundles `skiller` физически остались;
- после потери записей `skiller update --dry-run` видит файлы как `unmanaged-target` и
  fail-closed отказывается их перезаписывать.

Это order-dependent дефект «последний writer победил»: `skiller → maind → skiller`
ломается не при первой поставке, а при следующем обновлении. Существующий exact-adoption test
`maind` не покрывает ordinary deploy; тест `core` на retention не доказывает правильность всех
call sites.

## Причины

### F1 — три пространства версий показаны как одно

Umbrella `v0.15.2`, package API и publication units имеют независимый SemVer по D27. Это
полезно: неизменённый unit не получает бессмысленный cache churn. Но CLI/status не показывает
рядом umbrella tag, commit и digest, поэтому корректный `task@0.13.4` воспринимается как
устаревший относительно `v0.15.2`.

### F2 — tag gate проверяет только CHANGELOG

`packages/skiller/lib/skiller/release.py` вычисляет umbrella bump, переносит Unreleased и
печатает ручные команды tag/push. `scripts/verify-tag.py` сравнивает tag только с верхним
released heading в CHANGELOG. Ни один из них не проверяет изменённые unit trees, их versions,
generated locks или immutable tuple.

Именно поэтому `v0.15.0` и `v0.15.1` прошли с новыми байтами под прежними unit versions.

### F3 — release и delivery разорваны

Tagging не обновляет machine caches и consumer roots. `skiller update --all` обходит
зарегистрированные project connect/vendor/sync projections, но не вызывает уже существующий
`run_codex_native_install()`. Global Codex install выполняется только bootstrap-скриптом;
Claude cache и project activation имеют свои пути.

### F4 — live session не входит в модель состояния

Даже корректно заменённый cache не доказывает, что уже открытый thread перечитал plugin.
Официальный provider flow требует refresh/install и проверку в новом conversation. Сейчас
этот этап не отражён как `restart-required`, а пользователь ожидает немедленного переключения.

### F5 — общий lock не имеет обязательного multi-writer merge

Core API позволяет сохранить foreign records, но делает это опционально. Один caller уже
использует retention, другой — нет. Владение поэтому зависит от порядка команд. Локальный
fail-closed защищает пользовательские файлы, но обнаруживает повреждение слишком поздно.

### F6 — нет безопасной reconciliation для уже повреждённых root

Blind adopt/overwrite недопустим: среди файлов могут быть пользовательские изменения.
Оператор получает сотни `unmanaged-target`, но не получает классификацию exact-old,
exact-current, modified и provider-generated и не может восстановить ownership штатно.

### F7 — version string используется вместо content attestation

Одинаковая version после инцидента `v0.15.0/.1` не является доказательством одинаковых байтов.
Проверка обязана сравнивать digest installable tree от release manifest до cache и projection.

### F8 — partial rollout не имеет единого durable receipt

`update --all` продолжает соседние проекты и в конце возвращает non-zero — это правильная
изоляция сбоя. Но итог остаётся длинным console output, может быть усечён и не связывается
с release identity. Из-за этого отчёт одновременно содержит «не устанавливалось» и детальную
таблицу реально выполненной поставки.

### F9 — cache verifier не знает provider-owned extras

`packages/task/scripts/plan-session.py installed` проходит на synthetic fixture, но RED на
реальном Task cache только из-за трёх `migrated-command-skills`, созданных Codex. Неизвестный
лишний файл должен оставаться RED, а явно описанный provider-owned namespace — не должен.

### F10 — consumer acceptance проверяет не весь production path

Изолированный `CODEX_HOME` полезен для build/discovery, но не доказывает состояние настоящего
machine cache, всех registered roots и уже открытой сессии. Эти слои нельзя объединять одной
галочкой `installed`.

## Решения

### D1 — сохранить независимый SemVer и добавить release attestation

Не приравнивать `task/core` к umbrella автоматически. Для каждого umbrella release генерировать
детерминированный `release-attestation/v1`, например `releases/v0.15.2.json`:

```json
{
  "schema_version": "release-attestation/v1",
  "umbrella": {"version": "0.15.2", "tag": "v0.15.2", "commit": "<sha>"},
  "units": [
    {"id": "task", "version": "0.13.4", "tree_digest": "sha256:<digest>"},
    {"id": "core", "version": "0.13.2", "tree_digest": "sha256:<digest>"}
  ]
}
```

Release date берётся из CHANGELOG; wall-clock timestamp в committed artifact не добавляется.
`version/status --json` печатает umbrella, units, commit и digests вместе и не подразумевает
равенство номеров.

### D2 — immutable tuple становится release-blocker

До создания tag сравнивать каждый installable unit с предыдущим release:

- tree изменился, version прежняя → RED;
- tree не изменился, version прежняя → GREEN;
- version изменилась, но generation/lock не соответствует → RED;
- уже опубликованный `(unit, version)` встречается с другим digest → RED без override.

Исторический `v0.14.0 → v0.15.0` должен стать обязательным regression fixture.

### D3 — отделить publish от внешней мутации, но дать одну delivery-команду

Repo release остаётся детерминированным и не меняет десятки worktree скрытым side effect.
После tag оператор запускает одну явную команду вида
`skiller deliver --release v0.15.2 --all`, которая переиспользует существующие primitives:

1. проверяет release attestation и source checkout;
2. обновляет native Codex/Claude caches;
3. обновляет registered project projections и activation state;
4. делает readback по digest;
5. пишет durable receipt и возвращает non-zero при любом unresolved root;
6. явно сообщает `restart-required` для активных provider sessions.

Нельзя писать «поставлено во все проекты», пока receipt не GREEN. Частичный успех называется
`PARTIAL`, перечисляет обновлённые и заблокированные root и остаётся незакрытым до reconciliation.

### D4 — lock становится union по owner namespace

Все writers общего provider lock обязаны атомарно читать актуальный lock, заменить только
свои records и сохранить foreign records. Collision одного path между owners — fail-closed.
Нужен один core helper с явной семантикой `replace_owner_records`, чтобы correctness не зависела
от забываемого boolean. Аудит охватывает все call sites `maind`, включая ordinary deploy и D108,
а не только строку, проявившуюся в четырёх проектах.

### D5 — reconciliation только по доказуемому preimage

Добавить dry-run repair flow:

- `exact-current`: восстановить ownership без перезаписи bytes;
- `exact-known-old`: связать с известным release digest, затем штатно обновить;
- `provider-generated`: разрешить только declarative namespaces конкретного provider;
- `modified` или `unknown`: не трогать, показать compact diff и owner action;
- перед любой material write сохранить machine-local backup/preimage и записать его в receipt.

Автоматический force/adopt для `modified` запрещён. Первые recovery fixtures — четыре реально
заблокированных root; их рабочие изменения не входят в реализацию Swissknifeman.

### D6 — verifier различает managed и provider-generated bytes

Installed verification сравнивает все source-managed файлы по digest, разрешает только
версионированный allowlist provider-owned outputs и отклоняет неизвестные extras. Реальный
roundtrip Codex должен проходить после генерации `migrated-command-skills`; мутация одного
managed cache file должна давать RED.

### D7 — receipt является источником delivery projection

Machine-local receipt, например
`~/.swissknifeman/receipts/delivery/<release>/<run-id>.json`, содержит:

- release attestation identity;
- по каждому surface/root: before, action, after digest, status и reason code;
- отдельные состояния `current`, `updated`, `blocked`, `unverifiable`, `restart-required`;
- итог `GREEN` только при отсутствии unresolved delivery targets.

Человеческий summary и документационный отчёт генерируются из receipt либо сверяются с ним;
ручные взаимоисключающие утверждения не допускаются.

## Обсуждение альтернатив

### Один номер для umbrella и всех units

Плюс — визуально проще. Минусы — любой umbrella release меняет manifests/cache paths всех
units, даже если их байты не менялись; теряется смысл D27 и растёт churn. Это не исправляет
непроверенный delivery path. **Решение:** не принимать; исправить отображение и attestation.

### Автоматически раскатывать fleet внутри `release`

Плюс — одна команда. Минусы — repo-local tagging неожиданно мутирует чужие dirty worktrees,
машинные caches и открытые provider states; rollback и права становятся неясными.
**Решение:** publish и delivery — две явные стадии одной release-модели; terminal release report
обязан показывать обе, а пользовательский shortcut может последовательно вызвать их.

### Разнести lock по одному файлу на writer

Это устраняет clobber физически, но требует миграции readers, collision detection и cleanup
нескольких SSOT. Текущий lock уже хранит owner metadata. **Решение для первого cut:** один lock
с обязательным owner-scoped merge и alternating-writer tests. Разделение возвращается только
если atomic union невозможно обеспечить на реальных filesystem/provider paths.

## Этапы реализации

### P0 — зафиксировать incident corpus и не ухудшить четыре root

- сохранить sanitized fixtures tag/unit/digest для `v0.14.0`–`v0.15.2`;
- снять read-only inventory lock и bundles четырёх blocked проектов;
- классифицировать managed/provider-generated/modified без adoption;
- исправить в существующем delivery-отчёте противоречие «не устанавливалось» vs `Delivery`.

**Гейт:** fixtures воспроизводят immutable-tuple violation, lock clobber и false-red verifier.

### P1 — закрыть multi-writer lock defect

- изменить core lock API на owner-scoped merge;
- перевести все `skiller`/`maind` call sites;
- добавить `skiller → maind → skiller` и `maind → skiller → maind` tests;
- проверить preservation, own-record replacement, cleanup и path collision.

**Гейт:** ни один ordinary deploy не удаляет foreign records; collision остаётся RED.

### P2 — ввести release attestation и tag gate

- добавить schema/generator/checker release attestation;
- связать unit paths с их version carriers;
- проверять previous-tag digest/version invariant;
- расширить `scripts/verify-tag.py` и release documentation;
- показать umbrella+units+digests в human/JSON status.

**Гейт:** fixture `v0.14.0 → v0.15.0` RED, неизменённый unit без bump GREEN,
`v0.15.2` формирует однозначную attestation.

### P3 — починить native cache verification

- описать provider-owned generated namespaces;
- исправить Task installed verifier;
- добавить isolated real-Codex roundtrip и negative mutation cases;
- machine status отделить от project projection и session state.

**Гейт:** настоящий cache с `migrated-command-skills` GREEN; managed mutation и unknown extra RED.

### P4 — собрать delivery orchestrator и receipt

- подключить native installers к явной post-tag delivery-команде;
- обновлять все registered roots с per-root isolation;
- readback делать по attested digest, не по одной version string;
- сохранять JSON receipt даже при interruption/partial result;
- дать компактный summary и exact recovery command по каждому reason code.

**Гейт:** synthetic fleet с тремя root обновляет соседей при одном conflict, завершает `PARTIAL`,
сохраняет полный receipt и никогда не сообщает all-green.

### P5 — восстановить повреждённые проекты

- сначала dry-run classification и owner-readable report;
- exact-current/exact-known-old records восстановить штатной reconciliation;
- modified/unknown передать владельцу без перезаписи;
- повторить delivery до GREEN либо оставить явно принятый исключённый target в receipt.

**Гейт:** каждый из четырёх root имеет доказуемую диспозицию; ни один пользовательский byte
не изменён без разрешённого managed transition.

### P6 — закрыть observability и документацию

- обновить control-surface, install/update/release runbooks;
- документировать матрицу source → release → native cache → project → session;
- terminal report строить из receipt и показывать `restart-required`;
- проверить ссылки, docs build и отсутствие generated drift.

**Гейт:** по одному выводу оператор отвечает, какой umbrella/unit/digest находится на каждом
слое и почему открытая сессия может требовать перезапуска.

## Acceptance

1. Изменение installable tree без bump unit version блокирует release до tag.
2. Один `(unit, version)` никогда не соответствует двум digest в опубликованных attestations.
3. Machine cache, project projection и loaded session показываются раздельно.
4. `update --all` не утверждает, что native cache обновлён, если native step не выполнялся.
5. Общий lock сохраняет foreign ownership при любой последовательности writers.
6. Recovery не перезаписывает modified/unknown targets и имеет preimage/receipt.
7. Real Codex cache проходит verifier с известными provider-generated extras.
8. Partial fleet delivery всегда non-green и оставляет полный, неусекаемый JSON receipt.
9. All-green доказывается digest readback каждого целевого слоя, а не совпадением версии.
10. Новая сессия обнаруживает ожидаемый Task/Core; старая маркируется `restart-required`,
    а не ложно `current-runtime`.

## Безопасность и границы

- Roadmap не разрешает force-update четырёх dirty/unmanaged consumer roots.
- Не удалять и не переписывать чужие lock records для «починки» теста.
- Не считать mtime, symlink/source pointer или version string доказательством одинаковых bytes.
- Не включать machine-specific receipt в git; committed release attestation детерминирована.
- Не обещать hot reload открытой сессии, пока provider не даёт такого контракта.
- Не расширять первый cut до удалённого fleet daemon или нового package manager.
