# Roadmap: диета вендорных `notify`-скиллов через миграцию на `strategy: fork`

**Статус:** ⬜ отложено (идея Owner 2026-07-12, механизм-фундамент уже есть — задача процессная,
не движковая).
**Дом:** `packages/skiller/` — `upstream.json` (`strategy`), `scripts/update-upstreams.sh`,
скилл `skill-authoring` (правила правки вендорных скиллов).

## Идея (как её описал Owner)

skiller — отчасти маркетплейс: часть скиллов свои, часть — вендорные, помеченные
`upstream.json` (`docs/reference.md` — паспорт провенанса). Инструкция сейчас по умолчанию
трактует вендорные скиллы как «руками не трогать» — но некоторые важные при этом раздутые
(context-economy требует диеты, см. `plans/2026.07.12-CONTEXT-ECONOMY` P3), и их оптимизация
стопится из-за страха, что следующий апдейт апстрима затрёт локальную адаптацию.

Предложение Owner: адаптировать (сжать/подогнать под нас) такие скиллы, но при обновлении —
**не накатывать апстрим напрямую**. Скрипт получает новые данные апстрима, готовит отчёт
«скилл X изменился», агент читает отчёт, вручную смотрит дифф и **переносит изменения в уже
адаптированную версию** (а не затирает её). Большинство скиллов меняются редко — их
оптимизация не обязана стопиться из-за теоретической будущей синхронизации.

## Важно: механизм почти полностью уже существует

Ревизия `packages/skiller/scripts/update-upstreams.sh` + `schema/upstream.schema.json` +
`docs/guide/upstream-sync.md` показала: то, что просит Owner, — это **ровно** поведение
`strategy: fork`, уже реализованное:

- Раскладка: `SKILL.md` — тонкая обёртка с нашими правками (диета живёт здесь);
  `references/source.md` — pristine-зеркало апстрима (байт-в-байт, грузится по требованию).
- `--check`/`--apply` на дрейфе апстрима: зеркало и `SKILL.md` **не трогаются**; апстрим
  стейджится отдельно в `upstream/<name>.incoming.md`, `review_pending: true`.
- Гейт: `validate.sh` красный, пока `review_pending: true` — релиз/registry заблокированы,
  забыть про дрейф нельзя.
- Агент вручную: `diff references/source.md upstream/<name>.incoming.md` → переносит
  изменения в обёртку (сохраняя диету) → `--resolve` (зеркало := incoming, флаг снят).

Т.е. **не нужно проектировать новый механизм** — нужно (а) научиться его *применять*
систематически к нужным скиллам, (б) закрыть процессный разрыв ниже.

## Измеренный разрыв (2026-07-12, ревизия каталога)

- `strategy: fork` используется **у 1 скилла** из 56 с `upstream.json` (`ai/ai-agents`).
- `strategy: notify` — у **54** скиллов. Для `notify` при дрейфе апстрима поведение слабее:
  файл тоже не трогается, но **никакого incoming-диффа не стейджится** — только строка
  `[notify] … strategy=notify, review manually` в отчёте `--check`. Агент, решивший
  перенести апстрим-изменение, вынужден вручную заново идти по `url` и диффать —
  структурированного артефакта для этого нет.
- Среди `notify`-скиллов есть явно раздутые кандидаты на диету (замер SKILL.md, байты):
  `frontend-vue/vueuse-functions` (37 153B), `frontend-vue/vue-router-best-practices`
  (13 420B), `voice-ai/voice-ai` (11 756B), `frontend-vue/vue-testing-best-practices`
  (11 210B), `laravel-filament/filament` (10 336B), `quality/diagnosing-bugs` (9 671B) —
  все кратно выше рэтчет-порогов P3 (warn >300, error >450 для description; здесь речь о
  ТЕЛЕ скилла, отдельный порог не заведён).

## Что должно появиться (когда возьмём в работу)

1. **Критерий отбора кандидатов** «важный + раздутый notify-скилл»: нужен явный порог
   (напр. SKILL.md тела > N байт — калибровать отдельно от description-рэтчета P3) +
   сигнал важности (частота использования/подключения в проектах — если такой замер
   появится, напр. из `analyst`; в MVP сойдёт ручная разметка Owner).
2. **Плейбук миграции `notify → fork`** (можно оформить как режим существующего
   `update-upstreams.sh` или отдельный скрипт `scripts/notify-to-fork.sh`):
   - переносит текущий `SKILL.md` в `references/source.md` (pristine на момент миграции —
     ВНИМАНИЕ: если тело уже адаптировано вручную под `notify`, зеркало будет НЕ pristine;
     нужно либо перекачать чистый апстрим по `url` заново, либо явно зафиксировать
     стартовую точку как «наш адаптированный baseline», а не апстрим-baseline —
     решить при реализации, это меняет семантику дальнейших диффов);
   - переписывает `SKILL.md` в тонкую обёртку-навигатор с диетой (по формату,
     уже описанному в `docs/guide/upstream-sync.md` под fork);
   - меняет `strategy` в `upstream.json`, обновляет `files[].path` на
     `references/source.md`.
   - гоняет `validate.sh` (схема требует `files` присутствия и т.п.).
3. **Массовый прогон**: не по одному скиллу вручную — пачками (кандидаты из п.1), с
   `validate.sh` после каждой пачки, коммит на пачку (паттерн P3.1/P4.1 из
   context-economy: батч-диета + таблица было→стало в Completion Notes).
4. **(Опционально) усиление `notify`** до частичного incoming-стейджинга — если после
   миграции части скиллов на `fork` останутся важные `notify`-кейсы, где авто-адаптация
   нежелательна, но ручной дифф нужен так же часто — тогда стоит рассмотреть перенос
   incoming-стейджинга из `fork`-ветки в общий код для обеих стратегий. Не делать
   заранее — оценить по факту, сколько `notify`-скиллов реально нужно после п.1-3.

## Критерий внедрения

Пока **не сработал** — идея зафиксирована по запросу Owner, не по измеренному трению
(в отличие от `agent-packs-upgrade-drift.md`, где два полевых отказа). Брать в работу при
любом из:
- при очередной диета-фазе (по образцу P3 context-economy) явно всплывает notify-скилл,
  который хочется сжать, но страшно потерять при апдейте — конкретный кейс запускает п.2;
- апстрим одного из раздутых notify-кандидатов (список выше) реально задрейфовал и вручную
  дифф оказался болезненным (замер: сколько времени/токенов ушло на ручную сверку без
  incoming-артефакта) — это подтверждает нужность п.4.
