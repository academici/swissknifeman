# Декларативная политика исполнения

Носитель `packages/harness/configs/common/agent-packs/execution-policy.json` отвечает на два
вопроса, которые раньше решались ad hoc в каждой сессии: *когда оправдан спавн субагента* и
*что обязан нести таск субагента*. Схема запечатана контрактом
`plans/2026.07.29-HARNESS-AGNOSTIC/root/contracts/execution-policy-v1.md` (P4.2) — четыре
раздела, значения копируются оттуда дословно вместе с `provenance`.

## Четыре раздела

- **`spawn_threshold`** — правило решения (все positive-условия ДА, ни одного negative) плюс
  шкала `scale_by_task_class` (per-класс задачи, не токеновый бюджет).
- **`max_parallel_agents`** — потолки параллелизма по субъектам и провайдеру.
- **`allowed_agent_roles`** — производное правило над каноном `roles.json`, второго каталога
  ролей не заводит.
- **`delegation_contract`** — пять обязательных полей задания субагента + жизненный цикл точек
  принуждения `pending`/`enforced` с `pending_until`.

## Гейт — `execpolicy.py`

`packages/harness/lib/harness/execpolicy.py` проверяет ФОРМУ данных: закрытые наборы ключей,
обязательность `provenance` у числовых полей, резолв `allowed_agent_roles` против `roles.json`,
и статус точек принуждения. Двадцать условий §10 контракта — построчный чек-лист, каждая
проверка в коде несёт номер закрываемого условия.

```
PYTHONPATH=packages/harness/lib python3 -m harness.execpolicy --check
```

Шаг `[10/10]` в `packages/harness/scripts/validate.sh`. Файл — генерируемый носитель по
запечатанной схеме: правится по контракту, не руками мимо него (расхождение с
§2–§5 контракта — дефект носителя, а не локальное решение).

## Потребитель — грамматика PLAN

Точка `delegation_contract` переведена P4.4 из `pending` в `enforced`: пять полей задания
обязательны в грамматике `_common.orchestrator` (обоих провайдерских проекциях). Принуждение —
через потребителя (оркестратор читает и требует поля), не автоматический рантайм-перехват —
валидатор проверяет только форму носителя, не фактическое поведение оркестратора в живой сессии.
