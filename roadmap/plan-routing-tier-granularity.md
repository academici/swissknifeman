# Roadmap: блочный Routing уровня фазы over-provision'ит верхний тир модели на разнородные items

**Статус:** 🟢 внедрено сразу (2026-07-18, той же сессией — фикс текстовый; файл остаётся как анализ-история).
**Дом:** `packages/task/commands/plan-design.md` (DoR-чеклист, шаг Routing при детализации фазы) +
`packages/skiller/skills/general/plan-protocol/SKILL{.ru,}.md` §9 (Tier policy + Гранулярность);
lint-эвристика снята (см. п. 3 ниже).
**Связано:** azguard `plans/2026.07.18-AZGUARD-STABLE/plan.md` D28 (полевой фикс — готовый
прототип критерия); `roadmap/plan-audit-loop.md` (тот же класс: верхний тир жжётся там, где
работа механическая).

## Проблема

`plan-design` при детализации фазы пишет `## 3. Routing` **блочной строкой уровня фазы**
(`P2.1–P2.10 | fable/high | manual | design/contract-класс…`), и протокол это легализует дважды:

1. **DoR-чеклист** `plan-design.md` требует лишь «§3 Routing **покрывает** каждый item фазы» —
   блочный диапазон формально «покрывает», принудительного per-item пересмотра при детализации
   нет (черновой routing уровня фаз, заложенный при создании плана, просто доживает до exec).
2. **§9 Thinking policy** говорит «effort high+ ОБЯЗАТЕЛЕН для SemVer-public-API» — это правило
   про **effort**, но на практике plan-design распространяет его на **тир модели**: «фаза трогает
   публичные контракты» → вся фаза уезжает в fable/opus. Критерия выбора ТИРА МОДЕЛИ в §9 нет
   вообще (только матрица ролей и правила effort'а). Канонический пример формы §3 в §9 сам
   показывает диапазон-строку `P2.7–P2.9 | fable/high` — образец подталкивает к блочности.

Итог: тир фазы = максимум риска самого нагруженного item'а, размазанный на все items, включая
editorial/механику. Перебор тира легален по протоколу (гейт ловит только НЕДОБОР), поэтому
никто ниже по конвейеру его не оспаривает — ресурсы верхнего тира жгутся молча, «по прописи».

## Измеренный кейс (azguard, `2026.07.18-AZGUARD-STABLE`, 2026-07-18)

Routing P2: одна строка `P2.1–P2.10 | fable/high | manual` на 10 разнородных items; P3 — та же
блочность (`P3.1–P3.3 | fable/high`). Владелец заметил на третьем item'е («а вот сейчас на
filament зачем?») и потребовал построчную ревизию. Результат ревизии (D28):

| Класс item'а | Items | Было | Стало |
|:--|:--|:--|:--|
| Открытые design-решения / необратимая цена ошибки | P2.5, P2.9, P3.2 | fable/high | fable/high (оправдано) |
| Предписанная реализация по запинённым канонам (RAG/спека) | P2.4, P2.6, P3.1, P3.3 | fable/high | sonnet/high |
| Editorial/механика с детерминированными гейтами | P2.7, P2.8, P2.10 | fable/high | sonnet/medium plan-exec |

Из 10 оставшихся items **7 были over-provisioned на 1–2 тира**; 3 из них вообще не требовали
manual-сессии (уходят в `plan-exec`). Экстраполяция: без вмешательства владельца ~7 полных
fable/high-сессий ушли бы на работу sonnet-класса — на ОДНОМ плане одного пакета; дорожка
объявлена эталоном для флота пакетов, т.е. паттерн тиражировался бы.

Отдельный сигнал: недобор тира структурно заблокирован (routing-гейт `plan-exec`/`plan-run`),
а перебор — лишь «запись в Known Deviations» при фактическом исполнении. Перебор, **предписанный
самим Routing'ом**, не фиксируется нигде — асимметрия защиты: протокол защищает качество, но не
кошелёк.

## Root cause

Routing наследуется от чернового уровня «фаза → роль → тир» и при детализации фазы не проходит
принудительной дифференциации, потому что: (а) в §9 нет критерия тира модели (есть только
критерий effort'а); (б) DoR-гейт проверяет покрытие, а не гранулярность; (в) сила примера —
канон формы §3 демонстрирует блочную строку с верхним тиром.

## Направление фикса

1. **§9 plan-protocol — критерий тира модели** (формулировка D28 azguard как прототип):
   - верхний тир (fable/opus) — только если у item'а остаются **открытые design-решения**
     ЛИБО **цена семантической ошибки необратима/замораживается** (freeze-механизмы,
     breaking-семантика, канон флота);
   - предписанная реализация по уже запинённым канонам (RAG-вердикт, замороженная спека,
     D#-решение) → sonnet/high;
   - editorial/механика с детерминированными гейтами → sonnet/medium + `Exec = plan-exec`.
   Явно разделить: «effort high+ MANDATORY» ≠ «тир модели high» — это независимые оси.
2. **plan-design.md — DoR-гейт гранулярности:** при детализации фазы Routing её items становится
   **построчным**; блочная строка легальна только с явным маркером однородности (все items
   диапазона — один риск-класс по критерию §9, одна фраза «почему» истинна для каждого).
   Черновая блочность уровня фаз остаётся легальной ДО детализации (как сейчас задумано).
3. ~~plan-lint.py — эвристика-WARN~~ **СНЯТО при внедрении:** §9 Back-compat фиксирует
   осознанный инвариант «`plan-lint` секцию §3 НЕ парсит — гейт исполняет читающий
   исполнитель, не regex» (форм Routing во флоте много). Машинная эвристика противоречила бы
   ему; гейт гранулярности живёт в DoR-чеклисте `plan-design`. Вернуться, только если
   инвариант пересмотрят.
4. Опционально (по накоплению): перебор тира, предписанный Routing'ом и снятый later-ревизией,
   фиксировать D-записью с оценкой сэкономленных сессий — сырьё для `analyst` (сколько
   стоит блочность в среднем).
