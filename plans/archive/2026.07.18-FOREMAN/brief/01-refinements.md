# Уточнения владельца

## 2026-07-18 — журнал исполнения, индекс, прогресс-движок (после design pass 1)

Владелец расширил скоуп двумя блоками, связанными с супервизором:

### 1. Журнал исполнения per plan (отдельный файл, не handoff)

- Проблема: сессии CC не привязаны к плану — план исполняется разными сессиями,
  по логам сессий (`runs`-конфиги) невозможно сопоставить «какая команда реально
  запускалась в рамках какого плана».
- Нужен **полный пер-плановый лог**: дата/время → какая команда запущена → трения/споры
  в процессе (помечать) → финальный результат. Следующая команда — следующая запись.
- Сейчас подобное пишется в handoff — владелец склоняется (решение делегировал мне:
  принято, D8) писать в **отдельный файл**: разные файлы — разный анализ.
- В структуре плана — **корневой индекс-файл**: где что искать, что с чем связано.
- Назначение: дальнейший анализ + вход супервизора (сколько петель одной команды,
  есть ли прогресс).

### 2. Прогресс-движок супервизора + его собственный лог решений

- Бывают честно сложные задачи: 7 циклов (например, аудитов плана) — норма, если
  каждая итерация реально приближает к финалу → супервизор соглашается продолжать.
- Антипаттерн: «движемся на месте — одно правим, другое ломаем» → супервизор решает
  точечно поправить / вмешаться, а не гнать цикл дальше.
- Схему оценки прогресса супервизор строит по: аудитам, журналу, handoff, фазам.
- Правила оценки — **наращиваемые постепенно** (свод правил пополняется по опыту).
- Работа самого супервизора тоже **логируется**: какие решения принял и почему —
  чтобы владелец мог проверять супервизора.

## 2026-07-18 — иерархия супервизоров + мульти-канальный Q&A (второе уточнение)

### 3. Комплексный / иерархический супервизор (глобальная перспектива)

- В Brain есть глобальный план развития (взаимодействия модулей, общая стратегия);
  в каждом проекте — свои планы. Супервизор должен быть комплексным: **корневой
  супервизор в Brain** координирует проекты по глобальному плану (пример: для шага
  FlexCRM сначала нужен CoreX до стадии X → корневой ставит задачу супервизору CoreX
  «сделай и доложись» → по докладу двигает FlexCRM дальше).
- Оговорка владельца: «как правило, я буду глобально сам всё делать» — но архитектуру
  затачиваем под это; когда проекты реализованы и структура устоится, такой супервизор
  нужен: следить, что запущено, находить конфликты И точки соприкосновения/улучшения.
- Вердикт обсуждения (D11): не отдельная сущность, а **рекурсивная композиция того же
  Artifex** (корень = Artifex над оркестр-планом, дочерний прогон = item родителя);
  включение корневого уровня — v2 после пилота, композируемость контрактов — сейчас.

### 4. Блокирующий Q&A через мессенджер-ботов, мульти-канально

- При реальном конфликте в отсутствие владельца: бот (канал в мессенджере MAX)
  присылает **выжимку** конфликтной ситуации; владелец отвечает подробным текстом;
  супервизор продолжает ТОЛЬКО при стопроцентном понимании (вправе доспросить).
- Каналы — подключаемые и разные: Telegram в России деградирует, у MAX на iOS нет
  уведомлений; нужно несколько источников-ботов параллельно, чтобы вести работу
  даже вне дома. Вердикт обсуждения (D12): канал-агностик слой (notify + inbox),
  MAX first-class (Bot API официально есть — RAG:✅ 2026-07-18), единый inbox с
  дедупликацией; ответы владельца фиксируются в артефактах плана.

## 2026-07-18 — первичный анализ истории: извлечение принципов владельца (третье уточнение)

### 5. Майнинг принципов из исполненных планов

- До/для наполнения правил супервизора — **первичный анализ** (можно более простыми
  моделями): как исполнялись планы, какие решения принимались — чтобы выявить принципы,
  которыми владелец фактически руководствуется, и максимально их описать.
- Ключевое разделение, которое анализ должен формализовать:
  - **Требует внимания/согласования**: концептуальные взаимодействия между проектами
    (пример: FlexCRM ↔ CoreX — функционал нестабилен, «плавает») — здесь супервизор
    эскалирует.
  - **Свободно без вопросов**: любые улучшения В РАМКАХ одного пакета, если они
    вписываются в чистую реализацию — fluent API, расширяемость, конфигурируемость,
    надёжность.
- Философия владельца: «разработка идеальных систем — главный козырь; всё чисто под
  себя, под единую структуру» — улучшение качества никогда не блокируется.

## 2026-07-18 — стратегический канон Brain (четвёртое уточнение)

### 6. Глубокий анализ и самодостаточное описание экосистемы в Brain

- Отдельной фазой: глубокий анализ Brain — показать, что это НЕ набор общих проектов,
  а связанная экосистема со своей философией; всё завязано друг на друга.
- Цель: супервизор всегда видит стратегию/планы; максимально улучшить читаемость
  всего хранилища. Существующие артефакты (02-Knowledge/00-Strategy: ecosystem
  glossary, tech radar) — недостаточно объёмны; нужно **самодостаточно**: человек
  открыл — понял, куда всё движется, какая стратегия, какие принципы.
- Проанализировать и то, КАК сейчас идёт разработка и строятся планы — и описать.
- Потребители: супервизор Artifex И обычный Claude Code, работающий напрямую.
- Скиллы этого канона — именно в Brain: Brain = узловой хаб всех проектов, в нём
  общая стратегия; локальные планы дорабатываются в проектах (05-Projects/...).

## 2026-07-18 — мандат делегирования + run-folder супервизора (пятое уточнение)

### 7. Делегирование с мандатом и файловое состояние запуска

- Автоматика не 100%: владелец **делегирует** супервизору ограниченный мандат —
  «следи только за P1» или «за P1–P5» — подробным промптом с правами. Этот мандат
  должен быть **записан в сам запуск** (не только в чат), чтобы к нему можно было
  постоянно обращаться.
- Устойчивость к падению: комп упал/перезагрузился → супервизор должен видеть свой
  контекст. НО не через память (mAInd/memory) — она переполнится сиюминутными данными,
  нужными только в рамках одного прогона.
- Предложение владельца: **любой запуск супервизора = папка по аналогии с plans/**:
  `<текущая дата>-<код>`, внутри — `brief/` (мандат), отчёты о работе (JSON'ки),
  состояние «на каком этапе» — всё нужное для работы.
- Resume: команда «супервизор, продолжай <ПАПКА>» — указывается папка запуска,
  а не номер сессии; супервизор восстанавливается из неё и продолжает.
- Просьба: проверить ход мыслей через RAG; поискать готовые решения/куски именно по
  супервизор-основе (надёжный рантайм, взаимодействие супервизоров, зоны
  ответственности) — вторая половина после уже сделанного аудита скиллов; встроить
  найденное в план. Детализация должна стать самодостаточной.

## 2026-07-18 — устойчивость к исчерпанию лимитов учёток (шестое уточнение)

### 8. Квоты Claude Max и смена учёток

- Владелец использует Claude Code на учётках Max 20x, их будет 2–3; при длинных
  задачах учётки хватает на 2–3 дня. Когда лимит исчерпан — начинают сыпаться ошибки
  «лимит исчерпан».
- Процедура смены (сейчас ручная): зайти в веб-браузер → выйти из текущей учётки →
  войти в следующую; после перезапуска IDE (VS Code) новая сессия подхватывается
  автоматически, повторный вход не нужен.
- Требования к Artifex:
  - при исчерпании лимита **ничего не падает**: очередь встаёт на паузу, состояние
    сохранено, после перелогина — продолжение с того же места (дочерние сессии
    перезапускаются);
  - **срочное уведомление** на телефон (мессенджер MAX/TG) даже ночью (02:00–03:00):
    «лимиты закончились, произвести такие-то действия» — с инструкцией;
  - **учитывать типы лимитов**: пятичасовой (окно) — смена учётки бессмысленна,
    надо ждать до сброса; недельный — менять учётку;
  - смена учёток пока вручную (уведомление — на автомате); таких ситуаций будет
    немного, но учесть обязательно.
