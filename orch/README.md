# Выбор оркестратора для Swiss Knife Man

Дата исследования: **5 октября 2026**. Статус: **архитектурный аудит; миграция и новый runtime ещё не реализованы**.

Моя рекомендация — сохранить Task и Skiller как независимое ядро и **сначала проверить CAO как сменный исполнитель Python-workflow**. Это наиболее прямой путь к уже готовому управлению несколькими CLI и видимым терминалам. Окончательно выбирать его нужно после проверки восстановления, маршрутизации и взаимодействия с Task. AWS Labs в названии не заменяет эту проверку.

Собственный исполнитель остаётся обоснованным вариантом: в репозитории уже есть значительная часть нужных механизмов, а Claude Code, Codex и Grok имеют структурированные интерфейсы. Его разумно развивать, если CAO потребует постоянного ремонта парсеров или не пройдёт проверки жизненного цикла. У Vercel также появился экспериментальный HarnessAgent; исходный диалог недооценивает этот путь. Источники: [CAO](https://github.com/awslabs/cli-agent-orchestrator), [Grok scripting](https://docs.x.ai/build/cli/headless-scripting), [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk), [Claude headless](https://code.claude.com/docs/en/headless), [Vercel HarnessAgent](https://ai-sdk.dev/docs/ai-sdk-harnesses/overview).

## Решения, которые уже можно обосновать

1. **Task владеет планом, исполнитель владеет процессами.** Чтение JSON, выбор готового пункта, проверки и закрытие выполняет код. Модель получает конкретную стадию и её критерии результата.
2. **Один запуск имеет одного владельца workflow.** В варианте CAO им является его Python-workflow; в собственном варианте — наш runtime. Запуск CAO внутри Artifex внутри Harness добавит конкурирующие повторы и отмену.
3. **Модельный конвейер настраивается по задаче.** Дешёвый контекстный агент может быть обязательным в выбранном профиле. Передача простого кода дешёвой модели и независимое ревью включаются там, где дают пользу. Git и закрытие плана обычно вообще не требуют модели.
4. **Полный контекст остаётся доступным.** Новый индекс или представление для отдельной стадии не должны молча обрезать обязательные данные текущего Task.
5. **У инструкций уже есть канонические источники.** Provider-файлы преимущественно являются генерируемыми проекциями. Проблема — проверять доставку, фактическую загрузку и конфликты инструкций, а не объявлять все эти файлы независимыми копиями.
6. **Замена движка не требует удаления всего Harness.** Его установка окружения, настройки, hooks и provider-проекции нужны и при внешнем исполнителе.

## Что пока неизвестно

Исследованы исходники и первичные документы; получены 11 результатов запросов Perplexity, включая один пустой ответ и его повтор. Выполнены два существующих генераторных check и 56 существующих тестов Task — все прошли. Это подтверждает локальные механизмы Task, но не надёжность внешнего движка. [Протокол проверок](research/local-checks.json).

Во время исследования появились параллельные правки Task. Они сохранены и отражены в [source ledger](research/concurrent-source-changes.json); результаты тестов относятся к моменту их запуска, а не к позднему WIP.

Перед коммитом всех изменений полный package-validator Task и 317 тестов core прошли;
registry и command-проекции актуальны. Fleet-проверка архивного плана и проверка версий
сохраняют замечания, воспроизведённые на исходном `main`. [Проверки перед публикацией](research/publish-checks.json).

Не запускались платные coding-agent задачи, сервер CAO или Vercel sandbox. Поэтому **фактическая экономия, работа подписок именно на этих аккаунтах, устойчивость связки из трёх CLI и end-to-end resume пока не доказаны**. Эти вопросы вынесены в конкретный пилот, а не заменены оценками популярности или выдуманными сроками.

Для внешних утверждений различаются документация, просмотренный код, локальная проверка и проектное предложение. Хеши исходных файлов и версии зафиксированы в [машинном индексе](research/source-index.json). Это позволяет Claude Code перепроверить выводы, не повторяя всё исследование вслепую.
