# Roadmap: `plan-run` routing rejection must not become terminal `Blocked`

**Статус:** ⬜ к внедрению. Измеренный дефект: Agelto, план `2026.08.09-RELEASE-READINESS`, item P1.7, 2026-08-10.
**Критерий внедрения:** следующий item, меняющий `packages/task/commands/plan-run.md`, `packages/task/lib/task/journal.py` или `packages/task/lib/task/plan_item_state.py`, обязан реализовать все пункты этого документа и тесты. Не ждать повторного инцидента.

**Автор:** Codex, 2026-08-10. **Источник:** Dmitry Vostrikov, approval owner Agelto. **Владельцы:** `packages/task` и `packages/skiller`.

## Симптом

`$ task:plan-run <plan> Pn.m` при недоборе route должен остановиться до работы, оставить item без изменения статуса и выдать launch-block для той же команды в сессии с требуемыми model/effort. Одновременно его текст предписывает append journal event:

```text
result=blocked, friction=routing-blocked
```

В Layout v2 этот event является единственным входом generated item state. Поэтому следующая проекция ставит `**Status:** 🔴 Blocked` и `**Escalation Needed:** yes`; `status` делает фазу blocked. Повторный запуск из выданного launch-block читает уже terminal state и останавливается до routing-gate. Получается детерминированная петля «не выполнил → сказал повторить → запретил повтор».

В Agelto это произошло для P1.7: route `implementation/high · manual`, первая сессия была записана как ниже требуемой, journal получил `routing-blocked`, а state стал `🔴 Blocked`. Работа не начиналась, но carrier выглядел как escalation.

## Точная причинная цепочка

1. `packages/task/commands/plan-run.md`, routing-gate, явно требует `--result blocked --friction routing-blocked`, но строкой выше обещает: «статус item'а НЕ меняется».
2. `packages/task/lib/task/journal.py` допускает и `blocked`, и `routing-blocked`, однако не различает procedural route rejection и реальную блокировку исполнения.
3. `packages/task/lib/task/plan_item_state.py` содержит `RESULT_STATUS["blocked"] = "🔴 Blocked"`; execution events выбираются по имени команды, а не по тому, началось ли исполнение.
4. Тот же projector выставляет `Escalation Needed: yes` для любого red state. Это корректно для настоящей эскалации, но ложно для routing preflight.
5. `plan-exec.md` и `plan-run.md` требуют для `🔴 Blocked` escalation-triple; lint обнаруживает рассогласование, потому что routing-rejection не обязана и не должна создавать escalation block.
6. Precondition `plan-run` запрещает исполнять terminal `🔴 Blocked` item. Поэтому рекомендованный повторный launch-block не может привести к началу работы.

Это не ошибка пользователя и не отсутствие authority: это конфликт двух нормативных правил внутри Task runtime.

## Решение

Разделить **routing rejection до начала работы** и **execution block/escalation** на уровне journal schema и reducer.

1. Добавить отдельный journal `result`, например `routing-rejected` (или эквивалентное отдельное outcome-поле; имя должно быть каноническим и schema-validated).
2. `plan-run` при `ROUTING-BLOCKED` и `ROUTING-INCONSISTENT` пишет только этот result с `friction=routing-blocked`; `blocked` остаётся только для фактической блокировки/эскалации после начала item execution.
3. `plan_item_state` исключает routing-rejection из `execution_events`, `attempt` и last execution position. Если это единственное событие, state остаётся `⬜ Not started`, `Escalation Needed: no`, а next step ясно говорит rerun after route correction.
4. `plan_status` сохраняет событие в Update Log для аудита, но не меняет phase status/Owner Gates на escalation.
5. Launch-block routing rejection должен запускать ту же semantic command только при изменённой runtime-конфигурации; он не должен предлагать `plan-design`, пока не выявлен отдельный conflict/owner gate.
6. `blocked`/`escalated` по-прежнему дают `🔴 Blocked` + escalation triple и требуют отдельного пути resume/design. Семантика настоящего инцидента не ослабляется.

## Тесты приемки

Добавить fixtures и unit/integration tests, доказывающие одновременно:

- `plan-run` routing rejection добавляет durable journal provenance, но `state --all`, `status` и `plan-lint` остаются зелёными;
- state item остаётся `⬜ Not started`, `Escalation Needed: no`; он не получает escalation block и не попадает в Owner Gates;
- rerun с требуемым route может записать единственный `in-progress` event и пройти precondition;
- настоящий `blocked` и `escalated` сохраняют текущий red/escalation lifecycle;
- `routing-rejected` не увеличивает execution attempt и не создаёт return-loop/risk trigger;
- generated views свежи после обеих веток, а `plan-lint` не видит mismatch triple;
- command documentation не содержит одновременно «status unchanged» и `result=blocked`.

## Совместимость и миграция

Изменение forward-only. Исторические journal bytes не переписывать. Старые `result=blocked, friction=routing-blocked` двусмысленны: их нельзя молча переинтерпретировать, поскольку в истории мог быть реальный блок. Для уже затронутого item исполнитель добавляет новый legitimate `in-progress` event после correct route; прежняя запись остаётся process provenance. Для новых записей действует отдельный result.

## Дополнительный P1.2 incident — ADJUST не должен становиться terminal

В `2026.08.10-TASK-LEAN-AUTONOMY P1.2` field canary materialized one durable
`DecisionRequest` after the false route rejection. Generic request transport записал новый
`blocked` event и снова спроецировал `🔴 Blocked`, хотя D10/P1.2 определяют ADJUST как
nonterminal `🟡 In progress` с waiting continuation. Следовательно, исправление должно
различать и этот случай: pending owner decision не заменяет execution outcome и не может
использовать `blocked`, если договорённый результат — ADJUST. Добавить fixture
`ADJUST → DecisionRequest → 🟡` alongside routing-rejection fixture.

## Проверяемый результат

После route rejection оператор меняет только runtime model/effort и повторяет выданную команду. Повтор проходит precondition, начинает item и не требует фиктивного `plan-design`, ручной правки generated state или journal rewrite.
