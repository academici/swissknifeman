# 2026-08-13 — P10.6: broad in-scope remediation must not become a terminal block

**Статус:** ⬜ к внедрению.

**Источник:** Agelto `2026.08.09-RELEASE-READINESS`, P10.6, 2026-08-13.
**Затронуто:** `packages/task/commands/plan-exec.md`, `plan-run.md`,
`packages/task/lib/task/plan_blocking.py`, command projections и их fixture tests.

Исполнитель запустил native Codex `task:plan-run` для P10.6 с route evidence
`gpt-5.6-terra/high`; это удовлетворяло требованию item `implementation/high`.
Использованная installed projection была `task@0.13.2`:

- canonical source: local marketplace
  `/home/vostrikov/projects/packages/swissknifeman/packages/task`;
- Codex projection имеет canonical SHA
  `7159c37a87b114668c3439b1ae7725cc5bb9e16673f711000c863d7b5b36de96`
  для `plan-run`;
- source и installed adapter описывают continue-first / block-candidate policy. Это не
  был случай старого `task@0.11.1` из Agelto `AGENTS.md` и не доказательство stale

Текущий configured PHPStan исчерпал 256 MiB памяти, Pint dry-run нашёл семь нарушений
стиля, а временная проверка без baseline/exclude на `level:max` с `--memory-limit=1G`

`acceptance-failure`, создал block-candidate, получил isolated review `JUSTIFIED` и
`task.plan_blocking.evaluate()` вернул `terminal-block`/`BLOCK_CONFIRMED`.

## Почему это было неверно

P10.6 уже включает именно эту работу: `PHPStan level:max`, удаление baseline, запрет
ignore/exclude/level downgrade, root fixes для истинных type/behavior defects и full local
gate. Масштаб 1 591/266 делает работу дорогой, но сам по себе не доказывает ни отсутствующую
authority, ни frozen/public contract change, ни external dependency, ни небезопасный
rollback. Это in-scope remediation, которую следовало декомпозировать и исполнять в том же
item/attempt loop, а не превращать в terminal product status.

Моя ошибка была тройной:

1. Я принял *blast radius* за доказательство material boundary, не сопоставив finding с
   `Scope Included` и Code Guidance P10.6.
2. Я использовал слишком общий `acceptance-failure` в block-candidate. Reducer намеренно
   трактует подтверждённый `JUSTIFIED` как terminal, но не знает, что acceptance уже
   authoritatively включает remediation.
3. Я позволил external reviewer подтверждать неверно сформулированный вопрос («нужен ли
   redesign?»), а не сначала проверить «входит ли repair в объявленный item scope?».

Следовательно, terminal `🔴 Blocked` P10.6 — false escalation. Это не доказательство, что
Task policy отсутствует: `plan-exec` уже требует conflict-impact assessment и допускает
local reversible repair. Но policy пока не формализует правило для **широкой, но явно
in-scope remediation**, и reducer не получает scope-aware input.

## Что изменить

1. До `block-candidate` добавить обязательный scope-coverage gate: зафиксированный finding,
   включая broad static-analysis inventory, остаётся `repair-forward`, если его
   remediation прямо входит в `Scope Included`/Implementation Rules и не пересекает
   authority/frozen/public/security/data/external boundary.
2. Расширить closed candidate schema evidence полями `scope_coverage` (`in-scope` |
   `outside-scope` | `unknown`) и `boundary_evidence`; `acceptance-failure` с
   `in-scope` должен редуцироваться в `continue-local-repair`, даже если reviewer назвал
   объём большим.
3. Reviewer rubric должен требовать проверить declared scope и различать «need more work» от
   «cannot safely continue». `JUSTIFIED` допустим лишь при конкретной boundary evidence, не
   при количестве файлов/errors, времени или страхе scope creep.
4. Добавить fixture: item требует full-tree PHPStan max/no-baseline, inventory содержит сотни
   путей. Правильный результат — `local-repair`/decomposition и повтор исходного carrier;
   terminal block запрещён. Отдельно сохранить true-stop fixtures для missing owner authority,
   frozen/public contract, external dependency и unsafe rollback.
5. Вывести в `plan-run` receipt явное installed-adapter attestation (version + canonical
   command digest), чтобы incident analysis различала policy misuse и stale delivery.

## Возможные реализации

| Вариант | Плюсы | Риск / решение |
|:--|:--|:--|
| A. Scope-aware reducer | Машинно защищает terminal boundary; одинаково работает для всех providers | Нужно расширить schema/projections и fixture corpus; предпочтительный вариант |
| B. Только усилить prose/rubric | Дешёвое уточнение | Повторится при другом executor/reviewer; недостаточно |
| C. Запретить `acceptance-failure` как terminal всегда | Убирает этот false block | Ломает реальные невыполнимые acceptance/authority cases; неверно |
| D. Доверить owner chat как обход | Быстро продолжит текущий item | Нарушает durable authority; не заменяет lifecycle fix |

## Критерий готовности

Следующая правка lifecycle/block reducer реализует вариант A, добавит fixture из пункта 4,
прогонит canonical command + Codex/Claude projections и докажет, что broad in-scope work не
терминализируется, а истинные boundary cases остаются fail-closed. После реализации эта
roadmap-запись удаляется по правилу каталога.
