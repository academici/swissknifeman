# P3.4 CLI activity seam defect — 2026-08-04

## Observation

Terminal P2 `artifex.cli._start()` compiles a manifest, creates a `RunStore`, appends only
`freeze_run`, and returns `READY`. It accepts no provider or slice-count argument. Terminal
`artifex.cli._resume()` is only a status/reconcile wrapper.

The terminal `Scheduler` can dispatch an injected activity only when its caller supplies a
different internal slice shape: `slice_id`, `attempt`, `idempotency_key`, budget/usage fields and
an `authority_input` that the scheduler sends to the frozen authority evaluator. The P1 slice
manifest and worker-envelope contracts do not define a CLI mapping from compiled manifest to that
internal scheduler input, nor do they specify a provider request carrier for `start`/`resume`.

## Consequence

P3.4 cannot add the required explicit provider and `--max-slices 1` activity binding under its
declared Files without either inventing a new bridge contract or changing out-of-scope
`artifex/scheduler.py`. Both would violate the frozen P1/P2 ownership boundary and P3.4 scope.

## Required remediation

`task:plan-design 2026.08.03-ARTIFEX-SUPERVISOR P3.4` must define the exact manifest-to-activity
carrier and ownership, decide whether `scheduler.py` enters Files, and make the `start`/`resume`
provider dispatch acceptance executable before implementation resumes. It must preserve frozen
P0/P1 contract bytes and terminal P2/P3.1–P3.3 behavior unless an explicit recorded decision
changes the contract boundary.
