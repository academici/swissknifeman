### P1.1 — Заморозить роли читателей и реестр носителей

**Intent:** Записать контракт четырёх читателей плана (дизайнер / исполнитель / аудитор / владелец) — что каждому положено и чего ему НЕ положено — и завести реестр носителей, где каждый файл плана получает стабильный id, читателя-владельца, класс изменяемости и класс волатильности; машинная часть реестра выносится отдельным JSON, документ её объясняет и не повторяет.
**Why:** Замер показал, что все читатели читают одни и те же файлы, и платит за это самый частый — RAG:— (repo-grounded: `findings/00-plan-read-weight-2026-08-07.md` §3–§5). Внешняя практика даёт ровно недостающую абстракцию: форма запроса у текущего состояния, аудита и навигации РАЗНАЯ, историко-ориентированный потребитель — это отдельная проекция, а не обязанность обычного читателя — RAG:✅ 2026-08-07 (`findings/01-…` R4). Четвёртый читатель — дизайнер — назван самим владельцем («для новой сессии, когда возникает команда дизайна или сама разработка») и при этом самый дорогой: design-сессия идёт под frontier/high — RAG:— (repo-grounded: `brief/00-brief.md` §1 «Масштаб»; `plan-protocol` §13). Реестр — вход ВСЕХ последующих форм: путь чтения (P1.4), граница истории (P1.3) и гейты (P3) адресуют носители по его id, а не по прозе.
**Scope Included:** Документ контракта читателей: четыре роли, права и антиправа каждой, инвариант пересобираемости; определения классов изменяемости (`handwritten` / `append-only` / `generated-file` / `managed-block`) и волатильности (`stable` / `slow` / `volatile`) с правилом назначения по наблюдаемому факту; контракт маркеров для `managed-block` как исключения; **входной документ канона `plan-protocol` как носитель пути ДИЗАЙНЕРА (D93): он попадает в сессию каждого из четырёх читателей и потому является обязательным к чтению файлом по построению — без записи в реестре он выведен из условия приёмки D2(б) умолчанием, а не решением**; машинная часть — реестр носителей JSON со всеми носителями целевой раскладки.
**Scope Excluded:** Сами пути чтения и их порядок (P1.4); форма слепка (P1.2) и исторического вида (P1.3); реализация носителей и генераторов (P2); любые проверки в `plan-lint` (P3); правки команд и скилла (P6); очередь владельческих гейтов и рамка полномочий (P5); изменение `journal.jsonl` и его схемы.

**Implementation Rules:** - **Читателей ровно четыре, набор закрытый:** `designer` · `executor` · `auditor` · `owner`. Пятый читатель не заводится; если по ходу окажется, что какой-то путь не принадлежит ни одному из четырёх, это эскалация (см. Code Guidance), а не тихое расширение enum'а.
- У каждого носителя **РОВНО ОДИН `owner_reader`**; вторичные потребители перечисляются в `also_read_by` явно. Носитель без читателя-владельца и носитель с двумя владельцами одинаково запрещены: второй владелец — источник расхождения.
- **Классы изменяемости — закрытый набор из четырёх**, `managed-block` — исключение: строка реестра с этим классом обязана нести непустое `managed_block_justification` («почему смешение неизбежно»), иначе класс не применяется. Дефолт — `generated-file`: индустриальный дефолт «сначала отдельные генерируемые файлы» — RAG:✅ 2026-08-07 (`findings/05-…` R7).
- Для `managed-block` документ фиксирует полный контракт маркеров: namespace и ОДИНАКОВЫЙ стабильный id в обоих сентинелах, имя и версия генератора, sha256 канонизированного входа, отказ при отсутствии пары, отказ при двух парах на один id, отказ вместо частичного обновления при битом маркере — RAG:✅ 2026-08-07 (`findings/05-…` R7, fail-closed политика).
- **Класс волатильности назначается по наблюдаемому факту** «кто и когда переписывает эту секцию» и в реестре сопровождается полем-обоснованием. Назначение «на глаз» превращает правило порядка обратно в пожелание (митигация pre-mortem #6).
- Документ несёт инвариант пересобираемости дословно по смыслу: читателя можно заменить, но смысл, нужный для его пересборки, не может отсутствовать в логе; практически — любой вид сносится и пересобирается, а бриф, журнал, решения, findings и ТЗ снести нельзя — RAG:✅ 2026-08-07 (`findings/01-…` R4).
- **Машинная часть — отдельный JSON, документ её не дублирует** (D29). Ключи носителя: `id`, `path`, `owner_reader`, `also_read_by`, `mutability`, `volatility`, `volatility_basis`, `on_path_of`, опционально `managed_block_justification`, `class` (`spec` / `state` / `history` / `evidence` / `index`).
- Реестр перечисляет носители ЦЕЛЕВОЙ раскладки (`research/01-…` §4 + `research/03-…` §6.2), а не сегодняшней: он — вход P2, а не её описание. Сегодняшние носители, которые исчезают, отмечаются полем `superseded_by`.
- Реестр НЕ решает порядок и обязательность слотов — это P1.4; поле `on_path_of` объявляет только ПРИНАДЛЕЖНОСТЬ носителя пути читателя.
- **Реестр версионируется по раскладке и обязан объявить минимальный набор носителей, который потребляет P2** (D37): `plan-core` · `status-view` · `decision-record` · `decision-view` · `phase-index` · `item-spec` · `item-state` · `phase-closure` · `history-view` · `journal` · `handoff` · `brief` · `research` · `findings` · `roadmap` · `index` · `open-questions` · `bundle` · `artifacts`. Носители сегодняшней раскладки (v1) объявляются тем же реестром с пометкой версии и `superseded_by` — резолвер P2.1 обязан адресовать ОБЕ раскладки (D30), и реестр — его единственный вход. Добавлено при детализации P2 как реконсиль контракт-блока; расширение набора — новой D-записью, а не молча.
**Code Guidance:** Кода в item'е нет — есть контракт, и главный риск в нём: описать сегодняшнюю раскладку красивыми словами вместо того, чтобы задать целевую. Никакого «пусть пока будет как есть»: каждая строка реестра обязана быть проверена вопросом «кто физически перезаписывает этот файл и когда» — ответ идёт в `volatility_basis`; ответа нет → строка не готова. ЗАПРЕЩЕНО помечать item 🟢 при незакрытом предусловии «каждый из четырёх читателей — `owner_reader` хотя бы одного носителя И ни один носитель не имеет двух владельцев»: обходить гейт (завести читателя «прочие», приписать носитель двум ролям, оставить `volatility_basis` пустым) запрещено — не пройден → статус остаётся 🟡 + Pending Work с точной причиной. Прохождение подтверждается выводом команд из Validation, не словами. Если окажется, что какой-то реально существующий носитель не принадлежит ни одному из четырёх читателей — НЕ расширять enum самовольно: остановиться и эскалировать, это меняет решение D20 (число читателей). Самовольное расширение закрытого набора = дефект исполнения.
