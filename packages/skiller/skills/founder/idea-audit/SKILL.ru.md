# Skill: Idea Audit

Применять когда: есть сформулированная идея, raw-concept или готовый ТЗ/BRD, и нужно **обнаружить
скрытые ошибки до** того, как команда начинает строить. Проверка должна быть **неудобной** —
комфортный аудит бесполезен.

Базовый принцип (по методологии Anthropic Founder's Playbook): AI поддерживает то, во что верит
пользователь. Аудит направляет инструмент в **обратную** сторону — ищет уязвимости, пока они дёшевы.

---

## Когда НЕ применять

- Нет конкретной идеи / гипотезы → сначала `idea-discovery`.
- Нужен один точечный pressure-test одного тезиса → `adversarial-check` (быстрее, уже).
- Объект — готовый **ТЗ/BRD-документ** (полнота/противоречия/MoSCoW) → `requirement-critic` (он по
  написанному документу; idea-audit — по идее/концепту).
- Нужен широкий RAID/риск-разбор → `risk-assessment`; idea-audit — его стратегическая прелюдия.
- Уже идёт исполнение утверждённого плана → это execution, не аудит.

---

## Принципы

1. **Атаковать сильнейшую версию** тезиса, не удобную.
2. **Default to refuted**: нет данных = слабость гипотезы, а не нейтраль.
3. **First principles first**: разложить до атомов, не принимать индустриальные «очевидности».
4. **Архитектор тоже скептик**: техдолг, vendor-lock, неверная data-model убивают так же надёжно,
   как отсутствие рынка.
5. **Quantum of validation**: каждый вывод опирается на сигнал (данные / разговор / эксперимент),
   не на логику.

## Модуль 0. First-Principles Decomposition (обязателен первым)

Цель: убрать «очевидное» и проверить, что остаётся.

### Шаг 0.1. Список аксиом
Выписать **все неявные допущения**, на которых стоит идея («пользователи хотят X», «рынок Y
большой», «технология Z это позволяет», «конкуренты не сделали P, потому что…»). Формат каждой:
```
[Источник уверенности]: свой опыт / чужой опыт / данные / логика / вера
[Falsification signal]: при каком наблюдаемом событии аксиома рушится?
[Риск если неверна]: последствие для бизнеса
```

### Шаг 0.2. Рейтинг по риску
Ранжировать: Risk = (Вероятность ошибки) × (Impact если ошиблись). Топ-3 опасных аксиомы →
обязательные точки атаки в следующих модулях.

## Модуль 1. Рыночный скептицизм (5 векторов)

Прогнать по всем пяти. Цифры рынка — **только** web-grounded (см. «Web-grounding / RAG»), не из памяти.

### Вектор 1.1. «Боль реальна?»
- Сколько людей испытывают её **прямо сейчас**? Источник цифры?
- Как решают задачу **без** продукта? Если решают — боль терпима.
- Жёстко: «что конкретно сломается в жизни целевого пользователя, если продукта не будет?»
- Контекст: «no market need» исторически — причина №1 гибели стартапов (классический разбор
  CB Insights post-mortem'ов, ~42%; апдейт 2026 переформулирует как «poor product-market fit» ~43%).

### Вектор 1.2. «Timing правильный?»
- Почему именно сейчас? Что изменилось за 12–24 мес, чего не было раньше?
- Ничего не изменилось → почему не сделали 3 года назад? Изменилось → окно или устойчивый тренд?
- Проверить «Why now» через ≥3 независимых источника.

### Вектор 1.3. «Конкуренты провалились — почему вы нет?»
- Кто уже пробовал (даже косвенно)? Почему провалились?
- «Мы лучше» → в чём конкретно? Структурное преимущество или «мы умнее»?
- Построить **самый убедительный** case, где конкурент побеждает (не удобную версию угрозы).

### Вектор 1.4. «Платить готовы?»
- Willingness to pay тестируется действием, не словами. Что клиент делает **сейчас**, чтобы решить
  проблему? Платит за альтернативы? Сколько?
- «Пока не платят, но потом будут» — самое частое заблуждение early-stage.

### Вектор 1.5. «TAM настоящий или нарисованный?»
- Top-down TAM (большая цифра × доля) — всегда ложь. Требовать bottom-up: сколько конкретных
  компаний/людей готовы платить конкретную цену прямо сейчас?
- Минимально жизнеспособный рынок для unit-economics: CAC < LTV × 3.

## Модуль 2. Архитектурный pre-mortem

Цель: найти технические риски, которые убьют продукт на Scale/Launch, **до** первой строки кода.

### Шаг 2.1. «Представь провал через 18 месяцев»
> Проект провалился, инвесторы потеряли деньги, команда разошлась. Назови 5 конкретных
> **технических** причин, почему именно это произошло.

Обязательные категории разбора:

| Категория | Вопрос для pre-mortem |
|:---|:---|
| **Data model coupling** | Схема данных потребует полной переписки через 18 мес? |
| **Scalability cliff** | При каком объёме (DAU / RPS / размер данных) архитектура падёт? |
| **Vendor lock-in** | Какие решения создают зависимость, от которой сложно/дорого уйти? |
| **Integration brittleness** | Какие внешние API критичны? Что если изменятся / упадут / подорожают? |
| **Security debt** | Что упрощаем ради скорости, создавая дыры потом (auth, PII, финансы)? |
| **AI-specific risks** | Hallucination в критическом пути? Agentic drift? Prompt injection? Cost creep? |

### Шаг 2.2. Минимальная жизнеспособная архитектура
- Не проектировать всё — найти **минимальную** архитектуру до первых 1000 платящих без критического
  рефактора. «Architecture = решения, которые труднее всего изменить потом» — какие именно таковы здесь?

### Шаг 2.3. Build vs Buy vs Adapt
Для каждого ключевого компонента:
```
[Компонент] → Build / Buy / Adapt / Avoid
Обоснование: [1–2 предложения]
Риск выбора: [что пойдёт не так]
```

## Модуль 3. Внутренние противоречия концепта

### Шаг 3.1. Contradiction Scan
- Взаимно противоречащие утверждения; конфликтующие feature-promises («просто для новичков» +
  «мощно для экспертов» без explicit mode); временные (цель Q1, зависимость готова в Q3); ресурсные
  (команда 3 чел., план как у 15).

### Шаг 3.2. Optimism Bias Detector
- Разделы без рисков и только с плюсами → подозрительно.
- Цифры без источника → пометить `[UNVERIFIED]`.
- Конкурентный анализ, где все конкуренты слабее → скорее confirmation bias.

## Модуль 4. Kill-or-Build Verdict

### Scoring Matrix

| Критерий | Вес | Оценка (1–5) | Взвешено |
|:---|:---|:---|:---|
| Боль реальна и верифицируема | 3x | | |
| Timing правильный (Why now чёткий) | 2x | | |
| Willingness to pay подтверждена | 3x | | |
| TAM bottom-up жизнеспособен | 2x | | |
| Технический pre-mortem пройден | 2x | | |
| Противоречий в концепте нет | 1x | | |
| **ИТОГО** | **13x** | | **/65** |

**Интерпретация:**
- 50–65: 🟢 **BUILD** — переходить к BRD / architecture
- 35–49: 🟡 **REVISE** — вернуться к конкретным модулям, указать что именно
- 20–34: 🔴 **PIVOT** — рамка идеи ошибочна, менять сегмент / проблему / решение
- < 20: ⛔ **KILL** — структурные проблемы, без полной переработки нет смысла

### Формат вердикта
```
## Idea Audit Verdict: [название идеи]
Score: [X]/65 — [BUILD / REVISE / PIVOT / KILL]

### Критические уязвимости (исправить до BRD):
1. [уязвимость] → рекомендуемое действие

### Непроверенные аксиомы (требуют валидации):
- [аксиома] — способ проверки: [experiment / interview / data]

### Архитектурные решения, принять до BRD:
- [решение]

### Следующий шаг:
→ BUILD: `pm/brd` / REVISE: вернуться в `idea-discovery` / PIVOT: `adversarial-check` с новым тезисом
```

## Web-grounding / RAG

Рыночные векторы (Модуль 1), failed competitors, «Why now», любые цифры — **верифицировать через
внешний поиск**, не генерировать из памяти. Канон дисциплины — `general/verify-claims` (он резидентен
в каждом проекте). Перед фиксацией вердикта BUILD рыночные данные обязаны иметь источник.

---

## Что агент добавляет сам

- **Catch own bias.** Если предыдущий анализ был подозрительно оптимистичным — назвать и атаковать жёстче.
- **Asymmetry check.** «За» сильно перевешивает «против» → сигнал confirmation bias, не реальности.
- **Синергии с портфелем.** Проверить, не реализована ли идея частично в соседнем проекте (если есть
  карта проектов в контексте).
- **Stage-aware depth.** `stage: idea` → полный аудит. `stage: mvp+` → фокус на Модулях 2 и 3.

---

## Жёсткие запреты

НЕЛЬЗЯ:
- Давать вердикт BUILD без прохождения всех 4 модулей.
- Давать цифры TAM / CAC / LTV без источника.
- Пропускать архитектурный pre-mortem даже для «простых» идей.
- Принимать «мы умнее конкурентов» как преимущество без структурного обоснования.
