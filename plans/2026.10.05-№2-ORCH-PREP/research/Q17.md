# Q17

Запрос (perplexity-web-mcp stdio, default pool; search):

```text
Git 2.43+, several linked worktrees of one repository, each on its own branch. Answer in Russian, prose, max 500 words, with git-scm.com URLs:
1) Is it safe for two worktrees to run `git commit` at the same moment on different branches? Which shared locks can collide (refs/heads/<branch>.lock, packed-refs.lock, objects, auto gc / `gc.auto`, `git maintenance`) and what error text appears; recommended mitigation for automated agents (retry, gc.auto=0, maintenance off)?
2) During `git rebase` (merge backend, ort) and `git cherry-pick`, are gitattributes `merge=union` drivers applied the same way as in `git merge`? Which .gitattributes is read during rebase: the one in the working tree or the one in the commit being picked?
3) `git worktree remove` vs `prune` after a crashed process; what remains locked.
```

Ответ (как вернул сервис, 2026-10-07):

Да, параллельные git commit в разных linked worktrees на разных ветках безопасны в штатном режиме: индексы и HEAD раздельные, хотя refs и объекты общие. Отдельно нужно контролировать обслуживание репозитория и восстановление после аварий.

## 1. Коммиты и блокировки

Для обычного файлового backend refs (files) блокировки $GIT_COMMON_DIR/refs/heads/<branch>.lock общие по расположению, но разные для разных веток: два таких коммита друг другу не мешают. index.lock и HEAD.lock принадлежат конкретному worktree. Конкурентное изменение той же ветки другим процессом может дать cannot lock ref 'refs/heads/…': Unable to create '…lock': File exists; изменение ожидаемого значения ref — is at … but expected ….
packed-refs.lock действительно общий, однако обычный коммит не переписывает packed-refs: даже для упакованной ветки он создаёт/обновляет loose ref. Коллизии возможны при pack-refs, удалении refs, GC и другом обслуживании; типичный текст — Unable to create '…/packed-refs.lock': File exists. Общая objects/ не означает глобального mutex для коммитов: параллельная запись объектов — штатная операция.
Автоматическое обслуживание может запуститься после коммита. git maintenance run блокирует другие maintenance-запуски, но не обычные записи объектов; проигравшее обслуживание может просто пропустить запуск. git gc использует отдельную защиту через gc.pid; явный конкурентный запуск может сообщить gc is already running on machine … pid … (use --force if not), тогда как gc --auto обычно тихо отступает. Смешивать независимые GC и maintenance нельзя; особенно опасен gc --prune=now одновременно с записью.
Для агентов рекомендую заранее установить общие git config gc.auto 0 и git config maintenance.auto false; запланированное обслуживание отключить для этого репозитория через git maintenance unregister, либо весь пользовательский scheduler через git maintenance stop. Затем обслуживать централизованно. Повторять только временные lock-ошибки с ограниченным backoff, предварительно проверяя HEAD: ошибка обслуживания не означает, что коммит не создан.

## 2. Union при переносе коммитов

Да: merge-backend rebase с ort и cherry-pick используют тот же механизм файлового трёхстороннего слияния и учитывают merge=union. Драйвер нужен только при фактическом слиянии содержимого; он не устраняет структурные конфликты и не гарантирует осмысленный порядок строк.
Читается .gitattributes текущего рабочего дерева, при отсутствии — из текущего индекса, с учётом более приоритетного info/attributes. Это не автоматическое чтение атрибутов из переносимого коммита. При rebase сначала checkout новой базы, затем последовательное воспроизведение: действуют атрибуты текущего состояния, включая уже перенесённые изменения. Новое правило в самом переносимом коммите не следует считать действующим для его собственного слияния.

## 3. Remove и prune после аварии

remove удаляет существующий worktree и его административный каталог; грязный требует --force. prune удаляет устаревшие метаданные отсутствующих worktrees, а не очищает существующий каталог.
Авария может оставить локальные index.lock/HEAD.lock, состояние rebase/sequencer и общие ref/maintenance locks. prune не очищает общие locks. Удаляйте конкретный stale lock только после проверки отсутствия владельца. Маркер worktrees/<id>/locked — отдельная постоянная защита от prune/remove, не mutex Git-операции: нужен unlock либо для удаления remove --force --force. Сама ветка после удаления worktree сохраняется.
