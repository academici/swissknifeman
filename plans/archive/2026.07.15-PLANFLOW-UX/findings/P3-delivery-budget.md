# P3.5 — Budget-квантификация доставки гейта `workflow-craft`/`make-workflow`

**Дата:** 2026-07-15 · **Модель:** opus/high (plan-run, Exec=manual) · **Git-якорь:** дерево на `2173b27` (HEAD до item-коммита P3.5).
**Метод:** фактические прогоны `skiller budget` + прямой замер tier-0 через `budget.skill_budget` (тот же токен-оракул, что и гейт). Числа своего репо — с git-якорем.

---

## 0. Что на самом деле не доставлено (уточнение A1)

Recon (§1.2) точен: во флоте `core@`+`task@` **везде**, значит команда `/task:make-workflow`
(со статич-ревьюером) уже физически в проектах — она едет плагином `task@`. **Не доставлен ровно
один артефакт — реестровый скилл-требований `workflow-craft`** (`general`-бакет, в `core`-плагин не
входит, `task@` его не бандлит; подключён в 1/15 — agelto). Поэтому «доставка гейта» = **доставка
скилла `workflow-craft`**; вопрос канала (OQ-3) — про него.

Почему это и есть рычаг: `workflow-craft` — тонкий pointer-скилл, срабатывающий на «write a
workflow»/multi-agent orchestration. Его `description` (ярус-0) — то, по чему агент вообще УЗНАЁТ,
что дисциплина авторинга существует и надо свериться с 4 канон-шаблонами + матрицей. Нет
description в резиденте → агент не знает, что скилл есть → пишет workflow «на глаз» (ровно
систематические дефекты §1.3 recon). Тело (ярус-1) грузится только по срабатыванию — оно НЕ резидент.

## 1. Замеры (фактические, воспроизводимые)

| Метрика | Значение | Команда (на дереве `2173b27`) |
|:--|:--|:--|
| CORE резидент сейчас (⊕ tier-0, 9 скиллов) | **694 / target 750 — OK** | `skiller budget --check-core` |
| Остаток headroom CORE | **56 ток** | 750 − 694 |
| `workflow-craft` tier-0 (name+description, резидент) | **48 ток** | `budget.skill_budget('skills/general/workflow-craft')['tier0']` |
| `workflow-craft` tier-1 (тело, on-trigger — НЕ резидент) | 3096 ток | тот же вызов, `['tier1']` |
| CORE резидент ПОСЛЕ добавления (проекция) | **742 / 750 — OK** | 694 + 48 (два фактических замера) |
| Остаток headroom ПОСЛЕ | **8 ток** | 750 − 742 |

> **Честно «на грани» (Code Guidance D6):** число НЕ пробивает порог (742 < 750, статус остаётся
> `OK`, не `OVER`), но съедает 48 из 56 оставшихся токенов. **8 ток headroom** = `workflow-craft`
> фактически становится ПОСЛЕДНИМ скиллом, влезающим в CORE при target 750: любое следующее
> расширение ядра потребует либо ужать чей-то `description`, либо поднять target. Это не «дёшево и
> свободно» — это «влезает, заполнив ядро под потолок».
>
> `742` — **проекция** из двух реальных замеров (694 измерено + 48 измерено), НЕ пост-правочный
> прогон `--check-core`: config.py в этой фазе не трогается (scope-excluded). Воспроизводима
> сложением; при реальном rollout сверить `--check-core` после правки CORE_SKILLS.

**Про `--first-turn` 10K-порог (if-then item'а).** Прогон `skiller budget --first-turn` в самом
репо swissknifeman даёт 10674 ток (WARN) — но это футпринт ЭТОГО репо-хаба (36 скиллов meta + 2 MCP
+ большой CLAUDE.md), НЕ типового онбордженного dev-проекта (у того резидент скиллов ≈ CORE 694 +
agents + CLAUDE.md + хуки + MCP). Добавление 48 ток к first-turn любого проекта — в пределах шума,
10K-порог не при чём. **If-then item'а («>10K → сместить к required-on-onboard») НЕ срабатывает**:
релевантный гейт здесь — `--check-core` (742/750 OK), а не first-turn самого хаба.

## 2. Развилка канала (OQ-3) — варианты с ценой

| Канал | Резидент-цена | Охват | Механизм |
|:--|:--|:--|:--|
| **A. CORE_SKILLS** (10-й скилл ядра) | +48 ток в КАЖДЫЙ проект; CORE → 742/750 | ВСЕ онбордженные (present + future) авто | одна правка `config.py::CORE_SKILLS` + `core-policy.json`; `connect`→курир.плагин `core`, `vendor`→skill-level |
| **B. required-при-онбординге dev/оркестр-проектов** | 0 глоб.резидента; 48 ток только в проектах, куда доставлен | только классифицированные-как-нужные | нужен project-class гейт (профиль/`requires`) + логика «этому проекту — да»; будущие/непроклассифицированные — мимо |

**Ключевая асимметрия гейтов:** target 750 (`--check-core`) применим ТОЛЬКО к варианту A (CORE).
В варианте B `workflow-craft` в CORE не входит → 750-гейт его не считает вовсе; он лишь +48 к
first-turn тех проектов, куда доставлен (7K/10K-бюджет — незначимо). То есть «8 ток headroom» —
проблема ИСКЛЮЧИТЕЛЬНО варианта A.

## 3. Рекомендация (D6: видимость-гейта > экономии токенов)

**Рекомендую вариант A — CORE_SKILLS**, с честной оговоркой (ниже). Причины:

1. **Бюджет держит** (742/750 OK, замерено) — CLAUDE.md-гейт «новый always-on inject» пройден:
   48 ток резидента, тело 3096 остаётся on-trigger (не резидент). D6-порог «не в ущерб результату»
   не нарушен экономией.
2. **Авторинг workflow широк, не «dev-подмножество».** Recon-инвентарь (dterema, chatom, corex,
   themeon, vaulter, Brain-вэлт, estai, azguard…) — workflow пишутся в проектах РАЗНОГО класса, а
   Workflow-тул доступен сессии везде. Вариант B требует классифицировать «кому нужен» — и рискует
   ВОССОЗДАТЬ невидимость A1 для многих проектов, которые пишут workflow, но не попали под «dev».
3. **Наименьший механизм.** A = одна правка `CORE_SKILLS`, авто-охват всех текущих и будущих
   онбордов, без project-class логики. B требует построить и сопровождать классификатор.
4. **D6-честность:** беззубо-невидимый гейт (текущий охват ~0) хуже +48 ток/проект. Рекомендация —
   что лучше для ВИДИМОСТИ гейта, не что дешевле.

**Оговорка (передаётся Owner как часть решения):** вариант A заполняет CORE под потолок (8 ток
headroom) и слегка размывает принцип курирования «CORE = универсально-релевантное» (`workflow-craft`
релевантен УСЛОВНО — когда пишут workflow, в отличие от `context-economy`/`plan-protocol`, нужных
всегда). Если Owner приоритезирует **headroom ядра** или **строгую курацию** → вариант B (0 CORE-цены,
но нужен project-class гейт + риск недодоставки). Если выбран A и планируется рост CORE — заложить
скромный подъём target (напр. 750→800) отдельным решением.
