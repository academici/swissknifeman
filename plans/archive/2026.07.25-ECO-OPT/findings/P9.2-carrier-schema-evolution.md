# P9.2 — эволюция схемы conformance-pinned контракта: RAG-выжимка, 2026-07-28

Слой 1 (внешнее). Снято при разборе эскалации P9.2 (`plan-design`, Opus/high). Вопрос,
поставленный движку: **когда расширять frozen closed-world контракт version-dispatch'ем, а
когда заводить отдельную extension-таблицу по тому же ключу** — для policy-as-data реестров,
чей базовый файл пиннится конформанс-проверкой.

## §1. Запрос и движок

- Движок: `perplexity-web` `search` (flat-rate мост, RAG-ступень лестницы после промаха
  context7 — предмет не библиотечный API, а паттерн проектирования схем, context7 неприменим).
- Дата: **2026-07-28**.
- Запрос (сокращённо): *«Schema evolution for versioned JSON config contracts validated with
  closed-world (exact key set) validation: when to widen the frozen contract with version
  dispatch vs. add a separate extension table keyed by the same identity? Best practices 2025
  for policy-as-data registries, additive extension, avoiding coupling unrelated concerns into
  a conformance-pinned file.»*
- Источники ответа: <https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html>
  (compatibility guidance для closed content models),
  <https://www.reddit.com/r/dataengineering/comments/1j5j59f/how_do_you_handle_data_schema_evolution_in_your/>
  (полевая практика), плюс общая семантика JSON Schema `additionalProperties: false` /
  `unevaluatedProperties`.

## §2. Ответ движка (выжимка, не пересказ своими словами)

**Правило первого порядка.** Для closed-world exact-key контракта держать замороженный
контракт узким, а неродственные концерны выносить в отдельную extension-таблицу, если новые
данные *опциональны, ортогональны или живут в другом жизненном цикле*. Version-dispatch внутри
контракта оправдан, **только** когда новое поле — часть той же семантической единицы и обязано
валидироваться атомарно с базой.

**Version-dispatch — когда истинно ВСЁ:**
- новое поле требуется для осмысленной интерпретации записи;
- старая и новая формы достаточно взаимоисключающи, чтобы валидатор выбирал между ними;
- это по-прежнему один концептуальный документ, а не «база + опциональный оверлей»;
- один контракт должен остаться единственным SSOT для производителей И потребителей.

**Отдельная extension-таблица — когда истинно ЛЮБОЕ:**
- новый концерн опционален или разрежен;
- у базы и расширения **разные владельцы**;
- ожидается **разный темп эволюции**;
- не хочется расширять запиненную схему ради неродственной политики/флагов.

**Почему обычно лучше расширение.** Closed-world даёт сильные гарантии, но делает расширение
дорогим: каждый новый ключ становится событием совместимости. `additionalProperties: false`
блокирует необъявленные поля, и закрытые схемы особенно хрупки при попытке расширять их
композицией; Confluent'овская compatibility-модель показывает то же — closed content model
сужает множество безопасных изменений, поэтому расширение запиненного контракта должно быть
*осознанным, а не автоматическим*.

**Рекомендованная структура (дословная форма ответа):** `core_config` (identity + инварианты +
exact-key валидация) · `schema_version` (version-dispatch только для семантически ломающих
изменений) · `core_config_extension` (тот же ключ, namespace-scoped extras, опциональные
policy-оверлеи). Правило перехода: **если расширение начинает влиять на поведение ядра так, что
требуется атомарная валидация с базой — повышать его в замороженный контракт; пока оно
ортогонально — держать отдельно и связывать по идентичности.**

**Для policy-as-data реестров отдельно:** базовый файл — авторитетный контракт, расширения
модульны; это снижает churn, не даёт несвязанным владельцам сцепляться через общий файл и
локализует ревью либо в базовом контракте, либо в явно названной extension-области.

## §3. Вердикт применительно к P9.2

Проверка нашего случая по критериям движка — **все четыре признака extension-таблицы истинны**:

| Критерий | Наш случай |
|:--|:--|
| концерн опционален/разрежен | блок `review` нужен 5 записям из 44 |
| разные владельцы | база — provider-parity (Claude/Codex проекции, архивный `2026.07.19-DUAL-PROVIDER`); расширение — процедура ревью (L2, трек 1 OQ-4 / P7.2) |
| разный темп эволюции | реестр ревью правится при каждой правке содержания паков; provider-binding — при смене провайдера/селекторов |
| нежелание расширять запиненную схему | `role-bindings.json` конформанс-пиннут по sha256 в ДВУХ генерируемых файлах (см. `research/23`) |

Ни один критерий version-dispatch'а не выполняется: `review` **не** требуется для интерпретации
записи (`model_selector`/`color` самодостаточны), формы не взаимоисключающи, это база +
оверлей, и SSOT содержания ролей — вообще третий файл (`configs/common/agent-packs/roles.json`).

**Вердикт: extension-таблица.** Совпадает с решением владельца 2026-07-28 (D126).
Ограничение честности: ответ движка — синтез, не нормативный стандарт; несущим здесь он
является только в части «критерии выбора», а окончательное основание решения — repo-grounded
факты `research/23-P9.2-registry-carrier.md` §1–§3, воспроизведённые на дереве.
