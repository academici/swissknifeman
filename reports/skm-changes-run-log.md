### R11. P2.3: вопросы исполнителя — решение по аудиту и внешним источникам

- Исполнитель остановился `blocked` с тремя вопросами (Q1 форма close, Q2 request-документ в receipts, Q3 статус `nothing`). Ответы в плане дословно не было, поэтому по твоему запросу собрал основания.
- Аудит (`audits/skm.md`): «неизвестный outcome никогда автоматически не превращается в success»; «повторный resume не дублирует side effect»; durable-запись с idempotency key до побочного эффекта.
- Внешние источники (WebSearch, два запроса; perplexity-web здесь не подключён, его подключение меняет машинный конфиг и требует входа — это решение владельца): intent record перед внешним действием, ключ = бизнес-действие, «таймаут — не значит, что эффект не случился».
- Решения:
  - Q1 → вариант a: форма close с полем `by` сохраняется, `{outcome, gate}` остаётся у register. Меньше ломает контракты exec/v1.
  - Q2 → вариант a: request-документ разрешён, с защитой от сопоставления нового запроса со старой квитанцией (ключ = attempt).
  - Q3 → вариант b: `nothing` не засчитывается сам по себе; commit повторяется по букве item.rules[1]. Повтор безопасен: при пустом workspace это no-op, а ложного done не будет.
- Ответы записаны в `orch conduct answer`, пункт возобновлён (`resume --retry P2.3`). Решения — мои, по аудиту и внешним источникам; владелец может переопределить.

### R12. P2.3: цикл вопросов — расхождение спецификации пункта с контрактами, нужно решение владельца

- Три ревизии вопросов подряд (rev 1, 2, 3) с одними и теми же тремя расхождениями. Ответы по аудиту и внешним источникам (R11) снимают вопрос по существу, но не противоречие: исполнитель остановился на escalation «обязательные чтения противоречат цели».
- Противоречия (подтверждаю по коду и тексту пункта):
  1. `close` восстанавливается с `{outcome, gate}` по тексту пункта, а текущий `close` и `finish` работают с `{by, ...}`. Канонический вид сломает потребителя.
  2. Квитанция commit не содержит `attempt`; схема `work-source/v1` запрещает дополнительные поля ответа. Без этого crash point 6 не доказуем.
  3. `workspace_commit.status == nothing` есть в схеме и реализации, но не в `item.rules[1]`.
- Почему ответы не помогают: пункт требует то, что контракт не даёт (п. 2), и правило (п. 3), которого нет в схеме. Выбирать «а» или «б» без правки контракта или пункта нельзя — это изменение спецификации.
- Варианты решения (нужен выбор владельца):
