# P4 — Implement locale rendering and evidence-admitted lean skill migration

## Phase Context

P4 implements the frozen P2 locale/authoring contracts on top of terminal P3 control-plane
and status interfaces. Execution is closed until P0–P3 are terminal and the exact frozen
P2/P3 contract files and item commits named below exist. Locale resolution is a shared,
stdlib-only domain: packages and providers receive one immutable per-surface context but keep
ownership of their own source catalogs and rendered targets. Migration is admission-led, not
a bulk translation: every canonical unit needs an owner, preimage, immutable-token proof,
independent English/Russian review and rollback before it can change. Six items form one
sequential chain through a cumulative ledger, ending in a single regeneration/readback item.
The phase never mutates a consumer project, user locale state, provider trust/credentials or
another provider's files; those remain P5/P6 concerns.

P4.1–P4.6 use the D39 per-cwd carrier in `roadmap.md`; the root coordinator owns
integration, the cumulative ledger and item closure, while package mutations occur only from
fresh package-cwd sessions. P4.3–P4.6 additionally use D40 bounded ledger batches. Every batch
has a committed manifest/checkpoint, a distinct read-only reviewer record and deterministic
resume pointer; no next batch starts before the prior one is accepted.

The audit is not a pre-approved corpus diff. P4.2 produces one canonical lean template and its
generated distribution copy plus shared risk/invocation cross-field validation. P4.3 may merge,
thin, split, reclassify or retain a skill only when the admission row binds source/publication
class, real positive/negative provider replays, no-skill/minimal ablation, provider-qualified
budget evidence and independent review. Vue 11→8, navigator removal, singleton consolidation and a
universal Gotchas block have no default authorization.

**Scope Included:** shared locale values/resolution/catalog/rendering; plan/response/diagnostic
render contexts; one canonical lean skill template and generated copy; shared risk/invocation
semantics with provider adapter mapping; English-source and sparse-overlay validators;
owner/preimage/replay/ablation/review/rollback migration tooling; evidence-admitted migration of
skills, commands/plugins/diagnostics, code prose and development docs; terminal regeneration and
two-provider readback.

**Scope Excluded:** changing frozen P1/P2/P3 contracts; reading environment/filesystem inside
the pure resolver; provider/fleet rollout; translating IDs, paths, commands, schemas, keys,
diagnostic/action codes, placeholders or parser literals; automatic translation/self-review;
deleting an unadmitted RU source or local override; credential/trust repair.

> **Контракт фазы (contract-first).** Потребляет: terminal P0–P3; all frozen provider/Skill Core/adapter/skill-evidence/locale/authoring contracts; P2 carrier matrix/checker; P3 desired snapshot, audit graph and diagnostics · Производит: shared locale runtime, provider-owned render integrations, canonical evidence-admission ledger/migration tooling, reviewed lean English-source corpus, generated projections and P5/P7 acceptance evidence · Границы: no contract rewrite, heuristic-only content action, consumer/fleet mutation, provider trust/credential action, local-override adoption or cross-provider write.

## Phase Handoff

**Фаза P4 не закрыта.** P4.3 is `🔴 Blocked`: P4.2's terminal ledger contains no inventory roots or admitted skill rows, while the current Skiller corpus contains 232 canonical `SKILL.md` files. P4.3 therefore cannot create a migration checkpoint, review record, or rollback evidence without violating its frozen admission rules. Re-design P4.3 must establish an evidence-backed inventory/admission producer and reconcile the terminal journal fingerprint carrier before any corpus mutation. P4 performs no consumer, fleet, trust or credential mutation.
