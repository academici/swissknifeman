# Roadmap: качество description скиллов (явный триггер для авто-роутинга)

**Статус:** ОСТАТОК (P3.5, `2026.07.29-HARNESS-AGNOSTIC`, 2026-07-30). Гейт качества
description-как-триггера введён (`packages/skiller/scripts/validate.sh` + one-way рэтчет
`scripts/desc-trigger-burndown.txt`, по образцу гейта длины) и измеренный blocker-набор
(39 локальных описаний < 100 симв без триггера) починен по двуязычному потоку. Остаётся:
69 локальных описаний ≥ 100 симв без триггерной фразы — унаследованный долг в
`desc-trigger-burndown.txt`, сокращаются при следующей правке каждого скилла (one-way, не
батчем); и рычаг №4 владельца (`2026.07.25-ECO-OPT` D74) — сжатие описаний ради слотов
обнаружения, вне оси качества, не тронут этим item'ом. Массовая перезапись всех 69 разом
остаётся спекулятивной работой без измеренного провала роутинга (см. «Почему отложено
дальше этого» ниже — рассуждение не изменилось, изменился только счёт).

## Контекст

После удаления полного каталога скиллов из хаба (`generate-hub.sh` больше не дублирует
`description` каждого установленного скилла в CLAUDE.md консьюмера — см. commit, фикс
инцидента с задвоенным хабом у Agelto), весь авто-роутинг скилла держится ИСКЛЮЧИТЕЛЬНО на
`description` фронтматтера, который Claude Code индексирует нативно при старте сессии.
Раньше ручной каталог отчасти дублировал эту функцию как читаемая для человека шпаргалка;
теперь единственный сигнал роутинга — сам `description`.

Верифицированная (Perplexity + офиц. доки Claude Code) формула для надёжного авто-роутинга:

> **«[что делает скилл]. Use when [явные триггер-фразы/синонимы, включая домен-специфичные
> сокращения]»** — третье лицо, самый различающий сигнал первым (описание+`when_to_use`
> обрезаются на 1536 симв).

## Замер (skills.json, на момент фикса)

- Скиллов с явной триггер-фразой (`use when|activate when|activate on|activate before`,
  без учёта регистра): **73/207**.
- Без неё: **134/207** (после доп. правок в этой же сессии — **138/207**, см. `SKM_DESC_QUALITY=1
  bash packages/skiller/scripts/validate.sh`).
- Существующий гейт длины (`DESC_WARN_MAX=450`) сегодня почти не шумит (~8 нарушений) —
  включить проверку триггер-фразы БЕЗУСЛОВНО означало бы разом ~140 строк warning, что
  непропорционально и против собственного принципа репозитория «фичу внедряем по факту
  измеренной проблемы, не на упреждение» (см. `docs/reference.md`).

## Что уже сделано (инструмент замера, не гейт)

`packages/skiller/scripts/validate.sh` получил **opt-in** (по `SKM_DESC_QUALITY=1`)
предупреждение на description без явного триггера — НЕ включено в CI
(`.github/workflows/validate.yml` не трогали), только ручной замер по запросу.

## Почему отложено дальше этого

- Массовая правка ~140 описаний разом — не «фикс бага», а спекулятивная работа без измеренного
  провала роутинга; часть из них может и так триггериться штатно по имени/тегам/бакету.
- Правильный следующий шаг — не переписать все 140 в одну итерацию, а приоритизировать по
  ФАКТУ: скиллы с низкой/нулевой активацией (данные `lib/skiller/quality/audit.py`, если там
  уже есть usage-сигнал) или те, что реально «промахнулись» в наблюдаемых сессиях
  (`session-observer` — skill-skip находки).

## Дизайн (если дойдём)

- Оформить отдельным `task:plan-design` → `plans/SKM-MASTER-00X` (не расширять этот roadmap-файл
  в мастер-план явочным порядком).
- Батчи по бакетам, не сплошной проход по всем 207.
- Каждая правка описания — по формуле выше, третье лицо, синонимы/домен-аббревиатуры как
  триггер-токены.
- Гейт (`SKM_DESC_QUALITY` из опции в CI-обязательный) включать только после того, как основная
  масса «горячих» бакетов приведена в порядок — иначе CI получает шум без пользы на скиллах,
  до которых очередь ещё не дошла.

## Зависимости

- `packages/skiller/scripts/validate.sh` (замер уже есть).
- `lib/skiller/quality/audit.py` — источник приоритизации по факту использования (сверить, что
  там есть нужный сигнал, прежде чем писать план).
- `system/session-observer` — skill-skip находки как альтернативный источник приоритизации.
