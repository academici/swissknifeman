экономия (расчёт) → риск → класс. Опора — цифры P3.1 плюс 3 доп. read-only

оказались non-issue; фиксирую сам факт перепроверки, не только вывод).

**Риск сжатия сейчас:** понизить точность авто-роутинга без измеренной

### R3 — «Непросмотренные run-report'ы» (azguard/chatom/swissknifeman): перепроверено, false alarm
**Что проверено:** P3.1 зафиксировал 20 run-report'ов на 3 проектах без
единого урока в `.claude/analyst/` и назвал их «непросмотренными» (аналог
сигнала из `295951c`). Здесь прогнан `analyst digest --dry-run --json` на
САМОМ СВЕЖЕМ run-report каждого из трёх проектов (read-only, ничего не
пишет):
```
azguard:       {"candidates": []}
chatom:        {"candidates": []}
swissknifeman: {"candidates": []}
```
**Вывод:** SessionEnd-хук (`DIGEST=on` по умолчанию, `_run_digest` в
`run-report.py`) реально дёргает `analyst digest` и корректно резолвит
бинарь — иначе `--dry-run` не нашёл бы `analyst` вовсе. Экстракторы
(resolved-failure/workaround/рецидив) — намеренно высокоточные (по
`digest.py`), 0 кандидатов на сессию — легитимный результат, не сбой и не
забытый бэклог. Отсутствие `.claude/analyst/` на этих 3 проектах означает
«digest запускался и ничего не нашёл», не «не запускался».
**Расчёт экономии:** 0 (нечего экономить — не найдено проблемы для фикса).
**Риск:** — (действие не требуется).
**Класс:** **без действия** (P3.1-гипотеза скорректирована, не фикс).

### R4 — Бакеты `swissknifeman`/`loqum` (general+oss-dev): перепроверено, оба обоснованы
**Что проверено:** P3.1 отметил 2 marketplace-проекта на legacy
`core+general+oss-dev+task` вместо CORE-only как кандидатов на снятие.
Здесь — прямая проверка обоснованности (Implementation Rules: «сомнение =
не снимать»):
- `swissknifeman` — сам этот монорепо-реестр; в ЭТОЙ ЖЕ сессии активны и
  используются скиллы из `general`/`oss-dev` (`writing-style`,
  `naming-conventions`, `packages-stack`, `git-commit-rules`,
  `project-map`, `resolving-merge-conflicts` и др., список подтверждён
  доступными в сессии скиллами) — dogfooding, не забытый хвост.
- `loqum` — `.swissknife.json` явно и осознанно задаёт
  `["architect","ai","oss-dev","general"]`; `CLAUDE.md` проекта — «Phase 0
  (архитектурное проектирование, bootstrap)», platform-сервис реалтайм-ИИ —
  профиль объясняет широкий набор (architect+ai+oss-dev на стадии
  дизайна). Нет данных использования (0 run-report, 0 analyst-state) —
  но их отсутствие само по себе не аргумент «неиспользуемо» при явно
  осмысленной конфигурации.
**Расчёт (гипотетический, НЕ рекомендуется к исполнению):** миграция на
CORE-only сэкономила бы ⊕`2029-705=1324` ток/сессию на проект (общий
`general`=1402+`oss-dev`=627=2029 ⊕ tier0 против CORE 705) — цифра
зафиксирована на будущее, если появится измеренный сигнал неиспользования
(profile.py / access-log), но сейчас основания снимать нет.
**Риск снятия сейчас:** сломать активный dogfooding-набор
(`swissknifeman`) или архитектурный набор ранней стадии (`loqum`).
**Класс:** **без действия** (кандидат отклонён при проверке, не quick-win).

### R6 — Низкое покрытие analyst-цикла (2/20 проектов со стором, 5/20 с run-report) — процессная рекомендация
**Расчёт:** `analyst` (+ `token-report`) в принципе не считается на 18/20
(нет `usage-trend.ndjson`) и на 15/20 нет даже run-report вообще — не
потому что digest ломается (см. R3), а потому что: (a) хук `run-report`
включён не на всех 20 (harness-хуки — per-project настройка, не
глобальный демон); (b) там, где включён и накопил историю (agelto — 42
записи трека, 30 run-report), сигнал полезен (rolling-baseline уже
считается). Экономия конкретной цифрой не выражается (это data-coverage
gap, не token-waste), но ценность: без покрытия P3-класс отчётов (эта
самая фаза) не масштабируется на весь флот при следующем аудите.
**Риск:** трогать harness-хуки на 15 чужих проектах разом — межпакетное
изменение конфигурации множества репозиториев, шире «safe reversible
на одном проекте» из Scope P3.3.
**Класс:** **roadmap** (черновик-строки для `roadmap/analyst-fleet-coverage.md`,
файл создаётся в P3.3 если решат материализовать):
- Проблема: 15/20 проектов не пишут run-report → `analyst`/`token-report`
  не может ничего посчитать там, где данные никогда не появляются.
- Цифры: 5/20 с run-report (agelto 30, azguard 10, vaulter 9, chatom 6,
  swissknifeman 4); 2/20 с analyst-state; 2/20 с token-trend.
- Варианты (без обязательств): (1) включить `run-report` хук по
  умолчанию для новых онбордингов (`maind onboard`/`harness hooks`); (2)
  ничего не менять — данные появятся органически по мере использования
  проектов; (3) добавить `analyst`-срез в `maind projects status`/`maind
  fleet` для видимости покрытия без отдельной команды на проект.
- Не внедряется в этом плане (D6): требует решения по umbrella-политике
  hooks на чужих проектах, не «safe quick-win».
