# P3 слой 1 — полевая практика: как MCP-серверы отдают крупные результаты (2026-07-25)

Факт-класс FC-5 карты `research/03-P3-fact-classes.md`. Движок — `perplexity-web` (`search_advanced`,
web+social, 2026-07-25). Класс знания, который first-party дока не покрывает по определению
(D20-б): «что ломается на практике». Источники синтеза — публичные `mcp_best_practices.md` из
skill-каталогов (github: `Lupus/my-dot-claude`, `ComposioHQ/awesome-claude-skills`) + спека MCP
(пагинация `tools/list`/`nextCursor`).

## Вопрос

Как серверу самому ограничивать крупный tool-result: пагинация/курсор · summary+detail · фильтрация
полей · серверное усечение с явным маркером? Что ломается при **молчаливом** усечении? Учитывая, что
Claude Code уже предупреждает выше 10K токенов, режет по умолчанию на 25K (`MAX_MCP_OUTPUT_TOKENS`) и
выгружает превышение на диск, подставляя file-reference.

## Синтез ответа (сжато, с сохранением вердиктов)

**Порядок предпочтения:** курсорная пагинация для списочных данных → фильтрация полей для «широких»
объектов → split summary/detail для discovery-then-inspect → серверное усечение **только как последнее
средство** и только с явным само-описанием частичности.

- **Пагинация — протокольно-родная.** Спека MCP сама использует пагинацию с `nextCursor` в `tools/list`,
  что задаёт курсорное продолжение как канонический паттерн для крупных наборов; сохраняет порядок,
  позволяет модели дозапросить, снимает неоднозначность «пропавшего хвоста».
- **Фильтрация полей** сильнее усечения, когда объект широкий, а не длинный: модель получает **полные**
  записи по нужным полям вместо частичных записей с неизвестными пропусками.
- **Summary + detail:** `list_*`/`search_*` отдаёт компактные строки со стабильными id, `get_*` — полный
  объект по выбранному. Первый ответ мал, второй — намеренный, а не случайный.
- **Если всё же усекаете** — отдавайте явные метаданные: `truncated: true`, `returned_count`,
  `total_count`, плюс подсказку продолжения (`next_cursor`/`offset`/сужающий фильтр). Best-practice-гайды
  MCP прямо рекомендуют «clear truncation metadata and guidance for getting more results».

**Почему молчаливое усечение опасно (три отказа):**
1. **Галлюцинация полноты** — модель достраивает полный ответ из неполной выборки: домысливает
   недостающие элементы, считает, что записей больше нет, выводит неверные агрегаты («всего», «последний»).
2. **Потеря провенанса** — модель больше не различает «поля нет», «поле отфильтровано» и «кончился
   бюджет вывода»; три разных случая с разной реакцией схлопываются в один вводящий в заблуждение.
3. **Retry-путаница** — непонятно, просить ли следующую страницу, сузить ли фильтр или принять ответ
   за полный; агент либо останавливается рано, либо гоняет один и тот же запрос в разных формах.

**Конвенции сигнала частичности** (де-факто, не спека): булев `has_more`/`truncated` + токен
продолжения `next_cursor`/`next_offset` + `total_count`. Плюс короткая **человекочитаемая** строка в
текстовом слое («Output truncated after N tokens; use cursor=… to continue») — часть клиентов и моделей
читает текстовый слой надёжнее кастомных полей. Для `outputSchema` частичный результат обязан
оставаться валидным как **частичный**, а не маскироваться под полный (не переиспользовать пустой массив
/ отсутствующее поле в значении «усечено»).

**Про клиентский потолок — прямой вердикт синтеза:** «do **not** rely on the client's output cap as your
only safety mechanism. If the server returns a giant payload and the client writes overflow to disk with a
file reference, that is a **transport workaround, not a semantic guarantee** that the model understood the
whole result… the model may need a separate file-reading step, and the original call is no longer a clean
"answer". So the safest design is to use pagination or filtering first, and reserve overflow-to-file as an
emergency escape hatch rather than the primary delivery path.»

Правило-итог: «if the model must reason over the data, the server should make **completeness explicit**;
if the data is too large to reason over in one shot, the server should **partition** it into pages or
summaries, not silently compress it».

## Что это меняет в скоупе P3.2 (синтез, не цитата)

1. Дефолт «глухой потолок + `truncated: true`» — **не лучший** доступный дизайн; для списочных ответов
   (`maind_memory_recall`, `maind_graph_*`, `maind_projects_status`) первично **сужение/пагинация**,
   усечение — хвостовой случай.
2. Потолок целиться следует **ниже 10K токенов** (порог warning), а не под 25K.
3. Receipt обязан нести не только флаг, но и «сколько отдано / сколько всего / как дозапросить» — иначе
   он не снимает ни один из трёх отказов выше.

- Источники — **community best-practices** (skill-каталоги) и спека MCP в части пагинации; отдельного

  выгрузки; проверяется живым замером в P3.2, не принимается на веру.
