## Query

Без таблиц, только абзацы и списки. Октябрь 2026. Я строю локальный engine-agnostic оркестратор coding-агентов (Claude Code, Codex CLI, Grok Build) с портом/адаптерами на Python stdlib. Какой транспорт стандартизировать в порте адаптера: (a) Agent Client Protocol (ACP, agentclientprotocol.com: claude-agent-acp, codex-acp, нативный grok agent stdio), (b) отдельные JSONL-потоки каждого CLI (claude -p stream-json, codex exec --json, grok streaming-json), (c) tmux/TUI как AWS CAO, (d) Vercel AI SDK HarnessAgent? Оцени зрелость и версионирование ACP, наличие Python-клиента, сохраняется ли нативный подписочный логин и skills/plugins у Claude через claude-agent-acp (Agent SDK) против claude -p. Дай конкретную рекомендацию: что основной транспорт, что запасной, и как спроектировать порт, чтобы смена транспорта не ломала контракты. Первичные URL. Русский, до 600 слов.

## Answer (unchanged)

Для локального engine-agnostic оркестратора я бы стандартизировал ACP как основной транспорт, а нативные JSONL-протоколы CLI оставил бы запасными адаптерами. Но ACP здесь — не универсальный контракт на все возможности агентов: зафиксируйте версию протокола и адаптеров, а специфичные функции и ограничения явно отражайте в capabilities.

## Зрелость и покрытие

На октябрь 2026 ACP v1 — стабильная версия; v2 опубликован как draft. Развитие v1 идёт через согласование возможностей, а версия wire-протокола согласуется при initialize. Это уже больше, чем экспериментальный протокол, но v2 draft и появление новых стабилизируемых расширений означают, что полагаться на «ACP сам всё стандартизирует» пока нельзя.
Есть официальный Python SDK для ACP-клиентов и агентов. Он даёт типы схемы, asyncio-транспорт и управление жизненным циклом, так что отдельная реализация JSON-RPC поверх stdlib не обязательна. Если принципиально нужна только stdlib, реализуйте небольшой транспортный слой сами, но держите его за тем же внутренним портом.
Покрытие трёх движков неоднородно: Claude подключается через claude-agent-acp на базе официального Claude Agent SDK, Codex — через отдельный codex-acp; обе интеграции — внешние адаптеры, а не единый нативный интерфейс от вендоров. Список ACP-агентов подтверждает эти способы интеграции. Для Grok Build результаты подтверждают наличие адаптера в HarnessAgent Vercel, но не подтверждают нативный Grok ACP stdio — проверьте это отдельно, прежде чем считать пункт (a) готовым для всех движков.

## Claude: логин и функции

claude-agent-acp использует Agent SDK, а не просто оборачивает claude -p. SDK построен на той же основе, что Claude Code, и умеет читать пользовательские и проектные настройки; skills обнаруживаются из файловой системы, а при пропуске settingSources поведение соответствует стандартной загрузке CLI-настроек. Это позволяет сохранить локальный Claude Code workflow, включая skills и проектные инструкции.
При этом важно различать техническую совместимость учётных данных и обещанную гарантию. Документация SDK подтверждает загрузку Claude Code-настроек и claude.ai MCP-коннекторов при соответствующей авторизации, но изученные страницы не дают однозначной гарантии, что любой подписочный логин будет поддерживаться этим ACP-адаптером во всех конфигурациях. Проверьте на целевой версии SDK/адаптера запуск через уже авторизованный Claude Code и отдельно — загрузку skills, плагинов и MCP. Для локального личного инструмента это практический тест; для продукта, который предлагает чужим пользователям claude.ai-логин или его лимиты, не следует считать это допустимым без проверки актуальных условий Anthropic.

## Рекомендация и границы порта

Сделайте ACP основным там, где зрелый адаптер реально доступен; для Claude и Codex это разумная отправная точка. Для Grok подключите транспорт через отдельный адаптер после проверки доступного интерфейса. JSONL — запасной маршрут для случаев, где ACP-обёртка отсутствует, отстаёт от CLI или теряет нужные события. TUI/tmux оставьте только аварийной интеграцией: он привязан к терминальному представлению, а не к устойчивому событийно-командному контракту. HarnessAgent может быть полезным сравнительным ориентиром, но не подходит как транспортный стандарт локального Python-порта: он задаёт собственный уровень абстракции и не является stdlib-интерфейсом.
Чтобы смена транспорта не ломала контракт:
- Определите внутренние AgentPort и нейтральные события: TextDelta, ToolCall, PermissionRequest, FileChange, Usage, Completed, Failed.
- Разделите команды (start, send_input, approve, cancel, resume) и события; не протаскивайте ACP/JSONL-объекты в доменный слой.
- Добавьте capability discovery и явные unsupported/degraded состояния. Не симулируйте отсутствующие функции молча.
- Храните собственный session_id, а транспортный session/thread ID — только как привязку адаптера.
- Версионируйте отдельно контракт порта, версию ACP и версии адаптеров; фиксируйте их в lock-файле, тестируйте golden event traces и повторное подключение.
- Различайте завершение процесса, ошибку протокола и неуспешный результат агента. Для каждого транспорта проверяйте cancellation, backpressure, stderr и восстановление сессии.
