# Идея: кондуктор игнорирует `review.mode: none` пунктов и добавляет ревью сам; политика ревью плана не доходит до run

Статус: идея. Источник: оркестрация PLAN3 (vaulter) P5.3, 2026-10-17.

## Что произошло
- В плане у P5.3/P5.4 `review.mode: none`, ревью только на чекпоинтах (P5.6, P5.9, P5.11, codex gpt-6.1-sol).
- Кондуктор: стратег ревью (`review.strategy: auto`, model) выбрал `each` для обоих пунктов; плюс динамическое ревью
  (`review.dynamic`, риск-скор 65 ≥ 60) добавило ревью пункту, «у политики которого ревью нет».
- Итог P5.3: 3 круга grok-4.7/high (16+10+6 мин = 32 из 81 мин пункта); третий круг — одна находка, отклонена триажем.

## Почему
1. `review.mode` пункта не входит в слои run-options; стратег видит заголовок/цель/write-set/route, но не поле плана.
2. Динамическое ревью по умолчанию включено и перекрывает явное «none» плана; порог 60 достигается любым пунктом с
   diff_size+deviation+outside_write_set+executor_recommended.
3. `orchestration.options` в плане требует `bridges.roots` проекта; в проекте без него `planner set` даёт
   `EXTENSION_UNAVAILABLE`, т. е. политику ревью в план не положить, остаётся только `--options` на каждый запуск.
4. Нет способа сказать «ревью только на чекпоинте группы, другим ревьюером» из плана (ключ `reviewer` — только options).

## Предложение
- Мост planner-orch транслирует `review.mode` пункта в слой options: `none` → `review.dynamic=false` и исключение из
  стратегии (`strategy` учитывает пункты с `none` как «без ревью»); `requested` + `reviewer` → `reviewer` selector и
  группа ревью, заканчивающаяся этим пунктом (по `batches[].note`/`covers`).
- Стратег `auto` получает `review.mode` пункта и не может его повысить; динамическое ревью уважает `mode: none`
  (отключается только явным `review.dynamic: true` в слое выше).
- Лимиты `review_rounds`, число кругов без новых подтверждённых находок ≥Major: круг, где 0 подтверждено выше порога,
  заканчивает ревью (сейчас круг 3 был ради находки уровня ниже порога).
- `planner set … orchestration.options` без bridge roots: понятная подсказка «добавь bridges.roots» либо встроенный
  поиск моста рядом с launcher.

## Критерии приёмки
- План с `review.mode: none` на всех пунктах батча ⇒ ноль ревью в run без дополнительных флагов.
- Чекпоинт с `requested` ⇒ одно групповое ревью указанным ревьюером после последнего пункта группы.

## Дополнение: чего требовал владелец и чего не хватает (2026-10-17)

Требование владельца: «выстроить нормальную систему ревью, чтобы минимизировать» время на ревью. Смысл: ревью только
там, где concurrency / durability / destructive; остальные пункты — без ревью; чекпоинт покрывает несколько пунктов и
идёт сильным ревьюером один раз. План это выразил (`review.mode: none|requested`, `reviewer`, `batches[].note`,
`knowledge/orchestration#review-map-p5`), но **до исполнения доходит только то, что кондуктор получил как options**.

Чего не хватает, чтобы требование выполнялось без ручных флагов:
1. **Единый источник политики.** Сейчас три независимых источника: `review.mode` в пункте (план), `review.*`/`reviewer`
   (options), `[orch.conductor.risk]` (конфиг). Они не согласованы, побеждает самый «ревьюящий». Нужен порядок:
   явное `mode: none` в плане > стратег > динамический скор.
2. **Теги риска вместо карты в документе.** `risk: [concurrency|durability|destructive|security|public-api]` в пункте;
   политика проекта (stub/config) говорит «ревью только для этих тегов». Тогда карта чекпоинтов не дублируется в
   `knowledge/orchestration` и в `batches[].note`.
3. **Покрытие.** Чекпоинт объявляет `covers: [P5.1..P5.6]`; кондуктор ревьюит `git diff c6e69314..HEAD` по этому набору
   одним вызовом, а не только коммиты своей группы (`review_batch` читает коммиты группы текущего run).
4. **Цена ревью видна заранее.** `--dry-run` печатает, какие пункты ревьюятся, кем и сколько кругов максимум; сейчас
   об этом узнаёшь по логу (REVIEW_STRATEGY, REVIEW_ADDED).
5. **Круг без подтверждённых ≥Major заканчивает ревью;** сейчас P5.3: круги 16+10+6 мин, последний — одна находка,
   отклонённая триажем.
6. **Мост без `bridges.roots`:** `planner set … orchestration.options` падает `EXTENSION_UNAVAILABLE`; `launcher.py`
   должен регистрировать мост по умолчанию (как выставляет `PLANNER_ROOT`/`SKM_ORCH_ROOT`).

Измерение (PLAN3 P5.3): всего 81 мин; исполнитель 34 мин, ревью 32 мин (3 круга grok-4.7/high), правки 8 мин,
проверки 5 мин. Ревью — 40% времени пункта без запроса плана.

Обходной путь в сессии: `--options` на батч (`review.strategy`: `single` для чекпоинт-батчей с codex `gpt-6.1-sol`,
`none` + `dynamic:false` для остальных).

## Требование владельца к проектированию и валидации плана (2026-10-17)

**Стратегию ревью подбирает `plan-design`, а не исполнение.** При детализации фазы обязательный шаг: выбрать оптимальную
стратегию ревью и записать её настройки в JSON плана; кондуктор только исполняет записанное. Валидация плана
(`plan.py check`) обязана отклонять фазу, где стратегия не объявлена явно.

Что уже есть в схеме (`item.schema.json`):
- `review` обязателен у каждого пункта; `review.mode ∈ {none, self, requested}`; `review.reviewer{class,model,provider,effort,note}`.
- у фазы — `batches[]{id,items,mode,note}`.

Чего нет (поэтому стратегия не может быть выражена целиком и не доходит до run):
1. **Настроек стратегии в JSON.** Нет полей: `review.rounds_max`, `review.corrections_max`, `review.correct_min_severity`,
   `review.covers` (какие пункты/диапазон коммитов читает чекпоинт), `review.group` (в какой группе, после какого пункта),
   `review.dynamic: false`. Сейчас всё это только в run-options, а `orchestration.options` в плане недоступен без моста.
2. **Явного «ревью не нужно» с причиной.** `mode: none` не требует `reason`; нельзя отличить «осознанно без ревью»
   от «не продумали». Нужен `review.reason` (например `risk: none` / `covered-by: P5.6`) — обязателен при `none`/`self`.
3. **Проверки валидатора:**
   - у каждого пункта `review` задан явно (есть, но не проверяется смысл);
   - `mode: none` или `self` ⇒ есть `reason` или `covered_by` на пункт с `requested`, чей `covers` включает этот пункт;
   - `requested` ⇒ заданы `reviewer`, `rounds_max`, `covers`; пункт с тегом риска (concurrency/durability/destructive/
     security/public-api) не может быть «непокрытым» ни одним `requested`;
   - пункт с `requested`, не стоящий последним в своей группе `batches`, — ошибка (ревью читает группу целиком);
   - для каждого `batches[]` вычисляется и показывается стратегия ревью (`plan.py check --explain-review`).
4. **Кондуктор читает это поле** и строит `review.strategy`/`reviewer`/лимиты из плана; options — только переопределение.
5. **Шаг `plan-design`:** в чек-лист добавить «стратегия ревью по фазе: риски → чекпоинты → покрытие → ревьюер/effort/
   раунды → причина для остальных пунктов»; результат — в JSON, не в `knowledge/orchestration`.

Критерии приёмки (дополнение): фаза без явной стратегии ревью (нет `reason`/`covered_by` у не-ревьюируемых пунктов или
нет `covers`/`rounds_max` у чекпоинта) не проходит `plan.py check`; запуск `orch conduct run` на валидной фазе строит
ревью строго по плану без `--options`.

## Решение владельца по кругам ревью (2026-10-17, PLAN3 P5)
- Комбинированно: `review.max_rounds: 2` только для сложных батчей с большой правкой (P5.5–P5.6, P5.7+P5.8, P5.10+P5.11-checkpoint по риску),
  для остальных 1 круг; ревьюер чекпоинтов — `codex/gpt-6.1-sol/xhigh`.
- Нужно в кондукторе: `max_rounds` по размеру/риску батча, а не одно число на run; круг без подтверждённых ≥Major завершает ревью.
- Данные: P5.3 круги 16+10+6 мин, 8 из 9 находок подтверждены, круг 3 — отклонённая находка.
