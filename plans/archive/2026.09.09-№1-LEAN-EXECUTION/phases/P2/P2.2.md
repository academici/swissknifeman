### P2.2 — Producer readiness and priority-fix re-entry

**Intent:** Make producer readiness, approved no-op consumption and terminal-phase correction explicit so missing/stale output repairs locally, bounded cross-owner work uses a visible priority fix, and a closed phase reopens only on one proved trigger. RAG:— (repo-grounded: artifacts/source-roadmap/2026.08.15-empty-producer-ledger-must-continue-first.md:70-151; artifacts/source-roadmap/2026.08.16-terminal-phase-reentry-priority-fix-branch.md:66-129).
**Why:** The current downstream gate infers consumers from paths and command applicability but cannot distinguish a valid zero-write producer from missing/corrupt evidence; returns also misses pre-terminal re-entry proposals, so an empty verified producer can be misrouted back to an immutable phase. RAG:— (repo-grounded: findings/03-p2-design-baseline.md; packages/task/lib/task/plan_downstream.py:104-163; packages/task/lib/task/plan_returns.py:580-632).
**Scope Included:** Exact producer Deliverables directive and `producer-readiness/v1` schema with `nonempty-candidates|empty-by-decision`; terminal journal validation and consumer-bundle projection; roots/command/count/path-digest/source-commit/predicate/exclusions evidence; owner D# for empty mode; producer repair through P2.1; semantic downstream gate; `phase-reentry-justification/v1`; nested `fix-branch/v1` for an already declared target item; three re-open triggers; priority/resume dispatch; status/returns metrics; lint/delivery/command/provider parity and P5→P7 fixtures.
**Scope Excluded:** Treating every producer as nonempty; filesystem-driven admission or self-review; rewriting current locale-corpus content or the closed historical provider-locale plan; dynamic hidden item creation; reopening a terminal phase for stale view/proof run/approved no-op; bypassing owner, security, rollback or independent-review gates; phase audit evidence reuse (P3).

**Implementation Rules:** A producer declares exactly one backticked `producer-readiness/v1` directive in Deliverables naming its consumer and allowed closed modes; the terminal event carries the validated payload, and `plan_bundle` exposes only its digest-bound projection to that consumer. `nonempty-candidates` requires count >0; `empty-by-decision` requires count 0, exact exclusion evidence and an accepted D#. Missing/stale/corrupt readiness is `dependency-not-ready` through P2.1 before any block. Re-entry to a terminal phase is allowed only for `owner-decision-change`, irreparable `terminal-evidence-invalid` or `safety-or-authority-boundary`; all other modes continue current work or target an already declared priority-fix item. The nested fix record must bind origin, owner, scope, priority, rollback, validation and resume target, and status/returns must expose it. RAG:— (repo-grounded: artifacts/source-roadmap/2026.08.15-empty-producer-ledger-must-continue-first.md:126-151,215-246; artifacts/source-roadmap/2026.08.16-terminal-phase-reentry-priority-fix-branch.md:66-144; decisions/D7-one-repair-policy-chain.md).
**Code Guidance:** Use exact schema parsing, not keyword/prose heuristics. Start with the preserved P5→P7 approved-zero-event fixture: the named verifier decides `approved-no-op`; byte count or empty list never does. Test unsigned empty, corrupt, stale-derived and valid nonempty separately. Do not synthesize a priority item at runtime: validate an existing item spec and its `repairs=<origin>` relation, then let the P1 continuity controller choose current versus fresh root. Preserve terminal phase state until a valid re-entry trigger passes all four reopen steps. No special casing plan IDs, locale paths or old counts. Extend `returns --json` with proposal/outcome counters without changing return fingerprint identity.
