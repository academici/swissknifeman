# Roadmap: `batch` и `serial-batch` в execution roadmap Task

**Статус:** 🟡 спроектировано, код не написан. Критерий внедрения уже сработал на Agelto,
`2026.08.09-RELEASE-READINESS`: автор плана пометил все 75 items как `solo`, хотя запрос
владельца был направлен на сокращение простоев между безопасно совместимыми шагами.

**Дата design:** 2026-08-09.

**Следующий режим:** `$ task:dev` по этому файлу.

**Затрагиваемые пакеты:** `task`, `skiller` (`plan-protocol`).

## 1. Итог проектирования

Task получает четыре разных решения по группировке:

| Kind | ID | Смысл | Исполнение |
|:--|:--|:--|:--|
| `batch` | `B<n>` | Логически независимые items без внутригрупповой связи `Inputs ← Deliverables` | Одна команда и одна root-сессия, но items по-прежнему исполняются последовательно |
| `serial-batch` | `SB<n>` | Упорядоченная producer→consumer цепочка, где следующий item может потреблять результат предыдущего | Одна root-сессия, строгий порядок, полный lifecycle каждого item и fail-stop |
| `workflow` | `W<n>` | Настоящая orchestration/fan-out группа с workflow-скриптом и capability gate | По существующему workflow-контракту |
| `solo` | — | Один item с конкретной причиной, почему безопасная группировка невозможна | Отдельный запуск |

`batch` не означает параллельный runtime. Существующие `exec-items` и `run-items` уже умеют
последовательно провести несколько items через полный цикл; новый CLI и новая форма `Next` не
нужны. Параллельность остаётся ответственностью `workflow`.

Результат устраняет два дефекта одновременно:

1. blanket-решение «всё `solo`» перестаёт проходить без явного анализа кандидатов;
2. producer→consumer цепочки больше не ошибочно исключаются из непрерывного исполнения: для них
   появляется отдельный `serial-batch`.

## 2. Наблюдаемый дефект и противоречие канона

Task уже несёт `task:plan-design <ID> roadmap`, multi-item `task:plan-exec`, серии
`task:plan-run` и launch-block одной сессии. Но текущие носители расходятся:

- `packages/task/commands/plan-design.md` требует `batch/workflow/solo`, но не требует показать,
  какие кандидаты действительно проверены;
- `packages/skiller/skills/general/plan-protocol/SKILL.md` помещает membership в колонку
  `Batch` секции Routing;
- `packages/skiller/skills/general/plan-protocol/snippets/roadmap-template.md` называет Batch
  последовательными items со сцепленным scope;
- исходная граница этой roadmap-записи запрещала группу при `Inputs ← Deliverables`, то есть
  запрещала именно последовательные цепочки, ради которых нужно убрать простой;
- `packages/task/lib/task/plan_lint_checks/parsing.py::_lint_plan_roadmap_20()` принимает любой
  непустой `roadmap.md` и не проверяет наличие анализа группировки;
- `packages/task/commands/plan-exec.md` исполняет любой список items последовательно и не
  различает независимую группу и order-sensitive цепочку.

Автоматически выводить смысловую независимость из prose небезопасно. Структурный linter должен
проверять наличие решения и покрытие фаз, а качество dependency-анализа остаётся у
`plan-design` и `plan-audit`.

## 3. Решения

### D1 — закрытая таксономия

Закрытый enum: `batch | serial-batch | workflow | solo`.

- `batch` содержит минимум два соседних в execution order item'а одной фазы. Все участники
  готовы до старта группы и не потребляют Deliverables друг друга. Порядок перечисления
  технический, не семантический.
- `serial-batch` содержит минимум два соседних item'а одной фазы. Порядок нормативен; каждое
  внутреннее ребро producer→consumer явно видно в `Deliverables` предшественника и
  `Inputs`/`Required Reads` преемника.
- `workflow` сохраняет существующий отдельный критерий: orchestration carrier, готовый скрипт и
  capability gate. Независимость сама по себе ещё не делает группу workflow.
- `solo` содержит ровно один item. Причина должна быть item-specific: несовместимый route/Exec,
  owner gate, capability/time boundary, high-risk boundary, context budget либо отсутствие
  совместимого соседа. Общая фраза на весь план запрещена.

RAG:— (repo-grounded: `plan-exec.md` принимает несколько items и выполняет их последовательно;
`roadmap-template.md` уже различает обычную серию, workflow и solo).

### D2 — admission и review

Для `B<n>` и `SB<n>` обязательны:

- одна фаза и непрерывный участок execution order;
- совместимые model class, effort, `Exec` и capabilities;
- review каждого item сохраняется; эффективная глубина группы равна максимуму риска участников;
- owner/time/external-state/capability gate между items разрезает группу;
- gate до группы может блокировать группу целиком, gate после группы ей не мешает;
- каждый item сохраняет собственные validation, review, scope commit, bookkeeping commit,
  journal terminal event, handoff и status transition.

`Review=full` не разрешается подавить ради группировки. Если full-review item входит в допустимую
группу, full-review исполняется для него отдельно; экономия касается перезапуска и ожидания, не
качества результата.

RAG:— (repo-grounded: `plan-protocol/SKILL.md` Routing/review invariants и
`packages/task/commands/plan-exec.md` per-item lifecycle).

### D3 — fail-stop и JIT-readiness `serial-batch`

При старте `SB<n>` полностью ready должен быть первый item. У последующих items допустима ровно
одна нетерминальная зависимость: предыдущий участник той же цепочки; все остальные зависимости
терминальны.

После каждого item:

1. завершается его полный close;
2. для layout v2 регенерируются и проверяются затронутые state/status/decision views;
3. bundle следующего item строится и проверяется заново до его read cycle;
4. readiness, Routing и gate следующего item проверяются повторно;
5. только после этого серия продолжается.

`🔴`, `⛔`, красная validation/review, неразрешённый owner gate, невозможность собрать свежий
bundle или несовместимое материальное отклонение останавливают весь неисполненный suffix.
`🟠` разрешает продолжение только тогда, когда downstream-item явно принимает отклонение своим
контрактом; иначе серия останавливается на re-design.

Bundle/state schema и layout-v2 read path не меняются. `roadmap.md` не включается в item bundle:
это mutable dispatch carrier, а его digest создал бы freshness cascade при каждом закрытии или
regrouping. Структурный `execution-groups.json` откладывается до появления реального runtime
consumer.

RAG:— (repo-grounded: `plan-protocol/references/plan-layout-v2.md` carrier registry/projection
order и `packages/task/scripts/plan-views.py` bundle/state builders).

### D4 — единственный владелец membership

Для новых планов:

- `plan.md ## 3. Routing` владеет только отображением
  `Items → Model class/effort, Exec, Review, Почему`;
- `roadmap.md ## Карта исполнения` владеет финальными `Group` и `Kind`;
- `## Матрица решений по группировке` хранит evidence рассмотрения кандидатов, но не заменяет
  карту исполнения;
- launch-block'и являются производной от карты;
- workflow-скрипт реализует `W<n>`, но не переопределяет membership.

Новая каноническая Routing-таблица больше не эмитит колонку `Batch`. Историческая колонка
остаётся readable compatibility input и не получает ретроспективно значение
«независимая группа» или `serial-batch`. Диагностика `task_contract.py`, которая сейчас говорит,
что группа «belongs in the Batch column», должна направлять автора в `roadmap.md ## Карта
исполнения`.

Это forward-only исправление второго носителя одного факта. Массовая миграция старых планов не
проводится.

RAG:— (repo-grounded: `plan-protocol/SKILL.md` «One fact has one owner», текущая Routing-форма и
`plan-layout-v2.md` roadmap carrier ownership).

### D5 — обязательная матрица решений

Перед картой исполнения появляется точный раздел:

```markdown
## Матрица решений по группировке

| Фаза | Кандидаты | Решение | Проверенные Inputs/Deliverables | Route/Review | Гейты владельца | Причина |
|:--|:--|:--|:--|:--|:--|:--|
| P0 | P0.1–P0.2 | serial-batch:SB1 | P0.2 читает артефакт P0.1; обратной связи нет | implementation/medium · light | — | однонаправленная цепочка без промежуточного gate |
| P1 | P1.1, P1.2 | batch:B1 | зависимостей в обе стороны нет | implementation/medium · light | — | независимые совместимые срезы |
| P2 | P2.1 | solo | единственный item фазы | frontier/high · full | утверждение ADR | owner gate завершает отдельную сессию |
```

Правила матрицы:

- одна строка описывает одного рассмотренного кандидата;
- `Решение` имеет одну из форм `batch:B<n>`, `serial-batch:SB<n>`, `workflow:W<n>`, `solo`;
- каждая фаза представлена минимум одной строкой, включая single-item phase;
- рассматриваются как минимум соседние пары/тройки и очевидные кандидаты с общей
  route/scope-поверхностью; полный O(n²)-перебор не требуется;
- для `solo` колонка `Кандидаты` всё равно называет проверенный item/участок;
- матрица отражает текущий анализ и целиком пересобирается при refresh; прежние решения живут в
  git/Update Log, а не остаются в актуальном roadmap как конфликтующие строки;
- одинаковая причина, размноженная на весь план, является finding `plan-audit`, даже если
  структурный lint не умеет доказать шаблонность причины.

Новая карта исполнения:

```markdown
## Карта исполнения

| Item(s) | Group | Kind | Запуск | Model class/Effort | Review | Гейт владельца | Примечание |
|:--|:--|:--|:--|:--|:--|:--|:--|
| P0.1 P0.2 | SB1 | serial-batch | exec-items | implementation/medium | light | — | порядок нормативен |
| P1.1 P1.2 | B1 | batch | exec-items | implementation/medium | light | — | порядок технический |
| P2.1 | solo | solo | run-items | frontier/high | full | ADR | отдельный запуск |
| P3.1 P3.2 P3.3 | W1 | workflow | orchestration | implementation/medium | full | — | готовый workflow carrier |
```

Для `SB<n>` launch-block использует явный ordered item list. Диапазон остаётся compatibility
input, но новая форма не должна скрывать порядок. Команда определяется `Exec`: `exec-items` для
`plan-exec`, `run-items` для совместимого manual-route. Новый semantic `Next` не добавляется.

RAG:— (repo-grounded: существующий closed enum Next и multi-item формы в
`plan-protocol/SKILL.md`; полевая причина — раздел 2 этого файла).

### D6 — алгоритм `plan-design finish|roadmap`

До построения карты команда обязана:

1. убедиться, что skeleton-маркеров нет;
2. прочитать Status Board и specs всех items в пределах текущего layout;
3. для каждой фазы построить execution order;
4. проверить соседние пары/тройки по `Inputs`, `Deliverables`, `Required Reads`, `Files`, route,
   effort, `Exec`, Review, capabilities и owner gates;
5. классифицировать независимый совместимый участок как `batch`;
6. классифицировать доказанную однонаправленную dependency-цепочку как `serial-batch`;
7. применить существующий workflow-критерий к действительно orchestration-worthy группе;
8. оставить `solo` только с локальной причиной;
9. сначала записать матрицу, затем актуальную карту и launch-block'и;
10. сверить карту с Routing, workflow-скриптами и owner gates;
11. выполнить `plan-lint`.

`finish` выполняет этот алгоритм последним шагом после cross-phase reconcile. `roadmap` выполняет
его как лёгкую пересборку без изменения item specs. Если выяснилась ошибка самих контрактов фаз,
команда останавливается и требует новый `finish`, как и раньше.

`plan-audit design` проверяет смысловую сторону, которую linter не доказывает: реальные
dependency edges, покрытие items, конкретность `solo`, соответствие карты Routing, готовность
workflow и корректность launch-block'ов.

RAG:— (repo-grounded: `packages/task/commands/plan-design.md` modes `finish|roadmap` и
`packages/task/commands/plan-audit.md` roadmap audit checklist).

### D7 — минимальный forward-only `plan_lint`

Расширяется существующий `_lint_plan_roadmap_20`; отдельная семантическая dependency-модель не
добавляется.

Новые константы:

```python
ROADMAP_GROUPING_CANON_DATE = max("2026.08.10", <фактическая дата landing-коммита>)
ROADMAP_GROUPING_HEADER = "## Матрица решений по группировке"
ROADMAP_GROUPING_COLUMNS = (
    "Фаза",
    "Кандидаты",
    "Решение",
    "Проверенные Inputs/Deliverables",
    "Route/Review",
    "Гейты владельца",
    "Причина",
)
ROADMAP_GROUPING_KINDS = ("batch", "serial-batch", "workflow", "solo")
```

Активация:

- только полностью детализированный датовый план;
- Plan ID date `>= ROADMAP_GROUPING_CANON_DATE`;
- skeleton-план освобождён от гейта;
- pre-cutoff и legacy-планы не получают ни ERROR, ни новый WARNING;
- mtime, `Last Updated` и дата redesign не включают гейт;
- `plan-design roadmap` после landing эмитит новую форму и для старого плана добровольно, но
  отсутствие матрицы в старом плане не ломает lint.

Машина проверяет только:

- точный heading и точный порядок колонок;
- наличие хотя бы одной data-row;
- минимум одну строку для каждой фактической фазы;
- отсутствие неизвестных фаз;
- непустые `Кандидаты`, `Решение`, `Проверенные Inputs/Deliverables`, `Route/Review`, `Причина`;
- допустимую форму kind в `Решение`;
- `Гейты владельца` может быть `—`, остальные обязательные ячейки — нет.

Точные формы `Решение`: `batch:B[1-9][0-9]*`, `serial-batch:SB[1-9][0-9]*`,
`workflow:W[1-9][0-9]*` либо `solo`. Нулевые/пустые ID и свободная проза не принимаются.

Машина не проверяет независимость, полноту всех сочетаний, смысл Inputs/Deliverables,
совместимость route/review, достаточность причины `solo`, workflow threshold, membership карты
или launch-block. Это обязательный честный boundary нового гейта.

Отсутствующий `roadmap.md` даёт только существующую диагностику без каскадного сообщения о
матрице. Наборы отсутствующих/лишних фаз в сообщениях сортируются.

RAG:— (repo-grounded: текущий `_lint_plan_roadmap_20`, `PLAN_ID_DATED_RE` и forward-only gates в
`packages/task/lib/task/plan_lint_checks/`).

## 5. Диагностики `plan_lint`

Минимальный стабильный набор на русском:

- `roadmap: нет обязательной секции «## Матрица решений по группировке»`;
- `матрица решений по группировке: таблица не найдена`;
- `матрица решений по группировке: колонки [...] ≠ ожидаемых [...]`;
- `матрица решений по группировке не содержит строк`;
- `матрица решений по группировке: пустое поле «<имя>»`;
- `матрица решений по группировке: недопустимое решение «...»`;
- `матрица решений по группировке: фаза «P9» отсутствует в плане`;
- `матрица решений по группировке не покрывает фазы: P2, P3`.

Кривой roadmap не должен менять unrelated diagnostics Routing/Next/phase parsing. Если
`roadmap.md` отсутствует, matrix diagnostics не добавляются.

## 8. Acceptance criteria

- `batch` и `serial-batch` имеют одно и то же значение во всех canonical/command-carriers.
- Ни один новый текст не обещает parallel runtime для `batch`.
- `SB<n>` допускает только явную однонаправленную цепочку и останавливает suffix на неуспехе.
- Каждый item внутри B/SB сохраняет отдельные validation/review/commits/journal/handoff.
- Новая Routing-форма не владеет membership; legacy `Batch` читается, но не эмитится.
- `finish` и `roadmap` строят матрицу до карты и не могут завершиться blanket `solo`.
- Post-cutoff fully detailed plan без матрицы красный; pre-cutoff/legacy/skeleton не получают
  нового ERROR/WARNING.
- Правильная матрица с `batch`, `serial-batch`, `workflow`, `solo` проходит lint.
- Linter не заявляет, что проверил semantic independence или качество причины.
- Layout-v2 bundles/state/read-path не меняют schema; successor bundle проверяется JIT.
- Provider projections получены генераторами и проходят `--check`.
- Root CHANGELOG и package docs обновлены при реализации.

## 10. Отклонённые варианты

### A. Оставить один `Batch` для независимых и зависимых items

Отклонено: author и auditor не отличают технический порядок от обязательной dependency-цепочки;
ошибка predecessor не имеет явно заданной семантики suffix.

### B. Считать `batch` параллельным runtime

Отклонено: текущий executor последователен. Параллельность требует отдельного orchestration и
capability contract; обещать её только prose было бы ложью.

### C. Использовать `workflow` для любой независимой группы

Отклонено: workflow дороже и имеет собственный threshold/script/capability gate. Два обычных
независимых item'а не обязаны становиться multi-agent workflow.

### D. Учить linter выводить dependency из prose

Отклонено: parser не видит смысловые контракты, реальные owner gates и внешнее состояние; такой
гейт создаст ложную гарантию.

### E. Хранить membership одновременно в Routing и roadmap

Отклонено: два владельца одной группы неизбежно расходятся. Routing остаётся владельцем route,
roadmap — dispatch grouping.

### F. Добавить `serial-batch` в enum `Next` или новый CLI

Отклонено: существующие `exec-items`/`run-items` уже несут ordered item list. Kind принадлежит
roadmap, не транспортной команде.

### G. Добавить roadmap/grouping в layout-v2 bundles

Отклонено: regrouping после каждого close сделал бы все downstream bundles stale. До появления
machine runtime consumer достаточно JIT-проверки обычного successor bundle.

## 11. Границы

- Код, тесты, канон и generated-проекции в этом design-заходе не меняются.
- Runtime parallel Batch, cross-phase groups, partial-success continuation и новый workflow
  engine вне scope.
- Grouping не отменяет per-item commits, validation, review, owner gates или phase-first.
- Массовая миграция архивных/старых планов не выполняется.
- Внешних design-источников нет; `docs/reference.md` не обновляется.
