# Q6

Запрос (perplexity-web-mcp stdio, default pool; search; 2026-10-07):

```text
October 2026. Multi-agent coding pipelines with handoff briefs: a cheap "context packer" model reads all task materials (plan, research, decisions, code refs) and writes one compact self-contained brief; a strong executor model works only from that brief (no knowledge of plan structure); then a verifier runs checks, an optional reviewer of another provider reviews, the strong model fixes findings, and a cheap "registrar" model closes the task from the report. Answer precisely with primary sources (Anthropic engineering posts on multi-agent research system and context engineering, Cognition "Don't build multi-agents", OpenAI/Codex guidance, BMAD-loop, papers on lossy summarization/handoff in agent pipelines):
1) Known failure modes of lossy context compression/handoff between agents (dropped constraints, implicit decisions, conflicting assumptions) and recommended mitigations (deterministic verbatim mandatory fields + summarized optional material + pointers to originals, completeness checks, artifacts instead of chat).
2) When single-agent with full context beats orchestrated pipelines for coding; token cost multipliers reported.
3) Should acceptance/closing be judged by a cheap model or by executed checks; evidence of LLM-judge reliability for "task done vs deviation".
Answer in Russian, max 700 words.
```

Ответ (как вернул сервис):

По состоянию на 7 октября 2026: ваш последовательный pipeline разумен при одном writer и независимой проверке, но «исполнитель знает только сжатый brief» создаёт информационное узкое место. Приёмка должна опираться на проверяемые свидетельства; дешёвый registrar — оформлять результат, а не единолично решать, выполнена ли задача. Это архитектурный вывод из источников, не опубликованный benchmark именно вашей схемы.

## 1. Потери при compression/handoff и защита

Cognition, Don’t Build Multi-Agents (12.06.2025), выделяет две проблемы: неполный общий контекст и неявные решения, содержащиеся в действиях. Даже передача исходного задания недостаточна: последующие обсуждения, tool calls и изменения кода уточняют смысл требований. Компрессор допустим, но его качество требует отдельной инженерной работы; Cognition экспериментировала с дообучением небольшой модели.
Есть прямое экспериментальное подтверждение избирательной потери ограничений. Facts Without Rules: Boundary Metadata Collapse… (arXiv v1, 29.08.2026) показывает: при бюджете 25 слов операционные факты сохраняются почти полностью, тогда как ограничения использования информации исчезают или ослабляются. Для GPT-5-mini сохранность фактов — 0,997, маркеров границ — 0,690; для DeepSeek-R1-32B — 0,972 и 0,580. Это исследование privacy-handoff, не coding benchmark: перенос на архитектурные запреты — обоснованная гипотеза, не измеренный результат.
Практический контракт handoff — моя инженерная конкретизация рекомендаций источников:
- Кодом копировать дословно канонические обязательные поля: acceptance criteria с ID, запреты/non-goals, интерфейсные контракты, утверждённые решения, нерешённые вопросы. Не поручать packer решать, какие из них «важны».
- Моделью сжимать необязательное: исследование, объяснения, отвергнутые варианты; отделять факт от предположения.
- Добавлять ссылки на оригиналы, пути/символы и фиксированный commit. Исполнителю не обязательно понимать структуру плана, но необходим доступ к первоисточникам при неоднозначности.
- Проверять schema, наличие всех обязательных ID, точное совпадение защищённых полей; отдельно проверять смысловую полноту на размеченных задачах. Правильный JSON сам по себе не означает правильное содержание.
Anthropic, Effective context engineering (29.09.2025), рекомендует сначала максимизировать recall компрессии, затем сокращать лишнее. В multi-agent research post компания прямо советует сохранять результаты как артефакты и передавать ссылки вместо многократного пересказа через координатора: это уменьшает «испорченный телефон» и token overhead.

## 2. Когда single-agent предпочтительнее; стоимость

Single-agent с непрерывным релевантным контекстом предпочтительнее для тесно связанных изменений: общая архитектура, последовательные решения, много зависимостей и мало независимых подзадач. Anthropic прямо отмечает, что большинство coding-задач хуже распараллеливаются, чем research; OpenAI рекомендует оставлять короткие задачи и зависимые шаги у основного агента. Это рекомендации, не доказательство универсального превосходства.
«Полный контекст» не значит бесконечный transcript: Anthropic рекомендует минимальный достаточный высокосигнальный контекст. Обновление Cognition от 22.04.2026 уже поддерживает схемы «один writer + clean-context reviewer», подчёркивая необходимость сверять findings с исходными намерениями и scope. Поэтому позиция 2025 года — не актуальный абсолютный запрет multi-agent.
Опубликованные Anthropic множители: агент ≈4× токенов обычного чата, multi-agent ≈15× чата. Отношение этих ориентиров — ≈3,75×, но это не парное сравнение coding-pipeline с single-agent. Прирост 90,2% относится к внутренней research-оценке, не разработке ПО. Для вашей схемы подтверждённого множителя нет.

## 3. Кто вправе закрывать задачу

Разделите два вопроса:
- «Проверки прошли?» — исполняемые команды, exit codes, результаты acceptance-тестов, проверка артефактов.
- «Реализовано требуемое без отклонений?» — сопоставление исходных criteria с diff и свидетельствами; review, а при неоднозначности — человек.
BMAD-loop демонстрирует именно детерминированный control loop: completion checks, проверки артефактов, test/lint-команды, bounded retries; result.json агента не принимается на веру. Проект experimental beta, не доказательство надёжности.
SWE-Judge показывает улучшение корреляции с человеческими оценками на software-artifact benchmarks на 5,9–183,8%, но это ансамбль специализированных judges, не доказательство надёжности дешёвого бинарного registrar для «done/deviation». OpenAI также показывает преимущества reviewer с доступом к репозиторию и исполнению и предупреждает: чистое review не гарантирует безопасность.
Следовательно, registrar может подготовить запись закрытия; переход в done разрешает кодовый gate по проверенным evidence. Непроверяемые требования нельзя считать выполненными лишь потому, что тесты зелёные или отчёт убедителен.
