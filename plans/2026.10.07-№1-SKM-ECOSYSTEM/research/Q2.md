# Q2

Запрос (perplexity-web-mcp stdio, default pool; search; 2026-10-07):

```text
October 2026. Architecture question: separating a "planner" (produces a declarative plan: phases, tasks, linked files, roles, acceptance checks) from an "orchestrator" (executes declarative instructions through pluggable engines behind one port/interface, e.g. own Python runner vs AWS Labs cli-agent-orchestrator (CAO) driving Claude Code/Codex/Grok CLIs). Give prior art and lessons with primary-source URLs:
1) Declarative workflow spec + multiple interchangeable engines: CWL/WDL (Cromwell, Toil), Argo/Tekton, Kubernetes CRI, Open Agent Specification (Oracle Agent Spec) with multiple runtimes, Serverless Workflow spec, A2A and Agent Client Protocol (ACP). What went well, what went wrong (lowest common denominator, capability negotiation, leaky abstractions)?
2) Who should own the plan/workflow schema: the producer (planner), the executor (orchestrator), or a separate neutral contract package? How do these ecosystems version the contract?
3) Is an "engine-neutral orchestrator" worth it when only 1-2 engines exist (YAGNI vs ports-and-adapters)? Concrete criteria.
Answer in Russian, max 800 words.
```

Ответ (как вернул сервис):

"Экосистема","Что получилось","Ограничение и урок"
"CWL, WDL, Cromwell/Toil","Настоящее разделение языка и исполнителей. CWL различает обязательные requirements и необязательные hints: неизвестное requirement должно останавливать запуск. commonwl","Парсинг не равен совместимости: Toil прямо признаёт неполное соответствие WDL. У Cromwell поддержка runtime attributes различается между backends. Нужны conformance tests и проверка возможностей до исполнения. toil+1"
"Argo, Tekton","Декларативные Kubernetes-ресурсы, разделение описания и состояния выполнения; Argo поддерживает executor plugins. argo-workflows+1","Это не общий язык с взаимозаменяемыми Argo/Tekton engines: у проектов собственные API. Плагин выполнения шага не делает весь workflow переносимым. Их сильная сторона — богатая семантика конкретного контроллера, а не нейтральность. argo-workflows+1"
"Kubernetes CRI","Узкая граница kubelet/runtime позволяет заменять container runtime без перекомпиляции kubelet. github","CRI — исполнительный протокол, не workflow DSL. Совместимость строго ограничена: с Kubernetes 1.26 необходим CRI v1; новые возможности должны корректно деградировать согласно skew policy. kubernetes+1"
"Oracle Agent Spec","Непосредственный аналог: декларативные Agents/Flows, WayFlow reference runtime, адаптеры LangGraph, AutoGen, CrewAI. github","Наличие адаптера ещё не доказывает эквивалентность поведения. Подход «superset of capabilities» сохраняет выразительность, но увеличивает обязательства runtime; нужны проверки конкретных компонентов, а не обещание «поддерживаем Agent Spec». arxiv"
"Serverless Workflow","Отдельная спецификация и несколько runtimes; официальная документация сейчас представлена как Open Workflow Specification. github","Версия 1.0 существенно переработала DSL. Общий синтаксис не устраняет миграции и различия исполнения; обязательный базовый язык выражений плюс optional extensions лучше неявных backend-specific конструкций. github+1"
"A2A, Agent Client Protocol","A2A стандартизует взаимодействие агентов; ACP — взаимодействие клиента и агента. AgentCard/initialize объявляют возможности. a2a-protocol+1","Это не схемы вашего плана и не гарантия одинакового reasoning. Используйте их как транспорт/адаптер. Здесь ACP именно Agent Client Protocol, не Agent Communication Protocol."
