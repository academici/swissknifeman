## 1. Method, and the trap it is designed to avoid

The audit's own weakness is named in `findings/01-perplexity-audit-assessment.md`: most of its
`core/provider_*`, CLI and target-architecture material is written **from file names and sizes**
with probabilistic language ("вероятно", "почти наверняка"), and it "не строит dependency graph,
не читает большинство публичных функций и не проверяет существующие tests/contracts".

So the method here is the inverse of the audit's: for every claim, name the function, the caller
and the test that decides it — or say the tree cannot decide it, and name the missing evidence.
Three rules were applied literally:

1. **Reject ≠ "the author saw nothing".** Every `reject` carries `observation_upheld` naming the
   true part of the observation. Rejection is of the *proposed change*, not of the author's eyes.
2. **`unknown` is a real answer.** Two claims are undecidable on the committed tree. Neither was
   rounded into agreement or dismissal (`Code Guidance` — анти-подгонка).
3. **No verdict is argued from acceptance state** (D89). This is enforced mechanically: the
   verifier fails any hypothesis whose `observable_relevance` argues from acceptance completion.
   The two axes were never coupled — the hypotheses are about whether the code is what the audit
   says it is.

Ranking of accepted claims follows `Code Guidance`: **observed user outcome and Rule of Three**,
not elegance. That ranking is what removed most of the audit's backlog — see § 3.

## 3. The three accepted claims, and why exactly three

Nothing was accepted because it sounded structurally attractive. Each accepted row is either a
Rule-of-Three hit on the committed tree or a defect class the plan has already measured:

- **H12 → FP-3 (ownership predicate triplicated).** `managed target AND NOT user_owned` is
  implemented independently in `harness/agentpacks.py` (owner/writer), in
  `run-report/_lib.py::_protected_sets` (reporting) and in `pack-guard.py::_managed_files`
  (blocking). The blocking copy names the duplication in its own docstring as deliberate. All
  three are tested; **none is tested against the others**. The repo's own precedent for a
  deliberate hook-local copy (`_usage.py`) carries a `cmp` gate in `validate.sh` — this one does
  not. Failure mode is operator-visible: two hooks disagreeing about whether a file is protected.
- **H10 → FP-2 (run-report degrades silently).** Decided on the returned payload, not on style:
  `parse_events` returns fourteen keys and not one of them says how much was dropped. Malformed
  lines and unknown events vanish through bare `continue`; the only degradation signal in the
  whole payload is `usage = None`. `core/pathology.py` then under-fires without saying so. This
  is the same seam as the plan's own remaining red axis (a producer not declaring what it failed
  to produce), and the honest vocabulary already exists in `analyst.trace.build_trace_record`
  (`quality.completeness` / `missing` / `degraded`).
- **H08 → FP-1 (resolution is computed but never explained).** `resolve_provider_config` fills a
  `ConfigProvenance` for every effective leaf — which layer won, by which RFC6901 pointer,
  explicitly or by default — and no code path renders it to a human. The data is frozen; only the
  rendering is missing.

Everything else the audit proposed was either already implemented, already tested, or premised on
a lifecycle this code does not have (§ 4).

## 4. The load-bearing rejections, stated precisely

- **The provider lifecycle the audit reasons about does not exist here.** It assumes
  config → manifest → lock → artifact with manifest as a computed intent document. In this code
  `provider_manifest.py` is the **root-owned capability manifest** — an *input* projected into the
  config catalog by `provider_config_catalog` — and the lock is a sidecar of rendered-artifact
  provenance. Direction is manifest → config → render → lock. Every downstream claim built on the
  assumed pipeline (H03, H04, H05) inherits the error.
- **The "no explicit invariants" claim is refuted by 77 green tests.** Six of the seven "mandatory
  contract tests" the audit specifies map one-to-one onto existing tests; the seventh (identity
  rename/migration back-compat) has **no subject** — `ProviderId` is a closed two-member enum with
  no alias or migration path anywhere in `core/`.
- **The recommended agent-surface architecture is the implemented one.** Root projections are
  generated with `canonical` + `canonical_sha256` + `generator` in their frontmatter, are
  byte-identical across `.claude/` and `.agents/`, are re-checkable read-only
  (`registry --check`), and were measured cold by P1.4 at 216/204 identities with **0**
  catalog-wide collisions.
- **The predicted vendor drift is gated, not merely disciplined.** `validate.sh` [2/7] byte-compares
  `core/usage.py` against the hook copy and fails the build with the exact remediation command.
- **`core/cli.py` is not a coordination layer.** 111 lines: `parse_flags`, `parse_args`,
  `run_cmd`. Command dispatch lives per package. The "cli.py inside the domain core" reading is a
  file-name inference.
- **No measured incident points at core/provider structure.** The five frozen incident cases
  (`artifacts/source-evidence/precomputed/corpus.json`) are agent-run reliability defects: cold
  start, missing launch block, wrong scope return, audit loop, clean control. That is the ranking
  input the audit itself lacked, and it is why a 4299-line `core/` rewrite is not adopted.
