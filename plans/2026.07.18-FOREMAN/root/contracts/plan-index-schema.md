# Контракт корневого индекса плана (`plans/<ID>/index.md`)

**Назначение.** Быстрый вход в план — **карта ФАЙЛОВ и провенанс-связей**: «где что
искать, что с чем связано» (brief §1 п.17). Отвечает на два вопроса без чтения содержимого
файлов: (1) что лежит в каждой директории/файле плана (директорная карта); (2) какой
`findings/`/`research/` питает какую фазу (провенанс). Потребители — человек (доработка/аудит
плана) и супервизор Artifex (навигация по дереву плана при обходе).

**НЕ носитель статуса/контента** (D23). Индекс — карта, а не состояние: он **не** несёт
статус item/фаз (это Status Board — `plan.md §4` + `phases/Pn.md` Phase Status) и **не** несёт
«куда дальше» (это `handoff.md`). Внести туда статус или next — завести второй носитель одного
факта → гарантированный дрейф (§3 plan-protocol, отвергнутые варианты — plan.md §Обсуждение
«Корневой индекс плана»).

**Рекомендация генерации.** Индекс дорог не написанием, а поддержкой: чем больше в нём
изменчивого, тем быстрее протухнет. Рекомендуемая форма — **авто-генерируемый из дерева
файлов + frontmatter** (детерминированный генератор устраняет дрейф); MVP допускает ручной
`index.md` по шаблону (`snippets/index-template.md`, P1.4) с явным правилом обновления при
добавлении `findings/`/`research/`. Реализация генератора — follow-up/опционально (Scope
Excluded P1.2), НЕ этот контракт (он — схема).

---

## 1. Имя и место файла

- **Имя — `index.md`** (не `README.md`). `README.md` зарезервирован конвенцией черновиков в
  КОРНЕ `plans/` (§2 plan-protocol); внутри `plans/<ID>/` конфликта нет, но `index.md`
  однозначнее по назначению «карта директории».
- **Место — корень каталога плана**: `plans/<ID>/index.md`, рядом с `plan.md`/`handoff.md`.
- **Опциональность.** Индекс — навигационное удобство, не обязательный носитель факта: план
  без него валиден (вся истина — в `plan.md`/`phases/`/`handoff.md`). Канон/lint (P1.4)
  вводят его как рекомендацию (WARNING-уровень для датовых планов), НЕ жёсткий ERROR-гейт —
  в отличие от `brief/` (обязателен) и журнала.

## 2. Структура `index.md`

Три секции, строго в этом порядке. Формат — таблицы Markdown.

### 2.1 Секция «Карта директорий» (статична)

Назначение каждой директории/файла дерева плана в **1 строку**. Совпадает по СОСТАВУ с
Раскладкой 2.0 (§2 plan-protocol), но **конкретизирована файлами ЭТОГО плана** (какие фазы
реально заведены, какие контракты лежат в `root/`, какие workflow-скрипты созданы) — см. §3
границу. Карта СТАТИЧНА (меняется только при добавлении/удалении файлов), статус НЕ несёт.

| Столбец | Смысл |
|:--|:--|
| Путь | директория или файл (`phases/`, `handoff.md`, `root/contracts/plan-journal-schema.md`) |
| Назначение | 1 строка: что это и зачем (роль в плане) |

Покрываемые узлы (по факту наличия в плане): `plan.md`, `phases/Pn.md`, `handoff.md`,
`roadmap.md`, `journal.jsonl`, `brief/`, `findings/`, `research/`, `artifacts/`, `workflows/`,
`root/` (с перечнем контрактов), `open-questions.md`. Отсутствующие в плане узлы —
опускаются (карта отражает РЕАЛЬНОЕ дерево, не полную Раскладку).

### 2.2 Секция «Провенанс» (единственная содержательная)

Связь «какой `findings/`/`research/` питает какую фазу-потребителя» — материализует цепочку
слоёв знаний (§16 plan-protocol: `brief → findings → research → решения`). Это ЕДИНСТВЕННАЯ
секция, несущая связи, а не просто список файлов.

| Столбец | Смысл |
|:--|:--|
| Источник | файл слоя 1/2 (`findings/<slug>.md`, `research/NN-<slug>.md`) |
| Слой | `findings` (сырьё) \| `research` (синтез) |
| Питает | фаза/item-потребитель (`P1`, `P5.1`) — куда лёг факт/синтез |
| Суть | 1 строка: что даёт (RAG-выжимка / design-документ / recon) |

Провенанс-секция допускает ручное ведение (обновляется при добавлении источника), но НЕ
дублирует `Inputs`/`Required Reads` items как копию — см. §3 If-then (если полностью выводима
из них — секция сужается).

### 2.3 Секция «Ключевые артефакты `root/`» (опциональна)

Долгоживущий материал `root/` (контракты, philosophy, glossary — судьба docs проекта, §3
plan-protocol): имя + 1 строка + статус запечатывания контракта (`sealed`/`draft`) со ссылкой
на item-владельца. Статус ЗДЕСЬ — про контракт-артефакт (sealed/draft — свойство самого файла,
frontmatter контракта), НЕ про item плана: это не второй носитель статуса item (§3 граница
соблюдена — карта показывает зрелость артефакта, Status Board показывает прогресс исполнения).

## 3. Граница анти-второй-носитель (§3 plan-protocol) + граница с Раскладкой 2.0

**Анти-второй-носитель (жёстко).** `index.md` НЕ повторяет:

- **Status Board** (`plan.md §4 Phase Index & Status Board` + `phases/Pn.md Phase Status`) —
  единственный носитель статуса фаз/items. Индекс статус item/фаз НЕ несёт.
- **`handoff.md`** — единственный носитель «куда дальше» (перезаписываемый снапшот). Индекс
  «next» НЕ несёт.
- **`journal.jsonl`** (P1.1) — append-only история запусков. Индекс историю НЕ несёт (только
  указывает, что файл существует и его роль — в директорной карте §2.1).

Соблазн внести статус/next/историю → стоп: это источник дрейфа (два носителя одного факта).

**Граница с Раскладкой 2.0** (`skill core:plan-protocol §2`) — явна:

| | Раскладка 2.0 (§2 канона) | Директорная карта `index.md` (§2.1) |
|:--|:--|:--|
| Про что | ВСЕ планы экосистемы (шаблон дерева) | ЭТОТ план (реальное дерево) |
| Дом | скилл `plan-protocol` (канон) | `plans/<ID>/index.md` |
| Изменчивость | меняется с каноном плановой системы | меняется с файлами конкретного плана |

Директорная карта КОНКРЕТИЗИРУЕТ Раскладку файлами плана (какие фазы/контракты/workflow реально
заведены), не КОПИРУЕТ её как второй носитель канона.

**If-then (анти-дубль провенанса).** Если при внедрении окажется, что провенанс-секция (§2.2)
уже ПОЛНОСТЬЮ выводится из `Inputs`/`Required Reads` items (дубль без добавленной ценности) —
сузить индекс до директорной карты (§2.1) + эскалировать вопрос ценности провенанс-секции
владельцу (P1.4 канон), НЕ плодить дубль. Провенанс оправдан лишь пока даёт СВЯЗИ, не
восстановимые тривиально из items (напр. общеплановые `findings/<тема>-<дата>.md`, питающие
несколько фаз).

## 4. Генерация и поддержка (анти-дрейф)

- **Рекомендуемо — детерминированный генератор** из дерева файлов + frontmatter (`type`,
  `plan`, потребитель): обходит `plans/<ID>/`, читает frontmatter `findings/`/`research/`,
  собирает карту+провенанс. Генератор НЕ модель-пишет-от-руки (иначе дрейф). Реализация —
  follow-up (Scope Excluded P1.2); MVP — ручной по шаблону.
- **Ручной вариант (MVP)** — шаблон `snippets/index-template.md` (P1.4) с явным правилом:
  «обновлять при добавлении `findings/`/`research/` или запечатывании контракта `root/`».
- **Держать минимальным.** В индексе только МАЛОизменчивое (карта дерева + провенанс-связи);
  всё, что меняется каждый item (статус, next, метрики), — НЕ здесь (§3). Протухший индекс
  хуже отсутствующего: вводит в заблуждение навигацию человека и супервизора.
