## 1. Читаемые поля — грепаемые якоря

### 1.1 Заголовок `handoff.md` (SKILL §8, D30)

Драйвер определяет адресата прогона (последний закрытый item / фаза) по ПЕРВОЙ строке
`handoff.md`. Две легальные формы (иная = `plan-lint` ERROR):

| Форма | Смысл |
|:--|:--|
| `# HANDOFF — <ISO-дата> — after Pn.m` | закрыт **item** Pn.m (адресат = item) |
| `# HANDOFF — <ISO-дата> — after Pn` | закрыта/проаудирована/ре-дизайнена **фаза** Pn (шаг без item-адресата) |

**Regex (якорь парсера):**
```
^# HANDOFF — \d{4}-\d{2}-\d{2} — after P\d+(\.\d+)?$
```
- группа `\d{4}-\d{2}-\d{2}` — ISO-дата; `P\d+` — фаза; опц. `\.\d+` — item.
- Bootstrap-исключение: `after P0.0` стартового handoff (фазы `P0` нет) — регексом проходит,
  семантически «план ещё не начат».
- Тире — U+2014 (`—`), НЕ дефис. Парсер сверяет литерал.

### 1.2 Поле `**Next:**` и определение формы (SKILL §8, D40)

Поле `**Next:**` многострочно (тянется до следующего `**Field:**`, включает launch-block).
**Форма Next объявляется ПЕРВОЙ непустой строкой поля** (D40) — парсер читает форму со строки
`**Next:** …`, ниже неё за формой не смотрит (иначе цитата команды в ячейке «Суть» ложно
перехватит резолвер). Fallback (back-compat) — grep по всему полю только при провале первой строки.

**11 разрешённых форм Next (закрытый enum — иная = `plan-lint` ERROR):**

| # | Форма (якорь на первой строке `**Next:**`) | Когда |
|:--|:--|:--|
| 1 | `/task:plan-exec <ID> Pn.m [Pn.k …]` | item(ы) детализированы, Exec=plan-exec; список = батч-серия |
| 2 | `/task:plan-run <ID> Pn.m[-Pn.k]` | manual-item(ы) под моделью текущей сессии |
| 3 | `/task:plan-audit <ID> design` | план детализирован — pre-exec ревью |
| 4 | `/task:plan-design <ID> Pn` | следующая фаза — скелет |
| 5 | `/task:plan-design <ID> Pn.m` | item эскалирован (🔴) / ре-дизайн |
| 6 | `/task:plan-audit <ID> Pn` | фаза Pn терминальна — аудит |
| 7 | `/task:plan-close <ID> Pn[.m]` | items терминальны: закрыть фазу / сверить item |
| 8 | `/task:plan-close archive <ID>` | план терминален целиком |
| 9 | `«план закрыт»` | всё терминально, шаг вне протокола |
| 10 | `«ЗАПУСК ВРУЧНУЮ: <model/effort>»` | Exec=manual: команды нет, launch-block несёт голый промпт |
| 11 | `«ОЖИДАНИЕ: <условие> → <целевая форма>»` | шаг реален, но неисполним сейчас (time-gate/гейт) |

Драйвер обязан распознать ВСЕ 11 (иначе не отличит DRIVE от паузы). Решение по каждой форме —
§3 (маппинг событие→решение, D27).

### 1.3 Status Board `plan.md` (SKILL §4, D51)

Единственный носитель статуса ФАЗЫ. Якорь — заголовок секции + шапка таблицы:
```
## 4. Phase Index & Status Board
| Phase | Title | Items 🟢/всего | Status |
```
- Колонка `Items 🟢/всего` — счётчик закрытых (напр. `2/6`); драйвер читает прогресс фазы отсюда.
- Колонка `Status` — один из 6 канонических статусов (§1.4).
- Статус ITEM'а живёт в `phases/Pn.md` (строка `**Status:**` под `### Pn.m —`) и в таблице
  `## Phase Status` того же файла (`| ID | Title | Status | Updated |`). Статус фазы там —
  `plan-lint` ERROR (второй носитель).

### 1.4 Шесть канонических статусов (SKILL §6) — байт-в-байт

```
⬜ Not started
🟡 In progress
🟢 Done
🟠 Done with deviations
🔴 Blocked
⛔ Skipped by decision
```
Парсер сверяет ЛИТЕРАЛ (эмодзи + пробел + латинский текст). Любой статус вне этих шести —
breaking (§Пин и breaking). Терминальные для драйвера: `🟢`, `🟠`, `⛔` (item сделан/пропущен);
`🔴` — эскалация; `⬜`/`🟡` — не готов.

### 1.5 Сигналы эскалации воркера (SKILL plan-exec §5/§8)

Драйвер считает прогон требующим внимания владельца при ЛЮБОМ из грепаемых сигналов:

| Сигнал (якорь) | Источник |
|:--|:--|
| `ESCALATION-REQUIRED: Pn.m — <причина>` | финальная строка отчёта воркера |
| `**Status:** 🔴 Blocked` | item в `phases/Pn.md` + строка Phase Status |
| `**Escalation Needed:** yes` | поле item'а (`no`/`—` = нет эскалации) |
| `**Вердикт: RED**` / `**Вердикт: ATTENTION**` | блок `## Audit Pn` отчёта plan-audit (латинский литерал) |
| `ATTENTION` в теле отчёта прогона | run-report / текст воркера |

`**Вердикт: GREEN**` — находок нет, не эскалация.

## 2. JSON-контракт `--output-format json` (транспортный слой)

RAG:✅ 2026-07-18 (factsheet §5 + perplexity-supervisor-patterns §Консенсус). Драйвер запускает
воркер как `claude -p "/task:plan-exec <ID> Pn.m" --output-format json` и судит об ИСХОДЕ ПРОГОНА
(не о состоянии плана) по JSON-конверту + exit code.

**Поля конверта (читаемые драйвером):**

| Поле | Тип | Назначение |
|:--|:--|:--|
| `type` | str | должно быть `"result"` — иначе конверт не финальный/битый |
| `is_error` | bool | флаг ошибки прогона (транспорт/лимит/сбой) |
| `result` | str | финальный текст воркера (в т.ч. блок отчёта item'а) |
| `session_id` | str | id сессии (линковка с журналом P1.1/run-folder P0.6) |
| `total_cost_usd` | number | стоимость прогона (cost-aware сигнал P5, репорт mAInd P4.4) |
| `num_turns` | int | число ходов (лимит `--max-turns`, D7 — флаг работает) |
| `duration_ms` | number | длительность (диагностика) |

**Дефенсивный парсинг (ОБЯЗАТЕЛЬНОЕ правило, perplexity-supervisor-patterns §Pitfalls):**
1. Судить об успехе по `type=="result"` + `is_error==false` + **exit code**, а НЕ по stdout.
2. `-p` — не стабильный RPC: битый/отсутствующий JSON — не падать, обрабатывать как транспортную
   ошибку (§3, tier1 retry).
3. Логировать `claude --version` перед прогоном; отказ от неизвестных/старых версий (пин бинаря).
4. `--bare` НЕ применять к воркеру (отключает хуки/скиллы/CLAUDE.md — весь смысл Artifex в
   тулинге владельца); только для служебных вызовов драйвера, если появятся.

**Quota-детект (D18, RAG:✅ 2026-07-18 headless-uncertainties-resolved §9):** исчерпание лимита
учётки проявляется как `is_error==true` + exit 1; тип различается по ТЕКСТУ `result`
(`session limit` ≈ 5-часовое окно → ждать; `weekly limit` → URGENT-эскалация); **reset-timestamp
в JSON НЕТ**; CLI подхватывает новую учётку на СЛЕДУЮЩЕМ запуске после браузер-релогина. Quota —
ТРЕТИЙ класс сбоя (§3), НЕ обычный tier1 retry.

## 3. Маппинг «событие протокола → решение драйвера» (D27)

Скоуп авто-драйва MVP консервативен: драйвер авто-ведёт ТОЛЬКО DRIVE-форму (`plan-exec`) и
механический self-contained `plan-close`; всё спорное → пауза+эскалация (D27, «сомнение→эскалация»
D10).

| Событие (детект) | Решение драйвера |
|:--|:--|
| item `🟢`/`🟠`/`⛔` терминален + Next=`/task:plan-exec` | **DRIVE**: следующий item свежей сессией |
| item терминален + Next=`/task:plan-close` | авто-close (механический, self-contained) |
| item терминален + Next=`/task:plan-run`/`plan-audit`/`plan-design`/`ЗАПУСК ВРУЧНУЮ` | **пауза+эскалация** владельцу (нужна модель/решение вне пина) |
| Next=`«ОЖИДАНИЕ: <условие> → …»` | таймер до структурного условия, затем целевая форма |
| Next=`«план закрыт»` | **done** (прогон завершён успешно) |
| `🔴 Blocked` / `ESCALATION-REQUIRED:` / `Escalation Needed: yes` | **эскалация** + пауза очереди |
| `**Вердикт: RED/ATTENTION**` | **эскалация** + пауза |
| `type!="result"` / битый/пустой JSON | **tier1 retry** (транспорт, backoff) |
| `is_error` + exit1 + текст `session limit` (5h) | **quota-пауза → таймер до сброса** (D18, учётку не менять) |
| `is_error` + exit1 + текст `weekly limit`/неизвестный лимит | **quota → URGENT-эскалация** во все каналы (D18) |
| Next в фазе ВНЕ мандата запуска | **стоп** «мандат исчерпан» (D27, скоуп-гейт P0.6) |

Границы: soft/hard-параллелизм эскалаций по DAG — P5, НЕ MVP (D27/D33); tier2 semantic-retry
(менять промпт/скоуп) — драйвер P2.3, не этот контракт. Здесь фиксируется ЧТЕНИЕ сигнала и
класс решения, не реализация ретрая.

## 4. Правило breaking-детекта

Несовместимая смена схемы протокола БЕЗ синхронного bump'а пина этого контракта = **breaking**:
драйвер ОСТАНАВЛИВАЕТСЯ и эскалирует владельцу (§7 Consumed plan.md — «смена схемы без bump'а
контракта = breaking»). Конкретные ломающие изменения (закрытый перечень якорей контракта):

1. **Новый статус вне 6 канонических** (§1.4) — парсер статусов слепнет.
2. **Смена формата заголовка handoff** — regex §1.1 перестаёт матчить.
3. **Новая ОБЯЗАТЕЛЬНАЯ форма Next вне enum'а из 11** (§1.2) — драйвер не классифицирует шаг.
4. **Смена шапки/колонок Status Board** (`## 4.`, колонка `Items 🟢/всего`, §1.3).
5. **Смена полей JSON-конверта** (`type`/`is_error`/`result` переименованы/удалены, §2).

Детект — сверка версии/git-ref скилла при запуске (`claude --version` для бинаря + пин SSOT в
этом файле). При апгрейде плана-протокола донора: воркер, бампающий контракт, обязан обновить
пин (§Пин) и §7 Consumed plan.md; расхождение пина с фактической версией скилла на диске —
сигнал драйверу «стоп + эскалация», не тихая работа на устаревшей схеме.

**Анти-подгонка (code-guidance §1):** контракт описывает то, что протокол РЕАЛЬНО производит
(сверено с живыми `SKILL.md` §4/§6/§8 и snippets на commit `2cf26e8`), а не удобную драйверу
выдумку. Если handoff/статус в принципе машинно-нечитаемы в каком-то месте — НЕ чинить чужой
пакет (Scope Excluded фазы): proposal владельцу по `package-contribution-protocol` + эскалация.

## 5. Композируемость (D11) — контракт читается на любом уровне иерархии

Требование D11: иерархия супервизоров = РЕКУРСИЯ одного Artifex, не отдельная сущность.
Контракт ОБЯЗАН читаться одинаково на любом уровне:

- Дочерний прогон Artifex (супервизор на плане проекта X) представим как **item родительского
  плана** (оркестр-план экосистемы, сингтон AXIOMA-ORCHESTRA).
- «Доклад ребёнка» родителю = его `handoff.md` + журнал (P1.1/run-folder P0.6), парсимые ТЕМ ЖЕ
  контрактом: тот же regex заголовка (§1.1), тот же enum статусов (§1.4), те же формы Next (§1.2),
  тот же JSON-конверт (§2).
- Связь уровней — `plan_id` + `run_id` перекрёстными ссылками (run-folder P0.6 ↔ пер-плановый
  журнал P1.1). Дочерний run-folder несёт ссылку на родительский `run_id`.

**Границы (v1):** механизм иерархии (корневой супервизор гоняет дочерние) НЕ включается — это v2
после пилота P6.3 (OQ-4). Контракт лишь НЕ ЗАКРЫВАЕТ композицию схемой: ничего в §1–§4 не
предполагает единственный уровень. Схема пишется так, что дочерний handoff/статус/JSON —
валидный вход того же парсера.

## 6. Совместимость с будущим журналом (P1.1)

Scope P0.2 — только ТРЕБОВАНИЕ (не схема журнала, она — P1.1): контракт читает `session_id`,
`total_cost_usd`, `num_turns` из JSON-конверта (§2) — эти поля питают пер-плановый журнал P1.1
(стоимость, линковка сессии) и run-folder P0.6. Событие «исполнение item» журнала P1.1 несёт
`session_id`+`result`-исход, читаемые этим контрактом. Reconcile схемы журнала с полями §2 —
при детализации P1 (contract-first §5); расхождение → D# (supersedes), не тихая подгонка.
