# Roadmap: агент освежения проекта (freshness)

**Статус:** спекулятивно — не внедряем. **Критерий внедрения:** по факту измеренной проблемы
(D14, SKM-AUDIT-004): реальный случай, где устаревшее знание проекта (стек/зависимости/
конвенции) привело к ошибке ревью или разработки — не на упреждение.

## Проблема

Идея Owner (P7, field-feedback 2026-07-07): ревью-цепочка и dev-loop опираются на статичное
знание проекта на момент онбординга/последней синхронизации паков — версии зависимостей,
конвенции реестра, состав скиллов могут «протухнуть» без явного сигнала. Пример из этой же
фазы (P7.5): reviewer-агенты паков не видели конвенцию моделей реестра (`#[Table]`/
`#[ObservedBy]`/`$fillable`) — не потому что она изменилась, а потому что канал доставки
(`skills:` в subagent-frontmatter не инжектит snippets) не донёс её. Отдельный «агент
освежения» мог бы периодически сверять состояние проекта с реестром/апстримами и сигналить
дрейф — но это резидентная/периодическая фича, а не разовая правка.

## Почему не внедряется сейчас (D14)

Постоянная hook-инъекция или фоновый агент = резидентные токены каждой сессии
(`context-economy`) без измеренной проблемы, которую он решает лучше точечных фиксов
(как P7.5 — продублировать конвенцию строкой чек-листа). Философия репо: фичу внедряем
по факту измеренной проблемы, не на упреждение.

## Варианты (без обязательств)

1. On-demand команда (`maind doctor --audit freshness` в духе уже существующих
   `--audit pao`) — проверяет версии/конвенции по запросу, не резидентно.
2. Периодический fleet-скан через `analyst`/`maind sync` — сверяет проекты с реестром при
   каждой синхронизации (уже частично покрыто `maind sync`/`skiller update`).
3. Ничего не менять — точечные фиксы (как P7.5) закрывают конкретные дыры доставки
   конвенций без нового резидентного агента.
