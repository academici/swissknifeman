# Диагностика багов

Дисциплина для трудных багов. Пропускай фазы только при явном обосновании.

Исследуя кодовую базу, прочитай `CONTEXT.md` (если он есть), чтобы получить ясную ментальную модель релевантных модулей, и проверь ADR в той области, которую ты затрагиваешь.

## Фаза 1 — Построй feedback-loop

**Это и есть скилл.** Всё остальное — механика. Если у тебя есть **тугой** сигнал pass/fail по багу — такой, который краснеет на _этом_ баге, — ты найдёшь причину; бисекция, проверка гипотез и инструментация лишь потребляют его. Если такого сигнала нет, никакое разглядывание кода тебя не спасёт.

Вложи сюда непропорционально много усилий. **Будь агрессивен. Будь изобретателен. Откажись сдаваться.**

### Способы его построить — пробуй примерно в таком порядке

1. **Падающий тест** на любом seam, который дотягивается до бага — unit, integration, e2e.
2. **Curl / HTTP-скрипт** против запущенного dev-сервера.
3. **Вызов CLI** с фикстурным входом, сравнивающий stdout с известно-хорошим снапшотом (diff).
4. **Headless-браузерный скрипт** (Playwright / Puppeteer) — драйвит UI, проверяет утверждения на DOM/console/network.
5. **Реплей захваченной трассы.** Сохрани реальный сетевой запрос / payload / лог событий на диск; проиграй его через путь кода в изоляции.
6. **Одноразовый harness.** Подними минимальное подмножество системы (один сервис, замоканные зависимости), которое прогоняет путь кода с багом одним вызовом функции.
7. **Property / fuzz-loop.** Если баг — это «иногда неправильный вывод», прогони 1000 случайных входов и ищи режим отказа.
8. **Bisection-harness.** Если баг появился между двумя известными состояниями (коммит, датасет, версия), автоматизируй «загрузись в состоянии X, проверь, повтори», чтобы можно было прогнать `git bisect run`.
9. **Differential-loop.** Прогони один и тот же вход через старую версию vs новую (или две конфигурации) и сравни выводы (diff).
10. **HITL bash-скрипт.** Последнее средство. Если человек обязан кликнуть (или физическое устройство должно ответить — POS, libfptr10/Штрих-М), драйви _их_ через `snippets/hitl-loop.template.sh`, чтобы loop всё равно оставался структурированным. Захваченный вывод возвращается тебе.

Построй правильный feedback-loop — и баг исправлен на 90%.

### Затяни loop

Относись к loop'у как к продукту. Как только у тебя есть _какой-то_ loop, **затяни** его:

- Можно ли сделать его быстрее? (Закешировать setup, пропустить несвязанную инициализацию, сузить scope теста.)
- Можно ли сделать сигнал острее? (Проверять конкретный симптом, а не «не упало».)
- Можно ли сделать его детерминированнее? (Зафиксировать время, засидить RNG, изолировать файловую систему, заморозить сеть.)

30-секундный плавающий loop едва лучше отсутствия loop'а; 2-секундный детерминированный — тугой, это суперсила отладки.

### Недетерминированные баги

Цель — не чистый repro, а **более высокая частота воспроизведения**. Прогони триггер 100×, распараллель, добавь стресс, сузь временны́е окна, инъецируй sleep'ы. Баг с 50% плавающести отлаживаем; 1% — нет — поднимай частоту, пока не станет отлаживаемым.

### Когда ты действительно не можешь построить loop

Остановись и скажи об этом явно. Перечисли, что ты пробовал. Попроси у пользователя: (a) доступ к окружению, которое его воспроизводит, (b) захваченный артефакт (HAR-файл, дамп логов, core dump, запись экрана с таймстампами) или (c) разрешение добавить временную инструментацию в проде. **Не** переходи к выдвижению гипотез без loop'а.

### Критерий завершения — тугой loop, который умеет краснеть

Фаза 1 завершена, когда loop **тугой** и **способен покраснеть**: ты можешь назвать **одну команду** — путь к скрипту, вызов теста, curl, — которую ты **уже запускал хотя бы раз** (вставь вызов и его вывод), и которая:

- [ ] **Способна покраснеть** — она драйвит реальный путь кода с багом и проверяет **точный симптом пользователя**, так что краснеет на этом баге и зеленеет после фикса. Не «отрабатывает без ошибок» — она должна уметь _поймать именно этот баг_.
- [ ] **Детерминированна** — один и тот же вердикт на каждом запуске (плавающие баги: зафиксированная высокая частота воспроизведения, как выше).
- [ ] **Быстрая** — секунды, не минуты.
- [ ] **Запускаема агентом** — ты можешь запустить её без присмотра; человек в loop'е — только через `snippets/hitl-loop.template.sh`.

Если ты ловишь себя на чтении кода ради построения теории до того, как эта команда существует, **остановись — прыжок сразу к гипотезе — это ровно тот провал, который предотвращает этот скилл.** Нет команды, способной покраснеть — нет Фазы 2.

## Фаза 2 — Воспроизведи + минимизируй

Запусти loop. Смотри, как он краснеет — баг проявляется.

Подтверди:

- [ ] Loop порождает тот режим отказа, который описал **пользователь**, — не другой, оказавшийся рядом, отказ. Не тот баг = не тот фикс.
- [ ] Отказ воспроизводим на нескольких запусках (или, для недетерминированных багов, воспроизводим с достаточно высокой частотой, чтобы отлаживаться против него).
- [ ] Ты захватил точный симптом (сообщение об ошибке, неправильный вывод, медленный тайминг), чтобы поздние фазы могли проверить, что фикс действительно его адресует.

### Минимизируй

Как только покраснело, ужми repro до **наименьшего сценария, который всё ещё краснеет**. Срезай входы, вызывающие стороны, конфиг, данные и шаги **по одному**, перезапуская loop после каждого среза — оставляй только то, что несущее для отказа.

Зачем заморачиваться: минимальный repro сжимает пространство гипотез в Фазе 3 (меньше движущихся частей остаётся под подозрением) и становится чистым регресс-тестом в Фазе 5.

Готово, когда **каждый оставшийся элемент несущий** — удаление любого из них делает loop зелёным.

Не двигайся дальше, пока не воспроизвёл **и** не минимизировал.

## Фаза 3 — Выдвини гипотезы

Сгенерируй **3–5 ранжированных гипотез** до того, как проверять любую из них. Генерация единственной гипотезы заякоривает на первой правдоподобной идее.

Каждая гипотеза должна быть **фальсифицируемой**: сформулируй предсказание, которое она делает.

> Формат: «Если причина — <X>, то <изменение Y> заставит баг исчезнуть / <изменение Z> сделает его хуже.»

Если ты не можешь сформулировать предсказание, гипотеза — это вайб; отбрось её или заточи.

**Покажи ранжированный список пользователю до проверки.** У него часто есть доменное знание, которое мгновенно переранжирует («мы только что выкатили изменение в #3»), или он знает гипотезы, которые уже исключил. Дешёвый чекпоинт, большая экономия времени. Не блокируйся на нём — продолжай со своим ранжированием, если пользователь AFK.

## Фаза 4 — Инструментируй

Каждый зонд должен мапиться на конкретное предсказание из Фазы 3. **Меняй одну переменную за раз.**

Предпочтения по инструментам:

1. **Дебаггер / инспекция в REPL**, если окружение это поддерживает. Один брейкпоинт бьёт десять логов.
2. **Точечные логи** на границах, которые различают гипотезы.
3. Никогда «залогируй всё и грепай».

**Тегируй каждый отладочный лог** уникальным префиксом, например `[DEBUG-a4f2]`. Очистка в конце становится одним grep. Нетегированные логи выживают; тегированные — умирают.

**Перф-ветка.** Для регрессий производительности логи обычно неправильный инструмент. Вместо этого: установи baseline-измерение (timing-harness, `performance.now()`, профайлер, query plan), затем бисекти. Сначала измеряй, потом чини.

## Фаза 5 — Фикс + регресс-тест

Напиши регресс-тест **до фикса** — но только если для него есть **корректный seam**.

Корректный seam — это такой, где тест прогоняет **реальный паттерн бага** так, как он возникает на call site. Если единственный доступный seam слишком мелкий (тест с одним вызывающим, когда багу нужно несколько вызывающих; unit-тест, который не может воспроизвести цепочку, спровоцировавшую баг), регресс-тест там даёт ложную уверенность.

**Если корректного seam не существует, это само по себе и есть находка.** Зафиксируй это. Архитектура кодовой базы мешает запереть баг. Подними этот флаг для следующей фазы.

Если корректный seam существует:

1. Преврати минимизированный repro в падающий тест на этом seam.
2. Смотри, как он падает.
3. Примени фикс.
4. Смотри, как он проходит.
5. Перезапусти feedback-loop из Фазы 1 против исходного (неминимизированного) сценария.

## Фаза 6 — Очистка + post-mortem

Обязательно перед объявлением «готово»:

- [ ] Исходный repro больше не воспроизводится (перезапусти loop из Фазы 1)
- [ ] Регресс-тест проходит (или отсутствие seam задокументировано)
- [ ] Вся инструментация `[DEBUG-...]` удалена (`grep` по префиксу)
- [ ] Одноразовые прототипы удалены (или перенесены в явно помеченное отладочное место)
- [ ] Гипотеза, оказавшаяся верной, сформулирована в сообщении коммита / PR — чтобы следующий отладчик научился

**Затем спроси: что предотвратило бы этот баг?** Если ответ предполагает архитектурное изменение (нет хорошего тест-seam, спутанные вызывающие, скрытая связанность), передай в скилл `codebase-design` с конкретикой. Делай рекомендацию **после** того, как фикс на месте, а не до — сейчас у тебя больше информации, чем в начале.
