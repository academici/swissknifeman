# Roadmap: Task не должен выпускать user-facing final при открытом plan run

**Статус:** 🧪 session-bound guard реализован локально; полный transport/structured-handoff acceptance остаётся открытым (обновление в конце файла).

**Критерий запуска:** 2026-09-15, Edufy `2026.08.06-EDUFY-BUILD P7.4`.
Пользователь многократно потребовал продолжать до полного завершения, однако агент несколько раз
выпускал ответ на границе `final`. В это время durable state item оставался `🟡 In progress`:
в journal есть `plan_recovery.start` для run
`06058a8d85b31b4a874f42be4ec42185309a092edf8e823721c5d890369c17f5`, но нет terminal event
(`closed-green`, `blocked` или эквивалента) и нет `plan-delivery --kind terminal` receipt.

Это **не ложное закрытие plan item**: состояние P7.4 не было подменено и не должно быть
ретроактивно закрыто. Это ложное *user-facing завершение* открытой работы.

## Наблюдаемая цепочка

| Факт | Статус доказательства |
|:--|:--|
| P7.4 восстановлен как активный run, его generated state показывает `In progress`. | Наблюдалось в plan journal/state. |
| Для run нет terminal journal event и terminal delivery receipt. | Наблюдалось в журнале и артефактах delivery. |
| После частичных проверок агент возвращал `final`, хотя владелец требовал не останавливаться. | Наблюдалось в этой owner session. |
| `harness doctor --provider-audit --json` завершился успешно с `diagnostics: []`; catalog hash `sha256:3417643f87ca3b22c519e360201020bc50b6a81c774bd2dd938c612fdbefb66a`. | Воспроизводимая локальная диагностика. |
| Audit сообщает поддержку Codex surfaces `lifecycle.terminal-admission`, `lifecycle.run-report`, `lifecycle.router` и `lifecycle.review-gate`. | Воспроизводимая локальная диагностика. |

Последний факт не опровергает инцидент: provider audit подтверждает установку и декларацию
surface, но не доказывает, что каждое решение модели выдать chat `final` прошло через эту
surface.

## Причина и условия

### Установленная причина

1. Агент ошибочно трактовал успешную локальную проверку как достаточную границу ответа и
   использовал `final` для progress report. По контракту Codex частичный результат должен быть
   `commentary`; `final` допустим лишь после достижения запроса либо настоящей границы ожидания.
2. Task lifecycle хранит состояние plan item и умеет проверять terminal receipt, но текущий
   фактический путь формирования model response не обязан вызывать проверку открытого run перед
   эмиссией `final`.
3. `terminal_admission` ориентирован на terminal receipt/lease. Когда агент не строит receipt
   вовсе, этот guard не получает proposed terminal artifact и потому не является доказанной
   защитой от раннего chat-final.

### Условия проявления

- Запущен `task:plan-run`, а latest state item — `in progress`.
- Есть локальный промежуточный успех (например, subset тестов), но acceptance item ещё не
  исчерпан.
- Нет явного transport-level вызова, который сравнивает proposed `final` с current plan state.
- У владельца есть продолжающееся намерение «доделать всё», но это намерение не стало
  machine-checked precondition финального ответа.

### Что не установлено

Нельзя утверждать, что причина в повреждённом journal, provider configuration или в самом
`harness doctor`: журнал сохранил корректное открытое состояние, а doctor не предназначен для
контроля семантического выбора model-output. Нужен отдельный тест именно response-boundary.

## Разрыв с существующей защитой

Связанный carrier
[`2026.09.14-task-terminal-command-emission-regression.md`](2026.09.14-task-terminal-command-emission-regression.md)
разбирает иной случай: item был закрыт и receipt существовал, но exact native command не попала
в user-facing final. Здесь receipt отсутствует, потому что закрытия быть не должно. Общая щель —
отсутствие обязательного enforcement на реальном месте эмиссии `final`; исправлять их следует
согласованно, но не сливать доказательства и acceptance.

## Обязательное исправление

1. В единственном provider/agent response-finalization seam добавить детерминированную проверку
   `task.pre_final_open_run`.
2. Проверка читает declared plan/item и latest durable journal state. Если active run имеет
   `in-progress`, она отклоняет proposed `final` с кодом
   `TASK_OPEN_RUN_FINAL_FORBIDDEN` и возвращает управление в execution/commentary path.
3. Исключение допустимо только для структурированного waiting/blocked handoff, когда оно уже
   записано в state по канону и ответ содержит точный checkpoint; простая усталость агента,
   успешный subset тестов и отсутствие receipt исключениями не являются.
4. Для закрытого item сохраняется существующая terminal-admission проверка exact receipt.
   Отсутствие receipt при открытом run не должно означать `not applicable`.
5. Писать минимальный audit record каждого pre-final решения: item/run id, observed state,
   allow/reject reason. Не записывать пользовательский текст и секреты.
6. Уточнить `plan-run` projection: до terminal state разрешены только продолжение работы и
   `commentary`-progress, а не owner-facing `final`.

## Проверяемый acceptance

- Active P7.4-подобный run с зелёным subset тестов: proposed final отклонён; state остаётся
  открытым, работа продолжается.
- Active run при явном сообщении владельца «доделывай до конца»: тот же запрет.
- Канонический persisted `waiting-*`/`blocked`: допускается только точный structured handoff.
- `closed-green` с валидным receipt: terminal final допускается и сохраняет exact delivery
  fragment.
- Обычный ответ вне plan run не получает ложного запрета.
- Provider integration test достигает реального final dispatcher, а не только unit-test
  `terminal_admission` с искусственно созданным receipt.

## Граница и следующий владелец

Исправление принадлежит Task lifecycle и Codex provider adapter; вероятные точки исследования —
`packages/task/lib/task/terminal_admission.py`, `plan_delivery.py`, `commands/plan-run.md` и
Codex lifecycle hook/response dispatcher. Сначала надо установить единственное фактическое место,
которое может перехватить model `final`; нельзя заявлять enforcement только по инструкции в
markdown.

Это не разрешает агенту бесконечно выполнять новые неавторизованные работы и не отменяет явный
owner stop. Это запрещает только выдавать работу за завершённую, когда её durable execution state
ещё открыт. Carrier должен быть переведён в ограниченную implementation task после выбора
доступного response dispatcher; до этого он остаётся измеримым незакрытым полевым регрессом.
