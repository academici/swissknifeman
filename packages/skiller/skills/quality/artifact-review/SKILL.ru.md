# Таксономия ревью по типу артефакта

## Когда активировать

- Поступил запрос на ревью, и артефакт — НЕ только код: план, спека, ТЗ, документация.
- Диспетчеризуешь ревью-команду (`task:review`, `task:plan-audit`) и надо выбрать профиль.
- Пишешь findings и нужна единая шкала severity + лейблов вместо самодельной.

Не применять: как замену стек-специфичных чек-листов кода — их даёт skill-conformance
(оркестратор `task:review`, Stage B); этот скилл — верхний уровень: КАКИМ профилем мерить.

## Принцип

Ревью «одним взглядом на всё» пропускает классы дефектов: план ломается не там, где код.
Разделение design/doc/code review — индустриальная реальность (RAG:✅ P5.1 §7 2026-07-09);
named-стандарта severity именно для plan-review нет — шкала ниже адаптирована нами и
помечается соответственно. Каждому типу артефакта — своя **конституция соответствия**
(против чего сверяем) и свои **измерения** (что именно ломается).

## Три профиля

| Профиль | Конституция соответствия | Ключевые измерения |
|:--|:--|:--|
| **План/спека** | схема plan-protocol 2.0 + DoR | RAG-groundedness несущих (маркеры `RAG:✅`/`[UNVERIFIED]`); структурная полнота (секции/статусы/папки); непротиворечивость D-лога/фаз; Open Questions вынесены; гейты определены |
| **Документация** | канон структуры docs (Diátaxis / канон vault) | соответствие канону; staleness против кода (примеры/маршруты/флаги сверены); миграция план→docs без потерь; wiki-связность / битые ссылки |
| **Код** | скиллы стека (skill-conformance, `task:review` Stage A/B) | correctness / security / perf + skill-conformance по каждому применимому скиллу |

Конституция — не вкус ревьюера: находка «не соответствует» обязана ссылаться на конкретное
правило конституции (секцию схемы, правило канона, строку `## Conformance` скилла).

## Общие оси: severity × лейбл

Две **независимые** оси на каждую находку (RAG:✅ P5.1 §7, CONFIRMED: Conventional Comments —
лейбл о намерении комментария, severity — о весе):

**Severity** (вес находки):

| Severity | Значение |
|:--|:--|
| **Blocker** | артефакт нельзя принимать/мержить, пока не исправлено |
| **Major** | важный дефект: исправить сейчас или явным решением отложить (ticket/D#) |
| **Minor** | реальный, но некритичный дефект — на усмотрение автора со следом |
| **Nit** | мелочь/стиль; никогда не блокирует |

**Лейбл** (намерение комментария, Conventional Comments): `issue` / `suggestion` /
`question` / `nitpick`. Комбинации легальны и информативны: `issue(Blocker)`,
`suggestion(Minor)`, `question(Major)` — вопрос, от ответа на который зависит приёмка.

Правила: при сомнении severity ставить ВЫШЕ, не отбрасывать самому (детект ≠ гейтинг);
каждая находка несёт `file:line` + failure_scenario + ссылку на правило конституции.

## Ревью-фиксы

Фиксы по находкам — **отдельными коммитами** от ревью-отчёта и друг от друга
(commit-гейт P7.4): один смысловой фикс = один коммит `тип(scope): суть`, чтобы фикс был
атомарно откатываем и трассируем к находке.

## Диспетчеризация

По типу артефакта на входе (аналогично детекту стека в `task:review` Stage A):

| Артефакт | Команда-реализация профиля |
|:--|:--|
| План/спека (`plans/<ID>/…`) | `task:plan-audit` — объявленная реализация профиля «ревью плана» |
| Документация (`docs/`, README, гайды) | `task:review`, профиль doc |
| Код (дифф/ветка/PR) | `task:review`, профиль code (Stage A/B/C + skill-conformance) |

Смешанный вход (дифф трогает и код, и docs) — прогнать оба профиля, findings не смешивать:
у каждой находки указан профиль.

## Чеклист качества

- [ ] Профиль выбран по типу артефакта до начала ревью, не по привычке «читаю как код».
- [ ] Конституция названа явно; каждая находка ссылается на её конкретное правило.
- [ ] Каждая находка: severity (Blocker/Major/Minor/Nit) + лейбл + `file:line` + failure_scenario.
- [ ] Nit не блокирует; Blocker не понижен «чтобы не задерживать».
- [ ] Смешанный артефакт разобран по профилям, findings не перемешаны.
- [ ] Фиксы — отдельными атомарными коммитами, трассируемыми к находкам.

## Conformance

- Профиль ревью выбирай по типу артефакта: план/спека → plan-protocol+DoR, документация → канон docs, код → скиллы стека.
- Каждой находке — severity из enum `Blocker/Major/Minor/Nit` И лейбл `issue/suggestion/question/nitpick`; оси не смешивать.
- Находку «не соответствует» привязывай к конкретному правилу конституции (скилл→правило, секция схемы, канон).
- Каждой находке — `file:line` + failure_scenario.
- При сомнении severity ставь выше; сам находки не отбрасывай.
- `nitpick`/Nit не блокирует приёмку.
- Ревью-фиксы — отдельными коммитами, по одному на смысловой фикс.

## Связанные скиллы

- `quality/code-review` — процесс/чек-лист командного code review (P0–P3, SLA, префиксы `[blocker]`…); этот скилл — таксономия уровнем выше: какой профиль и какая шкала.
- `general/plan-protocol` — схема plan-protocol 2.0 + DoR = конституция профиля «план/спека».
- `quality/tech-debt-audit` — плановый аудит долга; сюда стекают Major-находки, отложенные решением.
- `general/git-commit-rules` — формат атомарных коммитов ревью-фиксов.
