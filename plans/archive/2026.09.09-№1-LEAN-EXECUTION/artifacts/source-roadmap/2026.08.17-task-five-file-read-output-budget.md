# Task: безопасное однократное чтение v2-контекста при ограниченном transport output

**Статус:** ⬜ к внедрению
**Измерено:** 2026-08-17, `2026.08.02-PROVIDER-CONTRACT-LOCALE` P7.4
**Владелец:** `packages/task` — `plan-exec` contract и Codex command adapter
**Класс:** полевой дефект инструкции/transport contract; не дефект файлов плана

## Проблема

`task:plan-exec` требует прочитать ровно пять v2-файлов один раз и запрещает повторное чтение.
Во время P7.4 все пять файлов были объединены в один `exec_command` output. Дочернему вызову
был задан `max_output_tokens=60000`, но внешний `functions.exec` остался на своём независимом
default `10000`. В результате внешний transport усёк совокупные `14716` оценочных токенов,
shell завершился с кодом `0`, а из видимого контекста исчезло само ТЗ P7.4.

Текущий текст протокола не говорит, что у Codex orchestration два независимых output-budget,
не задаёт способ обнаружить неполное чтение до продолжения и одновременно запрещает безопасное
восстановление через повторное чтение. Однострочный `bundles/Pn.m.json` усиливает проблему:
обычная постраничная выдача по строкам для него не работает.

## Диагностический feedback loop

Наблюдавшая команда читала только обязательные пять файлов:

```bash
for f in \
  plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/plan.md \
  plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/phases/P7/P7.md \
  plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/phases/P7/P7.4.md \
  plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/bundles/P7.4.json \
  plans/2026.08.02-PROVIDER-CONTRACT-LOCALE/phases/P7/P7.4.state.md
do
  sed -n '1,$p' "$f"
done
```

Observed outer result:

```text
Warning: truncated output (original token count: 14716)
```

Размеры входов на snapshot: `16614 + 5075 + 9752 + 26462 + 601 = 58504` bytes. Положительный
контроль вывел `21007` оценочных токенов из дочернего `exec_command` и сохранил terminal sentinel,
когда внешний JS не пересылал payload целиком, а проверял и возвращал только компактный verdict.
Это исключает повреждение файлов, `sed` и child limit как первичную причину.

Попытка вызвать ожидаемую семантическую команду диагностики также дала:

```text
CMD_SOURCE_MISSING: packages/task/commands/diagnostic.md
```

Поэтому расследование выполнено каноническим `quality:diagnosing-bugs`. Добавление новой
`task:diagnostic` не входит в эту работу: одного случая недостаточно для ещё одной public command.

## Корневая причина

1. `exec_command.max_output_tokens` и `functions.exec` `@exec.max_output_tokens` — независимые
   лимиты; увеличение только дочернего лимита не защищает внешний результат.
2. Канонический `plan-exec` описывает физическое «read once», но не определяет логический
   immutable snapshot и допустимое продолжение transport pagination.
3. Codex adapter не напоминает про внешний `@exec` budget и не требует проверяемый end marker,
   cursor либо полный digest receipt.
4. Пять файлов разрешено читать по отдельности, но инструкция не направляет исполнителя к этому
   безопасному варианту и не определяет fallback для одного файла больше transport cap.

## Целевой контракт

«Один раз» должно означать один content-addressed snapshot worktree-входов, а не один
непагинируемый tool response.

- Снять SHA-256 пяти файлов и материализовать один immutable snapshot/receipt до анализа.
- Читать каждый небольшой файл отдельным bounded result; не объединять все пять вслепую.
- Большой файл выдавать чанками из уже снятого snapshot по byte cursor, не перечитывая live
  worktree и не смешивая разные версии.
- Каждый chunk несёт `snapshot_sha256`, `offset`, `next_offset`, `complete`; последний chunk
  имеет проверяемый terminal marker.
- Любой `truncated output`, отсутствующий terminal marker или несовпавший digest даёт
  `PLAN_CONTEXT_TRUNCATED` до product-journal mutation и разрешает продолжение только из того же
  snapshot.
- Codex projection явно связывает child `max_output_tokens` с внешним `// @exec` budget;
  provider-neutral canonical contract не упоминает приватный transport API.

## Минимальный implementation slice

1. Уточнить логическую snapshot-once семантику в каноническом
   `packages/task/commands/plan-exec.md`.
2. Добавить в `packages/task/lib/task/command_render.py` Codex-only output-budget/truncation rule;
   регенерировать adapter projections владельцем генератора.
3. Если bounded per-file guidance не покрывает один файл выше cap, добавить stdlib-only helper
   `task.plan_context_snapshot` с receipt/cursor; не создавать второй парсер plan/bundle.
4. Зафиксировать golden/provider-parity cases и один regression, в котором совокупный контекст
   больше внешнего default cap, а `P7.4.md` находится в усекаемой середине.

## Acceptance

- Golden Codex projection содержит outer-budget guard, terminal completeness check и
  provider-neutral snapshot-once wording не меняет смысл Claude projection.
- Regression воспроизводит прежний silent partial context и после изменения получает либо все
  пять файлов одного snapshot, либо fail-closed `PLAN_CONTEXT_TRUNCATED` до journal start.
- Chunk continuation не выполняет повторное чтение worktree; изменение live-файла между чанками
  не смешивается со snapshot и даёт digest mismatch.
- Однострочный bundle больше transport cap читается полностью через byte cursor.
- `packages/task/scripts/validate.sh`, provider projection `--check`, registry/generator checks и
  root `validate.sh` зелёные; generated adapters не правятся вручную.

## Критерий внедрения

**Критерий уже сработал:** реальный P7.4 потерял ТЗ при успешном shell exit и потребовал нарушить
буквальное `read once` для восстановления. Реализовать при следующей правке `plan-exec` read gate,
Codex adapter transport rules или plan bundle/read-budget runtime — раньше других улучшений этой
же границы.

## Не входит

- повышение глобальных output limits без fail-closed completeness proof;
- удаление read-budget gate;
- повторное чтение live worktree как штатный recovery;
- новая public `task:diagnostic` без второго независимого измеренного запроса;
- исправление P7.4/P7.3 audit findings внутри этого roadmap item.
