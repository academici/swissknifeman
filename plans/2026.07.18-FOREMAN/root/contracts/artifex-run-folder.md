# Контракт run-folder + мандат запуска супервизора (Artifex)

**Назначение.** Канон **запуска** супервизора Artifex: durable файловое состояние одного
прогона + декларативный мандат делегирования. Каждый запуск = папка по аналогии с `plans/`
(`runs/<ГГГГ.ММ.ДД-КОД>/`), переживающая падение/ребут машины; resume — по **папке**, не по
session id (сессии эфемерны — D16). Сиюминутный state прогона живёт ТОЛЬКО здесь; в mAInd
уходят лишь итоги (фаза закрыта, стоимость, ATTENTION — D4/D16/D35).

**Граница с планом (P0.2).** Run-folder несёт состояние **драйвера** (курсор прогона, счётчики
попыток, пауза, активная учётка). Состояние **плана** (какие items 🟢, что дальше) живёт в
Status Board / handoff плана и читается по контракту `driver-plan-protocol.md` (P0.2) — SSOT
плана = сам план. Драйвер НЕ дублирует статус плана в run-folder как источник истины; при
расхождении курсора со state плана — **прав план** (§Resume, п. 5).

**SSOT.** Схема этого контракта — SSOT для драйвера P2.4 и P5.4. Layout слизан у Ralph
orchestrator (D17а, шаблон), НЕ импортирует его код/мир; роли Gas Town — референс зон для
иерархии D11 (§7), не реализуются в v1.

## 1. Структура папки `runs/<ГГГГ.ММ.ДД-КОД>/`

Дата-код имени — канон plan-ID (D16): `ГГГГ.ММ.ДД` + `-` + КОД (SCREAMING-KEBAB, напр.
`2026.07.20-FLEX2-P1-DRIVE`). Имя = `run_id` (durable ключ resume).

```
runs/<ГГГГ.ММ.ДД-КОД>/
├── brief/
│   └── 00-mandate.md        # мандат владельца (зона ответственности) — §4, заполняется при делегировании
├── state.json               # текущий снимок прогона (ПЕРЕЗАПИСЫВАЕТСЯ) — §2
├── journal.jsonl            # событийный лог прогона (APPEND-ONLY) — §3
└── reports/                 # per-item run-report JSON'ки (reuse harness run-report; §3 п. item_result ссылается)
    └── <item>-<session_id>.json
```

- `state.json` и `journal.jsonl` — **раздельны по семантике записи**: state = снимок
  (перезаписывается целиком при каждом переходе), journal = неизменяемая история (только append).
  Смешивать запрещено (§3 анти-второй-носитель plan-protocol).
- `reports/` — сырые run-report'ы воркеров (Ralph `events-*.jsonl` ≈ наши per-item отчёты);
  журнал ссылается на них по `session_id`, не дублирует их тело.
- Дата-папка durable: лежит в git-дереве проекта (см. §5 Дом), переживает ребут — как `plans/`.

## 2. Схема `state.json` (снимок, перезаписывается)

Единственный носитель **сиюминутного** состояния драйвера. JSON-объект:

| Поле | Тип | Обяз. | Назначение |
|:--|:--|:--:|:--|
| `schema_version` | str | ✔ | версия схемы run-folder (semver, синхронно с версией плана — D15ж) |
| `run_id` | str | ✔ | == имя папки `<ГГГГ.ММ.ДД-КОД>` (durable ключ resume) |
| `plan_id` | str | ✔ | ведомый план (`2026.07.18-FLEX-2` и т.п.) — линковка с журналом P1.1 |
| `plan_path` | str | ✔ | путь к плану (относительно дома, для чтения Status Board/handoff по P0.2) |
| `mandate_ref` | str | ✔ | путь `brief/00-mandate.md` (зона ответственности прогона) |
| `parent_run_id` | str\|null | ✔ | ссылка на родительский прогон (D11 композиция) — `null` в v1, схема НЕ закрывает иерархию |
| `status` | enum | ✔ | `active`\|`paused`\|`quota_paused`\|`escalated`\|`completed`\|`aborted` |
| `cursor` | obj | ✔ | где мы: `{phase, item, stage}`; `stage` ∈ `launching`\|`running`\|`parsing`\|`closing`\|`idle` |
| `counters` | obj | ✔ | `{attempts: {"<Pn.m>": n}, loops: n, escalations: n}` — попытки/петли (вход прогресс-движка P5) |
| `pause` | obj\|null | ✔ | при `paused`/`quota_paused`: `{reason, since_ts, resume_condition, limit_type?}`; иначе `null` |
| `account` | str\|null | ✔ | метка активной учётки при квота-детекте (D18), если детектируемо; иначе `null` |
| `cost_usd` | number | ✔ | накопленная стоимость прогона (сумма `total_cost_usd` воркеров, §3) |
| `updated_ts` | str | ✔ | ISO-8601 UTC последнего перехода |

- `status=quota_paused` — отдельно от `paused` (D18 третий класс сбоя): `pause.limit_type` ∈
  `session` (5h-окно → ждать, учётку не менять) \| `weekly`\|`unknown` (→ URGENT-эскалация).
- `cursor.item` = item, который драйвер ведёт СЕЙЧАС; при расхождении с планом — план прав (§5).
- Трассировка потребителей: `cursor`/`counters`/`pause` → драйвер P2.4 + прогресс-движок P5;
  `account`/`pause.limit_type` → quota-ветка P4.2 (D18); `parent_run_id` → иерархия D11 (v2).

## 3. Событийная схема `journal.jsonl` (append-only NDJSON)

Одна строка = одно событие прогона. Формат согласован с пер-плановым журналом P1.1 (D24/D26).

**Общие поля КАЖДОГО события** (⚑ = общие с пер-плановым журналом P1.1 — он их
потребляет/агрегирует):

| Поле | Тип | Общее с P1.1 | Назначение |
|:--|:--|:--:|:--|
| `ts` | str | ⚑ | ISO-8601 UTC |
| `run_id` | str | ⚑ | прогон (== `state.run_id`) |
| `plan_id` | str | ⚑ | ведомый план |
| `item_id` | str\|null | ⚑ | `Pn.m` или `null` (событие уровня прогона/фазы) |
| `event` | enum | — | тип события (ниже) |
| `session_id` | str\|null | ⚑ | id сессии воркера (линковка P0.2 §2 → P1.1); `null` для событий драйвера |

**Типы событий (`event`) и их доп-поля:**

| `event` | Доп-поля | Когда |
|:--|:--|:--|
| `run_started` | `mandate_ref`, `parent_run_id`, `plan_path` | старт прогона (первое событие) |
| `item_launch` | `command`⚑, `model`, `permission_mode` | запуск воркера свежей сессией (`command` — что запущено, ⚑ P1.1) |
| `item_result` | `result`⚑, `is_error`, `terminal_status`, `num_turns`, `total_cost_usd`, `report_ref` | исход прогона item (JSON-конверт P0.2 §2; `terminal_status` ∈ 6 статусов; `report_ref` → `reports/`) |
| `retry` | `tier` (1\|2\|3), `reason` | ретрай (tier1 транспорт / tier2 semantic / tier3 quota — P2.3) |
| `escalation` | `severity`, `kind`, `channels[]`, `envelope_ref` | эскалация владельцу (envelope P4.1/D32) |
| `quota_pause` | `limit_type`, `reset_wait?` | детект лимита учётки (D18) |
| `resume` | `from_stage`, `reason` | возобновление после паузы/краша |
| `decision` | `signals`, `applied_rules[]`, `verdict`, `rationale` | **лог решений супервизора (P5.4/D39)** — обогащённое событие, НЕ отдельный файл |
| `run_paused` | `reason` | пауза очереди (эскалация/недоставка каналов — D34) |
| `phase_closed` | `phase`, `items_done`, `items_total` | фаза плана закрыта в этом прогоне |
| `run_completed` | `outcome` (`done`\|`escalated`\|`aborted`) | терминал прогона |

- `decision`-событие (P5.4) пишется через тот же `run_folder.append_event` (reuse P2.4) — поля
  `signals` (метрики прогресс-движка P5.1) / `applied_rules` (id правил rulebook P5.3) / `verdict`
  (`progressing`\|`stalling`\|`unclear`) / `rationale`. Отдельного `decisions.jsonl` НЕТ (D39).
- `item_result.total_cost_usd` суммируется драйвером в `state.cost_usd`; он же — cost-aware сигнал
  P5.1 и репорт в mAInd P4.4 (D35).
- Append из параллельных под-сессий одного прогона — построчный (NDJSON без merge-конфликтов, D20).

## 4. Шаблон мандата `brief/00-mandate.md`

Мандат = **зона ответственности ОДНОГО запуска** (per run), в отличие от policy (per project,
постоянная — P0.3). Записывается В ЗАПУСК при делегировании, чтобы супервизор постоянно
перечитывал свои границы (resume, §5). Шаблон:

```markdown
---
type: artifex-mandate
run_id: <ГГГГ.ММ.ДД-КОД>
plan_id: <PLAN-ID>
issued: <ISO-дата>
issued_by: <владелец>
expires: <ISO-дата|—>          # опц. срок действия мандата
---

# Мандат запуска <ГГГГ.ММ.ДД-КОД>

## Скоуп фаз
<напр. «P1» | «P1–P5» — какие фазы плана супервизор ведёт; Next в фазе ВНЕ скоупа → стоп «мандат исчерпан» (P0.2 §3)>

## Права (что супервизор ВПРАВЕ авто-вести)
<подмножество авто-драйв-форм D27: напр. только `/task:plan-exec` DRIVE + механический `plan-close`>

## Ограничения (что супервизор НЕ делает — сверх policy)
<напр. «не трогать фазу P6-пилот», «не менять учётку», «эскалировать любой contract-item»>

## Каналы эскалации (порядок)
<напр. MAX → TG; наследует/сужает список из policy P0.3>

## Прочее
<пороговые оговорки, «ночью будить только на quota-weekly» и т.п.>
```

**Правило «мандат СУЖАЕТ policy, не расширяет» (граница с P0.3, D16).** Точная семантика:
эффективные права прогона = `policy ∩ mandate`. Мандат может ТОЛЬКО убрать право / сузить
скоуп фаз / укоротить список каналов — НИКОГДА добавить право, которого policy не даёт, или
фазу вне opt-in policy. Мандат, пытающийся расширить policy (право сверх policy, фаза вне
проектного opt-in) → **невалиден**: драйвер отказывается стартовать + эскалация владельцу (не
тихое усечение). Та же граница пересечения, что policy↔мандат в P0.3.

## 5. Семантика resume («продолжай <ПАПКА>»)

Resume — по **папке** (`artifex continue runs/<ГГГГ.ММ.ДД-КОД>` / «супервизор, продолжай
<папка>»), НЕ по session id: сессия эфемерна, папка durable, переживает ребут (D16). Порядок
чтения при восстановлении — строго:

1. **`brief/00-mandate.md`** — реконструкция зоны ответственности (скоуп фаз, права,
   ограничения, каналы). Без мандата прогон не возобновляется (зона неизвестна → стоп).
2. **`state.json`** — курсор (`cursor.phase/item/stage`), счётчики попыток, `status`/`pause`,
   активная учётка.
3. **`journal.jsonl` (хвост)** — последние события: чем закончился прерванный item, была ли
   пауза/квота/эскалация; сверка целостности со `state.json`.
4. **Состояние ПЛАНА** через контракт P0.2 — `handoff.md` (заголовок `after Pn[.m]`, Next) +
   Status Board `plan.md` (какие items терминальны). Это SSOT прогресса плана.
5. **Reconcile.** Если `state.cursor` расходится с фактическим состоянием плана (п. 4) —
   **прав план**: курсор пере-выводится из Status Board/handoff; прерванный на `stage∈{launching,
   running,parsing}` item ПЕРЕ-запускается свежей сессией (идемпотентность — воркер сам
   пере-исполнит незакрытый item по plan-протоколу); `stage=closing` без записи `item_result` →
   проверить, закрыл ли воркер item в плане (Status), при да — только дописать журнал (backstop
   D26), при нет — пере-запуск.

Крах во время `quota_paused` → при resume проверить сброс лимита (`pause.limit_type=session` →
ждать/таймер; `weekly` → мог смениться логин, пере-запуск прерванного item свежей сессией — D18).

## 6. Связь `run_id`↔`plan_id` с пер-плановым журналом P1.1 (reconcile-контракт)

Два журнала делят общие поля и связываются ключами (D24):

- **run-folder `journal.jsonl`** (этот контракт) = **сырой событийный лог ОДНОГО прогона**
  супервизора (все его сессии, ретраи, решения).
- **пер-плановый `journal.jsonl`** (P1.1) = **консолидированная история ПЛАНА** (одна запись на
  исполнение item, из ВСЕХ сессий — ручных и Artifex).

**Владение записью (D26):**

- Пер-плановый журнал пишет **воркер** (close-протокол `plan-exec`, хелпер `lib/task/journal.py`,
  P1.3) — одна запись на исполнение item.
- run-folder журнал пишет **драйвер** (событийно, этот контракт).
- **Линковка:** драйвер инъектит `run_id` в env воркера (`ARTIFEX_RUN_ID`) → воркерская запись
  P1.1 несёт `run_id` (поле nullable: ручной запуск → `null`, Artifex-порождённый → set).
- **Backstop:** драйвер БЭКФИЛЛИТ пер-плановую запись ТОЛЬКО когда воркер упал до close-протокола
  (crash/timeout/quota-abort → `result=blocked/escalated`) — единственный случай прямой записи
  драйвером в пер-плановый (роль backstop-хука D21). Так D24 «пишет в оба» соблюдается без
  двойной записи одной строки.

**Общие поля (контракт-ожидание к схеме P1.1, contract-first §5):** `ts`, `plan_id`, `item_id`,
`command`, `result`, `session_id`, `run_id`. **If-then (Code Guidance):** если при детализации
P1.1 её схема разойдётся с событийной схемой §3 здесь — **reconcile + D# (supersedes)**, НЕ тихая
подгонка одной из схем. Требование фиксируется здесь как контракт-ожидание; полный reconcile — при
детализации P1.

## 7. Композируемость (D11) и границы v1

- **Композиция (закладывается сейчас, включается v2).** `state.parent_run_id` + поле
  `parent_run_id` события `run_started` допускают ссылку дочернего прогона на родительский:
  корневой Artifex (оркестр-план экосистемы, сингтон AXIOMA-ORCHESTRA) ведёт item «проект X до
  стадии Y» = дочерний прогон Artifex со СВОИМ run-folder, ссылающимся на родительский `run_id`.
  «Доклад ребёнка» = его `handoff.md`+журнал, парсимые тем же контрактом P0.2. Схема НЕ ЗАКРЫВАЕТ
  иерархию — но механизм запуска дочерних прогонов НЕ вводится в v1 (OQ-4, v2 после пилота P6.3).
- **Дом `runs/` (решено, не TBD).** По умолчанию — **внутри проекта-цели, рядом с `plans/`**
  (`<проект>/runs/<дата-код>/`): прогон привязан к плану, durable вместе с репо проекта, resume
  работает из проекта, зеркалит канон дома `plans/` (plan-protocol). Корневой прогон
  оркестр-плана держит `runs/` там же, где singleton-план (корень vault `plans/` → корень
  vault `runs/`); дочерние — в своих проектах, кросс-линк по `parent_run_id`. **Центральный**
  единый store у Artifex — отвергнут (оторвал бы состояние от репо-цели, усложнил бы
  resume-по-папке и композицию); допускается лишь как явное исключение с обоснованием, дефолт —
  проектный.
- **Ralph/Gas Town — референс, не донор кода (D17б).** Ralph layout (`events-*.jsonl`↔`reports/`,
  `tasks.jsonl`, termination-контур) — ШАБЛОН структуры; его эвристика similarity ≥90% — в P5.1.
  Роли Gas Town (Witness≈проектный, Deacon≈корневой) — референс зон D11. Целиком не тащим (свой
  тяжёлый мир; SSOT = plan-protocol). **CC Tasks** как очередь items — отвергнут (P0.4 №6:
  `~/.claude/tasks` не first-party примитив) → очередь драйвера = плановые items из Status Board,
  своя (P2).
