## 3. Находки

### F1 — раздел «Входы активных планов» указывает на АРХИВНЫЙ план (3 записи)

`roadmap/README.md:47` объявляет три записи входами «активных планов» и запрещает их трогать
«вне их items». Названный план — `ECO-OPT`. Факт на `ebd42655`:

- каталог плана — `plans/archive/2026.07.25-ECO-OPT/` (заархивирован);
- `## 0. Meta` → `Status | 🟠 Done with deviations`;
- `## 4. Status Board`: `P4 … 1/3 … 🟠`, `P7 … 1/6 … 🟠` — колонка считает только 🟢;
  поимённо все items ОБЕИХ фаз терминальны (`🟢`/`🟠`), незакрытых нет.

Значит запись раздела ложна не «работа не доделана», а сильнее: **у трёх файлов сегодня нет
живого потребителя вовсе**, а заголовок раздела утверждает обратное. Для инварианта фазы это
именно отсутствие адреса: «вход плана, которого больше нет» адресом не является.

Что обязана сделать P7.3 (и чего не может решить этот синтез): по каждому из трёх файлов
свериться с Completion Notes закрывших его items ECO-OPT и присвоить класс — `closed-by-item`
(тогда файл удаляется, строка уходит в §«Закрыто и удалено» с указанием на архив),
`deferred-with-criterion` (остаток с критерием, который либо есть в самом файле — у
`2026.07.25-memory-hub-service.md` это §12, — либо его нет и тогда это вопрос владельцу) или
`rejected`.

### F2 — `upstream-notify-diet-fork.md`: критерий неструктурный и, вероятно, сработал

Критерий записан прозой: «диета-фаза упирается в notify-скилл, который жалко сжимать без
гарантии сохранности». Проверяемого события в нём нет (сравнить с №17/18: «повтор на ещё одном
проекте» — счётчик). При этом диета-фаза в этом плане **существует**: P3.4 отбирает скиллы под
`context: fork` по пинованному критерию D26, а P3.5 сжимает описания. То есть условие
формулировки, похоже, наступило — но ни один item плана этот файл своим не называет.

Разрешение — не в P7: правило плана (`plan.md` §2) гласит, что запись удаляет ЗАКРЫВШАЯ её
фаза. Если сверка с вердиктом P3.4 покажет, что запись закрыта, это **находка против P3**, а не
работа P7; P7.3 её фиксирует и предъявляет, но сам файл не трогает.

### F4 — карта приписала P3.5 два закрытия, которых нет в её ТЗ (найдено свипом `finish`, 2026-07-31)

Строки 3–4 первой редакции карты несли класс `closed-by-item` с носителем «`phases/P3.md` §P3.5».
Сверка со спецификацией item'а показала обратное: `Files`/`Deliverables`/`Validation` P3.5 не
содержали ни удаления файлов, ни правки `roadmap/README.md`, а `Scope Excluded` фазы P3 прямо
отдаёт выбор рычага Codex-фолбэка владельцу с адресом **P7.1**. Носитель класса был НАЗВАН, но
не проверен — тот самый класс дефекта, который карта заводилась предотвращать.

Разрешение (**D57**): `skill-description-quality.md` — `deferred-with-criterion` со структурным
критерием «непустой burn-down» (P3.5 правит только Статус записи);
`codex-skill-listing-fallback-overflow.md` — адрес P7.1, гейт владельца **OQ-8**. Счёт
`closed-by-item` 9 → 7; правка разошлась в контракт-блок P7, `Inputs` P7.3 и §2 этой карты.

### F3 — coupling-таблица пропустила фазу P2

`research/01-user-intent.md` §4 в строке `roadmap/**` пишет «Главный hotspot: **пять** фаз
удаляют/правят записи одного каталога» и перечисляет **четыре**: P1, P3, P5, P7. Пятая — **P2**:
item P2.4 удаляет `roadmap/mcp-config-example-emit.md` (`phases/P2.md` §P2.4). Тот же перечень
воспроизведён в D10. Само число «пять» в тексте выдаёт, что фаза выпала при переписывании
списка, а не была исключена решением.

Последствие ограниченное (правило «удаляет закрывшая фаза» действует независимо от того,
перечислена ли фаза), но D10 — носитель coupling-поверхности, по которому автор поздней фазы
проверяет, не заденет ли он чужую правку; неполный перечень делает эту проверку неполной.

## 4. Словарь классов адреса (закрытый)

Инвариант фазы («ноль записей БЕЗ адреса») проверяем, только если «адрес» — не оценка. Пять
классов, каждый со своим НОСИТЕЛЕМ и своим следом в каталоге:

| Класс | Что означает | Носитель | Судьба файла |
|:--|:--|:--|:--|
| `closed-by-item` | запись закрыта item'ом плана | `Scope Included`/`Files`/`Deliverables` того item'а | файл удалён закрывшей фазой + строка в `README` §«Закрыто и удалено» |
| `moved` | предмет переехал в профильный пакет | целевой `docs/roadmap.md` пакета | файл удалён, строка `README` указывает новый дом |
| `decided` | владелец вынес вердикт «не делаем» | D-запись плана + строка `docs/rejected-optimizations.md` | файл удалён, строка `README` §«Закрыто и удалено» с указанием на D# |
| `deferred-with-criterion` | отложено; возврат — по СТРУКТУРНОМУ критерию (событие/порог/счётчик) | строка `README` со Статусом = ровно ОСТАТОК | файл остаётся |
| `rejected` | отклонено ранее решением с записанным основанием | строка `docs/rejected-optimizations.md` + `⛔` в `README` | файл остаётся стабом |

**Структурность критерия** — не украшение: «повтор на ещё одном проекте», «10+ скриптов»,
«≥20 закрытий с <25 % вмешательств» проверяются счётом; «когда будет удобно» не проверяется
никогда и означает отсутствие адреса. Ровно этим F2 отличается от №17–19.
