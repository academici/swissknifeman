# Roadmap: lifecycle-aware exact isolation for Laravel parallel tests

**Статус:** ⬜ к внедрению. **Дата инцидента:** 2026-08-14.
**Владельцы:** `packages/skiller/skills/laravel-testing/test-isolation-guard`
(канонический skill и snippets); минимальная проверка delivery/projection — `packages/skiller`.
**Не владелец:** конкретный application plan, его `TestCase`, его DB naming или свободная
проза агента. `packages/task` не получает Laravel-specific policy без отдельного измеренного
cross-framework основания.

## Измеренная проблема

В field execution безопасного Laravel/Pest item одновременно потребовались:

1. early guard до `RefreshDatabase`, который не позволит затронуть рабочую DB;
2. exact проверка active DB каждого parallel worker, а не suffix/regex allowlist;
3. process-scoped local filesystem до первого app-owned write.

Текущий `test-isolation-guard` описывает guard в `TestCase::createApplication()` и suffix
`_test`. Это правильно для serial fail-safe boundary, но недостаточно для exact parallel
semantics. Попытка потребовать tokenized DB на том же seam создаёт ложный конфликт: исполнитель
либо получает RED, либо, хуже, расширяет allowlist и ослабляет declared invariant.

## Подтверждённая причинная цепочка

Порядок Laravel testing lifecycle был проверен по локальному framework source:

1. `InteractsWithTestCaseLifecycle::setUpTheTestEnvironment()` вызывает
   `refreshApplication()`, а значит и project `TestCase::createApplication()`;
2. только затем `ParallelTesting::callSetUpTestCaseCallbacks($this)` запускает callbacks;
3. framework `TestDatabases` в таком callback создаёт/выбирает worker DB и
   `switchToDatabase($testDatabase)`;
4. лишь после этого `setUpTraits()` вызывает `RefreshDatabase::refreshDatabase()` и его
   `migrate:fresh`.

Следовательно, `createApplication()` не может честно требовать уже tokenized DB: на этом
seam существует только canonical bootstrap DB. Зато
`ParallelTesting::setUpTestDatabaseBeforeMigrating()` получает exact selected DB после switch,
но до первой migration/write. Это единственный framework-owned seam для строгой parallel DB
assertion без race и without a widened naming rule.

## Целевое компактное правило skill

Skill не должен хранить project DB names или предписывать конкретный runner. Он обязан разделить
три границы и назвать правильный hook:

| Boundary | Где проверяется | Что доказывает |
|:--|:--|:--|
| Bootstrap | `phpunit.xml` + bootstrap до autoload | `APP_ENV`, canonical serial DB и safe cache/session/queue sources записаны в `$_SERVER`, `$_ENV`, `putenv()` |
| App boot | `createApplication()` | resolved config не указывает на non-test DB; filesystem policy ещё не может обращаться к remote disk |
| Parallel DB | `setUpTestDatabaseBeforeMigrating()` | resolved connection равен framework-selected DB для **этого** active token, до PDO/migration |
| Parallel filesystem | `setUpProcess()` + testing config boundary | каждый writable app disk имеет normalized local process root; no symlink/path escape or remote fallback |

Serial exact name и parallel name строятся одним project-provided deterministic resolver. Skill
не принимает `_test` regex как доказательство parallel correctness и не предлагает hard-coded
`<app>_test_test_<token>`: framework/version integration обязан передать observed selected name
из callback. Любое отсутствие seam, token or observed DB — fail closed with a named
`FRAMEWORK_LIFECYCLE_CONFLICT`, not a broadened allowlist, fallback to dev DB or silent skip.

## Предлагаемая реализация

1. Обновить canonical `test-isolation-guard/SKILL.md` и snippets. Явно разделить serial
   `createApplication` guard и exact parallel callback; убрать рекомендацию suffix-only как
   достаточную для parallel mode.
2. Добавить tiny reusable snippet/contract shape: project supplies canonical serial DB resolver,
   receives `database`/`token` only from `setUpTestDatabaseBeforeMigrating`, compares the
   observed resolved connection exactly, and reports Russian remediation text.
3. Сделать filesystem snippet lifecycle-aware: root derives from validated process identity,
   is normalized/realpath-checked under project testing base, each writable app-owned disk is
   rewritten to local configuration before use, and teardown may delete only that owned root.
   `Storage::fake()` remains an explicit behavior-test fake, never the global safety boundary.
4. Добавить concise stop branch to the skill: if project requirements demand exact token proof
   but the framework lifecycle/version cannot supply a pre-write callback, stop implementation
   and record a structured lifecycle conflict. Do not invent a regex or relax `RefreshDatabase`.
5. Regenerate all derived marketplace/Codex projections from the canonical skill and add a
   source-versus-projection freshness check.

## Regression fixtures and acceptance

- A minimal Laravel fixture proves the lifecycle order above. Its serial test sees canonical DB
  at app boot; its parallel test observes the framework-selected DB in the before-migrating
  callback; `RefreshDatabase` is invoked only after the exact check.
- A deliberate non-test DB and a malformed/absent token fail before connection/migration. A DB
  with a merely matching suffix but wrong active token also fails.
- Two parallel workers receive different normalized filesystem roots. Attempts to use a remote
  disk, escape with `..`, or traverse a symlink fail before a write; owned-only cleanup leaves
  a sentinel outside the process root untouched.
- Serial guard remains compatible with `RefreshDatabase`; no change silently weakens its existing
  dev/prod protection.
- Snippet test runs validate PHP syntax and framework behavior on the supported Laravel range.
  Canonical skill, generated Codex projection and installed marketplace fixture expose the same
  lifecycle rule.

## Non-goals

This is not a generic rewrite of `packages/task`, a universal database naming convention, a
replacement for project DB preflight, or permission to bypass framework facilities. It does not
make every agent infer a framework lifecycle from prose; it gives the Laravel skill a small,
tested decision table and a fail-closed outcome for unsupported integration shapes.

## Trigger for implementation

Implement when the next change touches `test-isolation-guard`, its snippets, or a related
Laravel parallel-testing integration. The field incident is already sufficient evidence; no
second project must be put at risk to justify the regression fixture.
