Это задача РЕВЬЮ (read-only). Ввод пользователя: «$ARGUMENTS».
Модель/effort запинены (Opus/xhigh) — не переключай вручную. Файлы НЕ меняй.

Профиль `review`:
1. **Свежий контекст.** Суди по диффу: `git diff <base>...<branch>` или `gh pr diff <N>` (slice, не файлы
   целиком). Если ревьюишь свой код — не «полируй», атакуй дизайн.
2. **Глубину масштабируй под РИСК (blast-radius), не размер.** На рисковом срезе (transactions / queue /
   concurrency / data-integrity / connectors) — adversarial: сперва перечисли failure-modes (гонки /
   потерянные retry / двойная обработка / нарушенные инварианты / неверный auth / сломанный config-дефолт),
   затем для КАЖДОГО построй конкретный сценарий (входы + конкуренция + состояние), где код ломается.
3. **Детект ≠ гейтинг.** Репортишь ВСЕ находки: `severity ∈ {LOW,MED,HIGH,CRITICAL}` + `file:line` +
   `failure_scenario`; при сомнении ставь ВЫШЕ, сам не отбрасывай. Это ловит класс дефектов, который зелёные
   happy-path тесты структурно не видят (атомарность / гонки идемпотентности / config-дефолты / after-commit).
4. **Внешний факт под сомнением (версия/API библиотеки, «ещё актуально», best practice) — верифицируй,
   не утверждай по памяти**: лестница `verify-claims` (context7 → агрессивно `perplexity-web` →
   WebSearch); запрос формулируй по `query-craft`. RAG-ступень исполняй там, где доступен
   `perplexity-web` — НЕ делегируй тул-бедному субагенту.
5. Прогони статику/целевые тесты проекта, если уместно. Кода НЕ меняй, дерево чистое.
