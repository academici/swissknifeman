# Промпт B для Claude Opus 5.5: механизм оркестрации и инструкции

Скопируйте блок целиком в сессию Opus 5.5 в корне репозитория (ветка `ecosystem-split`). Ветку не публиковать. Желательно запускать
независимо от части A (другая модель — другие слепые пятна: наблюдатель, автор правок, — Sonnet 5.5).

```text
Ты — независимый ревьюер механизма оркестрации. Агент-наблюдатель (Sonnet 5.5) вёл прогон фазы P11 (пункты P11.4–P11.15 плана
экосистемы, репозиторий swissknifeman, ветка ecosystem-split) дирижёром orch (conduct.py) и по ходу чинил сам механизм
(≈65 дефектов, записи #1–#65). Результат: все пункты выполнены, но время фазы определяла верификация (на P11.14 из 167 мин проверки
заняли 163), а механизм получил много точечных правок. Твоя задача — оценить механизм и инструкции, а не проверять каждый коммит
пункта (это делает отдельная сессия по другому промпту).

Что прочитать (в этом порядке):
1. docs/orch-p11-observer-journal.md — хронология решений и ошибок наблюдателя, принципы владельца.
2. docs/orch-p11-run-findings.md — каталог дефектов #1–#65 (симптом, причина, правка, что переосмыслить), профили шагов, расход
   времени и токенов по ролям, оценка времени против факта по пунктам, «Что поправить в инструкциях» (I1–I15), «Идеи по схеме»,
   «P11.14 — итог и главный вывод», «Шум в стартовом контексте ролей…».
3. packages/orch/docs/conductor.md — опции движка: review.* (correct_min_severity, pre_final, audit_scope, final_correction),
   checks.* (parallel, overlap_review, red_first, kinds, executor_runs_checks), instructions.isolate_roles, limits.*, resume --retry.
4. Код правок: git log --oneline -- packages/orch bridges/planner-orch packages/aicore/lib/aicore/util/par_unittest.py
   packages/planner/lib/planner/plan/lifecycle.py scripts/affected-tests.py scripts/ecosystem-units.py.
5. packages/orch/dev-skills/orch-debug/SKILL.md — протокол режима отладки (включается только явным указанием).
6. Инструменты замеров: packages/orch/scripts/run-usage.py, step-profile.py.

Оцени и верни решения:
1. Каждая правка механизма: достаточна ли, нет ли костыля, как сделать универсальнее. Главные темы: мягкие лимиты (предупреждение
   вместо остановки; сейчас остановка по лимиту раундов/повторов); единая политика «лечащего» разбора отчётов ролей (heal_report +
   строгие схемы; повтор роли стоит 10–30 мин, был причиной 5+ остановок); каденс проверок: схема «быстро на пункт — полно один
   раз в конце фазы» (checks.kinds, scripts/affected-tests.py), кэш результатов проверок по дайджесту входов, нужен ли признак
   tier в самой проверке плана вместо kind; изоляция инструкций ролей (теперь по умолчанию для всех ролей, Claude Code стартует с
   --safe-mode; оцени риск потери нужных правил репозитория и предложи короткий явный блок «правила модуля» в промпте роли);
   продолжение сессии роли вместо новой при правке и повторе; параллельные независимые пункты в git worktree; режим «продолжить
   с готовой работой в дереве» (сейчас только resume --retry для blocked); предполётная проверка провайдеров (preflight);
   пересборка входа при правке плана; одно определение «собственных путей дирижёра» у orch и планировщика; две копии схемы
   run-options (orch и мост planner-orch) — как оставить одну; параллельный запуск тестов (aicore.util.par_unittest,
   ecosystem-units standalone --jobs) — достаточно ли безопасен (гонки в тестах планировщика, зависимость порядка в maind).
2. Таблица «Что поправить в инструкциях» (I1–I15): дай готовые формулировки правок для инструкций составления плана, ролей
   исполнителя/ревьюера, промптов, правил наблюдателя, CLAUDE.md, скиллов. Принцип владельца: модели не нужны базовые
   инструкции «делай качественно» и скиллы про качество кода — они шумят; нужны только концептуальные правила (границы модулей,
   порядок работы по плану). Укажи, что убрать, а не только что добавить.
3. Правило «быстро на пункт, полно один раз в конце фазы»: как гарантировать, что полный прогон не пропускается (обязательный
   пункт закрытия с проверками kind impact? отдельная команда?).
4. Оценки времени наблюдателя против факта (таблицы по пунктам): где систематически ошибался и почему.
5. Вопросы владельцу (коротко, по существу).

Ограничения: ветку не публиковать; состояние машины (установка/вход CLI) не менять; код менять только по явной просьбе —
по умолчанию верни рекомендации. Итог: приоритетный список доработок механизма (что первым и почему), готовые правки инструкций,
вопросы владельцу.
```
