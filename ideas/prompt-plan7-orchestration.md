## Режим
- Все пункты исполняет `orch conduct` (не Agent-цикл и не вручную, кроме шагов, которые executor физически не может: запись вне
  проекта, Playwright/backend, живое состояние машины — их делаешь ты и пишешь в журнал, почему).
- Запуск: `orch conduct run --plan "PLAN7" --items P2.1 P2.2 --batch --frozen --debug --options OPTS.json`;
  перед запуском `--dry-run`. `--frozen` обязателен, когда пункт правит сам orch. Один батч = группа пунктов одного исполнителя.
  Шаблоны options и правила ревью — в `ideas/orch-session-prompt-vaulter-plan3.md` (раздел «Ревью»): групповое ревью
  `codex/gpt-6.1-sol/xhigh` на крупных батчах (P3, P1.1), мелкие без ревью; всегда задавай `review.strategy` и `dynamic:false`.
- Дебаг: флаг `--debug`, журнал `<run>/debug/journal.md` + `metrics.md` (скилл `orch-debug`). Каждое завершение пункта, каждая
  нештатная ситуация и каждый ручной шаг — запись в журнал.
- Наблюдение: `Monitor` на строки `item end` / `run end` / `stopped` / `REFUSED` / `QUOTA` / `ITEM_BLOCKED`; периодически (каждые
  5–10 минут) загляни внутрь: `git status`, `<run>/events`, stderr executor'а, `planner plans`. Монитор живёт ≤30 мин — перепоставляй.
  `ScheduleWakeup` ≤25 мин как страховка. Не опрашивай в цикле, не используй `sleep`.
- Фоновый run игнорирует SIGINT: остановка — SIGTERM по точному PID (не `pkill -f`).

## Что делаешь сам, а что фиксируешь
- **Мелкие проблемы** (опечатка, устаревший golden, красный тест из-за соседней правки, неверный флаг, отсутствие импорта) —
  чини сразу между пунктами в том же дереве, отдельным коммитом с явными путями; запиши одной строкой в журнал.
- **Большие проблемы** (дефект механизма orch/planner, архитектурное решение, расхождение с планом, что-то, что ломает несколько
  пунктов, нужное владельцу решение) — не чини на ходу: заведи файл `ideas/<короткое-имя>.md` (что произошло → причина → что
  сделано сейчас → предложение) и продолжай, обойдя проблему. Список для владельца — в финальном отчёте.
- Находки и замеры по ходу — `.swissknifeman/state/observer-plan7/findings.md` (как `observer-plan6`), в конце сведи в `docs/orch-workspace-run-findings.md`-подобный отчёт.
- Не расширяй объём пункта; чужой дефект вне пункта — заметка плана (`planner log`) с именем пункта-владельца или файл в `ideas/`.

## Жёсткие правила (уроки PLAN6)
- Коммиты только с явными путями; никогда `git add -A`, `--no-verify`, amend, `push --force`. Push — только `main` хаба и репозитории
  проектов, где в `@{u}..HEAD` лежат лишь твои коммиты (проверь `git log @{u}..HEAD`). **Не пушь vaulter**: в нём чужие коммиты.
- Живое состояние машины (P1.2, P4.1): сначала остановить все `conduct` (`ps aux | grep "conduct run"`), бэкап `tar` каталогов
  `~/.local/share/swissknifeman`, `~/.local/state/swissknifeman`, `~/.config/swissknifeman` в `~/skm-backup-<дата>/`, затем по
  одному проекту; после каждого — `workspace doctor`, `project doctor`, `planner plans` сравнить со снимком. Удалять нельзя
  (хук блокирует `rm`): только `mv` в бэкап. Одно разрушающее действие на вызов (классификатор режима блокирует циклы).
- Миграцию проекта с активным conductor/planner не делать (`MIGRATION_SOURCE_CHANGED`).
- Тесты: `python3 scripts/affected-tests.py --run` на пункт, `--tier all` на закрывающем фазу. CLI-тесты запускать с `cwd` во
  временной папке (в хабе лежит живой маркер). Playwright/e2e GUI на этой машине не запустить — вынеси в отчёт, что осталось
  прогнать владельцу.
- Шаги planner: `--actor provider/model[/effort]`; `finish` требует `--check Vn=0` на каждую acceptance-проверку (и проверки фазы на
  закрывающем пункте); `skipped` — только с принятым решением `--decision D#`; `--output json` ставится перед глаголом.
- Автоматический классификатор блокирует: `config set --machine` (проси владельца), `pkill` по шаблону, цепочки удалений.
- Executor не пишет вне проекта и не запускает Playwright: такие шаги — вручную (см. выше), с записью в журнал.
- В конце каждого пункта: коммит кода хаба, `planner finish`, `workspace sync --commit --push` (план лежит в workspace и коммитится
  отдельно от кода хаба — `planner commit` делает два коммита).
