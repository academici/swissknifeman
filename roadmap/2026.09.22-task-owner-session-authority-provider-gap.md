# Task `plan-run`: owner-gated item невозможно продолжить в Codex без внешнего attestation channel

**Дата:** 2026-09-22

**Статус:** 🟣 owner-направление принято; runtime-реализация намеренно отложена

**Field evidence:** CoreX
`2026.09.19-№1-COREX-PLATFORM-HARDENING P5.16`, Codex
`gpt-5.6-sol/xhigh`, `task:plan-run`

## Короткий вывод

Точный owner-запуск gated item успешно подтверждает plan, item, cwd, model и effort, но
не может материализовать finite owner grant в Codex. `task_contract` требует для protected
ветки `security-boundary` attestation, provider-owned verifier и независимый nonce store.
Текущий Codex adapter умеет читать только локальный thread state, сознательно маркирует его
как `workflow-guard` и не реализует verifier/nonce consumer. Результат — безусловный
`OWNER_ATTESTATION_UNSUPPORTED` до product/journal mutation.

Это безопасный fail-closed результат, но одновременно availability-дефект Task: команда и
документация предлагают exact owner invocation как путь materialization, хотя ни текущий Codex,
ни локальный Claude adapter не могут завершить этот путь. Повтор команды и новая сессия не
добавляют отсутствующую provider capability.

## Наблюдавшийся сценарий

1. Владелец запустил exact item:

   ```text
   $ task:plan-run 2026.09.19-№1-COREX-PLATFORM-HARDENING P5.16
   ```

2. Route capture успешно вернул `provider-thread-state`, правильные
   `gpt-5.6-sol/xhigh`, cwd, thread и exact invocation.
3. После промежуточного owner-сообщения materializer потребовал повторить exact invocation как
   последнюю отдельную строку. Inline-команда в поясняющем сообщении также не подошла.
4. Отдельная exact-команда прошла проверку current owner message, но
   `materialize_owner_invocation()` завершился:

   ```text
   OWNER_ATTESTATION_UNSUPPORTED: protected mode requires provider proof and an independent nonce store
   ```

5. P5.16 не получил durable start, product-файлы и journal не мутировали. Запуск новой Codex
   сессии дал бы тот же результат, потому что adapter не предоставляет требуемые функции.

## Корневая причина

Текущий authority contract смешивает два разных риска:

- разрешение владельца изменить ограниченный набор source-файлов в локальном checkout;
- доказательство права выполнить live/irreversible действие: production DDL, deploy, release,
  secret rotation, fleet operation или другой внешний эффект.

Для обоих используется один protected путь. Он корректно запрещает выдавать локальный JSONL за
криптографическое подтверждение владельца, но делает ограниченную локальную разработку полностью
неисполнимой на provider'ах без внешнего verification channel.

Технически противоречие видно в текущих владельцах:

- `packages/task/commands/plan-run.md` разрешает materialization exact owner invocation;
- `packages/task/lib/task/task_contract.py` вызывает verification с `protected=True`;
- `packages/task/lib/task/route_evidence.py` принимает protected grant только с
  `security-boundary`, verifier и nonce consumer;
- `packages/task/lib/task/route_evidence_codex.py` подтверждает current message/route, но не
  реализует `verify_owner_attestation()` и `consume_owner_nonce()`;
- `packages/task/docs/reference/plan-authority.md` честно признаёт local adapters только
  `workflow-guard` и потому фиксирует невозможность обещанного materialization path.

## Принятое направление решения

Разделить authority по требуемой границе доверия и позволить владельцу проекта выбирать более
свободный режим для bounded local source work, не выдавая его за security proof.

### 1. Два явных authority boundary

- `owner-session` — exact current owner invocation, конечные item/branch/scope, локальная source
  mutation, тестовая среда, отсутствие live/irreversible эффекта. Evidence остаётся честно
  помеченным `workflow-guard`.
- `provider-proof` — provider-owned proof и независимый nonce store. Обязателен для production,
  release, deploy, fleet, secrets, внешних необратимых действий и исполнения миграций вне
  изолированной `*_test` базы.

Строгий профиль остаётся default для внешних эффектов. Нельзя автоматически понизить
`provider-proof` до `owner-session`; допустимую границу объявляет item/project policy либо новое
явное owner-решение. Если item смешивает source edit и production action, его надо разделить.

P5.16 — показательный `owner-session` кандидат: он меняет две ещё не опубликованные migration
source files и проверяет их только на `corex_test`; фактическое применение DDL к production в его
scope не входит.

### 2. Same-session finite grant

Для `owner-session` exact invocation материализует только уже объявленные item, branch и scope,
записывает digest исходной owner-реплики и одноразовый activation key. Grant:

- не расширяет `Files`, окружение или тип действий;
- переживает additive follow-up в том же thread до первой успешной activation, чтобы владелец не
  повторял команду после каждого уточнения;
- идемпотентно повторяется после локальной transport/runtime ошибки;
- отменяется явным revoke, изменением item/branch/scope или завершением run;
- никогда не называется `security-boundary` и не удовлетворяет item, требующий
  `provider-proof`.

### 3. Capability preflight вместо цикла owner prompts

До просьбы повторить команду Task проверяет capability provider adapter. Если item требует
`provider-proof`, а verifier/nonce-store отсутствуют, возвращается один typed результат
`AUTHORITY_PROVIDER_UNAVAILABLE` с реальными вариантами продолжения. Новая сессия не предлагается
как лечение отсутствующей capability.

### 4. Настоящий strict channel остаётся отдельной поставкой

Для `provider-proof` нужен канал вне agent principal: подпись/approval token от provider UI,
owner-controlled broker или отдельный approval service с nonce store, недоступным shell/tools.
Хранить signing key рядом с Task, в repository или agent-readable filesystem запрещено.

## Acceptance

- Exact `task:plan-run` в текущем Codex thread допускает item с boundary `owner-session`, создаёт
  узкий auditable grant и продолжает product work без новой сессии.
- Additive owner-сообщение после exact invocation не заставляет повторять команду до activation;
  изменение scope или revoke по-прежнему закрывает grant.
- Повтор materialization после transport/runtime ошибки идемпотентен и не создаёт вторую Decision
  Log запись.
- Item с boundary `provider-proof` на Codex без verifier fail-closed одним
  `AUTHORITY_PROVIDER_UNAVAILABLE`; Task не предлагает бессмысленный relaunch.
- Production DDL/deploy/release/secret/fleet fixtures не принимают `workflow-guard` evidence.
- Source-only migration fixture на изолированной `*_test` базе проходит `owner-session`, но
  попытка применить ту же миграцию к non-test target требует отдельный strict grant.
- Codex и Claude projections одинаково показывают boundary, причину отказа и same-session Next.

## Границы

- Не объявлять editable transcript, route evidence или repository file доказательством личности
  владельца.
- Не ослаблять production/release/destructive authority ради удобства локальной разработки.
- Не считать любой `$ task:plan-run` глобальным разрешением; grant остаётся конечным и
  item-declared.
- Не реализовывать remediation в рамках этого roadmap update. По owner-решению проблема считается
  закрытой на уровне направления; source/runtime работа остаётся явно отложенной.

## Следующая реализация, когда владелец её возобновит

Ограниченное Task-изменение затронет authority schema/compiler, `task_contract`, provider
capability negotiation, `plan-run`/`plan-exec` canon, plan-authority docs и regression fixtures.
Отдельный master plan и новая consumer-сессия для фиксации этого решения не требуются.
