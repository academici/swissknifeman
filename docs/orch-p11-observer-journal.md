# Журнал наблюдателя: как вёлся прогон фазы P11

Хронология действий и решений агента-наблюдателя (Sonnet 5.5) при прогоне пунктов плана `2026.10.07-№1-SKM-ECOSYSTEM`
дирижёром `conduct.py`. Файл для финального ревьюера: он показывает не дефекты (их каталог — `docs/orch-p11-run-findings.md`,
записи #N), а **как работал наблюдатель**: что делал, почему, где ошибся, какие решения принимал владелец.

Время — UTC (Астрахань = UTC+4), если не сказано иное. Ссылки `#N` — записи журнала дефектов. Формат записи: **что** →
**почему** → **итог**. Журнал дописывается при каждом решении, не задним числом (ранние записи ниже восстановлены по логам
прогонов и истории сессии).

## Правила от владельца (в порядке появления)

1. Репетиция на пробном плане, затем настоящий пункт; без вопросов владельцу, без правок кода — только запуск и отчёт.
2. «Корректируй код и пробуй снова» → правки пакета разрешены; каждый пункт — одним запуском, наблюдение, разбор.
3. Лимиты токенов не нужны (только показывать); перерасход допустим как предупреждение, в разумных пределах.
4. Пункты идут по одному: после каждого — разбор механизма и улучшения, потом следующий.
5. Ревью по уровням: правятся только Major+, Minor/Nit откладываются в план на фазовую зачистку, повторный аудит —
   предфинальный и ищет только Major+.
6. Работающий результат не сбрасывать и не рубить из-за времени; оптимизации — к следующему пункту (#15, #16).
7. Улучшения вносить сразу и «без костылей»: настраиваемые опции пакета со схемой, документацией и тестами.
8. Вести журнал дефектов и этот журнал; в конце — промпт для Opus 5.5 со ссылкой на файлы.
9. Тезис: ничего не должно обрываться, если оно делает полезную работу; всё должно быть оптимально; наблюдатель
   работает как тим-лид (распределяет, следит, исправляет).

## Открытые вопросы к финальному ревьюеру

См. раздел «К разбору» каждой записи журнала дефектов и последний раздел «Идеи по схеме» там же: мягкие лимиты,

человекочитаемые ошибки схем и самопроверка отчёта.
