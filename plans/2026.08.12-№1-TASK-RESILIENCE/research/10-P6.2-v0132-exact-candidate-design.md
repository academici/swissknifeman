- `findings/25-P6-v0131-exact-validation-audit.md` — exact `v0.13.1` Task gate reproduction.
- `findings/26-P6.2-v0132-design-preflight.md` — owner resolution, tag anchors and current-tree facts.

## Exact candidate construction

The failure came from qualifying a product commit while silently overlaying plan bytes committed
later. The v0.13.2 sequence therefore separates three commits and never overlays a detached tree:

1. **Design/pre-candidate bookkeeping commit.** Commit the owner response, D29, rewritten P6.2
   spec, execution-start return-loop qualification, generated decisions/state/status and byte-fresh
   bundle before release bytes change. The qualification is a record-only preflight finding, not a
   second audit or reviewer judgement.
2. **Exact release candidate commit.** From a clean tree, bump canonical Task version sources to
   `0.13.2`, regenerate provider-owned outputs, cut `[Unreleased]` into `[0.13.2] - 2026-08-13`,
   regenerate P6.2 bundle after any execution-start carrier change, and commit once. Record this
   exact SHA; failed candidates are never tagged or amended into a false green claim.
3. **Post-candidate evidence commit.** Only after every gate is green in a clean detached worktree
   at the exact SHA, create annotated `v0.13.2`; then add a separate v0.13.2 capsule/finding and terminal
   state. These self-referential outputs are intentionally outside the tag target and must say so.

The candidate itself contains a byte-fresh P6.2 spec/bundle/state and the already committed
`8775852` delivery repair. The later capsule binds the candidate commit/tree, candidate carrier
digests, command exits, new tag object/peel and unchanged v0.13.0/v0.13.1 anchors. No candidate
gate may read current-worktree overlays or post-candidate plan files.

## Failure and rollback rules

- Any non-zero gate forbids `v0.13.2`, green capsule claims and terminal P6.2. Repair forward in a
  new commit, regenerate affected carriers, and re-run the full exact-SHA matrix.
- If `v0.13.2` appears before this execution, or either old tag anchor differs, stop as a safety/
  authority boundary; never delete, force-update or recreate a tag to make the checks pass.
- Push, GitHub release and registered rollout have no authorization. P6.3/P6.4 evidence is immutable
  historical evidence and is not rewritten to mention v0.13.2.

## Pre-mortem

Assume v0.13.2 is rejected six months later:

| Failure mode | Early signal | Mitigation | Owner |
|:--|:--|:--|:--|
| Candidate was qualified with current-worktree plan overlays | detached SHA lacks the bundle/state digest recorded as green | run every gate inside a newly created detached worktree; capsule records candidate-side carrier digests | P6.2 executor |
| Journal/state changed after the last bundle build but before candidate commit | return-loop qualification, `plan-views.py bundle --check` or Task validate fails on exact SHA | persist execution-start preflight/state/status and qualification before product bytes; rerun bundle generator/check immediately before candidate commit | P6.2 executor |
| Old release history was silently rewritten | v0.13.0/v0.13.1 object or peeled commit differs from finding 26 | verify both anchors before and after; mismatch is safety stop, never tag deletion/force-update | P6.2 executor |
| A long validator was counted green after transport dropped its exit | no reconciled PID/output/final exit for one gate | retain exact command/exit evidence and reconcile process state; unknown is non-green and forbids tag | P6.2 executor |
| Canonical version and generated provider outputs diverged | renderer/registry/docs checks report drift | update canonical sources first, regenerate through owner, require all `--check` gates on exact SHA | P6.2 executor |
