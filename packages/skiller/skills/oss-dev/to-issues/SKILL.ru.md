# To Issues

Разбить план на независимо-«хватаемые» issue с помощью вертикальных срезов (tracer bullets).

> **Конфиг трекера.** Перед публикацией нужны: репозиторий-трекер и словарь triage-лейблов. У нас
> это `gh` + лейблы конкретного репо (а не `/setup-matt-pocock-skills`). Если набор лейблов неясен —
> уточни у мейнтейнера или возьми из `oss-dev/github-flow`.

## Процесс

### 1. Собрать контекст

Работай с тем, что уже есть в контексте разговора. Если пользователь передаёт ссылку на issue (номер issue, URL или путь) как аргумент, забери её из трекера задач и прочитай полное тело и комментарии.

### 2. Изучить кодовую базу (опционально)

Если ты ещё не изучал кодовую базу, сделай это, чтобы понять текущее состояние кода. Заголовки и описания issue должны использовать словарь доменной терминологии проекта (`CONTEXT.md`) и уважать ADR в области, которую ты затрагиваешь.

Ищи возможности предварительно отрефакторить код, чтобы упростить реализацию. «Сделай изменение лёгким, а потом сделай лёгкое изменение» («Make the change easy, then make the easy change»).

### 3. Набросать вертикальные срезы

Разбей план на issue-**tracer bullet**. Каждая issue — это тонкий вертикальный срез, который проходит сквозь ВСЕ слои интеграции от начала до конца, а НЕ горизонтальный срез одного слоя.

<vertical-slice-rules>

- Каждый срез доставляет узкий, но ПОЛНЫЙ путь через каждый слой (схема, API, UI, тесты)
- Завершённый срез можно продемонстрировать или проверить сам по себе
- Любой предварительный рефакторинг (prefactoring) должен быть сделан первым

</vertical-slice-rules>

### 4. Опросить пользователя

Представь предложенное разбиение как нумерованный список. Для каждого среза покажи:

- **Title** (Заголовок): краткое описательное имя
- **Blocked by** (Заблокировано): какие другие срезы (если есть) должны завершиться первыми
- **User stories covered** (Покрытые пользовательские истории): какие пользовательские истории это адресует (если они есть в исходном материале)

Спроси пользователя:

- Ощущается ли гранулярность правильной? (слишком крупно / слишком мелко)
- Корректны ли отношения зависимостей?
- Нужно ли какие-то срезы объединить или раздробить дальше?

Итерируй, пока пользователь не одобрит разбиение.

### 5. Опубликовать issue в трекер задач

Для каждого одобренного среза опубликуй новую issue в трекер задач (через `gh issue create`). Используй шаблон тела issue ниже. Эти issue считаются готовыми для AFK-агентов (работающих в режиме «отошёл от клавиатуры»), поэтому публикуй их с правильным triage-лейблом, если не указано иное.

Публикуй issue в порядке зависимостей (сначала блокеры), чтобы можно было ссылаться на реальные идентификаторы issue в поле «Blocked by».

<issue-template>
## Parent

Ссылка на родительскую issue в трекере задач (если источником была существующая issue, иначе опусти эту секцию).

## What to build

Краткое описание этого вертикального среза. Описывай сквозное поведение от начала до конца, а не послойную реализацию.

Избегай конкретных путей к файлам или фрагментов кода — они быстро устаревают. Исключение: если прототип произвёл фрагмент, который кодирует решение точнее, чем это может проза (стейт-машина, редьюсер, схема, форма типа), вставь его прямо здесь и кратко отметь, что он пришёл из прототипа. Обрежь до частей, насыщенных решением, — это не рабочее демо, а только важные кусочки.

## Acceptance criteria

- [ ] Критерий 1
- [ ] Критерий 2
- [ ] Критерий 3

## Affected projects

Список затронутых репозиториев, если срез касается нескольких проектов экосистемы (иначе опусти секцию).

## Environment

Где проявляется/проверяется: production / staging / конкретное устройство (POS, фискальник). Опусти, если неприменимо.

## Blocked by

- Ссылка на блокирующий тикет (если есть)

Или «None - can start immediately» (Нет — можно начинать немедленно), если блокеров нет.

</issue-template>

НЕ закрывай и не изменяй никакую родительскую issue.

## Связанные скиллы

- `oss-dev/github-flow` — общий поток Issue→PR→Release (обязательная зависимость).
- `general/spec-interview` / `general/grill-with-docs` — откуда берётся план/ТЗ для разбиения.
- `general/implement` — следующий шаг: реализация по опубликованным issue (этот скилл `produces_for` его).
- `oss-dev/issue-triage` — стейт-машина обработки уже существующих issue/PR.
