с glob `*.zzp31paths` скилла `zz-p31-paths`. Все остальное (набор скиллов, флаги,
изоляция, величина оси A) наследуется от P3.1 без изменений

## 2. Механизм

Механизм: (C) условная загрузка

**Уточнение относительно решающей таблицы `research/11-…md` §5, строка 1.** Строка 1
предполагала, что триггер — сам факт совпавшего файла В ДЕРЕВЕ (A1 delta ≈ +88 и B1 дают
маркер). Оба этих буквальных условия НЕ выполнены: A1 — неразличимо, B1 — `Unknown
command`. То, что выполняется буквально, — воспроизводимая, идентичная в обоих прогонах
разница между **B1** (файл лежит, explicit ломается) и **B2** (файл лежит И сессия его
прочла, explicit работает): единственная переменная между этими двумя плечами — факт
чтения файла, и она категорически (не «около», а `Unknown command` → маркер) переключает
результат в обоих независимых прогонах. Это — прямое, буквальное подтверждение
first-party строки дока (`findings/P3.1-paths-escalation-rag-2026-08-01.md` §1): «loads
the skill automatically only **when working with files** matching the patterns» — «working
with», а не «lying in the tree». Вердикт по НАБЛЮДЕНИЮ (Code Guidance «Анти-самообман»):
`Unknown command` → `ZZP31-PATHS-BODY`, byte-в-байт, дважды.

Ни одна из оставшихся трёх строк решающей таблицы не описывает этот результат точнее:
«(A) баг жив» несовместима с воспроизводимым B1→B2 переключением; «смешанный»
(в терминах §5 — запись ВОЗВРАЩАЕТСЯ в листинг, но explicit остаётся сломан) описывает
противоположную по полярности комбинацию; «прибор не различает» опровергается тем, что
5 из 6 плеч (A1, A2, B0, B1, B2) дали идентичную классификацию в обоих прогонах —
нестабильно только B3.

## 3. Что этим НЕ доказано

- **Резидентная запись листинга** (ось A) НЕ возвращается ни в одном из проверенных
  состояний — ни при простом присутствии файла (A1/B1), ни было отдельно проверено
  состояние «файл прочитан» под LISTING_PROMPT (A1 не включал инструкцию читать файл).
  Практический вывод для авто-обнаружения (не явного вызова): скилл с `paths:` остаётся
  вне листинга даже когда совпадающий файл лежит в дереве — модель не может «сама
  наткнуться» на него через резидентный список, только если ей УЖЕ известно имя скилла
  (как в B2/B3, где имя присутствует в промпте).
- **Авто-активация по одной триггер-фразе после чтения файла** (B3) — неразличимо
  (расхождение прогонов), не подтверждена и не опровергнута этим item'ом.
- **Personal-слой** не проверяется этим стендом (`CLAUDE_CONFIG_DIR` запрещён D94) —
  свидетельство по личному слою берётся из репро #49835 (2.1.92, чужой замер, не наш).
- **Плагин-канал (`connect`)** этим item'ом не проверяется — адрес P3.2 при исходе (C).
- **`background: true`/`false`** не различается однопроходным `claude -p` (граница P3.1,
  в силе).
- Механизм переключения B1→B2 (что именно у клиента регистрирует slash-команду после
  чтения файла — тот же ли путь, что описан доком для авто-активации, или соседний)
  не инструментирован глубже наблюдаемого `result`; внутренняя реализация клиента —
  `[UNVERIFIED]`.

## 4. Вход для P3.2 (ветка OQ-2)

Решающая таблица адресует выбор ветки P3.2 (Scope Excluded этого item'а). Фактура: (C)
подтверждена буквально доком, но с более узким условием, чем «файл в дереве» — «файл
прочитан в сессии». Для АВТО-роутинга (весь смысл резидентного листинга) это условие
недостижимо циклически: модель не читает файл, который не знает искать, если скилл не
листится. Для ЯВНОГО вызова по известному имени, ПОСЛЕ того как файл уже был прочитан
по другой причине, — вызов работает.
