# Feedback loop from field work (improvement loop)

Internal skill (not exported). Direct consequence of CLAUDE.md's thesis "we implement a feature
**on measured need**, not preemptively" (the same principle governs deferred ideas): **field work on
projects IS the measurement**. Many projects, each with its own specifics; a deviation caught on
one project is captured here so the ecosystem learns it instead of losing it.

## When to activate

- Implementing/integrating/syncing/onboarding a project with ecosystem tooling (`skiller
  connect|vendor|integrate`, `maind onboard|sync|health`, `harness`, `swissknifeman
  setup|doctor`) — **and reality diverged from what was promised**.
- Any deviation from an instruction: the runbook/doc/skill says X, the tool does Y; a step
  fails; the result isn't right; "had to work around it by hand".
- Someone **reports** "ran setup on project Z — it broke/behaved strangely".

## Rule (classify the deviation → route)

First — **what exactly deviated** (that's the "measured problem" itself): the package's code? a
generated artifact? the instruction itself (doc/skill/runbook is stale)? project Z's specifics
that tooling didn't account for?

1. **Obvious bug / clear repo improvement** — behavior is unambiguously wrong, or the fix is
   trivial and local (a logic typo, a bad path, a forgotten case, a stale doc/skill sentence). →
   **Fix immediately**:
   - package code → fix + test;
   - instruction is stale → fix the doc/skill ([docs-maintenance] / [skill-authoring],
     canonical EN-only `SKILL.md` source);
   - a generated artifact is **never hand-edited** — fix the generator instead (see
     [package-architecture]).
   Close out via [release-discipline] (validate → registry → CHANGELOG → PR).

2. **Genuinely new / uncertain** — not sure it's a bug (may be by design, or your own
   mistake/project specifics); or it's a new capability, not a one-step fix. →
   **Don't implement speculatively.** Propose it for follow-up:
   - first turn the doubt into a fact: repo-grounded → confirm by reading code; external ("the
     library already does this", "not done that way anymore") → [decision-verification];
   - **capture it in repository artifacts** so it survives working-memory expiry: what was
     observed, on which project, and the evidence. Only an unresolved temporary blocker belongs
     in `maind memory remember --type blocker --ttl-hours 48`; default scope is project-private;
   - give it a receiver: an explored direction → a roadmap note (with an **"adoption
     criterion"** field); a concrete actionable defect/request → a GitHub issue (`gh issue
     create`, repo `academici/swissknifeman`).

Boundary: fix — when behavior is unambiguously wrong **and** the fix is local. Uncertain about
either — path 2 (propose), not "quietly patch the library for one project".

## Anti-patterns

- Silently work around a deviation in the current project and forget it (specifics not
  accounted for → will recur).
- "Fixing" the library for something that's actually correct, or only true for project Z.
- Dragging a new feature in speculatively instead of a roadmap note with an adoption
  criterion.
- Hand-editing a generated artifact instead of the generator.
