## 2. Спецификации фич и PRD

### 2.1 Выбор правильного формата PRD

| Шаблон | Сценарий применения | Размер команды | Сроки |
|----------|----------|-----------|----------|
| Стандартный PRD | Сложные фичи, кросс-командные зависимости | Несколько команд | 6–8 недель |
| Одностраничный PRD | Простые фичи, одна команда, быстрые итерации | Одна команда | 2–4 недели |
| Agile-эпик | Поставка по спринтам, развивающиеся требования | Scrum-команда | Постоянно |
| Бриф фичи | Фаза исследования, до утверждения | Любая | 1 неделя |

### 2.2 Структура стандартного PRD

#### Раздел 1: Постановка проблемы (Problem Statement)
- Опишите пользовательскую проблему в 2–3 предложениях
- Кто с ней сталкивается, как часто, в каком контексте
- Цена нерешения: боль пользователя, влияние на бизнес, конкурентный риск
- Доказательства: пользовательские исследования, данные тикетов поддержки, метрики, цитаты клиентов

#### Раздел 2: Цели (Goals)
- 3–5 конкретных, измеримых результатов (результаты — outcomes, не выходы — outputs)
- Различайте пользовательские цели (что получают пользователи) и бизнес-цели (что получает компания)
- Каждая цель должна отвечать на вопрос: «Как мы поймём, что это удалось?»

**Пример:**
- Пользовательская цель: сократить время выполнения ключевого сценария с 8 минут до менее чем 3 минут
- Бизнес-цель: повысить удержание новых пользователей на D30 с 38% до 52%

#### Раздел 3: Не-цели (Non-Goals)
- 3–5 вещей, которые эта фича явно НЕ будет делать
- Для каждой: кратко объясните, почему это вне скоупа
- Не-цели предотвращают расползание скоупа и задают ожидания стейкхолдеров

#### Раздел 4: Пользовательские истории (User Stories)

Формат: `Как [персона], я хочу [возможность], чтобы [выгода].`

Типы историй:

| Тип | Шаблон | Пример |
|------|----------|---------|
| Фича (Feature) | Как [персона], я хочу [действие], чтобы [выгода] | Как админ команды, я хочу настроить SSO, чтобы моя команда использовала корпоративные учётные данные |
| Улучшение (Improvement) | Как [персона], мне нужна [возможность], чтобы [цель] | Как продвинутый пользователь, мне нужны горячие клавиши, чтобы выполнять задачи, не отрывая рук |
| Исправление бага (Bug Fix) | Как [персона], я ожидаю [поведение], когда [условие] | Как пользователь, я ожидаю, что моя корзина сохранится при обновлении страницы |
| Энейблер (Enabler) | Как разработчик, мне нужно [задача], чтобы обеспечить [возможность] | Как разработчик, мне нужно реализовать кэширование, чтобы обеспечить мгновенный поиск |

**Проверка по INVEST для каждой истории:**

| Критерий | Вопрос | Проходит, если... |
|-----------|----------|------------|
| Independent (независимая) | Можно ли разработать без других незафиксированных историй? | Нет блокирующих зависимостей |
| Negotiable (обсуждаемая) | Гибкая ли реализация? | Возможны несколько подходов |
| Valuable (ценная) | Даёт ли пользовательскую или бизнес-ценность? | Чёткая выгода в части «чтобы» |
| Estimable (оцениваемая) | Может ли команда оценить размер? | Понятна достаточно хорошо для оценки |
| Small (небольшая) | Выполнима за один спринт? | ≤8 story points |
| Testable (тестируемая) | Можем ли мы проверить, что она сделана? | Чёткие критерии приёмки |

#### Раздел 5: Требования (MoSCoW)

**Must-Have (обязательно, P0):** Без этого фичу нельзя выпускать. Вопрос: «Если мы это вырежем, решает ли фича всё ещё базовую проблему?»

**Should-Have (следует иметь, P1):** Существенно улучшает опыт; базовый сценарий работает и без них.

**Could-Have (можно иметь, P2):** Хорошо включить, если позволяет ёмкость; нет задержки при вырезании.

**Won't-Have (на этот раз):** Явно вне скоупа; возможно, вернёмся.

Советы:
- Будьте безжалостны к P0. Если всё — P0, то ничто не P0.
- P1 должны быть тем, что вы уверены построить в ближайшее время.
- P2 — это архитектурная страховка: они направляют решения по дизайну.

#### Раздел 6: Критерии приёмки (Acceptance Criteria)

Формат Given-When-Then:
```
Given [предусловие или контекст],
When [действие, которое совершает пользователь],
Then [ожидаемый результат].
```

Примеры:
```
Given the admin has configured SSO for their organization,
When a team member visits the login page,
Then they are redirected automatically to the SSO provider.

Given the user has entered an invalid email format,
When they submit the registration form,
Then an inline error message displays "Please enter a valid email address."

Given the shopping cart contains items,
When the user refreshes the browser,
Then the cart contents remain unchanged.
```

Формат чек-листа (альтернатива):
```
- [ ] Admin can enter SSO provider URL in organization settings
- [ ] Team members see "Log in with SSO" button on login page
- [ ] SSO login creates a new account if one does not exist
- [ ] SSO login links to existing account if email matches
- [ ] Failed SSO attempts show a clear error message
```

**Минимальное число критериев приёмки по размеру истории:**

| Story Points | Минимум критериев приёмки |
|--------------|-----------------|
| 1–2 | 3–4 критерия |
| 3–5 | 4–6 критериев |
| 8 | 5–8 критериев |
| 13+ | Разбейте историю |

#### Раздел 7: Метрики успеха (Success Metrics)

**Опережающие индикаторы** (дни–недели после запуска):
- Уровень принятия (adoption rate): % подходящих пользователей, которые попробовали фичу
- Уровень активации (activation rate): % пользователей, выполнивших ключевое действие
- Уровень завершения задачи (task completion rate): % тех, кто успешно достиг своей цели
- Время выполнения (time to complete): сколько занимает ключевой сценарий
- Уровень ошибок (error rate): как часто пользователи сталкиваются с ошибками или тупиками

**Запаздывающие индикаторы** (недели–месяцы после запуска):
- Влияние на удержание: улучшает ли эта фича удержание пользователей?
- Влияние на выручку: ведёт ли это к апгрейдам или новой выручке?
- Изменение NPS / удовлетворённости
- Снижение числа тикетов поддержки

**Установка целевых значений:**
- Конкретно: «50% принятия в течение 30 дней», а не «высокое принятие»
- Опирайтесь на сопоставимые фичи, бенчмарки или явные гипотезы
- Задайте порог «успеха» и «амбициозную» (stretch) цель
- Определите метод измерения: инструмент, запрос, временное окно
- Укажите время оценки: 1 неделя, 1 месяц, 1 квартал после запуска

#### Раздел 8: Открытые вопросы (Open Questions)
- Помечайте каждый тем, кто должен ответить (инженерия, дизайн, юристы, данные, стейкхолдер)
- Различайте блокирующие (нужно ответить до старта) и неблокирующие

#### Раздел 9: Соображения по срокам (Timeline Considerations)
- Жёсткие дедлайны (контрактные, комплаенс, события)
- Зависимости от других команд
- Предлагаемое поэтапное разбиение для крупных фич

```
Scope → Draft → Review → Refine → Approve → Track
```

| Проход ревью | Ревьюер | Фокус |
|-------------|----------|-------|
| Реализуемость (Feasibility) | Инженерия | Технические ограничения, оценки трудозатрат |
| UX | Дизайн | Пробелы пользовательского опыта, флоу |
| Рынок (Market) | Продажи | Валидация рынка, блокеры сделок |

### 2.6 Управление скоупом

**Признаки расползания скоупа (scope creep):**
- Требования продолжают добавляться после утверждения спецификации
- «Маленькие» добавления накапливаются
- Команда строит фичи, которых никто из пользователей не просил
- Дата запуска постоянно сдвигается без явного пересмотра скоупа

**Предотвращение расползания скоупа:**
- Пишите явные не-цели в каждой спецификации
- Любое добавление в скоуп требует соответствующего удаления из скоупа или продления сроков
- Чётко разделяйте «v1» и «v2»
- Создайте «парковку» (parking lot) для хороших идей, которые вне скоупа этой версии
- Тайм-боксируйте исследования: «Если мы не разберёмся с X за 2 дня, мы это вырезаем»

## 3. Дорожная карта и приоритизация

### 3.1 Фреймворки приоритизации

#### Скоринг RICE

RICE Score = (Reach × Impact × Confidence) / Effort

| Измерение | Описание | Шкала |
|-----------|-------------|-------|
| Reach (охват) | Пользователей/клиентов, затронутых за квартал | Фактическое число (например, 5 000) |
| Impact (влияние) | Насколько сдвигает показатель на одного человека | 3 = огромное, 2 = высокое, 1 = среднее, 0.5 = низкое, 0.25 = минимальное |
| Confidence (уверенность) | Насколько уверены в оценках Reach и Impact | 100% = подкреплено данными, 80% = есть свидетельства, 50% = на ощущениях |
| Effort (трудозатраты) | Человеко-месяцы по всем функциям | Десятичное (например, 2.5) |

**Формат входного CSV для RICE:**
```csv
name,reach,impact,confidence,effort,description
Onboarding Flow,20000,massive,high,s,Complete redesign
Search Improvements,15000,high,high,m,Relevance and speed
Social Login,12000,high,medium,m,OAuth integration
Push Notifications,10000,massive,medium,m,Mobile push support
Dark Mode,8000,medium,high,s,Dark theme option
```

**Маппинг размера трудозатрат (effort):**
- xs = 0.5 человеко-месяца
- s = 1 человеко-месяц
- m = 3 человеко-месяца
- l = 6 человеко-месяцев
- xl = 12 человеко-месяцев

**Интерпретация результата приоритизации:**
- Быстрые победы (Quick wins): высокий RICE, низкие трудозатраты → Делать первыми
- Крупные ставки (Big bets): высокий RICE, высокие трудозатраты → Планировать аккуратно
- Заполнители (Fill-ins): низкий RICE, низкие трудозатраты → Делать, когда позволяет ёмкость
- Денежные ямы (Money pits): низкий RICE, высокие трудозатраты → Убрать из бэклога

**Проверка чувствительности перед финализацией:**
- Что, если оценки охвата ошибочны в 2 раза?
- Что, если оценки трудозатрат ошибочны в 2 раза?
- Меняется ли ранжирование существенно? Если да — соберите больше данных по неопределённым пунктам.

#### Фреймворк MoSCoW

| Категория | Определение | Цель спринта |
|----------|------------|---------------|
| Must have (обязательно) | Без этого дорожная карта проваливается. Не обсуждается. | Текущий |
| Should have (следует иметь) | Важно и ожидаемо, но поставка возможна и без них | Следующий |
| Could have (можно иметь) | Желательно, если позволяет ёмкость | Позже |
| Won't have (на этот раз) | Явно вне скоупа на этот период | Бэклог |

Когда использовать: при определении скоупа релиза или квартала, при переговорах со стейкхолдерами о том, что помещается.

#### Скоринг ICE

ICE Score = Impact × Confidence × Ease

- Impact (влияние): насколько это сдвинет целевую метрику? (1–10)
- Confidence (уверенность): насколько мы уверены в оценке влияния? (1–10)
- Ease (лёгкость): насколько это легко реализовать? Обратное трудозатратам — выше = легче (1–10)

Когда использовать: быстрая приоритизация бэклога фич, продукты на ранней стадии, ограниченные данные.

#### Матрица «Ценность vs. Трудозатраты» (2×2)

| | Низкие трудозатраты | Высокие трудозатраты |
|---|---|---|
| **Высокая ценность** | Быстрые победы → Делать первыми | Крупные ставки → Планировать аккуратно |
| **Низкая ценность** | Заполнители → Когда позволяет ёмкость | Денежные ямы → Вырезать |

Когда использовать: визуальная приоритизация на планёрках, формирование общего понимания.

#### Взвешенные факторы приоритизации

| Фактор | Вес | Вопросы |
|--------|--------|-----------|
| Бизнес-ценность | 40% | Влияние на выручку? Спрос пользователей? Стратегическая согласованность? |
| Влияние на пользователя | 30% | Сколько пользователей? Как часто используется? |
| Риск/зависимости | 15% | Технический риск? Внешние зависимости? |
| Трудозатраты | 15% | Размер? Сложность? Неопределённость? |

### 3.2 Форматы дорожной карты

#### Now / Next / Later

- **Now** (текущий спринт/месяц): зафиксированная работа. Высокая уверенность в скоупе и сроках.
- **Next** (1–3 месяца): запланированная работа. Хорошая уверенность в том, что, меньшая — в точных сроках.
- **Later** (3–6+ месяцев): направление. Стратегические ставки с гибким скоупом и сроками.

Лучше всего для: большинства команд, внешней коммуникации, избегания ложной точности дат.

#### Поквартальные темы

Организуйте вокруг 2–3 тем на квартал:
- Каждая тема = область стратегических инвестиций (например, «Готовность к enterprise», «Улучшения активации»)
- Под каждой темой: конкретные инициативы
- Темы привязаны к OKR

Лучше всего для: демонстрации стратегической согласованности, коммуникации с руководством, планёрок.

#### Дорожная карта, привязанная к OKR

```
Objective: [Qualitative, aspirational goal]
  └── Key Result 1: [Metric target]
       └── Initiative A: [Expected impact on KR1]
       └── Initiative B: [Expected impact on KR1]
  └── Key Result 2: [Metric target]
       └── Initiative C: [Expected impact on KR2]
```

Лучше всего для: организаций, работающих по OKR, чтобы у каждой инициативы было измеримое «зачем».

#### Каскад OKR (Компания → Продукт → Команда)

```
Company OKR
  └── Product OKR (contributes to company KR)
       └── Team OKR (contributes to product KR)
            └── Sprint Goals (contribute to team KR)
```

Оценка согласованности (alignment scoring): для каждой инициативы поставьте 0–3 за то, насколько прямо она продвигает каждый уровень OKR. Деприоритизируйте всё, что набирает 0 на уровне продукта.

### 3.3 Планирование ёмкости

**Стандартное распределение:**

| Категория | Доля | Описание |
|----------|-----------|-------------|
| Запланированные фичи | 70% | Пункты дорожной карты, продвигающие стратегические цели |
| Техническое здоровье | 20% | Техдолг, надёжность, производительность |
| Незапланированный буфер | 10% | Срочные проблемы, быстрые победы, кросс-командные запросы |

**Расчёт ёмкости:**
```
Sprint Capacity = Average Velocity × Availability Factor

Example:
Average Velocity: 30 points
Team availability: 90% (one member partially out)
Adjusted Capacity: 27 points
Committed: 23 points (85% of 27)
Stretch: 4 points (15% of 27)
```

**Факторы доступности (availability factors):**

| Сценарий | Фактор |
|----------|--------|
| Полный спринт, без отпусков | 1.0 |
| Один участник занят на 50% | 0.9 |
| Праздник в течение спринта | 0.8 |
| Несколько участников отсутствуют | 0.7 |

### 3.4 Маппинг зависимостей

**Типы зависимостей:**
- Технические: фиче B нужна инфраструктура из фичи A
- Командные: требуется работа дизайна, платформы, данных или другой команды
- Внешние: ожидание вендора, партнёра или сторонней интеграции
- Последовательные: нужно выпустить фичу A до старта фичи B
- Знаниевые: нужны результаты исследования до старта

**Управление зависимостями:**
- Перечислите все зависимости явно в дорожной карте
- Назначьте владельца каждой зависимости
- Установите дату «нужно к» (need by)
- Закладывайте буфер — зависимости это пункты наивысшего риска
- Помечайте кросс-командные зависимости заранее
- Имейте план на случай, когда зависимости срываются

**Сокращение зависимостей:**
- Можно ли построить более простую версию, избегающую зависимости?
- Можно ли распараллелить через контракт интерфейса или мок?
- Можно ли иначе выстроить последовательность, чтобы перенести зависимость раньше?
- Можно ли впитать эту работу в свою команду?

### 3.5 Коммуникация изменений дорожной карты

Когда дорожная карта меняется:
1. Признайте изменение: прямо скажите, что меняется и почему
2. Объясните причину: какая новая информация это вызвала?
3. Покажите компромисс: что было деприоритизировано? Что сдвигается?
4. Покажите новый план: обновлённая дорожная карта с отражёнными изменениями
5. Признайте влияние: кто затронут? Стейкхолдеры, ожидавшие деприоритизированных пунктов, должны услышать это напрямую.

**Избегайте «качелей» дорожной карты:**
- Не меняйте дорожную карту из-за каждого кусочка новой информации — имейте порог
- Группируйте обновления по естественным каденциям (месяц, квартал), если только не действительно срочно
- Различайте «изменение дорожной карты» (стратегическое) и «корректировку скоупа» (исполнение)
- Отслеживайте частоту изменений — частые изменения сигнализируют о неясной стратегии

### 3.6 Чек-лист валидации дорожной карты

Перед публикацией:
- [ ] Сравните топ-приоритеты со стратегическими целями — продвигает ли каждый пункт хотя бы одну?
- [ ] Проведите анализ чувствительности по неопределённым оценкам RICE
- [ ] Проведите ревью с ключевыми стейкхолдерами на предмет слепых зон
- [ ] Проверьте отсутствующие зависимости между фичами
- [ ] Валидируйте оценки трудозатрат с инженерией
- [ ] Подтвердите распределение ёмкости (70/20/10 или скорректированное под контекст)
- [ ] Убедитесь, что дорожная карта не перегружена — режьте скоуп, а не стандарты

## 4. Управление спринтами и agile

### 4.1 Обзор agile-церемоний

| Церемония | Цель | Длительность | Каденция |
|----------|---------|----------|---------|
| Sprint Planning | Зафиксировать работу на следующий спринт | 1–4 часа | Начало спринта |
| Daily Standup | Выявить блокеры, скоординироваться | 15 минут | Ежедневно |
| Sprint Review / Demo | Показать прогресс, собрать обратную связь | 1–2 часа | Конец спринта |
| Sprint Retrospective | Отрефлексировать и улучшить процесс | 1–2 часа | Конец спринта |
| Backlog Refinement | Грумить и оценивать предстоящую работу | 1–2 часа | Середина спринта |

### 4.2 Планирование спринта

**Пошагово:**
1. Рассчитайте ёмкость (velocity × фактор доступности)
2. Обсудите цель спринта со стейкхолдерами
3. Выберите истории из приоритизированного бэклога
4. Заполните до 80–85% ёмкости (committed — зафиксировано)
5. Добавьте stretch-цели (10–15%)
6. Определите зависимости и риски
7. Разбейте сложные истории на задачи
8. Проверьте: зафиксированные points ≤85% ёмкости; у всех историй есть критерии приёмки

**Шаблон загрузки спринта:**
```
Sprint Capacity: 27 points
Sprint Goal: [Clear, measurable objective]

COMMITTED (23 points):
[H] US-001: User dashboard (5 pts)
[H] US-002: Export feature (3 pts)
[H] US-003: Search filter (5 pts)
[M] US-004: Settings page (5 pts)
[M] US-005: Help tooltips (3 pts)
[L] US-006: Theme options (2 pts)

STRETCH (4 points):
[L] US-007: Sort options (2 pts)
[L] US-008: Print view (2 pts)
```

**Советы по фасилитации:**
- Приходите с предложенным порядком приоритетов — не просите команду приоритизировать с нуля
- Сопротивляйтесь перегрузке (overcommitment) — лучше зафиксировать меньше и поставлять надёжно
- Убедитесь, что у каждого пункта есть чёткий владелец и чёткие критерии приёмки
- Помечайте пункты, которые недооценены или имеют скрытую сложность

### 4.3 Метрики velocity и здоровья спринта

**Ключевые метрики спринта:**

| Метрика | Формула | Цель |
|--------|---------|------|
| Velocity | Points завершено / спринт | Стабильно ±10% |
| Надёжность коммитмента (Commitment Reliability) | Завершено / Зафиксировано | >85% |
| Изменение скоупа (Scope Change) | Points добавлено или удалено в середине спринта | <10% |
| Перенос (Carryover) | Points не завершено | <15% |
| Время разрешения блокера | Среднее число дней на устранение препятствия | <3 дней |
| Участие в церемониях | Посещаемость и качество | >90% |

**Оценка здоровья спринта (6 измерений):**
1. Надёжность коммитмента (25%): постоянство достижения цели спринта
2. Стабильность скоупа (20%): частота изменений скоупа в середине спринта
3. Разрешение блокеров (15%): среднее время устранения препятствий
4. Вовлечённость в церемонии (15%): участие и эффективность
5. Распределение завершения историй (15%): соотношение завершённых и частичных историй
6. Предсказуемость velocity (10%): постоянство поставки (целевой коэффициент вариации: <20%)

**Общая оценка здоровья:**
- 90–100: Отлично
- 80–89: Хорошо
- 70–79: Удовлетворительно — определите топ-1–2 области для улучшения
- <70: Требуется немедленное вмешательство

### 4.4 Анализ velocity и прогнозирование Монте-Карло

**Пример отслеживания velocity:**
```
Sprint 1: 25 points
Sprint 2: 28 points
Sprint 3: 30 points
Sprint 4: 32 points
Sprint 5: 29 points
------------------------
Average Velocity: 28.8 points
Coefficient of Variation: 9.2% (low volatility — high predictability)

Planning recommendation: Commit to 24–26 points
```

**Прогнозирование методом Монте-Карло:**
- Запустите 1 000+ симуляций, сэмплируя из исторического распределения velocity
- Результат: распределение вероятностей дат завершения или скоупа на целевую дату
- Отчитывайтесь как доверительные интервалы: 50%, 70%, 85%, 95%
- Пример: «Есть 70% вероятность, что мы завершим эту работу за 5 спринтов»
- Используйте диапазоны, чтобы честно сообщать стейкхолдерам неопределённость — избегайте одноточечных оценок

**Интерпретация волатильности:**
- CV <15%: низкая волатильность — высокая предсказуемость, фиксируйте уверенно
- CV 15–25%: умеренная волатильность — фиксируйте на уровне 80% ёмкости
- CV >25%: высокая волатильность — исследуйте первопричины до планирования

### 4.5 Фасилитация ретроспективы

**Стандартный формат:**
1. Задайте сцену: напомните команде цель, создайте психологическую безопасность
2. Соберите данные: что прошло хорошо, что нет, что было непонятно
3. Сгенерируйте инсайты: выявите паттерны и первопричины
4. Решите действия: выберите 1–3 конкретных улучшения, чтобы попробовать в следующем спринте
5. Закройте: поблагодарите людей за честную обратную связь, подтвердите владельцев действий

**Фасилитация на основе данных:**
- Представьте оценки и тренды здоровья спринта как отправную точку
- Поднимите паттерны из исторических тем ретроспектив
- Ограничьте число action items на основе исторической доли их выполнения командой
- Проектируйте эксперименты с измеримыми критериями успеха

**Критерии action item:**
- Конкретный: «добавить шаг CI для обнаружения N+1 запросов», а не «улучшить качество кода»
- С владельцем: один поимённо ответственный человек
- Со сроком: сделано к [дате], проверяемо на следующей ретро
- Измеримый: как мы поймём, что сработало?

**Стадии зрелости команды (по Такману):**

| Стадия | Поведение | Подход к фасилитации |
|-------|-----------|----------------------|
| Forming (формирование) | Вежливость, неуверенность, уступчивость | Дать структуру, обучение процессу, выстраивание доверия |
| Storming (шторминг) | Конфликт, проверка границ | Фасилитировать продуктивный конфликт, поддерживать безопасность |
| Norming (нормирование) | Кооперация, общие нормы | Строить автономию, передавать владение процессом |
| Performing (исполнение) | Высокая отдача, самоуправление | Вводить вызовы, поддерживать инновации |

### 4.6 Фреймворк психологической безопасности

На основе исследований Эми Эдмондсон и проекта Google «Project Aristotle»:

**Индикаторы для оценки (наблюдайте во время церемоний):**
- Высказываются ли члены команды, когда не согласны?
- Обсуждаются ли ошибки открыто, без обвинений?
- Просят ли люди о помощи, когда застряли?
- Озвучиваются ли непопулярные мнения?

**Выстраивание безопасности:**
- Моделируйте уязвимость: Scrum Master / PM открыто признаёт ошибки
- Поощряйте поведение поиска помощи и постановки вопросов
- Создавайте безопасные-для-провала эксперименты с ограниченным радиусом поражения
- Фасилитируйте трудные разговоры с защитными границами
- Отделяйте проблему от человека во всех обсуждениях на ретроспективе

**Целевой уровень психологической безопасности:** 4.0+ по 7-балльной шкале Эдмондсон, измеряется анонимным пульс-опросом.

### 4.7 Техники разбиения эпиков

| Техника | Когда применять | Пример |
|-----------|-------------|---------|
| По шагу процесса (workflow step) | Линейный процесс | «Checkout» → «Add to cart» + «Enter payment» + «Confirm order» |
| По персоне | Несколько типов пользователей | «Dashboard» → «Admin dashboard» + «User dashboard» |
| По типу данных | Несколько входов | «Import» → «Import CSV» + «Import Excel» |
| По операции (CRUD) | Управление данными | «Manage users» → «Create» + «Edit» + «Delete» |
| Сначала happy path | Снижение риска | «Feature» → «Basic flow» + «Error handling» + «Edge cases» |

### 4.8 Определение готовности (Definition of Done)

История завершена, когда:
- [ ] Код написан и прошёл peer review
- [ ] Юнит-тесты написаны и проходят
- [ ] Критерии приёмки проверены владельцем продукта (Product Owner)
- [ ] Документация обновлена
- [ ] Развёрнуто на staging-окружение
- [ ] Не осталось критических багов
- [ ] Критерии производительности выполнены (если заданы)
- [ ] Требования доступности (accessibility) выполнены (если заданы)

## 5. Метрики и OKR

### 5.1 Иерархия продуктовых метрик

#### North Star метрика
Единственная метрика, которая лучше всего отражает базовую ценность, доставляемую вашим продуктом. Должна быть:
- Согласованной с ценностью: растёт, когда пользователи получают больше ценности
- Опережающей: предсказывает долгосрочный успех бизнеса
- Действенной: продуктовая команда может на неё влиять
- Понятной: все в компании знают, что она означает

**Примеры North Star по типу продукта:**

| Тип продукта | North Star метрика |
|-------------|-------------------|
| Инструмент совместной работы | Еженедельно активные команды с 3+ участниками, вносящими вклад |
| Маркетплейс | Еженедельно завершённых транзакций |
| SaaS-платформа | Еженедельно активных пользователей, завершающих ключевой сценарий |
| Контент-платформа | Еженедельное время вовлечённого чтения/просмотра |
| Инструмент для разработчиков | Еженедельных деплоев с использованием инструмента |

#### Метрики L1 (индикаторы здоровья) — всего 5–7 метрик

**Привлечение (Acquisition):**
- Новые регистрации или старты триалов (объём и тренд)
- Конверсия регистрации (посетители → регистрации)
- Микс каналов
- Стоимость привлечения (платные каналы)

**Активация (Activation):**
- Уровень активации: % новых пользователей, выполняющих ключевое действие, которое предсказывает удержание
- Время до активации: длительность от регистрации до активации
- Уровень завершения настройки: % завершивших онбординг
- Метка времени момента первой ценности

**Вовлечённость (Engagement):**
- DAU / WAU / MAU
- Отношение DAU/MAU (липкость, stickiness) — цель >0.5 для продуктов ежедневного использования
- Частота ключевого действия
- Принятие фич: % использующих ключевые фичи

**Удержание (Retention):**
- Удержание D1, D7, D30
- Когортные кривые удержания
- Уровень оттока (churn rate)
- Уровень воскрешения (resurrection rate): % оттёкших пользователей, которые вернулись

**Монетизация (Monetization):**
- Конверсия: бесплатный → платный
- MRR / ARR
- ARPU / ARPA
- Выручка от расширения (expansion revenue)
- Чистое удержание выручки (net revenue retention)

**Удовлетворённость (Satisfaction):**
- NPS
- CSAT
- Объём тикетов поддержки и время разрешения

#### Метрики L2 (диагностические)
- Конверсия воронки на каждом шаге
- Использование и принятие на уровне фич
- Разбивки по сегментам (план, размер компании, география, роль)
- Метрики производительности (загрузка страницы, уровень ошибок, латентность API)

### 5.2 Фреймворк OKR

**Структура:**
```
Objective: [Qualitative, aspirational, time-bound]
  Key Result 1: [Metric] from [baseline] to [target] by [date]
  Key Result 2: [Metric] from [baseline] to [target] by [date]
  Key Result 3: [Metric] from [baseline] to [target] by [date]
```

**Пример:**
```
Objective: Make our product indispensable for daily workflows

Key Results:
  KR1: Increase DAU/MAU ratio from 0.35 to 0.50
  KR2: Increase D30 retention for new users from 40% to 55%
  KR3: 3 core workflows with >80% task completion rate
```

**Лучшие практики OKR:**
- 2–3 цели (objectives) с 2–4 KR каждая — правильный объём
- KR должны быть результатами (поведение пользователей, бизнес-результаты), а не выходами (выпущенные фичи)
- Ставьте stretch-OKR: 70% выполнения — это цель; если вы всегда достигаете 100%, они недостаточно амбициозны
- Оценивайте честно: 0.0–0.3 = провал, 0.4–0.6 = прогресс, 0.7–1.0 = достигнуто
- Проводите ревью в середине периода и корректируйте распределение усилий, если KR явно идут не по плану

### 5.3 Установка целевых значений метрик

1. **Базовая линия (Baseline)**: какое текущее значение? Нужна надёжная базовая линия до установки цели.
2. **Бенчмарк (Benchmark)**: чего достигают сопоставимые продукты?
3. **Траектория (Trajectory)**: каков текущий тренд? Уже улучшающаяся метрика оправдывает более амбициозную цель.
4. **Усилия (Effort)**: сколько инвестиций вы вкладываете в это?
5. **Уверенность (Confidence)**: задайте цель «commit» (высокая уверенность) и «stretch» (амбициозную).

### 5.4 Каденции ревью метрик

#### Еженедельная проверка метрик (15–30 мин)
- North Star метрика: текущее значение, изменение неделя-к-неделе
- Ключевые метрики L1: заметные движения
- Активные эксперименты: результаты и статистическая значимость
- Аномалии: неожиданные всплески или падения
- Алерты: всё, что вызвало мониторинговый алерт

#### Ежемесячное ревью метрик (30–60 мин, вся команда)
- Полный скоркард метрик L1 с трендами месяц-к-месяцу
- Прогресс по квартальным целям OKR
- Когортный анализ: показывают ли более новые когорты лучшие результаты?
- Принятие фич: как работают недавние запуски?
- Сегментный анализ: расхождение между типами пользователей?

#### Квартальный бизнес-ревью (60–90 мин, кросс-функционально)
- Оценка OKR за квартал
- Анализ трендов год-к-году
- Конкурентный контекст
- Что сработало, а что нет
- Установка OKR на следующий квартал

### 5.5 Принципы дизайна дашбордов

1. **Начинайте с вопроса, а не с данных.** Какие решения поддерживает этот дашборд?
2. **Иерархия информации.** North Star наверху, метрики L1 дальше, L2 на детализации (drill-down).
3. **Контекст важнее чисел.** Всегда показывайте: текущее значение, сравнение (предыдущий период, цель, бенчмарк), направление тренда.
4. **Меньше метрик, больше инсайта.** Максимум 5–10 метрик на дашборде.
5. **Согласованные временные периоды.** Не смешивайте дневные и месячные метрики в одном представлении.
6. **Визуальные индикаторы статуса.** Зелёный = в графике, Жёлтый = требует внимания, Красный = вне графика.
7. **Действенность.** Каждая метрика должна быть тем, на что команда может влиять.

**Раскладка дашборда:**
- Верхний ряд: North Star метрика с линией тренда и целью
- Второй ряд: скоркард метрик L1
- Третий ряд: ключевые воронки / метрики конверсии
- Четвёртый ряд: недавние эксперименты и запуски
- Низ / детализация: метрики L2 и сегментные разбивки

**Антипаттерны, которых стоит избегать:**
- Метрики тщеславия (vanity metrics): всегда растут, но не указывают на здоровье (всего регистраций за всё время)
- Слишком много метрик: требует прокрутки
- Нет сравнения: сырые числа без предыдущего периода или цели
- Устаревшие дашборды: не обновлялись и не пересматривались месяцами
- Дашборды выходов (output): измеряют активность команды, а не результаты пользователей
- Один дашборд для всех аудиторий: руководству, PM и инженерам нужны разные представления

### 5.6 Глубокие разборы активации и удержания

**Определение события активации:**
- Сравните удержанных пользователей с оттёкшими — какие действия совершили удержанные, которых не совершили оттёкшие?
- Событие активации должно сильно предсказывать долгосрочное удержание
- Должно быть достижимо в первой сессии или первые несколько дней

**Чтение когортной кривой удержания:**
- Начальный отвал: проблема активации (новые пользователи не получают ценности)
- Устойчивый спад со временем: проблема вовлечённости (даже активированные пользователи теряют интерес)
- Выполаживание после начального отвала: здоровая ситуация — у вас есть стабильная удержанная база

**Улучшение удержания:**
- Сегментируйте удержание по поведению активации и выявите разницу
- Сравнивайте когорты во времени — лучше ли удерживаются более новые когорты?
- A/B-тестируйте онбординг-флоу и измеряйте влияние на удержание, а не только на уровень активации

## 6. Пользовательские исследования и UX

### 6.1 Выбор метода исследования

| Тип вопроса | Лучший метод | Размер выборки |
|---------------|-------------|-------------|
| «Что делают пользователи?» | Аналитика, наблюдение | 100+ событий |
| «Почему они это делают?» | Интервью | 8–15 пользователей |
| «Насколько хорошо они могут это сделать?» | Юзабилити-тест | 5–8 пользователей |
| «Что они предпочитают?» | Опрос, A/B-тест | 50+ пользователей |
| «Что они чувствуют?» | Дневниковое исследование, интервью | 10–15 пользователей |

### 6.2 Процесс кастомер-дискавери (Customer Discovery)

```
Plan → Recruit → Interview → Analyze → Synthesize → Validate
```

**Шаг 1: Спланируйте исследование**
- Определите 3–5 конкретных исследовательских вопросов (не «что думают пользователи?»)
- Определите целевые сегменты
- Создайте сценарий интервью, сфокусированный на проблемах, а не на решениях

**Шаг 2: Наберите участников**
- 5–8 интервью на сегмент
- Микс продвинутых и оттёкших пользователей
- Включите участников, соответствующих вашей целевой персоне, а не только текущих клиентов

**Шаг 3: Проведите интервью**
- Полуструктурированный формат: следуйте сценарию, но идите за интересными нитями
- Фокусируйтесь на прошлом поведении, а не на будущих намерениях («расскажите о последнем разе, когда вы...», а не «стали бы вы когда-нибудь...»)
- Спросите «почему» пять раз, чтобы найти первопричину
- Записывайте с разрешения; делайте минимум заметок во время сессии
- Избегайте наводящих вопросов («Разве вам не понравилось бы...?»)

**Банк вопросов для интервью по типам:**

| Тип | Пример | Для чего |
|------|---------|---------|
| Контекст | «Проведите меня по своему типичному дню» | Понимание среды |
| Поведение | «Покажите мне, как вы делаете X» | Наблюдение реальных действий |
| Цели | «Чего вы пытаетесь достичь?» | Раскрытие мотивов |
| Боль | «Что самое трудное?» | Выявление фрустраций |
| Частота | «Как часто это случается?» | Оценка серьёзности |
| Рефлексия | «Что бы вы изменили?» | Генерация идей |
| JTBD | «Когда вы делаете X, чего вы в конечном счёте пытаетесь достичь?» | Jobs to be done |

### 6.3 Анализ и синтез интервью

**Теги кодирования данных:**
- `[GOAL]` — чего они хотят достичь
- `[PAIN]` — что их фрустрирует
- `[BEHAVIOR]` — что они на самом деле делают (vs. что говорят, что делают)
- `[CONTEXT]` — когда/где они используют продукт
- `[QUOTE]` — прямые слова пользователя как доказательство
- `[WORKAROUND]` — неудовлетворённые потребности в маскировке

**Процесс тематического анализа:**
1. Знакомство: прочитайте все данные до того, как что-либо кодировать
2. Начальное кодирование: щедро помечайте каждое наблюдение
3. Развитие тем: группируйте связанные коды в кандидатные темы
4. Ревью тем: проверьте каждую тему против данных — достаточно ли доказательств? Отличается ли от других?
5. Уточнение тем: чётко определите и назовите каждую тему (описание в 1–2 предложения)
6. Отчёт: распишите темы с подтверждающими доказательствами

**Кросс-интервьюный анализ:**
- Паттерн = 3+ участника упоминают одну и ту же тему
- Отмечайте частоту: сколько из N участников упомянули каждую тему?
- Выявляйте сегменты: есть ли у разных типов пользователей разные паттерны?
- Поднимайте противоречия: где участники не согласны? Часто это выявляет осмысленные сегменты.
- Находите сюрпризы: что бросило вызов вашим прежним допущениям?

**Customer Interview Analyzer — структура вывода:**
```
PAIN POINTS (N found)
  [HIGH] [Pain point description]
    "[Supporting quote]"

FEATURE REQUESTS (N found)
  [Request description] - Priority: High/Medium/Low

JOBS TO BE DONE
  When [context]
  I want [goal]
  So I can [outcome]

SENTIMENT ANALYSIS
  Overall: Positive/Negative/Mixed
  Key emotions: [list]

KEY QUOTES
  • "[Quote 1]"
  • "[Quote 2]"

THEMES
  - [Theme 1]
  - [Theme 2]
```

### 6.4 Фреймворки синтеза исследований

#### Affinity Mapping (карта близости)
1. Запишите каждое отдельное наблюдение как отдельную заметку
2. Кластеризуйте связанные заметки по схожести (дайте категориям проявиться, не задавайте заранее)
3. Подпишите каждый кластер
4. Сгруппируйте кластеры в группы более высокого уровня, если проявляются паттерны
5. Выявите темы из кластеров

**Советы:**
- Одно наблюдение на заметку — не комбинируйте инсайты
- Выбросы интересны — не запихивайте их насильно в кластер
- Сам процесс группировки строит общее понимание

#### Триангуляция
Усиливайте находки, комбинируя несколько источников:
- Методологическая: один вопрос, разные методы (интервью + опрос + аналитика)
- По источнику: один метод, разные сегменты участников
- Темпоральная: одно наблюдение в разные моменты времени

Находка, подтверждённая несколькими источниками, гораздо сильнее, чем из единственного источника.

#### Интеграция «качественное-количественное» (Qual-Quant)
- Качественное сначала: раскрывает, ЧТО происходит и ПОЧЕМУ — генерирует гипотезы
- Количественная валидация: раскрывает СКОЛЬКО и КАК МНОГО — тестирует гипотезы в масштабе
- Качественный глубокий разбор: объясняет неожиданные количественные находки

**Формат комбинированных доказательств:**
«47% опрошенных пользователей сообщают о трудностях с X (данные опроса), и интервью раскрывают, что это из-за Y (качественная находка, 6/8 участников).»

### 6.5 Разработка персон

**Создание персон на основе доказательств:**
1. Выявите поведенческие паттерны — кластеры схожих поведений, целей и контекстов
2. Определите различающие переменные — что различает кластеры? (размер компании, технический навык, частота использования, основной сценарий)
3. Создайте профили персон для каждого кластера
4. Валидируйте данными — можете ли вы количественно оценить размер каждого сегмента?

**Уровни уверенности персон:**

| Размер выборки | Уверенность | Сценарий применения |
|-------------|------------|----------|
| 5–10 пользователей | Низкая | Только разведывательно |
| 11–30 пользователей | Средняя | Направляющие решения |
| 31+ пользователей | Высокая | Решения по продуктовой дорожной карте |

**Шаблон персоны:**
```
[Persona Name] — [One-line description]

Who they are:
  Role, company type/size, experience level
  How they found/started using the product

What they're trying to accomplish:
  Primary goals and jobs to be done
  How they measure success

How they use the product:
  Frequency and depth of usage
  Key workflows and features used
  Tools they use alongside this product

Key pain points:
  1. [Pain] — [Frequency/severity indicator]
  2. [Pain] — [Frequency/severity indicator]
  3. [Pain] — workaround they've developed: [workaround]

What they value:
  What matters most in a solution
  What would make them switch or churn

Representative quotes:
  "[Quote 1]" — [Persona type, company size]
  "[Quote 2]" — [Persona type, company size]
```

**Стандартные архетипы:**

| Архетип | Сигналы | Фокус дизайна |
|-----------|---------|--------------|
| Power User (продвинутый) | Ежедневное использование, 10+ фич | Эффективность, кастомизация, горячие клавиши |
| Casual User (эпизодический) | Еженедельное использование, 3–5 фич | Простота, направление, безопасные значения по умолчанию |
| Business User (бизнес) | Рабочий контекст, командное использование | Совместная работа, отчётность, интеграции |
| Mobile First (сначала мобильный) | Мобильный — основное устройство | Тач-таргеты, офлайн, скорость |
| New User (новый) | Первый месяц | Онбординг, обучение, страховочные сетки |
| Administrator (администратор) | Управление системой | Контроль, видимость, безопасность, журналы аудита |

**Частые ошибки в персонах:**
- Демографические персоны: определение по возрасту/полу вместо поведения
- Слишком много персон: 3–5 — оптимальная зона
- Вымышленные персоны: придуманные, не основанные на исследованиях
- Статичные персоны: никогда не обновляются по мере эволюции продукта и рынка
- Персоны без выводов: если это не меняет продуктовых решений, оно бесполезно

### 6.6 Маппинг пути (Journey Mapping)

**Определение скоупа пути:**

| Элемент | Описание |
|---------|-------------|
| Персона | Какой тип пользователя |
| Цель | Чего они пытаются достичь |
| Старт | Триггер, начинающий путь |
| Конец | Критерий успеха / завершение |
| Временные рамки | Часы / дни / недели |

**Типичные стадии пути B2B SaaS:**
```
Awareness → Evaluation → Onboarding → Adoption → Advocacy
```

**Слои карты пути на каждой стадии:**
```
Stage: [Name]
├── Actions: What does the user do?
├── Touchpoints: Where do they interact? (product, email, support, sales)
├── Emotions: How do they feel? (1 = frustrated, 5 = delighted)
├── Pain Points: What frustrates them?
└── Opportunities: Where can we improve?
```

**Скоринг возможностей:**
Priority Score = Frequency × Severity × Solvability (каждое 1–5)

### 6.7 Юзабилити-тестирование

**Трансформация исследовательского вопроса:**

| Расплывчато | Тестируемо |
|-------|----------|
| «Удобно ли пользоваться?» | «Могут ли пользователи завершить оформление заказа за <3 минут?» |
| «Нравится ли пользователям?» | «Выберут ли пользователи Дизайн A или B?» |
| «Понятно ли это?» | «Могут ли пользователи найти настройки без подсказок?» |

**Выбор метода:**

| Метод | Участники | Длительность | Лучше всего для |
|--------|-------------|----------|----------|
| Модерируемый удалённый | 5–8 | 45–60 мин | Глубокие инсайты, сложные сценарии |
| Немодерируемый удалённый | 10–20 | 15–20 мин | Быстрая валидация, простые задачи |
| Партизанский (Guerrilla) | 3–5 | 5–10 мин | Быстрая обратная связь, ранние концепты |

**Формат дизайна задачи:**
```
SCENARIO: "Imagine you're planning a trip to Paris..."
GOAL: "Book a hotel for 3 nights within your budget."
SUCCESS: "You see the confirmation page."
```

Прогрессия задач: Разогрев → Ключевая → Вторичная → Граничный случай → Свободное исследование

**Метрики успеха:**

| Метрика | Цель |
|--------|--------|
| Уровень завершения | >80% |
| Время на задачу | <2× ожидаемого |
| Уровень ошибок | <15% |
| Удовлетворённость | >4/5 |

**Серьёзность проблемы юзабилити:**

| Серьёзность | Определение | Действие |
|----------|------------|--------|
| 4 — Критическая | Препятствует завершению задачи | Чинить немедленно |
| 3 — Крупная | Значительная трудность | Чинить до релиза |
| 2 — Незначительная | Вызывает колебание | Чинить при возможности |
| 1 — Косметическая | Замечена, но не проблематична | Низкий приоритет |

### 6.8 Оценка размера возможности (Opportunity Sizing)

Для каждой исследовательской находки оцените:
- **Адресуемые пользователи**: сколько пользователей могли бы выиграть?
- **Частота**: как часто затронутые пользователи сталкиваются с этим? (Ежедневно, еженедельно, однократно)
- **Серьёзность**: насколько это влияет на пользователей? (Блокер, значительное трение, мелкое раздражение)
- **Готовность платить**: приведёт ли решение этого к апгрейдам или удержанию?

**Формула скоринга возможности:**
Impact = Users Affected × Frequency × Severity

**Представляйте оценку размера диапазонами, а не ложной точностью:**
«Это затрагивает 1 500–2 500 пользователей в месяц», а не «Это затрагивает 2 137 пользователей в месяц».

Покажите свою работу: «На основе объёма тикетов поддержки приблизительно 2 000 пользователей в месяц сталкиваются с этой проблемой. Данные интервью (6/8 участников) предполагают, что 60% считают это значительным блокером.»

## 7. Дизайн-системы UI

### 7.1 Система дизайн-токенов

Дизайн-токены — это примитивные значения вашего визуального языка (цвета, отступы, типографика, тени), хранящиеся как именованные переменные, чтобы их можно было согласованно применять во всех компонентах.

**Категории токенов:**

| Категория | Описание | Ключевые значения |
|----------|-------------|------------|
| Colors (цвета) | Цветовые палитры | primary, secondary, neutral, semantic, surface |
| Typography (типографика) | Шрифтовая система | fontFamily, fontSize, fontWeight, lineHeight |
| Spacing (отступы) | Сетка 8pt | шкала 0–64, семантическая (xs–3xl) |
| Sizing (размеры) | Размеры компонентов | container, button, input, icon |
| Borders (границы) | Значения границ | radius (по стилю), width |
| Shadows (тени) | Стили теней | от none до 2xl, inner |
| Animation (анимация) | Токены движения | duration, easing, keyframes |
| Breakpoints (брейкпоинты) | Адаптивность | xs, sm, md, lg, xl, 2xl |
| Z-index | Система слоёв | от base до notification |

**Генерация цветовой шкалы:**

| 700 | Тёмный | Состояния active |

## 8. Конкурентный анализ

### 8.1 Определение конкурентного набора

**Четыре уровня конкурентов:**

| Уровень | Определение | Примеры |
|------|------------|---------|
| Direct (прямые) | Та же проблема, те же пользователи, тот же подход | Лоб-в-лоб в сделках |
| Indirect (косвенные) | Та же проблема, другой подход | Электронная таблица vs. специализированный инструмент |
| Adjacent (смежные) | Сегодня другое, но могут расшириться | Платформенные гиганты, смежные стартапы |
| Substitutes (заменители) | Совершенно другие решения | Нанять человека, отдать на аутсорс, ничего не делать |

### 8.2 Карта конкурентного ландшафта

Расположите конкурентов на осмысленных осях:
- Ширина vs. глубина (suite vs. точечное решение)
- Фокус на SMB vs. enterprise
- Self-serve vs. sales-led выход на рынок
- Простой vs. мощный (сложность продукта)
- Горизонтальный vs. вертикальный (общий vs. отраслевой)

Выбирайте оси, раскрывающие различия стратегического позиционирования, релевантные вашему рынку.

### 8.3 Матрица сравнения фич

**Построение матрицы:**
1. Определите области возможностей, используя категории покупателя (не внутреннюю архитектуру)
2. Перечислите конкретные возможности под каждой областью
3. Оцените каждого конкурента по согласованной шкале

**Шкала оценки:**

| Оценка | Описание |
|--------|-------------|
| Strong (сильно) | Лидер рынка. Глубокая функциональность, хорошо реализовано. |
| Adequate (адекватно) | Функционально. Справляется с работой, но не дифференцировано. |
| Weak (слабо) | Существует, но ограничено. Значительные пробелы или плохая реализация. |
| Absent (отсутствует) | Этой возможности нет. |

**Шаблон матрицы:**
```markdown
| Capability Area     | Our Product | Competitor A | Competitor B | Competitor C |
|---------------------|-------------|-------------|-------------|-------------|
| **[Area 1]**        |             |             |             |             |
|   [Feature 1]       | Strong      | Adequate    | Absent      | Weak        |
|   [Feature 2]       | Adequate    | Strong      | Weak        | Strong      |
| **[Area 2]**        |             |             |             |             |
|   [Feature 3]       | Strong      | Strong      | Adequate    | Absent      |
```

**Советы:**
- Оценивайте на основе реального опыта продукта и обратной связи клиентов, а не маркетинговых заявлений
- Будьте честны в том, где конкуренты лидируют — матрица, где вы всегда выигрываете, неправдоподобна
- Взвешивайте по тому, что важно ВАШИМ целевым клиентам, а не по общему числу фич
- Обновляйте ежеквартально — конкурентные матрицы быстро устаревают

### 8.4 Анализ позиционирования

**Фреймворк заявления о позиционировании:**
«Для [целевого клиента], который [потребность/проблема], [Продукт] — это [категория], которая [ключевая выгода]. В отличие от [альтернативы], [Продукт] [ключевой дифференциатор].»

**Анализ архитектуры сообщений:**

| Уровень | Что извлечь |
|-------|----------------|
| Категория | Какую категорию они заявляют? |
| Дифференциатор | Что делает их особенными внутри категории? |
| Ценностное предложение | Какой результат они обещают? |
| Точки доказательства | Какие свидетельства они приводят? |

**Типы возможностей позиционирования:**
- Незанятые позиции: ценностные предложения, которыми не владеет ни один конкурент и которые важны покупателям
- Переполненные позиции: заявления, которые делают все конкуренты и которые утратили смысл
- Возникающие позиции: новые ценностные предложения, движимые изменениями рынка (ИИ, комплаенс)
- Уязвимые позиции: заявления конкурентов, которые они не могут полностью выполнить

### 8.5 Анализ выигрышей/проигрышей (Win/Loss)

**Источники данных (ранжированы по качеству):**
1. Интервью с клиентом вскоре после решения (наиболее ценно, наименее смещено)
2. Exit-интервью с оттёкшими клиентами
3. Опросы потенциальных клиентов по проигранным сделкам
4. Заметки CRM от команды продаж (доступны сразу, но смещены)

**Вопросы интервью по выигрышу:**
- Какую проблему вы пытались решить?
- Какие альтернативы вы оценивали?
- Почему вы выбрали нас вместо альтернатив?
- Что чуть не заставило вас выбрать кого-то другого?
- Что должно было бы у нас сломаться, чтобы вы пересмотрели выбор?

**Вопросы интервью по проигрышу:**
- Какую проблему вы пытались решить?
- Что вы в итоге выбрали? Почему?
- Где наш продукт оказался недостаточным?
- Что мы могли бы сделать иначе?
- Пересмотрели бы вы нас в будущем? При каких условиях?

**Частые паттерны выигрышей/проигрышей:**

| Паттерн | Описание |
|---------|-------------|
| Пробел в фичах | У конкурента есть конкретная возможность, которой у вас нет и которая является дилбрейкером |
| Преимущество интеграции | Конкурент интегрируется с инструментами, которые покупатель уже использует |
| Подходящая структура цены | Другая модель (за место vs. по использованию) подходит лучше |
| Преимущество инкумбента | Стоимость переключения слишком высока — покупатель остаётся |
| Исполнение продаж | Лучшее демо, быстрее ответ, более релевантные кейсы |
| Бренд/доверие | Покупатель выбирает более безопасный или более известный вариант |

**Отслеживание win rate:**
- Рассчитывайте конкурентный win rate по каждому конкуренту: % сделок с участием каждого конкурента, которые вы выигрываете
- Отслеживайте во времени — выигрываете или теряете позиции по конкретным конкурентам?
- Сегментируйте по типу сделки: enterprise vs. SMB, новые vs. расширение

### 8.6 Идентификация рыночных трендов

**Источники:**
- Отчёты отраслевых аналитиков (Gartner, Forrester, IDC)
- Темы венчурных инвестиций
- Темы конференций с растущей посещаемостью
- Технологические сдвиги (новые платформы, API, возможности)
- Регуляторные изменения
- Изменения в поведении клиентов
- Движение талантов (куда идут топовые люди?)

**Фреймворк анализа трендов:**
1. Что меняется? (Опишите конкретно)
2. Почему сейчас? (Технологии, регулирование, поведение, экономика)
3. Кто затронут? (Какие сегменты клиентов)
4. Каков таймлайн? (Сейчас, 1–2 года, 3–5 лет)
5. Каково следствие для нас?
6. Что делают конкуренты в ответ?

**Варианты стратегического ответа:**

| Ответ | Когда | Риск/Награда |
|----------|------|-------------|
| Lead (вести) | Инвестировать рано, определить категорию | Высокий риск, высокая награда |
| Fast follow (быстро следовать) | Дождаться сигналов спроса клиентов, двигаться быстро | Ниже риск, труднее дифференцироваться |
| Monitor (мониторить) | Отслеживать тренд, задать триггеры для момента действия | Низкая ресурсная стоимость сейчас |
| Ignore (игнорировать) | Явно решить, что не релевантно стратегии | Риск ошибиться |

**Отделение сигнала от шума:**
- Сигнал: тренд, подкреплённый поведенческими данными, растущими инвестициями, регуляторным действием или спросом клиентов
- Шум: тренд, подкреплённый только медиа-хайпом или конференц-шумихой без тяги клиентов
- Тестируйте на ВАШИХ клиентах: просят ли они об этом или испытывают это изменение?

### 8.7 Каденция конкурентного мониторинга

| Активность | Частота | Источник |
|----------|-----------|--------|
| Ревью changelog / блога | Еженедельно | Сайты конкурентов |
| Мониторинг сайтов с отзывами | Ежемесячно | G2, Capterra, Trustpilot |
| Проверка цен | Поквартально | Страницы цен конкурентов |
| Анализ win/loss | Ежемесячно | CRM + интервью с клиентами |
| Скан ландшафта | Поквартально | Венчурное финансирование, вакансии |
| Глубокий конкурентный отчёт | Ежегодно | Полное обновление матрицы фич |

## 9. Коммуникации со стейкхолдерами

### 9.1 Апдейт для руководства / лидерства

Руководству нужно: стратегический контекст, прогресс по целям, риски, требующие их помощи, решения, требующие их участия.

**Шаблон:**
```
Status: [Green / Yellow / Red]

TL;DR: [One sentence — the most important thing to know]

Progress:
- [Outcome achieved, tied to goal/OKR]
- [Milestone reached, with impact]
- [Key metric movement]

Risks:
- [Risk]: [Mitigation plan]. [Ask if needed].

Decisions needed:
- [Decision]: [Options with recommendation]. Need by [date].

Next milestones:
- [Milestone] — [Date]
```

**Советы:**
- Начинайте с вывода. Руководству нужно «мы выпустили X, и это сдвинуло метрику Y», а не повествование о пути.
- Держите менее 200 слов. Захотят больше — спросят.
- Цвет статуса = ваша искренняя оценка, а не то, что они хотят услышать. Жёлтый — это хорошее управление рисками.
- Включайте только риски, по которым хотите помощи — не те, с которыми уже справляетесь.
- Запросы должны быть конкретными: «Решение по X к пятнице», а не «нужна поддержка».

### 9.2 Апдейт для инженерной команды

Инженерам нужно: чёткие приоритеты, технический контекст, разрешённые блокеры, решения, влияющие на их работу.

**Шаблон:**
```
Shipped:
- [Feature/fix] — [Link to PR/ticket]. [Impact if notable].

In progress:
- [Item] — [Owner]. [Expected completion]. [Blockers if any].

Decisions:
- [Decision made]: [Rationale]. [Link to ADR if exists].
- [Decision needed]: [Context]. [Options]. [Recommendation].

Priority changes:
- [What changed and why]

Coming up:
- [Next items] — [Context on why these are next]
```

**Советы:**
- Ссылайтесь на конкретные тикеты, PR и документы.
- Когда приоритеты меняются, объясняйте почему — инженеры более вовлечены, когда понимают причину.
- Будьте явны в том, что их блокирует и что вы делаете для разблокировки.

### 9.3 Апдейт для кросс-функциональных партнёров

**Шаблон:**
```
What's coming:
- [Feature/launch] — [Date]. [What this means for your team].

What we need from you:
- [Specific ask] — [Context]. By [date].

Decisions made:
- [Decision] — [How it affects your team].

Open for input:
- [Topic we'd love feedback on] — [How to provide it].
```

### 9.4 Апдейт для клиентов / внешний

**Шаблон:**
```
What's new:
- [Feature] — [Benefit in customer terms]. [How to use it / link].

Coming soon:
- [Feature] — [Expected timing]. [Why it matters to you].

Known issues:
- [Issue] — [Status]. [Workaround if available].

Feedback:
- [How to share feedback or request features]
```

**Советы:**
- Без внутреннего жаргона, номеров тикетов или технических деталей реализации
- Формулируйте всё в терминах того, что клиент теперь может ДЕЛАТЬ
- Будьте честны со сроками, но не перегружайте обещания
- Упоминайте известные проблемы только если они влияют на клиента и у вас есть план решения

### 9.5 Фреймворк отчётности о статусе

**Green / Yellow / Red:**

| Статус | Определение |
|--------|-----------|
| Green | Продвигается по плану. Нет значимых рисков или блокеров. В графике по обязательствам. |
| Yellow | Прогресс медленнее плана ИЛИ материализовался риск. Митигация идёт, но исход неопределён. Может не уложиться в обязательства без вмешательства. |
| Red | Значительно отстаём от плана. Крупный блокер без чёткой митигации. Не уложимся в обязательства без вмешательства (сокращение скоупа, добавление ресурсов или продление сроков). |

**Когда менять статус:**
- Переходите в Yellow при ПЕРВОМ признаке риска, а не когда уже уверены, что всё плохо
- Переходите в Red, когда исчерпали собственные варианты и нужна эскалация
- Возвращайтесь в Green только когда риск действительно разрешён
- Документируйте, что изменилось, когда меняете статус

### 9.6 Коммуникация рисков (фреймворк ROAM)

| Статус | Значение |
|--------|---------|
| Resolved (разрешён) | Риск больше не является заботой. Задокументируйте как. |
| Owned (с владельцем) | Риск признан, и кто-то активно им управляет. Укажите владельца + план митигации. |
| Accepted (принят) | Риск известен, но мы решаем продолжать без митигации. Задокументируйте обоснование. |
| Mitigated (смягчён) | Действия снизили риск до приемлемого уровня. Задокументируйте, что сделано. |

**Эффективная коммуникация рисков:**
1. Чётко сформулируйте риск: «Есть риск, что [нечто] случится, потому что [причина]»
2. Квантифицируйте влияние: «Если это случится, последствие — [влияние]»
3. Укажите вероятность: «Это [вероятно/возможно/маловероятно], потому что [свидетельства]»
4. Представьте митигацию: «Мы управляем этим путём [действий]»
5. Сделайте запрос: «Нам нужна [конкретная помощь], чтобы ещё снизить этот риск»

**Частые ошибки:**
- Прятать риски в хороших новостях — начинайте с рисков, когда они важны
- Быть расплывчатым: «Могут быть задержки» — уточняйте что, насколько и почему
- Представлять риски без митигаций — у каждого риска нужен план
- Ждать слишком долго — риск, сообщённый рано, это вход для планирования; сообщённый поздно — пожарная тревога

### 9.7 Документирование решений (ADR)

Формат Architecture Decision Record:
```markdown
# [Decision Title]

## Status
[Proposed / Accepted / Deprecated / Superseded by ADR-XXX]

## Context
What is the situation that requires a decision? What forces are at play?

## Decision
What did we decide? State clearly and directly.

## Consequences
- Positive consequences
- Negative consequences or tradeoffs accepted
- What this enables or prevents in the future

## Alternatives Considered
For each alternative: what was it, why was it rejected?
```

**Когда писать ADR:**
- Стратегические продуктовые решения (рыночный сегмент, выбор платформы)
- Значимые технические решения (архитектура, выбор вендора, build vs. buy)
- Спорные решения, где люди не соглашались
- Решения, ограничивающие будущие варианты
- Решения, которые, как вы ожидаете, люди позже поставят под вопрос

## 10. Персистентное планирование (на файлах)

Адаптируйте методологию «Planning with Files» для Perplexity Computer, чтобы поддерживать рабочую память на протяжении сложной многошаговой продуктовой работы.

### 10.1 Базовая концепция

```
Context Window = RAM (volatile, limited)
Workspace Files = Disk (persistent, unlimited)

→ Anything important gets written to a file.
```

Используйте для любой задачи, требующей 5+ шагов, работы в несколько сессий или сложного исследования.

### 10.2 Три файла планирования

| Файл | Назначение | Когда обновлять |
|------|---------|----------------|
| `task_plan.md` | Фазы, прогресс, решения | После завершения каждой фазы |
| `findings.md` | Исследование, открытия, цитаты | После ЛЮБОГО открытия |
| `progress.md` | Лог сессии, что пробовали, ошибки | На протяжении каждой сессии |

### 10.3 Шаблон task_plan.md

```markdown
# Task Plan: [Project Name]

## Goal
[Clear, specific statement of what success looks like]

## Phases

| Phase | Status | Output |
|-------|--------|--------|
| 1. [Phase name] | pending / in_progress / complete | [Expected deliverable] |
| 2. [Phase name] | pending | [Expected deliverable] |
| 3. [Phase name] | pending | [Expected deliverable] |

## Current Phase: [N]
[What is being done right now]

## Decisions Made
| Decision | Rationale | Date |
|----------|-----------|------|
| [Decision] | [Why] | [Date] |

## Errors Encountered
| Error | Attempt | Resolution |
|-------|---------|------------|
| [Error] | 1 | [What was tried] |

## Files Created
- [filename]: [what it contains]
```

### 10.4 Шаблон findings.md

```markdown
# Findings: [Project Name]

## Key Insights
- [Insight]: [Evidence / source]

## Data Points
- [Metric / fact]: [Source / confidence]

## Open Questions
- [Question]: [Status — answered / pending]

## Rejected Approaches
- [Approach]: [Why it didn't work]
```

### 10.5 Критические правила

**Правило 1 — Сначала создайте план.** Никогда не начинайте сложную задачу без `task_plan.md`.

**Правило 2 — Правило двух действий (2-Action Rule).** После каждых 2 операций поиска или исследования немедленно сохраняйте ключевые находки в `findings.md`. Предотвращает потерю информации.

**Правило 3 — Читайте перед решением.** Перед крупными решениями перечитайте `task_plan.md`, чтобы держать цели в фокусе.

**Правило 4 — Обновляйте после каждой фазы.** Помечайте статус фазы: `in_progress` → `complete`. Логируйте созданные файлы.

**Правило 5 — Логируйте все ошибки.** Каждая ошибка попадает в `task_plan.md`. Накапливает знания и предотвращает повторение.

**Правило 6 — Никогда не повторяйте провалы.**
```
if action_failed:
    next_action != same_action
Track what you tried. Mutate the approach.
```

### 10.6 Протокол ошибок «3 удара» (3-Strike)

```
ATTEMPT 1: Diagnose & Fix
  → Read error carefully
  → Identify root cause
  → Apply targeted fix

ATTEMPT 2: Alternative Approach
  → Same error? Try different method
  → Different tool? Different approach?
  → NEVER repeat the exact same failing action

ATTEMPT 3: Broader Rethink
  → Question assumptions
  → Search for alternative solutions
  → Consider updating the plan

AFTER 3 FAILURES: Escalate
  → Explain what you tried
  → Share the specific error
  → Ask for guidance
```

### 10.7 Тест перезагрузки из 5 вопросов

Если вы можете на них ответить, ваше управление контекстом надёжно:

| Вопрос | Источник ответа |
|----------|--------------|
| Где я? | Текущая фаза в task_plan.md |
| Куда я иду? | Оставшиеся фазы в task_plan.md |
| Какова цель? | Формулировка цели в task_plan.md |
| Что я узнал? | findings.md |
| Что я сделал? | progress.md |

### 10.8 Антипаттерны

| Не делайте | Делайте вместо этого |
|-------|------------|
| Начинать исполнение немедленно | Сначала создать task_plan.md |
| Сформулировать цели один раз и забыть | Перечитывать план перед крупными решениями |
| Прятать ошибки и молча повторять | Логировать ошибки в файл плана |
| Запихивать всё в контекст | Хранить большой контент в файлах |
| Повторять проваленные действия | Отслеживать попытки, мутировать подход |

## 11. Уникальные возможности Perplexity Computer

У Perplexity Computer есть встроенные инструменты, делающие несколько PM-процессов значительно быстрее традиционных подходов. Используйте их для продуктовой работы:

### 11.1 Исследование в реальном времени

**Веб-поиск** даёт актуальную, цитируемую информацию для:
- Конкурентной разведки: запуски продуктов, изменения цен, новые фичи
- Идентификации рыночных трендов: свежие отчёты аналитиков, раунды финансирования, отраслевые новости
- Бенчмарк-данных: отраслевые конверсии, бенчмарки удержания, модели ценообразования
- Настроений клиентов: отзывы, упоминания в соцсетях, обсуждения на форумах

**Как использовать в PM-работе:**
- Перед конкурентным анализом: ищите свежие обновления продуктов, посты в блогах и changelog'и
- Перед стратегическим планированием: ищите размер рынка, тренды роста и активность инвесторов
- Перед установкой целей OKR: ищите отраслевые бенчмарки по категории продукта
- Перед деками для стейкхолдеров: ищите свежие аналогичные кейсы

### 11.2 Живая конкурентная разведка

Ищите changelog'и конкурентов, отзывы G2/Capterra и страницы цен в реальном времени — без ручного исследования. Это делает еженедельный конкурентный мониторинг достижимым за минуты, а не часы.

**Процесс:**
1. Поиск «[Competitor] product updates [current month]»
2. Поиск «[Competitor] vs [Your product] review 2025»
3. Поиск «[Competitor] pricing»
4. Извлеките находки в findings.md, используя фреймворк персистентного планирования

### 11.3 Создание документов в масштабе

Perplexity Computer может генерировать:
- Полные PRD со всеми 9 разделами из краткого описания
- Конкурентные матрицы из данных поиска, отформатированные как markdown-таблицы
- Письма-апдейты для стейкхолдеров в правильном формате шаблона
- OKR-документы с каскадированными уровнями
- Документы планирования спринтов с расчётами ёмкости

### 11.4 Многоисточниковый синтез

Perplexity Computer может читать и синтезировать несколько файлов одновременно — полезно для:
- Синтеза транскриптов интервью из нескольких сессий сразу
- Перекрёстной сверки пользовательских исследований с продуктовыми метриками
- Сравнения нескольких черновиков PRD на предмет несоответствий
- Слияния дорожных карт нескольких команд

### 11.5 Генерация кода для PM-инструментов

Когда нужна ручная обработка данных:
- Генерировать скрипты скоринга RICE на Python
- Создавать таблицы дорожной карты в формате Markdown из входного CSV
- Строить кастомные скрипты расчёта метрик
- Генерировать скрипты анализа опросов для открытых ответов

## 12. Кросс-скилловые процессы

### 12.1 Разработка новой фичи (сквозная)

```
Discovery → Prioritization → Specification → Sprint Execution → Launch → Learning

Step 1: Customer Discovery (Section 6)
  - Run 5–8 user interviews
  - Analyze with Customer Interview Analyzer output structure
  - Synthesize into themes and opportunity sizing

Step 2: Prioritization (Section 3)
  - Score opportunities with RICE
  - Check against OKR alignment
  - Portfolio analysis: quick wins vs. big bets balance

Step 3: PRD Writing (Section 2)
  - Choose PRD format based on complexity
  - Draft all 9 sections
  - Review cycle: engineering, design, sales, support

Step 4: Sprint Execution (Section 4)
  - Break into INVEST-compliant user stories
  - Epic breakdown using splitting techniques
  - Sprint planning with capacity calculation
  - Daily standups and blocker tracking

Step 5: Launch (Section 9)
  - Internal update to engineering and cross-functional partners
  - Customer-facing release notes
  - Executive status update

Step 6: Measurement (Section 5)
  - Monitor leading indicators: 1 week, 2 weeks post-launch
  - Monitor lagging indicators: 1 month, 1 quarter post-launch
  - Post-launch retro: compare actual metrics vs. targets
```

### 12.2 Цикл квартального планирования

```
Step 1: Retrospective (Section 5)
  - Score OKRs from previous quarter
  - Analyze L1 metric trends
  - Identify what worked and what did not

Step 2: Competitive Review (Section 8)
  - Update feature comparison matrix
  - Review win/loss analysis for the quarter
  - Scan market trends

Step 3: Research Review (Section 6)
  - Synthesize user research gathered in the quarter
  - Update personas if new patterns emerged
  - Prioritize unaddressed opportunity areas

Step 4: OKR Setting (Section 5)
  - Draft team OKRs aligned to company OKRs
  - Validate KRs are outcome-based and measurable
  - Align with engineering and design capacity

Step 5: Roadmap Planning (Section 3)
  - RICE score top candidates for the quarter
  - Build quarterly themes roadmap
  - Map dependencies
  - Capacity check: 70/20/10 allocation

Step 6: Stakeholder Communication (Section 9)
  - Executive update: priorities and rationale
  - Engineering update: what is committed
  - Cross-functional update: what is coming and when
  - Customer roadmap preview (when appropriate)
```

### 12.3 Спринт «исследование → дорожная карта» (5 дней)

```
Day 1: Research
  - 4–6 user interviews (30 min each)
  - Record and transcribe

Day 2: Synthesis
  - Code all interview data with [GOAL][PAIN][BEHAVIOR][CONTEXT][QUOTE]
  - Affinity map across participants
  - Identify top 5 themes with supporting evidence

Day 3: Opportunity Sizing
  - Score each theme on Frequency × Severity × Breadth × Solvability
  - Cross-reference with product analytics
  - Present combined qual+quant evidence

Day 4: Prioritization
  - RICE score top 8–10 opportunities
  - Map to current OKRs
  - Identify quick wins vs. strategic bets

Day 5: Communication
  - Draft 1-page PRD for top-ranked opportunity
  - Update roadmap in Now/Next/Later format
  - Executive summary update (200 words)
```

### 12.4 Запуск дизайн-системы (для PM, управляющего командами дизайна)

```
Step 1: Token Generation (Section 7.1)
  - Confirm brand colors, style preference
  - Generate full token system

Step 2: Component Audit
  - Inventory existing components
  - Identify inconsistencies
  - Prioritize components to standardize

Step 3: Component Documentation (Section 7.3)
  - Define atomic design hierarchy
  - Document each component's token mapping, variants, and states

Step 4: User Validation (Section 6.7)
  - Usability test key component patterns with 5 users
  - Validate accessibility standards are met (Section 7.5)

Step 5: Developer Handoff (Section 7.6)
  - Export tokens in required formats
  - Sync with Figma
  - Document framework integration

Step 6: Adoption Tracking (Section 5)
  - Define success metric: % of product screens using design system tokens
  - Track adoption rate by team, sprint over sprint
```

### 13.2 Быстрый выбор фреймворка

**Приоритизация:**
- Нужна скорость + данные? → RICE
- Нужна согласованность со стейкхолдерами по скоупу? → MoSCoW
- Ранняя стадия, ограниченные данные? → ICE
- Визуальное командное обсуждение? → Ценность vs. Трудозатраты 2×2

**Формат дорожной карты:**
- Коммуникация для руководства? → Now/Next/Later
- Демонстрация стратегической согласованности? → Поквартальные темы
- Организация, управляемая OKR? → Привязка к OKR
- Планирование для инженерии? → Таймлайн/Ганта

**Метод исследования:**
- Нужно понять ПОЧЕМУ? → Интервью (8–15 пользователей)
- Нужно валидировать в масштабе? → Опрос (50+ пользователей)
- Нужно наблюдать поведение? → Юзабилити-тест (5–8 пользователей)
- Нужны поведенческие данные? → Аналитика (100+ событий)

**Формат PRD:**
- Сложно, несколько команд, 6+ недель? → Стандартный PRD
- Просто, 1 команда, 2–4 недели? → Одностраничный PRD
- По спринтам, развивающееся? → Agile-эпик
- Исследование до утверждения? → Бриф фичи

### 13.3 Справочник частых PM-ловушек

| Ловушка | Описание | Профилактика |
|---------|-------------|------------|
| Сначала решение (Solution-First) | Прыжок к фичам до понимания проблем | Начинать каждый PRD с постановки проблемы на основе доказательств |
| Паралич анализа | Чрезмерное исследование без поставки | Тайм-боксировать фазы исследования; задать дату решения |
| Фабрика фич (Feature Factory) | Выпуск фич без измерения влияния | Определять метрики успеха до постройки |
| Игнорирование техдолга | Не выделять время на здоровье платформы | Резервировать 20% ёмкости на техническое здоровье |
| Сюрприз для стейкхолдера | Не коммуницировать рано и часто | Еженедельные async-апдейты; ежемесячные демо |
| Театр метрик (Metric Theater) | Оптимизация метрик тщеславия вместо реальной ценности | Привязывать все метрики к доставленной пользовательской ценности |
| Расползание скоупа | Непрерывные добавления требований после утверждения | Писать явные не-цели; требовать компромиссов для добавлений |
| Ложная точность | Одноточечные оценки, поданные как уверенные | Использовать диапазоны и доверительные интервалы |
| Демографические персоны | Определение по возрасту/полу вместо поведения | Определять персоны по поведенческим кластерам |
| Переполненная дорожная карта | Перегрузка каждый квартал | Распределение 70/20/10; режьте до того, как перегрузить |

### 13.4 Чек-лист PRD

Перед отправкой PRD на ревью:
- [ ] Постановка проблемы включает конкретные доказательства (данные, цитаты, объём тикетов)
- [ ] Цели — измеримые результаты, а не описания выходов
- [ ] Не-цели явные, с причинами
- [ ] Пользовательские истории покрывают несколько персон, если релевантно
- [ ] Критерии INVEST проверены для каждой истории
- [ ] Все требования категоризированы (P0/P1/P2 или MoSCoW)
- [ ] Критерии приёмки написаны в формате Given-When-Then или чек-листа
- [ ] Метрики успеха определены с конкретными целями и методом измерения
- [ ] Открытые вопросы помечены владельцами и статусом блокировки
- [ ] Зависимости по срокам определены
- [ ] Инженерное ревью реализуемости завершено

### 13.5 Чек-листы качества исследований

**Качество персоны:**
- [ ] Основана на 20+ пользователях (минимум для высокой уверенности)
- [ ] Минимум 2 источника данных (количественный + качественный)
- [ ] Цели конкретны и действенны
- [ ] Фрустрации включают индикаторы частоты/серьёзности
- [ ] Выводы для дизайна конкретны и действенны
- [ ] Указан уровень уверенности

**Качество карты пути:**
- [ ] Скоуп чётко определён (персона, цель, временные рамки)
- [ ] Основана на реальных пользовательских данных, не на допущениях
- [ ] Все слои заполнены (действия, точки контакта, эмоции, точки боли)
- [ ] Возможности приоритизированы с оценками

**Качество синтеза исследований:**
- [ ] Данные закодированы согласованно
- [ ] Паттерны основаны на 3+ точках данных
- [ ] Находки включают подтверждающие доказательства (цитаты + данные)
- [ ] Рекомендации действенны
- [ ] Приоритеты обоснованы

### 13.6 Чек-лист мониторинга метрик

**Еженедельно (15 мин):**
- [ ] North Star метрика vs. прошлая неделя
- [ ] Любые аномалии метрик L1 (>10% изменение)
- [ ] Результаты активных экспериментов
- [ ] Сработавшие алерты

**Ежемесячно (45 мин):**
- [ ] Полный скоркард L1 с трендом
- [ ] Прогресс OKR относительно целей
- [ ] Сравнение когортного удержания
- [ ] Уровни принятия недавних фич

**Поквартально (90 мин):**
- [ ] Скоринг и оценка OKR
- [ ] Сравнения год-к-году
- [ ] Изменения конкурентного контекста
- [ ] Черновики OKR на следующий квартал
