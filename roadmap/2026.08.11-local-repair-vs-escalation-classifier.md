# Roadmap: локальный repair не должен превращаться в plan-design escalation

**Статус:** 🟡 частично реализовано планом `2026.08.12-№1-TASK-RESILIENCE`.
Continue-first observations, automatic local-repair branch, isolated block confirmation,
100% external RAG gate, reducer и provider projection parity внедрены. **Ровный остаток:**
closed all-five local-repair evidence carrier с pre/post validation и bounded diff; enforcement
repair path вне `Files`; installed adapter version/digest attestation; метрики первых 10 repairs.

**Автор:** Codex, 2026-08-11. **Источник:** Dmitry Vostrikov, approval owner Agelto.
**Владельцы:** `packages/task` и `packages/skiller`.

## Симптом

P4.2 должен был добавить VitePress build/verifier и доказать его item-owned carrier:
`bash docker/tests/documentation-build-contract.sh`. Первый же build воспроизводимо остановился:
VitePress воспринял `<Type>` в `docs/03_Dev/recipes.md` как незакрытый HTML-тег. Это один
committed documentation-input syntax defect, не меняющий generator/storage/auth/cache contract
D26/D27 и не требующий решения владельца.

Исполнитель прочитал одновременно два ограничения P4.2: `docs/03_Dev/recipes.md` отсутствует в
`Files`, а «content rewrite beyond config/index links» в `Scope Excluded`. Он классифицировал
это как `конфликт правил`, записал `result=escalated`, сделал P4.2 terminal `🔴 Blocked` и
передал его в `plan-design`. Product work был отменён и откатан.

Это неверный результат: малый, обратимый и семантически-нейтральный repair, необходимый для
заявленной validation, должен был остаться в текущем attempt, быть зафиксирован как локальная
repair/deviation и закончиться повторным original carrier. `Files` — граница product scope, а не
автоматический запрет на любой диагностированный syntax repair в уже потребляемом input corpus.

## Наблюдаемая decision trace

1. **Сигнал.** Declared validation упала до image stage на конкретной строке committed docs.
2. **Минимальное воспроизведение.** Ошибка указывала на один literal `<Type>` в inline code;
   изменение не требовало нового dependency, команды, разрешения или внешнего состояния.
3. **Неверный переход.** Исполнитель сопоставил только `path ∉ Files` и prose `Scope Excluded`.
   Он не проверил, является ли исправление bounded incidental repair и меняет ли оно один из
   перечисленных material surfaces.
4. **Неверный outcome.** Был выбран terminal `escalated`, хотя authority, frozen/public contract,
   secrets, generated asset, SemVer и architecture не были затронуты.
5. **Усиливающий фактор доставки.** Рабочий Codex adapter `task@0.11.1`, из которого был запущен
   P4.2, содержал старую жёсткую формулировку «план разошёлся с реальным кодом → эскалация». В
   исходном `packages/task` уже есть более точная ветка: `observe → minimal reproduce → classify
   → act → verify`, где `unrelated-pre-existing` допускает safe fallback/local reversible repair
   в том же attempt. Значит, недостаточно улучшить только canonical command: projected adapter
   и опубликованный marketplace должны нести тот же смысл и быть проверяемо свежими.

## Предлагаемое правило: bounded incidental repair

Перед любым `Blocked`/`escalated` исполнитель обязан применить один детерминированный classifier.
Repair остаётся в текущем attempt, если **все** условия выполнены:

1. signal воспроизводится declared Validation или её минимальным прямым prerequisite;
2. конкретный defect локализован в одном repository input file и repair имеет явно ограниченный
   diff (syntax, escaping, typo, deterministic generated-cache cleanup или compatibility glue);
3. repair не меняет наблюдаемую семантику продукта, public/frozen contract, schema/migration,
   authority/authentication/authorization, secret, deployment topology, dependency version,
   generated/protected source или external side effect;
4. repair не добавляет новый acceptance criterion, не расширяет allowlist и не подменяет
   declared Validation;
5. после него запускается тот же original carrier; его green result — единственное доказательство
   продолжения.

Тогда runtime создаёт structured `local-repair` record с причиной, paths, pre/post validation и
bounded diff. При terminal green он попадает в Known Deviations как **process** fact; сам по себе
он не превращает item в `🟠` и не открывает audit/design loop.

Если хотя бы одно условие не доказано, scope не расширяется молча. Escalation остаётся обязательной
для authority/frozen/public contract change, multiple-package refactor, protected generated asset,
необратимой операции, missing acceptance, security/data boundary или repair, который меняет
семантику вместо устранения дефекта формы.

## Классы похожих случаев

| Сигнал | Правильное действие | Когда эскалировать |
|:--|:--|:--|
| Syntax/markup error в committed input corpus ломает declared build | Bounded incidental repair + повторить carrier | Исправление меняет документационный/публичный смысл, затрагивает несколько несвязанных страниц или расширяет source corpus |
| Unit/contract test нашёл defect в пути из `Files` | Обычный fix в текущем attempt + повторить validation | Fix требует redesign контракта, migration или authority |
| Missing cache/temporary generated output или transient tool state | Safe cleanup/retry/bounded wait в текущем attempt | Повтор не детерминирован, нужен внешний владелец/ресурс или затронут persistent production state |
| Pre-existing unrelated red validation | Зафиксировать evidence, продолжить независимый scope либо оставить `🟠` с конкретным fix proposal | Red invalidates declared acceptance целиком и не имеет bounded neutral repair |
| Path вне `Files` | Сначала classifier, а не automatic stop | Path нужен для material product behavior либо нет доказательства нейтральности |

## Изменения источника истины и доставки

1. Canonical `packages/task/commands/plan-exec.md` и `plan-run.md` получают один closed-set
   classifier и один explicit local-repair journal/result representation; не оставлять его
   только prose guidance.
2. `task_contract`/state reducer различают `local-repair`, process deviation, material debt и
   true escalation; local repair не производит `🔴 Blocked`, escalation triple или owner gate.
3. `Files` diff gate допускает only classifier-qualified repair path и проверяет recorded bounded
   evidence; любой иной путь вне `Files` остаётся material deviation/escalation candidate.
4. Adapter generation and marketplace release add parity gate: canonical command, Codex adapter
   projection и installed version are digest-qualified; semantic drift выдаёт explicit
   `COMMAND_PROJECTION_STALE`, а не скрыто меняет execution policy.
5. Установленный package не берётся как evidence того, что source policy уже доступна исполнителю:
   launch/report печатают canonical version + adapter version/digest.

## Тесты приемки

- Fixture P4.2-style: malformed inline code in a declared build input is repaired as
  `local-repair`; original validation retries and item can close green without plan-design.
- Один repair path вне `Files` проходит только с all-five classifier predicates и structured
  record; two paths, semantic content change и allowlist widening fail closed.
- True contract/auth/schema/generated-asset cases still produce `🔴 Blocked`, escalation triple
  and design continuation.
- Pre-existing unrelated red that cannot be repaired locally yields an attributed `🟠`/fix proposal
  or a real escalation according to the classifier, never a fabricated green.
- Generated Codex adapter snapshot and installed marketplace fixture contain the same local-repair
  branch as canonical commands; stale projection is detected before mutation.
- `plan-lint`, state/status/bundle projections, journal schema and return-loop do not treat a
  local repair as an attempt failure, return event or owner gate.

## Измерение успеха

Record per plan: number of signal classifications, local repairs, escalations, false escalations
reopened to local repair, and time from first red signal to resumed declared validation. Review the
first ten qualified repairs manually: any repair that later changes a material surface tightens the
classifier; zero-evidence repairs are not counted as success.

## Связь с существующими направлениями

- `2026.08.10-adaptive-plan-governance.md` уже запрещает повторный heavy gate без нового material
  risk; эта запись добавляет более раннее решение: не создавать false terminal event вообще.
- `2026.08.10-plan-run-routing-blocked-terminal-loop.md` разделяет route rejection и true block;
  здесь та же инварианта применяется к local repair versus scope/authority escalation.

## Non-goals

Это не разрешение «чинить всё рядом», не отмена `Files`, не bypass owner gate и не замена
validation агентской оценкой. Любая неясность по semantic/material surface сохраняет fail-closed
ветку; оптимизируется только доказуемо узкий repair.

## Реализовано 2026-08-12

- `journal.py` и item-state отделяют `local-repair`, `block-candidate`, `decision-pending` и
  `routing-rejected` от terminal product outcomes и execution attempts.
- `block-candidate/v1` + `task.plan_blocking.evaluate()` требуют verified RAG для каждого
  external-кандидата и ровно одного отличного от executor reviewer; только `JUSTIFIED` разрешает
  terminal block, остальные verdict продолжают repair/evidence.
- Пять Task-команд, Claude golden и Codex adapters несут один continue-first контракт;
  provider generator `--check` и полный Task validate проверяют parity.

Пока не реализован carrier пяти predicates с path/pre/post/diff, поэтому соответствующие пункты
§«Изменения источника истины» 3 и 5 и два первых acceptance-теста остаются открытыми; это и есть
единственный продуктовый остаток этой записи.
