# Доменные паттерны PHP: VO · DTO · Pipeline · Specification

## Контекст

Четыре «голых» (без фреймворковых пакетов) доменных паттерна, которые ИИ постоянно путает между
собой и применяет не там. Скилл — это **руководство ВЫБОРА**: по задаче определить, какой из
четырёх нужен (а часто — что не нужен ни один), чем они отличаются, и где граница с готовыми
решениями Laravel/spatie. Реализационные шаблоны — в сниппетах; здесь — критерии и анти-паттерны.

Все четыре — про разделение ответственности в домене:
- **Value Object (VO)** — *значение с гарантией*: типобезопасная обёртка вокруг примитива с
  инвариантом и поведением. «Невалидного Email не существует».
- **DTO** — *данные без поведения*: типизированная структура для переноса между слоями.
  «Контейнер с полями, который ничего не решает».
- **Pipeline** — *последовательная трансформация*: обработка распадается на переставляемые этапы.
  «Конвейер шагов над одним значением».
- **Specification** — *композируемый предикат*: бизнес-правило «подходит / нет» как объект,
  комбинируемый and/or/not. «Правило, которое можно собрать из правил».

## Когда активировать

- Пишешь/ревьюишь класс, переносящий или проверяющий данные, и не уверен — VO, DTO, сервис или просто массив.
- Видишь примитив (`string $email`, `int $amount`), валидируемый в нескольких местах, — кандидат на VO.
- Метод разросся в длинную последовательность преобразований — кандидат на Pipeline.
- Условие фильтрации/допуска дублируется и комбинируется — кандидат на Specification.
- На ревью встретил «God-DTO» с методами, анемичный VO без инварианта или specification поверх БД.

## Алгоритм выбора

### Шаг 1. Сначала спроси: нужен ли паттерн вообще

Анти-bloat прежде всего. Паттерн оправдан, только если он убирает дублирование или защищает
инвариант. Если значение используется один раз и валидируется фреймворком — `string` достаточно.

- Валидация уже делается в `FormRequest`/`Data::from()` и значение больше нигде не проверяется → **не плоди VO**.
- Структура нужна только внутри одного метода → локальный массив/именованные переменные, **не DTO**.
- Одно линейное преобразование без ветвлений → обычный метод, **не Pipeline**.
- Единственное условие в одном месте → `if`/scope, **не Specification**.

### Шаг 2. Различи по природе задачи

| Вопрос | Ответ → паттерн |
|:--|:--|
| Это **значение** с правилом валидности, которое должно соблюдаться всегда? | **VO** |
| Это **набор полей** для передачи между слоями, без логики и инвариантов? | **DTO** |
| Это **процесс** из нескольких независимых этапов над одним объектом? | **Pipeline** |
| Это **правило** «подходит / не подходит», которое надо комбинировать? | **Specification** |

Паттерны **сочетаются**, не конкурируют: DTO может содержать поля-VO; Pipeline-шаг принимает и
возвращает DTO; Specification проверяет VO/модель. Выбор — про роль каждого класса, не «или-или».

### Шаг 3. Критерии и анти-паттерны по каждому

**Value Object** (`snippets/value-object.php`)
- Бери, когда: примитив имеет правила (email, телефон, деньги, диапазон дат, проценты), и эти
  правила или операции над значением встречаются больше одного раза.
- Признаки: `final readonly`, инвариант в конструкторе (бросает на невалидном входе), равенство
  по значению (`equals`), доменное поведение (`Money::add`, `Email::domain`).
- Анти-паттерны: **анемичный VO** — обёртка без инварианта и поведения (тогда это просто `string`,
  VO не нужен); сеттеры/мутаторы (VO иммутабелен — операция возвращает новый экземпляр); валидация
  «снаружи» VO при том, что VO заведён (инвариант обязан жить В конструкторе); суффикс `-VO`/`-Object`
  в имени (имя — доменное существительное, см. `php/naming-conventions`).

**DTO** (`snippets/dto.php`)
- Бери, когда: между слоями (контроллер→Action→репозиторий) передаётся набор полей, и хочется
  типизированный контракт вместо ассоциативного массива; для результата sync-операции — delta-DTO.
- Признаки: `final readonly`, promoted properties, **нет методов с логикой**, нет зависимостей от
  `Request`/Eloquent/DB; создаётся именованными аргументами (`php/named-arguments`).
- Анти-паттерны: **God-DTO** — DTO обрастает методами (`save()`, `calculate()`), превращаясь в
  сервис (логика → Action/Service, DTO остаётся данными); смешение с VO — поле с инвариантом
  лучше сделать VO, а DTO его переносит; DTO ради DTO там, где хватает массива в пределах метода.
- **Граница с пакетом:** нужны валидация-из-запроса, касты, `DataCollection`, `#[TypeScript]` —
  это `spatie/laravel-data` (`php/laravel-data`), а не «голый» DTO. «Голый» — когда зависимость
  от пакета нежелательна (домен-ядро, library-код) или структура чисто внутренняя.

**Pipeline** (`snippets/pipeline.php`)
- Бери, когда: обработка распадается на 3+ самостоятельных этапа (нормализация → обогащение →
  расчёт → проверка), которые хочется тестировать и переставлять по отдельности.
- Признаки: каждый шаг — отдельный класс/замыкание с единой сигнатурой; шаги не знают друг о
  друге; порядок задаётся списком, не зашит в код.
- Анти-паттерны: pipeline ради двух строк (одно-два преобразования — обычный метод); шаги с
  побочными эффектами на чужие данные (шаг должен быть локальным и предсказуемым); **изобретение
  своего Pipeline** при доступном `Illuminate\Pipeline\Pipeline`/фасаде `Pipeline` — бери
  фреймворковый, свой только когда зависимость нежелательна; **named-аргумент в полиморфном
  вызове** `handle()`/`isSatisfiedBy()` через интерфейс — имя параметра реализации интерфейсом
  не фиксировано, такой вызов падает `Unknown named parameter`; зови позиционно (исключение из
  `php/named-arguments`, оно — про конкретные сигнатуры).

**Specification** (`snippets/specification.php`)
- Бери, когда: бизнес-правило «подходит / нет» применяется в нескольких местах И комбинируется
  (A и B, A или не C); правило хочется назвать, протестировать, переиспользовать как объект.
- Признаки: один метод `isSatisfiedBy(): bool`; элементарные спецификации собираются `and/or/not`
  без правки исходных классов.
- Анти-паттерны: **specification поверх БД** — если правило фильтрует выборку, это model scope /
  `queryForUser` (`php/repositories`), а не in-memory предикат над загруженной коллекцией;
  спецификация ради единственного `if` в одном месте (over-engineering); смешение проверки с
  действием (specification только отвечает «да/нет», не выполняет побочных эффектов).

### Шаг 4. Размести и назови правильно

Размещение в дереве проекта — `php/laravel-structure`; имена (VO — доменное существительное без
суффикса, DTO — `Data`/`Form`) — `php/naming-conventions`; сборка Pipeline/Specification через
DI — `php/dependency-injection`; конструирование (конкретные конструкторы VO/DTO) именованными
аргументами — `php/named-arguments`. NB: именованный аргумент — для конкретной сигнатуры;
полиморфный вызов через интерфейс (`handle`/`isSatisfiedBy`) — только позиционно.

## Чеклист качества

- [ ] Перед введением паттерна проверено, что он убирает дублирование/защищает инвариант, а не добавлен «на будущее» (анти-bloat).
- [ ] **VO** имеет инвариант в конструкторе и поведение; не анемичная обёртка; иммутабелен (`final readonly`, без сеттеров); равенство по значению.
- [ ] **DTO** не содержит бизнес-логики и зависимостей от `Request`/Eloquent/DB; `final readonly`, promoted properties; не превратился в God-object.
- [ ] Выбор «голый DTO vs `spatie/laravel-data`» осознан: нужны касты/валидация-из-запроса/`#[TypeScript]` → пакет (`php/laravel-data`), иначе «голый».
- [ ] **Pipeline** не изобретён заново при доступном `Illuminate\Pipeline`; шаги самостоятельны, без побочных эффектов на чужие данные; порядок — данные, не код.
- [ ] **Specification** применена для in-memory правил, а не для фильтрации выборки (фильтрация → scope/`queryForUser`, см. `php/repositories`); только предикат, без действий.
- [ ] Полиморфные вызовы через интерфейс (`PipeStage::handle`, `Specification::isSatisfiedBy`) — позиционные, не именованные (имя параметра реализации интерфейсом не зафиксировано → `Unknown named parameter`).
- [ ] Поля-значения с инвариантом вынесены в VO, а DTO их лишь переносит (паттерны сочетаются, не дублируют ответственность).
- [ ] Имена доменные: VO без суффикса `-VO/-Object`, DTO — `Data`/`Form` (см. `php/naming-conventions`); конструкторы вызываются именованными аргументами (`php/named-arguments`).
- [ ] Неймспейсы/имена нейтральны (`App\Domain\...`), без бизнес-терминов конкретного проекта.
