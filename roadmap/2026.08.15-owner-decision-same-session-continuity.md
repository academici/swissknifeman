# Roadmap: session-continuity controller выбирает текущий или новый root

**Статус:** ⬜ к внедрению. **Даты инцидентов:** 2026-08-15, 2026-08-16.
**Источник:** Insiders `2026.07.30-SITE-HARDENING` P8.9 и swissknifeman
`2026.08.02-PROVIDER-CONTRACT-LOCALE` P6.2, `$ task:plan-run`.
**Владельцы:** `packages/task` (continuation semantics, command renderer и generated
provider projections), Codex/Claude transport/runtime (owner-decision UI и continuation loop).

## Вердикт

Да: выдавать владельцу новую команду для запуска того же незакрытого item'а после
`approval_required` — недопустимый UX и нарушение собственного continuation contract.
Сама остановка продуктовой мутации была правильной: P8.9 встретил scope/authority boundary и
создал durable `DecisionRequest`. Неправильным был следующий carrier: вместо ожидаемого
owner-choice в этой беседе и последующего `resume-root` был отдан fresh-process launch блока
`task:plan-run ... P8.9`.

Это не требование audit trail и не неизбежное ограничение авторизации. Очередь решений уже
защищает авторизацию и по умолчанию возобновляет **тот же** root. Дефект находится на стыке
projection/transport: смысл `same-session` теряется при рендеринге, а ожидание owner decision
не отделено от terminal handoff.

Повтор P6.2 показывает, что дефект шире owner-decision: после ложного terminal block executor
рекомендовал новый `plan-design` root, хотя текущая сессия уже содержала все Required Reads,
implementation evidence, clean-HEAD reproduction и достаточный route для bounded repair.
Новая сессия добавляла повторное чтение и риск потерять точную причинную цепочку, не создавая
никакой независимости или capability, нужной для исправления.

### Почему агент завершил ответ

Предыдущий ответ совместил два разных правила без их preconditions:

1. Правильно: `approval_required` нельзя молча разрешить через free prose; необходимо durable
   request.
2. Ошибочно применённое: generated Codex runtime требует native launch-block при executable
   handoff и запрещает завершаться без него.

После записи request я ошибочно интерпретировал parked subject как «следующий executable item» и
подчинился правилу 2. На самом деле он был `decision-pending`: у него нет нового runnable Next,
а его continuation уже зафиксирован как `resume-root`. Следовало отобразить варианты запроса в
той же беседе, дождаться owner choice и продолжить исходный run, не предлагая повторную команду.

Корневое `AGENTS.md` усугубляет чтение: «every finished task and terminal handoff ends with a
launch block» и «fresh-agent-execution» сформулированы широко. Они должны применяться только к
реальному terminal handoff либо carrier с `context_kind=cold-start`, а не к waiting-owner.

## Граница фактов и вывода

Проверены Task source, generated Codex projection, package tests и durable P8.9 request. В
доступном Swissknifeman code нет conversational modal/card emitter: `plan-decisions.py` — это
CLI над JSONL queue. Это **не доказывает**, что UI provider вообще не умеет показать popup; это
доказывает отсутствие связки Task `DecisionRequest` → provider UI → `resolve()` в проверенном
пакете. Конкретный transport write-site должен подтвердить владелец Codex/Claude runtime.

## Требуемое решение

### 0. Ввести единый `session-continuity-controller/v1`

Перед любым runnable handoff, restart recommendation или возобновлением после blocker/runtime
signal один provider-neutral controller обязан выбрать ровно один outcome:

- `continue-root` — продолжить текущий authoritative root/thread;
- `isolated-child-return` — выполнить ограниченную независимую проверку и вернуть evidence в
  текущий root;
- `cold-start-root` — открыть новый root и перечитать durable carriers.

`continue-root` — default. Controller принимает только проверяемые inputs: lifecycle
`active|waiting-owner|terminal`, сохранённые `session_id/run_id`, route/capability compatibility,
provider-attested context-health, уже загруженные Required Reads/evidence, размер оставшегося
bounded work и exact hard-boundary reason. Он также учитывает стоимость cold start: повторные
reads, setup, восстановление causal trace и риск расхождения с uncommitted work.

### Дополнение 2026-08-16: work- и model-aware выбор

Выбор root нельзя делать только по названию команды или общему правилу «новая сессия чище».
Перед handoff controller формирует `session-work-estimate/v1` и привязывает его к
`session-continuity-decision/v1`:

| Поле | Назначение |
|:--|:--|
| `current_route`, `required_route` | provider-attested model/class/effort текущего root и минимум следующей работы |
| `remaining_batch` | item IDs, declared capabilities, implementation/audit/design boundary и exact resume point |
| `continuation_setup` | уже проверенные inputs, tools, fixtures и causal evidence, которые current root может переиспользовать |
| `cold_start_cost` | bounded token/time estimate повторных reads/setup plus risk of losing uncommitted causal state |
| `fresh_route_gain` | только доказанное преимущество другой model/effort/capability; «дешевле» само по себе не gain |
| `context_health` | provider-attested `healthy|insufficient|unavailable`; отсутствие telemetry не считается `insufficient` |
| `decision` | `continue-root|cold-start-root|isolated-child-return`, rationale и recheck point |

Правило выбора:

1. При `active`, совместимом или превышающем current route, `context_health=healthy|unavailable`
   и bounded remaining batch controller выбирает `continue-root`. Переход на более дешёвую модель
   не оправдывает cold start, пока `fresh_route_gain` не превышает `cold_start_cost` и work не
   независима от текущего causal state.
2. `cold-start-root` допустим при provider-attested `insufficient`, несовместимом route/capability,
   physical loss resume либо protocol-mandated independent audit/design root. Тогда receipt обязан
   назвать pinned fresh route и reason; новый root читает только committed checkpoint carriers.
3. Несовместимость следующих частей одного plan не скрывается: controller продолжает совместимый
   suffix batch в current root, а hard-boundary successor получает отдельный cold launch. Нельзя
   обещать «закрыть весь план одной сессией», если Routing уже требует независимый audit/design.
4. Если estimate или context telemetry unavailable, default — `continue-root` до следующего
   durable checkpoint; heuristic fresh launch запрещён. Это сохраняет корректность без
   притворной точности токенового счётчика.

Поле `current_route` не является self-attestation: его источником остаётся existing
provider-thread-state/route receipt. `remaining_batch` берётся из Routing и committed handoff,
а не из текста final ответа.

#### Field application: PROVIDER-CONTRACT-LOCALE P7

На 2026-08-16 P7.1–P7.3 образуют batch `p7-real-first` с minimum
`implementation/high`; текущий P7.1 root attested как `gpt-5.6-terra/high`
(`implementation/high`) и уже держит P5 exact verifier, P6 evidence and P7.1 causal trace.
`fresh_route_gain=0`; current context-health telemetry отсутствует, но не negative. Поэтому
контроллер выбирает `continue-root` для P7.1 и, после committed checkpoints, для совместимого
P7.2/P7.3 suffix. P7.4 отдельно требует `frontier/xhigh` independent audit и по Routing
становится `cold-start-root`; текущая сессия не должна обещать закрытие P7 целиком.

Это решение относится только к исполнимому implementation suffix. В том же P7.1 измеренный
frozen-contract gap (не задано соответствие P4.3 migrated skill rows → capability/workflow/grader)
создал отдельную работу `task:plan-design P7.1`. Для неё `required_route=frontier/high`, а
protocol-mandated design root даёт доказанный `fresh_route_gain`; поэтому это
`cold-start-root: frozen-contract-design`, после которого implementation suffix снова обязан
оцениваться отдельно. Новая сессия здесь вызвана не предпочтением «более дорогой» модели, а
несовместимым routed видом работы и явной границей design/execution.

`cold-start-root` допустим только с одним доказанным reason:

1. контекст действительно недостаточен для оставшейся ограниченной работы, а checkpoint уже
   сохранён в durable carrier;
2. текущий route/capability не покрывает следующий шаг и не может быть безопасно продолжен в
   этом thread;
3. provider потерял физическую session и `resume-root` недоступен;
4. требуется независимый terminal audit/design root, прямо объявленный протоколом;
5. owner явно выбрал pause без возможности resume.

Само по себе окончание sampling turn, слово `blocked`, красная validation, путь вне `Files`,
смена item'а, наличие handoff или требование напечатать launch-block не являются reason для
новой сессии. Неизвестный context-health требует сначала получить evidence или сделать bounded
checkpoint/compaction; неизвестность не превращается автоматически в cold start.

Controller пишет `session-continuity-decision/v1` с outcome, exact reason, evidence IDs,
current/required route, context-health, reuse inputs и оценкой cold-start overhead. Renderer,
handoff, delivery и provider transport только исполняют этот verdict. Они не могут самостоятельно
заменить `continue-root` на fresh command. Для `cold-start-root` lint/delivery отвергают receipt
без reason/evidence; для `continue-root` они отвергают `codex -C ...` и другой fresh-process block.

Для swissknifeman P6.2 ожидаемый verdict фиксирован как `continue-root`: route достаточен,
Required Reads и failure evidence уже в текущем root, repair ограничен Harness↔Task journal
compatibility seam, owner/frozen/public/irreversible boundary отсутствует.

### 1. Ввести явное состояние ожидания владельца

`owner-decision-continuity/v1` должен различать три lifecycle-состояния run:

- `active` — executor выполняет разрешённую работу;
- `waiting-owner` — есть pending durable DecisionRequest, root/run identity сохранены;
- `terminal` — только здесь допустим normal terminal delivery/launch of a successor.

Pending request создаёт `waiting-owner`, не `Next` и не terminal handoff. Новый
`decision-wait-receipt/v1` связывает `plan_id`, `item_id`, `run_id`, `root_session_id`,
`decision_id`, digest canonical action/options, expiry и `continuation.mode=resume-root`.
Он хранит references/digests, а не произвольный raw context.

### 2. Сделать `context_kind` исполнимым

`PlanProviderInvocation` и `render_codex_launch()` обязаны принимать carrier context:

- `same-session` рендерит in-thread invocation/continue action и **не** fresh `codex -C ...`;
- `cold-start` рендерит pinned fresh launch только с declared `cold_start_reason`;
- `waiting-owner` не рендерит command вовсе: provider получает structured owner-decision
  payload.

Удалять защиту route evidence не нужно. Route correction, root eviction и специально
изолированный audit остаются legitimate cold-start cases; например, `plan-audit` уже имеет
отдельную семантику `cold-start-root: audit-root-terminal`. Однако generic `plan-run` не может
воспользоваться этим исключением без exact fallback reason.

### 3. Добавить owner-decision UI bridge и same-thread resume

Provider runtime получает receipt и показывает в **текущей** беседе bounded card/modal:
question, safe evidence summary, option IDs/outcomes, expiry и влияние каждого выбора. Choice
является explicit owner action, а не свободной фразой; bridge materializes signed/provenanced
response, делает `plan-decisions.py claim` + `resolve` с исходным continuation и немедленно
возобновляет `resume-root` execution loop.

Если интерфейс такого action временно недоступен, fallback fail-closed: показать `waiting for
owner decision`, decision ID и варианты без native restart command; не публиковать completion и
не объявлять новый executable item. Physical session loss допускает `cold-start-root` только
после документированной причины, которую уже требует resolver.

### 4. Закрыть pre-final transport gap

Дополнить работу из terminal-final continuity, а не заменять её:

- `waiting-owner` может завершить **sampling turn** structured yield-ом
  `awaiting_owner_decision`, чтобы UI отрисовал card, но это не `final` о завершении работы и не
  terminal handoff;
- transport запрещает completion `final` и launch-block, пока run `active` или
  `waiting-owner`; разрешение выдаёт только terminal receipt;
- после choice transport продолжает тот же root/run automatically. Если transport реально не
  может удержать thread, он сохраняет receipt и показывает resume control с тем же identity, а
  не копируемую новую команду.

Это важное различение делает возможным ответ пользователю во время ожидания без ложного
утверждения, что модель должна бесконечно держать один tool turn открытым.

## Предлагаемая развёртка

1. **Task semantics и fixtures.** Спроектировать `waiting-owner`/receipt, вывести его из
   existing pending queue без переписывания JSONL history, добавить schema/reducer invariants.
2. **Renderer/provider parity.** Исправить `command_render.py`, canonical plan command wording,
   generated projections и tests: `same-session` не может вызвать `codex_launch`; cold-start
   требует reason; `waiting-owner` не печатает launch-block.
3. **Transport bridge.** Найти фактические Codex/Claude card and final write-sites, добавить
   structured `awaiting_owner_decision` event, resolver callback и same-root execution loop.
4. **End-to-end proof и migration.** Прогнать queued P8.9-like fixture и interrupted/resumed
   case; старые pending requests выводить как `waiting-owner` derivation. Удалять legacy queue
   или auto-approve history запрещено.

Slice 1 можно тестировать в `packages/task` изолированно. Slice 3 — внешний provider/harness
owner gate; не следует имитировать его фиксом только в Artifex или текстом скилла.

## Матрица приёмки

| Сценарий | Доказательство |
| --- | --- |
| P8.9-like scope boundary | Создан ровно один durable request; текущий thread показывает owner options, без `codex -C` и без просьбы повторить `$ task:plan-run`. |
| Owner approves | Queue содержит valid claim/response; resolver возвращает исходные root session/run IDs и loop продолжает тот же item. |
| Owner rejects/escalates | Записан exact outcome; work не возобновляется и не подменяется fresh launch. |
| Same-session carrier | Renderer rejects `codex_launch()` for `context_kind=same-session`; provider projection показывает current-thread action. |
| Cold start действительно нужен | Только `resume_available=false` + nonempty fallback reason допускают pinned launch; reason виден в receipt. |
| 40 искусственных boundaries | Для `active`/`waiting-owner` нет completion final и launch-block; есть heartbeat либо `awaiting_owner_decision`. |
| Interrupted/resumed run | После valid owner decision не требуется новое owner approval и не теряется original continuation; route policy действует по explicit pause/renewal rule. |
| Provider parity | Codex и Claude получают одинаковые option IDs/outcomes и same-root semantics. |
| P6.2 bounded validation repair | Controller выбирает `continue-root`; renderer не печатает новую `task:plan-run`/`plan-design` launch-команду, а текущий root выполняет repair и повторяет carrier. |
| Измеренно исчерпанный context | После durable checkpoint controller выбирает `cold-start-root` с `context-budget` evidence и оценкой повторного чтения; без evidence fresh launch запрещён. |
| Совместимый route и сохранённый context | Даже после terminal-looking signal controller учитывает reuse cost и сохраняет текущую сессию, если hard boundary отсутствует. |

## Не входит в решение

- Не считать обычный chat text approval: durable authorization/provenance остаются обязательны.
- Не auto-approve scope, security, frozen-contract или external-state change.
- Не отменять route evidence, item routing и legitimate isolated cold starts.
- Не переписывать чужую историю P8.9 и не закрывать item без решения владельца.
- Не выдавать package-level фиксацию за transport fix, пока не найден real provider final/UI
  write-site.

## Граница исполнения

Документ не меняет Insiders P8.9, swissknifeman P6.2, их journal или provider transport. До
successor implementation корректное ручное поведение такое: сначала применить decision matrix
контроллера; при совместимом route, достаточном контексте и отсутствии hard boundary продолжать
текущий root. Для owner gate — materialize request, сообщить варианты в текущей беседе, записать
выбор через resolver и продолжить `resume-root`. Для P6.2 — восстановить false block forward и
закрыть bounded repair в текущей сессии; не просить владельца заново запускать активный
`task:plan-run` и не отправлять его в `plan-design`.
