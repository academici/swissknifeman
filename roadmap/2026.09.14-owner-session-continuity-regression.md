# Roadmap: Task не должен выдумывать новую Codex-сессию между обычными item'ами

**Статус:** код и локальная доставка проверены в Task 0.17.0; остаток — полевой acceptance, не повторная реализация.
**Критерий запуска:** немедленный: владелец потребовал исправить поведение после
двух ошибочных предложений restart вместо продолжения в текущем root.

## Инцидент

В одной owner-сессии был завершён FlexCRM `FLEX-2 P14.1`. После этого оператор:

1. предложил запустить тот же закрытый `P14.1` в новой сессии;
2. затем предложил отдельный новый launch для `task:plan-close FLEX-2 P14.1`.

Оба ответа противоречат цели владельца: одна сессия может и должна выполнять
один или несколько связанных пунктов. Повторный запуск закрытого item не создаёт
результат, а искусственный restart теряет рабочий контекст и заставляет человека
вручную переносить маршрут, модель и настройки.

## Что на самом деле говорят действующие источники

Это не безопасностное ограничение Task:

- `packages/task/commands/plan-run.md` прямо требует продолжать compatible ready
  successor в том же root и запрещает превращать обычное закрытие item, локальный
  обратимый repair или переход фазы в новую сессию, final либо owner-question.
- `packages/task/docs/continue-first.md` требует закрыть GREEN item и, при
  необходимости, фазу в том же invocation; отдельный `plan-close` текущего item
  не должен быть Next.
- Codex projection `task-plan-design/command.md` запрещает генерировать новый
  `codex` process между обычными item'ами при `continue-root`.
- Решение FlexCRM `D43-independent-app-delivery.md` отдельно уточняет: «один
  item — остановка в чате» не требует новой команды или новой сессии.

Следовательно, сбой — сочетание ошибки оператора и недостаточно жёсткого
runtime/adaptor guard, а не необходимость restart ради модели, effort, sandbox,
approval, плана или closure.

## Причинная цепочка

1. `Exec = plan-run` был отвергнут закрытым enum ещё до product write. Это
   отдельный alias-admission defect из
   `2026.09.14-task-plan-run-exec-alias-admission.md`.
2. Вместо `routing-rejected → local repair → continue-root` оператор слишком
   буквально воспринял lifecycle-ограничение и переключил выполнение на
   неформальный direct path.
3. После GREEN product work оператор прочитал устаревший handoff (`Next: P14.1`,
   `cold-start-root`) как команду создать новый root, хотя он не был обновлён
   именно из-за admission defect и не мог отменить наблюдаемый current context.
4. Затем он сформировал native Codex launch вручную для уже выполненного item,
   вместо того чтобы: (а) продолжить готового successor в том же root; (б) при
   отсутствии successor честно сообщить, что требуется scope следующего item;
   (в) печатать новую команду только по явному owner-запросу на новую сессию или
   typed `cold-start-root`/wait boundary.

## Цель

Сделать continuous owner session исполняемым default, а не фразой в документации.
Task должен помогать вести несколько связанных item'ов в одном root и не
предлагать повторный запуск или новый процесс без доказанной границы контекста.

## Предлагаемое исправление

1. Ввести единый `next-session decision` перед любым user-facing native launch.
   Он принимает current continuity, terminal item, persisted successor и exact
   owner intent; для закрытого item возвращает запрет на его повторный запуск и
   на отдельный `plan-close`.
2. По умолчанию после GREEN item закрывать item/фазу и искать совместимый ready
   successor в том же root. Отсутствие successor — это `next-scope-needed` в
   текущей сессии, не `cold-start-root` и не повод подставлять прошлый item.
3. Легаси `handoff.md` с `fresh session`/`cold-start-root` не может перебить
   attested current continuity, если это не свежий typed decision с named reason
   и checkpoint. Lint должен диагностировать stale handoff после
   `routing-rejected` или terminal item.
4. В Codex/Claude final renderer запретить вручную собранную команду для current
   terminal item. Native launch разрешён ровно при explicit owner request на
   новую сессию либо verified `cold-start-root`/`waiting-*`; тогда он обязан
   адресовать только новый runnable subject.
5. В agent-facing guidance заменить эвристику «item закончился → handoff» на
   простое правило: продолжай текущий root, пока владелец не просит паузу или
   reducer не доказывает boundary. Правила — помощь в выборе следующего действия,
   не повод остановить разработку.

## Acceptance

- Один root последовательно закрывает два compatible ready item'а без final,
  launch-block и нового процесса.
- После последнего item фаза закрывается в том же invocation; `plan-close` и
  повтор `plan-run` этого item не предлагаются и не рендерятся.
- При отсутствии следующего scope агент остаётся в текущей сессии и просит либо
  проектирует следующий item; он не выдаёт команду старого item.
- Stale handoff с legacy `fresh session` не создаёт новую сессию без нового
  typed continuity decision.
- Только явная просьба владельца о новой сессии либо доказанный
  `cold-start-root`/wait boundary выдаёт один native launch для нового subject.
- Regression tests покрывают `plan-run`, `plan-exec`, `plan-close`, Codex и
  Claude projections, closed single-item phase, multi-item batch и stale handoff.

## Границы

Не ослаблять authority, scope, route evidence, security или external wait gates.
Не запускать следующий product item без требуемого owner scope. Исправление
меняет только ложный session boundary и повтор закрытого subject.
