# Синтез 04 — модель драйвера exec-волны (фаза P4)

**Слой 2 (авторский синтез).** Стоит на: `brief/00-brief.md` §P4 (слой 0),
`findings/P4-headless-envelope-2026-07-31.md`, `findings/rag-2026-07-31-native-skill-fields.md`
§5–§6, `findings/repo-recon-2026-07-31.md` §10 (слой 1). Назначение: свести четыре части
ядра к исполнимой конструкции — кто что читает, кто выносит вердикт, кто пишет строку в
журнал и чем именно принимается фаза. Всё несущее отсюда получило адрес в D-логе (D28–D35)
и в items P4.1–P4.6.

## 1. Четыре части и граница между ними

| Часть | Отвечает за | НЕ отвечает за |
|:--|:--|:--|
| `plan_reader` | очередь фазы: item'ы в порядке Status Board, статус, маршрут, ячейка `Exec`, форма `Next`, причина отказа вождения | запуск, вердикт, запись |
| `worker` | один процессный прогон под таймаутом + дефенсивный разбор конверта + класс исхода прогона | вердикт по item'у, ретрай, журнал |
| `gate` | ОДИН из трёх вердиктов по закрытой таблице признаков | починку плана, ретрай, `plan-close` |
| `journal` | дозапись событий, которых воркер записать не мог + сводка волны | новый формат журнала, второй счётчик |

Связь строго последовательная по данным: `plan_reader` → `worker` → `gate` → `journal`.
Это и есть основание, по которому фаза **не заявляет оркестрацию** (`plan-protocol` §7:
критерий «N≥3 items с независимым scope» не срабатывает — Inputs каждого следующего item'а
ссылаются на Deliverables предыдущего внутри ОДНОЙ фазы).

## 2. Кто читает план — закрытый список источников

Ключевая находка recon'а: **всё, что драйверу нужно прочитать из плана, уже имеет машинного
читателя в репозитории.** Писать пятый парсер плана — прямое нарушение запрета второго
носителя факта.

| Факт | Источник | Проверено |
|:--|:--|:--|
| модель плана (Meta, Status Board, фазы, все 16 полей каждого item'а, поля `handoff.md`) | `python3 packages/task/scripts/plan-lint.py <plan-dir> --json` | `plan_lint.py:2168–2192` — `lint_plan` возвращает `{meta, status_board, phases{items{fields}}, handoff{fields}}`; `main()` печатает `{"plans": …}` |
| маршрут item'а из `## 3. Routing` (`model_class`/`effort`) | `python3 -m task.task_contract build --plan-dir … --item …` → `route.required` | живой прогон на `P3.1` → `{"required": {"effort": "high", "model_class": "implementation"}}` |
| селектор провайдера по нейтральному классу | `packages/task/configs/command-routing.json` → `mappings.claude-code.class_selectors` / `effort_selectors` / `invocation_binding.template` | `implementation → ["sonnet"]`, шаблон `/{command_id} {arguments}` |
| запись события | `python3 -m task.journal append …` | `journal.py:326–366` (CLI), `:47–50` (14 обязательных полей) |

**Единственная дыра.** `task_contract._find_routing_row` (`task_contract.py:223–305`) читает
из строки §3 только пару `<model>/<effort>` — колонку **`Exec`** он не возвращает, а
`plan_lint` секцию §3 не парсит вовсе (§9 «Back-compat»: «`plan-lint` does not parse section
3»). То есть читателя колонки `Exec` в репозитории **не существует**, и драйвер обязан
завести его сам. Это не дублирование (дублировать нечего), но мехáника поиска строки
(`Items` = один item либо диапазон одной фазы) у компилятора уже есть — её драйвер зеркалит
и накрывает drift-тестом на общей фикстуре.

**Почему это важно, а не педантизм.** §9 разрешает заполненной колонке `Exec` ужесточать
деривацию: `manual` легален при любой паре `model/effort`. Драйвер, выводящий право вождения
ТОЛЬКО из пары, погнал бы item, который план запретил гнать, — исторический класс дефекта F7
(«колонка как дыра в гейте»). Отсюда правило D31: **вождение только при дословном
`Exec = plan-exec`**, никакой деривации на стороне драйвера; несовпадение пары и колонки —
`ROUTING-INCONSISTENT` и стоп.

## 3. Межпакетная граница: процесс, а не импорт

`bin/harness:60–62` кладёт на `PYTHONPATH` ровно `packages/harness/lib` и (опционально)
корень монорепо ради `core`. Пакета `task` там нет. Три пути:

- **импортировать `task.*`** — сломает standalone-раскладку harness молча (пакет собирается и
  раздаётся отдельно; `validate.sh:14–21` прямо держит standalone-ветку живой);
- **склеить `sys.path`** к `packages/task/lib` (прецедент есть — `packages/maind/lib/maind/provider_deploy.py:239`)
  — переносит скрытую зависимость на раскладку каталогов;
- **звать процессом** — те же три команды, которые план-протокол уже предписывает людям и
  командам (`plan-exec.md` шаг 3 зовёт `python3 -m task.journal append` именно так).

Выбран третий (D29). Цена — накладные на запуск процесса (порядок десятков мс на item при
прогонах в минуты) и обязанность fail-loud при отсутствии пакета: «шаг недоступен» вместо
тихой деградации — тот же приём, что `plan-exec.md` §2 применяет к недоступному
`task.task_contract`.

## 4. Вердиктный гейт: три исхода, четыре источника признаков

Вердикт — **вывод**, а не машина состояний: `decide` вне скоупа (D9), и «драйвер потребляет
`decide`» в этом плане не утверждается ни разу.

Источники признаков: (1) класс исхода прогона от `worker`; (2) `plan-lint --baseline <SHA до
прогона> --gate new`; (3) git-топология двух коммитов (§8 «Item close order»); (4) статус
item'а и его поля после прогона (через `plan_reader`).

| Признак | Вердикт |
|:--|:--|
| конверт `type=result` + `is_error=false` + exit 0, новых ошибок линтера 0, оба коммита на месте в правильном порядке, статус `🟢` | **GREEN** |
| статус `🟠`, либо непустой `permission_denials`, либо непустой `Pending Work`/`Known Deviations`, либо доехал только item-коммит без bookkeeping, либо только новые WARNING | **ATTENTION** (волна продолжается, item называется поимённо) |
| новые ERROR линтера > 0 · статус `🔴` · `Escalation Needed: yes` · маркер `ESCALATION` в Completion Notes · коммитов нет вовсе · таймаут · битый/не-`result` конверт · `is_error=true` · признак квоты | **RED** (волна останавливается) |
| `Exec` ≠ `plan-exec` · `ROUTING-INCONSISTENT` · форма `Next` вне enum §8 | **RED** до запуска (воркер не спавнится) |

Два правила поверх таблицы: **любой RED побеждает** (вердикт не «смягчается» набором зелёных
признаков) и **сомнение → более строгий вердикт** (тот же fail-safe, что «doubt → `full`» в
§9). Отдельно: если `--baseline` недоступен, линтер по своему же коду деградирует к
`gate=all` (`plan_lint.py:2379–2386`) — драйвер обязан это распознать и пометить класс
оценки, а не выдать деградацию за чистый счёт.

Ретрая нет ни одного тира (D9): quota/transport — это RED + пауза + эскалация.

## 5. Журнал: почему драйвер пишет НЕ каждый прогон

`/task:plan-exec` пишет журнал сам — старт-запись `in-progress` (шаг 3 `plan-exec.md`) и
финал-запись `closed-green`/`closed-deviations` (шаг 7). Драйвер, пишущий «свою» строку на
каждый прогон, удваивал бы историю плана: два `closed-green` на один item — и любая будущая
статистика («сколько волн», «доля вмешательств», критерий OQ-3) считалась бы по завышенному
знаменателю.

Правило (D32): **драйвер пишет строку только там, где сессии воркера не было или она не
дошла до close-протокола** — `routing-blocked`, таймаут, транспортный сбой, квота, `no-op`
(прогон не сдвинул статус), RED без терминального статуса. Дискриминатор строк драйвера —
штатное поле схемы **`run_id`** (у строк воркера оно `null`: `plan-exec.md` его не
передаёт), плюс префикс `[wave <run_id>]` в `note`. Сводка волны считается по журналу и
конвертам — второго счётчика драйвер не заводит.

Цена ошибки здесь необратима и это меняет тир item'а: журнал append-only, а
schema-invalid строку **нельзя переписать** — только owner-gated sidecar через явную D-запись
(`plan-protocol` §2, D51). Отсюда правило «при сомнении строка НЕ пишется, возвращается
отказ» вместо «подобрать похожее значение из enum'а».

## 6. Приёмка: почему фикстура, а не живая фаза

Бриф говорит «приёмочный прогон». Буквальное чтение — прогнать волну по живой фазе плана.
Разбор упирается в два препятствия:

1. **Phase-first.** На момент исполнения P4.6 незакрытые `Exec = plan-exec` item'ы лежат в
   фазах **P5/P7**. Волна по ним означала бы, что P4 закрывает items чужой фазы и держит
   себя открытой поперёк порядка фаз.
2. **Недоказанный инструмент на боевых данных.** Первый в жизни прогон драйвера закрывал бы
   реальные items реального плана — с двумя коммитами, правкой Status Board и записями в
   append-only журнал, которые нельзя откатить «как будто не было».

Решение (D33) — приёмка из двух прогонов: **(a)** `--dry-run` на РЕАЛЬНОЙ фазе живого плана
(очередь, маршруты, точный argv, причины отказов — без спавна и без единой записи; read-only
проверяется `git status --porcelain`), **(b)** сквозная волна на **изолированном фикстурном
плане** во временном git-репозитории с настоящими `claude -p`-воркерами. Первое доказывает,
что чтение работает на боевом входе; второе — что цикл замыкается end-to-end.

Цена решения названа явно: число «доля вмешательств» из фикстурной волны — **синтетическое**.
Критерий OQ-3 («N волн» для остатка `artifex`) обязан нести класс этого числа, а боевая
статистика накапливается штатно — журналом при exec-волнах P5/P7, которые P7.1 и читает.

Прецедент в этом же плане: P3.1 строит стенд на изолированной фикстуре ровно по тем же
соображениям, и P2.2/P3.2 гейтят раскатку пилотом.
