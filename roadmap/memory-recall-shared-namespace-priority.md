# Roadmap: приоритет общего namespace в `maind_memory_recall` (mid-session recall)

**Статус:** 🟢 закрыто (2026-08-06, task:fix). Асимметрия обнаружена 2026-08-06 при разборе
подозрения владельца «токенов на одинаковые задачи стало уходить больше» (проект Agelto).
Внедрено п.6 ниже: `_recall_union` капает shared-scope'ы `RECALL_SHARED_LIMIT=40` (private —
без капа, `RECALL_LIMIT=200`), см. `packages/maind/lib/maind/memory.py` (константа рядом с
`RECALL_LIMIT`) и `packages/maind/lib/maind/mcp.py::_recall_union`. Тест:
`packages/maind/tests/test_mcp.py::TestToolCalls::test_recall_union_private_survives_large_shared_namespace`
(+ `packages/maind/tests/fixtures.py` — фейковый `/agentmemory/search` теперь уважает `limit`).

**Происхождение:** D10 (`2026.07.12-CONTEXT-ECONOMY`) ввёл принцип «project-only по умолчанию,
межпроектное — явно, не проглатывается», но применил его только к SessionStart-дайджесту.
Интерактивный MCP-recall (`maind_memory_recall`), который реально расходует токены на каждый
запрос Claude к памяти, этот принцип не унаследовал.

---

## 1. Что нашли

Два разных пути чтения памяти с разной политикой:

- **`_cmd_digest`** (`packages/maind/lib/maind/memory.py:596-665`) — дайджест в SessionStart-хук.
  По умолчанию `shared_max=0`: `ns:axioma` в дайджест НЕ попадает вообще, поднимается только
  явным `--scope ns:axioma`. Комментарий в коде прямо называет это D10.
- **`_recall_union`** (`packages/maind/lib/maind/mcp.py:196-215`) — то, что вызывает Claude
  командой `maind memory recall "<тема>"` / тулом `maind_memory_recall` посреди любой сессии.
  `project:<id>` разворачивается в `private + ns:<группы> + global` (`namespaces.recall_scopes`),
  каждый scope опрашивается с одним и тем же `RECALL_LIMIT=200` (`memory.py:288`), результат —
  просто конкатенация + дедуп по тексту. **Приоритета/веса приватному scope нет.**

Итог: дайджест на старте сессии бережёт бюджет, а каждый последующий recall внутри сессии — нет.
Асимметрия не была намеренным дизайн-решением, а недосмотром при внедрении D10.

## 2. Замер (2026-08-06, воспроизводим)

```
maind memory count --project agelto
→ project:agelto=2, ns:axioma=47, global=3 (уникальных 51)
```

Собственная память Agelto — **2 записи**, общая (axioma) — **47**, т.е. в 23 раза больше.
Live-запросы к демону (`maind memory recall --project agelto "<тема>"`):

| Запрос | Всего строк | Из них `ns:axioma` | Из них `project:agelto` | Байт ответа |
|:--|--:|--:|--:|--:|
| «память» | 3 | 1 | 2 | 1 561 |
| «workflow» | 7 | 6 | 0 | 9 334 |

На втором запросе — характерном для проекта без специфичной памяти по теме — **6 из 7
результатов и почти весь объём ответа (~9,3 КБ ≈ 2,3–2,4К токенов по грубой оценке 4 симв/ток)
пришли из общего axioma-пула**, не из памяти самого Agelto. Это структурно ожидаемо при
дисбалансе 2:47 — маленький приватный scope почти всегда «тонет» в общем при отсутствии веса.

## 3. Выгода по токенам — оценка, не гарантия

Известно из замера: один такой recall-вызов — уже ~2,3К токенов, большей частью общего контента
низкой релевантности задаче конкретного проекта. Если применить к `_recall_union` тот же принцип,
что и к дайджесту (shared по умолчанию не тянется / тянется с малым капом, поднимается explicit
`--scope ns:axioma` при реальной кросс-проектной задаче), экономия на **одном** таком вызове —
грубо 70–85% его объёма (по замеру выше).

Чего НЕ хватает для точного вердикта (по конвенции репо — не внедрять спекулятивно):
- **частота вызовов** `maind_memory_recall` за сессию/день по всей экосистеме — не измерена;
  без неё нельзя перевести «экономия на одном вызове» в «экономия на сессию»;
- доля вызовов, где ответ реально доминируется axioma (зависит от размера приватной памяти
  конкретного проекта — Agelto с 2 записями хуже среднего, у более старых проектов приватный
  пул больше и дисбаланс может быть меньше).

Направление эффекта не вызывает сомнений (общий пул объективно больше приватного и не имеет
верхней границы участия) — под вопросом только масштаб выгоды в реальном использовании.

## 4. Возможное решение (если дойдём, дизайн не финальный)

- В `_recall_union` — аналог `shared_max`/`shared_max` из `select_digest_items`: private-scope
  результаты всегда полностью, shared (`ns:*`, `global`) — капом (напр. top-N по BM25-score) или
  общим пониженным лимитом вместо равного `RECALL_LIMIT=200` на каждый scope.
- Не убирать общий scope из recall совсем — он несёт реальную кросс-проектную ценность
  (`[maind:ecosystem-link]`, общие решения); ограничить, а не выключить.
- Не трогать явный `--scope ns:axioma` (у него уже нет unwanted expansion, см.
  `_recall_union` docstring: «явно запрошенный scope не расширяется»).

## 5. Критерий внедрения

Любое из:
- Измеренная частота `maind_memory_recall`/сессию (напр. через `session-observer` или
  `skiller budget`) показывает, что recall — заметная доля контекстного бюджета сессии
  (не разовый факт, а систематика);
- Повтор жалобы владельца на рост токенов на «одинаковые задачи» ещё на одном проекте с похожим
  дисбалансом private/shared памяти;
- Кто-то меняет `_recall_union`/`select_digest_items` по другому поводу — тогда унификация
  политики (digest и recall — одна модель приоритета) становится почти бесплатной попутно.
