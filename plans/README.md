# plans/ — исполняемые мастер-планы монорепо

Каталог мастер-планов по протоколу `plan-protocol`: «сильная» модель (opus) проектирует план,
«дешёвая» (sonnet/haiku) исполняет его items без доступа к чату планирования. Каждый план —
каталог `plans/<PLAN-ID>/` с тремя видами файлов: `plan.md` (Meta, правила, Status Board, логи),
`phases/Pn.md` (по файлу на фазу: контекст + items + phase handoff), `handoff.md`
(rolling-указатель «где мы», перезаписывается).

- **Протокол (SSOT):** скилл `packages/skiller/skills/general/plan-protocol/` — схемы,
  6 канонических статусов, routing-матрица, эскалация; шаблоны — его `snippets/`.
- **Команды:** `/task:plan-design` · `/task:plan-exec` · `/task:plan-close` · `/task:plan-audit`.
- **Валидатор:** `python3 packages/task/scripts/plan-lint.py plans/<PLAN-ID>` (или `plans/` —
  все планы разом); exit 0 = формат чист. Из plugin-контекста команды зовут его через
  `${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.py`; нет переменной — используй прямой путь выше.

**ПРАВИЛО MD-only:** источник истины плана — только Markdown с жёсткими маркерами.
Любой JSON — производный артефакт (`plan-lint --json`), руками не правится и не хранится.

## Принципы кросс-плановой работы (решение владельца 2026-07-25)

**Носитель — ЭТА секция, единственный.** Три живых плана на неё ССЫЛАЮТСЯ из своих
`## 2. Execution Rules` и не копируют текст: копия принципа немедленно разойдётся с оригиналом
(рамка репо «единый источник истины > копий»). Принципы обязательны для всех живых планов и для
кросс-планового аудита этапа C.

Владелец сформулировал четыре: **нет неприкасаемого кода** · процессы **выверены, чётки,
обоснованы** · **никто никому не мешает** · всё **легко расширять и изменять**. Ниже они
переведены в проверяемые инварианты — интенция аудитом не проверяется, инвариант проверяется.
Каждая находка аудита обязана называть номер инварианта.

**Как принципы соотносятся с закрытыми решениями.** Они НЕ отменяют ни одной закрытой D-записи
сами по себе и не «снимают заморозки как класс» (это отклонено владельцем в том же диалоге). Они
меняют то, что аудит ПРОВЕРЯЕТ. Инвариант, столкнувшийся с закрытым решением, идёт в отчёт
находкой — решение о реопене принимает владелец.

### I. Нет неприкасаемого кода — граница обоснована, названа и ПРОХОДИМА

- **И1.** Каждая формулировка запрета в ТЗ item'а (`запрещено`, `не трогаем`, `чужая поверхность`,
  `заморожено`, `правка запрещена`) несёт ТРИ вещи: **владельца** поверхности · **причину**
  границы · **проход** — что именно делает исполнитель, если правка всё же нужна (эскалация → D#,
  cross-plan гейт, реопен фазы). Абсолютный запрет без прохода = находка.
- **И2.** Заморозка — не свойство файла, а **состояние с версией**: у каждого замороженного
  артефакта объявлен механизм расширения (по умолчанию **аддитивный**) и носитель версии.
  «Заморожено навсегда» не существует; «заморожено до X» — легально, если X назван.
- **И3.** Граница «чужая поверхность» называет **план И item** владельца, а не только пакет: иначе
  проход формально есть, но непроходим — эскалировать некому.

### II. Никто никому не мешает — у каждой общей поверхности владелец и порядок

- **И4.** Любой файл в `Files` у ≥2 живых items (в том числе разных планов) имеет названного
  владельца правки и порядок, и этот порядок записан в ТЗ **обоих** концов — не только в
  `roadmap.md` или в этом README. Односторонняя запись = находка (исполнитель второго конца её не
  прочитает).
- **И5.** Слепая зона машинного гейта = **0**, а носители, которых гейт не видит по построению
  (корневые файлы без `/` в пути — `CLAUDE.md`, `AGENTS.md`, `CHANGELOG.md`, `config.json`:
  `cross-plan-files.py::normalize()` отбрасывает такие токены), перечислены явно со своими
  писателями и проверяются ЧТЕНИЕМ. Невидимый носитель без явного перечня = находка.
- **И6.** Ни одна пара живых планов не держит **противоречащих** решений об одной поверхности.
  Противоречие — блокер до его снятия D-записью, а не «разрулим по ходу исполнения».

### III. Выверено, чётко, обосновано

- **И7.** Каждый несущий пункт несёт RAG-маркер из закрытого enum трёх значений, и `RAG:—` не
  стоит ни на одном ВНЕШНЕМ факте (версия/API, «ещё актуально», рынок, возможности чужого сервиса).
- **И8.** **Премиса проверяется до закрытия вопроса, а не после.** Два датированных прецедента в
  одном плане: `2026.07.25-ECO-OPT` D75 (ложный несущий факт прожил в детализированном ТЗ целый
  заход) и D83 (премиса owner-вопроса опровергнута замером ДО его исполнения). Практически: вопрос
  владельцу предъявляется **с числом**, а не с рассуждением; вердикт на сводке субагента
  предъявляет первоисточник (D53).
- **И9.** Каждый гейт **диагностичен**: fail-closed называет объект и причину. Гейт, который
  краснеет без имени объекта, отключают — и это наблюдённый режим отказа, а не гипотеза.

### IV. Легко расширять и изменять

- **И10.** Расширение **аддитивно по умолчанию**: новый гейт, поле, статус или словарь не делает
  невалидными артефакты уже живущих планов и флота. Прецеденты отклонения ради этого инварианта —
  D42/D43/D44 `2026.07.25-ECO-OPT` (седьмой статус, пятая колонка D-лога и 17-е поле item'а
  отклонены именно так).
- **И11.** У механизма, повторённого **≥3 раз дисциплиной вместо инструмента**, объявлен порог
  выноса в канон, и порог проверяется. Текущее состояние: связок «держится ПОРЯДКОМ, не
  инструментом» — **семь** (порог перейдён, кандидат в roadmap ECO-OPT); рэтчет-файлов — два
  (порог 3, D50).
- **И12.** У каждой хеш-записи, метрики и артефакта провенанса есть **названный потребитель**;
  запись без потребителя = `provenance theatre` и подлежит снятию, а не сохранению «на будущее».

## Кросс-плановая последовательность (выход этапа C, 2026-07-25)

**Как читать.** Это исполнимый маршрут этапа D: сквозной порядок items трёх живых планов,
собранный по фактическим `Files` и гейтам ТЗ (не по заголовкам фаз). Такты открываются гейтами;
**треки внутри такта независимы и идут параллельно, внутри трека порядок строгий**; каждый шаг
называет гейт (если есть) и следующий шаг. Чередование планов — ожидаемое свойство маршрута.
Сокращения: **AR** = `2026.07.24-AGENT-RELIABILITY` · **ECO** = `2026.07.25-ECO-OPT` ·
**FM** = `2026.07.18-FOREMAN`.

**Дисциплина сопровождения** (без неё список дрейфует — наблюдённый режим отказа ручных
последовательностей, RAG:✅ 2026-07-25 perplexity): (1) перед КАЖДЫМ item —
`python3 plans/cross-plan-files.py --strict`; **правило чтения его кода возврата (Ф9): exit 1
сам по себе НЕ стоп** — инструмент возвращает 1 при ЛЮБОМ живом пересечении, а 19 известных
пересечений накрыты владельцами и порядком; стоп — только НОВОЕ пересечение против перечня 19
или пересечение без владельца/порядка (до исполнения payload D формулировки «`--strict`
зелёный» в ТЗ читаются именно так); (2) после закрытия каждой ФАЗЫ любого плана хвост
этой секции пересобирается по фактическому состоянию (правка секции + строка Update Log
затронутого плана); (3) зависимость, всплывшая на исполнении, дописывается в ТЗ **обоих** концов
(И4), а не только сюда; (4) **автопродолжение:** сессия, закрывающая item/фазу, помимо штатного
обновления `handoff.md` своего плана СВЕРЯЕТСЯ с этим маршрутом и в финальном сообщении выдаёт
следующий шаг маршрута — номер шага, команду и модель/effort — даже когда следующий шаг в
