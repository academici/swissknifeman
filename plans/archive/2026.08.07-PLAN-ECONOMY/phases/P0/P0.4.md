### P0.4 — Закрыть учёт корней в `sweep` и снять машинный замер по всему живому флоту планов

**Intent:** Сначала закрыть учёт корней входа в `plan-weight.py sweep` (перехват недоступного корня + top-level `roots[]` с закрытым enum статусов и счётчиками, тесты на три класса корня), затем прогнать инструмент по всем корням планов флота, получить распределение веса обязательного чтения ПО ПУНКТАМ (а не по планам, как в первичном замере), зафиксировать машинный дамп и написать отчёт, честно разделяющий резолвленное и нерезолвленное по закрытой таксономии.
**Why:** Порог (P0.5) выбирается из распределения, а не из одного числа, и распределение обязано быть по пунктам: гейт D2(а) меряет вес ЛЮБОГО пункта, а первичный замер `findings/00-…` считал пол по планам и не включал `Required Reads` вовсе. Без честной доли нерезолвленного порог будет выбран по заниженным числам (митигация pre-mortem #4). Учёт корней предшествует прогону не из аккуратности: сегодня один недоступный корень роняет прогон ЦЕЛИКОМ непойманным `PermissionError` и уносит все остальные корни, а читаемый корень без планов исчезает из вывода бесследно — то есть условие закрытия этого item'а («каждый корень либо померян, либо явно помечен недоступным») сегодня не проверяемо машинно ни в какой форме (RAG:— repo-grounded: `findings/16-…` O1–O3, O5; `packages/task/lib/task/plan_weight.py:573–597`). Решение D110, граница правки — D111, провенанс и состав замера — D112.
**Scope Included:** Правка функции `sweep()` и её ветки печати в `main()` по форме `research/13-…` §3; тесты на три класса корня; манифест корней флота с провенансом; прогон инструмента; машинный дамп результата; отчёт-findings по предписанному скелету; сводка по категориям пробелов, по статусам корней и по корням без планов.
**Scope Excluded:** Любые правки планов и `Required Reads` (D3); выбор и обоснование порога (P0.5); режим ingestion манифеста в CLI (отклонён D110); ЛЮБАЯ правка `packages/task/lib/task/plan_weight.py` вне `sweep()`, её печати и тестов (граница D111: `measure_item`, `measure_plan`, `Measurer`, оценщик, таксономия пробелов пункта не трогаются — потребность в такой правке есть основание остановиться и реопенить P0.3, а не патчить здесь); правка `plan_lint.discover_plan_dirs` (владелец другой; пре-существующий дефект среды `plans/.claude`/`plans/__pycache__` чинится в owning-источнике, не здесь); порог по `dense_ascii_share` (D109 — его замораживает P0.5).

**Implementation Rules:** - **Шаг 1 — учёт корней в `sweep()`, форма задана и не изобретается.** Top-level ключ `roots` — список записей В ПОРЯДКЕ АРГУМЕНТОВ (не сортировать: порядок входа и есть соответствие манифесту), запись — `{"root": <аргумент дословно>, "status": …, "discovered": <int>, "measured": <int>, "failed": <int>, "detail": <строка|null>}`. Enum статусов ЗАКРЫТ и описывает ТОЛЬКО резолвинг корня: `resolved` (`discover_plan_dirs` вернул список, в том числе пустой) · `unreadable` (вызов бросил `OSError`, включая `PermissionError`, — перехватить и продолжить с остальными корнями) · `missing` (вернул `None`). Четвёртый статус НЕ заводится: «корень читается, планов нет» — это `resolved` с `discovered: 0`. `totals` получает срез `totals["roots"] = {"total", "resolved", "unreadable", "missing"}`.
- **Один факт — один носитель.** `roots[]` становится ЕДИНСТВЕННЫМ носителем исхода КОРНЯ; сегодняшняя запись о нерезолвленном корне из `errors[]` УХОДИТ, `errors[]` остаётся носителем исхода ПЛАНА (записи с ключом `plan_dir`). Ключ `unreadable_roots` НЕ заводится (D110).
- **Человеческий режим печати обязан называть то же, что машинный:** `НЕ ИЗМЕРЕН: <root>: <detail>` для `unreadable`/`missing`, `БЕЗ ПЛАНОВ: <root>` для `resolved` с `discovered == 0`, счёт корней — в итоговой строке. Молчание в человеческом режиме — тот же дефект, что молчание в JSON.
- **Тесты — три класса корня отдельными кейсами** (недоступный на чтение каталог; читаемый каталог без планов; несуществующий путь) плюс кейс «недоступный корень НЕ мешает померить соседний здоровый» (регрессия на O2) плюс кейс сходимости `sum(measured) == totals["plans"]`. Кейс недоступности снимает права `chmod 000` во временном каталоге и возвращает их в `tearDown` (иначе временный каталог не удалится); если среда прогона выполняется от root и `chmod 000` не даёт `PermissionError` — кейс не подгоняется под среду, а помечается `skipTest` с явной причиной.
- **Шаг 2 — манифест корней: явный файл с провенансом.** `artifacts/fleet-roots.json` — `{"generated_at": "<ISO-дата>", "session_repo_head": "<короткий sha этого репозитория>", "roots": [{"path": …, "project": …, "expected": "<что там ожидается>", "revision": "<короткий sha HEAD чужого репозитория|null>", "revision_note": "<почему null: не git-репозиторий / корень недоступен>"}]}`. Ревизия чужого корня обязательна, потому что числа по чужим корням не пинятся git-ref'ом ЭТОГО репозитория (D112, `plan-protocol` §8 D53): без неё замер невоспроизводим. Не получена — `null` + причина, ВЫДУМЫВАТЬ НЕЛЬЗЯ.
- **Шаг 3 — прогон:** корни передаются `sweep` В ПОРЯДКЕ манифеста, только в дефолтном режиме оценки (`--exact` в этом item'е не используется — D11), вывод `--json` идёт в `artifacts/fleet-weight.json`. Аргументы формируются из манифеста программно (`python3 -c` → список), а не голым `$(…)`-разворотом, если хоть один путь содержит пробел.
- **Единица распределения — пункт**, не план. В дампе на каждый item: план, фаза, id, вес резолвленного, состав файлов, категории пробелов.
- Отчёт пишется по фиксированному скелету, чтобы его можно было потребить в P0.5 без интерпретации: (1) что и когда мерили, каким инструментом, какой калибровкой (id/дата артефакта) и на каких ревизиях — своей и чужих корней; (2) охват — сколько корней и с какими статусами, сколько планов, фаз, пунктов; **корни `resolved` с нулём планов перечисляются поимённо** (объявленный несущим планы корень с нулём — находка, а не пустая строка); (3) распределение веса по пунктам — p50/p90/p95/max, отдельно по «здоровым» и «крупным» планам, и **отдельно по живым и по архивным планам** (детерминированное разделение по сегменту пути `/archive/`, D112); (4) файлы, превышающие лимит одного чтения, — перечень, **разделённый по гейтам** (`size_bytes` / `tokens` / оба, D107): сколько файлов ловит каждый гейт по отдельности и сколько ловил бы только один из них; (5) пробелы по четырём категориям с долями; (6) **распределение `dense_ascii_share` по обязательным путям чтения** (D109) — сколько файлов и в каких долях, попадает ли плотный ASCII в `Required Reads` вообще, и какие именно файлы дают верхние доли; это ВХОД решения P0.5 о реокалибровке, поэтому раздел приводит числа, а не оценку; (7) что этот замер НЕ доказывает.
- **Две оси недоступности не смешиваются.** Статус корня `unreadable` (корень ВХОДА `sweep`) и пробел пункта `unreadable_root` (`repo_root` конкретного плана) — разные факты; отчёт называет их раздельно и не складывает. Смешение этих осей и породило эскалацию этого item'а.
- Раздел (7) обязателен и должен явно сказать: числа по составу — **нижняя оценка** (нерезолвленные `Required Reads` не учтены), числа по токенам — **верхняя оценка** (по построению калибровки), И назвать границу применимости этой верхней оценки: она доказана на корпусе прозы планов и опровергнута на плотном ASCII (`findings/15-…` §5), поэтому строки с высоким `dense_ascii_share` из раздела (6) НЕ несут гарантии «оценка не занижает». Замолчать любую из трёх асимметрий = выдать оценку за измерение. Там же называется дефект среды этого репозитория (`plans/.claude`, `plans/__pycache__` распознаются как каталоги планов и попадут в `failed` корня `swissknifeman/plans`) — как дефект среды, а не как пробел флота.
- Дамп `fleet-weight.json` — генерируемый артефакт (root.generated-artifacts): руками не правится, пересобирается прогоном.
- **Ни один файл в `plans/` ДРУГИХ проектов не изменяется и не создаётся (D3)** — чужие корни только читаются. Правка собственного пакета `packages/task/**` разрешена ровно в границах `Files` и D111.
