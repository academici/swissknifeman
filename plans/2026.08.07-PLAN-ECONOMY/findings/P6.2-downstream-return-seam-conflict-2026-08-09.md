# P6.2 — downstream record conflicts with return reducer

## Reproduction

1. Add the real producer input `phases/P0/P0.1.md` to fixture consumer `P1.1`.
2. Run `python3 packages/task/scripts/plan-downstream.py --plan-dir
   packages/task/tests/data/plan-v2 --item P0.1 --record --json`.
3. Run `python3 packages/task/scripts/plan-views.py returns --plan-dir
   packages/task/tests/data/plan-v2 --json --gate`.

Step 2 writes the required item-scoped `unknown` downstream finding keyed by consumer-spec SHA-256
and producer commit. Step 3 fails with `seam carrier не читается` on that record: the current
`plan_returns` reducer treats every finding as a return-seam carrier and rejects the downstream-gate
frontmatter.

## Why this blocks P6.2

P6.2 must record `green`, `red`, and `unknown` results on every producer close, while terminal
escalation qualification continues to use `plan_returns`. The required record therefore makes a
subsequent generated view fail. Adding a return-specific `file`/seam field to a downstream contract
record would alter a frozen carrier; silently filtering it in `plan_returns` would change a file
outside P6.2's declared scope. The item explicitly requires escalation rather than an in-place
contract repair in this case.

## Required redesign

`task:plan-design 2026.08.07-PLAN-ECONOMY P6.2` must decide and pin the ownership boundary: either
the return reducer selects only explicit return-seam records, or downstream records get a sanctioned
separate registry/location. The chosen change needs a differentiating regression test: a valid
downstream `unknown` record must coexist with `plan-views returns --gate` without being classified as
`new` or silently omitted.
