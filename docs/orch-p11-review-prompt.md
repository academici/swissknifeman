# Ревью прогона фазы P11 дирижёром orch: промпты и выбор модели

Материалы лежат в репозитории (ветка `ecosystem-split`, push не делался). Ниже: что проверять, две готовые части промпта и
рекомендация по модели.

## Выбор модели

| Часть | Что делает | Модель | Почему |
| --- | --- | --- | --- |
| **A. Сверка решений с кодом** | по каждому из ≈40 спорных решений и 17 коммитам пунктов: открыть коммит, проверить утверждение, вернуть «принять / отклонить / доработать» | **Claude Sonnet 5.5, effort high** | работа проверочная, по чек-листу, с чтением диффов и запуском тестов; Sonnet почти не уступает Opus на таком, дешевле и быстрее; объём большой, но независимый по пунктам (можно параллелить по пунктам) |
| **B. Оценка механизма и инструкций** | правки движка (`packages/orch`, мост, параллельные тесты, схема «быстро/полно»), таблица правок инструкций I1–I14, что сделать универсальнее | **Claude Opus 5.5** | вопросы архитектурные (мягкие лимиты, единая политика лечения отчётов, кэш результатов проверок, параллельные пункты в worktree); и главное — **независимость**: наблюдатель (автор правок) — Sonnet 5.5, у одного семейства общие слепые пятна, а часть А тоже Sonnet |

Если бюджет один: **Opus 5.5 одним проходом по частям B+А-выборочно** (независимость важнее цены); если нужно максимально дёшево — только Sonnet 5.5 high, но тогда решения по механизму (часть B) считать менее независимыми. Часть А можно запускать несколькими параллельными сессиями Sonnet по пунктам P11.4…P11.15.

## Что читать (одинаково для обеих частей)

1. `docs/orch-p11-observer-journal.md` — хронология решений и ошибок наблюдателя, принципы владельца.
2. `docs/orch-p11-run-findings.md` — каталог дефектов (#1–#64), профили шагов и расход времени/токенов по ролям, оценка времени против факта по каждому пункту, разделы «Спорные решения для проверки финальным ревьюером» (1–36), «Что поправить в инструкциях» (I1–I14), «Идеи по схеме», «P11.14 — итог и главный вывод», «P11.15 — независимый аудит», «Коррекция по аудиту».
3. `packages/orch/docs/conductor.md` — опции движка (`review.*`, `checks.*` вкл. `kinds`/`red_first`/`overlap_review`, `instructions.isolate_roles`, `limits.*`, `resume --retry`).
4. `packages/orch/dev-skills/orch-debug/SKILL.md` — протокол режима отладки (включается только явным указанием).
5. Инструменты замеров: `packages/orch/scripts/run-usage.py` (время и токены по ролям), `step-profile.py` (профиль шага по потоку), `scripts/affected-tests.py` (тесты по затронутым пакетам).
6. Артефакты пунктов: `plans/2026.10.07-*/artifacts/P11.N/` (review-verdict.json, stage-report.json, evidence), аудит `P11.15` и `knowledge/audit-p11-2026-10-13.json`.
7. Коммиты: `git log --oneline` (≈100 коммитов; коммиты пунктов — по заголовку «feat(skm-ecosystem): …» с номером пункта в скобках; правки механизма — `fix(orch)`, `feat(orch)`, `feat(aicore)`, `fix(planner…)`).

## Часть А — промпт для Sonnet 5.5 (high): сверка решений с кодом

```text
Ты проверяешь работу автономного прогона фазы P11 по плану экосистемы. Пункты P11.4–P11.15 выполнили роли-субагенты под
управлением дирижёра orch; их коммиты в ветке ecosystem-split (git log --grep "skm-ecosystem"). Наблюдатель (Sonnet 5.5) записал
в docs/orch-p11-run-findings.md раздел «Спорные решения для проверки финальным ревьюером» (пронумерованы 1–36) и в
артефактах пунктов — вердикты ревью. Твоя задача — проверить КАЖДОЕ спорное решение по коду, а не по описанию.

Для каждого номера: (1) открой коммит/файл, на который указывает запись; (2) проверь утверждение (запусти нужный тест командой
`python3 scripts/affected-tests.py --paths <файлы> --run` или конкретным `bash packages/<модуль>/scripts/test.sh`; maind — только
если его файлы затронуты); (3) верни строку: «№ — принять / отклонить / доработать — причина в одном предложении — файл:строка».
Особое внимание: отклонённые триажем Major (P11.7 F1), обход public-hygiene «заглушкой» (P11.8), конформанс-тест MCP, который не
исполнялся (P11.10), масштаб удаления core/artifex и правки вне write set (P11.12), отсутствие ревью в P11.13, оставленные
«deferred minor» и устаревшие пути topology/projects, шесть находок аудита P11.15 и их исправление (коммит 2c372d0e).
Не меняй код и не публикуй ветку. Итог — таблица «№ / вердикт / причина / файл:строка» и список того, что нельзя проверить
без запуска (с командой запуска).
```

## Часть B — промпт для Opus 5.5: механизм и инструкции

```text
Ты — независимый ревьюер механизма оркестрации. Агент-наблюдатель (Sonnet 5.5) вёл прогон фазы P11 дирижёром orch и по ходу
чинил сам механизм (≈60 дефектов, #1–#64 в docs/orch-p11-run-findings.md). Прочти материалы по списку в
docs/orch-p11-review-prompt.md. Оцени и верни решения:

1. Каждая правка механизма: достаточна ли она, нет ли костыля, как сделать универсальнее. Главные темы: мягкие лимиты
   (предупреждение вместо остановки); единая политика «лечащего» разбора отчётов ролей (сейчас heal_report + строгие схемы,
   повторы стоят 10–30 мин); каденс проверок (опция checks.kinds и правило «быстро на пункт — полно один раз»; кэш результатов
   проверок по дайджесту входов; нужен ли уровень tier в самой проверке плана вместо kind); изоляция инструкций ролей
   (instructions.isolate_roles теперь по умолчанию для всех ролей, Claude Code стартует с --safe-mode: оцени риск потери нужных
   правил репозитория и предложи короткий явный блок «правила модуля» в промпте роли); продолжение сессии роли вместо новой;
   параллельные независимые пункты в worktree; режим «продолжить с готовой работой в дереве» (сейчас только resume --retry для
   blocked); предполётная проверка провайдеров; пересборка входа при правке плана; одно определение «собственных путей дирижёра»
   у orch и планировщика; две копии схемы run-options (orch и мост) — как оставить одну.
2. Таблица «Что поправить в инструкциях» (I1–I14): дай готовые формулировки правок для инструкций составления плана, ролей
   исполнителя/ревьюера, промптов, правил наблюдателя, CLAUDE.md, скиллов (в том числе: не повторять роли «качество кода» —
   модель знает; оставлять только концептуальные правила: границы модулей, порядок работы по плану).
3. Правило «быстро на пункт, полно один раз в конце фазы»: достаточно ли оно, и как гарантировать, что полный прогон не
   пропускается (например, обязательный пункт закрытия с kind impact).
4. Оценки времени наблюдателя против факта (таблицы по пунктам): где он систематически ошибался и почему.
5. Вопросы владельцу (коротко).

Ограничения: ветку не публиковать (push делает владелец); состояние машины (установка/вход CLI) не менять; код менять только
по явной просьбе — по умолчанию верни рекомендации.
```
