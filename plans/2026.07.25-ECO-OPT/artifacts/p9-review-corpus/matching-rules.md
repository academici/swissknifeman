# matching-rules.md — правило матчинга находок прогона против ключа (P9.3)

Объявлено ДО первого прогона ревью (коммитится вместе с `answer-key.json`/`cases.json`,
`git log` подтверждает порядок). Матчер — `score_review_runs.py`, детерминированный,
без LLM-judge: неоднозначный матч печатает пару кандидатов и **падает**, решает человек
(арбитраж), а не скорер молча.

## Единица сопоставления

Находка прогона — строка `runs-baseline.csv` с полями `case_id, run_idx, finding_id_local,
file, line_from, line_to, type, severity, statement`. Находка ключа — запись
`answer-key.json` с `must_find=true` (ловушки `is_trap=true` в матчинг НЕ участвуют как
цель — см. «Три корзины» ниже, они участвуют только в подсчёте `judged FP`).

## Условия матча (ВСЕ обязательны — AND, не OR)

1. **Тот же `case_id`.** Находки разных кейсов никогда не матчатся друг с другом.
2. **Тот же файл.** `file` находки прогона байт-в-байт равен `location.file` записи ключа
   (относительный путь от корня соответствующего репо — `repo_path` из `cases.json`).
3. **Пересечение диапазонов строк ≤ ±10.** Диапазон находки прогона `[line_from, line_to]`
   и диапазон ключа `[location.line_from, location.line_to]` считаются match-совместимыми,
   если `line_from_прогона ≤ line_to_ключа + 10` И `line_to_прогона ≥ line_from_ключа - 10`
   (раздвинутое на 10 строк в обе стороны пересечение отрезков). Точечная находка
   (`line_from == line_to`) — частный случай той же формулы.
4. **Совпадение `type`.** `product`/`evidence`/`process` — точное совпадение (словарь L3,
   `review_policy.FINDING_TYPES`). Разное `type` при остальных совпавших условиях —
   НЕ матч (разные измерения одного участка кода — легитимно раздельные находки).
5. **Не required: текстовое совпадение `statement`/`severity`.** Формулировка находки
   ожидаемо отличается между независимыми прогонами (перефразировка) — текст в матчинг НЕ
   входит (иначе матчер стал бы вторым LLM-judge по смыслу текста). `severity` расходится
   часто (см. Известная граница ниже) и в АВТОМАТИЧЕСКИЙ матч не входит — расхождение
   severity фиксируется отдельно как разброс, не как непойманная находка.

## One-to-one жадное сопоставление

Для каждого кейса `case_id`, для каждого прогона `run_idx`, кандидаты матчей находок ключа
против находок прогона сортируются по убыванию **ширины пересечения строк** (шире
пересечение — приоритетнее). Жадно, по убыванию приоритета: если ОБЕ стороны пары (находка
ключа и находка прогона) ещё свободны — матч фиксируется, обе стороны помечаются занятыми.
Одна находка ключа не может матчиться с ДВУМЯ находками одного прогона и наоборот
(запрет many-to-one/one-to-many — иначе overlap завышается, RAG-цитата
`findings/P9-review-stability-facts.md` §1). После жадного прохода:

- Находки ключа БЕЗ пары в этом прогоне → `missed` (не найдено).
- Находки прогона БЕЗ пары в этом прогоне → кандидаты в `judged FP` или
  `plausible but unlabeled` (см. ниже).

**Неоднозначность** — ситуация, когда у находки прогона ЕСТЬ более одного кандидата в
ключе с ОДИНАКОВОЙ шириной пересечения (тай-брейк не выводится числом) — скорер печатает
ОБЕ пары и завершает работу ненулевым кодом; арбитраж — человек, не эвристика "первый по
порядку в файле".

## Три корзины (RAG: не всё вне ключа — ложный позитив)

- **`matched TP`** — находка прогона, сматчившаяся (правила 1–4) с находкой ключа
  `must_find=true`.
- **`judged FP`** — находка прогона, сматчившаяся (правила 1–4) с находкой ключа
  `is_trap=true` (ловушка: план заранее знает, что это НЕ настоящая проблема — см.
  `answer-key.json` T001–T003). Это ЕДИНСТВЕННЫЙ путь в `judged FP`.
- **`plausible but unlabeled`** — находка прогона, не сматчившаяся НИ С ЧЕМ в ключе
  (ни с `must_find`, ни с `is_trap`). НЕ считается автоматически ложной (RAG-правило,
  `findings/P9-review-stability-facts.md` §1) — прогон мог найти реальную проблему, которую
  ключ не разметил. Схлопывание этой корзины в `judged FP` запрещено дословно.

## Метрики (считает `score_review_runs.py`)

- **`R` (pass@3 по ключу).** Для находки ключа `must_find=true` — найдена ли она ХОТЯ БЫ
  в одном из трёх прогонов кейса. `R` = доля таких находок по всем кейсам.
- **`R1` (медиана recall одного прогона).** Для каждого прогона отдельно — доля находок
  ключа, сматченных именно в этом прогоне; `R1` — медиана по всем прогонам всех кейсов.
- **`J` (медиана попарного Jaccard).** Для каждой пары прогонов ОДНОГО кейса (3 прогона →
  3 пары) — Jaccard по множествам `matched TP`-идентичностей (`finding_id` ключа, на который
  смэтчился прогон); `J` — медиана по всем парам всех кейсов.
- **`U1` (доля находок, встретившихся ровно в одном прогоне).** Среди ВСЕХ `finding_id`
  ключа, найденных хотя бы раз (по любому из трёх прогонов кейса) — доля тех, что найдены
  РОВНО одним прогоном из трёх (не двумя, не тремя).

## Известная граница (записывается как факт, не молчится)

- Грубость правила ±10 строк — цена простоты матчера; более узкое окно занижало бы recall
  на легитимной перефразировке диапазона (например находка на "строке объявления функции"
  vs "строке возврата внутри неё"), более широкое — завышало бы Jaccard склейкой разных
  находок одного файла.
- `severity` сознательно вне матчинга: два прогона могут честно разойтись в оценке тяжести
  ОДНОЙ и той же находки (Major vs Minor) — это не должно считаться "находка не совпала".
- Матчер НЕ проверяет, что predicted `statement` описывает ТУ ЖЕ причину, что и ключ (только
  локацию+тип) — находка "не по адресу" (правильные file:line, но другая по существу
  проблема) технически засчитается как матч. Это осознанный компромисс простоты правила
  (без LLM-judge над текстом) — назван, а не спрятан.
