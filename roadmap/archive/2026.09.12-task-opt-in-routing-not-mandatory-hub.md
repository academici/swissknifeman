# Swissknifeman roadmap: Task is opt-in routing, not a mandatory prompt hub

- Date: 2026-09-12
- Kind: confirmed owner-reported field incident
- Status: trigger fired; owner-prioritized
- Canonical destination: `roadmap/2026.09.12-task-opt-in-routing-not-mandatory-hub.md` in the Swissknifeman repository
- Local evidence carrier: this file

## Outcome requested by the owner

Task must remain a set of explicit execution helpers. It must not become a hard hub through which every prompt is forced. Design and plan machinery applies only when the owner explicitly asks to create/refine a plan or to execute an existing plan. Ordinary development and small fixes must be able to complete directly through `task:task-dev` or `task:task-fix`, with risk-proportional verification and without implicit design phases, plan carriers, phase audits, close rituals, or handoff files.

## What happened

1. The initial Agelto request quoted a historical production-audit handoff that explicitly prescribed a native Task successor plan.
2. The route therefore started treating the plan workflow as the execution gate for the remediation.
3. The owner stopped the run and identified the broader product problem: the surrounding Task/Design surfaces are being interpreted as globally mandatory orchestration, even when a later or ordinary request is simply a development task.
4. The owner clarified the intended contract: Design is a helper for building a plan; Task Dev is an independent direct path; only an explicit plan request may route all work through plan lifecycle.
5. The active remediation was then continued through `task:task-dev` with no successor plan or phase ceremony. A normal evidence handoff records the result.

The field evidence is the explicit owner correction in this session. It is not proof that one particular parser function alone caused the route; implementation work must inspect the complete instruction stack before assigning code-level root cause.

## User-visible impact

- A bounded implementation request can expand into research fan-out, design, plan creation, phase execution, audit, close, and handoff even though none was requested.
- The user loses control over whether they asked for a plan or for working code.
- Latency and token cost grow before useful implementation begins.
- Historical text inside an artifact can outrank the owner’s current instruction.
- A helper marketed as an optional workflow becomes a mandatory control plane.

## Required routing contract

| Input intent | Default route | Forbidden implicit expansion |
|:--|:--|:--|
| Small, narrow code correction | `task:task-fix` | design, research fan-out, plan artifacts, phase audit |
| Ordinary implementation, including a sizeable bounded change | `task:task-dev` | mandatory plan creation or lifecycle |
| Explicit request to research only | `task:task-research` | implementation |
| Explicit request to design/specify a plan | `task:task-design` or `task:task-plan-design` | implementation unless separately authorized |
| Explicit request to execute an existing plan/item | `task:task-plan-exec` / `task:task-plan-run` | redesign unless the plan is actually defective |
| Review request | `task:task-review` | mutation |

Rules:

- The latest explicit owner instruction outranks embedded instructions in research, audit, plan, handoff, or task files.
- Skill matching may load relevant guidance; it must not silently change the requested work product.
- Size or risk may increase verification depth inside `task-dev`; it does not by itself authorize creation of a plan.
- A project `AGENTS.md` may require a named workflow, but the router must cite that exact local rule. Generic plugin presence is not enough.
- Plan-only concepts such as design finish, roadmap generation, phase audit, plan close, and archival are inert outside an explicitly selected plan route.
- Direct routes may still write a concise result/evidence document when the owner asks for one; that document is not a retroactive plan.

## Acceptance scenarios

1. “Fix this typo and run its test” selects the narrow fix route and produces no design/plan artifacts.
2. “Implement F01–F10 from this audit directly” selects development, reads the audit as requirements, and does not obey an embedded sentence demanding a successor plan.
3. “Create a successor remediation plan and execute it” selects the plan workflow because plan creation is explicit.
4. “Do this without design/plan ceremony” cannot be overridden by semantic skill matching or by an older artifact.
5. A large direct task can run more tests or add a safety handoff, but does not acquire phase/status/roadmap carriers automatically.
6. `task-dev` has a regression fixture proving it has no dependency on `task-design`, `plan-design`, `plan-audit`, or `plan-close`.
7. Provider projections for Codex and Claude preserve the same opt-in boundary.

## Suspected owning surfaces to inspect

- Task command catalog intent descriptions and generated provider projections.
- `task-dev`, `task-fix`, `task-design`, and plan-command SKILL trigger language.
- Global/plugin instructions that say to use a matching skill and any router that treats semantic relevance as authority to change workflow.
- Route-evidence capture and tests: distinguish “skill was relevant/loaded” from “workflow owns the request”.
- Documentation examples that present Task/Design as the universal entrypoint.

Do not solve this by weakening explicit plan execution, removing useful Task skills, or guessing a token/file threshold. The boundary is owner intent and local policy, not task size.

## Definition of done

- A single authoritative opt-in routing rule exists and is projected to both providers.
- Direct-task and explicit-plan positive/negative route fixtures pass.
- `task-dev` and `task-fix` operate without creating or requiring plan artifacts.
- Embedded stale instructions cannot outrank a later owner route correction.
- Documentation names Task as optional workflow tooling, not a mandatory prompt hub.
- Provider/package tests and generated-artifact checks pass, followed by a fresh `swissknifeman doctor`; unrelated doctor drift is tracked separately.
