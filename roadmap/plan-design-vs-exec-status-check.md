# Roadmap: агент рекомендует `plan-design` вместо `plan-exec`, не проверив фактический статус фазы

**Статус:** ⬜ отложено (найдено на `insiders`, `plans/2026.07.16-INS-EVO` P1, 2026-07-17).
**Критерий внедрения:** повтор на ЕЩЁ ОДНОМ плане/проекте (агент рекомендует `plan-design` для
фазы, которая по факту уже в статусе Ready/DoR — второй замер подтвердит, что это системный
разрыв, а не разовая невнимательность одной сессии).

## Вводные

Проект: `insiders` (`/home/vostrikov/sibintek/projects/insiders`, Laravel-приложение, ветка
`modules-structure`). План: `plans/2026.07.16-INS-EVO` (protocol 2.0, 8 фаз / 33 item-скелета).
Владелец только что закрыл фазу P0 (гигиена+CI+Docker) и попросил «следующую команду плана новой
фазы в новой сессии» — имея в виду P1 (полнота workflow-графа), которая по истории сессии уже
была полностью спроектирована ранее:

- v0.7.0 (2026-07-16): Fable детализировал P1–P7 до DoR (28 items, все 16 полей, Code Guidance)
  и собрал `plans/2026.07.16-INS-EVO/roadmap.md`.
- v0.8.0 (2026-07-16): формы `handoff.Next` расширены, канон Design Passes закрыт.

Этот факт лежал у меня прямо в системном контексте сессии (SessionStart-хук, дайджест памяти
проекта `sibintek-insiders`) в момент, когда владелец задал вопрос.

## Ошибка

На запрос «следующую команду плана новой фазы» я выдал:

```
/task:plan-design 2026.07.16-INS-EVO P1
```

Правильная команда (фаза уже спроектирована и в Ready/DoR, нужно исполнение первого item'а):

```
/task:plan-exec 2026.07.16-INS-EVO P1.1
```

Владелец среагировал жёстко («почему опять design???? по плану полное проектирование, а потом
общее исполнение») и попросил прогнать разбор ошибки перед тем, как продолжать.

## Разбор причины (проведён по прямому запросу владельца в сессии)

- Сработал поверхностный лексический паттерн: «новая фаза» → рефлекторный выбор
  `task:plan-design`, без обращения к фактическому статусу фазы (Draft/Ready/InProgress/Done).
- Ключевой факт («P1–P7 уже детализированы до DoR, roadmap.md собран») был в контексте сессии
  (SessionStart-дайджест памяти), я его видел раньше в диалоге, но не связал с вопросом
  «что дальше» — не сделал явную проверку статуса перед тем, как выбрать команду протокола.
- Смешение двух разных осей: «фаза не начата ИСПОЛНЕНИЕМ» (P1 действительно ещё не исполнялась)
  было спутано с «фаза не спроектирована» (P1 давно спроектирована). Это разные, несмежные стадии
  жизненного цикла плана (design-gate DoR пройден отдельно от exec-gate), а решение было принято
  так, будто это одна ось «новое/старое».
- Не было явного шага «прочитать `phases/P1.md` / `roadmap.md` → Status фазы» перед выдачей
  команды — решение принято по umolчанию (default to design on "new phase"), а не по факту.

## Почему это риск, а не разовая случайность

- Тот же паттерн возможен в ЛЮБОЙ сессии, где агент не хранит явную память статуса фазы и
  формулировка пользователя («новая фаза», «следующая фаза», «дай команду по плану») лексически
  триггерит `plan-design`, даже если фаза уже прошла design-gate в одной из прошлых сессий.
- Стоимость ошибки не нулевая: `plan-design` — это Opus/high (дорогой прогон), плюс риск
  избыточного/повторного редизайна уже готового ТЗ (могло исказить существующие Code Guidance).
- Структурно похоже на разрыв, уже описанный в этом каталоге (`plan-lesson-capture.md`) —
  там протокол не заставляет фиксировать пост-closure находки; здесь протокол/навигация не
  заставляют агента явно сверяться со статусом фазы перед выбором `plan-design` vs `plan-exec`.

## Чем это НЕ дублирует существующее

- **`plan-lesson-capture.md`** — про то, что находки ПОСЛЕ закрытия item'а не попадают в план
  автоматически. Эта идея — про выбор КОМАНДЫ протокола ДО начала работы над фазой, ошибка на
  входе в конвейер, а не на выходе.
- **`plan-audit-loop.md`** (не читал подробно, но по названию) — вероятно про адверсариальный
  аудит уже закрытой работы; эта находка — про предотвращение неверного шага ДО его совершения.

## Набросок реализации (при возврате к идее)

1. **Явный pre-flight шаг в `plan-protocol`/`task:plan-*` роутинге**: прежде чем рекомендовать
   `plan-design` для фазы Pn, обязательный `Read`/`Grep` статуса фазы (`phases/Pn.md` → Status,
   или `roadmap.md` → таблица фаз) — если статус Ready/DoR, `plan-design` не предлагается, сразу
   `plan-exec` на первый незакрытый item.
2. Возможно, отдельная лёгкая команда-роутер (`/task:plan-next <PLAN-ID> [Pn]`), которая сама
   читает `plan.md`/`roadmap.md`, определяет реальный статус фазы/item'ов и ВЫБИРАЕТ команду
   (`plan-design` только если Draft/нет DoR, иначе `plan-exec`/`plan-close`), вместо того чтобы
   агент угадывал по формулировке пользователя.
3. Опциональная подстраховка в навигации (`.ai/guidelines/navigation.md`-аналог для plan-protocol
   скилла): явная фраза «перед `plan-design` — проверь, нет ли уже готового `roadmap.md`/DoR для
   этой фазы» рядом с описанием команды в SKILL.md.

## Альтернатива (если критерий так и не сработает)

Полагаться на то, что пользователь поправит агента при ошибке (как произошло здесь) — сработало
в этот раз без потерь (ошибка поймана ДО запуска дорогого `plan-design` прогона), но это разовая
защита от воли/внимательности владельца, а не от протокола. Не внедрять формальный pre-flight
шаг стоит, только если повторных случаев не наберётся.
