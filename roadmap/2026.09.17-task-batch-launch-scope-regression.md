# Roadmap: Task не должен сужать batch до первого ready item в native fresh launch

**Статус:** воспроизведённая полевая регрессия; исходники Task не менялись.

**Критерий запуска ремонта:** сработал 2026-09-17. После owner-запроса на новую
сессию для CoreX `2026.09.15-№1-COREX-FLEXCRM-REMAINING P6.6` агент выдал
одиночный `task:plan-exec … P6.6`, хотя установленный batch `B-P6-SEARCH` —
`P6.6–P6.8`, а сохранённый handoff уже корректно объявлял `task:plan-run …
P6.6-P6.8`.

## Воспроизведённый факт

План объявляет один Routing group:

| Carrier | Наблюдение |
|:--|:--|
| `plan.md`, строки 146–148 | `B-P6-SEARCH`: P6.6, P6.7, P6.8; `implementation/high`; `plan-exec` |
| `phases/P6/P6.md`, строки 80–82 | то же membership и последовательная граница search harness → installed seal |
| `roadmap.md`, строки 73, 77 | dependency chain `P6.6 → P6.7`, затем P6.8; batch допускает only ready frontier |
| `handoff.md` | canonical Next: `run-items: task:plan-run 2026.09.15-№1-COREX-FLEXCRM-REMAINING P6.6-P6.8`, Batch `B-P6-SEARCH`, `cold-start-root` |

Правильная native Codex launch-команда для зафиксированной границы:

```bash
codex -C /home/vostrikov/projects/packages/corex -m gpt-5.6-terra -c 'model_reasoning_effort="high"' -a never -s danger-full-access '$ task:plan-run 2026.09.15-№1-COREX-FLEXCRM-REMAINING P6.6-P6.8'
```

`plan-run` связывает весь ordered workset, но не делает будущий consumer готовым
заранее: сначала допускается P6.6; P6.7 может стартовать лишь после его durable
terminal evidence; P6.8 — после фактической готовности всех declared producers.
Таким образом диапазон не означает параллельную или преждевременную запись.

## Причина

1. Оператор ошибочно подменил **workset, который должен быть передан новому
   invocation**, его первым **ready frontier**. Это разные понятия: frontier
   управляет порядком исполнения внутри `plan-run`, а не сокращает owner-visible
   batch launch.
2. Persisted `handoff.md` прошёл lint именно потому, что адресует полный remaining
   adjacent suffix. Но user-facing native command был собран вручную и не был
   выведен из того же `plan_delivery`/handoff receipt.
3. Существующий handoff-lint проверяет batch membership в carrier, но не способен
   проверить уже отправленный в чат shell command. Поэтому корректный handoff и
   некорректный final могли разойтись.
4. `status.md` был ошибочно смешан с admission/navigation в ментальной модели.
   Это generated journal-state projection: на момент инцидента P6.6–P6.8 честно
   остаются `⬜ Not started`, поскольку product attempt не начинался. Принятие
   D40 и готовый bundle не должны подделывать «started». Current launch scope
   принадлежат Routing, bundle/admission и handoff, а не status view.

## Граница ремонта

- Не менять CoreX product code, P6 scopes, dependency order, authority gates или
  status literals ради этого carrier.
- Не трактовать batch range как разрешение запускать P6.7/P6.8 до producer evidence.
- Не превращать `status.md` в вручную редактируемый launch ledger: его owner —
  `task plan-views status`, и он должен пересобираться после journal mutation.
- Не разрешать агенту выбирать одиночный `plan-exec` как «эквивалент» delivery
  command полного batch без explicit owner request на exactly scoped ready subset.

## Предложение ремонта

1. Сделать native fresh-launch renderer единственным источником command: он получает
   terminal/continuity receipt с exact Routing membership и не принимает вручную
   сформированные item arguments.
2. Если persisted semantic Next — `run-items` с range, provider launch обязан
   сохранить `task:plan-run` и тот же range. Сужение до первого item — typed
   `BATCH_LAUNCH_SCOPE_MISMATCH` до user-facing final.
3. В terminal/fresh-launch finalization сверять четыре значения: semantic Next,
   routing batch membership, `batch_receipt` remaining suffix и rendered native
   invocation. Не полагаться только на lint `handoff.md`.
4. В diagnostics явно печатать различие `workset` / `current ready frontier` и
   показывать exact continuation range. Это предотвращает ложное объяснение,
   что downstream P6.7 «не ready», поэтому его нельзя указывать в launch.
5. Добавить отдельный generated admission/navigation view либо явно оставить
   handoff его единственным carrier; в любом случае `status.md` должен по-прежнему
   строиться из journal и отражать только фактическое состояние item.

## Acceptance

- Для batch `P6.6–P6.8` с producer→consumer dependency свежий native Codex launch
  содержит ровно `task:plan-run <PLAN-ID> P6.6-P6.8`; модель, effort, cwd,
  approval и sandbox берутся из current route/receipt.
- Первый execution step допускает только P6.6; P6.7/P6.8 не получают journal start
  до фактической готовности. После terminal P6.6 same invocation продолжает
  P6.7 без нового launch и без изменения bound workset.
- Renderer или terminal admission отвергает command, в котором full batch receipt
  был сужен до `plan-exec … P6.6`, даже если handoff сам по себе корректен.
- Regression покрывает `plan-exec` single-item group, `plan-run` range, ready
  subset with pending consumer, `cold-start-root` и explicit owner request на
  новую сессию для Codex и Claude projections.
- После start/terminal event `status.md` пересобирается owning generator и
  `--check` проходит; до journal start он не заявляет ложный progress только из-за
  принятого design/adoption decision.
