# Ecosystem Reuse Gate

Гейт «advisory-with-teeth»: перед тем как проектировать новую функциональную
единицу с нуля, скилл принудительно сверяет её с живым реестром экосистемы
(«радаром») и прогоняет универсальные правила vendor-vs-build. Дефолт —
переиспользование; `build-new` допускается только когда явно сработало одно
из правил ниже.

Это **механизм**, не данные: скилл не знает имён конкретных проектов, пакетов
или вендоров — путь к живому реестру экосистемы передаётся как параметр
вызова. Конкретную привязку к данным конкретной экосистемы несёт отдельный
проектный скилл (см. «Ссылки»).

## Контекст

Когда проектируется новый проект, пакет или крупная фича, легко заново
изобрести то, что в экосистеме уже решено — вендором, зависимым пакетом или
уже написанным доменным слоем. Без принудительного гейта дисциплина
переиспользования держится только на памяти проектировщика и деградирует со
временем.

## Входные данные

- Путь к живому реестру экосистемы (tech-radar) — параметр вызова, не хардкод.
- Формулировка проектируемой функциональной единицы (какую задачу решаем).
- Язык/рантайм и ограничения проекта-потребителя (лицензия, self-host,
  комплаенс, домен).

## Алгоритм

1. **Прочитать реестр.** Загрузить tech-radar экосистемы по указанному пути.
   Пути нет или файл недоступен → сообщить и остановиться — без реестра гейт
   не может выдать вердикт.
2. **Сопоставить единицу с реестром.** Найти в карте «единица → компонент»
   точное или близкое совпадение по формулировке задачи. Совпадения нет →
   явно зафиксировать «не найдено» (не молчаливый пропуск) и перейти к шагу 3
   как к кандидату `build-new`.
3. **Прогнать 7 if-then правил по порядку** (первое сработавшее — вердикт):
   1. Зрелый вендор/OSS с совместимой лицензией и локализуемым self-host,
      покрывающий существующее применение в экосистеме (Rule-of-3) →
      `use-vendor`.
   2. Тот же тип функционала уже покрыт существующим пакетом экосистемы в том
      же языковом кластере → `use-package` (консолидация в существующий
      пакет, не новый).
   3. Дублирование подтверждено, подходящего вендора нет (комплаенс /
      локализация / домен-специфичность) → `build-new` тонкий адаптер/хаб —
      НЕ переизобретение всего вендорного функционала.
   4. Вендор закрывает инфраструктурное/durability-ядро, но нужен доменный
      DSL/контракт поверх → `build-new` тонкий слой НАД вендором, ядро
      вендора не дублировать.
   5. Два независимых потребителя (N=2), разные языковые рантаймы/профили
      нагрузки, без общего кода уровня приложения → `keep-per-project`, не
      форсировать слияние.
   6. Регуляторика уже задаёт вендора (обязательный сертифицированный
      протокол/провайдер) → вендор не пересматривается, дублируется только
      адаптер-слой (см. правило 3).
   7. Мощный сквозной концерн, потребляемый несколькими рантаймами/продуктами
      за пределами основного ядра и достаточно крупный для отдельного проекта
      → `build-new` **standalone-пакет** со своим репо/философией, НЕ модуль
      ядра; пакет сам владеет своей vendor-стратегией, реестр указывает на
      пакет, не на его внутренний вендор (потребление ядром — через тонкий
      адаптер).
4. **Вынести вердикт.** Один из `use-vendor` / `use-package` / `build-new` /
   `keep-per-project`, с явным указанием, КАКОЕ правило сработало, и цитатой
   из реестра (строка/раздел), обосновывающей решение.
5. **Запрет-шорткат.** `build-new` без явного прохода по правилам 1–2 (и
   отметки, что они не сработали) — запрещённый вывод скилла.

## Выходные данные

Reuse-отчёт в чате: единица → вердикт → сработавшее правило → цитата
реестра. Не отдельный файл — решение встраивается в диалог проектирования
(new-project / tech-stack-selection).

## Чеклист качества

- [ ] Реестр экосистемы прочитан по параметру пути (не по памяти, не
      захардкожен).
- [ ] Единица сопоставлена с картой реестра явно (совпадение или явное «не
      найдено»).
- [ ] Все 7 правил прогнаны по порядку до выбора вердикта.
- [ ] `build-new` не выведен без обоснования, какое правило (3/4/6/7)
      сработало.
- [ ] В теле скилла нет имён конкретных проектов/пакетов/вендоров-примеров.
