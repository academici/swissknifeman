## 2. Методология исследований и рабочие процессы

### 2.1 Иерархия исследований

Перед запуском любой исследовательской задачи определите уровень вопроса:

| Уровень | Тип вопроса | Подход |
|---|---|---|
| **Уровень 1** | Единичный проверяемый факт | Один поиск; цитировать источник |
| **Уровень 2** | Сравнительный анализ | Параллельные поиски; сводная таблица |
| **Уровень 3** | Исследовательский / разведочный | Итеративный поиск; параллелизм субагентов |
| **Уровень 4** | Обзор литературы / метаанализ | Академический поиск; сеть цитирований |
| **Уровень 5** | Стратегическая разведка | Конкурентный анализ; 400+ интеграций |

### 2.2 Рабочий процесс глубокого исследования (Perplexity Computer)

Этот процесс применяется к вопросам уровней 3–5, требующим синтеза по множеству источников.

#### Фаза 1: Ориентирование (5–10 минут)
1. **Сформулируйте 3 затравочных запроса** — широкую, среднюю и специфичную версии вопроса
2. **Запустите параллельные поиски** — используйте `search_web` со всеми тремя запросами одновременно
3. **Определите авторитетные источники** — отметьте издателей, организации, владельцев первичных данных
4. **Картируйте ландшафт знаний** — что известно, оспаривается, неизвестно или свежее?

#### Фаза 2: Глубокое погружение (15–45 минут)
1. **Извлеките первоисточники** — используйте `fetch_url` на авторитетных URL (не агрегаторах)
2. **Перекрёстно проверяйте утверждения** — любой факт, процитированный лишь одним источником, является предварительным
3. **Академический слой** — используйте `search_vertical(vertical="academic")` для рецензируемых материалов
4. **Социальный слой** — используйте `search_social` для дискурса в реальном времени и зарождающихся точек зрения
5. **Сохраняйте промежуточные находки** — записывайте структурированные заметки с URL источников в рабочую область

#### Фаза 3: Синтез (10–20 минут)
1. **Постройте реестр утверждений** — перечислите все фактические утверждения с силой их источника
2. **Определите области консенсуса против спорных** — где источники согласуются, а где расходятся?
3. **Отметьте свежесть информации** — это данные 2024 или 2020 года?
4. **Составьте исследовательскую справку** по шаблону из §13.1

#### Фаза 4: Проверка качества
1. Проверьте каждое количественное утверждение по его источнику
2. Убедитесь, что для ключевых данных цитируются первоисточники (а не агрегаторы)
3. Примените проверку на ошибку выжившего: кого НЕТ в этих источниках?
4. Оцените уверенность: Высокая (несколько первоисточников) / Средняя (один первоисточник) / Низкая (только вторичные)

### 2.3 Параллелизованное исследование субагентами

Для крупных исследовательских задач (10+ сущностей, несколько регионов, многогранные темы):

```
План мастер-агента:
├── Субагент A: Тематический домен X (поиски + сохранение находок в workspace/research-A.json)
├── Субагент B: Тематический домен Y (поиски + сохранение находок в workspace/research-B.json)
├── Субагент C: Сбор проверенных URL изображений/медиа
└── Мастер-агент: Читает все файлы рабочей области, синтезирует, строит финальный артефакт
```

**Правила параллелизации:**
- Каждый субагент пишет в уникальное имя файла (никогда не перезаписывает)
- Субагенты включают URL источников для каждого факта
- Мастер-агент НЕ переисследует; только синтезирует
- Никогда не стройте финальный актив до завершения всех файлов исследования

### 2.4 Преемственность исследований между сессиями

В начале любой исследовательски-нагруженной задачи:
1. Поищите в памяти предыдущую работу по той же теме
2. Прочитайте релевантные файлы рабочей области из предыдущих сессий
3. Стройте на предыдущих находках, а не начинайте с нуля
4. Отметьте, что изменилось с последнего исследовательского прогона (зависящие от даты факты)

### 2.5 Рабочий процесс исследования контента (с учётом SEO)

Когда исследование питает создание контента:

**Шаг 1: Исследование ключевых слов**
- Определите основное ключевое слово (целевой объём 500–5 000 поисков в месяц)
- Найдите 3–5 вторичных ключевых слов
- Соберите 10–15 LSI-терминов (latent semantic indexing, латентно-семантическое индексирование)

**Шаг 2: Аудит конкурирующего контента**
- Найдите топовые по ранжированию статьи по основному ключевому слову
- Определите: что они покрывают, что упускают, какой ракурс неоспорен
- Картируйте контентный пробел, который заполнит ваш материал

**Шаг 3: Сбор авторитетных источников**
- Для каждого крупного утверждения определите хотя бы один первоисточник
- Предпочитайте: государственные данные, рецензируемые исследования, официальные отчёты, первичные новости

**Шаг 4: Бриф контента**
- Целевой объём слов: 1 500–2 500 для всестороннего охвата
- Структура: вступление → проблема/контекст → 3–5 ключевых разделов → заключение с CTA
- Включите ключевое слово в заголовок, первый абзац, 2–3 заголовка H2

### 2.6 Фреймворк конкурентного исследования

| Шаг | Действие | Инструмент |
|---|---|---|
| 1. Определить конкурентов | Найти участников рынка | `search_web` |
| 2. Профилировать каждого конкурента | Извлечь их страницы «о компании», цен, фич | `fetch_url` |
| 3. Мониторинг тональности | Искать в соцсетях упоминания бренда | `search_social` |
| 4. Академическое / патентное сканирование | Искать ИС, научные публикации | `search_vertical(academic)` |
| 5. Синтезировать боевую карту | Сравнить фичи, цены, позиционирование | Записать в рабочую область |

## 3. Построение графа знаний

*(Из Tapestry — превращает документы в связанные сети знаний)*

### 3.1 Что такое граф знаний в этом контексте?

Граф знаний связывает сущности (людей, концепции, события, места, продукты), извлечённые из контента — статей, PDF, видео, научных работ — в структурированную сеть отношений. В отличие от плоского резюме, граф знаний позволяет:
- Видеть, какие концепции центральны, а какие периферийны
- Прослеживать цепочки доказательств от утверждений обратно к источникам
- Выявлять пробелы в охвате вашего исследования
- Сливать знания из нескольких документов

### 3.2 Рабочий процесс Tapestry: Извлечь → Связать → Спланировать

Скилл Tapestry оркестрирует полный конвейер извлечения знаний:

```
Входной URL (YouTube / Статья / PDF)
        ↓
   [Определить тип контента]
        ↓
   [Извлечь контент]
   ├── YouTube → yt-dlp + дедупликация VTT
   ├── Статья → reader / trafilatura / fallback на curl
   └── PDF → pdftotext / poppler
        ↓
   [Сохранить чистый текст в файл]
        ↓
   [Создать план действий Ship-Learn-Next]
        ↓
   Выход: content_file.txt + action_plan.md
```

**Триггерные фразы**: "tapestry [URL]", "weave [URL]", "make this actionable", "extract and plan [URL]"

### 3.3 Протокол извлечения сущностей

При построении графа знаний из корпуса документов:

**Шаг 1: Определите типы сущностей**
```
Person      → исследователи, авторы, руководители, исторические фигуры
Organization → компании, организации, государственные органы
Concept     → теории, методологии, фреймворки, продукты
Event       → конференции, публикации, инциденты, вехи
Place       → страны, города, лаборатории, рынки
Claim       → фактические утверждения с уровнями уверенности
```

**Шаг 2: Извлеките отношения**
```
X AUTHORED Y         (Person → Document)
X FOUNDED Y          (Person → Organization)
X INTRODUCED Y       (Organization → Concept)
X CONTRADICTS Y      (Claim → Claim)
X CITES Y            (Document → Document)
X APPLIES_TO Y       (Concept → Domain)
X PRECEDED Y         (Event → Event)
```

**Шаг 3: Назначьте провенанс источника**
Каждая сущность и отношение должны нести:
- Документ-источник
- Ссылку на страницу / таймкод
- Уровень уверенности (Высокий / Средний / Низкий)
- Дату информации

**Шаг 4: Определите кластеры и пробелы**
- Кластеры = плотно связанные подграфы (ядро тем)
- Изолированные узлы = неисследованные области
- Недостающие связи = исследовательские вопросы для следующей итерации

### 3.4 Формат вывода графа знаний

```markdown
## Граф знаний: [Тема]

### Ключевые сущности
| Сущность | Тип | Связи | Ключевой источник |
|--------|------|-------------|------------|
| [Имя] | Person | 14 | [URL] |
| [Имя] | Concept | 22 | [URL] |

### Ключевые отношения
- [Сущность A] **DEVELOPED** [Сущность B] (Источник: [doc], уверенность: High)
- [Сущность C] **CONTRADICTS** [Сущность D] (Источник: [doc], уверенность: Medium)

### Кластеры
1. **Кластер 1: [Метка]** — сущности: A, B, C, D
2. **Кластер 2: [Метка]** — сущности: E, F, G

### Пробелы исследования
- [ ] Нет источников об отношении между X и Y
- [ ] Только один источник с низкой уверенностью для утверждения Z
```

### 3.5 Синтез из нескольких документов

При слиянии знаний из 5+ документов:

1. **Извлеките списки сущностей** из каждого документа независимо
2. **Дедуплицируйте сущности** — разрешите синонимы (напр., "ML" = "machine learning")
3. **Слейте графы отношений** — отметьте, когда документы согласуются, конфликтуют или молчат
4. **Взвесьте по авторитетности источника** — рецензируемое > первичные новости > блог > форум
5. **Постройте единый граф** — запишите в структурированный файл рабочей области
6. **Определите консенсусную точку зрения** против спорного фронтира

## 4. Извлечение и синтез контента

### 4.1 Извлечение статей

**Порядок приоритета инструментов:**
1. `reader` (Mozilla Readability CLI) — лучший универсальный
2. `trafilatura` (Python) — лучший для блогов, новостей, не-английского
3. `fetch_url` с LLM-промптом — лучший для контекста Perplexity Computer
4. `curl` + HTMLParser — fallback, менее точный

**Установка:**
```bash
# Вариант 1: reader (npm)
npm install -g @mozilla/readability-cli

# Вариант 2: trafilatura (pip)
pip3 install trafilatura
```

**Рабочий процесс извлечения:**
```bash
# С reader
reader "https://example.com/article" > temp_article.txt
TITLE=$(head -n 1 temp_article.txt | sed 's/^# //')

# С trafilatura
TITLE=$(trafilatura --URL "$URL" --json | python3 -c "import json, sys; print(json.load(sys.stdin).get('title', 'Article'))")
trafilatura --URL "$URL" --output-format txt --no-comments > temp_article.txt

# Очистить имя файла
FILENAME=$(echo "$TITLE" | tr '/' '-' | tr ':' '-' | tr '?' '' | cut -c 1-80 | sed 's/ *$//')
mv temp_article.txt "${FILENAME}.txt"
```

**Что удаляется экстракторами статей:**
- Навигационные меню и хедеры/футеры
- Реклама и промо-баннеры
- Формы подписки на рассылку
- Сайдбары со связанными статьями
- Кнопки шеринга в соцсети
- Оверлеи согласия на cookie

### 4.2 Извлечение транскриптов YouTube

**Полный рабочий процесс:**
```bash
VIDEO_URL="https://www.youtube.com/watch?v=XXXXX"

# 1. Получить заголовок видео для имени файла
VIDEO_TITLE=$(yt-dlp --print "%(title)s" "$VIDEO_URL" | tr '/' '_' | tr ':' '-')

# 2. Проверить доступные субтитры
yt-dlp --list-subs "$VIDEO_URL"

# 3. Сначала попробовать ручные субтитры (высшее качество)
yt-dlp --write-sub --skip-download --output "transcript_temp" "$VIDEO_URL"

# 4. Fallback: автогенерируемые субтитры
yt-dlp --write-auto-sub --skip-download --sub-langs en --output "transcript_temp" "$VIDEO_URL"

# 5. Дедуплицировать и очистить VTT → обычный текст
python3 -c "
import sys, re
seen = set()
vtt_file = 'transcript_temp.en.vtt'
with open(vtt_file, 'r') as f:
    for line in f:
        line = line.strip()
        if line and not line.startswith('WEBVTT') and '-->' not in line:
            clean = re.sub('<[^>]*>', '', line)
```

### 6.1 Выбор правильной меры центра

| Ситуация | Использовать | Почему |
|---|---|---|
| Симметричное распределение, без выбросов | Среднее | Наиболее эффективная оценка |
| Скошенное распределение | Медиана | Робастна к выбросам |
| Категориальные или порядковые данные | Мода | Единственный вариант для нечисловых |
| Скошенное с выбросами (выручка, время) | Медиана + среднее вместе | Разрыв показывает величину скоса |

**Всегда сообщайте среднее И медиану вместе для бизнес-метрик.** Если они значимо расходятся, данные скошены, и одно среднее вводит в заблуждение.

### 6.4 Обнаружение выбросов

**Метод Z-оценки** (нормальные распределения):
```python
z_scores = (df['value'] - df['value'].mean()) / df['value'].std()
outliers = df[abs(z_scores) > 3]  # За пределами 3 стандартных отклонений
```

**Метод IQR** (робастный; работает на скошенных данных):
```python
Q1 = df['value'].quantile(0.25)
Q3 = df['value'].quantile(0.75)
IQR = Q3 - Q1
lower = Q1 - 1.5 * IQR
upper = Q3 + 1.5 * IQR
outliers = df[(df['value'] < lower) | (df['value'] > upper)]
```

**Обнаружение аномалий во временных рядах:**
1. Вычислите ожидаемое значение (скользящее среднее или тот же период прошлого года)
2. Вычислите остаток (фактическое − ожидаемое)
3. Пометьте остатки за пределами 2–3 стандартных отклонений
4. Различайте: точечная аномалия (одиночный всплеск) против точки изменения (устойчивый сдвиг)

**Обработка выбросов — НЕ удаляйте автоматически. Вместо этого:**
1. Исследуйте: ошибка данных, подлинный экстремум или другая популяция?
2. Ошибки данных → исправьте или исключите с документированием
3. Подлинные экстремумы → сохраните; используйте робастную статистику (медиана, IQR)

### 6.5 Проверка гипотез

**Фреймворк:**
1. **H₀ (нулевая гипотеза)**: Различия не существует (предположение по умолчанию)
2. **H₁ (альтернативная)**: Различие существует
3. **Альфа**: Порог значимости, обычно 0,05
4. **Вычислите тестовую статистику + p-значение**
5. **Интерпретируйте**: p < альфа → отклонить H₀ → свидетельство реального различия

**Распространённые тесты:**

| Сценарий | Тест | Метод Python |
|---|---|---|
| Сравнить средние двух групп | Независимый t-тест | `scipy.stats.ttest_ind` |
| Сравнить коэффициенты конверсии | Z-тест для долей | `statsmodels.stats.proportion.proportions_ztest` |
| До/после на тех же сущностях | Парный t-тест | `scipy.stats.ttest_rel` |
| Сравнить средние 3+ групп | ANOVA | `scipy.stats.f_oneway` |
| Ненормальные данные, две группы | Манна-Уитни U | `scipy.stats.mannwhitneyu` |
| Две категориальные переменные | Хи-квадрат | `scipy.stats.chi2_contingency` |

**Статистическая против практической значимости:**
- Статистическая значимость: различие вряд ли случайно
- Практическая значимость: различие достаточно велико, чтобы иметь значение
- Всегда сообщайте КАК p-значение, ТАК И размер эффекта + доверительный интервал
- При больших выборках крошечные бессмысленные различия становятся статистически значимыми

| Географические паттерны | Хороплет; пузырьковая карта | Таблица |

**Никогда не используйте**: 3D-графики, круговые диаграммы с >6 секторами, две оси без явного обоснования, столбчатые графики, не начинающиеся с нуля.

```python
def format_number(val, format_type='number'):
    if format_type == 'currency':
        if abs(val) >= 1e9: return f'${val/1e9:.1f}B'
        elif abs(val) >= 1e6: return f'${val/1e6:.1f}M'
```

### 7.5 Принципы дизайна

**Цвет:**
- Используйте цвет для кодирования данных, а не для украшения
- Подсветите инсайт ярким акцентом; всё остальное приглушите в серый
- Последовательный (sequential): одноцветный градиент (светлый→тёмный) для упорядоченных значений
- Расходящийся (diverging): двухцветный градиент с нейтральной серединой для данных, центрированных на нуле
- Категориальный: максимум 6–8 различных оттенков, прежде чем наступит путаница
- Никогда не полагайтесь только на красный/зелёный; 8% мужчин страдают красно-зелёным дальтонизмом

**Типографика:**
- Заголовок формулирует инсайт: «Выручка выросла на 23% год-к-году» > «Выручка по месяцам»
- Подзаголовок добавляет контекст: диапазон дат, фильтры, источник данных
- Подписи осей: читаемые, с единицами, по возможности без поворота на 90°

**Макет:**
- Удалите «мусор» графика: лишние линии сетки, рамки, фоновые цвета
- Сортируйте категории по значению (не по алфавиту), если нет естественного порядка
- Столбчатые графики должны начинаться с нуля — всегда
- Линейные графики могут иметь ненулевые базовые линии, когда важен диапазон вариации

### 8.2 Распространённые ловушки анализа

**Взрыв джойна:**
```sql
-- Проверьте ДО и ПОСЛЕ джойна
SELECT COUNT(*) FROM table_a;                         -- 1,000
SELECT COUNT(*) FROM table_a a JOIN table_b b ON ...; -- 3,500 (проблема!)
-- Исправление: используйте COUNT(DISTINCT a.id) при подсчёте через джойны
```

**Ошибка выжившего:**
- Анализ «текущих пользователей» упускает ушедших пользователей
- Спросите: «Кого НЕТ в этом наборе данных, и изменили бы они мой вывод?»

**Неполное сравнение периодов:**
- «Январь ниже декабря» — но январь ещё не закончился
- Исправление: всегда фильтруйте по завершённым периодам или сравнивайте окна равной длины

**Сдвиг знаменателя:**
- Коэффициент конверсии «улучшился», потому что вы изменили способ подсчёта подходящих пользователей
- Исправление: используйте консистентные определения метрик; документируйте любые изменения определений

**Среднее средних:**
```python
# НЕВЕРНО: (50 + 200) / 2 = 125, когда группы неравного размера
# ВЕРНО: (100*50 + 10*200) / 110 = 63.64
# Всегда агрегируйте из сырых данных, а не из предагрегированных сводок
```

**Несовпадения часовых поясов:**
- Разные источники могут использовать разные часовые пояса
- Исправление: стандартизируйте все временные метки в UTC перед любыми джойнами или агрегациями

**Ошибка отбора в сегментации:**
- «Пользователи, завершившие онбординг, имеют более высокое удержание» — циклично; они самоотобрались
- Исправление: определяйте сегменты по характеристикам до воздействия, а не по результатам

### 8.3 Проверки разумности результатов

| Тип метрики | Проверка разумности |
|---|---|
| Счётчики пользователей | Совпадают с известными цифрами MAU/DAU? |
| Выручка | Правильный порядок величины против известного ARR? |
| Коэффициенты конверсии | Между 0–100%? Совпадают с дашбордом? |
| Темпы роста | Реалистичен ли >50% MoM, или это ошибка данных? |
| Средние | Разумны с учётом формы распределения? |
| Проценты | Проценты сегментов суммируются к ~100%? |

**Техники перекрёстной валидации:**
1. Вычислите ту же метрику двумя разными способами и проверьте согласие
2. Точечно проверьте отдельные записи вручную
3. Сравните с известными бенчмарками (дашборды, финансовые отчёты)
4. Реверс-инжиниринг: если общая выручка X, то на-пользователя × число пользователей ≈ X?
5. Граничные проверки: отфильтруйте на один день, одного пользователя — имеет ли это смысл?

### 9.7 YAGNI и управление объёмом

Применяйте YAGNI (You Ain't Gonna Need It — «тебе это не понадобится») безжалостно ко всем дизайнам:
- Удаляйте любую фичу, не требуемую текущей заявленной потребностью
- Оспаривайте каждое добавление «нам это может понадобиться позже»
- Предпочитайте простейшее решение, которое решает заявленную проблему
- Документируйте отложенные фичи явно (не включайте их молча)

## 10. RAG-системы и исследования с помощью ИИ

### 10.1 Архитектура RAG-системы

Retrieval-Augmented Generation (RAG, генерация с дополнением извлечением) улучшает ответы LLM, извлекая релевантный контекст из вашего корпуса документов перед генерацией ответа.

```
Запрос пользователя
    ↓
[Эмбеддинг запроса]
    ↓
[Поиск в векторном хранилище] ← (предварительно построено из вашего корпуса документов)
    ↓
[Извлечённые контексты (top-k)]
    ↓
[Промпт LLM = Система + Извлечённый контекст + Запрос пользователя]
    ↓
[Сгенерированный ответ]
    ↓
[Проверка достоверности: ответ опирается на извлечённый контекст?]
```

### 10.2 Строительные блоки RAG

**Шаг 1: Загрузка документов**
```python
# Разбиение документов на чанки для эмбеддинга
def chunk_document(text, chunk_size=512, overlap=64):
    tokens = text.split()
    chunks = []
    for i in range(0, len(tokens), chunk_size - overlap):
        chunk = ' '.join(tokens[i:i+chunk_size])
        chunks.append(chunk)
    return chunks
```

**Шаг 2: Эмбеддинг и индексирование**
```python
# С использованием sentence-transformers (локально, бесплатно)
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('all-MiniLM-L6-v2')
embeddings = model.encode(chunks)

# Хранить с метаданными
import faiss
index = faiss.IndexFlatIP(embeddings.shape[1])
index.add(embeddings.astype(np.float32))
```

**Шаг 3: Извлечение**
```python
def retrieve(query, index, chunks, model, top_k=5):
    query_embedding = model.encode([query]).astype(np.float32)
    scores, indices = index.search(query_embedding, top_k)
    return [(chunks[i], scores[0][j]) for j, i in enumerate(indices[0])]
```

**Шаг 4: Генерация с контекстом**
```python
def generate_answer(query, contexts):
    context_text = '\n\n'.join([ctx for ctx, score in contexts])
    prompt = f"""Answer the question based only on the context below.

Context:
{context_text}

Question: {query}

Answer:"""
    # Передайте в выбранную вами LLM
    return llm_call(prompt)
```

### 10.3 Фреймворк оценки RAG

**Оценивайте по трём метрикам:**

| Метрика | Определение | Цель |
|---|---|---|
| Релевантность контекста | Извлечённые чанки релевантны запросу | > 0,80 |
| Достоверность ответа | Утверждения ответа поддержаны извлечённым контекстом | > 0,90 |
| Покрытие извлечения | На запрос можно ответить из top-5 извлечённых чанков | > 0,85 |
| Корректность ответа | Ответ совпадает с эталоном (если доступен) | > 0,75 |

**Паттерн скрипта оценки:**
```bash
python scripts/rag_evaluator.py \
  --contexts retrieved.json \
  --questions eval_set.json \
  --metrics relevance,faithfulness,coverage \
  --output report.json --verbose
```

**Распространённые режимы отказа RAG:**

| Проблема | Симптом | Исправление |
|---|---|---|
| Плохое разбиение на чанки | Релевантная информация разбита по чанкам | Семантическое разбиение; увеличить перекрытие |
| Нерелевантное извлечение | Чанки контекста не совпадают с запросом | Лучшие эмбеддинги; фильтрация по метаданным |
| Галлюцинация | Ответ противоречит контексту | Добавить проверку достоверности; temperature=0 |
| Отсутствующий контекст | Ответ слишком часто говорит «не знаю» | Расширить корпус; увеличить top-k |
| Сбои чувствительности к дате | Устаревшая извлечённая информация | Добавить фильтры по дате в метаданных |

### 10.4 Паттерны промпт-инжиниринга

**Основные паттерны:**

| Паттерн | Когда использовать | Пример |
|---|---|---|
| **Zero-shot** | Простые, чётко определённые задачи | «Классифицируй это письмо как спам или не спам» |
| **Few-shot** | Сложные задачи, требующие консистентного формата | 3–5 примеров перед задачей |
| **Chain-of-Thought** | Рассуждения, математика, многошаговая логика | «Думай шаг за шагом...» |
| **Role Prompting** | Нужна экспертиза или конкретная перспектива | «Ты эксперт-налоговый бухгалтер...» |
| **Structured Output** | Нужен парсируемый JSON/XML | Включить схему + принуждение формата |
| **Self-Consistency** | Рассуждения с высокими ставками | Запустить несколько раз; взять большинство голосов |
| **ReAct** | Агенты, использующие инструменты | Цикл Думать → Действовать → Наблюдать |

**Рабочий процесс оптимизации промпта:**

```bash
# Шаг 1: Базовый анализ
python scripts/prompt_optimizer.py current_prompt.txt --analyze --output baseline.json

# Шаг 2: Применить паттерны на основе найденных проблем
# Неоднозначный вывод → добавить явную спецификацию формата
# Слишком многословно → извлечь в few-shot примеры
# Несогласованные результаты → добавить роль/персону
# Отсутствуют граничные случаи → добавить границы ограничений

# Шаг 3: Сгенерировать оптимизированную версию
python scripts/prompt_optimizer.py current_prompt.txt --optimize --output optimized.txt

# Шаг 4: Сравнить
python scripts/prompt_optimizer.py optimized.txt --analyze --compare baseline.json
```

## 11. Итеративное обучение и обратная связь

### 11.1 Фреймворк Ship-Learn-Next

Превратите пассивное обучение в активное строительство, используя цикл Ship-Learn-Next:

```
SHIP  → Создай что-то реальное (код, контент, продукт, анализ)
LEARN → Честная рефлексия о том, что произошло
NEXT  → Спланируй следующую итерацию на основе извлечённых уроков
```

**Основной принцип**: 100 повторений побеждают 100 часов учёбы. Обучение = делать лучше, а не знать больше.

**Триггерные фразы**: "turn [content] into a plan", "make this actionable", "I watched/read X — now what?"

### 11.2 Определение квеста

Хороший квест конкретен, ограничен по времени и производит реальный артефакт.

**Плохой квест**: «Изучить машинное обучение» (слишком расплывчато, нет конечного состояния)
**Хороший квест**: «Построить и развернуть регрессионную модель на наборе данных Titanic к [дате]»

**Вопросы для определения квеста:**
1. Чего вы хотите достичь за 4–8 недель?
2. Как выглядел бы успех в конкретных терминах?
3. Что-то реальное, что вы могли бы построить/создать/выпустить?
4. Какова минимально приемлемая версия?

### 11.3 Структура повторения (Rep)

Каждое повторение (итерация) следует этой структуре:

```markdown
## Rep N: [Конкретная, отгружаемая цель]

**Цель отгрузки (Ship Goal)**: [Конкретный артефакт]
**Срок**: [Конкретный дедлайн — на этой неделе / к дате]
**Критерии успеха**:
- [ ] [Конкретный измеримый результат 1]
- [ ] [Конкретный измеримый результат 2]

**Что вы будете практиковать** (из исходного контента):
- [Навык/концепция 1]
- [Навык/концепция 2]

**Шаги действий**:
1. [Конкретный шаг]
2. [Конкретный шаг]
3. [Конкретный шаг]
4. Отгрузи это (опубликуй/разверни/поделись/продемонстрируй)

**Минимальные ресурсы** (только то, что нужно для этого повторения):
- [Ссылка или референс, если действительно нужно]

**После отгрузки — рефлексия**:
- Что на самом деле произошло?
- Что сработало? Что нет?
- Что вас удивило?
- Оцените это повторение: __/10
- Одна вещь, которую попробовать иначе в следующий раз?
```

### 11.4 Проектирование прогрессии (повторения 2–5)

Каждое последующее повторение добавляет ОДИН новый элемент и строит на уроках предыдущего повторения:

```markdown
## Rep 2: [Следующий уровень]
**Строит на**: Том, что вы узнали в Rep 1
**Новый вызов**: Одна новая вещь, чтобы попробовать или улучшить
**Ожидаемая сложность**: Сложнее (потому что вы освоили Rep 1)

## Rep 3: [Продолжение прогрессии]
**Строит на**: Rep 1–2
**Новый вызов**: [...]

## Reps 4–5: Будущий путь
(Детали эволюционируют на основе того, что вы реально узнаете в Reps 1–3)
```

**Принципы прогрессии:**
- Каждое повторение добавляет ровно один новый элемент (не несколько)
- Повышайте сложность на основе продемонстрированного успеха
- Держите повторения отгружаемыми (всегда производите реальный артефакт)
- Достаточно малыми, чтобы начать сегодня; достаточно большими, чтобы узнать что-то реальное

### 11.5 Обучение из исследований

**После завершения исследовательского проекта:**

1. **Документируйте, что сработало** — какие поисковые стратегии были наиболее продуктивными?
2. **Документируйте, что не сработало** — какие источники были ненадёжными? Какие поисковые термины вернули мусор?
3. **Обновите свою карту качества источников** — добавьте новые надёжные источники в свой список проверенно-хороших
4. **Захватите переиспользуемые шаблоны** — сохраните любые аналитические фреймворки, которые оказались полезными
5. **Запишите открытые вопросы** — что это исследование вывело на поверхность, что заслуживает будущего изучения?

**Шаблон ретроспективы:**
```markdown
## Ретроспектива исследования: [Тема]
Дата: [дата]

### Что сработало хорошо
- [поисковая стратегия / источник / подход]

### Что не сработало
- [подход и почему он провалился]

### Удивительные находки
- [неожиданные открытия]

### Открытые вопросы на следующий раз
- [ ] [вопрос 1]
- [ ] [вопрос 2]

### Созданные переиспользуемые активы
- [шаблон / фреймворк / список источников]
```

### 11.6 Чего НЕ делать (антипаттерны)

- НЕ создавайте план учёбы — создавайте план ОТГРУЗКИ
- НЕ перечисляйте все ресурсы для потребления — выберите минимум для текущего повторения
- НЕ позволяйте идеальному быть врагом отгруженного
- НЕ принимайте расплывчатые цели — настаивайте на «отгрузить Y к дате Z»
- НЕ планируйте больше 2 повторений вперёд без предварительной отгрузки
- НЕ пропускайте шаг рефлексии — именно там живёт обучение

## Карточка быстрого доступа

### Когда какой инструмент поиска использовать

| Нужно | Инструмент | Заметки |
|---|---|---|
| Актуальные новости / события | `search_web` | Используйте дату в запросе для свежести |
| Научные работы | `search_vertical(academic)` | Возвращает DOI; извлеките первоисточник |
| Тональность бренда | `search_social` | Используйте операторы `from:`, `#hashtag`, `-is:retweet` |
| Исследование продуктов | `search_vertical(shopping)` | Возвращает цену + URL источника |
| Профессиональные профили | `search_vertical(people)` | На основе LinkedIn |
| Контент конкретной страницы | `fetch_url` с промптом | Всегда извлекайте первоисточник; не агрегаторы |
| Визуал живой веб-страницы | `screenshot_page` | Для захвата UI, конкурентного анализа |

### Быстрый справочник по статистическим тестам

| Тип данных | Две группы | Три+ групп | Парные | Связь |
|---|---|---|---|---|
| Нормальные, непрерывные | t-тест | ANOVA | Парный t-тест | Pearson r |
| Ненормальные, непрерывные | Манна-Уитни U | Краскела-Уоллиса | Уилкоксон | Spearman r |
| Бинарные / доли | z-тест для долей | Хи-квадрат | МакНемар | Коэффициент фи |

### Выбор графика (одной строкой)

- **Во времени** → Линейный график
- **Сравнение** → Горизонтальные столбцы (отсортированы по значению)
- **Распределение** → Гистограмма + линии среднего/медианы
- **Корреляция** → Диаграмма рассеяния (2 переменные) или тепловая карта (много переменных)
- **Композиция** → Столбцы с накоплением (мало категорий) или treemap (иерархия)
- **Сегменты** → Малые множества

### Уровни уверенности для утверждений

| Уровень | Критерии |
|---|---|
| **Высокий** | Несколько независимых первоисточников согласуются; рецензируемые или официальные данные |
| **Средний** | Один первоисточник; или несколько вторичных источников в согласии |
| **Низкий** | Один вторичный источник; непроверено; или источники конфликтуют |
| **Непроверено** | Заявлено, но пока не подкреплено источником; требует последующей проверки |
