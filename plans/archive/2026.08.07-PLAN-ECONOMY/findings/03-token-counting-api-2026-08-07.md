## 1. Единственный корректный измеритель — `count_tokens`

Эндпойнт: `POST /v1/messages/count_tokens`. SDK-форма (Python):

```python
resp = client.messages.count_tokens(
    model="claude-opus-5",
    messages=[{"role": "user", "content": open("CLAUDE.md").read()}],
)
resp.input_tokens
```

CLI-форма (`ant`, тот же эндпойнт):

```sh
ant messages count-tokens --model claude-opus-5 \
  --message '{role: user, content: "@./CLAUDE.md"}' \
  --transform input_tokens -r
```

Существенные свойства для P0:

- **Счёт зависит от модели.** Справочник формулирует это прямо: «Token counts are
  **model-specific** — pass the same model ID you'll use for inference». Порог, не назвавший
  токенизатор, — бессмысленное число.
- **Эндпойнт stateless.** Диффа не существует: чтобы сравнить две версии файла, считаются обе и
  вычитаются. Значит инкрементального «сколько добавила эта правка» из API не получить — только
  два полных замера.
- **Нужны учётные данные и сеть.** Клиент резолвит их в порядке `ANTHROPIC_API_KEY` →
  `ANTHROPIC_AUTH_TOKEN` → активный OAuth-профиль `ant auth login` → WIF → профиль на диске.
  Незаданный `ANTHROPIC_API_KEY` НЕ означает отсутствия доступа; но и наличие доступа у человека
  за терминалом не означает наличия его в CI.

## 2. Сторонние токенизаторы для Claude неверны — с числом

Справочник (`shared/token-counting.md`) формулирует запрет и его цену:

> **Do not use `tiktoken`.** It's OpenAI's tokenizer. It undercounts Claude tokens by ~15–20% on
> typical text, and by much more on code or non-English input.

Два следствия, оба несущие для P0:

1. Ошибка **в опасную сторону**: сторонний токенизатор ЗАНИЖАЕТ. Гейт на заниженной оценке даёт
   ложный зелёный — ровно тот отказ, который этот план обязан исключить.
2. Промах растёт на коде и не-английском. Планы этого флота — RU/EN markdown с таблицами и
   вставками кода, то есть худший случай для чужого токенизатора.

## 3. Токенизатор менялся между поколениями — и не на проценты

- Opus 4.7 ввёл новый токенизатор; Opus 4.8 и Fable 5 используют тот же. Переход **с Opus 4.6 и
  старше** даёт «roughly 1×–1.35× as many tokens» на том же тексте.
- Sonnet 5 относительно Sonnet 4.6: «approximately 30% more tokens than on Sonnet 4.6».
- Указание для мигрирующих — не применять «blanket multiplier», а перемерить `count_tokens`
  против нового ID.

Для P0 это значит: артефакт калибровки обязан пинить семейство токенизатора и дату, а «просто
пересчитать коэффициент» при смене поколения — не правка константы, а перекалибровка.

## 4. Минимальный кэшируемый префикс — тоже привязка к модели

Справочник даёт таблицу минимумов и предупреждает, что она **не монотонна** по поколениям:
512 токенов у Claude Opus 5 / Fable 5 / Mythos 5; 1024 у Opus 4.8, Sonnet 5, Sonnet 4.6/4.5, Opus
4.1/4; 2048 у Opus 4.7 и Haiku 3.5; 4096 у Opus 4.6/4.5 и Haiku 4.5. Префикс короче минимума
молча не кэшируется (`cache_creation_input_tokens: 0`, без ошибки).

Это не про P0-порог напрямую, но подтверждает требование D8 и обязано попасть в P1/P2: «маленький
носитель» может оказаться некэшируемым, и это молчаливый отказ, а не ошибка.

## 5. Чего этот источник НЕ даёт

- Не даёт алгоритма токенизатора и не позволяет посчитать токены оффлайн точно. Локального
  корректного токенизатора Claude здесь нет вовсе — только сетевой эндпойнт.
- Не даёт лимита размера одного чтения инструментом среды: это свойство харнеса, а не API
  (`findings/00-…` §7 — наблюдение по среде, измеряется отдельно в P0).
- Не даёт rate-limit'ов конкретно для `count_tokens`: справочник описывает общие лимиты уровня
  организации и заголовки `retry-after` / `x-ratelimit-*`, отдельной строки под count_tokens в нём
  нет. **[UNVERIFIED]** — точная квота эндпойнта в этой сессии не установлена; практическое
  следствие для P0: калибровочный прогон обязан идти пачками с паузой и переживать 429, а не
  предполагать безлимитность.
