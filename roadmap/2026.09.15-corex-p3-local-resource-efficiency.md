# Расход ресурсов SKM Task: диагностика CoreX B-P3-LOCAL и алгоритм улучшений

**Дата:** 2026-09-15. **Статус:** измеренный полевой инцидент; анализ завершён, исправления runtime не реализованы этим отчётом.

**Заказ владельца:** изучить сессию, план, артефакты и взаимодействие разработки; определить, насколько рационально расходуются ресурсы; сохранить отчёт об улучшениях в SKM ROADMAP. Это исследование процесса, не новый master plan, phase audit или разрешение реализовать предложения.

**Критерий запуска исправлений:** уже наблюдался: жалоба владельца на длительность, три source-carrier ремонта между пунктами/при handoff, сбой projection после terminal, примерно 13 минут работы после закрытия последнего разрешённого пункта. После принятия конкретного implementation scope работа получает одного владельца в ограниченном задании; эта запись не создаёт параллельный исполняемый backlog.

## Вывод

Разработка дала содержательный результат и реальные доказательства опасных сценариев, но процесс расходовал ресурсы нерационально. Главная проблема — не скорость выполнения тестов: существенная часть времени ушла на обязательный большой корпус, ручную сборку доказательств, несовместимые носители и восстановление закрытия. Сократить число проверок без разбора причин было бы неправильным лечением.

Нужно сохранить physical tenant isolation, concurrent claim, crash/replay, archive verification before DROP, точные owner receipts и source qualification. Убрать следует повторное вычисление неизменных данных, позднее обнаружение ошибок схемы, влияние будущего scope на закрытие текущего, ручные receipt/read runners и вывод больших технических носителей в контекст.

Обнаружены и ошибки исполнителя, и дефекты SKM. Некоторые носители плана были некорректными ещё до execution; часть дальнейших ошибок создал сам исполнитель. Нельзя всё объяснить «SKM потребовал» или считать все прогоны тестов лишними.

## Установленные проблемы

### RSC-01. Штатная диагностика не видит текущий Codex execution

**Приоритет P0 для достоверности измерений; owner: harness acquisition + shared usage/runs, analyst/maind presentation.**

`maind analyze --cwd --session <thread> --no-health --json` вернул `GREEN`, `confidence: low`, `run_report: null`. Есть forensic bash counts, но `cat .../tests/...` тоже попадает в test hints: это не доказательство test success. `analyst token-report` использовал 22 legacy trend rows; последний timestamp — 2026-08-07, текущего thread нет. `analyst sessions` приобретает Claude JSONL, а не текущий Codex rollout.

**Изменение:** существующий provider-neutral acquisition должен нормализовать доступные Codex usage records и компакции в тот же runs/usage SSOT. `maind` агрегирует, `analyst` анализирует; Task не получает вторую токен-математику. В отчёте обязателен `requested identity / acquired identity / coverage / missing slices`; missing current usage — `resource assessment unavailable`, даже если outcome forensic verdict GREEN. Не превращать отсутствие optional telemetry в product blocker.

**Acceptance:** точный thread найден; 334 usage records без duplicate response IDs; main/compaction totals reconciled; mismatched/old trend не служит baseline; нет ложного «ресурсы рациональны» при null run-report. Сырые transcripts остаются local, outward payload — counters/abstracted findings.

### RSC-02. Канонический decision template несовместим с native parser

**Приоритет P0; owner: Task plan-protocol templates/schema qualification.**

`decision-record-template.md` предлагает header fields без YAML и `## Decision` / `## Why`. `parse_decision()` требует YAML `id/date/status/item/items/supersedes/superseded_by`, `## Решение` / `## Почему`. Read-only reproduction отклоняет заполненный canon template: `нет YAML-frontmatter`; даже с верным YAML English headings отклонены.

В сессии новые `corex:PLAN1.D25`–`corex:PLAN1.D28` не имели всей metadata. Terminal второго run был записан, затем `build_views` упал. Понадобились original-byte archives, reconciliation hashes и повторные projections. Это не новое архитектурное решение владельца.

**Изменение:** один machine-owned compatible template/factory, проверяемый реальным parser; preflight всех затронутых decision records перед first protected write и перед terminal preparation. Locale отображения не должен случайно менять schema anchors.

**Acceptance:** заполненный штатный template round-trips; accepted permission payload сохраняется; не нужны ручные добавления null/headings после GREEN. Проверить обе provider projections, а не только unit parser с hand-written YAML.

### RSC-03. Разные парсеры путей дают unresolvable reads и пустое product доказательство

**Приоритет P0, в том числе для корректности guards; owner: Task declared-input/path grammar.**

`split_entries()` считает ненумерованный semicolon Required Reads одной entry. `_declared_paths()` делит по `·`/`,` или backticks, но не исходную semicolon Files sentence с prose. В обоих archived pre-START evidence graphs product anchor содержит **одну missing строку**, collisions пусты. `verify_closure()` допускает GREEN при одинаковых missing anchors. Это доказательство неизменности отсутствующей строки, а не реальных product bytes.

Перечень чтений пришлось ремонтировать в `corex:PLAN1.D24`, `.D27`, а successor — `.D29`. В финальном recovery добавлен отдельный explicit real-file anchor. Он честно доказывает post-terminal bookkeeping interval; исходный полноценный pre-terminal real-file graph восстановлен не был. Зелёные реальные тесты этим не опровергнуты, но качество native byte guard недостаточно.

**Изменение:** одна AST/grammar для Paths/Inputs/Reads/Files, отдельное поле prose, явные globs и declared-output states; grammar validate до source intake. Empty/missing-only anchor не даёт product coverage GREEN; разрешённые ещё не созданные output files имеют explicit planned state и проверяются после создания. Guards должны обнаруживать material input/product overlap на реальных путях.

**Acceptance:** semicolons либо корректно/losslessly нормализованы, либо один ранний actionable error; не silent missing path. Все declared existing product paths bound, новые outputs учитываются; реальная source mutation меняет anchor. Unicode/cross-plan regression и parser parity сохраняются.

### RSC-04. Source completeness оплачивается как повторное освоение общего корпуса

**Приоритет P1; owner: Task input contracts/read continuity.**

Durable read proofs: первый пункт 102 entries / 29 files / 1 751 835 selected bytes / 539 336 estimated tokens; второй 101 / 28 / 1 779 151 bytes / 544 565 estimated tokens. У второго 96 reused entries / 1 730 571 bytes; новый source payload всего 48 580 bytes. Это хороший reuse, который нужно сохранять.

Но cold corpus существенно больше окна модели. Три compactions до первого product START, большой output intake и checkpoint reconciliation — ожидаемое следствие контракта, а не только забывчивости модели. Жёсткий номинальный budget дальнейшего пункта продолжает считать уже освоенный корпус; CoreX получает новый запрос owner exception после каждой группы.

**Изменение:** раздельно измерять полный declared corpus, обязательные selected units и incremental unread work в данном root. Machine-owned source capsule содержит immutable requirement IDs, hashes, selectors, coverage, owner gates и delta; первичная semantic consumption не подменяется SHA. Для ранее consumed selections сохранять version-qualified reuse и устойчивую migration между source versions. Если контракт действительно требует всё целиком, сохранить это требование и заранее показать цену; изменение обязательных selectors требует явного contract decision.

**Acceptance:** unchanged source не читается повторно при compaction/item transition; changed selected bytes требуют реального delta read; complete-source identity/coverage сохраняется; никаких skip по одному hash. Nominal/incremental estimates показываются отдельно, действующий strict budget не обходится новым названием.

### RSC-05. Будущий scope блокирует локальное закрытие, а ALLOW имеет неоднозначный смысл

**Приоритет P0/P1; owner: Task scoped admission/closure/delivery.**

`lint_read_budget()` берёт все незавершённые ready items активной фазы. После двух GREEN возникает native D2a ERROR для **неавторизованного будущего** `corex:PLAN1.P3.3`: 583 017 > 100 000 estimated tokens. Handoff требует его bundle; `batch_admission` после carrier repair говорит ALLOW, но проверяет routing/bundle/producer closure, а strict read-budget остаётся BLOCKED.

Текущее `.D23` исключение распространялось только на B-P3-LOCAL. Его нельзя расширить автоматически. Фаза не закрыта. Финальный global lint exit 1 **сохранён** в `final-bookkeeping-checks.json`; отдельно классифицирован local structural PASS с единственным out-of-scope future budget block. Global lint не был честно весь GREEN после handoff.

**Изменение:** API получает exact authorized execution/closure scope и выводит verdict vector: product acceptance, current structural closure, successor structural readiness, successor effective admission. Future BLOCKED не отменяет валидное local terminal; future START остаётся запрещён. Handoff умеет сказать «prepare decision/admission», сохранив conditional native command. Scope filter задаётся contract/reducer, а не agent regex поверх stderr.

**Acceptance:** два локальных GREEN закрываются при strict RED будущего пункта; ограничения future unchanged; partial routing ALLOW не называется full admission. Current broken per-read/source/receipt внутри разрешённого scope продолжает блокировать. Нет необходимости спрашивать новый owner scope ради завершения старого.

### RSC-06. Закрытие собирается из зависимых side effects без единого recoverable порядка

**Приоритет P1; owner: existing Task recovery/journal/projection APIs.**

Собственный `close-local.py` сделал append terminal → states/status → decisions → successor. После schema failure terminal уже durable; пришлось восстанавливать остальные этапы. Это корректная основа recovery, но нет ready-to-use orchestration для исполнителя. Кроме того, `build_states(..., check=False)` сам вызывает `materialize_next_ready` для identifiers, а caller ещё вызывает его явно: generator имеет скрытую downstream mutation.

**Изменение:** один существующий owning finalization seam: prepare/validate immutable terminal data and affected projections in memory → append idempotent terminal → materialize affected views once → successor readiness → delivery. Durable journal остаётся authority; multi-file FS writes не называть atomic transaction. Recovery resumes exact run/attempt по manifest stages. Pure renderer не запускает successors; coordinator делает это один раз.

**Acceptance:** schema defect найден до append; fault injection после append восстанавливает только незавершённые stages, без второго START/terminal/test replay; один materialize на ready successor. Старые readers/public compatibility сохранены.

### RSC-07. Whole-plan seals и accepted payloads смешаны с volatile metadata

**Приоритет P1; owner: Task digest topology + CoreX plan-owned design check.**

`task-check.py design` seals все `decisions/*`, включая `_archive/_current/_index`, затем execution меняет projections. Сессия неоднократно resealed design-finish, иногда **до** regeneration views; следующая проверка предсказуемо упала на `decisions/_archive.md`. Scope receipt whole-file SHA тоже изменился при обязательной metadata нормализации, хотя принятого решения никто не менял.

**Изменение:** accepted normative payload отдельно от mutable/generated envelope; immutable original acceptance binding сохраняется. Whole integrated design baseline не reseal из-за execution navigation. Дельта authoritative spec/decision требует targeted qualification/нового accepted version, а projection delta — freshness check после regeneration. Не удалять обязательные источники: изменить их роль/volatility в owning topology осознанно.

**Acceptance:** добавление execution log/projection не инвалидирует product/design proof; substantive source/owner permission change инвалидирует нужные anchors. Accepted receipt можно проверить без реконструкции owner words из archives после косметической правки.

### RSC-08. Scoped measurement на деле считает все пункты и раздувает архивы

**Приоритет P1; owner: Task measure/compile primitives.**

`measure_plan(..., only_item=...)` сначала проходит все фазы/items и измеряет их, потом выбирает selected_items. Plan-owned lint тоже делает whole measure перед native lint, который опять вызывает measure. Full native-weight snapshots примерно по 1,10 MB сохранены трижды. Global lint observation занял около 18 с; отдельные state/recovery операции также запускали repeated bundle work.

**Изменение:** один parse/index snapshot на invocation; лёгкая symbolic grammar всех specs на design boundary, тяжёлый selected + declared dependency closure measure на execution boundary. Shared file byte/hash/token estimate cache в рамках вызова, keyed by actual content + role + calibration version; persistent cache только при измеренной необходимости. В stdout — counters/blockers/delta, полный inventory по явному output.

**Acceptance:** only-item не выполняет token measuring 78 items; provider/parser/calibration/source change invalidates соответствующий cached estimate; whole plan remains available explicitly. Никаких fleet scans ради одного item. Замер matched fixture до/после обязателен, обещать ускорение сейчас нельзя.

### RSC-09. Validation задана списком команд вместо проверяемого coverage graph

**Приоритет P1; owner: Task validation planning + consumer test topology.**

Обязательные root lanes, Arch и package suites местами пересекаются; root `test` исключает pg, `test:pg` включён отдельно, tenancy `test` включает собственную PG suite. Разные package/host/native/matrix/upstream profiles нельзя считать взаимозаменяемыми просто по слову `test`. Но большие списки провоцируют либо full replay, либо произвольный agent skip.

**Изменение:** каждому carrier назначить invariant IDs, profile/environment, owned input set и live/static boundary. После delta запускать обязательные invalidated carriers в dependency order; неизменные receipt-bound carriers reuse, когда контракт это допускает. Перед final убрать только подтверждённое двойное покрытие, через revision Validation policy. Suite command identity alone не достаточно для reuse.

**Acceptance:** core root guard delta покрыт core/Arch; tenancy archive/concurrency — package+physical lanes; read-only docs/projection delta не запускает PHP product tests; command/config/fixture/SDK/env change вызывает нужный rerun. DROP/tenant/crypto/concurrency доказательства не исчезают. Mutation lane сериализована с writes/tests, использующими изменяемые source bytes.

### RSC-10. Шумные выводы и shell/poll orchestration увеличивают model work

**Приоритет P1, быстрый эффект; owner: agent guidance + tool output adapters.**

35 truncated outputs, повторные чтения API/template, большие JSON и raw logs. В конце `git diff --check` по log artifacts дал 1 694 строки whitespace warnings; следующий command через `;` вернул exit 0, поэтому outer exit не доказывает успешность diff check. Product-only whitespace check затем действительно прошёл. Raw logs нельзя «исправлять» и ломать SHA ради такого check.

Исполнитель также начал dependent bookkeeping checks до окончания projection/reseal repair. Провалы были закономерными, не новой неопределённостью кода. Это agent error; более точное guidance и structured tool boundary могут предотвратить повтор.

**Изменение:** ожидаемая status vector + concise errors в model payload, full logs — file pointer+SHA. Не прятать предыдущий command exit за `;`, `|| true` или последним успешным command. Читать complete bounded selections с заранее известным limit; dependencies/edits/reseal/validate последовательно, независимые reads/checks — batch. Long-running runner возвращает group status и completion event, а не заставляет model вручную узнавать множество cell APIs.

**Acceptance:** failure одного carrier виден в structured result независимо от последующей команды; raw output immutable; planned reads не теряются из-за truncation. Red→green records preserved, stdout не становится самостоятельным нормативным документом.

### RSC-11. Слишком много bespoke evidence tooling; результаты считаются вручную

**Приоритет P1/P2; owner: Task existing evidence/run primitives.**

Для двух items появились четыре собственных runners/readers/closure helpers, checkpoint updates и reconciliation files. Самостоятельный `run-checks.py` полезно сериализует PG/mutation и сохраняет outcome envelope. Но он становится ещё одним протоколом с manually selected files, assumptions и отдельными API discoveries.

Handoff утверждает первый required-read count 105, durable progress и current bundle имеют 102 entries. Три own source hashes изменились после редактирования — это отдельный delta, а не автоматическое доказательство missing reads. Для второго есть explicit final-bundle-delta proof. Всё это должен согласовывать generator, а не длинная summary после compaction.

**Изменение:** reuse existing shared command envelope/read-progress/projection APIs из одного thin executor. Counts/remaining/receipt pointers/status выводятся из machine state, checkpoints хранят только decisions/risks/next actions и короткие links. Read proof содержит actual acquisition/semantic acknowledgement отдельно от content identity. Envelopes byte-bind реальные code/test/tool/config inputs на capture, не только hash лога и текст `review: PASS`.

**Acceptance:** exact source units consumed/reused/changed/remaining воспроизводимы; stale 105/102 claim отвергнут; metadata delta не требует новой рукописной read script. Тайминг, exit, environment identity и source manifest сохраняются; human review не заменён count assertions.

### RSC-12. История Task не показывает дорогостоящие execution repairs

**Приоритет P1/P2; owner: Task history/returns provenance.**

Native `returns` сообщает `return_events: 0`. `history` показывает START/terminal, но не `.D23`–`.D29`: records имеют `item: design`, `items: [design]`. Кроме этого `_decision_records` фильтрует только `decision.item == item_id`, не multi-item membership. Нет основания читать «0 returns» как отсутствие ремонта или re-planning.

**Изменение:** различить authoring scope документа и affected execution subjects; history выбирает реальные affected items/owner scope. Cheap stage/repair events агрегируются existing run-report, без нового daemon или второго journal. Mechanical normalization не оформляется как новый owner product choice; material authority changes сохраняют настоящий decision gate.

**Acceptance:** история показывает точный permission adoption/carrier/projection repairs обеих локальных items; metadata repair counted separately от product defect/owner wait. Один run не превращается в несколько запусков. События ведут к месту дефекта, а не увеличивают ritual отчётности.

## Предлагаемый алгоритм разработки

Алгоритм ниже — предложение для будущего owning implementation. Он не изменяет права, validators или планы текущего consumer.

### 1. Сначала определить work product и authority

Для обычного fix/dev — direct route, meaningful affected verification, один результат; существующий plan сам по себе не открывает lifecycle. Для explicit plan execution — selected items, порядок, scope, route и current run. Для диагностики — read-only native summaries и один incident report; не запускать product plan, fleet health или новый audit ради анализа.

Собрать scope object: разрешённые items/files, обязательные source units, source/check profiles, gates, owner decisions, запрещённые side effects. Future recommendation находится в отдельном object и не выдаёт authorization. Route overshoot был допустим; автоматический downgrade модели ради предполагаемой цены не предлагается. First response overhead ≈20K не доказывает, что главная проблема — число установленных skills.

### 2. Один ранний prepare на выбранный batch

Проверить совместимость canonical command/template/schema, paths/sections/globs, decisions, source producers и stable/volatile roles. Это лёгкая детерминированная grammar pass, не повтор всех исследований и не чтение будущих отсутствующих reports.

Измерить cold corpus и incremental unread selected work; показать все обязательные лимиты. Если защищённый delta не разрешён — сначала полностью подготовить конкретный пакет, затем спросить только missing owner choice. Пока ждём, выполнять только авторизованные независимые действия; owner gap отдельно от execution cost.

### 3. Intake один раз, затем delta/reuse

Для каждой mandatory selected unit: actual content acquisition → source/selection binding → semantic acknowledgement/coverage → durable receipt. На item transition или compaction сверить state/changed hashes, загрузить только недостающие либо изменившиеся inputs; summary не заменяет source proof. Required sources остаются обязательными, а доказанно consumed units не повторяются в том же qualified root.

### 4. Продуктовая работа и проверки

Перед первым product write должны пройти полное current admission и START original run/attempt. Сначала воспроизвести значимый defect/invariant и определить минимальный owning delta. Реальные safety scenarios сохранять. Независимые reads/static checks batch; общий PG/physical profile, destructive fixtures и source-mutating mutation tests сериализовать.

После каждой product delta пересчитать invalidation в coverage graph. Само закрытие предыдущего item не инвалидирует tests; новый source/test/config/environment input инвалидирует конкретное доказательство. Когда все declared carriers current GREEN — остановить product validation. Новая проверка допустима при новой материальной гипотезе, изменении входов или явном live boundary.

### 5. Закрыть и продолжить без repair loop

```text
prepare_terminal(selected_scope, real_product_anchor, current_receipts)
    validate affected decisions/specs/source manifests and prepared views
    append idempotent terminal for original run/attempt
    regenerate affected projections once
    check local closure structure + byte identity
    compute successor readiness separately from successor authorization
    if successor inside authorized batch and full admission passes:
        materialize exactly one successor bundle; continue same root
    else:
        persist conditional next action and exact unmet future gates
        make one scoped commit
        build and verify terminal delivery against final state
```

После interrupted stage восстановить stage по journal/manifest, а не повторять START, tests или redesign. Closure-only delta получает одну structural reconciliation. Будущий strict budget error остаётся future block, без agent-authored regex исключения и без затягивания completed current scope.

### 6. Диагностика по событию, не постоянный ритуал

Существующий nearest command: `analyst:deep`, рядом `maind analyze`/`analyst token-report`; для Task transitions — `plan-views returns/history`. Отдельного semantic `task:diagnose` в изученном Task 0.17.0 catalog **нет**. Документация/command routing должны помогать найти эти capabilities; прежде чем добавлять ещё одну команду, улучшить existing discovery и точный session acquisition.

`analyst:deep` не запускался как subagent workflow: исходный owner scope запрещал дочерних агентов; пользователь отдельно потребовал изучить именно сессию. Использованы native deterministic summaries и local structured extraction, raw transcript наружу не передавался. Не требуется автоматически ingest/promote lessons или менять skills для выполнения этого отчёта.

После ATTENTION/owner complaint собрать stage durations, input/output/cache/compaction, check coverage/reasons, repair causes и final delivery; создать один incident carrier. Ежедневный full deep audit каждой задачи добавил бы ту же нагрузку, которую надо устранить.
