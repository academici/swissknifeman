# P4 — Cross-machine память mAInd (демон-хост + Tailscale/LAN)

## Phase Context

Фаза реализует **вариант 1** роадмап-стаба `roadmap/cross-machine-memory.md` (D4): единственный
живой демон agentmemory на always-on хосте, остальные машины — сетевые клиенты через
Tailscale/LAN. Критерий активации стаба сработал (у владельца несколько постоянных машин), запрет
file-sync живого стора остаётся в силе и в этой фазе только усиливается фактами.

**Что разведка этого захода изменила в постановке** (слой 1 — `findings/P4-cross-machine-facts.md`;
слой 2 — `research/05-P4-fact-classes.md` карта ДО поиска и `research/06-P4-target-design.md` синтез):

1. **Демону НЕ нужен не-loopback bind — при транспорте `tailscale serve`.** Он проксирует только
   `127.0.0.1`-бэкенд, поэтому управляемый `config/memory/iii-config.yaml` (`host: 127.0.0.1`)
   остаётся нетронутым, а доступ режется ACL/grants до одного порта; key expiry работает как
   автоматический предохранитель (findings §1). Вариант `0.0.0.0` + firewall отклонён (D28).
   **Поправка `finish` (D80):** транспорт ближайшей стадии — **LAN**, а `tailscale serve` стоит на
   триггере ⇒ этот пункт на LAN-стадии НЕ действует: bind нужен, файл правится, ACL/grants
   заменяются firewall-правилом хоста. Запрет `0.0.0.0` из D28 в силе — bind на КОНКРЕТНЫЙ
   LAN-адрес.
2. **У движка ЕСТЬ аутентификация, а у нас нет способа ею воспользоваться.** `AGENTMEMORY_SECRET`
   включает глобальный bearer-middleware (401 на всё без токена), без секрета сетевая экспозиция —
   анонимная запись памяти; при этом `core/http.py` не умеет передавать заголовки вообще, а `ping`
   трактует 401 как «жив» (findings §2, `research/06` §3). Это меняет объём P4.2 и добавляет
   coupling с пакетом `core/` (D29).
3. **Формат стора не тот, что описан в стабе.** `state_store.db` — каталог из 9 JSON-блобов
   (6,4 МБ), каждый = целый scope; file-sync двух писателей перетирает scope целиком, а не «портит
   SQLite» (D30). Побочно найден встроенный **mesh-sync** (LWW, оба конца с секретом) — upstream
   вариант 2; предъявляется владельцу, не внедряется (D31).
4. **Клиентские предохранители Claude Code не помогают:** у stdio-серверов нет per-request таймера
   и авто-переподключения (findings §7) ⇒ бюджет ожидания живёт в нашем HTTP-клиенте.
5. **Сетевая цена измерима заранее:** SessionStart-дайджест тянет ВЕСЬ пул
   (`export(url, "")` → `GET /agentmemory/memories?namespace=`), проба живости — два ping'а по 3 с
   (`research/06` §4). Это делает P4.2 measure-first в части бюджета ожидания.

**Что изменил ответ владельца по OQ-7 (2026-07-25, D78).** Пакет решения P4.1 сжат с восьми открытых
пунктов до **одного**: закрыты транспорт (**A**, `tailscale serve` на loopback), `AGENTMEMORY_SECRET`
+ ACL/grants, носитель токена (**`secret_file` 0600, НЕ env** + расширение `core.http`), офлайн
(**fail-soft без кэша/outbox**, запрет подъёма демона при `role=client` — КОДОМ), миграция стора
(только при смене хоста, app-level export + проверка восстановлением), бэкап (export по расписанию +
проверка **восстановлением**, ретеншн 7–30 дней + 1–3 месячных точки), mesh-sync (**не используем**).
Открыт ровно пункт 1 — **какая машина держит демон**, с записанным критерием: (б) домашний always-on
узел предпочтительно; иначе (а) машина с наибольшим аптаймом; (в) арендованный хостинг — только при
осознанном согласии, что кросс-проектный контекст 15 проектов живёт у провайдера. **Owner-гейт P4.1
сохраняется, P4.2/P4.3 по-прежнему ждут** — выбор хоста определяет ветки реализации; семь закрытых
пунктов становятся предпосылками ТЗ P4.2/P4.3, их пере-обсуждение = реопен с D-записью. Раздел ADR
«известные ограничения» сохраняется в полном составе.

**Что изменил `finish` (2026-07-25, D80) — восьмой пункт закрыт, owner-гейта в фазе БОЛЬШЕ НЕТ.**
Хост — **ТЕКУЩАЯ машина** (критерий D78 отработан: домашнего always-on узла нет ⇒ ветка (а);
арендованный хост и выделенный узел признаны ненужными). Транспорт ближайшей стадии — **LAN**;
`tailscale serve` не отменён, а поставлен НА ТРИГГЕР «третья машина ИЛИ работа вне LAN». Отсюда три
конкретных сдвига в ТЗ фазы: (1) **P4.1** сжимается до написания ADR по восьми принятым ответам —
решений в нём не осталось, класс работы упал frontier → implementation (§3 Routing), а вопрос
владельцу заменяется подтверждением; (2) **P4.2** получает в скоуп
`packages/maind/config/memory/iii-config.yaml` — при варианте A этот файл не трогался вовсе, при
LAN он держит bind на **конкретный LAN-адрес** (не `0.0.0.0` — запрет D28 в силе); (3) **P4.3**
переформулирует гейт 4 приёмки: «недоступность извне tailnet» → «недоступность из-за пределов
подсети LAN», иначе гейт проверяет предохранитель, которого на этой стадии нет. Пункт 6 пакета
(миграция стора) **обнуляется** — хост совпадает с текущей машиной, переносить нечего.
Цена LAN-стадии названа заранее и обязана попасть в «известные ограничения» ADR: секрет
(`AGENTMEMORY_SECRET`, D29) становится ЕДИНСТВЕННЫМ предохранителем, автоотзыв по истечению ключа
устройства отсутствует, ротация — ручная операция runbook'а, а сегмент LAN шире tailnet. Путь роста
(компания, авторизация по scope, серверное назначение конфигов) описан в
`roadmap/2026.07.25-memory-hub-service.md` — **фаза на него ссылается и не пересказывает**; его §11
уже перечисляет ровно то, что делает эта фаза, а §12 — критерии возврата.

**Порядок и границы.** P4.2 правит `lib/maind` **после** терминальной P3.2 (D23): точка врезки в
`mcp.py` — ровно одна ветка недоступности памяти в `_run_tool`; воронку результата (`_content`,
тримминг/receipt) P4.2 не трогает (D32, `research/06` §7). Гейтом плана

граф и реестр проектов остаются per-machine — это названное ограничение варианта, а не пробел.

### P4.2 — Реализация remote-host режима в maind

**Status:** ⬜ Not started
**Intent:** Научить узел различать роли (`memory.role` = `standalone` | `host` | `client`),
