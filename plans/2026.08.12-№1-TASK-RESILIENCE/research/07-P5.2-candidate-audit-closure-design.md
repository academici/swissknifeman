# P5.2 candidate/audit/closure design

## Evidence chain

Raw repository observations are recorded in `findings/14-P5.2-design-preflight.md`. The original
owner intent and phase topology remain in `brief/00-brief.md`, `research/00-user-intent.md`,
`research/01-target-design.md`, and `research/02-phase-topology.md`.

## Selected boundary

P5.2 owns one deterministic lifecycle seam:

```text
terminal item specs/states + declared product Files + scope/risk
  → phase candidate snapshot + stable fingerprint
  → one phase_audit_policy decision
  → direct low-risk close OR latest same-fingerprint GREEN audit
  → terminal phase mutation
  → generated phase closure view
```

The fingerprint excludes journal/audit/closure bookkeeping and the general Git HEAD, so appending
the audit that attests a candidate cannot invalidate that same candidate. It includes terminal
spec/state bytes and the declared product tree, so a material item/product mutation makes prior
audit evidence stale. RAG:— (repo-grounded: `packages/task/lib/task/plan_gates.py`).

The policy and close commands consume the same candidate snapshot. Full review, material risk,
non-green terminal status, multi-item light review, or unresolved routing require an audit;
none/single-green-light may close directly. A required audit is accepted only when the latest
phase audit is GREEN and byte-bound to the same fingerprint. RAG:— (repo-grounded:
`packages/task/lib/task/plan_gates.py`, `packages/task/docs/methodology.md`).

## Alternatives and exclusions

- Recreating the deleted audit-before-close roadmap carrier is rejected: Git preserves its history
  and `roadmap/README.md` marks it implemented; a new copy would create two owners of the rule.
- Replacing the candidate digest with Git HEAD is rejected because audit bookkeeping would
  self-invalidate the evidence it just produced.
- Expanding P5.2 to all seven remaining spec→product→closure topology items is rejected: the
  surviving roadmap explicitly marks those as residual work and this item only stabilizes the
  already-landed phase-candidate seam.
- `plan_returns.py` is excluded: its return-fingerprint loop is orthogonal to candidate audit/close.
- Provider generation, registry and aggregate docs parity remain P5.3.

## Acceptance matrix

1. Candidate stability: append audit bookkeeping → same fingerprint.
2. Candidate invalidation: terminal item spec/state or declared product bytes change → new fingerprint.
3. Policy: full/material/non-green/multi-light/unresolved → audit; none/single-light-green → close.
4. Binding: snapshot/fingerprint mismatch → `PHASE_CANDIDATE_SNAPSHOT_MISMATCH`.
5. Audit evidence: missing/stale/ATTENTION/RED/invalid remain distinct refusal codes; latest matching
   GREEN allows close.
6. Owner decisions: accepted exact-scope direct-green and exact full-phase audit-cap remediation
   pass; missing, superseded, wrong-scope, incomplete-item-set or missing literal refuses.
7. Closure: live phase refuses the generated closure; terminal phase generation is deterministic
   and fresh.

The executor must use general contract paths, never hard-code fixture decision numbers, weaken the
ordinary fresh-audit branch, hand-edit a generated carrier, or absorb the deeper roadmap backlog.
