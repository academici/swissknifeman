# Roadmap: Task final обязан выдавать launch-block, а не прятать его в handoff

**Статус:** 🔥 trigger сработал; owner-prioritized (CoreX, 2026-09-13).

**Критерий запуска:** немедленно — владелец зафиксировал повторяющийся отказ: terminal
`task:plan-exec` завершался сводкой без команды новой сессии и metadata-таблицы.

## Field incident

В CoreX terminal `P2.2` корректно записал в `handoff.md` семантический Next, metadata-таблицу
и Codex-native команду. В user-facing final executor выдал только сводку результата. Владельцу
пришлось отдельно потребовать команду, после чего сначала был изменён обзорный `docs/roadmap.md`
вместо самостоятельного carrier этого каталога.

Проблема повторяемая, а не косметическая: новый сеанс не может быть начат копипастой из terminal
ответа; владелец вынужден искать `handoff.md` и проверять, какие флаги/модель/effort применить.

## Диагностика

`skiller doctor` от 2026-09-13 подтвердил исправность registry, adapter paths и отсутствие vendor
drift. Значит, это не проблема установки Swiss Knife Man.

Канон уже требует правильное поведение:

- `packages/task/adapters/codex/skills/task-plan-exec/command.md` требует для каждого executable
  handoff metadata-таблицу и один fenced Codex command с `-C`, `-m`, reasoning effort, `-a never`,
  `-s danger-full-access`; его final-response guard запрещает заканчивать только сводкой;
- `packages/skiller/skills/general/plan-protocol/snippets/launch-block-template.md` требует ту же
  таблицу перед provider-native командой для Codex и Cloud Code; команда не живёт в ячейке таблицы;
- форма `ОЖИДАНИЕ` не означает, что следующей команды нет: fenced block содержит `# НЕ раньше:` и
  команду, которую можно запустить после точного гейта.

Причина — ошибка исполнения: executor неверно приравнял waiting Next к отсутствию executable
successor, сохранил launch-block только на диске и не перенёс его в final. Обзорный Roadmap также
оказался неверным приёмником: этот каталог требует один self-contained file на проблему.

## Граница исправления

Не менять семантику `plan_delivery`, readiness или owner gates. Нельзя печатать команду текущего
закрытого item и нельзя обходить `ОЖИДАНИЕ`. Исправляется только provider terminal rendering и его
проверяемый контракт.

## Набросок реализации

1. В Codex adapter добавить явный terminal-final renderer: он принимает rebuilt delivery receipt и
   для любого нетерминального Next печатает exact recommendation, затем metadata-таблицу
   `Batch / Model / Thinking / Context / Суть`, затем единственный `**Native Codex command:**`
   fenced `bash` block. Модель/effort берутся из Routing successor, а не предыдущего item.
2. Для `ОЖИДАНИЕ` renderer сохраняет ожидающее условие первой строкой и вставляет `# НЕ раньше:`
   перед той же командой. Это guard, а не разрешение обхода product authority.
3. В provider-neutral template явно закрепить, что Cloud Code получает идентичную metadata-таблицу
   перед своим native invocation; различается только fenced command, не поля таблицы.
4. Добавить regression cases: terminal exec Next и terminal waiting Next без таблицы/command block
   отклоняются; успешный Codex fragment содержит `-C`, `-m`,
   `model_reasoning_effort`, `-a never`, `-s danger-full-access`; Cloud Code fragment содержит
   таблицу перед native invocation. Тест не допускает две provider-команды в одном final.

## Acceptance

- После каждого terminal ответа с нетерминальным Next владелец видит metadata-таблицу и одну
  копируемую provider-native команду, не открывая `handoff.md`.
- `ОЖИДАНИЕ` сохраняет точный gate и команду с `# НЕ раньше:`.
- Codex и Cloud Code используют одинаковую семантику таблицы; в каждом ответе только активный
  provider command.
- Проверка покрывает exec и waiting ветви и не позволяет регрессии закончиться голой сводкой.
