# Changelog

## [Unreleased]

- planner: `plan.py start <plan> <item> --continue correction --receipt PATH [--findings KEYS]` continues an in-progress item to correct recorded review findings with a cheaper executor: the actor is admitted against the optional `route.correction` (`class`, `effort`, optional `provider`/`model`) of the item, else against its `route`, and `result.continuation` records it; `finish --executed-by` of that executor is checked the same way. Without `route.correction`, and for a new item or a start without `--continue`, nothing is relaxed (a plain resume below the route now hints at `--continue correction`). `ITEM_OWNED` now says the item is held by a session and names the `--take-over` command (ownership is per session, not per model); new refusal `CONTINUATION_INVALID`.
- orch: `review.correction_route: bounded-implementer` runs the corrections of review findings without a Blocker on the bounded-implementer role (own session) when its route meets the claim's `route.correction`, else `route`; otherwise the executor corrects and `CORRECTION_ROUTE_REFUSED` says why. A correction that changes paths beyond its findings, the tests, `CHANGELOG.md` and the docs is `CORRECTION_SCOPE_GREW`: a deviation and a beacon on the executor route, a stop of the piece on the bounded route. The class of a route that names a model is the class the model catalog gives it (`aicore.provider.models.admitted_class`) when lower than the stage label, so `{model: haiku, model_class: implementation}` no longer passes an implementation piece; an unknown model is said once (`ROUTE_MODEL_UNKNOWN`). The planner-orch claim answer carries `route.correction`; the execution-input `route.minimum` keeps only class, effort, provider and model.
- orch: the observer report has the metrics of every piece for every run, debug or not (`metrics` of `observer.json`, table *Item metrics* of `observer.md`): wall time, active time by role group, checks share, executor/review/checks rounds, steps repeated after a resume, heals and repairs, beacons, fresh/cached/output tokens, deviations, triage and review findings and the health transitions of `supervisor.jsonl`, all from the journal, state, agent records and supervisor log, never from raw streams. Debug mode no longer creates empty `<run>/debug/{journal,metrics,findings}.md`: `DEBUG_MODE` points at the observer metrics, and the orch-debug skill no longer polls status every 30 minutes but wakes on health, supervise, autopilot and run-end signals.
- orch: `orch conduct prune --compress-older-than DAYS [--apply] [--json]` gzips the raw role streams (`streams/*.jsonl|.txt|.stderr|.times`) of old finished runs under their lease, removing an original only after its copy reads back the same (`compress-result` document with `--json`); `step-profile.py` and beacons read the `.gz` of a packed stream. Retention of the aicore event journal stays with aicore (trigger: `events.jsonl` over 50 MB).
- orch: a conductor started with SIGINT ignored (in the background of a shell) now ends `INTERRUPTED` on the SIGINT of `orch conduct autopilot stop` or the supervisor instead of running on until a later SIGTERM.
- orch: fewer stops and loops from the P7–P8 run review. RESULT_INCOMPLETE no longer sends work back when the acceptance checks run the self-check command or the conductor runs it green itself (`SELF_CHECK_COVERED`); a group review skipped by a stopped run is reported (`GROUP_REVIEW_PENDING`, observer) and done over the finished pieces; generated paths (`[orch.conductor] generate`, `generate_check`, `generated_paths`, machine level) are regenerated by the run checkout's own generator before checks instead of blocking as WRITE_PROTECTED_PATH (`GENERATED`, stop `GENERATE_FAILED`); leftover Claude sandbox stubs under `.claude/` are removed at start and resume (`SANDBOX_STUBS_REMOVED`).
- orch: clearer beacons. STAGE_SLOW/STAGE_IDLE/RUN_SLOW say when the role stream last grew and leave out sandbox infrastructure processes; tool denials name the program or path and mark the expected ones of a read-only shell; the reviewer role keeps to simple read commands and writes an unrunnable reproduction as `static:`, and its denials reach triage; no ROUTE_UPGRADED when the route does not change; no RESULT_HEALED for an absent optional scout write-set; the task part of a prompt (input, diff, findings) is measured as its own budget class, so BUDGET_OVER no longer fires on every role.
- planner-orch: a brief repeated during a piece ignores the content snapshots of its reads, so the executor's own edits no longer cause INPUT_REBUILT.
- scripts: `affected-tests.py` runs the typecheck baseline gate with every `packages/*/lib` Python change and on tier all; orch type errors back to the baseline.
- Planner-orch: generated brief/research inputs use `@plan/inputs/` in both plan layouts, and execution evidence stays in lifecycle-owned check results, preserving phase readiness across conductor items and resumes.
- Planner: phase readiness certificates bind semantic inputs and policy; `readiness record|status`, required design-audit gates and execution-economy audit checks. Planner-orch provides read-only `planner:check` preflight for incomplete briefs and unknown scenarios. Schema compatibility recognises required objects as disjoint from bounded empty-object branches.
- orch, gui-orch: detached run/resume with nonce-bound startup acknowledgement and private logs; GUI launches survive restart and show conductor health, silence, beacon and launcher. Added printable/verifiable systemd user supervisor units, conductor lifecycle events and warning events for stage/check/disk/stall beacons.
- orch: detached resume reports invalid retries and limit overrides before acknowledging startup; roles and checks do not inherit the conductor's internal detach authority or launcher environment.

### Changed

- orch, gui-orch: a run whose piece waits for the answer to a question now ends `waiting` (`run.end` outcome `waiting`, `state.status` `waiting`, Stop `WAITING_DECISION`, **exit code 4**) instead of `stopped` / `ITEM_BLOCKED` (exit 1), and with `on_blocked = report` instead of `finished` (exit 0) while a piece still waits. `conduct status --json` lists `waiting: [{item, question_ids, since}]`; `orch conduct continue --run R [--item I …] [--partial]` and `answer … --continue` go on with the answered pieces in one command (`QUESTIONS_OPEN`, exit 1, when a blocking question has no answer; `NOT_WAITING` for a piece that does not wait). The GUI can answer questions (`gui-orch.answer`), continue (`gui-orch.continue`) and `resume` with `--retry`, and shows a waiting run as such. A script that reads exit 1 as "the run stopped" must handle 4 first; a blocked piece without a question and a denied question stay `ITEM_BLOCKED`, exit 1.
- orch: an `escalation` issue of the stage-report may name `escalation_class` (`decision`, `environment`, `pre_existing_red`, `scope`, `authority`), and the executor role gets an Autonomy section (what to decide alone, what to ask, what to escalate). A `decision` escalation without a question becomes the blocking question `esc-<n>` and takes the normal question flow, gates included; the other classes are blocks with the codes `ENVIRONMENT_BLOCKED` (with the hint to run `orch.py doctor`, check the sandbox and `--allow-path`), `PRE_EXISTING_RED`, `SCOPE_EXPANSION` and `AUTHORITY_REQUIRED` and never reach the advisor.
- orch, planner, planner-orch: answers are no longer lost with the run. After a piece is registered (never while a question of it still waits), the conductor records each answer of an owner and each advice or panel recommendation it applied as an accepted decision of the plan (`orch.py source decision`, the new optional work-source/v1 operation `decision`; the plan gets a `D#` with `applies_to` the piece, `answered_by` and an `origin` with `question_key`, `question_digest`; a file input appends to `decisions.json`; a source without it is the info `DECISION_NOT_RECORDED`). The next run of the piece answers the same question from that decision without stopping (`QUESTION_REUSED`; `question_key` is the hash of the piece, kind, text with its numbers, full options and answer schema, so a changed number or option is a new question, and a decision that does not fit is `QUESTION_REUSE_REFUSED`); approval and credential are never reused. `exec/v1` decisions may carry `question_key` and `question_digest`, `plan/v1` decisions an optional `origin`, records/v1 questions `question_key`, `question_digest`, state `advice_applied`.
- orch: `[orch.advisor] panel = ["grok/frontier/high", "claude-code/frontier/high"]` (2 or 3 routes) with `panel_on` (`low_confidence` by default, `always`) asks independent advisors for one problem: agreement is applied, a majority gets one round of critique by a member of the minority, a split goes to the owner. It is one round of `max_rounds`, at most `len(panel)+1` calls, every call admitted by the token budget, and its result passes the same human gate, minimum confidence and path categories as one advice. The record is `advice-<n>-panel.json` (new `advice-panel/v1` kind); infos `ADVISOR_PANEL` and `ADVISOR_PANEL_FAILED` (a member that cannot start, such as `codex`, is skipped).
- orch, planner: review corrections now use bounded `fix-brief/v1` handoffs (12 findings / 24000 characters), preserve every Blocker and carry deferred Major findings into later corrections. Check tails are bounded; group reviews use closed JSON. Interactive plan-run uses the conductor review-only runner and content-bound receipts, with one recorded review-intent rule.
- orch: executor sessions keep a slot per piece with a fingerprint (provider, project, worktree, attempt, instructions, authority, isolation home, base): a retry of an earlier piece resumes its own session, a changed authority or instructions never resumes, and every executor round says `SESSION_RESUMED` or `SESSION_FRESH` with the reason (also `data.session` of `orch.agent.started` and the observer report). Resume follows the provider's capability record (Codex and Grok resume through the launch catalog), `session.max_idle_s` expires an idle session, a group review follow-up resumes the session of the last reviewed piece or starts fresh with the handoff of the whole group, and an older run's single session slot is migrated on resume (`SESSION_STATE_MIGRATED`). `batch-review.py` writes the follow-up input of a Blocker or Major finding, and a route that has no resume command (a Codex command line from `[orch.conductor.argv]`) starts every session fresh.
- orch: group-review follow-ups retain overflow findings in a durable backlog, assign later bounded correction rounds, and block settlement with explicit unresolved debt when the correction allowance is exhausted.
- orch, planner: blocked registrations omit automatic review receipts; historical corrected findings no longer authorize edits after a later review. A check-fix following a completed overlap review without a combined correction requires a new review within the existing round limit.
- orch, planner, planner-orch: per-item reviews now produce content-bound `review-receipt/v1` records and finding keys. Registration forwards `--review-receipt` to planner finish; opt-in `settings.review_receipt: required` gates requested reviews on a fresh receipt and no open Blocker findings. `register-review --receipt` records the receipt, and legacy findings accept `id` and `reproduction`.

### Added

- orch, planner, planner-orch: run option `commit.mode: implementation-and-fixes` (default `final-only`, which changes nothing) commits a piece in stages: the implementation as a checkpoint after the first green checks and before the first review, one fix commit per green correction of the review (trailers `Plan-Run`, `Plan-Attempt`, `Plan-Stage`, and `Plan-Review`, `Plan-Findings` on a fix), then the final commit of the records and plan files. Each stage has its own receipt (`receipts/commit-<stage>.json`) and a crash between a stage commit and its receipt never commits the stage twice (the commit is found by its `Plan-Stage` trailer). The review reads from the parent of the first commit of the piece (`state.items.<ref>.commits`), the group review and the handoff read all of them. `plan.py commit --paths-only --path P…` commits exactly the given product paths (`PATH_OUTSIDE_SCOPE` for a path the task files do not cover) and leaves plan files and the other dirty paths; `orch source commit` takes `--role`, `--stage`, `--trailer`; a group-review follow-up carries `plan`, `items` and the finding keys in its provenance and in its commit message. The interactive `plan-run` command now commits the implementation before the review, each fix with `--role fix`, and the rest at the end.
- orch: startup fence of the autopilot. Launch intents are written, adopted and cancelled only under the new short `<runs root>/autopilot-launch.lock` (lock order: launch lock, checkout lock, run lease). A child `run`, `continue` or `resume` of the autopilot (`SKM_ORCH_AUTOPILOT_STATE`, `SKM_ORCH_AUTOPILOT_LAUNCH_ID`) checks under that lock, before any lock, lease, run folder, claim or role, that `autopilot.json` still names its run and launch id as `launching`. It keeps the lock until its `started` acknowledgement is written; otherwise it acknowledges `refused` with the new code `AUTOPILOT_LAUNCH_CANCELLED` and exits 1. A controller adopts an acknowledged launch, also one acknowledged after its 20 s wait ran out, and cancels a new run that never started after 30 s (`never_started` once). For an existing run it replaces the cancelled intent, in the same save, by the next attempt with a new launch id: that attempt survives a crash, a stop or `max_runs` and is started again before readiness. A `continue` saves the pieces it takes back, and its next attempt is `resume --retry` of them, so a continue that died after taking them back is not refused `NOT_WAITING`. A run held without the acknowledgement stops with `AUTOPILOT_CHECKOUT_LOST`, and a partial new run with `AUTOPILOT_STATE_INVALID`. A late child of a cancelled launch can no longer start, and the session no longer stops on it. `detach.spawn` takes an optional `ack_nonce` and sets up the acknowledgement channel itself (generated by default).
- orch: `orch conduct autopilot start|status|pause|resume|drain|stop|explain`, a deterministic controller (no model) that works through a plan lane after lane: it continues runs whose questions were answered first, else asks the work source for the next lane (op `readiness`), checks that exactly the phase of that lane is ready, starts `conduct run --plan P --items <lane>` as a detached child with `autopilot-options.json` (`scope.outside = block`, and the run cap of `--run-tokens-hard-max`), and classifies how it ended: go on, wait for answers while independent lanes run, wait for a quota reset and resume, resume a crashed, hung or once-failed run within `max_recoveries` (through the supervisor library and a plain `conduct resume`), or stop with an `AUTOPILOT_*` code (exit 0 for `NO_WORK`, `DRAINED`, `STOPPED`, `MAX_RUNS`, `MAX_WALL`, 1 for the others), written to `<runs root>/autopilot.json` (new records/v1 kind `autopilot-state`, with the launch intent of each child written before it starts) and sent as the new event `orch.autopilot.stopped`. Policy `[orch.autopilot]`: `allowed` only from the machine layer (a project that sets it is ignored and the session stops `AUTOPILOT_NOT_ALLOWED`), `enabled` by the project, `require_readiness` on when any layer turns it on, every limit (`max_runs`, `max_wall_s`, `max_no_progress_runs`, `max_auto_decisions`, `quota_wait_max_s`, `max_recoveries`) the lowest of the layers and flags; the deadline of `max_wall_s` survives restarts. One controller per checkout (`autopilot.lock`, `AUTOPILOT_BUSY`); requests go through `autopilot.request.json` (records/v1 `autopilot-request`); `status --json` and `explain --json` print the new conductor/v1 kinds `autopilot-status` and `autopilot-explain`.
- orch, planner-orch: the optional, read-only work-source/v1 operation `readiness` (`{collection, plans_root?}` → `{outcome: ok|refused, phases: [{id, status, digest}], next: {kind, items, phase, message}, reason_code?, message?}`) and `orch.py source readiness (--plan P | --input FILE) [--plans-root DIR]`, for autopilot: the planner bridge answers the readiness of every detailed phase (`plan.py readiness status`) and the next lane, read from `plan.py next --parallel 1 --json` exactly as `claim` reads it; a file input and a source without the operation are refused with `READINESS_UNSUPPORTED`. A new `oneOf` branch of the work-source/v1 input and output schemas: `aicore schema compat` reports `oneof-changed` (the contract is alpha; a warning, not a regression).
- orch: `orch conduct supervise [--once] [--run R] [--recover notify|stop-only|resume]` and `orch conduct reap --run R`. The supervisor classifies each run by its health and acts within `[orch.supervisor] recover` (default `notify`: say so only; a project file cannot raise it and a flag can only lower the machine's): it snapshots and stops a hung conductor by `(pid, start_ticks, boot_id)` of its lease (SIGINT, SIGTERM, SIGKILL to that pid only, nothing when the identity does not match), reaps the role processes and agent records of a dead one under the checkout lock and run lease, and with `resume` starts a detached `conduct resume`, never after a stop that needs the owner and at most `max_recoveries` per `window_s` per run (then `given_up`). Every action is a line of `<run>/supervisor.jsonl`, an `info` line `SUPERVISOR_*` and an `orch.conductor.health` event; the memory of the breaker is `supervisor-state.json`. `orch.conductor.health` joins the published events.
- orch: heartbeat and health of a run. The conductor writes `<run>/heartbeat.json` (`records/v1` `heartbeat`: identity, `seq`, the step, the last sign of progress, the CPU of the process tree, the repeated command and the blocking call in progress with its deadline) from its own loop and from the looks at its roles and checks, never from a timer; `lease.json` names the owner by `start_ticks`, `boot_id` and `launcher` (`SKM_ORCH_LAUNCHER`), so a pid alone is never taken for the owner. A role that writes nothing but spends CPU in its process tree is no longer stopped by `stage_idle_timeout_s` (nor a check by `check_idle_timeout_s`); a sleeping tree still is. New beacons `STALL_SUSPECTED` (the same tool command `limits.stall_repeat_n` times, or a stream that grows `limits.stall_window_s` without a tool step), `CHECK_IDLE` (`limits.check_idle_warn_s`) and `HEARTBEAT_NOT_WRITTEN`; they stop nothing. `orch conduct status` shows a `health:` line (`health` in `--json`) and `orch conduct runs --json` a `health` class per run: `running`, `waiting_provider`, `waiting_tool`, `waiting_owner`, `waiting_budget_reset`, `suspected_stall`, `hung`, `orphaned`, `stopped`, `finished`, `unknown`. Three new `limits` keys (`stall_window_s`, `stall_repeat_n`, `check_idle_warn_s`).

## [0.34.0] - 2026-10-23

### Changed

- orch: `scope.outside_module` defaults to `deviation`: files of another module than the write set names no longer stop a piece; they are a deviation that raises its review risk, and a plan layer can still set `block`. In phases P4–P5 every one of the three `OUTSIDE_MODULE` stops was a legitimate repair accepted later.
- orch: the writing Claude Code roles (executor, bounded-implementer) start with `--setting-sources user,project`. In a linked worktree Claude Code also loaded the main checkout's `.claude/settings.local.json`, whose context-economy `Read` denies (`skills.json`, lock files) became `/dev/null` masks under the sandbox, so an executor could not regenerate `packages/skiller/skills.json`. The user's own denies still apply.

### Added

- orch: write-protected paths. `policies/protected_writes.py` lists the paths `claude-code` refuses to write in a session without prompts (measured on 2.1.309: `pyrightconfig.json`, `.mcp.json`, `.env`, `.envrc`, `.npmrc`, `.pre-commit-config.yaml`, `.gitmodules`, `.claude.json`, shell rc files and everything under `.claude/`, `.vscode/`, `.idea/`, `.husky/`, `.devcontainer/`, `.git/`, at any depth). Before the scout the conductor checks the write set of the piece: the beacon `WRITE_PROTECTED_PATH` names the paths and the executor prompt gets a `Protected paths` rule (stage the content under `<artifacts>/protected/<path>`, end `blocked` with `WRITE_PROTECTED_PATH: <path> -> <staged path>`; the owner places the file and retries). The executor no longer meets the refusal after a whole round.
- orch: `orch conduct status` shows why a blocked piece stopped: the code of its first escalation after the outcome and its text on an `escalation:` line (`escalation` in `--json`); the `item.end` line of a blocked piece carries them as `reason_code` and `message`.
- aicore, hub: `aicore schema codegen --root DIR --out FILE [--check]` generates a stdlib `TypedDict` module (`NotRequired`, `Literal`, `Union`, `Dict` for `patternProperties`) from the contract schemas of a directory, deterministically; `--check` exits 1 with `SCHEMA_CODEGEN_DRIFT: <out>`, and a shape outside the supported mapping exits 1 with `SCHEMA_CODEGEN_UNSUPPORTED: <file>:<pointer>`. `aicore schema` now dispatches `compat` and `codegen`. `configs/schema-types.json` and `scripts/schema-types.py --check|--write` keep `orch/_types/{records,conductor,exec,work_source}.py` and `planner/plan/_types.py` in step with their schemas (the generator `schema-types` is part of the golden check). `RunStore.load`/`save` and `questions.read` are annotated with the generated `Run`, `State` and `Questions`; behaviour is unchanged.
- aicore: shared primitives. `aicore.util.lock` (`FileLock` with the samestat loop, `hold`, `LockTimeout`, `probe_free`, `lock_descriptor`), `aicore.util.timefmt` (`utc_now`, `utc_stamp`, `parse_rfc3339` giving an aware UTC datetime, `epoch`, `seconds_between`; a naive text is UTC, a bad text is `None`) and `aicore.util.docio` (`read_document` / `write_document`: parse, migrate, validate against the schema, `durable_replace`; `DocumentCorrupt`, `DocumentInvalid`).

- orch: run records contract `schemas/records/v1` (`run`, `state`, `questions`, `item-options`, `item-routes`, `lease`; `orch.conductor.records`). `run.json`, `state.json`, `questions.json` and the `options.json`, `routes.json` and lease files of a run are checked against it when written and when read: a document that does not match stops with `RUN_INVALID`, `STATE_INVALID`, `QUESTIONS_INVALID` or `RECORD_INVALID` and names the file, the JSON pointer and the problem, instead of being read as nothing (a broken `questions.json` used to look like "no questions"). Runs started before have no tag and are migrated in memory, so they resume; their files are not rewritten by a read. `orch.py validate` knows the six kinds.

- orch: run records contract, part 2: `schemas/records/v1` adds `risk`, `review-strategy`, `process`, `agent-request`, `agent-result`, `agent-usage` (tag `$schema`) and `review-verdict`, `provider-gates`, `observer-report`, `prompt-diff`, `conformance-report`, which keep their published short tag `"schema": "<name>/v1"`; `orch.py validate` knows all 17 kinds and `scripts/test-schema-tags.py` resolves every tag with none pending. `risk.json`, `review-strategy.json`, `process.json` and the agent `request.json`/`result.json`/`usage.json` are checked when written and read; the agent records are now written crash-safely (fsync of the file and its folder). A `result.json` is either a finished run (exit, decisions, duration, stream, lingered) or an orphan (`error` `ORPHANED`); an empty one is `RECORD_INVALID`, not a successful run. The cold recovery of a step's token usage reads the agent records the same way: a damaged `usage.json` stops with `STATE_CORRUPT` or `RECORD_INVALID` instead of counting as zero tokens against `stage_tokens_max`. Cold recovery stops with `RECORD_INVALID` on a `process.json` or `request.json` that does not match, before any signal. A damaged `provider-gates.json` (not JSON, or not `provider-gates/v1`) is no longer read as "no gates": it is `STATE_CORRUPT` or `RECORD_INVALID` with the JSON pointer, the run that reads it stops and `orch conduct gates` exits 1 (a missing file, a symlink or a non-regular file is still no gates). `observer.json`, `review-verdict.json`, `orch conduct prompt diff --json` and `orch conformance` are checked before they are written or printed; their bytes are unchanged. A resume whose state lost the batch review plan takes the `review-strategy.json` the run had already written instead of choosing again.
- orch, bridges/planner-orch: work source contracts. A brief is checked as an exec/v1 execution-input by the planner bridge before it is stored (`BRIEF_INVALID`, nothing stored) and by the conductor before it writes `input.json` (`BRIEF_INVALID` stop; a re-asked brief that does not match keeps the earlier input). The report of a registration is the new kind `register-report` of `work-source/v1` (closed fields, non-blank texts, a non-empty `evidence` of an issue; unique `checks_run` ids in code): the conductor checks the body before it writes `register-report.json` (`REGISTER_REPORT_INVALID` stop, a conductor defect found before anything is registered), the file source refuses a report outside it with the codes of the plan source (`REGISTER_UNCLASSIFIED`, `REGISTER_REPORT_INVALID`) before its gate, and the bridge keeps `check_report` with its codes and then checks the schema for parity (`REGISTER_REPORT_INVALID: schema parity: …`). `orch.py validate` knows `register-report`, `input` and `output`.
- planner: the scout map `context/<item>.scout.json` is a `scout-map` document (`$schema`, `item`, `provider`, `model`, `created_at`, `entries` of `{path, symbol?, why}`; a line that names no path keeps its text with `path` null), checked before it is written (a map outside it is a failed scout; `start` goes on). The context pack has the schema `context-pack` and is checked before it is written (`SCHEMA_INVALID`): the plan documents in it are held to their own kinds and the scoped summaries, read entries, decisions of other plans and ready units to closed shapes, so a damaged plan file (an item with a number for `summary`) no longer reaches an executor through the pack. A scout file of an older planner (`{"entries": [lines]}`) is left out of the pack. The bridge turns the entries into the same `path[:symbol] — why` hints as before.
- orch: `orch conduct answer` checks an answer against the question's `answer_schema` (`--text` is read as JSON unless the schema asks for a string): a mismatch is `ANSWER_INVALID` and nothing is written; a schema outside the closed profile is not applied, the answer is kept with `answer_schema_ignored` and `ANSWER_SCHEMA_IGNORED` is printed (and emitted when `resume --retry` hands the answer over).
- aicore: `load_contract_set` resolves a `$ref` from one contract set of a module to a sibling set of the same module (`urn:swissknifeman:<module>:<contract>:<kind>:v<N>` -> `schemas/<contract>/v<N>`).

- aicore, orch, planner, workspace, brain, gui: the `data` of an event is checked against the schema its `dataschema` names before the event is journaled (`aicore.ext.events.validate_data`, `check_data`). Data that breaks it is not written; the emitter prints `<MODULE>_EVENT_NOT_EMITTED: <type>: EVENT_DATA_INVALID: <first problem>` and the exit code of the command does not change; with `SKM_CONTRACTS_STRICT=1` (all `scripts/test.sh`) it raises `ExtError('EVENT_DATA_INVALID')`. brain publishes `schemas/event-data/v1/brain.note.created` and gui declares and publishes its journal events (`gui.run.started|succeeded|failed|cancelled|timed-out|lost|denied`, `gui.config.changed`); the broker used to emit `gui.run.timed_out`, which is not a valid event type, so that event was never journaled. `scripts/test-event-contracts.py` now fails when a module emits a type that is not in its `provides.events` or has no schema.
- orch: a progress line that breaks the `progress-line` contract is written to `progress.invalid.jsonl` and replaced in `progress.jsonl` by an `info` line `PROGRESS_LINE_INVALID`; the readers of the journal keep only valid lines, and `observer.json` has an optional `discarded_lines` count (also shown in `observer.md`). The observer report is written with `records.write` (crash-safe, mode `0600`, keys sorted).

- hub: type gate. `bash scripts/typecheck.sh --baseline` runs the pinned pyright 1.1.414 (a pyright of another version on `PATH` is not used; then `uvx`, then `pipx run`; `TYPECHECK_TOOL_MISSING` exit 2) over every `packages/*/lib` in basic mode and fails with `TYPECHECK_REGRESSION: <pkg> <old> -> <new>` when a package has more errors than `configs/typecheck-baseline.json`; `--update-baseline` writes only smaller counts (growth needs `--allow-growth "<reason>"`).
