## 1. Граница результата (объявляется ДО таблицы чисел)

Корпус — **8 кейсов, 50 находок `must_find`** (нижняя половина диапазона «50–100 = sanity check
и отладка рубрики», research/18 §4 + findings/P9-review-stability-facts.md §2) — **это диагностика
процедуры на малой выборке, не статистически надёжная оценка её качества.** Числа ниже НЕ
поддерживают формулировки вида «ревью стало стабильнее» или «покрытие выросло» (D58) — это
BASELINE (первый замер), сравнивать пока не с чем; сравнение — работа P9.4.

Матчинг (`matching-rules.md`) сознательно грубый: файл + type + пересечение строк ±10, БЕЗ
проверки смысла `statement` — находка «не по адресу» технически засчитывается как матч, если
формально совпали локация и тип. На практике за время разметки матчей вскрылось **29
неоднозначностей** (одинаковый score у двух кандидатов) — все разрешены человеческим арбитражем
(`arbitration.json`, ОБЯЗАТЕЛЬНОЕ поле `reason` на каждое решение) СТРОГО по содержанию находки
(что она реально утверждает), не по эвристике «выбрать первую по порядку». Основной источник
неоднозначностей — находки-ключи с широким/пересекающимся диапазоном (например «нет теста на X»
не привязано к одной строке) и «пробел в тестах» реальных прогонов, описывающие ДРУГУЮ, не
размеченную в ключе проблему на том же диапазоне (см. `plausible_but_unlabeled`, §3).

## 2. Метрики (пары point + разброс)

| Метрика | Значение по корпусу | Что это |
|:--|:--|:--|
| **J** (медиана попарного Jaccard) | **0.75** | согласие между прогонами одного кейса по множеству найденных must_find |
| **U1** (доля находок, встреченных ровно 1 разом из 3) | **0.20** | 80% найденных находок ловятся ≥2 прогонами из 3 — конвергентно для найденного |
| **R** (pass@3 по ключу) | **0.80** (40 из 50) | доля must_find, пойманных хотя бы ОДНИМ из 3 прогонов своего кейса |
| **R1** (медиана recall одного прогона) | **0.62** | типичный ОДИНОЧНЫЙ прогон ловит ~62% размеченных находок своего кейса |

**Разброс по кейсам (не прячется — J кейса C3 ниже объявленного порога 0.3, это измеренный факт):**

| Кейс | Класс | must_find | J (попарный) | R (кейс) | R1 (медиана) |
|:--|:--|--:|--:|--:|--:|
| C1 (flexcrm, логика) | логика | 7 | 0.80 | 0.86 (6/7) | 0.71 |
| C2 (core/io.py) | логика | 7 | 0.40 | 1.00 (7/7) | 0.71 |
| **C3 (harness review-gate)** | логика | 9 | **0.29** | 0.78 (7/9) | 0.56 |
| C4 (docs-impact CI) | конфигурация-провижининг | 6 | 0.50 | 0.67 (4/6) | 0.50 |
| C5 (public-hygiene/verify-tag) | конфигурация-провижининг | 6 | 0.75 | 0.67 (4/6) | 0.67 |
| C6 (docs/status.md) | доки | 7 | 0.75 | 0.57 (4/7) | 0.57 |
| C7 (maind mcp trimming) | логика | 4 | 0.75 | 1.00 (4/4) | 1.00 |
| C8 (core/provider_lock) | логика | 4 | 0.75 | 1.00 (4/4) | 1.00 |

**C3 (`J = 0.29 < 0.30`) — измеренный факт, не помеха.** Это самый большой и самый насыщенный
кейс (9 must_find, 769-строчный дифф с bash-диспетчером + python doctor.py); три прогона нашли
СИЛЬНО разные подмножества из 9 размеченных находок (пересечение слабое), при этом КАЖДЫЙ прогон
по отдельности был плодовит (12–24 находки на прогон, включая много `plausible_but_unlabeled`).
Интерпретация ГРАНИЦ, а не вывод: низкий `J` здесь похож на «пространство находок кейса C3
шире, чем один прогон может покрыть за проход» (объём/плотность реальных дефектов в диффе), а не
обязательно на «процедура ревью нестабильна вообще» — с корпусом в 1 кейс на класс разделить эти
две гипотезы нельзя (граница размера корпуса, см. §1).

## 3. Три корзины (детерминированы `score_review_runs.py`, RAG-правило: вне ключа ≠ ложь)

| Корзина | N | Комментарий |
|:--|--:|:--|
| `matched TP` | 94 | матчей находок прогонов с `must_find`-находками ключа (по всем 8 кейсам × 3 прогона) |
| `judged FP` | 3 | матчей находок прогонов с находками-ловушками (`is_trap=true`, T001–T003) — **из 72 возможных столкновений с ловушкой (3 ловушки × 24 прогона) сработало лишь 3** — это позитивный сигнал дисциплины против ложных срабатываний на правдоподобных, но опровергнутых гипотезах |
| `plausible but unlabeled` | 290 | находки прогонов, не совпавшие НИ С ОДНОЙ записью ключа — **не считаются ложными** (RAG-правило); включают как генеральную «плотность» реальных ревью-находок (каждый прогон нашёл СИЛЬНО больше 50/8≈6 находок на кейс — плотность реальных диффов выше плотности разметки ключа, ожидаемо для 50-находочного sanity-корпуса), так и отдельные острые находки за пределами ключа (например независимая находка про порядок `ResolveTenant`/`SubstituteBindings` в кейсе C1, зафиксированная в `arbitration.json` как заведомо НЕ форсированная в матч) |

## 5. Правило вердикта P9.4 (объявлено ЗДЕСЬ, до получения чисел повторного замера — Implementation Rules item'а)

Дословно из `phases/P9.md` (объявлено на дизайне item'а, до этого baseline-прогона):
**`ΔJ ≥ +0.10` И `ΔR ≥ 0` → сигнал улучшения; `ΔR < −0.05` → регресс; иначе → «сигнала нет».**
База сравнения для P9.4 — числа §2 этого документа (`J=0.75`, `R=0.80` по корпусу; см. также
разбивку по кейсам §2 для локализации, откуда идёт дельта, если она будет).
