### 1. High — a new `patternProperties` entry is marked compatible when it rejects old documents

`packages/aicore/lib/aicore/util/schemacompat.py:160` and `:181`

`property-removed` is suppressed when any new pattern matches the name, and `pattern-property-added` is always `breaking=False`. The value schemas are not compared. A document that validated before can fail after, with no breaking change in the report. Two shapes:

* An existing property stays, and a new pattern also matches it and is stricter (`id` string, plus `^[a-z]+$` requiring an integer). Both schemas apply, so `"id": "abc"` dies with `type`.
* The property is deleted and a pattern covers the name with a narrower schema (`a` string replaced by `^a$` integer).

```text
== pattern overlaps existing property
 old valid: True
 new valid: False
 new issues: [('/id', 'type')]
 changes: [('/patternProperties/^[a-z]+$', 'pattern-property-added', False, ...)]
 BREAKING REPORTED: False

== removed property covered by narrower pattern
 old valid: True
 new valid: False
 new issues: [('/a', 'type')]
 changes: [('/patternProperties/^a$', 'pattern-property-added', False, ...)]
 BREAKING REPORTED: False

== added overlapping pattern
 old valid: True
 new valid: False
 new issues: [('/ab', 'min_length')]
 changes: [('/patternProperties/^ab', 'pattern-property-added', False, ...)]
 BREAKING REPORTED: False
```

The same hole is what `pattern-property-added`’s own test locks in: `{}` to `patternProperties: {"^a": string}` rejects `{"a": 1}` and is reported as non-breaking.

### 2. High — a breaking `$ref` sibling on a later use of the same target is dropped

`packages/aicore/lib/aicore/util/schemacompat.py:91`

The visited key is the resolved target `(owner, fragment)`. The first use marks that pair. A later use of the same target returns immediately, so sibling keywords on that use are never compared. With `x` a plain `$ref` and `y` the same `$ref` whose `minLength` goes from 1 to 5, `{"x": "ab", "y": "abcd"}` is valid before and invalid after (`/y` `min_length`). `compare` returns `[]`.

```text
== $ref sibling tightened only on the second use
 old valid: True
 new valid: False
 new issues: [('/y', 'min_length')]
 changes: []
 BREAKING REPORTED: False
```

### 3. High — keywords beside `$ref` replace the target, so a stricter target is reported as a relaxation

`packages/aicore/lib/aicore/util/schemacompat.py:227`

`_expand` copies the referenced schema and then overwrites it with sibling keywords. The validator applies the referenced schema and the siblings together. Old: `$ref` to `{type: string, minLength: 5}`. New: `$ref` to `{type: string, minLength: 100}` plus sibling `minLength: 0`. `"hello"` passes the old schema and fails the new one (`min_length`). The checker reports only a non-breaking relaxation:

```text
== $ref sibling overrides a stricter target
 old valid: True
 new valid: False
 new issues: [('', 'min_length')]
 changes: [('', 'bound-relaxed', False, 'minLength is now 0 (was 5)')]
 BREAKING REPORTED: False
```

### 4. Medium — a map pattern can allow dotted entry names, and dotted paths cannot read or unset them

`packages/aicore/lib/aicore/config/model.py:265` (`_split_key` at `:72`, `matches` at `:110`)

The dot guard only rejects a pattern that matches the string `a.b`. `^x\.y$` and `^(?!a\.b$)[a-z.]+$` both load. TOML then stores the entry as one key, `("things", "x.y")`. `get("things.x.y")` and `_unset = ["things.x.y"]` split on every dot and miss it. `as_dict()` still shows the value.

```text
pattern '^x\\.y$' LOADED
  as_dict: {'things': {'x.y': 'secret'}}
  get 'things.x.y': CONFIG_UNKNOWN_KEY key=things.x.y
  get ('things', 'x.y'): secret
  unset resolve: CONFIG_UNKNOWN_KEY key=things.x.y ... unknown key for module 'maps'
```

The same output for `^(?!a\.b$)[a-z.]+$`. The shipped aicore patterns do not match these keys. Any other module schema that passes this check can.

### 5. Low — `propertyNames` with `type` other than `string` passes the profile

`packages/aicore/lib/aicore/util/schema.py:268`

The profile checks which keywords appear, not that `type` is `"string"`. A schema with `propertyNames: {"type": "integer"}` loads. Every real property name then fails `property_name`.
