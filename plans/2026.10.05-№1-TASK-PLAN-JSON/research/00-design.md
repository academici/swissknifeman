# PLAN1 design dossier — JSON-first Task plans

Normative for all phases together with D1–D4. Worked examples: `artifacts/design/examples.md`.
Every section names its owning item. "MUST" items are acceptance-relevant; everything else is guidance
the executor may refine locally without a decision.

## 1. Target layout (D1) — owner: P1.1/P1.2

Owner rule 2026-10-05: no migration or v2-awareness in code; plans are read and written only through `plan.py`; no code parses plan Markdown.

```text
plans/<PLAN-ID>/
  plan.json                 # identity, goal, rules, phase order, settings          (schema plan)
  brief.json                # owner messages verbatim + extracted requirements      (schema brief)
  phases/<Pn>/phase.json    # phase context, scope, batches, validation             (schema phase)
  phases/<Pn>/<Pn.m>.json   # one item: stable spec + volatile `result`              (schema item)
  phases/<Pn>/<Pn.m>/       # item workspace for sub-agents (owner M4), created on first unit
    <U#>.json               #   one work unit: spec + status + outcome                 (schema unit)
    <U#>/brief.md           #   generated mini-pack for the worker
    <U#>/…                  #   worker outputs: report, logs, scratch artifacts
  decisions/<D#>.json       # one decision or open question                          (schema decision)
  log.jsonl                 # append-only events, one JSON object per line           (schema log-event)
  research/ artifacts/      # free-form supporting files, referenced by path
  context/                  # generated context packs (gitignored via plan .gitignore)
  .gitignore                # "context/\n.lock\n" — written by `plan.py new`
  index.md plan.md roadmap.md status.md handoff.md open-questions.md   # generated views
  AGENTS.md CLAUDE.md       # generated provider guard: what to ignore, how to change the plan (§13)
```

Rules:
- JSON is the only source of truth; all checks run on JSON (`plan.py check`), no Markdown parsing exists.
  The six `.md` files are views; each starts with
  `<!-- generated by task plan.py render — edit JSON through plan.py -->`.
- Every JSON document has `"$schema": "urn:swissknifeman:task:plan:<kind>:v1"`; `<kind>` ∈
  `plan, brief, phase, item, unit, decision, log-event`. `log.jsonl` lines carry `"v": 1` instead of `$schema`.
- Paths inside JSON: repository-relative POSIX paths; a path starting with `@plan/` is relative to the
  plan directory (`@plan/research/00-design.md`). No absolute paths, no `..` segments.
- IDs: phase `P<n>` (n ≥ 0, no zero padding for new plans; `P08` style accepted when migrated),
  item `P<n>.<m>`, decision `D<n>`, owner message `M<n>`, requirement `B<n>`, validation `V<n>`.
  Qualified foreign refs: `PLAN<N>.P2.3`, `PLAN<N>.D4`, `<repo>:PLAN<N>.P2.3` (syntax-checked only).
- File name equals ID: `phases/P1/P1.2.json` ↔ `"id": "P1.2"`; `decisions/D3.json` ↔ `"id": "D3"`.
- JSON formatting (canonical, MUST): UTF-8, `ensure_ascii=False`, indent 2, keys ordered by the schema's
  `properties` order (unknown keys impossible — `additionalProperties: false`), trailing newline.
  Canonical form makes diffs stable across providers.

#### 2.5.1 unit.schema.json (owner M3/M4 — orchestration inside an item)

An item may be split by the designer (or by the executor at start, through `plan.py push`) into work units that
can be handed to other agents. The item executor stays the integrator: it dispatches, reviews, tests and finishes
the item. Units are not separate plan items: no own batch, no own route row, no own phase closure.

| Field | Type | Req | Notes |
|:--|:--|:--|:--|
| `$schema` | const URN | ✓ | |
| `id` | `^U[0-9]+$` | ✓ | local to the item; qualified form `P1.2/U3`; file `phases/<Pn>/<Pn.m>/<U#>.json` |
| `item` | itemId | ✓ | owning item |
| `title` | text | ✓ | |
| `goal` | text | ✓ | observable result of the piece |
| `files` | array path (minItems 1) | ✓ | files the unit OWNS (write set); parallel units must be disjoint |
| `reads` | array `{path, section?, why}` | | extra context beyond the item's reads |
| `depends_on` | array `^U[0-9]+$` | | units whose output this one needs |
| `checks` | array `^V[0-9]+$` or check | | item validation ids or own unit checks the worker runs |
| `route` | route | ✓ | minimum class for the worker (often below the item route) |
| `mode` | enum `self, delegate, either` | ✓ | `either` = executor decides; `self` = never hand out |
| `instructions` | text | | worker-facing guidance (≤ ~15 lines) |
| `status` | enum `todo, dispatched, returned, accepted, reworked, rejected` | ✓ | lifecycle-owned (`plan.py unit`) |
| `outcome` | object `{agent: actor, at: ts, notes?: text, changed?: array path, minutes?: integer}` or null | | written by `plan.py unit` |
| `updated_at` | ts | ✓ | |

Workspace `phases/<Pn>/<Pn.m>/<U#>/`: `brief.md` (generated at `dispatch`), and whatever the worker produces
(report, logs, scratch). Workers write code only to the unit's `files`; outputs that are not product go to the
workspace. Referenced in JSON as `@plan/phases/<Pn>/<Pn.m>/<U#>/<file>`.

Rules (checked by `check`): unit ids unique; `depends_on` acyclic and local; two units without a dependency path
between them have disjoint `files` (glob overlap = error) — so they can run in parallel; every `files` entry of a
unit should be covered by the item's `task_files` (warning otherwise); item `finish --status done` requires every
unit `accepted` or `rejected` with the item executor having done the work (`rejected` needs `outcome.notes`).

Detailed-item completeness (checked by `plan.py check` for items of a `detailed` phase, MUST):
`summary`, `why`, `scope.include`, `validation` (≥1 acceptance), `deliverables` (≥1) non-empty, and
`reads` or `task_files` non-empty. Skeleton phases may hold items with only the required schema fields.

## 3. Validator profile (R7) — owner: P1.1, module `lib/task/plan/schema.py`

Supported keywords (closed set; any other keyword in a schema → `SchemaProfileError` at load, fail closed):
`$schema, $id, $defs, $ref, title, description, type, enum, const, properties, required,
additionalProperties (false only), items, minItems, uniqueItems, minLength, pattern, oneOf, default`.
`type` may be a string or list (`["string","null"]`). `integer` accepts `int` but not `bool`; `number`
accepts int/float, not bool. `$ref` resolves only `#/$defs/x` and `urn:…:defs:v1#/$defs/x` from the
registry of loaded schema files. `default` is annotation only (store fills defaults explicitly).

API:
```python
class ValidationIssue(NamedTuple): path: str; code: str; message: str   # path like "/reads/2/path"
def load_registry(schema_dir: Path | None = None) -> Registry           # cached; default packages/task/schemas/plan/v1
def validate(doc: object, kind: str, registry: Registry | None = None) -> list[ValidationIssue]
```
Error codes: `type, enum, const, required, additional, pattern, min_items, unique, min_length, one_of, ref`.
Messages are English, one line, include the JSON pointer.

## 4. Store and authoring API — owner: P1.2, modules `store.py`, `model.py`, `ops.py`, `check.py`

- `model.py`: ID regexes and parsing (`parse_ref`, `item_phase("P1.2") -> "P1"`, numeric sort key so that
  `P1.10` follows `P1.9`), status enums, emoji mapping for views
  (`todo ⬜ Not started, in_progress 🟡 In progress, done 🟢 Done, done_with_deviations 🟠 Done with
  deviations, blocked 🔴 Blocked, skipped ⛔ Skipped by decision`), class/effort order, `phase_status(items)`.
- `store.py`: `Plan` = loaded snapshot (`plan`, `brief`, `phases{}`, `items{}`, `decisions{}`; log is read lazily);
  `open_plan(ref, plans_root=None)` resolves plan id, `PLAN<N>` short id, or path; `PlanLock` (fcntl
  `flock` on `<plan>/.lock`, 30 s timeout → `PLAN_LOCKED`); `save(doc, path, kind)` validates then writes
  atomically (temp file + `os.replace`) in canonical form, sets `updated_at`; `append_log(event)` validates
  and appends one line under the lock.
- `ops.py` (each mutation = lock → load → change → validate whole changed doc → save → `views.render_all`):
  `new_plan(codename, title, *, plans_root, repository, owner, authoring, date=None, plan_id=None,
  short_id=None)` — allocation identical to today's `plan_numbering.next_identity` (scan live + archive,
  read `| Short ID | PLAN<N> |` rows from `plan.md`, which the v3 plan view also renders); explicit
  `plan_id/short_id` adopt an existing identity (migration). Creates plan.json, brief.json (first owner
  message from `--message-file`/`--message`, required because `messages` has minItems 1), `.gitignore`,
  `log.jsonl` with `plan_created`. `goal`/`context` default to the title until set (`check` warns while
  `context == title`).
  `add_phase(plan, title, *, phase_id=None, data=None)`, `add_item(plan, phase, title, *, data=None)` (next
  free `Pn.m`, appended to `phase.items` and to a new solo batch unless `--batch` given),
  `add_decision(plan, title, *, data=None)` (next `D#`), `patch(plan, ref, merge_patch)` (RFC 7386 merge
  patch on the stable fields; `result`, `status`, `closed`, `design` are lifecycle-owned → `FIELD_OWNED`),
  `push(plan, ref, field, value)` (append to an array field), `set_brief(plan, merge_patch)`,
  `set_plan(plan, merge_patch)`, `set_batches(plan, phase, batches)`.
- `check.py`: `check(plan) -> list[Issue(level, code, where, message)]`; errors: schema, id/filename
  mismatch, phase item list ≠ files, unknown local ref in `depends_on/related/decisions/applies_to`, item in
  0 or >1 batches, batch item from another phase, dependency cycle (items and phases), detailed-item
  completeness (§2.5), decision conditional fields, `..`/absolute paths, `result` inconsistent with status
  (`done*` needs `finished_at`; `in_progress` needs `started_at`; `skipped` needs `result.decision`),
  stale views (`render --check`). Warnings: `required` read path missing and not produced by an `artifacts`
  output of a dependency; `task_files` with `change: modify` that does not exist.

## 5. Templates and views (B7) — owner: P1.3, modules `templating.py`, `views.py`

Mustache subset (`templating.py`, ≤ ~150 lines, no escaping, Markdown output):
`{{name}}` / `{{a.b}}` lookup through the context stack; `{{.}}` current value; `{{#x}}…{{/x}}` — list →
iterate, truthy scalar/dict → render once with it pushed; `{{^x}}…{{/x}}` — render when falsy/empty;
`{{>name}}` — partial `templates/plan/_name.md`; `{{! comment}}`. Missing key renders `""`. A standalone
tag line (only a section/partial tag plus whitespace) is removed together with its newline — so table rows
from partials produce no blank lines. Unknown tag syntax → `TemplateError` (fail closed).

Templates: `packages/task/templates/plan/{index,plan,roadmap,status,handoff,open-questions}.md` and partials
`_meta-row.md, _phase-row.md, _item-row.md, _batch-row.md, _decision-row.md, _question.md, _event-row.md`.
`views.py` builds a plain dict view-model per template (all strings pre-formatted: emoji status, `cell()`
escapes `|` and collapses newlines for table cells, dates) and renders; templates contain no logic beyond
sections. `render_all(plan)` writes only changed files; `render_all(plan, check=True)` returns the list of
stale files without writing.

## 6. Lifecycle (P2.1) — module `lifecycle.py`

### 6.1 next(plan) → Next

Walk `plan.phases` in order; skip closed phases. For the first phase not closed:
- phase deps (`depends_on`, default previous phase) not all closed → `waiting` on them;
- `design == skeleton` → `design-phase`;
- else first batch (in `batches` order) that has a non-terminal member: ready members = non-terminal items
  whose `depends_on` are terminal (`done`, `done_with_deviations`, `skipped`; `blocked` is NOT satisfying)
  or earlier members of the same batch; if none ready → `waiting: <first unmet dep>`; owner-gate items without a
  grant → `waiting: gate <GATE>`; else `run-items` with the batch's remaining members in phase order and
  route = max over members.
All phases closed → `archive` if plan status ≠ archived, else `terminal`. A blocked item makes its phase
`blocked`-closed only through `finish`; `next` then reports `waiting: blocked <item> — <escalation>`.

### 6.2 start(plan, items, actor, *, grants=(), scout=None) → StartResult

1. Validate: items exist, belong to one phase, phase `detailed`, each item `todo` or `in_progress` (resume),
   dependencies satisfied (as in 6.1, earlier requested items count), owner-gate items have a
   `gate_granted` log event for their gate or a `--grant` value recorded now.
2. Route: resolve `actor.model` against `command-routing.json` `mappings[provider].model_inventory.entries`
   (id, then `patterns` regex, skip `status: retired`); admitted class = highest of entry roles among
   `economy < implementation < frontier`. Lower than an item's `route.class` → `ROUTE_UNDERSHOOT`
   (refuse, no mutation). Unknown model or provider → warning `ROUTE_MODEL_UNKNOWN` recorded in the start
   event `data`, NOT a refusal. Effort compared the same way when `actor.effort` is given; lower → refuse.
   No session-log scraping, no exact-invocation matching.
3. Mutate: status `in_progress`, `result.started_at` (kept on resume), `result.executor`; log `start`
   (data: requested items, route verdict); build context packs (P2.2) for each item; render views.
4. Return: paths of context packs + compact text: "Read context/<item>.md first. Batch: … Next after finish: …".

### 6.3 finish(plan, item, status, *, notes, checks={V#: exit}, deviations=(), pending=(), escalation=None,
commits=(), decision=None)

- `done`: every `acceptance` check of the item has exit 0 in `checks` (or recorded earlier in
  `result.checks`); missing/non-zero → `CHECKS_MISSING`/`CHECKS_RED` (no mutation).
- `done_with_deviations`: acceptance checks recorded (any exit) and ≥1 deviation text.
- `blocked`: `escalation` required. `skipped`: accepted decision ref required.
- Writes `result`, status, `finished_at`; log `finish`. If every item of the phase is terminal → write
  `phase.closed` (result = worst of members: blocked > done_with_deviations > done; all skipped → skipped)
  and log `phase_closed`; if every phase is closed → plan `status: done`. Render views. Return `next()`.
- `finish` on an item not `in_progress` → `NOT_STARTED` (except `skipped`, allowed from `todo`).

### 6.4 Other verbs

| Verb | Effect |
|:--|:--|
| `log(plan, target, type, summary, impact=None, next=None, refs=())` | friction types only (`deviation, blocker, difficulty, assumption, note`); validates and appends; renders `handoff.md` |
| `decide(plan, D#, accept=option or text, rationale, by=owner|agent)` | open → accepted (writes `decision`, `rationale`, `answered_by`), log `decision` |
| `supersede(plan, old, new)` | sets `superseded_by`/`supersedes`, statuses |
| `grant(plan, gate, note)` | log `gate_granted` (owner authority recorded by the agent on an explicit owner message; `note` quotes it) |
| `design_done(plan, phase)` | runs `check` limited to the phase; errors → refuse; sets `design: detailed`, log `design_done` |
| `reopen(plan, item, reason)` | terminal → `todo`, clears `phase.closed`, logs `note` with reason (owner amendment path; replaces v2 repeat-admission) |
| `archive(plan)` | requires plan `done` or `--force` with reason; moves dir to `plans/archive/`, status `archived`, log `archived` |

There are no batch receipts, digest seals, design fingerprints, terminal leases, evidence graphs or
write-site checks (D2).

## 7. Context pack (B5) — owner: P2.2, module `context.py`

`build(plan, item_id, *, max_inline_lines=200) -> Path` writes `context/<item>.md` and returns its path.
Order follows the Codex Goal/Context/Constraints/Done-when pattern (R5):

1. **Task** — `PLAN<N>.<item> — <title>`; plan title; phase; batch members; route; how to finish (two CLI lines).
2. **Goal** — item `summary`, `why`; plan `goal` (one paragraph).
3. **Scope** — include / exclude.
4. **Context** — phase `goal`, `context`, `contract`, `pitfalls`; plan `rules`.
5. **Decisions** — every ref in item `decisions` + accepted decisions whose `applies_to` contains the item or
   its phase: `decision` + `consequences` (open ones flagged "OPEN — ask/decide before relying").
6. **Upstream results** — for `depends_on` and `related` local items: status, `result.notes`,
   `result.deviations`, output `artifacts`.
7. **Reads** — in order: path, section, why, required; for `.md` files with `section` the section body is
   inlined when ≤ `max_inline_lines` (heading match: case-insensitive heading text or `§N` prefix); other
   files are listed only. Missing required read → `start` refuses with `READ_MISSING` unless the path is an
   `artifacts` output of a dependency that is not yet terminal (then reported as such).
8. **Files to change (hint)** — `task_files` with exists/new marker.
9. **Artifacts** — inputs/outputs.
10. **Lessons** — friction events (`deviation, blocker, difficulty, assumption`) from this phase and from related
    items, newest first, max 10, one line each.
11. **Rules & guidance** — item `rules`, `guidance`, `examples` (paths).
12. **Done when** — validation checks (id, cmd, expect, kind), deliverables, phase validation if this is the
    phase's last item.
13. **Scout map** (P4.1, only when present) — `context/<item>.scout.md` content.

The pack prints its size (chars, ≈tokens = chars/4) for information only; there is no size gate.
