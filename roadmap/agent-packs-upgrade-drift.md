# Roadmap: agent-packs upgrade — сверять ФАКТ файлов, а не только номер версии

**Статус:** ⬜ к внедрению — критерий сработал (два независимых полевых кейса в одной раскатке 2026-07-11).
**Дом:** `packages/harness/lib/harness/agentpacks.py` (`upgrade`), `harness agent-packs`.

## Проблема (измеренная)

`harness agent-packs upgrade` решает «нужно ли обновлять» **только по номеру версии пака**
(`pack.json:version` против записи в `.claude/agent-pack.lock.json`). Фактическое состояние файлов
в проекте не сверяется. Отсюда два разных отказа, оба пойманы живьём при раскатке SKM-ROADMAP-005:

**Кейс A — изменение не доезжает (тихо).** P6.2 добавил пункт «Glossary impact?» в 5 `reviewer.md`
паков, но `pack.json` не бампнул. `upgrade` отвечал `agent-pack 'laravel-package' уже актуален
(v0.2.0)` и **не доставил изменение ни в один из 11 проектов** с установленными паками. Дефект
обнаружился только ручным грепом «а строка-то доехала?». Контент-дрейф источника невидим для
апгрейда.

**Кейс B — удалённые файлы не восстанавливаются.** В botkit стояли ДВА стек-пака с пересекающимися
targets (`backend-laravel` + `laravel-package`); снос первого удалил файлы, которыми владеет и второй
(reviewer, slice-builder, test-writer, dev-loop, review-gate…). `upgrade --pack laravel-package`
снова ответил **«уже актуален (v0.2.1)»** и оставил проект с паком в локе и БЕЗ его файлов.
Спасло только то, что рядом лежали `.pack-new`, и что `render --auto` умеет пере-материализовать
из lock-ответов. Проект с гитигнорнутым `.claude/` (как botkit) в такой ситуации не откатывается
через git — это тихая потеря рабочей конфигурации.

Общий корень: **версия — не инвариант состояния.** Lock уже хранит `base_sha256` каждого файла —
данные для честной сверки есть, но `upgrade` их не использует как триггер.

## Правила (что должно стать)

1. **`upgrade` сверяет факт, а не только версию.** Для каждого файла пака: существует ли target;
   совпадает ли его хэш с `base_sha256` лока; совпадает ли хэш ИСТОЧНИКА с тем, из которого
   рендерился lock. Любое расхождение → файл в план апгрейда, независимо от номера версии.
2. **Отсутствующий target — всегда `new`,** даже при равных версиях (кейс B: восстановление).
3. **Дрейф источника при равной версии — `warn` + предложение применить** (кейс A): «пак v0.2.0
   не менял версию, но 5 файлов источника изменились — применить?». Молча игнорировать нельзя.
4. **Категории сохраняются** (`new` / `safe-apply` / `conflict` / `user-owned`): локальные правки
   по-прежнему не затираются, конфликт по-прежнему пишет `*.pack-new`.
5. **Бамп версии остаётся обязательным для авторов паков** — правило не отменяется, но перестаёт
   быть ЕДИНСТВЕННОЙ защитой (сейчас забытый бамп = тихая потеря доставки).
6. **Пересечение targets между паками** (корень кейса B) — минимум `warn` в `agent-packs doctor`:
   «два пака владеют одним файлом» (сейчас это молча ломается при `remove`).

## Реализация

- `agentpacks.py`: план апгрейда строить из сверки хэшей (target-факт + source-факт против lock),
  а не из `version >`. Ветка «версии равны» → не `return`, а обычный расчёт плана (пустой план →
  честное «нечего делать»).
- `agent-packs doctor`: добавить измерение «targets, на которые претендуют 2+ установленных пака».
- Тесты: (а) контент источника изменён при равной версии → upgrade предлагает apply; (б) target
  удалён при равной версии → upgrade восстанавливает; (в) локально правленный target при равной
  версии → `conflict`/`.pack-new`, не затирание.

## Критерий внедрения

**Сработал** — два независимых отказа за одну раскатку, оба с тихой потерей (недоставленное
изменение и удалённые файлы). Внедрять ближайшей правкой `agentpacks.py`; отдельного тула не
заводить (анти-bloat — это поведение существующей команды).

## Источник

Полевая раскатка SKM-ROADMAP-005 на флот (2026-07-11): кейс A — «Glossary impact?» (P6.2) не доехал
ни в один из 11 проектов; кейс B — botkit, снос `backend-laravel` унёс общие файлы `laravel-package`,
`upgrade` их не вернул. Оба зафиксированы по `field-feedback-loop` (отклонение от обещанного
поведения — не глотать, а маршрутизировать).
