Против first-party лимита: бюджет листинга = **1% контекстного окна модели**. Для 1M-контекста
(Opus 5 / Sonnet 5) это ≈ **10 000 символов**; для 200K-модели — ≈ 2 000.

### Что из этого следует

Типовой php/laravel-подписчик (`general`+`architect`+`system`+`quality`+`php`) несёт
≈ 4 797+2 998+1 937+2 652+3 256 = **15 640 символов** описаний — то есть **переполняет** 10 000-символьный
бюджет примерно в 1,5 раза. При переполнении клиент, по first-party, «drops descriptions starting with
the skills you invoke least» — то есть часть описаний **уже не доезжает до модели**, а имена остаются.

Отсюда три вывода, каждый из которых меняет ТЗ экс-P7:

1. **Экономии резидента от сжатия почти нет.** Резидент уже ограничен сверху бюджетом; сжатие топ-7 на
   ~30% (порядка 700–800 символов при текущих 360–420 симв/описание) снимает ~5% переполнения. Прежняя
   формула «≈260 ток × N подписчиков» описывает мир без бюджета листинга.
2. **Реальный выигрыш сжатия — не токены, а попадание в листинг.** Освобождённые символы достаются
   описаниям скиллов, которые сейчас роняются как «реже вызываемые». Это выигрыш **точности
   срабатывания**, и мерить его надо иначе (какие скиллы вернулись в листинг), чем экономию.
3. **Есть более сильные и более дешёвые рычаги того же класса**, которых в экс-P7 не было:
   `skillListingBudgetFraction`/`SLASH_COMMAND_TOOL_CHAR_BUDGET` (поднять бюджет),
   `skillOverrides: "name-only"` (снять описание у низкоприоритетных, не трогая исходники), и
   сокращение самого набора бакетов у проекта. Первые два — настройки, не правки 216 файлов.

## 2. L4 (экс-P8): куда целиться тримминг maind

### Repo-факт: где точка врезки

`packages/maind/lib/maind/mcp.py` — 382 строки, stdlib. Все 11 инструментов возвращают результат через
**одну воронку** `_content(payload, is_error=False)` (`mcp.py:97-102`), которая делает
`json.dumps(payload, ensure_ascii=False, indent=2)`. То есть потолок/receipt внедряются в одном месте,
без правки каждого инструмента. `isError` там уже занят под ошибку инструмента — под «частичность»
переиспользовать нельзя.

Форма ответов по классам:
- **списочные** (растут неограниченно): `maind_memory_recall` (union по scope'ам), `maind_graph_query`/
  `maind_graph_neighbors` (обход глубины `depth`), `maind_graph_project`, `maind_memory_links`
  (граф + память), `maind_projects_status` (hub + отчёт по каждому проекту);
- **ограниченные по природе**: `maind_memory_store`/`forget`, `maind_graph_path`, `maind_agents_list`,
  `maind_projects_list`.

`indent=2` — заметная доля объёма на крупных payload'ах и первый кандидат к отключению при превышении
порога (чистая экономия без потери данных).

### Целевые числа (пересобраны под first-party)

| Порог | Источник | Что значит для нас |
|:--|:--|:--|
| **10 000 токенов** | warning Claude Code | **рабочая цель потолка** — ниже него, чтобы не порождать предупреждение |
| 25 000 токенов | дефолт `MAX_MCP_OUTPUT_TOKENS` | верхняя граница «до выгрузки на диск», не цель |
| 500 000 символов | потолок `_meta["anthropic/maxResultSizeChars"]` | рычаг для заведомо крупного инструмента, если урезать нельзя |
| 2 048 байт | обрезка `description` инструмента и server instructions | ревизия описаний 11 тулов (`mcp.py:26-81`) |

### Порядок предпочтения (синтез слоя 1 + формы наших ответов)

1. **Сузить на входе** — параметры/лимиты у списочных инструментов (`limit`, глубина, поля), чтобы
   крупный ответ не рождался.
2. **Summary+detail** там, где обход по природе широкий (`maind_projects_status`).
3. **Потолок + честный receipt** — хвостовой случай: `truncated: true` + `returned_count`/`total_count`
   + подсказка «как дозапросить». Голый флаг не снимает ни один из трёх отказов полевой практики
   (галлюцинация полноты · потеря провенанса · retry-путаница).
4. **`_meta`-аннотация** — только для инструмента, чей полный ответ реально нужен целиком.

Клиентская выгрузка-на-диск — **аварийный выход, не канал доставки**: она меняет режим работы (модели
нужен отдельный шаг чтения файла), поэтому сервер обязан ужиматься **до** порога, а не полагаться на неё.
