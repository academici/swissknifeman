# P0.4 — self-host hook integrity: diagnosis and repair record

RAG:— (repo-grounded: own runs of `codex doctor --json`, `harness doctor`,
`harness hooks --provider codex --observer --dry-run`, `maind.provider_deploy` on the
real self-host tree; `findings/04-runtime-preflight.md`).

## 1. What was broken (before this item, on `5e9436cf`)

`findings/04-runtime-preflight.md` (2026-07-24) named two live defects:

- `harness.codex.lifecycle.hooks: ownership-conflict → refuse (unmanaged-target)` — the
  self-host `.codex/hooks.json` carried one hand-written `SessionStart` entry (the maind
  memory-digest command) with no `.swissknifeman/provider-artifacts.lock.json` record, so
  the harness lifecycle CLI refused to touch it rather than risk overwriting the memory
  hook.
- `harness.codex.lifecycle.handler: missing → create` — the `context.observer` surface
  (declared `hook-native` for Codex in `lifecycle-context-bindings.json`) had never been
  materialized: no `.codex/hooks/lifecycle.py`, no registration.

Confirmed unchanged at the start of this item: `sha256(.codex/hooks.json)` on disk was
exactly `7d7538d021228e8e61d124f4b60b6db04434f8121de30b8672f05e4bf038c3db` — the identical
byte-for-byte content the pre-existing, already-tested maind `D104` bootstrap-transfer
fixtures (`packages/maind/tests/test_provider_deploy.py`, `_D104_PREIMAGE`) were built
against.

## 2. What already existed and only needed to be invoked

A prior (ECO-OPT) initiative had already built the full composition path, tested against
this exact preimage, but never applied it to the live self-host tree:

- `packages/harness/lib/harness/hooks.py`: `codex_d104_observer_fragment` (the P5-owned
  native observer registration + `render_codex_hook_handler()` bytes) and
  `validate_d104_codex_lifecycle_composition` (fail-closed shape check of the composed
  document).
- `packages/maind/lib/maind/provider_deploy.py`: `plan_d104_bootstrap_transfer` — reads the
  live `.codex/hooks.json` preimage, asks harness for the observer fragment, composes
  `{"hooks": {"SessionStart": [<preserved memory group>, <observer group>]}}`, validates it,
  and returns a `BootstrapTransferPlan` (two `ArtifactRenderRequest`s: `.codex/hooks.json`
  update, `.codex/hooks/lifecycle.py` create) admitted through `core.provider_lock`'s
  bootstrap-transfer seam (exact preimage hash pin, `.bak` before write, full rollback on
  any interruption — `packages/maind/tests/test_provider_deploy.py::test_d104_transfer_*`).

## 3. What this item did

Invoked the existing, tested library call directly against the live repo (no new
composition logic written):

```python
transfer = plan_d104_bootstrap_transfer(repo_root, harness_configs=repo_root / "packages/harness/configs")
apply_plan(repo_root, transfer.plan)
```

Result, verified byte-for-byte against the maind test's expectations:

- `.codex/hooks.json` — `SessionStart` now carries two groups: the original memory command
  (`bash .../.claude/maind-memory.sh`, byte-identical, first) and the new observer group
  (`matcher: "startup|resume|clear|compact"`, command invoking
  `.codex/hooks/lifecycle.py --surface context.observer`).
- `.codex/hooks/lifecycle.py` — created (`render_codex_hook_handler()` output): validates
  `--surface context.observer`, validates the required SessionStart payload keys, emits a
  read-only `systemMessage`, exits `2` on any malformed input or wrong surface.
- `.swissknifeman/provider-artifacts.lock.json` — created; owns both artifacts under
  adapter `maind.d104.bootstrap-transfer`.
- `.codex/hooks.json.provider-artifact.bootstrap-transfer.bak` — the exact preimage,
  written before the update (gitignored, `*.bak`; rollback path if a restart surfaces an
  unexpected regression).

Then addressed the two remaining named defects: `harness doctor`'s `run-report` staleness
(`~/.claude/hooks/run-report/_lib.py` behind the repo source — refreshed with
`harness hooks --global`, a global, non-git action) and a stale-path defect discovered
while running this item's own Validation (§4).

## 4. A stale-path defect found while running Validation (outside this item's Files)

Three of the four required `unittest` commands passed unmodified. The fourth,
`test_provider_instructions.py`, errored on all 14 cases with the same root cause:
`packages/harness/lib/harness/instructions.py:241` (`contract_path()`) still pointed at
`plans/2026.07.19-DUAL-PROVIDER/root/contracts/provider-instruction-contract.md` — a path
that stopped existing when commit `5b79f926` archived that plan to
`plans/archive/2026.07.19-DUAL-PROVIDER/...` (unrelated prior close, not caused by this
item). The same stale root also broke `test_instruction_compatibility.py` (3/6) and
`packages/harness/scripts/validate.sh` in its entirety, independent of the hook work here.

`instructions.py` is not in this item's `Files` (it belongs to the D86
instruction-projection subsystem, a different seam than the hook lifecycle this item
owns). Leaving `validate.sh` red for the whole package for an unrelated one-line stale
reference was judged worse than the boundary purity of not touching it — synced the path
(`instructions.py:241`, plus the one hardcoded test-only occurrence in
`test_provider_conformance.py:170`) to `plans/archive/2026.07.19-DUAL-PROVIDER/...` under
agent authority E (D50), recorded as a Files-boundary deviation (Known Deviations,
`phases/P0.md` P0.4).

## 5. A named, understood (not a defect) characteristic

`./packages/harness/bin/harness hooks --provider codex --observer --trusted --target . --dry-run`
reports `status: warning`, `stale-source → update` for both artifacts (exit `0`, not
refused). This is expected: the harness-standalone CLI plans its own
`ArtifactSource("harness.codex.lifecycle-bindings", ...)` provenance, while the lock
records `maind.d104.bootstrap-transfer`'s provenance (`hooks.py` + the `.codex/hooks.json`
preimage) — two different adapter identities own the same artifact IDs by design, because
the D104 composition exists specifically for the case where a pre-existing memory hook
must be preserved rather than re-derived from the plain harness catalog. The authoritative
check for this composed state is `maind.provider_deploy.plan_provider_artifacts` (run
directly against the live tree during this item): both `harness.codex.lifecycle.hooks` and
`harness.codex.lifecycle.handler` report `noop`/`clean`. Confirmed non-regressing this
item's own floor F5 (`hook_reference_resolution`).
