# Roadmap: terminal final continuity receipt

**Статус:** 🟡 Task receipt реализован планом `2026.08.12-№1-TASK-RESILIENCE`;
остаток — transport lifecycle heartbeat/quiet/interrupted-resume и фактический provider-final gate.
**Владельцы:** `packages/task`, Codex/Claude provider adapters и harness delivery seam.

## Симптом

Исполнитель несколько раз вывел `final` при незавершённом plan item. Для Codex это завершает
текущий ход: исчезает live commentary, следующие shell actions не продолжаются автоматически,
а владелец не может отличить длинный реальный прогон от преждевременной остановки. Повторный
пользовательский prompt нужен только для возобновления уже авторизованного work.

## Предпосылки и причина

1. `final` является transport-level terminal signal, но Task expected output описывает его как
текстовый формат, без machine-readable assertion о terminal plan state.
2. Provider не обязан публиковать heartbeat во время долгого tool execution; stdout появляется
после yield, поэтому молчание не несёт различимого статуса.
3. Существующий terminal-handoff receipt проверяет содержимое delivery после реального handoff,
но не запрещает `final` до terminal journal/status/closure.
4. Владелец одновременно просил «только финал» и видеть живой процесс; система не различает
«не присылай промежуточный результат» от «не показывай heartbeat».

## Решение

Ввести provider-neutral `terminal-final-continuity@v1`.

1. Task command перед разрешением `final` создаёт receipt: plan/item, run_id, terminal journal
pointer, terminal item state digest и (для phase work) closure digest. Отсутствие terminal state
даёт `FINAL_BEFORE_TERMINAL_FORBIDDEN` и удерживает dispatch активным.
2. Для tool execution дольше 30 секунд adapter публикует commentary heartbeat с run_id, текущей
операцией и elapsed time; это не результат и не меняет owner-visible plan state.
3. Owner preference разделяется на `progress=quiet|heartbeat|verbose`; даже `quiet` не разрешает
terminal final до receipt, а `heartbeat` публикует только liveness без лишней prose.
4. Codex и Claude projections получают одинаковое правило: `final` допустим только после
receipt; phase close требует terminal GREEN closure, а не только закрытый item.
5. Runtime tests моделируют tool yield, interrupted turn и resumed run: не должно требоваться
новое owner approval, когда journal фиксирует тот же active run.

## Приёмка

- early final для `In progress` item выдаёт `FINAL_BEFORE_TERMINAL_FORBIDDEN`;
- terminal item/phase produces byte-bound receipt; stale receipt fails;
- 31+ second fake tool execution emits one heartbeat per bounded interval;
- `quiet` suppresses prose details but preserves execution and terminal receipt;
- provider projection parity and Task validate are green.

## Первые точки изменения

- `packages/task/commands/plan-{exec,run,close}.md` и generated provider projections;
- `packages/task/lib/task/journal.py`, plan state/closure projections и command-render tests;
- harness/Codex terminal-delivery adapter, где доступен lifecycle tool call.

## Доказательства

- Agelto P5.6, 2026-08-11: multiple premature `final` responses while the item remained
  `In progress`; no Audit 3 was requested or created.
- Existing `2026.08.11-terminal-handoff-recommendation-receipt.md` covers correct next-step
  delivery after a real terminal handoff; this note covers the earlier liveness/termination seam.

## Реализовано 2026-08-12

`task.plan_delivery` и `scripts/plan-delivery.py` связывают terminal journal pointer/run_id,
item-state, closure, plan/handoff digests и commit SHA; nonterminal subject получает
`FINAL_BEFORE_TERMINAL_FORBIDDEN`, stale carrier — `STALE_TERMINAL_RECEIPT`. Команды
`plan-exec|run|close` и обе provider-проекции запрещают final без свежего receipt.

Subject correlation, запрет Next на уже terminal item и installed adapter version/command-digest
attestation также реализованы 2026-08-13. Открыты только пункты решения 2–3 и transport-часть 5:
Task не владеет lifecycle долгого tool call или фактическим transcript/final сигналом. Их надо
закрывать в следующей правке harness/Codex/Claude delivery seam; Task receipt уже является
входным контрактом.
