## 1. Зависимости и runtime-discovery

В допустимо:
```
{ "name": "planning", "version": "1.2.0", "dependencies": [ "shared-skills", {"name": "engine", "version": "^2.0"}, {"name": "audit", "marketplace": "other", "version": "~1.3.0"} ] }
```
Строка означает зависимость без ограничения версии; объект поддерживает name, marketplace, version. Диапазоны включают ^, ~, >=, точную версию. Для git-источников выбирается максимальный подходящий тег <plugin-name>--v<version>. Межмаркетплейсная автоматическая установка требует allowCrossMarketplaceDependenciesOn в корневом marketplace; исключение — зависимость уже установлена и включена на том же scope.
Optional/soft dependencies в опубликованной схеме не предусмотрены: dependencies означает обязательные включённые плагины. Не добавляйте выдуманный optionalDependencies или optional: true. Для подключаемых движков рекомендую отдельные адаптеры orchestration-engine-X, каждый с обязательными зависимостями, а ядро — без зависимости на все движки. Это архитектурная рекомендация, не встроенный механизм optional dependencies.
Для обнаружения используйте документированный :
```
claude plugin list --json
```
Проверяйте id, enabled, errors, version, scope, installPath: «установлен», «включён» и «успешно загружен» — разные состояния. Отдельный CLI-вызов не наследует автоматически session-only --plugin-dir; для реальной доступности движка добавьте собственный capability/health-check.
CLAUDE_PLUGIN_ROOT указывает на текущий плагин, не на реестр остальных. CLAUDE_PLUGIN_DATA — сохраняемый между обновлениями каталог ~/.claude/plugins/data/<id>/; наличие каталога не доказывает активность плагина. Не вычисляйте чужие cache paths: получайте путь через CLI либо задавайте endpoint/команду явно. В Bash tool эти переменные не экспортируются; в Markdown skills/commands подставляются ${...}. Hooks и stdio MCP получают ROOT/DATA в окружении.

## 2. Python CLI и конфигурация

прямо предусматривает bin/: при включённом плагине этот каталог добавляется в PATH Bash tool, но не глобально в терминал пользователя. Для claude.ai/Cowork top-level bin/ запрещён; там используйте scripts/ и явные пути в hooks/MCP.
Мой рекомендуемый layout:
```
.claude-plugin/plugin.json bin/planning-cli src/planning/ pyproject.toml uv.lock skills/ hooks/hooks.json config.example.toml
```
bin/planning-cli — executable wrapper, определяющий root по собственному расположению: нельзя предполагать, что Bash экспортировал ROOT/DATA. Python-окружение храните в ${CLAUDE_PLUGIN_DATA}/venv, не в обновляемом ROOT. Bootstrap делайте идемпотентным, с блокировкой и проверкой lockfile; возможны uv либо python -m venv, но установку Python/uv и зависимостей организует ваш wrapper/setup, не поле dependencies плагина. Документация прямо предназначает DATA для virtual environments.
Используйте для engine, endpoint, config-path; sensitive: true — для секретов. Несекретные значения сохраняются в pluginConfigs, секреты — в secure storage. Hooks получают CLAUDE_PLUGIN_OPTION_<KEY>; MCP может использовать ${user_config.KEY}. .example плюс gitignored локальный TOML — ваша convention, не автоматическая функция Claude Code; храните пользовательский файл вне cache ROOT.

## 3. Marketplace и независимые релизы

Один каталог может смешивать источники: .
git-subdir использует sparse/partial clone. Каждый плагин должен быть самостоятельным: не рассчитывайте на соседний Python-код вне выбранного подкаталога.
Практика релиза: независимый semver в каждом plugin.json; не дублируйте version в marketplace; повышайте его при изменении поставляемых файлов. Для воспроизводимости задавайте ref/sha; для constrained dependencies выпускайте теги planning--v1.2.0, например через claude plugin tag --push. Такая схема поддерживает независимые версии и внутри monorepo. CI: claude plugin validate … --strict.

## Проверка первоисточником (WebFetch 2026-10-07)

https://code.claude.com/docs/en/plugins/dependencies подтверждает: `dependencies` в plugin.json (строка или
{name, version, marketplace}); semver-диапазоны разрешаются по git-тегам `<plugin-name>--v<version>`
(`claude plugin tag --push`); необязательных зависимостей нет; плагин-набор (bundle) — плагин только с
`name` и `dependencies`; межмаркетплейсные зависимости — через `allowCrossMarketplaceDependenciesOn`.
Локально: Claude Code 2.1.292, `claude plugin tag|prune|list --json` присутствуют.
