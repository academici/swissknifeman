# P3 — Add provider adapters and fresh worker lifecycle

## Phase Context

P3 binds the deterministic P2 candidate to the installed Codex and Claude Code CLIs without moving
provider semantics into the scheduler. P3.1–P3.3 and the additive P1.6/P2.6 admission chain are
terminal; D80 returns P3.4 to implementation with an exact admission→native-tool projection, and
D81 gives its additive P3 manifest sole ownership of cross-generation P2→P3 integrity. Pure adapters map one frozen
`worker-envelope-v1` request into literal argv and untrusted provider records back into the same
closed result taxonomy. One shared bounded process runner owns timeout, byte/event caps, process
groups, redaction and fresh-attempt behavior. RAG:— (repo-grounded:
`research/09-p3-provider-adapter-design.md`; `research/20-p3.4-successor-contract-design.md`).

**Scope Included:** plan-local Codex/Claude adapter modules, parity cases/validator, provider
registry, bounded activity-port/CLI binding, fake-binary tests and minimized live smoke evidence.

**Scope Excluded:** package/root CLI or fleet rollout, provider fallback, session reuse, raw
streams/prompts/transcripts/secrets, unbounded/nested workers, P2 state-machine changes, P4 fault
certification, hook repair, production business slices and any acceptance based on docs alone.

> **Контракт фазы (contract-first).** Потребляет: reclosed P1 six-contract set + reclosed P2 dispatch-admission seam/candidate + terminal P0 provider matrix + terminal P3.1–P3.3 adapters/parity · Производит: one bounded fresh-worker activity binding and minimized smoke/aggregate evidence · Границы: plan-local prototype only; no authority/budget/grant synthesis, package/fleet rollout, session reuse, provider fallback or child-agent execution.
