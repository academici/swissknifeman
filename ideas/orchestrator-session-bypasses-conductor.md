# Идея: сессия «оркестратора» обходит `orch conduct` и вручную имитирует кондуктор

Статус: идея, не реализовано. Источник: сессия оркестрации PLAN3 (vaulter), P4.5–P5.3,
2026-10-16/17. Связано: `orchestrator-ignores-plan-batches.md`, `plan-must-not-prescribe-executor-workflow.md`.

## Что произошло

Владелец поручил «оркестрировать исполнение плана». В SKM для этого есть кондуктор: `orch conduct run --plan P --items … --batch`
ведёт пункт через context → scout → executor → checks → review → triage → correction → registrar → git, сам запускает роли
(headless claude-code / codex / grok) без запросов разрешения, пишет журнал и observer-отчёт, понимает `--debug`.

Сессия вместо этого ~20 пунктов подряд (P4.5–P5.3) исполняла цикл вручную:

- `plan.py next/start/context/finish/commit` вызывались самой сессией;
- код писал субагент, запущенный инструментом Agent (`general-purpose`) — не роль кондуктора;
- проверки, лог, ревью (`codex exec` со stdin), дозакоммит остатка делала сама сессия.

Владелец заметил это только на P4.17/P4.18 и P5.3: «все должно выполняться через оркестрацию, а ты только запускаешь»,
«если я говорю делать через оркестрацию, для запуска агента не надо спрашивать разрешение». Принцип: поручение
«через оркестрацию» — это поручение запустить кондуктор, а не разрешение/запрет на отдельные запуски агентов; ни выбор
способа запуска, ни запуск роли не требуют подтверждения владельца, и сессия не должна подменять кондуктор своим циклом.

## Почему так вышло

1. **Промпт оркестратора описывал ручной цикл** («`next` → `start` → `context` → субагент (Agent, general-purpose) →
   `finish` → `commit`»), а не команду `orch conduct run`. Сессия исполнила буквально написанное. Про `orch` в промпте и в
   `CLAUDE.md` проекта не было ни слова.
2. **Флаг `--debug` из того же промпта сессия искала у `planner`** (`plan.py … --debug` → unrecognized argument) и записала
   «невозможно». Он есть у `orch conduct run --debug`. Ошибочный вывод «у CLI нет такого флага» вошёл в отчёт.
3. **`plan.py next` печатает `run-items: planner:plan-run …`**, а не `orch conduct run …`. Подсказка ведёт на ручную
   команду плана (`plan-run`), а не на кондуктор. Сессия последовала подсказке и не искала дальше.
4. **Кондуктор не стартует «как есть» из сессии-оркестратора:**
   - `BRIDGE_PARTNER_UNAVAILABLE` (мост `planner-orch` не находит `PLANNER_ROOT`/`SKM_ORCH_ROOT`/`AICORE_ROOT`), хотя launcher
     запущен из проекта; помогло вручную экспортировать три переменные из соседнего чекаута swissknifeman;
   - `ITEM_OWNED`: пункты, начатые вручную `plan.py start`, принадлежат сессии; мост «никогда не забирает работу». Выход
     найден только чтением кода (`_owner_conflict`: владение проверяется, лишь когда обе стороны называют session —
     помог `start --take-over` без `--session`);
   - `ROUTE_UNDERSHOOT`: пункт с route `frontier`, а кондуктор допускает `claude-code/sonnet` только как `implementation`;
   - в проекте нет `.swissknifeman/stubs/` с правилами исполнителя (D41–D45 — режим прогонов — живут в плане).
   Каждый отказ по отдельности «объясним», но вместе они подталкивают оркестратора вернуться к ручному циклу.
5. **Две конкурирующие «оркестрации» без указателя, какая главная:** Agent tool (всегда доступен в сессии), `plan-run` и
   `orch conduct`. Нигде не написано, что для плана с батчами и ревью-чекпоинтами нужно именно третье.
6. **Накопленная инерция:** после резюме контекста остались «цикл на пункт» и таблица item-map; поменять способ посреди
   фазы казалось дороже, чем продолжать.

## Как исправить в SKM

1. **`plan.py next` называет кондуктор:** строка `conduct: orch conduct run --plan <P> --items <…> --batch [--debug]` рядом
   (или вместо) `run-items: planner:plan-run …`; если `orch` доступен — именно она основная.
2. **Шаблон/stub оркестратора** (`planner.run.orchestrator`) начинается с «запусти `orch conduct run`, наблюдай
   `status/observe`, реагируй на стопы по таблице agent-mode.md»; ручной цикл — только как явный fallback при недоступном
   кондукторе, с записью `log --type deviation`. Любой пользовательский промпт, дублирующий цикл, сверяется с этим stub.
3. **Окружение моста:** `launcher.py` (`orch …`, `planner …`) всегда выставляет `PLANNER_ROOT`, `SKM_ORCH_ROOT`, `AICORE_ROOT`
   (как для `plan.py`); `BRIDGE_PARTNER_UNAVAILABLE` должен называть, какую переменную и какой путь проверили.
4. **Переход от ручного старта к кондуктору:** `orch conduct run --adopt` (или `orch conduct adopt --items …`) сам
   выполняет `take-over` для пунктов, начатых тем же пользователем/проектом без session конкурирующего run;
   `ITEM_OWNED` подсказывает конкретную команду («`plan.py start … --take-over` без `--session`» или
   `orch conduct run --take-over`).
5. **Маршруты:** при `ROUTE_UNDERSHOOT` кондуктор печатает, какой `[orch.conductor]`-опцией/`--options` включить
   frontier-исполнителя (`orch route explain`), а не только отказывает.
6. **Агент без `orch`:** если сессия всё же запускает исполнителя инструментом Agent, `plan.py finish` в событии
   `executor` помечает `engine: manual-agent`; `plan.py stats` показывает долю пунктов, исполненных не кондуктором.
7. **`CLAUDE.md`-блок проекта** (генерируется `project init`): одна строка «Исполнение плана — `orch conduct`; `plan.py`
   вручную — только для authoring и ручного ремонта».

8. **Команда `/orch` (предложение владельца).** Явный вход «работаем через оркестрацию»: slash-команда/скилл
   `/orch <PLAN> [Pn.m …] [--debug]`, которая подключает инструкции оркестратора в сессию (как `/plan-run` подключает
   `plan-run.md`). Содержимое: `plan.py overlays` + stubs `planner.run.orchestrator`; окружение моста; запуск
   `orch conduct run … --batch [--adopt] [--debug]`; наблюдение (`status/observe/questions`); таблица действий после
   стопа из `docs/agent-mode.md`; запрет подменять кондуктор Agent-циклом; правила проекта (режим прогонов, ревью-чекпоинты)
   — из stubs. Без `/orch` сессия ведёт себя как обычный агент и не считается оркестратором. Реализация: команда в
   `packages/orch/commands/orch.md` (+ адаптеры claude/codex/cursor), `project init` подключает её в проект.

## Критерии приёмки

- `/orch <PLAN>` загружает инструкции оркестратора и запускает `orch conduct run` без ручного экспорта окружения и без
  вопросов владельцу о запуске ролей.

- `plan.py next` печатает готовую команду `orch conduct run … --batch`.
- `orch conduct run` из свежей сессии проекта стартует без ручного экспорта переменных окружения.
- Пункты, начатые вручную тем же проектом, принимаются кондуктором командой из текста ошибки.
- `plan.py stats` отличает пункты, исполненные кондуктором, от ручных.

## Что делаю в текущей сессии

- P5.3 и P5.4 запущены через `orch conduct run --batch --adopt --debug`; дальше — только через кондуктор.
- Для исполнителей ставлю frontier-маршрут по route пункта; ревью RC-P5-* — как требует кондуктор/план.
- Отклонение (P4.5–P5.2 вручную) и ошибка с `--debug` попадут в итоговый отчёт.

## Дополнения из практики перехода на кондуктор (2026-10-17)

- Без `--adopt` кондуктор считает «грязным» и `plans/**` (журнал и JSON пункта после ручного `plan.py start`): коммит
  плановых файлов нужен перед каждым запуском; с `--adopt` папка плана разрешена. Единое правило: папка плана и
  `artifacts/` не считаются изменениями вне write-set ни в одном режиме.
- Брошенные claim'ы прежних запусков держат `ITEM_OWNED` (владелец — session `run-…` остановленного запуска). Помогает
  `orch conduct release --run <тот запуск> --all`, но надо угадать, какой из запусков держит claim; `ITEM_OWNED` должен
  называть run id и готовую команду `release`.
- `orch conduct release --run <запуск без claim'ов> --all` падает трейсбеком `TypeError: expected str, bytes or
  os.PathLike object, not NoneType` (`_fork_exec`), а не сообщением «у запуска нет claim'ов».
- Маршрут исполнителя `frontier` не выбирается по умолчанию (в launch-catalog у executor только class `implementation`):
  `ROUTE_UNDERSHOOT` лечится `--options` со `stages[{role: executor, model_class: frontier}]`; кондуктор должен сам
  выбирать класс из `route` пункта (он уже его знает) или называть эту опцию в сообщении.
