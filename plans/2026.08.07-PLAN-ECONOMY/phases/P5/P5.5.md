### P5.5 — Доказать queue semantics исполняемым producer-based acceptance

**Intent:** После исправленного P5.4 заменить статическое доказательство исполняемым acceptance producer'ом: на свежих копиях тестового плана реально создать и применить policy auto-answer и owner `continue`/`park`/`reject`, проверить queue+journal+item/status projections, детерминированно собрать results/report и воспроизвести их из названного item tree с явным bootstrap. RAG:— (repo-grounded: Audit P5 finding 4; D144; `research/22-p5-audit-reopen-2026-08-09.md` §4).
**Why:** Прежний report читает заранее закоммиченный `queue.jsonl`, отсутствует на названном item commit, а exact Validation без `PYTHONPATH` падает; поэтому зелёные числа не доказывают producer path. P5.5 остаётся closing consumer исправленного P5.4: только он может показать, что contract enforcement, outcome semantics и state regeneration работают вместе, не меняя frozen P4/P5 contracts. RAG:— (repo-grounded: `phases/P5/P5.md` Audit finding 4; старый `artifacts/P5/acceptance-report.md`; D144).
**Scope Included:** `artifacts/P5/validate_acceptance.py` как deterministic stdlib producer/checker; machine results JSON и human report; fresh temp-copy runs для policy clarification auto-answer и owner authorization outcomes `apply`/`park`/`reject`; assertions на contract-valid queue events, verified provenance, continuation только при apply, blocked non-apply, subject-locality, regenerated state/status и отсутствие copied P4 owner packet; `--write`/`--check`; explicit repository bootstrap; detached-item-tree replay; обновление tests/docs/CHANGELOG.

**Implementation Rules:**
- Acceptance начинает каждый scenario с новой временной копии baseline fixture и вызывает реальные producers. Чтение заранее решённой committed queue допустимо только как вход regression fixture и никогда не удовлетворяет acceptance predicate. RAG:— (repo-grounded: Audit finding 4).
- Policy scenario вызывает `plan_authority.auto_answer_clarification()` и `plan_requests.append_auto_answer()` полной contract pair; проверяет `resolver=policy`, verified provenance, before/after/reclassification digests, semantic resolution и свежие views. Ручная запись auto-answer JSON запрещена. RAG:— (repo-grounded: frozen clarification contract; D144).
- Owner scenarios создают реальный return-loop request через P4→P5 adapter, claim и `resolve()` для отдельных свежих copies: `continue/apply` возобновляет exact root и ставит subject `in-progress`; `park` и `reject` не возвращают continuation и оставляют ровно target subject blocked; unrelated subject не меняется. RAG:— (repo-grounded: D144 outcome table).
- Results JSON содержит scenario ids, observed outcomes, queue/journal counts, subject statuses, continuation modes и frozen input digests; report строится только из results. Оба файла детерминированы, `--check` пересчитывает на fresh copies и сравнивает bytes. Wall-clock/temporary paths/random ids в output запрещены.
- Volatile `at` и temp paths проверяются на форму/связность, но не попадают в normalized results; producer-call assertions и pinned input digests не дают детерминизму превратиться в чтение статического fixture. RAG:— (repo-grounded: `research/22-…` pre-mortem).
- Первая строка report честно называет границу: synthetic Layout-v2 scenarios доказаны; P6 command integration/live fleet не доказаны. Метрики остаются раздельными, без вывода «весь протокол работает».
- Validator/bootstrap явный: `PYTHONPATH="$PWD:$PWD/packages/task/lib"`; cwd — repository root. Все acceptance artifacts входят в item commit P5.5 до bookkeeping. Detached replay использует этот hash и не читает последующий tree.
- Frozen contracts/config D143/P4 artifacts, P6, чужие планы и `packages/artifex` read-only. Несовпадение frozen форм — escalation, не fixture edit.
**Code Guidance:** Acceptance script — исполняемый oracle, а не генератор красивого текста. Каждый публичный claim report обязан происходить из assertion над событиями, journal и generated views того же fresh run. Никакого спец-кода «если fixture plan-v2-p5»: producer APIs получают обычный plan-dir. Анти-подгонка: старый статический queue можно удалить/оставить как regression input, но нельзя считать его прогоном; tests должны падать на старом P5.4 минимум по invalid auto-answer и non-apply resume. ЗАПРЕЩЕНО помечать item 🟢, пока (а) все четыре scenarios созданы producers, (б) report/results byte-identical на повторе, (в) `--check` зелёный в detached item tree, (г) artifacts перечислены diff-tree item-коммита, (д) exact full tests/validate зелёные, (е) frozen inputs не изменены. Обход через post-item bookkeeping report, рабочее дерево или ручную queue запрещён.
