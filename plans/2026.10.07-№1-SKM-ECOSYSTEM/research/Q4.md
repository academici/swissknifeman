# Q4

Запрос (perplexity-web-mcp stdio, default pool; search; 2026-10-07):

```text
October 2026. Splitting a Python + Markdown monorepo of developer tooling into several independently publishable packages that talk "through bridges" (adapters). Best practices with primary-source URLs:
1) Contract/interface package vs duplicated schemas vs consumer-driven contract tests (Pact-style) between separately versioned packages; how to avoid a "distributed monolith".
2) Optional integration pattern: package A works standalone, gains features if package B is installed (Python entry points / plugin discovery via importlib.metadata entry_points, pluggy, CLI subprocess + JSON contract). Pros/cons of in-process import vs subprocess CLI with versioned JSON for decoupling.
3) Migration strategy from monorepo to multi-repo: git filter-repo/subtree to keep history, order of extraction (leaf packages first), keeping a temporary integration repo/CI that tests the matrix of versions.
Answer in Russian, max 700 words.
```

Ответ (как вернул сервис):

Рекомендую сначала разделить зависимости и релизы внутри монорепозитория, затем переносить Git-историю. Главный критерий — независимость: пакет A должен работать без B и выпускаться без синхронного обновления всех адаптеров; отдельные репозитории сами этого не обеспечивают.

## 1. Контракты между пакетами

Ниже — архитектурная рекомендация; схемы, интерфейсы и контрактные тесты решают разные задачи.
Pact проверяет взаимодействия, используемые потребителями, а не просто соответствие общей схеме: consumer генерирует примеры, provider подтверждает их. Схема описывает допустимую структуру, но сама не доказывает совместимость поведения. , .
Для Python-вызовов и CLI рекомендую Pact-style тесты: fixtures запросов/ответов, исполнение реального адаптера, проверка ошибок и побочных эффектов. Не нужно искусственно добавлять HTTP ради Pact.
Чтобы избежать distributed monolith, установите:
- Однонаправленные зависимости; A знает порт, bridge знает A и B.
- Собственное владение данными; никаких импортов внутренних модулей соседнего пакета.
- Совместимость со старым потребителем при добавлении возможностей.
- Независимые версии пакета и протокола; breaking change — новый протокол либо переходное окно.
- Отсутствие требования «все обновляются одновременно».

## 2. Опциональные bridges

Предпочтительная структура: A, B, A-B-bridge. A объявляет порт, bridge публикует entry point, пользователь устанавливает интеграцию отдельно либо через extra.
```
[project.entry-points."a.bridges"] b = "a_b_bridge:Bridge"
```
```
from importlib.metadata import entry_points for ep in entry_points(group="a.bridges"): bridge_type = ep.load()
```
Entry points позволяют установленному пакету объявлять расширение без зависимости host-пакета на конкретный plugin. Discovery и .load() — отдельные операции. , .
Рекомендую загружать bridge только при использовании соответствующей функции, проверять api_major/capabilities, явно обрабатывать конфликт имён. Отсутствие B допустимо; сломанная установленная интеграция должна выдавать диагностируемую ошибку, не маскироваться как «не установлена».
Для subprocess рекомендую handshake версий/capabilities; stdout — только JSON/JSONL, stderr — логи; документированные exit codes, лимиты и таймауты. Это граница процесса, не security sandbox.
pluggy полезен, когда нужны несколько реализаций hooks и управление их выполнением, а не только поиск одной фабрики. Он поддерживает hookspec и загрузку через entry points. .

## 3. Порядок миграции

- Постройте граф зависимостей; устраните циклы. Выделяйте листья первыми, но стабильный API-контракт — до зависимых bridges.
- В монорепозитории создайте самостоятельные pyproject.toml, тесты и сборку каждого пакета. Проверяйте установленные wheels, не workspace-импорты; Markdown/resources включайте и проверяйте в артефакте.
- Переносите историю в свежем клоне:
```
git filter-repo --subdirectory-filter packages/tool_a
```
Для разнесённых исходников, тестов и Markdown используйте несколько --path и --path-rename. GitHub документирует извлечение подпапки; детали фильтрации — у автора .
Альтернатива для одной подпапки:
```
git subtree split --prefix=packages/tool_a --branch=tool-a-history
```
Оба подхода создают переписанную историю, а не сохраняют исходные SHA. subtree split сохраняет относящиеся к подпапке изменения в синтетической истории. .
- Оставьте временный integration repo: manifests/lockfiles, сценарии, без копий исходников. Матрица: A без B, минимально поддерживаемые версии, latest/latest, старый consumer/new provider, кандидат релиза.
- Используйте CI как доказательство совместимости конкретных версий, не как общий release train. Аналогичный принцип реализует : версионируемые контракты и результаты проверок.
