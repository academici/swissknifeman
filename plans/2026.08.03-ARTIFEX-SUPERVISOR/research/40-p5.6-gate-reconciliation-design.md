## 0. What the escalation actually was, and what it turned out to be

P5.6 stopped `🔴` on one question: `validate-shadow.py` carries a second stale guard the item's
«exactly four repairs» never enumerated, and two remediations looked equally plausible. Verifying
that question first-party (layer-1 finding §1) produced a third option that dominates both, and
verifying the *other* three repairs — which the escalation had not re-examined — surfaced two
further defects that would each have caused another stop:

| # | Defect | Found by | Resolution |
|--:|:--|:--|:--|
| A | stale `business carriers exist before exact owner grant` guard | the escalating session | D128 |
| B | wrong `--prototype` literal + undetermined frozen anchor for repair (2) | the escalating session | D129 |
| C | `validate-repository-pilot.py` can never exit 0 (0/3 accepted) — P5.6's and P5.4's acceptance both unreachable | **this pass** | D130 |
| D | Implementation Rule (5) forbids the correct P4 anchor `3533234c` (a legitimate P4.7 fix that also touched harness) | **this pass** | D131 |

C and D matter more than A: A stops the item with a clear diagnostic, while C and D would have let
an executor either grind against an unsatisfiable criterion or — worse — «reach green» by weakening
something, which is exactly the failure mode P5.6 exists to prevent.

## 1. Decision A (D128) — the stale shadow guard: two-sided, not either/or

The guard asserts a **one-time historical fact**: at the moment the shadow evidence was frozen, no
business carrier existed, so the trial catalog cannot have been shaped by knowledge of the
candidate. That fact is permanently true and permanently checkable — just not against the *live*
tree, where P5.1 has since legitimately minted the carriers under D105.

Two things follow, and they are not alternatives:

1. **In `validate()` the assertion belongs at the freeze snapshot.** Resolve the freeze commit at
   run time — all four frozen carriers have exactly one commit each and it is the same commit
   (layer-1 §1) — and assert through `git ls-tree` that no business carrier existed there. This is
   literally Implementation Rule (1)'s two-sided shape: *the frozen side is proven against the
   generation it was cut at*.
2. **In `--write` the guard is a refusal, and it must precede the write.** «You may not re-cut the
   shadow freeze once business carriers exist» is the live-tree half, it stays true forever, and it
   is the only action that could actually violate candidate-independence. Today the check sits
   *after* the write (`main()` calls `validate()` unconditionally, layer-1 §1), i.e. it fires only
   once the damage is on disk.

**Rejected — relax-in-place only** (the escalation's option 1 in isolation): leaves `--write` able
to overwrite the freeze on top of existing carriers, and leaves the post-write ordering bug intact.

**Rejected — retire the non-`--write` mode** (the escalation's option 2): the mode's other checks —
catalog / mapping / shadow / request byte-drift and the frozen G2 predecessor pin — are green,
live and load-bearing for every later gate. Retiring the mode to silence one stale line trades four
working invariants for one, and the comparison drawn with the read-only
`repository-pilot-results-v1.json` does not hold: that file is inert recorded evidence, this is an
active re-derivation of four frozen carriers.

The precedent the escalation cited (`findings/P5-retry-carrier-set.md` §3 — «extend the item only
when exactly one fix is possible») is satisfied, not bypassed: after verification exactly one
coherent fix remains, and it is neither of the two the escalation weighed.

## 2. Decision B (D129) — repair (2): the anchor is determined, and the live side must not vanish

Three separate things were wrong in one line, and only the first was noticed by the escalation.

1. **The call-site literal.** `--prototype` must resolve to `artifacts/P3/adapter-manifest-v1.json`
   (`validate-package-promotion.py:104`); the Validation line passed `artifacts/supervisor`, so
   every run died on an argument check *before* the gate it was supposed to exercise. Corrected in
   P5.6's Validation, matching P3.md's own line for the same script.
2. **The frozen anchor is not a choice.** The manifest has exactly one commit in its entire
   history, `367e477a` (layer-1 §2). `124df816` is P4.8's item commit and never touched it. So the
   anchor is resolved at run time — `git log -1 --format=%H -- <manifest>` — and no generation
   literal enters the validator or the call site (Implementation Rule (1), second sentence).
   `--historical-commit` stays as an explicit override for the historical replays that already use
   it.
3. **The live side would otherwise be asserted against nothing.** In the existing
   `--historical-commit` branch the validator skips the current-tree comparison entirely
   (`validate-package-promotion.py:79-91`). Passing the flag alone therefore *silences* F2 rather
   than repairing it. The repair must add the live half: the current package equals the sole G2B
   digest in `business-successor-generation-v1.json`, the same helper shape F1's draft already
   introduced in `validate-shadow.py`. Two-sided, exactly like A.

## 3. Decision C (D130) — separating «evidence is intact» from «evidence shows acceptance»

`validate-repository-pilot.py` answers two different questions with one exit code. Its first ~100
lines verify that the recorded pilot evidence is structurally intact, admission-bound, version-
pinned and generation-current; its last four lines report whether the measured slices were
accepted. P5.2 is closed `🟠` on `0/3 accepted` and its three D122 admissions are one-shot and
spent — that number is now immutable history. So the second answer is permanently «no», and any
consumer that reads the conflated exit code concludes «the evidence is broken», which is false.

**Resolution: split the exit codes** — `0` = evidence intact *and* 3/3 accepted; `2` = evidence
intact, honest partial/zero acceptance report; `1` = structural failure, staleness, mutated bytes.
Consumers gate on «not `1`» plus the printed report.

This is not the forbidden «soft Validation point». A soft point relaxes a threshold the spec itself
set; here the threshold is unchanged and nothing becomes optional — a second, previously
unexpressible verdict gets its own machine-readable value, and the failure classes that used to
return `1` still return `1`. The acceptance count remains fully visible: it is printed, and it is
the reason the code is `2` rather than `0`.

**Rejected — grep the output text** (`FAIL: not accepted:` present, `stale` absent): makes a
downstream gate depend on a prose string, which is the class of gate that greens on a blank.
**Rejected — leave it red under an owner exemption**: that is precisely the «four red gates
everyone knows are expected» state P5.6 was created to end (its own Why), and it would put the
exemption inside P5.4's pre-intent gate, the last place an exemption should live.

Consequence outside P5.6's own scope, handled in this pass rather than deferred: P5.4's pre-intent
gate sentence is reworded from «green» to the exit-code contract for this one validator. P5.6 must
not edit another item's acceptance (its Scope Excluded), so the edit is made here, by design
authority, and recorded as D130.

## 4. Decision D (D131) — what «P4-owned» means for the anchor

New anchor: `3533234c`, on which `git diff --exit-code -- phases/P4.md artifacts/P4` is empty, and
which the frozen P5.1 trial catalog independently pins as `source_tree_ref` (layer-1 §4) — two
independent derivations agreeing is stronger evidence than either alone.

Implementation Rule (5) as authored («each intervening commit … touch only P4 evidence paths»)
rejects this anchor: `3533234c` is `fix(harness): восстановить committed-tree validation P4`, which
repaired the P4 validators *and* the harness half of the same defect in one commit. That is normal
§6 `Files`-scoped hygiene, not a foreign capture. The rule confuses two questions — *is this
commit's change to P4 evidence legitimate and P4-owned* (the one that matters) versus *did the
commit touch anything else at all* (irrelevant to a path-scoped `git diff`).

Reformulated: for each intervening commit, the **P4-evidence portion** of its diff must be owned by
a P4 item or the P4 phase close, shown by reading the message and that portion of the diff; paths
outside `phases/P4.md`/`artifacts/P4` are recorded in the finding and do not by themselves stop the
item. What still stops it: a P4-evidence change that no P4 item or phase close accounts for.

And a boundary the anchor move must respect: `124df816` also names the **owning snapshot of the
historical P4.8 leaf validator** (P5.1's Scope/Rules/Validation, D106). Those occurrences must not
move — a historical validator runs at its own commit by design. Only the
`git diff --exit-code … -- phases/P4.md artifacts/P4` form is retargeted, in the two P5.5 Validation
occurrences (layer-1 §5); the two prose mentions are forwarded-debt notes and are updated for
truthfulness, not as acceptance commands.

## 5. Why the item stays one item

All four repairs share one cause (a pinned generation versus a tree that legitimately advanced),
one pattern (two-sided: frozen side against its own snapshot, live side against the current
generation, resolved at run time), one prohibition (no recorded byte moves) and one consumer
(P5.4's pre-intent gate). Splitting them would multiply sessions without reducing coupling — each
repair would still have to re-establish the same context. The item's cost grows by the guard
repair, the exit-code split and the ledger, and it remains `implementation/high · manual · full`
review: the design is now settled, but the artifacts guard evidence integrity.

## 6. What this pass deliberately did not touch

F3 (the aggregate contract manifest not knowing the additive seventh contract) stays P5.7's, whose
real fix is `contract-manifest-v2.json`, not a P5.6-style relaxation. No package byte, no recorded
evidence byte, no admission, no provider process. The uncommitted F1 draft in the working tree is
kept, not reverted: it is verified-correct in-scope progress, and P5.6's next attempt builds on it.
