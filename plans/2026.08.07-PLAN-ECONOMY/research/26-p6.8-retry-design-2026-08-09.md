а существующие строки v1.0.0 не редактируются. Это даёт P6.9 один стабильный путь и сохраняет
различимость attempts по version/commit/raw path.

## 2. Детерминированный порядок attempt v1.1.0

1. До измерения проверить frozen identity v1.1.0 и совпадение current contract hashes с
   preflight §1; v1.0 prior result и raw bytes должны оставаться доступными.
2. Исполнить manifest `measurement.command` на migrated arm A и сохранить stdout в versioned raw
   JSON. Применить reducer дословно: ready failure → `fail`; иначе pending producer → `deferred`;
   иначе all ready green → `pass`. Historical maximum/gaps печатаются evidence-only и не входят в
   hard verdict. Любой `fail`/`deferred` останавливает attempt и сохраняет P6.8 non-green.
3. Только после arm-A `pass` создать реальный layout-v2 `PLAN-MIGRATION` текущей
   `task:plan-design new` командой. Если команда выдаёт v1 или не создаёт digest-qualified v2
   carriers, это field defect authoring path, а не разрешение править экземпляр руками.
4. Исполнить тот же measurement command на arm B; не смешивать ни значения, ни claims рук.
5. Только после arm-B `pass` исполнить manifest-declared session canary по exact четырём ветвям и
   прогнать machine comparator. Reviewer provenance и hard-boundary reason проверяются поле-в-поле.
6. Дописать append-only раздел отчёта: первая строка — граница доказанного; затем отдельные таблицы
   arm A, arm B, canary, anti-displacement answer, confounds, raw paths/hashes и итоговый enum.
7. P6.8 становится green только при `pass/pass` и exact canary; иначе status/Pending Work честно
   фиксируют первый красный/отложенный предикат, P6.9 не запускается.

## 3. Связь с P6.9

P6.9 читает тот же append-only отчёт, но его предусловие — не существование файла, а наличие
финального раздела `Attempt v1.1.0` с exact положительным verdict. Producer edge остаётся P6.8.
Чтобы P6.9 сам не нарушил read budget, bundle input большого donor `plan.md` заменяется тремя
уже существующими content-preserving slices; write target донора и validation не меняются.

## 4. Анти-scope

Не меняются threshold, qualified unit, scope traversal, admission states, arms, canary branches,
`plan_weight`, frozen contract carriers, historical item specs и старый RED. Не ремонтируются
hook provenance, provider projections или authoring command в P6.8. Если fresh authoring path не
может произвести требуемый layout v2, attempt останавливается с новым exact finding у owning P6.5,
без ручной достройки arm B.

## 5. Новый precondition после проверки production tool

Порядок §2 является условным и не запускается на текущем v1.1.0. Диагностика preflight §5
доказала, что manifest-declared `plan-weight.py` продолжает измерять legacy v1 read path, хотя
frozen scope требует exact v2 five-slot traversal. Поэтому не существует честного способа
«просто выполнить» frozen command: её green не доказывает заявленный scope.

Минимальный repair path требует владельческого решения, потому что одновременно открывает ранее
закрытые P2.10/P6.7 и переиздаёт frozen acceptance identity. Рекомендуемый вариант:

1. reopen P2.10 как owning implementation item;
2. перевести `plan_weight` layout-v2 branch на registry-driven five-slot traversal, включая
   bundle selection и byte-fresh item state, сохранив v1 branch отдельно;
3. добавить regression tests на отсутствие `handoff` и exact пять slots для v2;
4. reopen P6.7, выпустить successor patch acceptance contract/manifest с pinned repair evidence и
   сохранить v1.0.0/v1.1.0 как prior results;
5. только затем redetail/resume P6.8 на новом frozen identity.

Альтернатива — не менять frozen контур и терминально оставить P6.8 blocked/P6.9 unexecuted.
Выбор между этими вариантами не является constructive design внутри P6.8 и материализуется как
`DecisionRequest`; до owner response handoff не должен запускать `task:plan-run P6.8`.
