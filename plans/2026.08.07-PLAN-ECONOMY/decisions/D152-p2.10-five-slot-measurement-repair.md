## Решение

По явному ответу владельца «продолжай здесь до конца» выбран вариант
`repair-and-refreeze` из DecisionRequest `P6.8-measurement-scope-repair-2026-08-09`.
P2.10 реопенится как owning implementation item и исправляет только layout-v2 ветвь
`plan_weight`: она измеряет пять executor slots замороженного `read-path` v1
(`plan-core`, `phase-context`, `item-spec`, `item-input-bundle`, `item-state`), исключает
`handoff`, проверяет свежесть bundle/state и считает digest-qualified bundle selections.
Layout-v1 ветвь остаётся совместимой с прежним путём. После доказательства repair P6.7
реопенится для successor patch frozen acceptance identity, и лишь затем P6.8 повторяет
приёмку. RAG:— (owner/repo-grounded: `brief/01-refinements.md`; owner response artifact;
`findings/P6.8-retry-preflight-2026-08-09.md` §5).

## Почему

Frozen acceptance v1.1.0 заявляет five-slot layout-v2 scope, но вызывает реализацию,
которая читает legacy `plan → handoff → phase → Required Reads`. Зелёный результат такой
команды был бы ложной уликой. Терминальная остановка была второй допустимой ветвью, однако
владелец явно потребовал продолжить работу до конца, поэтому выбран минимальный repair в
владельце дефекта с последующей перезаморозкой identity.

## Consequences

Разрешено forward-only открыть P2.10 и P6.7, изменить
`packages/task/lib/task/plan_weight.py` с regression tests и выпустить successor patch
acceptance contract до нового P6.8. Не разрешено менять threshold `100000`, qualified unit,
пять slots, arms, reducer states, session canary либо переписывать результаты v1.0.0/v1.1.0.
Если общий production path после repair даёт fail/deferred, P6.8 фиксирует этот фактический
вердикт; подгонка scope или чисел запрещена.
