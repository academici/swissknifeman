# SKM-PLAN-BUNDLE-ADMISSION-GAP — 2026-09-16

**Status:** source remediation implemented and delivered to this repository runtime; field
consumer acceptance remains

**Original scope:** diagnostic only. The implementation outcome is recorded in the audit task
linked from the live roadmap. P5.1 was subsequently resumed as a separate execution record, which
normalized its own carrier and generated its own bundle/state.

## Incident

The owner invoked:

```text
$ task:plan-exec 2026.09.15-№1-COREX-FLEXCRM-REMAINING P5.1
```

The Codex executor confirmed its route (`implementation/high`) but could not capture the mandatory
five-carrier context: `bundles/P5.1.json` was missing. Its first result was therefore
`PLAN_CONTEXT_TRUNCATED`.

That message is technically true but operationally misleading. P5.1 is not an out-of-order request:
`task.plan_recovery.validate_request()` returns `START_ITEM`, and `plan_weight.measure_plan()` reports
`admission_state=ready`, `admission_pass=true`, `d2a_pass=true`, and `d2b_pass=true` for P5.1.

## Reproduced cause

Rendering the missing carrier without writing it fails deterministically:

```bash
python3 packages/task/scripts/plan-views.py bundle \
  --plan-dir plans/2026.09.15-№1-COREX-FLEXCRM-REMAINING \
  --item P5.1 --stdout
```

Result:

```text
unresolvable_entry: future outputs are contracts during design, not missing mandatory design inputs or fabricated GREEN. Actual immutable independently owned source+permission G-DEPENDENCY. Missing exact engine receipt gates only engine subset
```

`P5.1.md` puts both source paths and explanatory policy prose in one semicolon-separated `Inputs` field.
`task.plan_bundle._raw_entries()` splits that field into entries, while
`task.plan_bundle.model()` requires every resulting entry to resolve to a repository source or a
decision. The prose entry has neither, so the bundle cannot exist. The same pattern makes the
currently admission-passing P5.2, P5.3, and P5.5 bundles unrenderable as well.

This is a plan-contract defect, not a missing external engine receipt and not a Codex route failure.
The earlier conclusion that P4.7 was a prerequisite of P5.1 was wrong: P4.7 is the in-progress
phase's stale generated-carrier issue, but it does not reject the direct P5.1 request.

## Why design-time validation did not stop it

The Task bundle gate deliberately renders only ready items of **active phases**. P4 is the only
active phase; P5 is `⬜ Not started`. Consequently, `plan-lint` does not dry-render P5.1 even though
the plan's own admission model declares it ready and directly executable. The plan can therefore
be reported as detailed while a legitimate direct execution request cannot materialize its required
bundle.

The local diagnostic tools do not show a broken Task installation:

- `skiller status` reports the marketplace registry at `HEAD 17f31648` with the `task` plugin enabled.
- `maind doctor` passes all checks. Its skill-drift and duplicate-channel warnings concern the local
  `ecosystem-mcp`/`ecosystem-setup` copies, not Task bundle generation.

There are separate baseline errors around P4.7/P4.8 (stale P4.7 state and bundle; P4.8 read-budget
and state errors). They should be repaired, but they are not the cause of P5.1's bundle-rendering
failure.

## Required repair

These are follow-up recommendations, not work performed by this diagnostic or by the P5.1
qualification run.

1. **Repair the plan specs before execution.** `Inputs` must contain only individually resolvable,
   portable source/decision declarations. Move the policy sentences from P5.1/P5.2/P5.3/P5.5 to
   `Implementation Rules` (or another narrative field) and quote source paths consistently.
2. **Add a Task design/lint regression gate.** For every non-terminal item with
   `admission_state=ready` and `admission_pass=true`, dry-render `plan_bundle.model()` during plan
   design/finalization. The check must not require persistent bundles for blocked future items.
3. **Improve executor preflight.** A requested ready item with an absent/unrenderable bundle should
   return a specific recovery diagnosis (item, failed `Inputs` entry, and exact `plan-views bundle`
   command), rather than surfacing only the generic snapshot code `PLAN_CONTEXT_TRUNCATED`.
4. **Add tests.** Cover mixed path-plus-prose `Inputs`, a ready item in a non-active phase, and the
   resulting executor diagnostic. The regression must prove that the design-time gate catches the
   defect before any `$ task:plan-exec` attempt.

## Acceptance for closure

- P5.1/P5.2/P5.3/P5.5 render their bundles deterministically without fabricated future evidence.
- The plan's ready direct-execution subset passes the new dry-render gate.
- A missing ready bundle yields an actionable typed diagnostic.
- Existing P4.7/P4.8 baseline diagnostics are reconciled independently and no longer obscure this
  failure mode.

### Scope и граница этого документа

Это отчёт о воспроизведённых дефектах SwissKnifeMan. Он не является исправлением

### Наблюдение A: `maind analyze` использовал чужое доказательство

Вызов из CoreX:

```bash
maind analyze --cwd --json --no-health
```

вернул `RED` для `project=corex`, однако вложенный primary `run_report` был
старым отчётом Edify: `generated_at=2026-08-07…`, команды ссылались на
`~/projects/edufy`, а `files_changed` содержал абсолютные пути
`/home/vostrikov/projects/edufy/...`. Такой отчёт содержал упавшие тесты и
workflows, поэтому они ошибочно стали красным verdict для CoreX.

Факт, что файл лежал под `<corex>/.claude/runs/`, оказался единственной
проверкой происхождения. Поле `cwd` не спасает: в воспроизведённом отчёте оно
указывало CoreX, в то время как command/file evidence доказывали иной проект.

**Последствие.** Любой финал или остановка, опирающиеся на этот verdict, не
доказаны. Правильный результат для такого случая — не GREEN и не RED, а
`ATTENTION`/`untrusted-run-report` с машиночитаемым кодом
`RUN_REPORT_PROJECT_MISMATCH`; чужие `tests/workflows/tool_failures` должны
быть исключены из расчёта verdict.

### Наблюдение B: порядок preflight превращает производный carrier в блок

`task.plan_recovery.validate_request()` допускает P5.1 как `START_ITEM`, а
измеритель сообщает `admission_state=ready`. Но `plan_recovery.start()` и
`plan-session prepare` сначала захватывают пять carriers через
`plan_context.capture()`, где bundle обязателен, и только потом делают
`plan_bundle.build(..., check=True)`. Отсутствующий `bundles/P5.1.json` поэтому
даёт общий `PLAN_CONTEXT_TRUNCATED` раньше, чем оператор получает причину или
может восстановить детерминированный вид.

Это не authority/safety boundary: bundle является детерминированной проекцией
item-spec + источников. Для существующего и разрешённого item его отсутствие
должно автоматически запускать идемпотентный materialize, затем повторный
snapshot. Только неразрешимый declaration остаётся локальной задачей текущего
attempt и должен сопровождаться exact entry/path, а не ложным финалом.

### Наблюдение C: `Inputs` смешивает носители и объяснительную прозу

`plan_bundle._raw_entries()` делит `Inputs` по `;`, а `plan_bundle.model()`
требует, чтобы каждая часть разрешалась в файл или decision. В P5.1 исходная
строка после валидных путей содержала policy prose («future outputs are
contracts…»). Рендер возвращал `unresolvable_entry` для этого текста.

Это authoring/normalization defect, не отсутствие будущего producer output и не
доказательство external block. Автоматическая лестница должна:

1. Отделить markup/formatting и generated-carrier drift, которые исправляются
   без остановки.
2. Для смешанного поля показать precise entry и перенести prose в narrative
   field в текущем plan-owned attempt, сохранив source declarations.
3. Запрашивать владельца лишь если исправление реально меняет scope, frozen
   contract, безопасность, необратимое действие или внешние полномочия.

### Наблюдение D: journal и owner views не имеют обязательной сверки

`journal.jsonl` уже содержал terminal rows для P4.7/P4.8/P5.1, но `status.md`
и отдельные item-state carriers оставались на старой позиции. `plan_status`
и `plan_item_state` корректно могут пересобрать эти projections, однако
terminal flow не делает их единым обязательным postcondition до derivation
Next/final. В результате агент может честно увидеть terminal evidence и всё же
сообщить статус, противоречащий owner view.

Generated carriers не являются предметом ручного решения. Перед terminal
delivery нужна идемпотентная reconciliation transaction:

```text
terminal journal evidence
  -> item-state(s)
  -> status + decision views
  -> next-ready bundle
  -> freshness/check + terminal receipt
  -> final
```

Если любой шаг выше восстанавливается из тех же immutable inputs, он продолжает
attempt. Финал запрещён до его завершения; это не повод передавать мелкую
починку владельцу.

### Required policy order

В источнике команды и в reducer-API должен быть один короткий порядок, который
не перекрывается низкоуровневыми правилами:

1. **Deliver outcome:** продолжать owner-authorized scope до acceptance.
2. **Repair locally:** автоматически исправлять deterministic, reversible,
   plan-owned и in-scope drift; проверять результат.
3. **Reconcile truth:** journal, state, status, bundle и receipt обязаны
   согласоваться перед Next/final.
4. **Escalate narrowly:** остановка допустима только после воспроизведения
   safety/authority/irreversible/external/product-decision boundary.
5. **Never overclaim:** stale, cross-project или incomplete evidence понижает
   confidence и требует повторного прохода, но не создаёт RED/terminal сам по
   себе.

Существующие механизмы `plan_repair`, `plan_blocking` и `review_policy` уже
выражают часть continue-first логики. Проблема — в раннем carrier capture,
отсутствии provenance validation и отсутствии одного enforceable
post-terminal reconciliation, а не в необходимости добавить ещё один жёсткий
plan gate.

### Non-goals и guardrails для будущего исправления SKM

- Не dry-renderить все далёкие «ready» items как обязательные persistent
  bundles: в текущих plans этот статус может описывать будущую возможность, а
  не немедленный запуск. Это создаёт массовые ложные блоки.
- Не скрывать malformed declaration: вернуть typed local-repair diagnosis с
  entry/path и продолжить его repair в том же attempt.
- Не считать грязное дерево или baseline другой задачи основанием для RED.
- Не менять schema/authority/frozen contracts под видом carrier repair.

## Execution incident: batch scope was incorrectly narrowed

The owner-authorized execution request named `P5.2 P5.3`. The executor
completed and reported P5.2 as though it were the terminal requested scope,
instead of deriving the next member of the admitted batch and continuing with
P5.3. This was an execution error, not a plan defect and not a boundary:
P5.3 is the adjacent consumer in the same owner-authorized batch.

The command policy must treat an explicit admitted item list/range as a work
set. A GREEN member triggers carrier reconciliation and then immediate
continuation to its compatible ready batch successor; it does not trigger a
chat final. The only exits are acceptance of the whole requested batch or a
reproduced safety, authority, irreversible, external, or product-decision
boundary affecting the remaining member. P5.3 must therefore be executed
before any completion statement for this batch.

## Addendum: circular recommended-batch admission

While resuming the exact `P5.2 P5.3` work set, the direct
`task_contract.admit_batch()` path returned `BATCH_STALE` for the first member
because it required P5.2 terminal evidence before it would admit the batch
whose purpose was to start P5.2. The immutable routing compiler itself already
identified `B-P5-WAKEUP` with ordered membership `[P5.2, P5.3]`; constructing
the empty-prefix receipt from that routing record made the legitimate start
possible.

This is a second execution-policy defect: a recommended batch must admit its
first ready member with an empty completed prefix, then require each durable
terminal row before admitting the successor. It must not turn the missing
terminal evidence it is about to create into a false stale/boundary condition.
No Task source was changed here; the observation is recorded for the same
future SKM remediation and regression matrix.

## Addendum: self-invalidating evidence anchors

P5.3 also reproduced a plan-carrier conflict: its generated receipt appeared
in `Files`, and `packages/tenancy/composer.json` appeared in both `Files` and
`Required Reads`. The Task evidence graph therefore returned
`SELF_INVALIDATING_EVIDENCE_ANCHOR` at pre-final even though all implementation
checks were green. Both are deterministic plan-owned normalization errors:
the receipt is a deliverable, not a product input, and a product file must not
also serve as its own immutable digest input. Removing those duplicate roles,
regenerating the bundle, and repeating pre-final produced `allow`.

This should be covered by the same continue-first policy: report the exact
collision, normalize the carrier within the current scope, regenerate derived
views, and continue. It is not a reason to claim a technical boundary or end a
requested batch early.
