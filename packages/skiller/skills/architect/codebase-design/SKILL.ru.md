# Codebase Design

Проектируйте **глубокие модули** (deep modules): много поведения за маленьким интерфейсом, размещённым на чистом seam, тестируемым через этот интерфейс. Используйте этот язык и эти принципы везде, где код проектируется или перестраивается. Цель — рычаг (leverage) для вызывающих, локальность (locality) для сопровождающих и тестируемость для всех.

## Словарь

Используйте эти термины в точности — не подменяйте их словами «компонент» (component), «сервис» (service), «API» или «граница» (boundary). Согласованный язык — это и есть весь смысл.

**Module** (модуль) — что угодно, имеющее интерфейс и реализацию. Намеренно не привязан к масштабу: функция, класс, пакет или срез, пересекающий несколько слоёв. _Избегайте_: unit, component, service.

**Interface** (интерфейс) — всё, что вызывающий должен знать, чтобы корректно использовать модуль: сигнатура типа, но также инварианты, ограничения порядка, режимы ошибок, требуемая конфигурация и характеристики производительности. _Избегайте_: API, signature (слишком узко — они относятся только к поверхности на уровне типов).

**Implementation** (реализация) — то, что находится внутри модуля, его тело кода. Отличается от **Adapter** (адаптера): нечто может быть маленьким адаптером с большой реализацией (Postgres-репозиторий) или большим адаптером с маленькой реализацией (in-memory-фейк). Прибегайте к слову «адаптер», когда речь о seam; «реализация» — в остальных случаях.

**Depth** (глубина) — рычаг на интерфейсе: объём поведения, который вызывающий (или тест) может задействовать на единицу интерфейса, который ему приходится изучить. Модуль **глубокий** (deep), когда большой объём поведения сидит за маленьким интерфейсом, и **мелкий** (shallow), когда интерфейс почти так же сложен, как реализация.

**Seam** _(Michael Feathers)_ — место, где можно изменить поведение, не редактируя в этом месте; *локация*, в которой живёт интерфейс модуля. Куда поместить seam — это отдельное проектное решение, отличное от того, что находится за ним. _Избегайте_: boundary (перегружено понятием bounded context из DDD).

**Adapter** (адаптер) — конкретная вещь, удовлетворяющая интерфейсу на seam. Описывает *роль* (какой слот он заполняет), а не существо (что внутри).

**Leverage** (рычаг) — то, что вызывающие получают от глубины: больше возможностей на единицу интерфейса, который они изучают. Одна реализация окупается на N местах вызова и M тестах.

**Locality** (локальность) — то, что сопровождающие получают от глубины: изменения, баги, знание и проверка концентрируются в одном месте, а не расползаются по вызывающим. Исправил один раз — исправлено везде.

## Глубокий против мелкого

**Глубокий модуль** (deep module) = маленький интерфейс + много реализации:

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**Мелкий модуль** (shallow module) = большой интерфейс + мало реализации (избегайте):

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

Проектируя интерфейс, спросите:

- Могу ли я сократить число методов?
- Могу ли я упростить параметры?
- Могу ли я спрятать больше сложности внутри?

## Принципы

- **Глубина — свойство интерфейса, а не реализации.** Глубокий модуль может быть внутри собран из маленьких, мокируемых, заменяемых частей — они просто не являются частью интерфейса. У модуля могут быть **внутренние seam'ы** (приватные для его реализации, используемые его собственными тестами), а также **внешний seam** на его интерфейсе.
- **Тест на удаление (deletion test).** Представьте, что вы удаляете модуль. Если сложность исчезает — он был сквозным прокидыванием (pass-through). Если сложность вновь появляется по N вызывающим — он отрабатывал своё содержание.
- **Интерфейс — это тестовая поверхность.** Вызывающие и тесты пересекают один и тот же seam. Если вам хочется тестировать *за пределами* интерфейса — вероятно, модуль имеет неправильную форму.
- **Один адаптер означает гипотетический seam. Два адаптера означают реальный.** Не вводите seam, пока через него что-то реально не варьируется.

## Проектирование под тестируемость

Хорошие интерфейсы делают тестирование естественным:

1. **Принимайте зависимости, не создавайте их.**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

   > PHP-эквивалент: `class OrderProcessor { public function __construct(private PaymentGatewayInterface $gateway) {} }`.
   > Dart: `class FiscalService { FiscalService(this._driver); final FiscalDriverInterface _driver; }`.

2. **Возвращайте результаты, не производите побочные эффекты.**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **Малая площадь поверхности.** Меньше методов = меньше нужных тестов. Меньше параметров = проще настройка теста.

## Связи

- **Module** имеет ровно один **Interface** (поверхность, которую он предъявляет вызывающим и тестам).
- **Depth** — свойство **Module**, измеряемое относительно его **Interface**.
- **Seam** — это место, где живёт **Interface** модуля **Module**.
- **Adapter** сидит на **Seam** и удовлетворяет **Interface**.
- **Depth** производит **Leverage** для вызывающих и **Locality** для сопровождающих.

## Отвергнутые трактовки

- **Глубина как отношение строк реализации к строкам интерфейса** (Ousterhout): поощряет раздувание реализации. Мы вместо этого используем глубину-как-рычаг (depth-as-leverage).
- **«Интерфейс» как ключевое слово `interface` в TypeScript или публичные методы класса**: слишком узко — интерфейс здесь включает каждый факт, который вызывающий должен знать.
- **«Boundary» (граница)**: перегружено понятием bounded context из DDD. Говорите **seam** или **interface**.
