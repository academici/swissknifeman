# Ревью механизма оркестрации после P11 (Opus 5.5): решения и сделанное

Разбор прогона фазы P11 по журналам `docs/orch-p11-observer-journal.md` и `docs/orch-p11-run-findings.md` (записи #N, таблица
I1–I15). Здесь — что решено, что сделано в коде и инструкциях и что подтверждается только экспериментом
(`docs/orch-p12-prep-prompt.md`). Наблюдение за фазой P12 — `docs/orch-p12-observer-prompt.md`.

## Главные выводы

1. Время фазы определяла верификация, а не исполнение: тяжёлые проверки стояли в приёмке каждого пункта и повторялись
   целиком в каждом круге правок. Лечение — каденс проверок (быстро на пункт, полно один раз при закрытии фазы),
   параллельные и кэшируемые тесты модулей.
2. Половина остановок — форма, а не суть: отчёт роли не проходил схему, и роль повторялась целиком (10–30 мин). Лечение —
   три ступени: правило, ремонт дешёвой моделью, повтор.
3. Четыре остановки на коммите (#13, #20, #29, #45) — из-за того, что изменённые пути брались из отчёта последнего раунда.
   Лечение — истина из git после каждого раунда и явная политика путей вне write set.
4. Лимиты рубили полезную работу (#16, #11). Решение владельца: лимиты — база и маяки, не обрыв.

## Решения (принятые по указанию владельца)

| Тема | Решение |
| --- | --- |
| Лимиты времени и токенов | Ничего не обрывается. Маяки `STAGE_SLOW` (2700 с), `STAGE_IDLE` (600 с тишины), `CHECK_SLOW` (900 с), `BUDGET_OVER` говорят, что выполняется сейчас (последняя команда роли и процессы её сессии). Потолки `*_timeout_s` остались опциями, по умолчанию выключены (и в схеме конфига `[orch.conductor.limits]`). |
| Лимиты раундов | `review_rounds`, `corrections`, `check_fixes` — цели. Сверх цели раунд идёт, пока последняя правка дала прогресс (сменился набор красных проверок или стало меньше падений; меньше или другие находки), до `ceiling_factor` × цель (2). Каждый такой раунд — `LIMIT_OVER` и заметка плана. Правка без прогресса — честная остановка. |
| Отчёты ролей | `heal.py` чинит форму по правилу (статус не повышается, ничего не выдумывается, каждое исправление названо); затем роль `report-fixer` (economy: haiku / luna / grok, `limits.repairs`, по умолчанию 1) переписывает только блок результата из ответа роли; полный повтор — последним. Ошибка `oneOf` называет поле и значение ближайшей ветки. |
| Пути вне write set | `scope.outside: deviation` (по умолчанию): пути показываются ревьюеру, записываются как отклонение и коммитятся с пунктом; `block` — остановка сразу после исполнителя. Для ИИ-прогона выбран `deviation`: работа не теряется, а решение видно в ревью и в плане. |
| Изоляция ролей | `--safe-mode` по умолчанию (флаг проверяется по `--help` CLI; без него — только переменные окружения и маяк `ISOLATION_PARTIAL`). Нужные правила модуля приходят блоком «Repository rules» (`instructions.module_rules`: секции `module-folders`, `module-boundaries`, `engineering-invariants` из CLAUDE.md/AGENTS.md корня и папок write set); скиллы изолированной роли вставляются текстом. |
| Пробы провайдеров | Платных проб нет. Дирижёр проверяет запуск всех обязательных ролей до работы пункта; `run --dry-run` показывает `available` и флаги изоляции. |
| analyst | Инструмент вне проверок ядра, как maind (`standalone.tools`). |
| Полный прогон | `phase.validation` — полный проход фазы. Мост отдаёт его пункту, закрывающему фазу (`cadence: phase`), а `plan.py finish` не закрывает фазу без результатов этих проверок. Отдельная команда не нужна. |
| Продолжение сессии роли | Не делается: ремонт отчёта решает ту же задачу дешевле и не зависит от провайдера; правки после мер идут 1–3 мин. |
| Параллельные пункты в worktree | Отложено: критический путь — проверки, они упираются в CPU. Вернуться после замеров P12 с новым каденсом. |

## Сделано (код)

- **orch**: маяки и «что выполняется» (`process.activity`), токены отменённой роли (`partial_usage`), метки времени
  потока (`<stream>.times`); лимиты по прогрессу (`_allowance`); `heal.py`, роль `report-fixer` в каталоге запуска,
  ремонт до повтора; изменённые пути из git (`scope.py`), политика `scope.outside`, список путей вне write set в промпте
  ревьюера; preflight ролей; пересборка входа при изменении плана (`INPUT_REBUILT`); `run --adopt`, `settle`; правила
  модуля и скиллы текстом для изолированных ролей; `checks.cadence`; проверки без обрыва с маяком; отчёт наблюдателя
  считает маяки, ремонты и долю проверок во времени; `estimate.py`; исправлены: повторная отправка находок
  объединённой правки (A), потеря проверок при падении параллельного ревью (D), мёртвая ветка бюджета.
- **роли**: исполнитель запускает тесты своего изменения (приёмку гоняет дирижёр), читает и правит файлы инструментами,
  а не через `cat`/`sed`; триаж отклоняет Major только с выполненным воспроизведением (проверяется контрактом).
- **planner**: ворота закрытия фазы по `phase.validation`; `plan.py check` — `check_cadence`, `validation_id_clash`;
  `scripts/test.sh` (два набора параллельно; validate использует его).
- **мост planner-orch**: проверки фазы для закрывающего пункта; `scripts/sync-schema.py` — зеркало схемы опций с проверкой
  дрейфа (планировщик принимает схему слота только файлом внутри моста, поэтому одна копия — генерируемая); тесты параллельно.
- **aicore**: `par_unittest` изолирует TMPDIR/XDG/SKM_*HOME, снимает окружение до импорта тестов (корень #56 и, вероятно,
  #58), раздаёт шарды по замеренному времени (кэш в `.git/par-unittest/`), `--clash fail` / `SKM_TEST_CLASH=fail` в CI;
  читаемые ошибки `oneOf`.
- **хаб**: `affected-tests.py` — кэш зелёных результатов по содержимому (в `.git/affected-tests/`, никогда для `--tier all`),
  golden и тесты скриптов для путей хаба, деление ядер; analyst — инструмент; `docs-impact.py` — удаление пакета целиком,
  `--worktree`; отчёты наблюдателя дирижёра игнорируются (политика, `doctor`, документация согласованы).

Замеры тестов после правок: maind 38 → 10 с; planner engine 187 → 62 с (со второго прогона), planner `tests/` ≈ 60 с параллельно
с engine; мост planner-orch 206 → 20 с; orch ≈ 80–110 с.

## Сделано (инструкции)

- `CLAUDE.md`, блок «Development mode»: убраны «Quality over speed» и «чини всё вне scope»; добавлены правило дефекта вне
  пункта (заметка с владельцем), проверка затронутых тестов, полный проход в закрывающем пункте, режим прогона дирижёром.
- `planner-development-philosophy`: write set по ссылкам (grep), быстрые проверки пункта, тяжёлые — в `phase.validation`,
  уникальные id, проверки истории — фазовые, инструменты.
- `skill-authoring`: `golden.py check` и захват golden вместе со скиллом, затронутые тесты (I11).
- `orch-debug`: маяки вместо обрывов, `--adopt`/`settle`/`--retry`, `estimate.py`, метрики пункта, сверка путей вне write set.
- Таблица I1–I15: I1, I2, I3, I4, I5, I6, I7, I8, I10, I11, I13, I14, I15 — сделаны; I9 — заменён проверкой запуска ролей
  (пробы платными запросами не нужны); I12 в журнале отсутствует.
