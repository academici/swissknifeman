две ступени «дешёвая перед дорогой», порог severity «RED только на сломанном продукте фазы»,
потолок двух раундов на фазу). Здесь остаётся только **детерминированная CLI-ступень**
`plan-lint --conflicts` (машинная сверка трёх SSOT ПЕРЕД дорогим проходом) — в `plan_lint.py`

## Первопричина — не исполнители, а конструкция гейта

`packages/task/commands/plan-audit.md` (на `b5ca096`) не задаёт:

1. **границы scope** — мандат «найди ВСЁ плохое в артефакте», а не «выполнены ли Deliverables фазы
   по её Scope Included»;
2. **порога severity** — «при сомнении ставь ВЫШЕ, сам не отбрасывай» (:49) + `RED` = любой Major
   (:57) ⇒ RED почти гарантирован по конструкции, стоит подать 800 строк свежей прозы;
3. **лимита раундов** — сценария «третий RED = решение владельца» не существует;
4. **альтернативы реопену** — единственный путь ремедиации: переоткрыть фазу и дописать items
   ВНУТРЬ неё (D24/D31/D32), отчего фаза растёт, а вместе с ней — поверхность следующего аудита.

Отдельный усилитель для планов-о-протоколе: **самореференция** (план исполняется по протоколу,
который сам переписывает) — каждое новое правило канона обесценивает форму отчётности текущего
плана на лету. Это не общий случай, но именно он дал третий круг.

## Решение (проект)

**A. Двухступенчатая проверка вместо одного безграничного прохода.**

1. **Конфликт-скан (дёшево, детерминированно, машинно)** — сперва. Класс, который дал ВСЕ
   окупившиеся находки, машинно проверяем: сверка трёх SSOT (`SKILL.ru.md` ↔ `SKILL.md` ↔
   `plan_lint.py`), enum'ы (формы `Next`, значения `Context`), гейт непереводимых литералов
   (`i18n-keep`), тесты линтера, `validate.sh` пакетов, `plan-lint --baseline`. Прогон — минуты,
   не часы; тир — sonnet/low или вовсе скрипт. Кандидат в CLI: `plan-lint --conflicts` либо
   `analyst`-чек.
2. **Короткий финальный аудит (opus/xhigh)** — ОДИН, и только на то, что скан не покрывает:
   семантика правил, no-op под 🟢, scope drift. Глубину НЕ снижать: цена ошибки в
   основообразующем пакете асимметрична (дефект не падает — он тихо обесценивает гейт у всех
   потребителей).

**B. Правила остановки в `plan-audit.md`** (item P3.3 этого плана, D44):

- **Scope-граница:** аудит судит фазу по её `Scope Included` / `Deliverables`, а не «по всему,
  что видно в файле».
- **Порог severity:** `RED` только когда сломан ПРОДУКТ фазы (правило, ломающее флот; no-op под
  🟢; невоспроизводимая Validation; ложное утверждение о факте). Дефект бухгалтерии плана, прозы,
  формулировки → **ATTENTION** + Pending Work, НЕ реопен.
- **Потолок раундов:** два аудита на фазу. Третий раз — решение владельца: сдать `🟠` с названным
  долгом либо убить фазу. Молчаливого «ещё круг» не существует.
- **Дефолт ремедиации меняется:** follow-up items в СЛЕДУЮЩЕЙ фазе (или отдельная фаза
  ремедиации); реопен — только если дефект в самом Deliverable закрытой фазы.

**C. Дешёвая ступень для «точечного пробоя»** (запрос Owner). Столкнулись с конфликтом/RED —
сперва бьём точечно КАЖДЫЙ конфликт (узкий item + детерминированная Validation), и лишь потом
один короткий финальный проход. Не «каждый раз гнать слоями всю фазу заново».
