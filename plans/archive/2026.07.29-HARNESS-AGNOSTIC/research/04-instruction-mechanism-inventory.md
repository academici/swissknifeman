## 4. Ограничения механизма, которые связывают авторинг

Сняты чтением реализации — исполнителю фазы они дороже прозы контракта:

1. **Каждое `compatibility_assertions`-утверждение обязано присутствовать в рендере
   дословно** (`instructions.py:559-568`, подстрочная проверка `assertion not in rendered`).
   Значит сжатие прозы ограничено снизу набором утверждений: ужимать можно всё, кроме
   зафиксированных литералов, иначе `INSTRUCTION_COMPATIBILITY_MISMATCH`.
2. **Ожидаемый инвентарь ID — константы кода**, не данные каталога:
   `COMMON_IDS`/`EXTENSION_IDS`/`SCOPES`/`TARGETS`, `CONTRACT_VERSION`, `CATALOG_VERSION`
   (`instructions.py:26-110`). Добавление секции — правка констант + каталога + фрагмента
   + фикстуры + теста точных счётчиков
   (`test_exact_49_common_18_extension_67_total_and_twelve_targets`).
3. **Фрагмент запинен хешем в каталоге**: каждая запись несёт
   `sources[0].sha256` фрагмента, и валидатор сверяет его с фактическим файлом
   (`instructions.py:695-701`). Правка фрагмента без обновления хеша = `provenance-invalid`.
4. **Фикстура совместимости — независимый baseline**, а не производная: её `records` должны
   совпасть с каталогом поимённо и по порядку (`_validate_compatibility_fixture`). Её
   правка законна только как явная миграция совместимости с новым решением владельца — и
   утверждения для неё снимаются с **живых авторских руководств**, а не с рендера
   (иначе это ровно тот «refresh expected from actual output», который контракт запрещает).
5. **`contract_path()` уже archive-aware** (`resolve_plan_dir`), поэтому архивация донора
   (P0.5) механизм не ломает.
6. **Lock `.swissknifeman/provider-artifacts.lock.json` — трекается git** и уже несёт две
   записи от живой транзакции донора (`harness.codex.lifecycle.*`, D121). Принятие 12
   целей добавляет 12 записей в тот же файл; чужие записи не трогаются.

## 5. Решения по развилкам (принято исполнителем по Р6)

| Развилка | Решение | Почему |
|:--|:--|:--|
| Куда девать правила `CLAUDE.md`, не попавшие в канон | Три законных дома: **новая common-секция** (правило нужно всегда и обоим), **provider-extension** (правило про нативную поверхность одного провайдера), **скилл реестра** (ситуативная процедура). Четвёртый исход — «удалить как выводимое из кода» — допустим только с явной строкой в матрице | Скиллы публикуются в оба канала (`.claude/skills` + `.agents/skills`, `findings/01` Ф1) и грузятся по требованию — единственный ленивый носитель, не ломающий паритет |
| `.claude/rules/` с `paths` как носитель выноса | **Отклонено** | Claude-only: у Codex аналога нет (`findings/02` Ф8), вынос общего правила туда молча лишает второй провайдер правила — то есть производит ровно тот разрыв, который фаза чинит. Как Claude-native носитель для Claude-native правил остаётся легальным, но в этой фазе не заводится |
| `@import`-разбиение корневого файла | **Отклонено** | Экономии контекста не даёт: импорт грузится на старте (`findings/02` Ф7, дословно) |
| Пользовательский «хвост» вне маркеров | **Не заводить.** Целевое состояние управляемой цели — только два блока | Байты вне маркеров пользовательские и гейтом дрейфа не покрыты; оставить там правила значит воспроизвести исходную болезнь |
| Принять существующие файлы vs. удалить и создать через `apply` | **Adoption-режим** | Удаление с последующим `create` — обход собственности: теряются pre-image/semantic mapping/rollback контракта, а сам контракт запрещает аппроксимировать принятие другими действиями. Плюс adoption переиспользуется на 25 онбордженных проектах, где та же коллизия неизбежна |
| Язык и плотность канона | Английский, сжатое изложение | Решение владельца Р5 (`brief/01-refinements.md`) |
