# P4 — карта внешних факт-классов ДО поиска (слой 2, 2026-07-25)

Порядок обязателен по **D20**: сначала перечислить, какие классы ВНЕШНИХ фактов несёт фаза,
затем искать. DoR-гейт проверяет форму RAG-маркеров, а не полноту множества — эта карта и есть
проверка полноты. Файл написан ДО первого запроса; исходы проставлены ниже, после прогона.

Фаза P4 = реализация варианта 1 стаба `roadmap/cross-machine-memory.md` (D4): единственный живой
демон agentmemory на always-on хосте + остальные машины как сетевые клиенты через Tailscale/LAN.

## Что уже известно из репо (НЕ ищем — repo-grounded, подтверждается чтением кода)

- Точка врезки URL уже существует: `resolve_ports(env, config)` даёт приоритет
  `AGENTMEMORY_URL` → `config.memory.url` → `http://127.0.0.1:<http_port>`
  (`packages/maind/lib/maind/memory.py:27-37`); ключ `url` уже валиден в схеме конфига
  (`packages/maind/lib/maind/config.py:131-132`).
- Демон сегодня слушает **только loopback**: `iii-http` `host: 127.0.0.1`, `iii-stream`
  `host: 127.0.0.1` (`packages/maind/config/memory/iii-config.yaml:10-11,45-46`); стор —
  `store_method: file_based`, `file_path: ./data/state_store.db` (там же, iii-state).
- MCP-сервер проекта — `maind mcp --scope <scope>` (`provision/deploy.py:137-140`), он резолвит
  URL памяти тем же `resolve_ports` (`mcp.py:196,257`), то есть удалённый хост подхватывается
  без изменения `.mcp.json` проектов (важно: зашитые пути `.mcp.json` не ломаем — §2).
- Round-trip-гейт уже есть: `health.memory_roundtrip` (store → recall → forget,
  `packages/maind/lib/maind/health.py:86-105`); `maind doctor` печатает состояние памяти по URL
  (`doctor.py:286-289`) и требует локально установленный Node/`agentmemory` (`doctor.py:247-251`).
- Демон как systemd `--user` юнит: `provision/service.py` (`ExecStart=<root>/bin/maind memory run`,
  `Restart=on-failure`, подсказка про `loginctl enable-linger`).
- SessionStart-дайджест деградирует тихо: `memory digest` пуст → `exit 0`
  (`templates/health/memory-digest-hook.sh:14-15`).
- Ступень 5 машинного bootstrap безусловно ставит **локальный** демон
  (`scripts/bootstrap-machine.sh:96-104`) — именно она порождает второго писателя.

## Сознательно НЕ внешние (repo-grounded — проверяются чтением кода, не ищем)

- Существование и приоритет seam'а `AGENTMEMORY_URL` / `config.memory.url` — `memory.py:27-37`.
- Кто именно резолвит URL на клиенте (`maind mcp`, `health`, `doctor`, `memory digest`) — grep
  по `resolve_ports`.
- Что делает ступень 5 `bootstrap-machine.sh` и почему она порождает второго писателя.
- Формат scope-маркеров и схема памяти (канон PR #59) — фаза их не трогает (границы контракта).

## Исходы прогона (заполняется ПОСЛЕ поиска, 2026-07-25)

| # | Исход | Где лежит |
|:--|:--|:--|
| FC-1 | **найдено — сужает выбор транспорта.** `tailscale serve` проксирует ТОЛЬКО `127.0.0.1`-бэкенд ⇒ демон остаётся loopback-only и `iii-config.yaml` не правится; доступ режется до одного порта ACL/grants (deny-by-default); key expiry автоматически отрезает доступ. Цена: бэкенд не видит client IP | `findings/P4-cross-machine-facts.md` §1 |
| FC-2 | **найдено — меняет дизайн P4.2.** У движка ЕСТЬ bearer-аутентификация `AGENTMEMORY_SECRET` (глобальный middleware → 401); без секрета сетевая экспозиция = анонимная запись; `/health` публичен всегда; remote-режим штатный (upstream деплой-шаблоны). Наш клиент заголовки передавать не умеет вовсе (`core/http.py`) — при включённом секрете всё падает в 401 | `findings/P4-cross-machine-facts.md` §2 |
| FC-3 | **найдено — поправка к премисе стаба + машинные гейты.** `state_store.db` физически **каталог** из 9 JSON-блобов (6,4 МБ), каждый = целый scope ⇒ file-sync двух писателей перетирает scope целиком (не «порча SQLite»). Доказательства единственного писателя: нет юнита + нет живого pidfile + порт 4111 свободен + `memory.url` не loopback. Побочно: у движка есть встроенный **mesh-sync** (LWW, требует секрет на обоих концах, приватные IP пиров блокируются) — это upstream-вариант 2, не замена варианту 1 | `findings/P4-cross-machine-facts.md` §3–4 |
| FC-4 | **найдено.** `cp`/`rsync` живого каталога даёт смесь состояний; порядок предпочтения — app-level `GET /agentmemory/export` → короткая остановка демона → снимок ФС; целостность доказывается тестовым восстановлением со smoke-чтением, не наличием файла; ретеншн 7–30 дней + 1–3 месячных точки | `findings/P4-cross-machine-facts.md` §5 |
| FC-5 | **найдено.** Чтение — fail-soft с ЯВНЫМ режимом «memory unavailable» (молчание = `silent mismatch`, худший отказ), критичное — fail-hard; локальный кэш/outbox платит дублями, порядком и LWW-перетиранием и допустим только с версией/идемпотентностью/пометкой stale; таймауты LAN/VPN 1–2 с (лёгкие) / 5–10 с (тяжёлые), 2–3 ретрая с backoff | `findings/P4-cross-machine-facts.md` §6 |
| FC-6 | **найдено — отрицательный результат для «положимся на клиента».** У stdio-серверов НЕТ per-request таймера и НЕТ авто-переподключения; per-tool дефолт ~28 ч, idle 30 мин. Значит бюджет ожидания обязан жить в нашем HTTP-клиенте (`core/http.py`: 3/5/10 с) | `findings/P4-cross-machine-facts.md` §7 |
| FC-7 | **найдено — одно наблюдение, правки не требует.** `loginctl enable-linger` — условие роли always-on; `After=/Wants=network-online.target` в user-юните ожидания сети не даёт (чужой инстанс менеджера), но для loopback-демона безвредно | `findings/P4-cross-machine-facts.md` §8 |

**Что карта дала сверх «просто поиска» (проверка D20-механики):** три класса оказались
дизайн-меняющими и ни один не следовал из формулировок контракт-блока P4 — FC-2 (у движка уже
есть аутентификация, а наш HTTP-клиент физически не умеет её использовать), FC-3 (формат стора
не тот, что описан в стабе, плюс существует upstream mesh-sync, о котором ADR обязан сказать) и
FC-6 (клиентские предохранители Claude Code нашему stdio-серверу не помогают). Третий датированный
кейс в пользу правки, запланированной P6.3.
