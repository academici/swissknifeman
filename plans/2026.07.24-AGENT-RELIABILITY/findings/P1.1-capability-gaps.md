`findings/03` control 7 asks for capability coverage derived **from actual carrier
literals**, not from declarations. Measured against the frozen catalog:

**Gap 1.1 — `command.interactive-user-input` does not exist.** `configs/provider-capabilities.json`
declares 35 capabilities; none covers interactive user input. `task:design` requires
`AskUserQuestion` in its body, so its `capability_requirements` cannot express the
requirement, and no preflight can fail closed on a provider that lacks the surface. This is
exactly the defect `findings/03` recorded ("capability reference for `task:design` does not
contain interactive-user-input"), still live and now reproducible by command.
*Owner:* P1.3 renders capability/behaviour structurally; adding a capability id to the frozen
catalog is a public-contract change and follows D23 (proposal → ADR → SemVer), so P1.1 names
it rather than inventing it.

**Gap 1.2/1.3 — `Workflow({` without `command.workflow-carrier`.** Both plan commands spell
the Claude workflow carrier while declaring only filesystem/git capabilities. On Codex the
capability is `adapted` (`command_render._CODEX_WORKFLOW_CARRIER` projects the literal into
prose), so today the projection hides the gap instead of failing closed — a declaration
mismatch, not a runtime break. Note `task:make-workflow` declares the capability correctly,
which is why the comparison is meaningful rather than a blanket complaint.
*Owner:* P1.3 (carrier capabilities), consumed by P2.4 route/capability evidence.

Everything else is clean: every capability that a carrier **declares** resolves in the
manifest for both providers, with no `unsupported` level among declared requirements.
