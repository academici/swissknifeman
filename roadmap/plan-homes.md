# Roadmap: plan-homes — репо-дом планов по умолчанию + канон имён

**Статус:** ⬜ к внедрению (идея Owner 2026-07-10) — развитие «двух домов» plan-protocol 2.0.
**Дом:** скилл `general/plan-protocol` + `brain` CLI (синк) + vault-гайдлайны (CLAUDE.md схема).

## Идея Owner

Планы хранить не в корневом `plans/` vault, а **внутри самих проектов/продуктов** — на одном
уровне с `docs/`/`docs-public/`, с линковкой в соответствующие проекты vault. CLAUDE.md в
корне описывает схему и самодостаточен для обоих контекстов (сессия в vault И сессия в репо
проекта). Плюс: текущие планы разношёрстны (FLEX → FLEX-IMPL → FLEXCRM-W2, v2…) — нужна
жёсткая структура имён. План = исполним любой моделью (ТЗ для холодной сессии), дорогая
модель — только финальный аудит (действующий канон D17/D21 ECOSYSTEM — подтверждается).

## Правила (проект решения)

1. **«План живёт там, где его deliverables»:**
   - repo-план пакета/продукта → `plans/` в репо проекта (уровень `docs/`), синк с vault
     тем же механизмом `brain sync` (frontmatter `repo:`), в vault — линк из control tower;
   - программный/межпроектный план (ECOSYSTEM, FLEX-IMPL) → vault `plans/` (deliverables
     размазаны по многим репо — единственный дом);
   - protocol 2.0 «Home» из «пока vault, репо создаст P0» становится «репо по умолчанию».
2. **Ось видимости** (по прецеденту docs/docs-public): публичные OSS-репо (AzGuard, Chatom,
   FlexCMS) НЕ получают приватный план в git — бизнес-контекст остаётся в vault; в репо
   допустима только публичная roadmap-выжимка. Классификатор — поле Meta `visibility:`.
3. **Канон имён и преемственность:** `<PROJECT>[-<трек>]` без v2/W2-суффиксов; новая волна
   того же трека = новый план с полем Meta `supersedes: <старый ID>` + архив старого
   (конвейер `plan-close archive` существует). Lint: план без `supersedes` при совпадающем
   префиксе с архивным = warning.
4. **Доставка схемы — компактный скилл-карта + CLAUDE.md-секции** (уточнение Owner
   2026-07-10):
   - **Скилл-карта** (рабочее имя Owner «vault-brain»; кандидаты: `ecosystem-map`) —
     МАКСИМАЛЬНО компактный (≤50 строк, указатели вместо копий канона): «как всё завязано»
     — где docs/docs-public и их синк (`brain sync`), где план проекта (репо-дом) и его
     линк в vault, где control tower, куда писать findings/artifacts. Портируется в КАЖДЫЙ
     проект, работающий с планами. Дом: бакет `axioma` (имена проектов разрешены;
     прецедент `axioma-stack` — путь-указатель на живой канон, не вшитая копия) или
     maind-managed скилл (прецедент онбординга). НЕ дублирует plan-protocol: «как
     формируются планы, команды, чеки» — отдельный скилл (plan-protocol + workflow-craft),
     карта только говорит, ГДЕ что лежит.
   - **CLAUDE.md обоих контекстов**: краткая секция «документация и планы» (5–10 строк со
     ссылкой на скилл-карту) в корневом CLAUDE.md vault И в CLAUDE.md каждого проекта —
     раскатка при следующем `maind sync`/`skiller vendor` (адаптеры уже управляемые,
     прецедент CLAUDE.md §10 vault).
5. **Миграция — только вперёд:** существующие планы vault не переезжают; терминальные — в
   архив по мере закрытия.

## Зачем

Сессии в репо проекта (без vault) получают план рядом с кодом — самодостаточность холодного
старта; vault остаётся хабом (control towers, программные планы, линки). Разношёрстность
имён закрывается конвенцией + lint, а не памятью владельца.

## Критерий внедрения

Вместе с пакетом SKM-плана оркестрации (settings-doctor, workflow-craft, wf-status,
ephemeral-дисциплина): это правки того же скилла plan-protocol — делать одним заходом,
чтобы не перекатывать канон дважды.
