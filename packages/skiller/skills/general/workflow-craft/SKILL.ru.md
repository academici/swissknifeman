# Workflow-craft

Тонкий скилл-указатель на канонический конструктор workflow-шаблонов
(`packages/task/workflows/`). Это ДИСЦИПЛИНА активации и выбора, НЕ копия
содержимого шаблонов — тела шаблонов и правила слотов живут в
`packages/task/workflows/README.md`, этот скилл на них ссылается.

## Когда активировать

Используйте этот skill, когда пользователь просит:

- «составь/напиши/сгенерируй workflow», «оркестрация субагентов»,
  «мультиагентный прогон», «запусти несколько агентов параллельно»;
- авторинг `*.js`-скрипта для Workflow-тула (`scriptPath`/named-workflow);
- переработку/расширение уже существующего workflow-скрипта плана.

**Field-case, который скилл закрывает:** проект подключён к skiller, конструктор
существует и содержит обязательное review в dev-шаблоне — а модель всё равно
сочиняет оркестрацию с нуля по свободной формулировке «составь workflow по
разработке» и теряет обязательную стадию ревью. Свободная формулировка не
матчится ни на один существующий триггер — этот `description` — недостающий
триггер.

**Граница против соседних скиллов (не смешивать):**

- `complex-task-orchestrator` — декомпозиция задачи ВООБЩЕ (слои, инварианты,
  DoD) внутри ОДНОЙ сессии агента, без порождения отдельного `*.js`-скрипта и
  без запуска субагентов Workflow-тулом. Если результат работы — план действий
  в этом же диалоге, а не файл workflow-скрипта — это тот скилл, не этот.
- `plan-protocol` — формат и жизненный цикл мастер-плана (`plans/<ID>/`, фазы,
  статусы, DoR/DoD). Мастер-план МОЖЕТ порождать workflow-скрипт для фазы
  исполнения (см. «Место и имя файла» ниже) — но сам план не про оркестрацию
  субагентов, а про постановку работы.
- `/task:make-workflow` (команда-гейт, если подключена) — интервью + генерация
  + автоматический выходной ревьюер вокруг этой же дисциплины. Если команда
  доступна — предпочти её ручному следованию скиллу: она гарантирует, что
  красный вердикт ревьюера не выпустит скрипт без фикса.

## Порядок действий (в этом порядке, не переставлять)

### 1. Сначала матчинг на 4 канонических шаблона

Открой `packages/task/workflows/README.md` — там 4 параметризуемых шаблона:
`wf-research-fanout.js`, `wf-author-by-spec.js`, `wf-audit-adversarial.js`,
`wf-dev-slice.js`. Конструктор — **библиотека портируемых шаблонов, не
кодогенератор**: задача почти всегда ложится в один шаблон или в пайплайн из
нескольких (research-fanout → author-by-spec/dev-slice → audit-adversarial).
Скопируй подходящий шаблон в `plans/<ID>/workflows/` плана-владельца и заполняй
слоты. Если задача правда не ложится ни в один шаблон и не в их комбинацию —
это осознанное исключение (main loop дорогой модели), а не повод писать
оркестрацию с нуля молча.

### 2. Обязательные стадии по типу задачи (SSOT-матрица)

Workflow бывает ровно двух типов, и у каждого — свой фиксированный набор
обязательных стадий. Смешивать типы или урезать обязательную стадию —
дефект, даже если пользователь явно не попросил её вслух (review для
dev-workflow не вопрос интервью, а данность).

| Тип | Шаблоны-основа | Обязательные стадии | Чего НЕТ |
|:--|:--|:--|:--|
| **Проектирование** (design-only) | `wf-research-fanout.js`, `wf-audit-adversarial.js` | RAG-research → дизайн (main loop дорогой модели) → adversarial-аудит/DoR-гейт → фиксы → re-audit | кода, тестов, semver |
| **Разработка** (dev) | `wf-dev-slice.js`, `wf-author-by-spec.js` | срез → impl → tests-to-green → risk-адаптивное review → гейты между срезами → коммит | дизайн-решений на дешёвой модели (эскалация в main loop, не решать самой) |

Это ядро скилла (SSOT матрицы) — команда `/task:make-workflow` и её выходной
ревьюер цитируют ЭТУ таблицу, а не собственную копию; расхождение — правь
только здесь.

**Не изобретай обязательные стадии сверх этой таблицы** (source: `roadmap/
workflow-craft.md` §1.5 + `packages/task/workflows/README.md`) — если кажется,
что нужна ещё одна обязательная стадия, это повод предложить правку матрицы
явно, не тихо добавить её в один скрипт.

### 3. Правила слотов — ссылкой, не дублировать

Как заполнять слоты (константы в шапке скрипта, embedded-конфиг вместо
args-строки, structured-summary по схеме у каждого `agent()`, judge-panel
только для high-stakes, max-iteration у любого loop-until) — см.
`packages/task/workflows/README.md` §«Правила заполнения слотов». Начал
пересказывать эти правила здесь вместо ссылки — стоп, это дубль конструктора.

### 4. Место и имя файла

Скрипт — артефакт плана-владельца: `plans/<ID>/workflows/wf-<plan-id-lower>-
<назначение>.js`, не свободное место в репозитории. Если задача не привязана
к мастер-плану (разовый прогон вне `plans/`) — это исключение, но канон при
наличии плана обязателен (см. `plan-protocol` — схема «двух домов»).

### 5. RAG-опция при нестандартной оркестрации

Если задача требует оркестрации, которую 4 шаблона не покрывают напрямую
(редкий случай, не первый выбор) — прежде чем изобретать паттерн с нуля,
проверь актуальные практики через `research/query-craft` (как сформулировать
запрос) → `general/verify-claims` (когда и как верифицировать). Промаркируй
результат в комментарии скрипта: `RAG:✅ <дата> <источник>` либо
`[UNVERIFIED]`, если движок был недоступен — не выдавай непроверенную
оркестрацию за проверенную.

## Чеклист перед выдачей скрипта

- [ ] Задача сначала сверена с 4 шаблонами — не написана с нуля, если ложится.
- [ ] Тип определён (design-only / dev), обязательные стадии из матрицы на месте.
- [ ] Правила слотов соблюдены (константы, embedded-конфиг, structured-summary,
      max-iteration) — по README, не по памяти.
- [ ] Место и имя файла — канон `plans/<ID>/workflows/wf-<id>-<назначение>.js`.
- [ ] Нестандартная оркестрация промаркирована RAG:✅/[UNVERIFIED].

## Связанные скиллы

- `general/complex-task-orchestrator` — декомпозиция задачи внутри одной сессии
  без порождения отдельного workflow-скрипта (граница выше).
- `general/plan-protocol` — формат мастер-плана; workflow-скрипт — артефакт
  фазы исполнения плана, «два дома» задают его каноническое место.
- `general/spec-interview` — механика «один вопрос за раз» используется
  командой-гейтом `/task:make-workflow` при уточнении слотов шаблона.
- `research/query-craft` — как сформулировать RAG-запрос при нестандартной
  оркестрации (шаг 5).
- `general/verify-claims` — когда и как верифицировать внешний факт вообще.
