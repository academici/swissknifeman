# Roadmap: plan-protocol — разорвать цикл аудитов из-за самоинвалидирующегося evidence anchor

**Статус:** 🟡 частично реализовано планом `2026.08.12-№1-TASK-RESILIENCE`, но полевой
regression 2026-08-13 показал неполную стабилизацию. Общий Git HEAD исключён из digest, однако
в digest всё ещё входит весь SHA generated item state; audit's own terminal/reconciliation events
меняют этот state и вновь делают только что полученный GREEN audit stale. **Остаток:** сначала
устранить self-induced state/projection drift, затем пункты 1–3 и 5–7 целевого контракта для
полного spec→product→closure graph; seam-grouping из пункта 4 также не реализован целиком.

## Проблема

P1.7 потребовал один clean product commit, который одновременно:

1. меняет product-файлы из `Files` item'а;
2. объявляет эти же файлы digest-qualified inputs своего bundle;
3. запускает на том же commit полный release carrier с `bundle --check`.

После product mutation digest bundle неизбежно устаревает. Значит, требование «product-only
single anchor + fresh bundle на этом же anchor» невыполнимо по построению. Дополнительно item-spec,
решение и bundle были закоммичены позже product commit, поэтому cold-start на названном anchor даже
не мог собрать Task Contract для P1.7.

Аудиты затем находили последствия по одному: stale bundle, неполные correction events,
расхождение closure view с фактически произведённым и дрейф line-citation. Каждая ремедиация
добавляла новый слой поверх прежней topology, но не меняла саму topology. Так возникает цикл:

```text
невыполнимый single anchor
  → частичное выполнение
  → close с deviation
  → audit RED
  → новый remediation-item с тем же anchor contract
  → следующий audit RED
```

Audit cap ограничивает число повторов, но не устраняет причину. Он лишь передаёт владельцу выбор
между принятием долга и ещё одной ручной переделкой.

## Откуда дефект взялся

- Task Contract проверяет форму evidence, но не строит dependency graph «что должно быть
  закоммичено до mutation, а что появляется только после close».
- Bundle admission не запрещает self-invalidating contract: пересечение `Files` item'а с
  digest-inputs допустимо даже при требовании `bundle --check` на product anchor.
- Команды планирования используют слово `anchor` как один carrier для двух разных фактов:
  неизменности продукта и свежести plan projections.
- Ремедиация аудита адресует список findings, а не общий seam, породивший несколько findings.
- Closure projection перечисляет заявленные Deliverables независимо от того, доказаны ли они
  terminal evidence; поэтому `Done with deviations` может выглядеть как «Произведено».
- Исторические `path:line` citations проверяются против текущего дерева и дрейфуют после законной
  правки файла, если ссылка не привязана к commit.

## Целевой контракт

Ввести явную двухступенчатую модель evidence:

```text
spec anchor → product anchor → closure anchor
```

- **Spec anchor**: item-spec, решения и исходный bundle уже закоммичены; Task Contract собирается
  на этом commit до product mutation.
- **Product anchor**: только product/files diff и product acceptance. Он доказывает продукт, но
  не обязан содержать post-mutation projections.
- **Closure anchor**: product paths byte-identical product anchor; bundle/state/status/decisions,
  citations и aggregate carrier свежи и зелёны.

Это не три обязательных commit для каждого item: compiler схлопывает ступени, когда dependency
graph не содержит конфликта. Разделение обязательно только при реальной write/read collision.

## Изменения в Swissknifeman

1. `task_contract.build/evaluate` fail-closed проверяет, что spec/decision/bundle являются
   предками product execution anchor; иначе `block:EXECUTION_INPUTS_NOT_ANCESTOR`.
2. Pre-mutation compiler строит множество `Files ∩ digest_inputs`. Если Validation требует
   same-anchor bundle/state check после изменения пересечения, вернуть
   `block:SELF_INVALIDATING_EVIDENCE_ANCHOR` с предложением product/closure split.
3. Схема evidence получает явные `product_anchor` и `closure_anchor`; closure gate проверяет
   byte-identity product paths между ними и запускает plan projections только на closure anchor.
4. `plan-audit` группирует findings по root seam. Повторный fingerprint того же seam запрещает
   ещё один symptom-item: сначала исправляется topology/contract, затем выполняется один
   детерминированный carrier. Audit cap остаётся аварийным ограничителем, не механизмом решения.
5. Closure view выводит Deliverable в «Произведено» только при terminal evidence, которое его
   подтверждает; иначе он находится в «Не произведено / Pending Work» и блокирует green close.
6. Исторические citations становятся commit-qualified либо проверяются на commit audit block;
   current-tree citations остаются строгими.
7. Owner-directed targeted closure после audit cap допустим без нового аудита, только если один
   deterministic closure carrier закрывает все findings, strict gates зелёны и открытого Pending
   Work нет.

## Acceptance

- Фикстура P1.7-типа блокируется до mutation с
  `SELF_INVALIDATING_EVIDENCE_ANCHOR`, а не закрывается с deviation.
- Spec, появившаяся после product commit, даёт `EXECUTION_INPUTS_NOT_ANCESTOR`.
- Product/closure split проходит: product acceptance зелёная на первом anchor, projections и
  aggregate carrier — на втором, product-path diff между ними пуст.
- Closure не пишет недоказанный Deliverable в «Произведено».
- Повторный audit fingerprint маршрутизируется в один seam-fix и не создаёт третий remediation
  layer.
- Commit-qualified историческая citation не ломается от последующей правки текущего файла.
- После deterministic targeted closure phase status зелёный, strict citations дают 0, Pending
  Work и material Known Deviations пусты; повторный audit не требуется.

## Реализовано 2026-08-12

`task.plan_gates.phase_candidate_fingerprint()` теперь строит один стабильный digest из scope,
material risks, terminal item spec/state и фактических repository carriers из `Files`. Общий HEAD
остаётся только `observed_repository_head` и не участвует в digest. Тест доказывает три ветки:
append audit-блока сохраняет fingerprint; item field и product file меняют его. Это закрывает
самоинвалидацию phase audit→close, но не выдаётся за реализацию всего evidence graph выше.

## Полевой regression — 2026-08-13

Agelto `2026.08.09-RELEASE-READINESS` P9 завершил независимый двухчасовой GREEN audit с
fingerprint `577bfdf…`. Его audit commit `5e6ce95b` дописал terminal/reconciliation events и
пересобрал P9 item-state projections; следующий `task:plan-close` построил `12aec…` и вернул
`PHASE_AUDIT_STALE`, хотя новый product risk, не-green item или material deviation отсутствовали.
Владельцу пришлось принять узкий direct-close D84, чтобы не запускать тот же audit повторно.

Причина: `phase_candidate_fingerprint()` хеширует файл item state целиком. Поля projection
`through.journal_line`, `inputs_sha256` и evidence/Completion Notes изменяются собственными
audit bookkeeping events, хотя не являются новой product-семантикой. Комментарий функции обещает,
что candidate bookkeeping исключён из fingerprint, но фактический SHA state этому противоречит.

Следующая правка `packages/task/lib/task/plan_gates.py` обязана:

1. fingerprint только material terminal evidence, отделяя state position/evidence от projection
   metadata и audit-owned reconciliation noise;
2. добавить regression fixture: `audit-green` + штатная regeneration state/status/bundle не
   меняют candidate и разрешают immediate `phase_close_gate` без owner override;
3. доказать, что изменение item status/material Completion Notes/spec или declared product file
   всё ещё делает audit stale.

До этого phase close не должен автоматически направлять владельца на повторный full audit, если
единственная разница candidate возникла из audit's own generated carriers; он должен вернуть
машинно классифицированный `audit-bookkeeping-only` repair/rebind path.
