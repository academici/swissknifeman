**Implementation Rules:** - **Конвертер детерминирован и идемпотентен:** повторный прогон на уже мигрированном дереве не меняет ни байта. Он не зовёт модель и не «улучшает» текст: перенос дословный, переформулировки запрещены.
- **Инвентарь снимается ДО и ПОСЛЕ.** До: **значение каждого поля `## 0. Meta` (все, включая `Design Passes`, `visibility`, `Home`, `Layout`, `Paused By`, `supersedes`)**, значение каждого из 16 полей каждого пункта, текст ячеек `Решение`/`Почему`/`Consequences` каждой D-записи, текст каждой строки Update Log, текст каждой развилки `## Обсуждение`. После: каждый элемент инвентаря обязан найтись в целевом дереве дословно с точностью до нормализации пробелов. Не найден хоть один — конвертация ПРОВАЛЕНА, а не «почти удалась».
- **Поля Meta проверяются ПОИМЁННО, а не по числу (D96).** Три поля меняют носитель по D32 (`Version`/`Status`/`Last Updated` → `status.md`) и обязаны найтись ТАМ; остальные обязаны найтись в ядре `plan.md` v2. Пропажа поля, которого нет в `plan_lint.REQUIRED_META_FIELDS` (там только Plan ID/Title/Version/Status), линтером НЕ ловится — то есть без этого пункта инвентаря `Design Passes: 4/4` и `visibility: private` исчезли бы при зелёном линте, и следующий `plan-audit design` не смог бы исполнить собственный пункт 5. Инвентарь несёт список ИМЁН полей до миграции и их адреса после.
- **Inplace-конвертер применяется ровно к одному плану** — `plans/2026.08.07-PLAN-ECONOMY`. Чужой source допустим только с парой `--dry-run --output <tmp>`: source после прогона байтово неизменен, output вне source, отсутствие любого флага = отказ. Это seam раннего P3.7 canary, не миграция флота (D3/D120).
- **Переходное правило пишется в `## 2. Execution Rules`** мигрированного плана дословно по смыслу: до перевода команд (P6) закрытие пункта на плане v2 идёт «запись в журнал + находка/решение при необходимости + регенерация видов», а не правкой полей в файле пункта; поля исхода в файле ТЗ запрещены и ловятся линтером. Правило стоит в первом слоте пути — то есть исполнитель прочитает его раньше всего (митигация pre-mortem #4).
- **Baseline обязателен и двусторонний:** для КАЖДОГО пункта плана считается вес обязательного чтения до миграции (по пути v1) и после (по пути v2), оба числа кладутся в генерируемый артефакт вместе с порогом и единицей (id калибровки + `model_id`). Помимо `after > threshold` отчёт ОБЯЗАН перечислить `gaps` по kind/path и aggregate до/после; D2(b) не прячется за зелёным D2(a).
- **P2.8 не выдаёт forecast за admission.** Терминальные до Layout v2 items сохраняются как historical evidence; ещё не произведённый declared output не считается нулём или pass; ready-path самого P2.8 обязан пройти оба frozen conditions. Полный hard verdict живого плана принадлежит P2.10 после machine semantics P2.9 (D131).
- **Не проходит готовый путь → эскалация, а не подкрутка.** Порог и лимит заморожены; их подъём или незамеренное сокращение пути запрещены. Baseline проблем становится входом P2.9/P2.10, а не исчезает из отчёта.
- **Phase status редуцируется по терминальности, не по цвету 🟢.** Все items `🟢/🟠/⛔` → terminal phase (`🟠`, если есть deviations); P0/P1 не могут оставаться `🟡` только потому, что часть закрыта с deviations. Лечить симптом переписыванием их Phase Handoff запрещено — owning source `plan_status.py`.
- **Отчёт `findings/07-…` пишется по скелету P0.4:** что и когда мерили, каким инструментом и какой калибровкой; охват; веса до/после по пунктам с распределением; что превысило порог; что этот замер НЕ доказывает. Последний раздел обязателен: одна миграция одного плана — не распределение по флоту.
- **Артефакты `p2-migration-inventory.json` и `p2-weight-before-after.json` — генерируемые** (канон `root.generated-artifacts`): руками не правятся, пересобираются прогоном.
- **Компилятор контракта пункта обязан быть зелёным НА КАЖДОМ пункте мигрированного плана** (D84): `task_contract.build` — обязательный шаг закрытия любого пункта (`plan-exec.md:53`, `:140`; `plan-close.md:61`), и если он не собирается на v2, исполнение P3–P6 останавливается на первом же пункте. Это ПРЕДУСЛОВИЕ терминальности фазы, а не отчётная строка: не собрался хоть один — миграция провалена так же, как при потере элемента инвентаря. Инвентарь поэтому обязан нести список идентификаторов пунктов (`item_ids`), чтобы проверка шла по факту, а не по памяти.
- **Обратимость обеспечивается git**, а не флагом конвертера: миграция делается отдельным коммитом, до неё дерево чистое (`git status --porcelain` пуст по `plans/`), чтобы откат был одной командой. **Предусловие чистого дерева выполнимо начиная с коммита детализации плана (D88)** — до него оно было невыполнимо, потому что весь результат дизайна лежал неотслеженным.
**Code Guidance:** Это необратимая перестройка живого плана, поэтому главный риск — «почти удалось»: потерянная D-запись или поле пункта, которые всплывут через месяц. Инвентарная сверка — гейт, а не отчёт: одна ненайденная строка означает провал конвертации целиком. Расхождение инвентаря — сигнал, а не помеха: разобрать до корня и зафиксировать вывод; выкинуть «неудобный» элемент из инвентаря или ослабить сравнение до «похоже» ЗАПРЕЩЕНО. ЗАПРЕЩЕНО помечать item 🟢 при незакрытых предусловиях: (а) инвентарь сошёлся полностью; (б) `plan-lint` на мигрированном плане даёт 0 ошибок до включения нового P3 gate; (в) все виды свежи; (г) повторный конвертер не меняет ни байта; (д) baseline по каждому item печатает aggregate И все gap kinds, а не только четыре D2(a); (е) `task_contract.build` собирается на каждом item и `review_policy` не возвращает `unknown`; (ж) каждое Meta-поле найдено; (з) ready-path P2.8 проходит D2(a)+D2(b); (и) D131/P2.9/P2.10 присутствуют в плане и roadmap. Обходить гейты («поднять threshold», «считать missing нулём», «объявить весь план принятым сейчас») запрещено. Future failures не делают P2.8 красным после D131, но обязаны остаться в baseline и блокировать закрытие P2 через P2.9/P2.10.
