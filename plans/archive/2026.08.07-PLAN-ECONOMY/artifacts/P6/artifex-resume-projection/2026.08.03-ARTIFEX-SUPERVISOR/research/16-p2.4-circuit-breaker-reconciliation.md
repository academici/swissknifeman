# P2.4 circuit-breaker reconciliation

## Inputs and constraint

This synthesis consumes `findings/14-p2.4-circuit-breaker-recon-2026-08-04.md` and the frozen P1
run/authority carriers it cites. The constraint is fail-closed: P2.4 may compose existing contract
members but may not mint a new state, event, authority reason or transition inside implementation.

## Canonical adapter mapping

| Scheduler condition at `READY` | Authority result | Durable run event | State after | Activity |
|:--|:--|:--|:--|:--|
| same stable finding reaches `retry_count >= same_finding_max` | `OWNER`, `RETRY_BUDGET_EXHAUSTED`, `allowed=false` | `budget_exhausted` | `BUDGET_EXHAUSTED` | forbidden |
| any other exhausted pre-dispatch attempt/token/cost/time/turn ceiling | `OWNER` with the applicable closed budget reason | `budget_exhausted` | `BUDGET_EXHAUSTED` | forbidden |

The event uses the triggering slice's next legal attempt identity and stable idempotency key; its
minimized `evidence` is the exact closed P2.3 decision record, not a scheduler-authored reason.
`input_hashes` retain the pinned manifest/authority input links already required by the run and
slice contracts. The scheduler appends no `append_intent`, invokes no activity port and exposes no
acceptance on this branch.

`BUDGET_EXHAUSTED` is a run-wide admission stop. A subsequent scheduling call refuses with the
frozen state rule and cannot select an independent slice. Only a durable explicit owner decision
may continue to `READY` or abort to `ABORTED`; retry/reset-by-restart is forbidden.

## Post-boundary cap sequence

A worker-side cap may become known only after a boundary. P2.4 does not invent an illegal direct
transition from `BOUNDARY_ACTIVE`/`OBSERVED`. It persists the bounded observation, follows the
existing validation/reconcile path to a non-accepted terminal attempt, returns to `READY` only when
the frozen state machine permits it, then evaluates replay-derived counters and appends
`budget_exhausted`. Unknown/third-state/failed-rollback outcomes remain `INCIDENT`, not budget
events.

## Rejected alternatives

1. Add `circuit_breaker_tripped` or `repeated_finding` to `supervisor-run-v1`: rejected because it
   is a major frozen-contract change with a manifest and consumer ripple, while the existing
   budget transition already preserves the required outcome.
2. Map repeated finding to `source_drift` or `INCIDENT`: rejected because the cause is a known
   bounded retry exhaustion, not corrupted/unknown state.
3. Keep the stop only in memory or a derived owner queue: rejected because restart would lose the
   breaker and derived projections are not replay authority.
4. Treat the breaker as per-slice only and continue independent work: rejected for v1 because the
   frozen destination is run state `BUDGET_EXHAUSTED`; relaxing it requires a later contract
   version and evidence, not a P2 shortcut.

## Deterministic proof obligations

- Positive: `retry_count = 2` produces the P2.3 `RETRY_BUDGET_EXHAUSTED` decision, exactly one
  `READY --budget_exhausted--> BUDGET_EXHAUSTED` append, zero intents and zero activity calls.
- Replay: reopening reconstructs `BUDGET_EXHAUSTED`; another scheduling request cannot dispatch
  any slice before an explicit owner event.
- Resume: `owner_decision_continue` returns to `READY`; `owner_decision_abort` reaches `ABORTED`.
- Mutation: an invented breaker event, wrong destination, missing triggering identity, or an
  attempt to append from an illegal state is rejected rather than normalized.
- Contract preservation: the P1 aggregate validator remains green and the pinned P1 contract,
  cases and manifest files have no diff.
