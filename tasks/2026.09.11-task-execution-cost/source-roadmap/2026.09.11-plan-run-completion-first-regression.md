# Инцидент: `plan-run` разрезал одну работу на лишние сессии вместо завершения результата

**Статус:** 🔴 подтверждённый defect исполнения и Task lifecycle. Исправление не откладывать
как ergonomics-улучшение: это прямое owner-directed требование после повторяемого сбоя на
живом плане.

**Дата и поле:** 2026-09-11, Agelto,
`2026.09.10-№1-PARSING-PRODUCTION-REMEDIATION P1.4`.

## Наблюдаемая трассировка

1. Владелец дал **один** вызов `$ task:plan-run … P1.4` и чёткий terminal gate: не закрывать
   item до повторного независимого `task:review` с GREEN.
2. Реализация, scoped validation и повторное независимое review были доведены до GREEN в этой
   owner session. Gate означал «закрыть после GREEN», а не «попросить владельца открыть
   отдельную сессию для закрытия».
3. Агент ошибочно выдал новый launch для `$ task:plan-close … P1.4`, представив наличие
   отдельной semantic-команды как обязательную границу пользовательской сессии.
4. После возражения владельца агент не завершил closure сам, а предложил ещё один launch
   `$ task:plan-run … P1.4`. Это повторно переложило уже завершённую работу на владельца и
   не дало настоящего следующего шага.
5. Только после нескольких прямых поправок было установлено фактическое продолжение:
   закрыть P1.4 в текущей сессии, а следующим самостоятельным вызовом делать phase audit P1,
   поскольку именно он указан в Phase Assurance до P2.1.

Симптом не сводится к неверной строке handoff: агент оборвал автономную работу раньше
результата, создал лишние handoff-сессии и дважды назвал неверный следующий action.

## Что не было причиной

- Инструкция владельца не требовала отдельного close-вызова; она задавала только admission
  gate для closure.
- Наличие `$ task:plan-close` не требует нового Codex процесса. Runtime adapter прямо
  определяет `$ task:…` как invocation **в текущей Codex session**.
- Инструкции Task не оправдывают передачу уже готовой terminal bookkeeping работы владельцу.
  Ошибка — в их механическом и неверном применении агентом.

## Корневая причина

1. **Подмена outcome процедурой.** Агент принял доступную semantic-команду за обязательную
   пользовательскую границу вместо того, чтобы продолжить исходный `plan-run` до его
   terminal результата.
2. **Ложный handoff.** `review GREEN` был обработан как повод вернуть управление владельцу,
   хотя это был последний gate перед закрытием того же item.
3. **Неверный successor.** Агент вывел прямого следующего item, не пересчитав состояние фазы:
   P1 требует audit/close, следовательно P2.1 ещё не runnable.
4. **Нет предфинального stop-check.** Перед ответом не был задан вопрос: «осталась ли
   безопасная, автономно выполнимая работа, необходимая для запрошенного результата?» Для
   journal/view closure ответ был «да».

## Требуемая модель поведения

### Completion-first invariant

`plan-run` обязан доводить текущий item до результата максимально в **той же owner session**.
После GREEN всех заявленных gates агент сам выполняет terminal bookkeeping: final evidence,
journal transition, state/status projection, обязательные layout checks и точный handoff.

Нельзя завершать ответом с просьбой запустить `plan-close`, повторный `plan-run` того же item
или иной локальный lifecycle шаг. Исключения исчерпывающие: владелец прямо просит остановиться;
нужна новая owner authority; внешний инструмент действительно недоступен после безопасных
попыток; либо продолжение необратимо меняет внешний мир без разрешения.

### Semantic command не равен session boundary

Команда `plan-close` может быть внутренним reducer/подшагом `plan-run`; сама по себе она не
создаёт handoff. Новый native Codex launch разрешён только для семантически следующей работы
после фактического closure текущей работы, а не для очередного carrier того же результата.

### Successor после closure

Next вычисляется из **получившегося** phase state, dependencies и Phase Assurance, не из
линейного номера item. Если P1 после P1.4 требует independent phase audit, единственный
корректный launch — `task:plan-audit … P1`; P2.1 появляется только после его closure.

## Требуемое исправление Task

1. В lifecycle `plan-run` ввести явное состояние `closure-pending`: когда product work и все
   declared gates зелёные, оно автоматически запускает in-session close reducer и не рендерит
   пользовательский handoff.
2. Ввести общий `completion_readiness` guard перед любым final ответом. Он обязан отклонять
   final, если остаётся безопасный closure/write-view/verification шаг текущего invocation.
3. Разделить `semantic_command` и `session_boundary` в routing/delivery API. `plan-close` из
   обычного `plan-run` — internal continuation; standalone launch допускается только при
   явном пользовательском `$ task:plan-close`.
4. Делать `Next` только через phase-aware resolver после closure. Resolver не вправе назвать
   direct successor, если phase carrier требует audit или ещё не существует closure carrier.
5. Если terminal projection временно не проходит, сообщать точный технический blocker и
   продолжать безопасную диагностику; не подменять это новой командой для владельца.

## Обязательные регрессии

Добавить fixture реального layout v2: текущий `P1.4` в progress, все target validation и
independent review GREEN, а P1 имеет required phase audit перед `P2.1`.

- Один `$ task:plan-run … P1.4` создаёт terminal journal/state/status closure в том же
  execution path; в финальном delivery отсутствуют `task:plan-close` и повторный
  `task:plan-run … P1.4`.
- Предфинальный guard отрицательно проверяет попытку отдать владельцу closure, пока current
  item всё ещё `closure-pending`.
- Сгенерированный следующий native launch равен `task:plan-audit … P1`, а не P2.1 и не P1.4.
- При RED review или неготовом gate item не закрывается; owning continuation остаётся точной
  product/review работой, а не фиктивной close-сессией.
- Отдельно проверить разрешённые исключения: явный stop от владельца, реальная owner authority
  и устойчиво недоступный обязательный инструмент. Только они могут прервать completion-first
  путь и должны быть явно записаны как причина.

## Критерий готовности

Исправление считается готовым лишь когда regression fixtures проходят в Task CI и вручную
проверяется полный owner transcript: один исходный `plan-run` → gates → in-session closure →
один действительно следующий native launch. Нельзя «исправить» дефект увеличением TTL,
ослаблением layout checks, скрытием Next или заменой close на ещё один обязательный gate.
