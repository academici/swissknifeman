# Петля обратной связи из полевой работы (improvement loop)

Внутренний скилл (не экспортируется). Прямое следствие тезиса AGENTS.md
«фичу внедряем **по факту измеренной проблемы**, не на упреждение» (и принципа
`roadmap/README.md`): **полевая работа над проектами — и есть измерение**.
Проектов много, у каждого своя специфика; отклонение, пойманное на одном проекте,
ловится здесь, чтобы экосистема его учла, а не потеряла.

## Когда активировать

- Внедрение/интеграция/синхронизация/онбординг проекта тулингом экосистемы
  (`skiller connect|vendor|integrate`, `maind onboard|sync|health`, `harness`,
  `swissknifeman setup|doctor`) — **и реальность разошлась с обещанным**.
- Любое отклонение от инструкции: раннбук/док/скилл говорит X, инструмент делает Y;
  шаг падает; результат не тот; «пришлось руками обойти».
- Мне **сообщают** «запустил setup на проекте Z — сломалось/повело себя странно».

## Правило (классификация отклонения → маршрут)

Сначала — **что именно отклонилось** (это и есть «измеренная проблема»):
код пакета? генерируемый артефакт? сама инструкция (док/скилл/раннбук устарел)?
специфика проекта Z, которую тулинг не учёл?

1. **Очевидный баг / явное улучшение репо** — поведение бесспорно неверное или
   улучшение тривиально и локально (опечатка в логике, кривой путь, забытый кейс,
   устаревшая фраза в доке/скилле). → **Дорабатываю сразу**:
   - код пакета → правка + тест;
   - устарела инструкция → правка дока/скилла (`docs-maintenance` / `skill-authoring`,
     RU-источник → EN-канон);
   - генерируемый артефакт **руками не правлю** — чиню генератор (см. `package-architecture`).
   Завершаю по `release-discipline` (validate → registry → CHANGELOG → PR).

2. **Действительно новое / есть сомнение** — не уверен, что это баг (может, так задумано
   или виновата моя ошибка/специфика проекта); или это новая возможность, не решение в один
   шаг. → **Не внедряю спекулятивно.** Предлагаю на доработку:
   - сначала верни сомнение в факт: repo-grounded → подтверди чтением кода; внешнее
     («библиотека уже это умеет», «так больше не делают») → `decision-verification`;
   - **захвати немедленно**, чтобы не потерялось между проектами:
     `maind memory store` (namespace проекта/`swissknifeman`) — что наблюдал, на каком проекте;
   - оформи приёмник: исследованное направление → спека в `roadmap/` (с полем
     **«критерий внедрения»**); конкретный actionable-дефект/запрос → GitHub issue
     (`gh issue create`, repo `academici/swissknifeman`).

Граница: чините — когда поведение бесспорно неверно **и** правка локальна. Сомневаетесь
в любом из двух — путь 2 (предложить), а не «тихо поправить библиотеку под один проект».

## Анти-паттерны

- Молча обойти отклонение в текущем проекте и забыть (специфику не учли → повторится).
- «Починить» библиотеку под то, что на самом деле корректно или верно только для проекта Z.
- Затащить новую фичу спекулятивно вместо спеки в `roadmap/` с критерием внедрения.
- Править руками генерируемый артефакт вместо генератора.

## Связанные скиллы

- `release-discipline` (root) — завершение фикса (validate → registry → CHANGELOG → PR).
- `decision-verification` (root) — снять сомнение «баг или внешнее/задумано» до действия.
- `docs-maintenance` / `skill-authoring` (root) — когда отклонила сама инструкция (док/скилл).
- `package-architecture` (root) — что генерируется чем (чинить генератор, не артефакт).
- `cross-project-optimizer` (root) — если отклонение = повторяющийся across-проектов паттерн.
