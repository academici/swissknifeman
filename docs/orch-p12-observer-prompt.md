# Промпт 2: наблюдатель фазы P12 (оценка доработок механизма)

Стартовая инструкция для агента, который ведёт фазу P12 дирижёром по пунктам (например, Sonnet 5.5 medium). Перед
запуском фаза должна быть детализирована владельцем, а промпт 1 (`docs/orch-p12-prep-prompt.md`) — выполнен.

```text
Используй скилл orch-debug. Ты ведёшь фазу P12 плана экосистемы дирижёром orch (conduct.py) по одному пункту и после
каждого оцениваешь, как работает механизм. Как запускать — CLAUDE.local.md (движок, переменные окружения,
команда run/resume/status); правила — CLAUDE.md. Push не делать, состояние машины не менять.

Что изменилось после P11 и что ты проверяешь (подробно — docs/orch-p11-review-opus.md, опции и маяки —
packages/orch/docs/conductor.md):
1. Ничего не обрывается по времени. Маяки STAGE_SLOW / STAGE_IDLE / CHECK_SLOW / BUDGET_OVER показывают, что
   выполняется. На каждый маяк: прочитай, что он называет (тест, сборка, тихий вызов модели) и реши — ждать или
   разбираться. Запиши каждый маяк и своё решение. Не убивай работающую роль.
2. Лимиты раундов — цели: сверх цели раунд идёт, пока есть прогресс (LIMIT_OVER). Оцени: были ли такие раунды
   полезны (что исправили) или пункт был слишком крупным.
3. Отчёты ролей лечатся правилом (RESULT_HEALED) и ремонтируются report-fixer (RESULT_REPAIRED) до повтора роли.
   Считай: сколько лечений, ремонтов, полных повторов; время ремонта против времени повтора.
4. changed_paths берутся из git; пути вне write set — отклонение и строка для ревьюера. Считай такие пути на пункт и
   смотри, нужны ли они были (это сигнал для нарезки следующих пунктов).
5. Роли изолированы (--safe-mode) и получают блок Repository rules. Смотри в prompts/ первого пункта, что блок есть и
   короткий; ищи нарушения границ модулей в работе исполнителя.
6. Исполнитель гоняет только тесты своего изменения. Профиль executor (step-profile.py): доля собственных прогонов
   проверок должна быть < 15 %.
7. Каденс проверок: в приёмке пунктов — быстрые проверки затронутого; полный проход — phase.validation, его получает
   только пункт, закрывающий фазу, и фаза не закроется без его результатов. Доля проверок во времени пункта (отчёт
   наблюдателя: checks_share) — главный показатель; на P11 она доходила до 97 %.
8. Тесты модулей параллельны и кэшируются (affected-tests.py): смотри длительность checks.N против P11.

До каждого пункта: plan.py check (предупреждения check_cadence и validation_id_clash устранить в плане до запуска),
dry-run сценария (все роли available), оценка estimate.py по входу пункта. После каждого пункта: run-usage.py,
step-profile.py по шагам ролей, observer.md прогона, сверка оценки с фактом (отклонение > 30 % — причина).

Метрики пункта (одна строка таблицы на пункт): время пункта и оценка; минуты executor / review / checks / правок;
checks_share; круги проверок и ревью, LIMIT_OVER; повторы ролей, лечения, ремонты; маяки по кодам; свежие токены
in/out по ролям; пути вне write set; находки по уровням, подтверждённые/отклонённые, отклонённые Major (заметки плана);
доля собственных проверок исполнителя.

Оценка после каждого пункта (коротко, в журнал): что из пунктов 1–8 сработало, что нет, с цифрой; что помешало;
что бы ты изменил (опция, правило плана, промпт роли) — как предложение, не правка. Чинить механизм по ходу — только
блокирующий дефект (с тестом, в отдельном worktree, между пунктами, по правилам orch-debug); остальное — в журнал.

Журналы: docs/orch-p12-run-findings.md (дефекты #N, таблица метрик, оценки по пунктам, «спорные решения» пунктов,
«что поправить в инструкциях») и docs/orch-p12-observer-journal.md (хронология решений). В конце фазы — итоговая секция
«Помогло ли»: по каждому из пунктов 1–8 вердикт (помогло / не помогло / не проверено) с цифрами P11 → P12, и
промпт для финального ревьюера со ссылками на эти файлы.
```
