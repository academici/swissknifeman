## Closed invariants

1. **Project selection carrier.** Only the repository root for canonical project
   `swissknifeman` may create or merge `.swissknife.json#/providers`. The exact v1 layer is
   `{"contract_version":"1.0.0","selection":{"claude-code":{"enabled":true},"codex":{"enabled":true}}}`.
   An absent file becomes a JSON object with only `providers`; an existing root must be a JSON
   object. Every sibling outside `/providers` is preserved semantically. A present
   `/providers` layer is validated by the frozen P1 parser before and after the merge; only the
   two `enabled` leaves may be added/replaced, while capabilities, native extensions and other
   valid provider fields are preserved. Invalid JSON, a non-object root, unsupported contract
   version, unknown fields/provider IDs, an unsafe/symlink target, or a different project/root
   refuses before write. No fleet/default/global carrier is read as a write target.
2. **Exact ownership candidate.** Only root-relative `.mcp.json`, artifact ID
   `maind.provider-deploy.claude-code`, boundary `whole-file`, and preimage SHA-256
   `cf4537196c3fefd6fd3980221bd3677f74e7867392ad49364e1e891e1f7c8283` are admitted. The
   independently rendered expected bytes must equal that preimage and decode to the exact
   server-ID set `maind`, `perplexity-web`, `serena`; current definitions are therefore
   preserved on the first transaction. Any different path, ID, boundary, preimage, expected
   bytes or server set refuses before write.
3. **One atomic ownership chain.** D104's sealed two-artifact bootstrap plan is the exact
   predecessor. Before the first write, one P2 transaction validates all three target
   preconditions, the absent canonical lock, exact backup destinations and the final lock with
   the two unmodified D104 records plus exactly one `.mcp.json` record. Success creates
   recoverable backups and the canonical three-record lock; `.mcp.json` bytes do not change.
   Any failure restores the byte-exact pre-transaction root and removes only transaction-created
   partials. Ordinary `plan_artifact_lock`, update and repair behavior remain unchanged; no
   generic adoption API or hash-only ownership inference is allowed.
4. **Whole operation preflight.** P6 first constructs and validates the project-carrier plan,
   the dual-provider effective selection, both provider artifact plans, the sealed D104 plan and
   the exact P2 ownership chain. A non-green component yields a structured result and writer
   count `0`; selection is never written early to make later planning pass.
5. **No live execution in remediation.** P2.7/P6.11 work only in `TemporaryDirectory` roots.
   P6.12 independently inspects the real repository read-only and proves the exact candidate
   classification plus a stable before/after SHA-256 inventory. Live apply/repair/rollback
   remains the existing P7.2 post-isolated Owner gate.

## Sequential remediation

### P2.7 — exact chained ownership transaction

Add the smallest closed admission/plan/apply surface needed for invariant 2–3. Before source
editing, the executor updates the existing contribution proposal and ADR with exact public
symbols, SemVer-minor consequence and rollback state machine. If and only if the proposal is
equivalent to D108, the executor records a delegated D109 citing the standing instruction and
continues; broader public semantics, another target/preimage or a general adoption primitive
escalates. Focused core tests cover exact success, all mutated admission fields, stale
preconditions at apply time, write failure at every transaction step, byte-exact rollback,
ordinary-lock regressions and no live path access.

### P6.11 — project selection and operation composition

Add a P6-owned pure project-carrier plan plus explicit apply/rollback, reusing the frozen P1
parser/resolver rather than duplicating provider schema. Wire the maind project operation to
load this carrier as the project rank, render the dual-provider plans, and request the exact P2
chain. Preflight every plan before the first writer call; preserve provider-tagged results and
the ordinary unmanaged-target behavior outside D108. Focused maind tests use only disposable
roots and cover absent/existing/idempotent carrier cases, sibling preservation, all refusal
conditions, success/rollback, second-run empty plan and Claude-only/non-D108 regressions.

### P6.12 — independent no-write and rollback conformance

Without package/source edits, independently derive the expected selection, server set, paths,
hashes, action ordering and final three-record lock from the frozen contracts and D108. Run the
temporary-root Claude-only/Codex-only/dual matrix, fault-inject every write boundary, verify
byte-exact rollback and second-run idempotence, then run both live readers with a sorted
before/after repository inventory and writer spy. Publish a committed conformance report.

After P2 and P6 are separately closed and freshly audited, rerun P7.2 in a new routed session
from its first preflight step. The rerun consumes D108/D109 and P6.12 evidence; it does not
reuse the earlier failed attempt as GREEN. It performs isolated matrices first and reaches the
unchanged live exact path/action Owner gate only after isolated GREEN.
