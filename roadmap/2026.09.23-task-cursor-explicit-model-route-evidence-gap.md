# Task Cursor: explicit `--model` не даёт достоверный route evidence для Grok high

**Дата:** 2026-09-23

**Статус:** 🔴 воспроизведённый source/consumer gap; remediation не реализована

**Field trigger:** AzGuard `2026.09.22-№1-AZGUARD-CORRECTNESS`, подготовка
`P1.2`, B2, B4 и B6 к исполнению на Grok 4.6/4.7 high. Владелец явно выбрал
Composer 2.5 для bounded work и Grok для сложных execution batch’ей; GPT‑5.6 Sol
оставлен крайним резервом, GPT‑6 Sol — аудитам.

## Наблюдение и граница доказательства

Cursor CLI `agent --list-models` в consumer-сессии показал selectors
`cursor-grok-4.6-high` и `grok-4.7-high`; `agent --help` подтверждает явный
`--model`. Повторная проверка каталога 2026-09-23 из swissknifeman завершилась
`getaddrinfo EAI_AGAIN api2.cursor.sh`, поэтому новый live-catalog verdict не
заявляется. Текущий source достаточно показывает дефект независимо от сети:

- `packages/task/lib/task/route_evidence_cursor.py::_capture_argv()` читает
  явный `--model`, но безусловно присваивает `effort_selector = "medium"`.
  Даже `--model grok-4.7-high` не может доказать требуемый `frontier/high`.
- `packages/task/configs/command-routing.json` распознаёт в Cursor frontier
  `grok-4.7` и `grok-4.6`, но не их видимые CLI high selectors. Значит
  `_selector_class()` отвергает явный pinned Grok launch.
- `capture_current()` ловит **любую** `RouteEvidenceError` из `_capture_argv()`
  и затем читает `~/.cursor/cli-config.json`. Этот файл отражает глобально
  выбранную модель, но не доказывает, что именно она обслуживает текущий
  процесс с явным `--model`. Совпавшая конфигурация может случайно скрыть
  дефект; устаревшая — дать ложный route либо ложный отказ.

Это дефект admission/evidence, не доказательство неправильного выполнения
продуктового кода. Для Composer 2.5 на `implementation/medium` явный CLI pin
пока совместим с фиксированным `medium`; Grok high остаётся проблемным.

## Минимальное воспроизведение

1. Зафиксировать из `agent --list-models` и provider-owned state актуальные
   CLI selectors и параметры high; не брать их из prose или ручного alias.
2. Подать `_capture_argv()` валидный `agent --workspace <repo> --model
   grok-4.7-high --force 'task:plan-exec <PLAN> Pn.m'` и отдельный
   `cursor-grok-4.6-high` fixture. Ожидается `frontier/high`; текущая
   реализация не выдаёт его из argv.
3. Поставить в `cli-config.json` другую selectedModel и вызвать
   `capture_current()` при том же явном launch. Текущая fallback-ветка может
   принять не связанную с процессом конфигурацию вместо fail-closed verdict.
4. Повторить с запуском **без** явного `--model`: только этот режим вправе
   использовать live cli-config при доказанном cwd/semantic invocation.

## Критерий запуска ремонта

Trigger уже сработал: потребительский план требует Grok high, а текущий
native CLI pin не даёт достоверного Task admission. Исправлять в owning Task
source отдельным bounded заданием, не переписывая AzGuard Routing под дефект
адаптера и не объявляя GPT‑5.6 Sol обычным исполнителем.

## Acceptance будущего исправления

- Явный `--model` разрешается в тот же canonical model class и effort, который
  реально выбран процессом; Grok 4.6/4.7 high проходят `frontier/high` без
  чтения глобального cli-config. Provider aliases и versioned CLI selectors
  сопоставлены явно и проверены по доступному live catalog.
- Если явный selector неизвестен, несовместим с требуемым route или не даёт
  доказать effort, admission возвращает typed fail-closed результат. Он **не**
  замещается cli-config, prose, другой сессией или self-attestation.
- Fallback на cli-config сохраняется только для запуска без явного `--model`
  и не утверждает больше, чем способен связать с текущим invocation.
- Tests покрывают оба Grok high selectors, Composer 2.5, stale/different
  cli-config, missing effort, invalid explicit model и разрешённый no-model
  config path. Изменённые Task source, provider projections и generated
  artifacts квалифицируются штатными Task checks.
- Полевой AzGuard `P1.2` допускается под Grok 4.6 high, B2 под Grok 4.7 high
  без GPT‑5.6 Sol fallback и без обхода route evidence.

## Границы

Не менять consumer plan ради ложного GREEN, не отключать route gate, не считать
глобальную config модель доказательством явного CLI запуска. Здесь записана
проблема и измеримый следующий шаг; Task runtime в этом roadmap update не
меняется. Рабочее дерево `packages/task/` уже содержит посторонние незавершённые
изменения — их нельзя откатывать или присваивать этому carrier.
