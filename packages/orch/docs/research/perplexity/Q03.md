Итог: из перечисленного только AWS CLI Agent Orchestrator (CAO) подтверждён первичными источниками как близкий к полному совпадению: он запускает реальные CLI в отдельных терминалах, показывает их работу и имеет программируемые workflows с журналом и resume. OpenHarness силён как живой терминальный cockpit, но по проверенным материалам не подтверждён как движок программируемых resumable stages. Ещё два достойных кандидата — kodo и codex-orchestrator, с оговорками ниже.

## Два дополнительных кандидата

- — наиболее интересный дополнительный кандидат на programmatic stages: первичный README описывает циклы, checkpoints/resumable logs, последовательные стадии и параллельные стадии в git worktrees, с backend на установленных CLI. Но это не доказательство полной совместимости именно с Grok Build или безошибочного восстановления всех сценариев. Важное ограничение: независимый verification gate по умолчанию не принудителен.
- — серьёзный узкий вариант для Codex CLI: tmux-сессии, live attach/watch, передача follow-up, машинно-читаемые job metadata и сохранение логов. Однако это не мульти-провайдерный workflow engine; в README описана staged pipeline skill, но не подтверждён durable resume программных стадий после сбоя.

## Preview и что не проверено

- CAO: источники подтверждают наличие workflow/resume в проекте и релизных материалах, но этот обзор не проверял локально конкретную версию, сквозное восстановление после аварии или отсутствие повторного выполнения уже завершённых побочных эффектов. Не следует считать эти свойства гарантированными только по описанию.
- OpenHarness: проверены реальные терминалы, поддержка CLI и чтение transcript/hooks; не подтверждены эквивалент CAO workflow-движка, программный stage API и восстановление цепочки после сбоя.
- Pydantic AI Harness: экспериментальным явно назван ACP; это не означает, что experimental весь runtime.
- Harness CLI 3.0: public beta по объявлению Harness, несмотря на широкий набор платформенных команд.
- Dify: конкретную текущую архитектуру и релизные ограничения не верифицировал — не трактуйте классификацию как аудит его всех функций.
Практический отбор: сначала пилотировать CAO как наиболее прямое соответствие; OpenHarness рассматривать как cockpit/видимость, а не автоматически как замену workflow runtime. Kodo проверить на resumability и нужных CLI, если важны циклы и stages; codex-orchestrator — только если достаточно Codex-специализированного диспетчера.
