# Разбор аудита Perplexity от 2026-09-23

Источник: [`2026-09-23-perplexity-1.md`](../audits/2026-09-23-perplexity-1.md). Проверка выполнена по текущему `HEAD` (`b005b6da`) **и** незакоммиченным изменениям рабочего дерева 2026-09-23. Это решение по направлению и короткая очередь работ, не новый Task plan и не активация Task workflow. Внешний поиск не нужен для выводов ниже: проверяемые утверждения относятся к локальному коду и зафиксированному решению владельца.

## Решение

Направление аудита верное: уменьшать цену обычного пути и оставлять строгие доказательства на границах с реальным эффектом. Но аудит местами оценивает размер файлов вместо поведения, предлагает повторно внедрить уже существующие механизмы и в главном пункте спорит с явным решением владельца. Поэтому не принимаю его P0–P3 как готовую очередь коммитов или 6.8/10 и 8.5/10 как измеренные оценки.

Для обычной разработки уже существует прямой путь без неявной активации Task. Внутри **явно включённого** плана сохраняем записанное правило: все объявленные фазы детализированы, затем один общий design audit, затем исполнение. Это подтверждено в [`roadmap/2026.09.17-task-final-plan-audit-and-route-coalescing.md`](../roadmap/2026.09.17-task-final-plan-audit-and-route-coalescing.md). Разрешить `plan-exec` после P1 при P2–P7 в состоянии skeleton означало бы тихо отменить это правило. Обратимую разведку можно проводить как прямо разрешённую обычную разработку или явно ограниченный design spike; её результаты затем входят в план. Исполнение объявленного плана до audit GREEN требует отдельного изменения правила, а не новой трактовки `Next`.

При этом финальный design gate должен быть **одним** проходом по готовому плану, с локальным исправлением обнаруженных расхождений. Он не должен заставлять перечитывать весь план при каждом редактировании Pn или проводить внешний research без влияния на решение. Свобода агента остаётся в порядке исследования, локальных исправлений, выборе достаточной проверки и продолжении в той же сессии внутри разрешённой области.

**Новый риск в рабочем дереве, которого нет в snapshot аудита:** незакоммиченный `_supporting_artifacts()` делал четыре design-файла обязательными для каждой фазы. В текущей правке это исправлено: обычная фаза обходится без dossier, а явно начатый сложный dossier проверяется целиком. Изменение выбранного dossier входит в fingerprint общего design audit.

Слабые оценки из первой таблицы аудита — гипотезы о стоимости, а не замеры нового состояния. Для повторного аудита связываю каждую из них с наблюдаемым поведением:

## Сквозные предложения аудита

- **Уровни Direct/Tracked/Governed/Protected:** полезная модель для объяснения эффекта пользователю, но четыре глобальных режима легко станут ещё одним control plane. Начать с локальной матрицы действий: локальная обратимая запись, shared/public contract, внешний/production/необратимый эффект. Уровень не должен вычисляться из числа файлов или возраста plan directory. Реализация отдельного enum нужна только при двух и более независимых runtime-потребителях.
- **Prompt economy:** принимать. Сократить дублирование phase Markdown/parsed items и foreign lint до переписывания общих инструкций. Мерить возвращаемые bytes и один реальный prompt; число файлов само по себе не равно стоимости токенов.
- **Evidence reuse:** принимать принцип, отложить общую cache-систему. Digest команды и исходников не достаточен для тестов, зависящих от среды, времени, БД или внешнего сервиса. Сначала для одной детерминированной проверки определить входы, TTL/среду, invalidation и явный отказ от reuse для live gate. Существующее правило `plan-exec.md` уже допускает reuse пока relevant inputs не менялись.
- **Persistent incremental index:** отложить до профиля длинного плана. Новый index требует собственного repair, схемы и согласования с journal; иначе он увеличит именно ту бюрократию, которую призван убрать. Сначала замерить journal scans, state builds и writes, затем оптимизировать самый дорогой reducer.
- **Cost telemetry:** принимать в минимальной форме: duration, вход/выход bytes, число parse/build/write и validation runs на уровне Task command. Provider tokens и денежная стоимость доступны не для всех providers и могут требовать отдельного учёта; не обещать точный `input_tokens` из локального runtime. Не логировать содержимое prompt или секреты.
- **Anti-bureaucracy checks:** полезны как 3–4 целевых сценария на observable side effects и число построений. Аудит предлагает абсолютные SLO (`один model call`, `ноль full rebuild`) без baseline и учёта recovery; их нельзя объявлять нормой до измерений. Дополнительный тест нужен лишь когда предотвращает воспроизводимую регрессию.

## Короткая очередь исполнения

Это последовательность независимых, обзорных изменений, а не полный план в Task. Каждый этап заканчивается работающим кодом или проверенным решением о прекращении работы. Новые policy/схемы допускаются только при конкретном consumer и сохранении существующих инвариантов.

1. **Выполнено — снять лишнюю обязательность.** Supporting dossier теперь нужен только когда его объявили; сохранена проверка полноты сложного handoff. Изменения внесены поверх существующего рабочего дерева без отката чужих правок.
2. **Выполнено — закрыть ошибку перехода.** P1 ready/P2 skeleton не даёт стартовать; finish и текущий GREEN design audit обязательны. Прямой `start` и handoff тоже проверяют gate. Для AzGuard выполнена read-only проверка реального плана.
3. **Частично — удешевить локальный design.** Foreign errors выдаются как count/digest, bundles не пишутся при design нового плана. Full lint до и после локального редактирования пока остаётся: он нужен для доказательства новых foreign ошибок; отделять его после профиля и сохранения этой защиты.
4. **Частично — адаптировать проверки.** Authoring теперь различает binding acceptance, условный impact и live boundary. Runtime route/review policy сохранена до измеренного случая ложной блокировки. Cursor explicit `--model` gap остаётся отдельным приоритетным дефектом.
5. **Дальше по доказательству — измерить и упростить.** Минимальные `wall_ms`/`payload_bytes` добавлены. Один профиль длинного плана определит, нужен ли index, evidence cache, renderer split или carrier cleanup. Без материальной повторной работы этап закрывается без рефакторинга.

Критерий каждого этапа: явный before/after на одном соответствующем сценарии, сохранённый fail-closed verdict на реальной защищённой границе и только затронутые проверки Task. Не нужно разрабатывать абстрактную систему классов, индекс или новые схемы ради выполнения пунктов аудита.

## Выполнено в этой сессии и оставшаяся граница

Один агент без Task workflow внедрил общий design gate в `plan_readiness`, ранний отказ в `plan_work.prepare`, повторную проверку на прямом `plan_recovery.start`, проверку handoff и fingerprint у design audit journal event. Планы с новым execution-sheet marker уже подпадают под gate; для датовых планов от 2026-09-24 marker нельзя удалить ради обхода. Два уже исполнявшихся плана от 2026-09-22 без marker сохраняют прежний путь. Локальный design возвращает краткую foreign-error сводку, optional dossier больше не обязателен, а новый формат не пишет bundles до выбранного start. Команды и runtime projections синхронизированы через генератор. Карта источников истины и типовых отказов записана в `packages/task/docs/reference/control-plane-map.md`. `plan-work.py` теперь возвращает диагностические `wall_ms` и `payload_bytes`.

Текущая обязательная проверка Task прошла: 1195 тестов, один пропуск, provider projection check GREEN. Практический read-only прогон на плане AzGuard сначала обнаружил строки `pending-validation`/`environment` вне схемы. К последней проверке этот внешний рабочий файл уже содержал `blocked`/`local-repair` в строках 19–20; актуальный gate сообщает `PLAN_DESIGN_FINISH_MISSING` для плана с marker. Изменения AzGuard здесь не выполнялись. Gate читает историю через штатный authoritative reader, включая его правила точечных исторических исключений, и не маскирует повреждённую историю как отсутствие audit. Два уже исполнявшихся плана 2026-09-22 в этом репозитории без marker проверены отдельно: они остаются в legacy-режиме.

На том же плане (7 фаз, 15 items) read-only полный `lint_plan` занял около 949 мс и вернул 5 ошибок, а расчёт design fingerprint — около 12 мс. Это один локальный замер, не SLO. Он не подтверждает, что введение отдельного local lint/index сейчас окупит дополнительную сложность; полезнее сначала устранить реальные ошибки и повторить замер на другом длинном плане.

**Не объявляю решёнными без доказательства:** полное разделение local/plan-wide lint (F-04), cost/capability envelope маршрутов (F-06/F-12), digest reuse и incremental index, а также рефакторинг `plan_weight`/`command_render`. У этих работ есть стоимость совместимости и новые собственные состояния. Следующий исполнитель должен сначала получить профиль одного длинного плана и конкретную ложную блокировку/повторную работу; только после этого менять соответствующий reducer. Это сохраняет движение к экономии без очередного слоя политики.

## Как проверять следующий аудит Perplexity

Просить проверку текущего commit **и** незакоммиченного diff, с отдельными выводами для обычной разработки, локального design, общего finish/audit, старта и закрытия item. Для каждого нового замечания нужны: конкретная команда или путь, наблюдаемый лишний вызов/запись/отказ, затронутый инвариант и минимальная правка. Число модулей, размер файла и предлагаемая оценка сами по себе не доказывают дефект.

Повторять пять практических сценариев: малый fix без Task; P1 ready при P2 skeleton (start отказан); полностью готовый план с актуальным GREEN audit (start разрешён); изменение item spec после GREEN (audit устарел); повреждённая journal-строка (типизированный отказ без молчаливого переписывания). Для стоимости записывать `wall_ms`, `payload_bytes`, число full lint/bundle writes и provider tokens только из реального receipt. Сравнивать с этим срезом и указывать регрессии по каждому сценарию, чтобы не возвращаться к уже отвергнутым предложениям о provisional execution и обязательном dossier.

## Передача на версионирование и раскатку

Это отдельная работа после фиксации текущего diff. В дереве уже были незакоммиченные изменения `maind`, `skiller` и `task` до этого аудита; следующий исполнитель должен разделить их по фактическому scope, не сбрасывать и не выдавать весь diff за изменения этого ответа. Источник release version — действующие manifests и `packages/skiller/configs/publication-versions.json`, а не число из отчёта. `scripts/release-fleet.sh` выполняет только локальную post-tag доставку и требует tag ровно на HEAD; он сам не создаёт tag или публикацию.
