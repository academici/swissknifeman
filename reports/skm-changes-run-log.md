### R7. Решение по стратегии проверок (делегировано владельцем)

- Для оставшихся пунктов (с P2.1) каждый run идёт с файлом опций `checks.executor_runs_checks: true` (передаётся `--options`, в репозиторий не записывается): исполнитель запускает свои целевые тесты до сдачи, раньше находит устаревшие ожидания и `TypeError`-подобные ошибки.
- Не менял: `kinds` (импакт-проверки V50+ — гарантия связей между пакетами и требование `CLAUDE.md` orch про standalone), `cadence`, `parallel`.
- Полный набор не сокращён до одного прогона: повторные `validate.sh` и `affected-tests` заданы в `validation` самих пунктов плана. Убрать их — изменение спецификации пунктов, это решение владельца плана. Записано как заметка для владельца.
- Ожидаемый эффект: меньше красных раундов (в P1.2 два из трёх раундов были по причинам, которые целевые тесты показывают сразу). Измерю на P2.1 и P2.2.

### R8. P2.1: исполнитель вернул `blocked` из-за среды проверок (V9, V10)

- Прогон `cnd-20261019T124519Z-1a9182` (с `executor_runs_checks: true`): executor `codex/gpt-6.1-sol/xhigh` 22м25с, 8.0M in / 52K out, закончил `blocked`. Исполнитель не проходил проверки сам: V1–V3 зелёные (17/535/29 тестов), V9 и V10 — внешние причины по его отчёту:
  - V9: `test_project.py` выбирал `/tmp` как проект (в `/tmp` найден `.git`) и падал;
  - V10: при записи `.git/affected-tests/green.json` — `EROFS`.
- Проверка: `test_project.py` сейчас 4/4 OK; `/tmp/.git` отсутствует; запись в `.git/affected-tests` проходит. Причина, похоже, временная среда, а не код пункта. Точную причину EROFS не установил: возможно, проверка шла под ограничением записи (Landlock-guard).
- Решение: прогон остановлен как `ITEM_BLOCKED`, изменения пункта лежат в дереве. По правилам orch — не `resume --retry` (переделало бы работу исполнителя), а `run --adopt`: работа принимается как предыдущая попытка пункта, исполнитель доделывает и проходит проверки.
- Статус: в работе (запуск `--adopt`).
