# Roadmap: `plan-run` не связывает явный owner-запуск с gate и не умеет календарный resume

**Статус:** ⬜ один подтверждённый field incident (`agelto`,
`2026.09.10-№1-PARSING-PRODUCTION-REMEDIATION P4.3`, 2026-09-11).
**Критерий внедрения:** повтор `AUTHORITY_CONTRACT_GAP` на другом owner-gated item **или**
первый фактический calendar resume, который нельзя выразить без ложного `waiting-owner`/
повторного owner-опроса. До срабатывания второго замера это спецификация ограниченного
изменения Task, а не разрешение ослабить deny-by-default authority.

## Пользовательский эффект

Владелец явно запустил точный item командой:

```text
$ task:plan-run 2026.09.10-№1-PARSING-PRODUCTION-REMEDIATION P4.3
```

Item требует durable owner authorization до 72-часового controlled-production gate. Исполнитель
прочитал это как обязанность ещё раз спросить владельца о разрешении и параметрах окружения,
хотя owner-session invocation уже задаёт item, маршрут и намерение исполнения. В результате
автономная работа остановилась на человеческом gate, а не дошла до машинного preflight и честного
`GO`/`NO-GO`.

После коррекции владельца автономный preflight дошёл до настоящей границы: целевое production-
окружение в consumer checkout не сконфигурировано (`.env.production` отсутствует,
`COMPOSE_PROJECT_NAME` не задан, production Docker project/remote context отсутствуют). Это уже
внешнее состояние, а не отсутствие owner authority. Текущий Task vocabulary, однако, умеет
выразить только `waiting-owner` и потому смешивает две разные причины ожидания.

## Tight repro

Репродукция выполнена дважды worktree-local runtime'ом Task:

```bash
PYTHONPATH=packages/task/lib python3 - <<'PY'
from pathlib import Path
from task import task_contract

plan = Path('/home/vostrikov/projects/agelto/agelto/plans/'
            '2026.09.10-№1-PARSING-PRODUCTION-REMEDIATION')
contract = task_contract.build(plan, 'P4.3')
assert contract['authority']['class'] == 'owner-gate', contract['authority']
PY
```

Оба запуска закономерно завершились `exit 1`. Фактический compiler result:

```json
{
  "code": "AUTHORITY_CONTRACT_GAP",
  "item": "P4.3",
  "prose_requires_durable_authority": true,
  "bundle_authority_paths": [],
  "compiled_authority": {
    "class": "routine",
    "granted": true,
    "granted_by": "phases/P4/P4.3.md:P4.3"
  }
}
```

То есть plan/item prose требует отдельный gate, bundle не переносит authority path, а компилятор
считает исполнение routine и разрешённым самим item carrier. Это не неоднозначность прочтения
одного агента: три машинных представления дают несовместимые ответы.

## Диагностика инструментами пакета

- `bin/swissknifeman maind analyze --project agelto --json` видит подключённый проект, но его
  `run_report` является старым synthetic snapshot (2026-08-08); текущую authority-ошибку он не
  диагностирует. `ATTENTION` относится только к dirty worktree consumer-проекта.
- `bin/swissknifeman analyst status --json` показывает один накопленный event и отсутствие
  candidate/curated lessons; authority incident автоматически в analyst не попал.
- `bin/swissknifeman doctor` подтвердил работоспособность Task/maind/analyst путей. Его отдельный
  FAIL про три stale project hubs и warnings про vendor/channel drift к repro не относятся.
- Источник дефекта локализован прямой репродукцией в `task_contract`, а пробел resume — сравнением
  закрытых enum `plan_continuity`/`terminal_admission` с жизненным циклом item.

## Проверенные гипотезы

| Приоритет | Гипотеза | Результат |
|:--|:--|:--|
| H1 | Prose-gate не связан с машинным authority contract. | **Подтверждено:** prose=true, bundle paths пусты, compiler=`routine/granted`. |
| H2 | Явный owner `plan-run` не имеет нормативного правила materialization в plan-native grant. | **Подтверждено:** команда наследует provider-attested route, но `task_contract` признаёт owner-gate только при явно переданном `protected_transition` и позднем committed `[OWNER-GRANT:*]`. |
| H3 | Calendar/external-state pause ошибочно сводится к owner wait. | **Подтверждено кодом:** закрытые enum содержат `waiting-owner`, но не `waiting-external`/`resume-at`. |
| H4 | Это только неверная интерпретация агента при достаточном machine contract. | **Опровергнуто:** два детерминированных repro дают тот же разрыв. |

## Корневая причина

`task_contract.build()` рассматривает обычный item carrier как достаточный источник routine
authority. Защищённая ветка появляется только когда внешний caller уже знает и передаёт exact
`protected_transition={gate_id, branch, scope}`; затем `_resolve_authority()` ищет в item marker
`[OWNER-GRANT:*]`, Decision Log и repository-owner message. Ни bundle, ни compiler не обязаны
сопоставить естественно-языковое «только после durable owner authorization» с этим механизмом.

Одновременно `plan-run` требует provider-attested route/run receipt, но не определяет, является
ли точный owner invocation исходным owner message и как безопасно материализовать его finite scope.
Поэтому у адаптера остаются два плохих варианта: повторно спрашивать уже выразившего намерение
владельца либо молча считать item routine.

После старта долгого gate возникает второй разрыв. `plan_lifecycle` может выбрать семантическое
`waiting`, но `plan_continuity` и terminal lease имеют только `waiting-owner`. Нет typed carrier с
`resume_at`, fingerprint окружения и ссылкой на незавершённое observation window. 72-часовой item
нельзя корректно начать сейчас и продолжить после календарной границы, не изображая новый owner
gate или новый независимый run.

## Ожидаемый контракт

1. Linter/compiler должен fail closed кодом наподобие `AUTHORITY_CONTRACT_GAP`, если item prose
   объявляет owner authorization, а item/bundle не содержит однозначного machine-readable gate.
   Тихий результат `routine/granted` для такого carrier недопустим.
2. Точный provider-attested owner invocation может быть входом для materialization grant, но только
   когда он связывает один plan/item и его уже объявленный finite scope. Он не расширяет Files,
   окружения, release/fleet authority и не разрешает необъявленное irreversible действие.
3. Materialization должна создать проверяемый plan-native carrier с provenance исходной owner
   реплики до защищённой product mutation. Свободный текст агента и caller kwargs не являются
   authority.
4. Authority wait и external/calendar wait должны быть разными typed состояниями. Для второго
   нужны как минимум `reason`, `resume_at`, observation/evidence fingerprint, runnable-after
   predicate и exact continuation; повторная авторизация владельца без изменения scope не нужна.
5. `plan-run` обязан после owner invocation автономно пройти read-only preflight. Реальный fail
   окружения фиксируется как `NO-GO`/repair evidence, а не превращается задним числом в вопрос
   «можно ли запускать?».

## Набросок реализации после второго замера

1. Добавить явное authority поле в item/bundle schema и `plan_lint`; не пытаться распознавать
   произвольную prose регулярным выражением как постоянное решение. Для migration diagnostics
   допустим узкий warning по известным формулировкам.
2. В provider adapter добавить builder owner-invocation evidence → plan-native owner message →
   exact Decision Log grant. Builder принимает только item-declared gate/scope и fail closed при
   любом расхождении.
3. Научить `task_contract.build()` различать routine item и объявленный protected transition без
   знания caller'а. `protected_transition` остаётся запросом на конкретную ветку, но не единственным
   способом обнаружить существование gate.
4. Расширить `plan_continuity`, соответствующие JSON Schema и `terminal_admission` состоянием
   `waiting-external` (или более общим typed pause) с `resume_at` и checkpoint. Обновить renderer и
   `plan_delivery`, не добавляя свободных provider-specific решений.
5. Синхронизировать command canon `plan-run`/`plan-exec` и `plan-protocol` skill: exact owner launch
   считается намерением исполнить item, но не доказательством неограниченной production authority;
   вторичный вопрос допустим только при реально невыводимом scope/product decision.

## Регрессионная приёмка

- Fixture по форме Agelto P4.3: prose требует durable authorization, machine gate отсутствует —
  lint/build возвращает один стабильный `AUTHORITY_CONTRACT_GAP`, не `routine/granted`.
- Тот же fixture с exact owner invocation и plan-declared finite scope — grant материализуется и
  допускает только этот item/scope; altered item, branch, scope, actor или revoked grant закрыты.
- Запуск без owner invocation не получает authority из имени `Approval Owner`, route metadata или
  свободного текста исполнителя.
- Calendar fixture стартует observation один раз, до `resume_at` даёт typed nonterminal pause без
  owner questionnaire, после `resume_at` продолжает тот же evidence chain и допускает терминал
  только с полным окном.
- Production preflight failure даёт честный `NO-GO` и repair continuation; никакой тест не подменяет
  72 часа fixture clock advance без сохранённого start/end evidence.
- Старые routine items, существующие exact `[OWNER-GRANT:*]` grants, revocation и fail-closed
  authority tests остаются GREEN.

## Границы

- Не вводить глобальное правило «любой `$ task:plan-run` разрешает production/release».
- Не выводить секреты, target credentials, fleet scope или destructive action из route evidence.
- Не считать local/staging прогон эквивалентом production observation, если Acceptance требует
  production.
- Не ослаблять Decision Log continuity, revocation или owner-message provenance.
- Не маскировать отсутствие окружения синтетическим GREEN и не закрывать calendar-gated item до
  фактического конца окна.
