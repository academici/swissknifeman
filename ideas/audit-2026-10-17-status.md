# Идея: что осталось от аудита 2026-10-17 и почему

Статус: идея, не реализовано. Источник: полный аудит репозитория от 2026-10-17 (локальный файл, в git не входит) и его
раздел «Статус выполнения». Сделанное описано в `CHANGELOG.md [Unreleased]` и в коммитах «аудит 2026-10-17»; здесь только
то, что отложено, с причиной и рекомендацией. Пока нет триггера, ничего из этого не строится.

## Закрыто в последнем проходе

- типизация: `workspace` и `brain` без ошибок pyright (`scripts/typecheck.sh`, ручной шаг, pyright не закреплён по версии);
- planner: две реальные ошибки по `None` исправлены (пустой `--project`, нечитаемый `--reviewer`), остальные срабатывания
  pyright ложные (см. «Pyright для planner, orch, gui»);
- ограничения размера в контрактах `event`, `plugin-request`, `plugin-response`, gui `run-api`, `stream`, `terminal`,
  `view-data`;
- обработчики Codex/Grok: команда хука берёт самый внешний репозиторий с обработчиком, а не ближайший;
- `orch conduct prune --older-than DAYS` (по умолчанию сухой прогон).

## Отложено

### `SkmError` вместо `die`/`sys.exit` в harness, maind, skiller, analyst
Причина: крупный рефакторинг по четырём модулям, не меняющий поведение; риск регрессий в CLI-кодах возврата выше пользы
сейчас. Рекомендация: отдельный пункт плана по одному модулю за раз, начиная с harness (больше всего `die`), с тестами
кодов возврата до правки.

### Общий движок doctor и `aicore.util.git`
Причина: дубли есть, но каждый doctor проверяет своё; общий движок без второго потребителя — спекулятивная машинерия.
Рекомендация: выделять, когда третий модуль потребует тот же каркас проверок.

### Обработчики `lifecycle.py` как реальные модули, а не строки
Причина: обработчики сейчас рендерятся из строк и защищены golden-генератором `harness-hook-handlers`, дрейф закрыт.
Перенос в модули меняет способ поставки файлов потребителям (копия одного файла превращается в пакет). Рекомендация:
делать вместе с решением о том, как обработчики поставляются потребителям.

### Замена 87 копий regex на `$ref` и `pattern_of()`
Причина: массовая правка контрактов, каждый `schema compat` даёт предупреждения; польза — меньше дрейфа, срочности нет.
Рекомендация: переносить по семействам при их плановом изменении, `common` уже содержит `sha256_hex`,
`sha256_prefixed`, `version_dir`.

### Примеры для 85 контрактов без них
Причина: объём; контракты без примеров не ломаются. Рекомендация: добавлять примеры в тот же коммит, который меняет
контракт; для остальных — один пункт плана на модуль (orch и harness первыми).

### Закрепление upstream-скиллов на SHA
Причина: решение о политике обновления upstream принадлежит владельцу (закрепить — значит вручную поднимать версии).
Рекомендация: закрепить по SHA и поднимать версии осознанно, с просмотром diff до принятия.

### Нормализация путей домашнего каталога в `plans/**/artifacts`
Причина: файлы — исторические записи выполненных планов; правка меняет их хеши в журналах. Рекомендация: не править
записи, а не допускать абсолютные пути в новых артефактах (проверка в `public-hygiene.py` для новых файлов).

### Привязка токена памяти к scope на стороне демона
Причина: демон agentmemory внешний, граница за пределами репозитория. Рекомендация: сообщить апстриму; пока действуют
обязательный секрет при LAN-bind и аудит записей в `global`.

### Команда `maind memory promote`
Причина: нужна политика, кто и когда переносит запись из проекта в `global`; решение владельца.

### Компактирование журнала событий aicore
Причина: меняет смещения доставки подписчиков, требует ADR и решения владельца. `conduct prune` журнал не трогает.
Рекомендация: ADR с вариантами (усечение по возрасту со сдвигом смещений либо сегментирование).

### `direction` для смешанных семейств контрактов
Причина: у семейств, где один контракт и входной, и выходной, `direction` задаётся неоднозначно.
Рекомендация: разделять такие контракты на входной и выходной при их следующем изменении.

### Pyright для planner, orch, gui
Причина: известный долг. Планировщик: 138 ошибок, orch: 88, gui: 77 (из них 33 — нет `starlette`, `anyio`, `uvicorn` в
окружении проверки). Срабатывания по `Optional` у planner в основном ложные: сужение типа через `isinstance(x.get(...), dict)`
pyright не видит, а `settings.for_root(...)` не аннотирован (результат без типа). Рекомендация: сначала аннотировать
`settings.for_root` и тип события журнала (`store.log_lines`) (проверить, сколько это снимет), затем включать модули в `pyrightconfig.json` по одному.

### TypedDict из схем и миграция maind, skiller, analyst на pyright
Причина: нужен генератор из JSON Schema; без него TypedDict вручную расходятся со схемами. Рекомендация: после
сокращения долга planner и orch.

### Отклонения от задания, которые стоит знать
- `conduct prune` удаляет только с `--apply`; `--dry-run` принят как явное указание и совпадает с умолчанием.
- Типизация в CI не подключена: pyright не закреплён по версии (`scripts/ci-matrix.py` закрепляет линтер).
- Артефакты `orch-artifacts` — это закоммиченные записи; после `prune --apply` удаление видно в `git status`.
