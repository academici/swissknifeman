# P4 — Канон планов: репо-дом, имена, дом workflow-скриптов

## Phase Context

Фаза правит SSOT плановой системы — скилл `general/plan-protocol` и валидатор
`packages/task/lib/task/plan_lint.py` — ОДНИМ заходом, чтобы не перекатывать канон дважды (D2).
Сливаются две спеки: `roadmap/plan-homes.md` (репо-дом планов по умолчанию вместо vault; ось
видимости `visibility:` для публичных OSS-репо; канон имён `<PROJECT>[-<трек>]` без v2/W2-суффиксов
с полем `supersedes:` и архивом предшественника; доставка схемы компактной скилл-картой ≤50 строк
+ секции CLAUDE.md обоих контекстов) и `roadmap/workflow-craft.md` ч.1.6 (единственный дом
workflow-скриптов — `plans/<ID>/workflows/`, имя `wf-<plan-id-lower>-<назначение>.js`, наличие
скрипта — часть DoR фазы исполнения массивного плана).
Оба изменения — публичный контракт протокола для всей экосистемы, потому дизайн-items идут на
opus/high (см. `## 3. Routing`), а `plan_lint` и скилл правятся СИНХРОННО: расхождение валидатора
и SSOT — известный класс дефекта (CLAUDE.md пакета task).
**Формат имени плана — `<ГГГГ>.<ММ>.<ДД>-<КОДОВОЕ-ИМЯ>`** (напр. `2026.07.10-SETTINGS-DOCTOR`):
планы хранятся постоянно и копятся, датовый префикс даёт хронологическую сортировку `plans/` и
ориентацию «когда» без чтения Meta (D16, владелец 2026-07-10). Регулярка ID заводится в
`plan_lint.py` (сейчас её там НЕТ — паттерн живёт только в §2 скилла) и расширяется в
`SKILL.ru.md` → `SKILL.md`; старый паттерн `[A-Z][A-Z0-9-]+` остаётся валидным.
Миграция только вперёд: существующие планы не переезжают и не переименовываются, терминальные
уходят в архив по мере закрытия. Фаза закрыта, когда канон описан, линтер его проверяет, а карта
раскатана.

> СКЕЛЕТ — не детализирован, разворачивается /task:plan-design SKM-ROADMAP-005 P4

## DoR (Definition of Ready)

Прогоняется `/task:plan-design` перед выдачей «фаза готова»; `plan-audit` сверяет пост-фактум.

- [ ] Все `[NEEDS CLARIFICATION]` сняты (0 маркеров в фазе).
- [ ] Scope Included / Scope Excluded фазы заполнены (эквивалент Goals/Non-Goals).
- [ ] Alternatives для несущих решений зафиксированы в D-логе.
- [ ] Open Questions разнесены по статусам `open-questions.md`.
- [ ] Несущие факты несут RAG-маркеры (`RAG:✅ …` / `[UNVERIFIED]`).
