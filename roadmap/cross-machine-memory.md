# Roadmap: межкомпьютерная синхронизация памяти mAInd

**Статус:** ⛔ Deferred by decision (D12, план `2026.07.12-CONTEXT-ECONOMY` P7.2, 2026-07-12) —
роадмап-стаб вместо реализации; в релиз машинного bootstrap (P7) не входит.

**Дом (при реализации):** `packages/maind` (`lib/maind/memory.py` + `provision/service.py`,
`provision/sync.py`) — расширение оркестрации демона, не новый пакет.

## Проблема

`bootstrap-machine.sh` (P7.1) поднимает на новой машине **новый, пустой** локальный демон
agent-memory (`maind service install`). Накопленная память (факты/контекст, `state_store.db`)
с других машин не переносится — вторая машина/участник команды стартует с нуля. Это осознанный
пробел P7, не баг: нужен явный дизайн синхронизации, а не «чуть-чуть докрутить» попутно
(Code Guidance P7.2).

## Почему это НЕ shared-папка (анти-паттерн, зафиксировать явным запретом)

**Расшаривание каталога с живым стором agent-memory (`state_store.db`, бинарный SQLite/индекс)
через Syncthing/Dropbox/NFS/аналоги — ЗАПРЕЩЕНО.** RAG-подтверждение
(2026-07-12, `plans/2026.07.12-CONTEXT-ECONOMY/findings/P0-rag-bootstrap-memory-sync.md`):
file-level sync не транзакционен, конкурентная запись двух машин портит SQLite/бинарные индексы
без предупреждения (silent corruption) — риск теряется до обнаружения, восстановление дороже,
чем отсутствие синхронизации вообще.

## Два безопасных варианта (D12)

1. **Демон на одном хосте (always-on) + доступ по Tailscale/LAN.**
   Один физический/виртуальный узел (NAS, домашний сервер, всегда включённая машина) держит
   единственный живой демон agent-memory; остальные машины подключаются к нему по сети
   (Tailscale VPN или LAN) как MCP-клиенты — не поднимают собственный локальный демон.
   - Плюсы: единственный писатель → нет конкурентной записи, чистая семантика, экономия
     дублирования памяти между машинами.
   - Минусы: офлайн-машина (нет сети до хоста) теряет доступ к памяти; требует держать хост
     живым; сетевая экспозиция демона — нужен контур доверия (Tailscale ACL / firewall).

2. **Export/import событий (event-log).**
   Каждая машина держит свой локальный демон; синхронизация — через append-only снапшоты/
   экспорты (JSON event-log) в обычной синк-папке (безопасно для append-only файлов, в отличие
   от живого бинарного стора), конфликты разрешаются LWW (last-write-wins) или CRDT-подобной
   логикой мержа при импорте.
   - Плюсы: работает офлайн (экспорт/импорт асинхронны), не требует всегда включённого хоста.
   - Минусы: требует реализации протокола экспорта/импорта + конфликт-резолвера в `maind`;
     задержка синхронизации (не realtime); риск логической, не файловой, гонки при мерже.

**Оба варианта не реализованы.** Выбор между ними — по факту появления второй постоянной
машины/команды с реальной потребностью в общей памяти (см. критерий активации ниже), не заранее.

## Критерий активации

Появление **второй постоянно используемой машины у одного оператора** (не разовый bootstrap
чистого контейнера) **или команды из ≥2 человек**, которым реально нужна общая память между
своими локальными демонами (а не только общий `ns:<группа>`-scope на едином хосте maind, который
уже работает сегодня без этого стаба). До этого момента реализация опережала бы измеренную
потребность (философия репо: «Спекулятивное — в `roadmap/`. Фичу внедряем по факту измеренной
проблемы»).
