# Разработка через тестирование (Test-Driven Development)

## Философия

**Базовый принцип**: тесты должны проверять поведение через публичные интерфейсы, а не детали реализации. Код может полностью измениться — тесты не должны.

**Хорошие тесты** написаны в интеграционном стиле: они прогоняют реальные пути исполнения кода через публичные API. Они описывают, _что_ система делает, а не _как_ она это делает. Хороший тест читается как спецификация — «пользователь может оформить заказ с валидной корзиной» точно сообщает, какая возможность существует. Такие тесты переживают рефакторинги, потому что им безразлична внутренняя структура.

**Плохие тесты** связаны с реализацией. Они мокают внутренних коллабораторов, тестируют приватные методы или проверяют результат внешними средствами (например, напрямую запрашивают базу данных вместо использования интерфейса). Тревожный признак: ваш тест ломается при рефакторинге, хотя поведение не изменилось. Если вы переименовываете внутреннюю функцию и тесты падают — эти тесты проверяли реализацию, а не поведение.

Примеры см. в [tests.md](snippets/tests.md), а рекомендации по мокам — в [mocking.md](snippets/mocking.md).

## Антипаттерн: горизонтальные срезы

**НЕ пишите сначала все тесты, а потом всю реализацию.** Это «горизонтальная нарезка» — когда RED трактуется как «написать все тесты», а GREEN — как «написать весь код».

Это порождает **дрянные тесты**:

- Тесты, написанные пачкой, проверяют _воображаемое_ поведение, а не _фактическое_
- Вы в итоге тестируете _форму_ вещей (структуры данных, сигнатуры функций), а не поведение, видимое пользователю
- Тесты становятся нечувствительны к реальным изменениям — проходят, когда поведение сломано, и падают, когда с поведением всё в порядке
- Вы обгоняете свет своих фар, фиксируя структуру тестов до того, как поняли реализацию

**Правильный подход**: вертикальные срезы через tracer bullets («трассирующие пули»). Один тест → одна реализация → повтор. Каждый тест отвечает на то, что вы узнали из предыдущего цикла. Поскольку вы только что написали код, вы точно знаете, какое поведение важно и как его проверить.

```
НЕВЕРНО (горизонтально):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

ВЕРНО (вертикально):
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## Рабочий процесс

### 1. Планирование

При изучении кодовой базы прочитайте `CONTEXT.md` (если он есть), чтобы имена тестов и словарь интерфейса совпадали с доменным языком проекта, и соблюдайте ADR в той области, которую вы затрагиваете.

Прежде чем писать какой-либо код:

- [ ] Согласуйте с пользователем, какие изменения интерфейса нужны
- [ ] Согласуйте с пользователем, какие виды поведения тестировать (расставьте приоритеты)
- [ ] Выявите возможности для глубоких модулей (маленький интерфейс, глубокая реализация) — запустите скилл `codebase-design` ради словаря и проверок тестируемости
- [ ] Перечислите виды поведения для тестирования (не шаги реализации)
- [ ] Получите одобрение плана у пользователя

Спросите: «Как должен выглядеть публичный интерфейс? Какие виды поведения важнее всего протестировать?»

**Нельзя протестировать всё.** Согласуйте с пользователем, какие именно виды поведения важнее всего. Сосредоточьте усилия по тестированию на критических путях и сложной логике, а не на каждом возможном краевом случае.

### 2. Трассирующая пуля (Tracer Bullet)

Напишите ОДИН тест, который подтверждает ОДНУ вещь про систему:

```
RED:   Написать тест для первого поведения → тест падает
GREEN: Написать минимальный код, чтобы он прошёл → тест проходит
```

Это ваша трассирующая пуля — она доказывает, что путь работает от начала до конца.

### 3. Инкрементальный цикл

Для каждого оставшегося поведения:

```
RED:   Написать следующий тест → падает
GREEN: Минимальный код, чтобы прошёл → проходит
```

Правила:

- Один тест за раз
- Только столько кода, сколько нужно для прохождения текущего теста
- Не предвосхищайте будущие тесты
- Держите тесты сфокусированными на наблюдаемом поведении

### 4. Рефакторинг

После того как все тесты прошли, ищите [кандидатов на рефакторинг](snippets/refactoring.md):

- [ ] Вынесите дублирование
- [ ] Углубите модули (спрячьте сложность за простыми интерфейсами)
- [ ] Применяйте принципы SOLID там, где это естественно
- [ ] Подумайте, что новый код раскрывает про существующий код
- [ ] Прогоняйте тесты после каждого шага рефакторинга

**Никогда не рефакторьте в состоянии RED.** Сначала доберитесь до GREEN.

## Чек-лист на каждый цикл

```
[ ] Тест описывает поведение, а не реализацию
[ ] Тест использует только публичный интерфейс
[ ] Тест пережил бы внутренний рефакторинг
[ ] Код минимален для этого теста
[ ] Не добавлено спекулятивных фич
```
