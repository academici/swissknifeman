## §1. Карта распространения: что физически меняется у потребителей и когда

| Канал | Носитель у потребителя | Когда доезжает изменение | Эффект merge |
|:--|:--|:--|:--|
| **CLI пяти команд** | симлинки `~/.local/bin/{swissknifeman,skiller,harness,maind,analyst}` → файлы ОСНОВНОГО рабочего дерева | **мгновенно в момент коммита в `main`** | ⚠️ переключение инструмента всего флота |
| **MCP-серверы хаба** | `.mcp.json` онбордженных проектов с зашитыми путями в основное дерево | мгновенно (тот же путь, новый код) | ⚠️ то же |
| **Скиллы connect-канала** | кэш плагинов Claude Code, локальный marketplace, auto-update ВЫКЛЮЧЕН | только по `/plugin marketplace update` + `/reload-plugins` в проекте | нет |
| **Скиллы vendor-канала** | физические копии в репо проекта + `skills-lock.json` | только по `skiller sync` | нет |
| **agent-packs** | установленные копии в `.claude/` проекта + `agent-pack.lock.json` | только по `agent-packs upgrade` | нет |

Источники: строки 1–2 — замер P0.1 (`ls -la ~/.local/bin` — пять симлинков в основное дерево)
и правило корневого `CLAUDE.md` «пути maind зашиты в `.mcp.json` онбордженных — не ломать»;
строка 3 — `findings/06` Ф23 (first-party); строки 4–5 — `packages/skiller/CLAUDE.md`
(«vendor — физический перенос», lock-файлы) и договорённость плана про `agent-packs upgrade`
(`plan.md` §5 D-заметка к P4.4).

**Два вывода, несущих для фазы.**

1. **Точка переключения флота — MERGE, а не реинсталл.** Реинсталл `install.sh` лишь
   переставляет симлинки на те же файлы (и прогоняет пакетную пост-настройку); сами файлы
   меняются в момент, когда `main` получает коммит. Значит смоук-проверка флота обязана идти
   НЕМЕДЛЕННО после merge, а якорь отката — фиксироваться ДО него.
2. **«Флот получил новые правила» — НЕ то, что доказывает эта фаза.** Скиллы, паки и
   инструкции доезжают только явными командами на стороне проекта. P5 доказывает, что контур
   ЖИВ и совместим; раскатка — отдельная работа с собственным гейтом (уже в `deferred`).

## §2. Инвентарь гейтов: что даст CI и чем он заменяется до push

Плана касается неприятная асимметрия: гейты монорепо живут в GitHub Actions и триггерятся
**push/pull_request** (`.github/workflows/*.yml` — секции `on:`), а фаза сознательно
останавливается ДО push (граница наружу — гейт владельца, контракт-блок P5). Значит перед
merge гейты обязаны быть прогнаны локально — иначе «зелёное» состояние ветки не проверено
ничем, кроме дисциплины исполнителей отдельных items.

| CI-job | Что гоняет | Локальный эквивалент до merge |
|:--|:--|:--|
| `validate.yml` | `validate.sh` пакетов skiller · harness · maind | те же три + **`analyst` и `task`** (см. пробел ниже) |
| `test.yml` | `test.sh` трёх пакетов, `core/tests`, ruff (`F,B`, пин `0.15.19`) на матрице python 3.9–3.13 | те же на ОДНОЙ локальной версии python (замер: 3.12.3); матрица — только в CI |
| `hygiene.yml` | `docs-impact.py` (+тест), `status-check.py docs/status.md` (+тест), `public-hygiene.py` (+тест) | те же команды дословно; `docs-impact` — с `--base main --head HEAD` |
| `hygiene.yml` (после P2.5) | `provider-docs.py --check` + `test-provider-docs.py` | те же |
| `docs.yml` | сборка VitePress на push в `main` | вне скоупа фазы (публикация — граница наружу) |
| `release-tag` job | `verify-tag.py` на теге | вне скоупа (тег — гейт владельца) |

**Измеренный пробел CI (не чинится этой фазой):** `validate.yml` и `test.yml` НЕ зовут
`packages/analyst/scripts/validate.sh` и `packages/task/scripts/validate.sh`, хотя оба
существуют — а `plan-lint` по всему `plans/` живёт именно внутри `task/validate.sh`
(`packages/task/scripts/validate.sh` [5/5]). То есть плановая дисциплина монорепо сегодня
машинно не проверяется ни на одном PR. Компенсация в рамках фазы — прогон всех ПЯТИ
`validate.sh` до merge; расширение самих workflow — чужой предмет (→ `open-questions.md` OQ-9).

**Честная граница локального прогона:** одна версия python против матрицы из пяти и
отсутствие изоляции runner'а. Локальное «зелено» НЕ равно «CI зелёный» и не должно так
называться в отчёте; окончательную проверку даёт push, который в этот план не входит.

## §3. Пробел матрицы зрелости `docs/status.md` (обязательство без владельца)

Замер: `docs/status.md` — матрица «Пакет | Возможность | Зрелость | Evidence / boundary»,
22 строки, словарь зрелости закрыт пятью значениями (`available` · `experimental` ·
`behind-gate` · `disabled` · `superseded`, синхронизирован с `plan-protocol` § Capability
maturity), гейт — `scripts/status-check.py`, шаг `status-check` в job `hygiene`.

Замер по плану: `grep -rn "status\.md\|status-check" phases/*.md plan.md` — **ни одного
совпадения**. То есть план производит новые возможности флота, но ни один его item не
обязуется отразить их в матрице зрелости, при живом CI-гейте на этот файл.

Возможности, произведённые фазами P1–P4, которым нужна строка (или правка существующей):

| Возможность | Производитель | Замечание к зрелости |
|:--|:--|:--|
| `harness instructions <plan\|check\|adopt\|apply\|repair>` | P1.4 (реализация) + P1.5 (живая транзакция) | принятие — owner-gated действие: `available` только с evidence живого прогона |
| Codex lifecycle/context поверхности (`harness hooks --provider codex --surfaces …`) | P2.2 (наблюдатели), P2.3 (гейты) | round-trip с живым Codex CLI в скоуп не входил (D3) — граница обязана быть названа в Evidence |
| Гейт свежести канона каркаса | P3.3 | доказан только негативным прогоном (обязателен по его Code Guidance) |
| `skiller budget --provider` (вторая модель бюджета обнаружения) | P3.4 | гейт перебора — WARN по D26, это `behind-gate`/`experimental`-класс, а не «работает» |
| Политика исполнения + валидатор + шаг `[9/9]` | P4.3 (носитель), P4.4 (приземление) | потребитель политики — грамматика PLAN; принуждение не автоматическое |

**Вердикт:** обязательство назначается ОДНОМУ item'у фазы P5 (пред-мердж закрытие), а не
распределяется по четырём уже детализированным фазам. Причины: (1) значение зрелости —
суждение о СДАННОМ состоянии, и оно знаемо только когда все четыре фазы терминальны;
(2) распределение потребовало бы реопена четырёх фаз, прошедших DoR; (3) сам гейт
(`status-check`) срабатывает на merge/push, то есть его естественный владелец — фаза
возврата. Риск обратной стороны — «матрица пишется по памяти плана» — снимается требованием
прогонять команду Evidence каждой затронутой строки на merge-коммите (см. §7 R6).

## §4. Почему фаза раскладывается на ТРИ item'а

Скелет нёс два (`merge` · `реинсталл+верификация`). Замер показал, что между ними живут два
разных рабочих дерева и одна необратимая граница, а перед ними — целый пласт работы, которая
обязана быть закончена ДО merge и физически исполняется в дереве изоляции.

| Item | Дерево исполнения | Природа | Своя машинная Validation |
|:--|:--|:--|:--|
| P5.1 — пред-мердж закрытие | дерево изоляции (ветка) | контент + прогон гейтов + снимок «до» | пять `validate.sh`, три root-гейта, `plan-lint`, непустые файлы снимка |
| P5.2 — merge | ОСНОВНОЕ дерево | необратимая граница | `git diff --stat main <ветка>` пуст, смоук старого контура зелёный |
| P5.3 — реинсталл, дельта, снятие | ОСНОВНОЕ дерево | приёмка + уборка | дельта парного прогона, отсутствие worktree и bin-dir |

Смена рабочего дерева между item'ами — естественная граница закрытия (два коммита, handoff,
`plan-lint` — всё это делается в конкретном дереве), а склейка «закрытие релиза + merge» в
один item спрятала бы гейт: исполнитель, уже стоящий на merge, дописывал бы CHANGELOG и
матрицу зрелости задним числом, под давлением «осталось только слить».

## §5. Дисциплина чисел по чужому корню: приёмка — только ДЕЛЬТА парного прогона

Флот (`~/.swissknifeman/projects.json`, `~/.maind/**`, состояние 25 проектов) — **чужой
корень** относительно этого репо: он живёт своей жизнью и меняется между прогонами.
`plan-protocol` §8 прямо запрещает доказывать регрессию/совместимость абсолютными числами
по такому корню: доказательство — пара прогонов на ОДНОМ снимке чужого дерева, опубликованная
как дельта диагностических множеств.

Отсюда конструкция приёмки М10:

- **Снимок «ДО» берётся в P5.1**, ПРЕЖНИМ контуром (без префикса PATH), и коммитится как
  артефакт плана — переснимать его после merge ЗАПРЕЩЕНО (иначе дельта доказывает себя).
- **Снимок «ПОСЛЕ» берётся в P5.3**, после реинсталла, теми же тремя командами.
- Публикуется **дельта**: `swissknifeman doctor` (построчно), `maind projects status --json`
  (по структурным ключам), `harness doctor --provider-audit --json` (`green` + диагностики).
- **Волатильные поля называются поимённо и исключаются из сравнения**: живость демона памяти
  (`memory.running`/URL), счётчики графа (`nodes`/`edges`), счётчики уроков analyst, время
  прогона. Всё, что не в этом перечне, обязано совпасть — расхождение либо объяснено
  фактом плана, либо это находка.

## §6. Якоря отката и что действительно необратимо

| Шаг | Обратимость | Якорь |
|:--|:--|:--|
| merge в `main` (локальный) | обратим | SHA `main` ДО merge, записанный в Completion Notes P5.2 и в процедуру |
| реинсталл `install.sh` | обратим | повторный прогон из основного дерева восстанавливает те же симлинки |
| снятие worktree и bin-dir | обратим (процедура P0.1 создаёт заново), но ЛОКАЛЬНО дорого | §«Создание» процедуры |
| **push/PR/тег** | практически необратим (публичная история) | **вне плана — гейт владельца** |

Отсюда порядок: якорь → merge → смоук → (при провале — откат по якорю) → реинсталл →
дельта → и только потом уборка. Ветка `next/harness-agnostic` после merge **не удаляется**:
пока `main` не отправлен наружу, ветка — второй, независимый от reflog якорь отката, и её
удаление ради «чистоты» меняет цену ошибки без единой выгоды.

## §7. Pre-mortem фазы P5 (протокол Klein): «через полгода это провалилось — почему»

Фаза трогает ядро экосистемы и живой инструмент 25 проектов — pre-mortem обязателен
(`plan-protocol` §7, high-stakes). Причины записаны независимо, затем сгруппированы;
у каждой — mitigation с адресом в item'е.

| # | Как провалилось | Mitigation (адрес) |
|:--|:--|:--|
| **R1** | Merge упёрся в чужую правку: владелец параллельно работал в основном дереве, исполнитель «разрулил конфликт по ходу» и внёс в `main` смесь двух работ | P5.2: предусловие «рабочее дерево основного каталога чистое» проверяется командой ДО merge; грязное дерево или конфликт → СТОП + эскалация, не разрешение конфликта своими руками |
| **R2** | «Локально зелено» выдано за «CI зелёный»: реальный прогон был на одной версии python без ruff-пина, после push CI покраснел, а план уже закрыт | P5.1: в отчёте называются версия python и перечень НЕ воспроизведённого (матрица 3.9–3.13, изоляция runner'а); формулировка «CI зелёный» запрещена |
| **R3** | Приёмка флота оказалась фиктивной: `doctor` гоняли из активированного изолированного контура, то есть проверяли то, чем флот не пользуется | P5.1/P5.3: команды прогоняются БЕЗ префикса PATH, и в отчёт вклеивается резолв симлинка (`readlink -f "$(command -v swissknifeman)"`) как доказательство, каким именно контуром получен вывод |
| **R4** | Worktree сняли раньше, чем основное дерево доказано рабочим, и откат стал ручной археологией | P5.3: снятие — ПОСЛЕДНИЙ шаг, после зелёной дельты; ветка сохраняется (§6) |
| **R5** | Дельта не сошлась — базлайн пересняли после merge, и приёмка стала тавтологией | P5.1: снимок «ДО» коммитится артефактом; P5.3 Code Guidance: пересъём базлайна = подгонка результата, запрещена, расхождение объясняется или эскалируется |
| **R6** | CHANGELOG и матрица зрелости написаны «по плану», а не по дереву: строки описывают то, что план ОБЕЩАЛ, а не то, что сдано | P5.1: каждая затронутая строка `docs/status.md` несёт Evidence-команду, фактически прогнанную, с вклеенным выводом; зрелость выбирается из закрытого словаря, «есть команда» ≠ `available` |
| **R7** | Фаза превратилась в «дочинить всё, что забыли четыре фазы»: красный гейт лечили правкой кода прямо здесь | P5.1 Code Guidance: красный гейт, требующий правки КОДА, — эскалация в фазу-владельца (§10, триггер «rule conflict»/«unclear acceptance»), а не работа этого item'а; P5.1 закрывает только релизные носители |
