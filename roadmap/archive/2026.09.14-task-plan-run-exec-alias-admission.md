# Roadmap: `plan-run` не должен блокироваться как несовместимый с `plan-exec`

**Статус:** ✅ реализовано и локально доставлено — Task 0.17.0; parser/lint/native regressions GREEN.
**Критерий запуска:** владелец уже приоритизировал исправление; реализовать как ограниченную
Task-правку после проверки паритета shared contract, CLI/adapters и lint.

## Наблюдаемый инцидент

В `flexcrm` владелец запустил ровно тот handoff, который был сгенерирован для нового item:

```text
$ task:plan-run FLEX-2 P14.1
```

`FLEX-2` объявляет для P14.1 `Exec = plan-run`, а `P14.md` и `handoff.md` называют ту же
команду. Маршрут сессии, Docker pre-flight, тестовая БД и schema gate были GREEN. До product
write admission остановился на:

```text
TaskContractBuildError: routing: Routing: line 82: invalid Exec 'plan-run'
```

Причина измерима в самом Task: пользовательская документация описывает `plan-run` как маршрут,
который выполняет canonical lifecycle `plan-exec`, но `_EXECUTABLE_ROUTING_EXEC_VALUES` и
`plan_lint` принимают только `plan-exec | manual | plan-design`.

## Ошибка оператора

После отказа оператор неверно назвал решение «корректировкой Routing/Task runtime», хотя
новосессионная команда уже была верно выбрана планом: `task:plan-run`. Нельзя перекладывать
несовместимость внутреннего enum на владельца или заставлять его вручную менять эквивалентную
команду. Handoff должен оставаться исполнимым, если он согласован с Routing и adapter-ом.

## Цель

Сделать `plan-run` и `plan-exec` совместимыми там, где первый лишь наследует маршрут и
делегирует общий lifecycle второму. Admission должен проверять смысл операции, а не отказывать
из-за двух имён одного execution path.

Это не отменяет fail-closed границы для реальных различий: owner authority, scope, зависимостей,
provider-attested model/effort, capabilities, evidence integrity и необратимых действий.

## Предлагаемое решение

1. Ввести один канонический resolver Routing Exec, который нормализует `plan-run` в execution
   lifecycle `plan-exec`, сохраняя исходное имя команды для provider route evidence и delivery.
2. Использовать resolver во всех потребителях: `task_contract.compile_batch_routing`,
   `plan_lint`, plan-protocol/docs и Codex/Claude adapter projections. Не поддерживать отдельные
   списки допустимых значений.
3. Для старых и новых планов принять `Exec = plan-run` как валидное объявление. При необходимости
   generated view показывает canonical lifecycle рядом с исходной командой, но не требует
   ручного переписывания готового handoff.
4. Если команда и Exec действительно неэквивалентны, вернуть диагностичный отказ с двумя
   значениями и конкретным способом исправления; не маскировать его общим `invalid Exec`.

## Acceptance

- Plan с `Exec = plan-run` и handoff `$ task:plan-run <PLAN> <ITEM>` проходит batch admission,
  contract build и journal start при прочих GREEN prerequisites.
- Тот же item сохраняет точное provider route evidence для `plan-run`, а общий execution lifecycle
  остаётся `plan-exec` без дублированной реализации.
- `plan-exec`, `manual` и `plan-design` сохраняют нынешнюю семантику; невалидные значения всё ещё
  fail closed с понятной диагностикой.
- Есть регрессионные тесты для parser/lint, batch admission и обоих provider projections.
- Документация больше не противоречит enum и generated handoff-команда не может оказаться
  неисполняемой только из-за alias mismatch.

## Границы

Не превращать admission в warning-mode и не обходить contract/authority/evidence проверки.
Не добавлять автопереключение модели или скрытую смену команды. Это узкая нормализация
эквивалентных имён на единственной границе Routing.
