# Roadmap: финальный аудит плана должен согласовать целостность и экономичные execution batch’и

**Статус:** 🔴 field evidence получен; owner подтвердил обязательный порядок, runtime-правило не внедрено.

> **Обновление 2026-10-01:** правило «детализировать весь план → общий design audit → execution»
> владелец заменил: execution допускается по фазам, whole-plan audit — только при
> `**Design Audit:** required` или по запросу (D1 задания `tasks/2026.10.01-task-lean-execution`).
> Группировка batch и класс модели как граница совместимости ниже остаются в силе.

**Критерий запуска:** зафиксирован хотя бы один готовый детализированный план, в котором
после design-finish обнаруживается одно из трёх: несогласованность между фазами/пунктами,
неэкономичное дробление совместимых пунктов на cold-start сессии либо потеря незакрытого
пункта при заявлении о завершении плана. Перед ремонтом нужен минимальный плановый срез с
Routing, фактическими model/effort, оценкой cold-start cost и terminal evidence.

**Триггер сработал 2026-09-22:** в `azguard:PLAN1` после детализации только P1 команда
`task:plan-design` записала `Next = task:plan-exec ... P1.1`, хотя P2–P7 оставались
скелетами. Это допустил действующий канон: `packages/task/commands/plan-design.md` и
`runtime/plan-protocol/references/design-mode.md` направляют уже готовую фазу в execution,
а обязательного plan-wide design gate перед первым execution не содержат. Владелец повторно
зафиксировал нормативный порядок: **детализировать весь план → выполнить один общий аудит
дизайна → только затем разрешить execution**. AzGuard handoff исправлен на design P2 как
локальный carrier; это не заменяет ремонт Task runtime.

## Проблема

Нынешняя последовательность authoring естественно проходит через общий план, фазы и
детализацию каждого пункта. После того как все пункты уже определены, появляется знание,
которого не было на ранних проходах: полный объём работ, сквозные зависимости, общие reads/
files/validation, реальная цена нового root и различия назначенных маршрутов.

Нужен обязательный завершающий проход **по целому плану**, до передачи его в исполнение. Он
должен исправить обнаруженные пробелы и согласовать данные так, чтобы план был целостным; в
том же проходе он должен рассмотреть grouping всех execution item’ов там, где это уменьшает
стоимость без потери корректности. Сейчас эти решения могут приниматься фрагментарно во время
детализации, а агент в длинном плане может не удержать полный workset и не довести часть
пунктов до явного terminal state.

## Требуемая модель

0. До детализации всех объявленных фаз `plan-design <ID> <Pn>` никогда не предлагает
   `plan-exec`/`plan-run`, даже если текущая фаза локально execution-ready. Semantic Next ведёт
   к следующей недетализированной фазе. После последней фазы Next ведёт в `design-finish`, затем
   ровно в один `plan-audit <ID> design`; execution допускается только после GREEN design audit
   и закрытия его owning corrections.
1. После детализации всех фаз `design-finish` запускает отдельный plan-wide consistency gate,
   а не только генерацию views. Он сверяет покрытие каждого `Pn.m` фазой, Routing, зависимостями,
   required reads, files, validation, deliverables, acceptance/close gates и semantic Next.
   Найденное несоответствие возвращается в owning phase/item и после исправления проход
   повторяется до согласованного снимка.
2. На согласованном снимке строится candidate grouping. Его единица — последовательный
   execution batch с доказанной экономией повторного контекста: общими prerequisite/read/file/
   validation/setup либо producer→consumer цепочкой. В оценку входят объём workset, оставшийся
   context budget и цена cold start; отдельные commits и item-close сами по себе не повод
   дробить группу.
3. Назначенный **класс модели** — жёсткая граница совместимости. Нельзя объединять рутинный
   большой пункт, оправданный на более лёгком классе, с соседним frontier/тяжёлым пунктом и
   молча поднять весь batch до дорогой модели только ради одной сессии. Такой кандидат
   остаётся раздельным, если не появилось самостоятельное доказательство, что маршрут самого
   первого пункта нужно изменить.
4. Разница только в **effort** может быть нормализована до большего effort для одной группы,
   но лишь при явном сравнении: дополнительная цена повышенного effort меньше либо оправданнее
   повторного cold start, а суммарный объём укладывается в context budget. `medium → high` не
   является автоматическим разрешением; при крупном рутинном элементе или слабой связности
   batch остаётся раздельным.
5. Финальный carrier фиксирует исходные per-item route, выбранные batch’и, причину каждого
   объединения/разделения, расчётную экономию и любое осознанное повышение effort. Изменение
   порядка возможно только при сохранении dependency/owner/irreversible границ и должно быть
   отражено в обновлённых Routing и roadmap projections.
6. План нельзя объявить design-ready или terminally complete, пока детерминированная
   coverage-проверка не сопоставит каждый declared item с одним и только одним состоянием:
   готов к исполнению в batch, выполнен/закрыт, blocked/waiting с владельцем продолжения либо
   намеренно исключён accepted decision. Сводка не заменяет эту проверку и не может «потерять»
   незакрытый пункт из-за неполного контекста агента.

## Границы

- Это не разрешение менять scope, acceptance, model class, owner gates или зависимости ради
  красивой группировки.
- Batch по-прежнему не пересекает phase audit/close, не смешивает Exec mode, не скрывает
  owner/irreversible gate и не превышает оставшийся context budget.
- `plan-run` сохраняет свой ordered workset и ready-frontier semantics: grouping не означает
  преждевременный старт downstream item’а и не отменяет item-level terminal evidence.
- Не вводить always-on полный контекст: финальный проход работает по committed structured
  carriers/индексам и обязан иметь измеренный budget verdict.

## Предполагаемое направление ремонта

1. Добавить к plan-design явный finalization state между детализацией и `design-finish`, а к
   plan-lint — детерминированные проверки полного coverage и согласованности projection’ов.
2. Вынести плановую оценку batch compatibility/cost в один shared reducer, чтобы authoring,
   lint, handoff и execution не применяли разные эвристики.
3. Сделать route coalescing двухступенчатым: hard reject при разных model class; для effort
   elevation — persisted cost/rationale verdict. При отсутствии verdict остаётся per-item или
   совместимый исходный batch.
4. Добавить regression fixtures: mixed-class adjacent items не повышаются ради grouping;
   `implementation/medium` + `implementation/high` объединяются только при положительном
   cost/context verdict; cross-phase/owner boundary разделяет batch; непокрытый или незакрытый
   item блокирует design-ready и whole-plan terminal claim.
5. Прогнать свежий field plan через полный цикл: phases → all items detailed → final audit/fixes
   → route grouping → design handoff → ordered execution/terminal reconciliation.
6. Добавить regression на наблюдённый AzGuard случай: P1 execution-ready, P2–P7 skeleton;
   `finalize-design P1` обязан выбрать design P2 и отклонить execution Next. После последней
   детализированной фазы он обязан выбрать `design-finish`, затем `audit-design`, и только
   GREEN plan-wide audit открывает первый execution item.

## Необходимые доказательства при запуске

- снимок исходного и финального Routing с каждым item и route;
- расчёт cold-start versus higher-effort cost, включая context-budget verdict;
- результаты coverage/consistency lint и список исправленных расхождений;
- journal/terminal evidence, показывающее, что каждый пункт получил terminal или typed waiting
  outcome и ни один не пропал из final claim.
