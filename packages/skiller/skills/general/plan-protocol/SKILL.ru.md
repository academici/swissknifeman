# Plan Protocol

SSOT plan-протокола экосистемы: как устроен исполняемый мастер-план, который «сильная»
frontier-класс пишет, а implementation/economy исполняет без доступа к чату планирования. Протокол фиксирует
ТОЛЬКО Axioma-специфику — схемы, гейты, маркеры, конвейеры; общие практики планирования,
которые plan mode / модель умеют сами, здесь не пересказываются.

## 1. Когда активировать

- Многофазная работа длиннее одной сессии (план переживает контекст).
- Паттерн «frontier планирует, implementation/economy исполняют».
- Вызов любого semantic command ID `task:plan-*` (design/exec/run/close/audit).

**Порог «нужен ли план» (эвристика):**

| Признаки задачи | Маршрут |
|:--|:--|
| Мелкая правка, багфикс, одиночный файл | `/task:fix` без мастер-плана |
| Фича в одном модуле, PoC, эксперимент | `/task:dev` без мастер-плана |
| Кросс-модульное; compliance (54-ФЗ/платежи/PII); >1 репо; >1 сессии | ОБЯЗАТЕЛЕН `task:plan-design` с гейтами этого протокола |

## 2. Раскладка

```text
plans/<PLAN-ID>/
├── plan.md            # мастер-план (Meta, Context, Rules, Routing, Status Board, логи)
├── phases/Pn.md       # по файлу на фазу: контекст фазы, items, phase handoff
├── handoff.md         # rolling-указатель «где мы» (перезаписывается)
├── index.md           # карта файлов + провенанс findings/research→фаза (раздел 2, опционален)
├── roadmap.md         # исполнительская карта: батчи/workflow/гейты (раздел 8; обязателен после полной детализации)
├── journal.jsonl      # append-only история исполнения item'ов, одна запись на запуск task:plan-* (раздел 2)
├── journal-exceptions.jsonl # optional append-only owner-gated exceptions для historical schema-invalid строк
├── brief/             # слой 0 «вход»: бриф владельца + дописываемые уточнения (раздел 16, ОБЯЗАТЕЛЕН)
├── findings/          # слой 1 «сырьё»: RAG-выжимки, recon, исходные документы (раздел 16)
├── research/          # слой 2 «синтез»: авторские design-документы (раздел 16)
├── artifacts/         # рабочие артефакты фаз, судьба — архив
├── workflows/         # полевые копии workflow-скриптов плана (шаблоны-исходники — packages/task/workflows/)
├── root/              # долгоживущий материал, судьба — docs проекта (раздел 3)
└── open-questions.md  # спорное/нерешённое (протокол — раздел 3)
```

Обязательны `plan.md`/`phases/`/`handoff.md` И `brief/` (слой 0 — гейт `plan-lint`:
для датовых планов от 2026.07.16 отсутствие непустого `brief/*.md` — ERROR, план не
проходит утверждение; старее/legacy — WARNING). Остальное опционально, по потребности
плана. `PLAN-ID` — один из двух каноничных паттернов:

**Журнал исполнения `journal.jsonl`** (append-only NDJSON, схема — контракт
`plan-journal-schema.md`, канон-раздел ниже наследует его формат без копирования): одна
запись на исполнение item'а любым запуском `task:plan-*` (старт `result:"in-progress"` +
финал терминальным `result`), пишет close-протокол команды (`lib/task/journal.py`).
Существующие строки НИКОГДА не переписываются/не удаляются — история, а не текущее
состояние (не дублирует Status Board/handoff). Гейт `plan-lint`: для датовых планов от
2026.07.18 отсутствие/невалидный `journal.jsonl` — ERROR; старее/legacy — WARNING (soft-гейт
против поломки уже идущего флота — тот же паттерн, что у брифа/roadmap).

**Historical schema exception.** Обычная compensating event-запись не исправляет
schema-invalid историческую строку: strict per-line gate проверяет её независимо. Если
переписывание запрещено append-only contract'ом, владелец может одобрить отдельным D# ровно
одно provenance-preserving исключение через `python3 -m task.journal exception ...`.
Хелпер дописывает optional `journal-exceptions.jsonl`, фиксируя physical target line + SHA-256
исходных UTF-8 bytes без newline, точный `invalid_fields`, owner D#, actor и reason. v1
допускает только поле `friction`; target обязан быть существующей JSON event-строкой того же
плана и иметь ровно названные schema-ошибки. Duplicate target, hash mismatch, valid target,
отсутствующий D# и malformed JSON fail closed. Sidecar не несёт event/status/next и не может
таргетить sidecar, поэтому не становится вторым current-state carrier и не образует cycle.
Старую строку и старую D# не редактируют; новая D# явно supersedes ошибочную remediation.

**Индекс плана `index.md`** (опционален) — карта ФАЙЛОВ плана + провенанс-связи
(`findings`/`research` → фаза-потребитель); НЕ носитель статуса/next (это Status Board/
`handoff.md`). Рекомендуется авто-генерируемым из дерева+frontmatter; MVP — вручную по
шаблону `snippets/index-template.md`. Гейт `plan-lint` — только WARNING (навигационное
удобство, не обязательный носитель факта, в отличие от журнала/брифа).

- **датовый** (предпочтительный, D16) — `<ГГГГ>.<ММ>.<ДД>-<КОДОВОЕ-ИМЯ>`, например
  `2026.07.10-SETTINGS-DOCTOR`: датовый префикс даёт хронологическую сортировку `plans/`
  и ориентацию «когда» без чтения Meta;
- **старый** (back-compat, D24) — `[A-Z][A-Z0-9-]+`, например `AUDIT-W2`, `MIGRATE-V3`.

Старый паттерн `[A-Z][A-Z0-9-]+` остаётся валидным, существующие планы НЕ
переименовываются; миграция — только вперёд (терминальные уходят в архив по мере закрытия).

Корень `plans/` рядом с каталогами планов:

- **`plans/ACTIVE.md`** — плоский указатель активного плана. Канон — РОВНО 4 строки
  (парсится `plan-lint`): `# ACTIVE`, пустая строка, `**Active:** <PLAN-ID>`
  (нет активного — `—`), `**Updated:** <YYYY-MM-DD>`. Скелет —
  `snippets/active-template.md`. Ведут команды: `plan-design` (режимы new/from-draft —
  ставит ID нового плана) и `plan-close` (закрыт ВЕСЬ план — сбрасывает в `—`).
- **Конвенция черновиков:** любой плоский `.md` прямо в `plans/` (кроме `ACTIVE.md` и
  `README.md`) — черновик plan mode; разворачивается командой
  `task:plan-design from-draft <файл>` (`plan-lint` предупреждает о залежавшихся).

**ПРАВИЛО MD-only:** Хранимый формат плана — только Markdown с жёсткими маркерами.
Любой JSON — производный артефакт парсера (`plan-lint --json`), не источник истины.

**Дом workflow-скриптов.** Мультиагентный workflow-скрипт — артефакт плана-владельца
(как `findings/`/`artifacts/`): единственное место — `plans/<ID>/workflows/`, вне плана
скриптам не место. Имя — `wf-<кодовое-имя-lower>-<назначение>.js`, где кодовое имя (D28) =
часть ID после даты для датового формата (`2026.07.10-FLEX` → `flex`) либо весь ID для
старого (`SKM-ROADMAP-005` → `skm-roadmap-005`), всегда lowercase; пример —
`wf-ecosystem-design-fleet.js`. Пайплайн-доки прогонов — `<Pn>-pipeline.md` рядом.
Дисциплина авторинга скрипта (обязательные стадии, слоты, structured-summary) — скилл
`workflow-craft`; здесь только ГДЕ лежит и КАК называется. Библиотека портируемых
шаблонов-исходников — `packages/task/workflows/README.md`.

## 3. Канонический корень плана

Смысловое различие двух каталогов артефактов (RAG:✅ P5.1 §2 arc42 — timeless-материал
в корень, итерации — в дочерние):

- **`root/`** — долгоживущий материал, судьба — документация проекта:
  `architecture.md`, `data-model.md`, `contracts/`, `philosophy.md`, `glossary.md`.
  Набор — по потребности плана, не все файлы обязательны.
- **`artifacts/`** — рабочий материал фаз, судьба — архив вместе с планом.

**Протокол Open Questions** (RAG:✅ P5.1 §7 IETF rough consensus): спорный пункт НЕ
блокирует план, если вынесен в `open-questions.md` с одним из статусов:

```text
Exploration
Decision pending (нужен владелец)
Resolved → D#
```

Правила: вопрос, «висящий» в теле фазы без выноса, = находка аудита; закрытие плана
с pending-вопросами = только `🟠 Done with deviations`; возражение фиксируется
содержательно («не нравится» — не возражение).

**Носители развилки — две роли, без дублей:** `## Обсуждение` в plan.md (раздел 4) =
ПРОВЕНАНС (варианты, рекомендация, куда легло), архивируется вместе с планом;
`open-questions.md` = ТРЕКЕР незакрытого — развилка со статусом ≠ `Resolved` ОБЯЗАНА иметь
запись там, резолвнутая НЕ копируется (дублей не держим); незакрытых нет → файл НЕ
заводится (пустой = шум-артефакт).

**Re-design поверх закрытых фаз** (RAG:✅ P5.1 §7 superseded-цепочки): новое решение =
новый D# со ссылкой «supersedes D#-старый»; старый D# НЕ редактируется.

**Реопен фазы — ЧЕТЫРЕ шага** (все обязательны; пропуск = находка аудита):

1. Status фазы `🟢`/`🟠` → `🟡` — в **`## 4. Phase Index & Status Board`** (`plan.md`).
   Это ЕДИНСТВЕННЫЙ носитель статуса ФАЗЫ (D51): таблица items в `phases/Pn.md` статуса фазы
   НЕ несёт — строку-не-item `plan-lint` отвергает ERROR'ом (§5). Второй носитель одного факта =
   источник рассинхрона, заводить его запрещено. Статусы items реопененной фазы правит её
   ремедиация (по ТЗ новых items), а не шаг реопена.
2. Version bump плана.
3. D-запись о причине реопена.
4. **`## Phase Handoff` реопененной фазы ИНВАЛИДИРУЕТСЯ.** Блок НЕ удаляется (провенанс
   сдачи — что и когда было сдано — сохраняется); его **первой непустой строкой** ставится
   маркер:

   ```text
   > УСТАРЕЛ — фаза реопенена <D#>
   ```

   Дальше маркера (в той же цитате) — факт на дату реопена: почему блок ниже врёт
   (сколько items и какой статус СЕЙЧАС, каков следующий шаг). Жирное начертание маркера
   (`> **УСТАРЕЛ — фаза реопенена D#.**`) легально — гейт смотрит на начало строки.
   Снимает маркер **только `plan-close`** при следующем закрытии фазы — перезаписывая блок
   целиком. Основание (H2): блок, переживший реопен, продолжает утверждать «фаза закрыта,
   N/N терминальны» и уводит cold-start-агента, который читает файл фазы (дважды подряд
   именно так и случилось — свойство протокола, не забывчивость исполнителя).

   `plan_lint` держит гейт: фаза НЕтерминальна + блок утверждает закрытие
   (`терминальн` / `фаза закрыта` / `Сдано:`) + маркера нет → **WARNING** «Phase Handoff
   протух». Утверждение о закрытии фазы читается **по первой непустой строке блока** —
   там же, где ищется маркер, — и снимается ОТРИЦАНИЕМ на ней же (`не закрыт…`): гейт
   судит СУБЪЕКТ утверждения, а не встреченное слово (D50). Поэтому честный промежуточный
   блок «**Фаза P5 НЕ закрыта.** Терминальны только P5.1 и P5.2» законен и молчит («терминальны»
   там — про ITEMS), а «**Сдано:** фаза … терминальна (3/3)» при нетерминальной фазе — WARNING.
   Пиши вердикт о фазе ПЕРВОЙ строкой: ниже гейт не смотрит. Утверждение об АКТУАЛЬНОСТИ
   содержимого блока машинно не проверяется — это чеклист `plan-audit`.

## 4. Схема plan.md

Скелет — `snippets/plan-template.md`. Секции строго в этом порядке:

- **`## 0. Meta`** — таблица `Поле | Значение`: Plan ID / Title / Version / Status / Document Type /
  Authoring Model / Last Updated / Repository / Related Packages / Execution Mode /
  Target Operator Models / Approval Owner. Необязательные поля:
  - **Home** — `brain` | `repo:<путь>`: где живёт исполняемая копия плана; по умолчанию
    репо проекта (раздел 12, D31);
  - **visibility** — `private` | `public`, дефолт `private` при отсутствии (D25): `public`
    → в git-репо допустима только публичная roadmap-выжимка, приватный бизнес-контекст
    остаётся в vault;
  - **supersedes** — `<старый-ID>`: план сменяет предшественника той же волны трека;
    предшественник уходит в архив `plans/archive/` (раздел 12);
  - **Paused By** — какой план перехватил ACTIVE и когда; заполняет режим `new`
    plan-design, дописывая поле предыдущему активному плану.
- **`## 1. Context`** — 5–15 строк: что делаем и почему. Самодостаточно: исполнитель
  НЕ видит обсуждение, в котором план родился.
- **`## 2. Execution Rules`** — выжимка правил исполнения ≤20 строк + план-специфичные
  отклонения. Полный протокол — этот скилл, его не копировать целиком.
- **`## 3. Routing`** — ТОЛЬКО отклонения от SSOT-матрицы роутинга (раздел 9).
  Пустая секция = действуют дефолты. Канон-форма строки (колонка `Exec`), правило
  деривации `Exec` и routing-гейт — раздел 9; легаси-формы остаются валидными.
- **`## 4. Phase Index & Status Board`** — таблица `Phase | Title | Items 🟢/всего | Status`.
- **`## 5. Decision Log`** — таблица `D# | Дата | Решение | Почему`.
- **`## 6. Update Log`** — append-only таблица `Дата | Кто (role/model) | Что`.
  Жёсткий лимит «Что» ≤ 2 строк, канонический формат:
  `<item> закрыт: <1 строка сути> — детали см. phases/Pn.md <item> Completion Notes`.
  Пересказывать Completion Notes в Update Log ЗАПРЕЩЕНО (инцидент EDUFY: 54KB plan.md).
- **`## 7. Contracts`** — **опциональная** (только у планов, которые экспортируют ИЛИ
  потребляют замороженные контракты; отсутствие секции — не дефект). Номер 7 — канон
  для НОВЫХ планов, но `plan-lint` опознаёт секцию ПО ЗАГОЛОВКУ, а не по номеру: план,
  уже занявший 7 своей секцией, ставит `## N. Contracts` под свободным номером. Колонки —
  байт-в-байт (их парсит `plan-lint`; расхождение — WARNING):

```text
  ## 7. Contracts

  ### Exported
| Контракт | Версия | Статус | Потребители | Уведомлены |
|:--|:--|:--|:--|:--|
| root/contracts/module-manifest.md | v2.0.2 | frozen | FLEX-2 (Epic 8) · ERP-IMPL (erp-03) | 2026-07-13 |

  ### Consumed
| Контракт | Донор-план | Pinned | Замечено | Реакция |
|:--|:--|:--|:--|:--|
| REGHUB/root/contracts/module-manifest.md | REGHUB | v2.0.0 | v2.0.2 (2026-07-13) | P8.2 — поднять до v2.0.2 |
```

- **`## Обсуждение`** — **опциональная**, БЕЗ номера, последней секцией (легаси-планы держат
  её под номером — опознаётся по ЗАГОЛОВКУ, как Contracts). Носитель развилок дизайна; у
  КАЖДОЙ развилки — ОБЯЗАТЕЛЬНАЯ строка статуса (enum раздела 3):

```text
  ### N — <развилка одной строкой>
  - **(рекоменд.) Вариант A.** Плюсы … Минусы …
  - **Вариант B.** Плюсы … Минусы …
  **Статус:** Resolved → D# | Decision pending (нужен владелец) | Exploration
```

## 5. Схема phases/Pn.md

Скелет — `snippets/phase-template.md`. Структура файла фазы:

- `# Pn — Title`
- **`## Phase Context`** — 5–10 строк, самодостаточно (фазу можно исполнять,
  не читая другие фазы).
- **`## Phase Status`** — таблица `ID | Title | Status | Updated`. Строки — ТОЛЬКО items:
  статус ФАЗЫ живёт в Status Board `plan.md` (§3/§4, D51), строку `Pn` здесь `plan-lint`
  отвергает ERROR'ом («строка без соответствующего item»).
- **Items.** Заголовок item — СТРОГО `### Pn.m — Title`. Поля — СТРОГО строками
  `**Поле:** значение`, в этом порядке:
  `Status, Intent, Why, Scope Included, Scope Excluded, Inputs, Files, Required Reads,
  Implementation Rules, Code Guidance, Validation, Deliverables, Completion Notes,
  Pending Work, Known Deviations, Escalation Needed`.
  Пустое значение — канонический символ «—» (не пустая строка, не «N/A»).
  Исключение: у поля `Escalation Needed` — и ТОЛЬКО у него — маркер `no` равноправен «—».
  **Code Guidance ОБЯЗАТЕЛЕН**: стиль решения, запреты, допустимые абстракции,
  обязательные тесты, запрещённые shortcuts — то, что дешёвая модель не выведет сама.
- **`## Phase Handoff`** — заполняется при закрытии фазы (что сдали, что дальше).
  При **реопене** фазы блок не удаляется, а инвалидируется маркером
  `> УСТАРЕЛ — фаза реопенена <D#>` первой строкой (§3, 4-й шаг реопена); перезаписывает
  его `plan-close` при следующем закрытии фазы.

**Маркер фазы-скелета.** Фаза, намеренно не детализированная при авторинге, несёт
в Phase Context фиксированную строку:

```text
> СКЕЛЕТ — не детализирован, разворачивается `design-phase: task:plan-design <ID> Pn`
```

При маркере пустые поля item'ов легальны, включая Code Guidance = «—». Без маркера
пустой Code Guidance — дефект плана.

**Contract-first дизайн-флоу (опциональный режим авторинга).** Альтернатива пофазному
«развернул одну фазу → сразу exec»: при `new` запечатать ВСЕ фазы скелет-маркерами и вписать
в каждый `Phase Context` **контракт-блок** — что фаза потребляет от предыдущих фаз и производит
для следующих; item-детали разворачивать just-in-time (`task:plan-design <ID> Pn`) на фактах
уже закрытых фаз. Цель — увидеть межфазовые конфликты и coupling-поверхность ДО детализации
(упреждает ripple «фикс одной фазы ломает другую»), не платя полную верхнюю цену дизайна всех
items сразу. Режим ОПЦИОНАЛЬНЫЙ и АДДИТИВНЫЙ к скелет-маркеру: контракт-блок не обязателен,
его отсутствие НЕ дефект, скелет-маркер самостоятелен и работает без него.

Канон контракт-блока — одна строка в `Phase Context` (рядом со скелет-маркером):

```text
> **Контракт фазы (contract-first).** Потребляет: … · Производит: … · Границы: …
```

- **Потребляет** — вход от УЖЕ закрытых фаз (артефакты, контракты, решения D#);
- **Производит** — что фаза отдаёт следующим (файлы, канон-правки, D#);
- **Границы** — что фаза сознательно НЕ трогает (передано другой фазе).

**Полная детализация до exec — ДЕФОЛТ (D-канон 2026-07-16).** Contract-first скелеты —
инструмент АВТОРИНГА, а не разрешение стартовать exec на полусыром плане: по умолчанию
ВСЕ фазы доводятся до DoR (refine-цикл §7) и утверждаются владельцем ДО первого
`plan-exec`/`plan-run`, затем собирается `roadmap.md` (§8) — и исполнение идёт батчами
без бэбиситтинга. Штатный конвейер авторинга — ПОФАЗНЫЙ: `new` (вид сверху:
скелеты+контракты, здесь задаются выравнивающие вопросы) → `Pn` по фазе за заход,
ОТДЕЛЬНЫМИ командами/сессиями — фазы слабо связаны, вопросы и утверждение владельцем
происходят внутри захода фазы; последовательность проявляется по мере проходов →
`<PLAN-ID> finish` (финальное закрытие дыр: сквозной reconcile всех фаз — вывод
«конфликты устранены» делается только когда видны ВСЕ подробности; roadmap.md собирается
его ПОСЛЕДНИМ шагом и только на чистом плане) → `plan-audit design` → exec.
Однопроходный вариант (одна сильная сессия детализирует всё) — только для малых планов
(≤3 фаз) или по явному выбору владельца: на большом плане один поток = высший риск
ошибки и смешанные согласования. `<PLAN-ID> roadmap` — отдельная ЛЁГКАЯ пересборка
карты (изменили/добавили фазу, закрыли фазы) без полного свипа; менялись контракты фаз —
нужен новый `finish`, не пересборка. Just-in-time детализация (exec стартует при живых
скелет-маркерах) допустима ТОЛЬКО по явной D-записи с причиной (волатильная фаза, чей
вход радикально зависит от исходов ранних фаз); молчаливый exec по скелетам = находка
plan-audit. Владелец-гейты внутри плана (утверждения матриц/ADR/спек design-item'ов)
при этом остаются — полная детализация убирает рутинные ручные запуски, а не решения
владельца.

**Дизайн-бюджет: проектировочные прогоны (D-канон 2026-07-16).** При `new`, сразу после
анализа брифа и оценки объёма, автор объявляет в `## 0. Meta` поле
`Design Passes: k/N — <обоснование>` (регистратор-эвристика, N — МИНИМУМ прогонов:
≤3 фаз или ≤10 items → 1; 4–7 фаз или 15–35 items → 2; кросс-репо / ядро экосистемы /
высокая неопределённость брифа → 3; владелец может поднять N явно — на качестве плана
не экономим, тратим с умом: прогоны окупаются). Прогон = полный проход дизайна
(new/фазы — или refine уже детализированных фаз) В НОВОЙ СЕССИИ — контекст сбрасывается
намеренно, свежий взгляд ловит то, к чему замылившаяся сессия слепа. Финал каждого
прогона: k++ в Meta, строка Update Log «Design pass k/N: что сделано; куда не дотянулись;
фокус следующего прогона», handoff.Next — launch-block следующего прогона С ЭТИМ фокусом
(новая сессия стартует с моментов, до которых не дотянулся предыдущий). Последний прогон
завершается `finish`. `finish` при k<N — только по явной D-записи владельца о сокращении
бюджета; `plan-audit design` сверяет счётчик с Update Log. Отсутствие поля = N=1
(малый план).

**Reconcile при детализации** (детерминированно, дёшево — скелет не терминален): разворачивая
фазу Pn, сверь `Потребляет` её контракт-блока с `Производит` фактически закрытых предыдущих
фаз. Расхождение (ранняя фаза произвела иначе, чем ждал скелет) → обнови контракт-блок Pn +
заведи D# (при отмене раннего решения — `supersedes D#`, см. §3 «Re-design поверх закрытых
фаз»). Молча подогнать скелет под факт без D# = scope drift.

**Превентивное перечисление coupling-поверхности** — часть флоу, НЕ отдельный тяжёлый ритуал:
при `new` (или первой детализации) перечисли файлы/секции-канона, которые трогают ≥2 фазы,
в `## 5. Decision Log` (D# «coupling-поверхность») либо в `Phase Context`. Видимая связность
упреждает ripple: автор поздней фазы видит, что её правка заденет раннюю, ДО того как напишет её.

**RAG-маркеры** на несущих фактах в Intent/Why/Implementation Rules и в D-логе
обязательны — схема и определение load-bearing в разделе 7.

## 6. Статусы

РОВНО 6 канонических строк — копировать байт-в-байт (greppable, парсер жёсткий):

```text
⬜ Not started
🟡 In progress
🟢 Done
🟠 Done with deviations
🔴 Blocked
⛔ Skipped by decision
```

Статус живёт в плане: завершение работы без обновления плана = незавершённое
исполнение. Закрыл item — обнови `Phase Status` и Status Board в `plan.md`.

**Статус при отклонениях.**

```text
Непустые Known Deviations САМИ ПО СЕБЕ статус item'а НЕ меняют.

🟠 Done with deviations ОБЯЗАТЕЛЕН при material-отклонении (любое из):
- Scope Included выполнен не полностью или выполнен иначе, чем предписано;
- Validation осталась красной (не починена в рамках Scope);
- затронут public contract / SemVer / замороженный контракт СВЕРХ ТЗ item'а;
- acceptance-критерий item'а не выполнен;
- принят workaround, который ЖИВЁТ В КОДЕ/артефакте (а не в процессе исполнения);
- item-коммит несёт дифф вне `Files` item'а (посторонний захват рабочего дерева либо
  файл «по делу», не заявленный в ТЗ) — независимо от того, верен ли сам дифф.
  НЕ считается foreign diff (material-отклонением не является, в `Files` не обязателен):
  (а) `plans/<ID>/**` и `plans/ACTIVE.md` — штатная часть закрытия item'а (§8:
  bookkeeping-коммит); (б) **детерминированный производный артефакт** — выход НАЗВАННОЙ
  команды регенерации над `Files`-источниками item'а (реестр-манифесты, сгенерированный
  канон другого языка, локфайлы, снапшоты доков): регенерация — прямое ожидаемое
  следствие правки item'ом своих источников, не «чужая работа» (реальная защита foreign-
  diff остаётся — carve-out (б) НЕ покрывает недетерминированное/ручное/чужое). Не путать
  с «фазовой когерентностью производного» ниже: там — про ОСТАВИТЬ артефакт протухшим,
  здесь — про КОММИТ его регенерации.

🟢 Done сохраняется при process-отклонении, но запись в Known Deviations ОБЯЗАТЕЛЬНА:
перебор тира (исполнено моделью/effort ВЫШЕ предписанных Routing), бандлинг коммитов,
порядок правок, стилистика отчёта. Тихое умолчание = дефект (находка аудита).

Недобор модели/effort НИЖЕ предписанного Routing — не process-отклонение: он запрещён
routing-гейтом §9, item в таком виде не исполняется вовсе.

Дефект САМОГО ТЗ (правило ТЗ ошибочно или невыполнимо) — тоже НЕ отклонение исполнителя:
он эскалирует (§10: конфликт правил / неясные acceptance), владелец или plan-design вносит
новый D# и СИНХРОНИЗИРУЕТ Scope Included item'а с решением; закрытие идёт по ОБНОВЛЁННОМУ
ТЗ → 🟢 + запись в Known Deviations (что изменено, каким D#). Правка ТЗ по ходу БЕЗ D# —
material-отклонение (scope drift), даже если результат «лучше».

«Мягкий пункт Validation» (пометка в ТЗ, что конкретный порог/пункт необязателен) —
ЗАПРЕЩЕНА: красный пункт Validation ВСЕГДА material (см. выше) либо, если порог самого
ТЗ ошибочен/неудобен, — эскалация владельцу за новым D# (см. «Дефект самого ТЗ» выше),
не тихое послабление исполнителем на месте. Ручка «soft» — путь к тому, что любой
неудобный порог тихо аннулируется тем, кто его же и превысил (прецедент D58: P2.13
закрыт `🟢` при красном пункте, потому что ТЗ само объявило его мягким).
```

**Коммит-гейт закрытия.** Статус `🟢`/`🟠` не ставится без закоммиченного диффа item'а:
Conventional Commits (рус.), `validate.sh` затронутого пакета зелёный ДО коммита;
незакоммиченного диффа по Scope item'а в дереве не остаётся (`git status`); дифф ВНЕ
Scope item'а — не коммитить, зафиксировать в Pending Work. Инцидент-основание — D12
плана SKM-AUDIT-004: 4 «закрытых» item'а числились готовыми, а их код лежал
незакоммиченным в рабочем дереве.

```text
Item закрывается ДВУМЯ коммитами (единственная топология — §8 «Порядок закрытия item'а»;
здесь — только СБОРКА каждого, порядок шагов не дублируется):
- item-коммит        → `git add <пути из Files>`        (только Scope item'а);
- bookkeeping-коммит → `git add plans/<ID> plans/ACTIVE.md` (только файлы плана).

ДВА — это топология ЗАКРЫТИЯ, а не потолок числа коммитов:
- внутри ШАГА 1 дифф Scope может собираться НЕСКОЛЬКИМИ коммитами, если каждый атомарен
  по смыслу; item-коммит — ЗАВЕРШАЮЩИЙ коммит шага 1, и в handoff (§8, шаг 3) идёт
  ИМЕННО его хеш;
- фикс по замечаниям ревью — коммит СВЕРХ топологии (не `amend` — трассируемость: видно,
  что нашло ревью), а НЕ альтернатива ей: топология закрытия от него не меняется.
Ни то, ни другое не разрешает СЛИЯНИЕ шагов 1 и 6 в один коммит — см. бандл ниже.

`git add -A` и `git commit -a` ЗАПРЕЩЕНЫ: рабочее дерево может нести чужой дифф
(владелец правит код параллельно с агентом) — он уедет в item-коммит незамеченным.
Посторонний дифф в дереве исполнитель НЕ трогает (не коммитит, не стэшит, не ревертит,
не «прибирает») — он НАЗЫВАЕТ его в отчёте item'а: чужая работа не его предмет.
Инцидент-основание — F1 аудита P2 плана 2026.07.13-PLAN-PROTOCOL-GAP: `git add -A`
затащил в item-коммит правку чужого продуктового файла (`integrate.py`).

Бандл (дифф Scope и bookkeeping ОДНИМ коммитом) — process-отклонение: 🟢 + запись в Known
Deviations, но handoff и в нём ОБЯЗАН нести реальный хеш item-коммита (§8, шаг 3), которого
в момент сборки бандла ещё не существует. Значит бандл покупается ЧИНЯЩИМ коммитом с хешем
— эта цена называется в отчёте, а не скрывается; плейсхолдер вместо хеша — дефект.
Инцидент-основание — G2 повторного аудита P2 того же плана: расхождение §6 и §8 о числе
коммитов уже породило плейсхолдер `<P2.5>` вместо хеша в handoff.
```

**Фазовая когерентность производного.** Item вправе оставить ПРОИЗВОДНЫЙ артефакт
протухшим (сгенерированный EN-канон скилла, реестр, снапшот доков), если выполнены ВСЕ
три условия: (а) фаза несёт ТЕРМИНАЛЬНЫЙ item регенерации, (б) он назван в Pending Work,
(в) отчёт честно говорит, что `validate.sh` красный ИМЕННО производным дрейфом. Коммит-гейт
на таких item'ах проверяется по НЕпроизводным ошибкам; полный зелёный обязателен на
терминальном item'е фазы. Регенерировать производное после КАЖДОГО item'а, правящего один
и тот же источник, — значит выпустить N несогласованных снимков канона, который ещё
дописывается. Молча закрыть item при красном `validate.sh` — не отклонение, а ложь в
Completion Notes.

**DoR-гейт фазы.** Фаза не переводится из дизайна в исполнение, пока не пройден
Definition of Ready — чеклист и refine-цикл в разделе 7. Фаза, ушедшая в exec с
незакрытыми `[NEEDS CLARIFICATION]`, = находка plan-audit.

## 7. Refine-цикл и готовность

**Маркер `[NEEDS CLARIFICATION: <вопрос>]`** — канонический способ пометить
неоднозначность прямо в тексте плана/ТЗ item'а (RAG:✅ P5.1 §1 spec-kit). Спорное место
при авторинге — либо маркер, либо вопрос владельцу; самовольное допущение запрещено.
Гейт бинарный: 0 маркеров.

**DoR-гейт фазы** (Definition of Ready, RAG:✅ P5.1 §7 Atlassian) — фиксированный
чеклист; plan-design обязан прогнать его перед выдачей «фаза готова», plan-audit
проверяет пост-фактум:

- [ ] Все `[NEEDS CLARIFICATION]` сняты (0 маркеров в фазе).
- [ ] Scope Included / Scope Excluded фазы заполнены (эквивалент Goals/Non-Goals).
- [ ] Alternatives для несущих решений зафиксированы в D-логе.
- [ ] Каждая развилка `## Обсуждение` несёт строку статуса; всё, что ≠ `Resolved`, имеет
      запись в `open-questions.md` (раздел 3).
- [ ] Несущие факты несут RAG-маркеры.
- [ ] **Для фаз с ЗАЯВЛЕННОЙ оркестрацией** (multi-agent/fan-out): готовый workflow-скрипт
      в `plans/<ID>/workflows/`, launch-block handoff ссылается на него по `scriptPath`
      (D29). Условие — ТОЛЬКО при заявленной оркестрации: ручное item-by-item исполнение
      фазы workflow НЕ требует (дом/имя скрипта — раздел 2, авторинг — скилл `workflow-craft`).

**Критерий «фаза обязана заявить оркестрацию»** (D16 — раньше решение оставалось на
усмотрение исполнителя каждый раз заново, отсюда наблюдаемая непоследовательность).
Фаза ОБЯЗАНА завести workflow-скрипт (item-by-item НЕ легален), если сработал ЛЮБОЙ
из двух сигналов:

- **N≥3 items с независимым/parallelizable scope** — items фазы не блокируют друг
  друга по данным (Inputs одного item'а не ссылается на Deliverables другого item'а
  ЭТОЙ ЖЕ фазы) И у каждого есть детерминированные Validation-команды (конкретные
  команды с проверяемым результатом, не «проверь вручную»);
- **длинная автономная цепочка с внешним состоянием** — фаза рассчитана на прогон
  без ручного вмешательства между item'ами дольше одной сессии-исполнителя (состояние
  передаётся через git+plan, а не через контекст чата).

Ни один сигнал не сработал (items <3, либо scope items связан последовательно, либо
Validation неформализуема) — фаза остаётся ручной, workflow НЕ заводится «на всякий
случай» (лишний файл + лишняя дисциплина слотов без нужды). Критерий бинарный: агент
сверяет факт по items фазы (число, зависимость Inputs↔Deliverables, наличие команд
Validation) — не оценивает «на усмотрение».

**RAG-маркеры в схеме.** Каждый load-bearing факт/вердикт в Intent/Why/Implementation
Rules item'а и в D-логе несёт РОВНО ОДИН маркер из закрытого enum'а трёх значений
(D29 — раньше их было два, и repo-grounded факту нечего было вписать честно):

- `RAG:✅ <дата/суть запроса>` — ВНЕШНИЙ факт верифицирован через RAG.
- `RAG:—` — repo-grounded факт / внутреннее правило: подтверждается чтением кода этого
  репо или самого плана, внешней верификации не требует. Основание — в скобках:
  `RAG:— (repo-grounded: plan_lint.py:88)`.
- `[UNVERIFIED]` — не проверено, решение принято на риске.

Load-bearing = «на этом стоит проектное решение». Несущий пункт без маркера = дефект
схемы, находка аудита. `RAG:—` НЕ годится ни для одного ВНЕШНЕГО факта (версия/API
библиотеки, «ещё актуально/устарело», рынок, возможности чужого сервиса/MCP) — там либо
`RAG:✅`, либо `[UNVERIFIED]`; `RAG:—` на внешнем факте = та же находка аудита.

**Refine-цикл** — канонический контур авторинга:
design → self-audit (DoR-чеклист) → правка → повтор до 0 маркеров.

**RECOVERY при клинче.** Refine-цикл выше сходится, пока фикс ЛОКАЛЕН. КЛИНЧ — когда правка
одной фазы/item'а рябит в другую (плотно-связанный SSOT): per-change-рефайн даёт thrash —
каждый локальный фикс вскрывает новое рассогласование; big-bang «накопить и разобрать в
конце» прячет несовместимости до поздна. Дисциплина сходимости — средний путь (RAG:✅ P5.1
SBD/LRM/progressive-freeze, `findings/P5-design-convergence.md`):

- **Средний батч вокруг ОДНОГО coupling-hotspot'а** — сгруппируй правки вокруг одного
  связного дизайн-вопроса, примени во ВСЕ затронутые фазы/секции разом (не микро-твик на
  каждое изменение, не «весь дизайн одним махом»); носитель батча — колонка `Batch` §3
  Routing (§9 «Батчинг подфаз»), RECOVERY не вводит свой механизм.
- **Интеграционная валидация ПОСЛЕ КАЖДОГО батча** — DoR-чеклист по всем затронутым фазам,
  не только в конце. «Финальная консолидация в конце» ≠ «копить рассинхрон весь дизайн»:
  без per-батч-валидации это тот самый big-bang-анти-паттерн.
- **Финальная консолидация — единый проход** (сверка целого после закрытия хотспотов), а НЕ
  полный re-design N раз.
- **Progressive-freeze** — стабилизированную фазу морозит контракт-блок (§5, contract-first);
  дальше только детали, не новые контракты (reconcile `Потребляет`↔`Производит` при
  детализации поздних фаз, §5).
- **Пустой feasible-set → удалить вариант, не патчить** (SBD): ни одна правка hotspot'а не
  мирит фазы → вариант структурно нежизнеспособен — убери его через `## Обсуждение`+D#, не
  наращивай костыли вокруг.
- **Стратегия декомпозиции при клинче** — эскалация к Perplexity (RAG-делегирование), а не
  импровизация «на глаз».
- **Критерий остановки:** 0 открытых high-severity рассогласований между фазами И все
  coupling-hotspot'ы согласованы — дальше только редакторские правки. AUDIT-петля (потолок
  раундов аудита, §13/`plan-audit`) закрыта отдельно — RECOVERY закрывает DESIGN-рефайн-петлю.

**Pre-mortem для high-stakes** (фискалка/платежи/tenant-isolation/ядро экосистемы):
перед закрытием фазы дизайна — раунд по протоколу Klein (RAG:✅ P5.1 §7, prospective
hindsight +30%): «план провалился через 6–12 мес — почему»; независимая запись причин →
кластеризация → mitigations с owner в Risks/D-лог.

## 8. Handoff-стандарт

`plans/<ID>/handoff.md` — rolling-указатель, ПЕРЕЗАПИСЫВАЕТСЯ при каждом закрытии
item/фазы (история версий — в git, не в файле). Скелет — `snippets/handoff-template.md`.
Поля:

- Заголовок — две формы (иная = ERROR `plan-lint`; D30):
  - `# HANDOFF — <ISO-дата> — after Pn.m` — закрыт item (адресат — последний закрытый item);
  - `# HANDOFF — <ISO-дата> — after Pn` — закрыта/проаудирована/ре-дизайнена ФАЗА, то есть
    шаг, у которого «последнего закрытого item'а» как адресата нет (`plan-close <ID> Pn`,
    `plan-audit <ID> Pn`, `plan-design <ID> Pn`).
  - У формы `after Pn.m` **фаза `Pn` обязана существовать в плане** (объявлена в Status Board
    ЛИБО имеет файл `phases/Pn.md`) — иначе ERROR «висячая ссылка» (D37/D41). Единственное
    исключение — bootstrap-заголовок `after P0.0` стартового handoff'а (фазы `P0` не бывает).
    Существование самого ITEM'а `Pn.m` не гейтится (back-compat флота).
- **Next:** semantic carrier из закрытого enum ниже; provider invocation рендерится отдельно.
- **Done:** что закрыто.
- **Remaining:** что осталось.
- **Sources of truth:** где правда (plan.md, phases/Pn.md, ключевые файлы).
- **Open risks:** открытые риски.
- **Workarounds/Deferred/Open questions:** ключи совпадают с run-report
  `devloop{workarounds,deferred,open_questions}` — сверяемость с телеметрией.

**Launch-block.** Каждая выдача «что запускать дальше» — handoff.Next и финалы отчётов
plan-exec/plan-close/plan-audit — обязана иметь фиксированную форму
(`snippets/launch-block-template.md`):

```markdown
**Next:** <kind>: task:<plan-command> <PLAN-ID> <arguments>

| Параметр | Значение |
|:--|:--|
| Model class | <economy / implementation / frontier> |
| Effort | <low / medium / high / xhigh> |
| Capabilities | <semantic capability IDs; `—` если дополнительных нет> |
| Context | <одно из трёх значений enum'а ниже> |
| Суть | <1 строка> |

````
<provider renderer: Claude `/task:…` ИЛИ Codex `$ task:…`; semantic payload не менять>
````
```

**Самодостаточность (cold-start).** Команда в launch-block обязана работать из холодной
сессии: plan-ID + пути входных доков (cold-start reads) + встроенное утверждение гейта,
если исполнение гейтится. Ссылки вида «эта сессия» — только как дополнение.
`plan-lint` проверяет: handoff.Next содержит launch-block-таблицу и code-block (грепаемо;
для датовых планов от 2026.07.16 отсутствие — ERROR, старее/legacy — WARNING).

**Scope-payload: launch-block, несущий НАХОДКИ (D-канон 2026-07-17).** Команда, передающая
следующей сессии находки, — вердикт `plan-audit` `RED`/`ATTENTION` (§3) и фикс-предложение
C3/D6 — голой быть НЕ имеет права. Под ней в том же code-block'е идут четыре строки
(порядок фиксирован):

````
<provider-rendered invocation>

РЕЖИМ: <реопен по §3 (4 шага) | детализация | ремедиация — что именно делает сессия>
ВХОД: <файл → блок с находками; cold-start read>
СКОУП: <нумерованный список: что сделать>
НЕ ТРОГАТЬ: <анти-скоуп: что оставить как есть>
````

Почему каждая:

- `РЕЖИМ:` — `design-phase: task:plan-design <ID> Pn` МНОГОЗНАЧЕН: свежая сессия, увидев фазу с
  терминальными items, сама решает «реопен или детализация» и ошибается в сторону дорогого.
- `ВХОД:` — исполнение правила cold-start выше («пути входных доков»): без него payload
  живёт только в чате и умирает с сессией. Тот же класс, что «долг живёт только в handoff»:
  handoff — rolling pointer, и в момент передачи он ещё указывает на ПРЕДЫДУЩИЙ шаг, то есть
  активно уводит принимающую сессию мимо находок.
- `СКОУП:` / `НЕ ТРОГАТЬ:` — единственное, что удерживает сессию от переразработки уже
  закрытого. Анти-скоуп обязателен именно потому, что дорогая ошибка здесь — не «сделает
  мало», а «переделает всё».

Инцидент-основание: аудит P0 плана `2026.07.16-INS-EVO` (2026-07-17) выдал launch-block
`/task:plan-design <ID> P0` без payload'а — владелец прочитал его как «фазу предлагают
разрабатывать заново»; сам `plan-audit.md` ровно голую команду и предписывал, при том что
правило cold-start существовало. Не хватало ФОРМЫ и ГЕЙТА, а не доктрины.

**Носитель payload'а — сам отчёт на диске.** `plan-audit` кладёт launch-block подсекцией
`### Что запускать` в КОНЕЦ своего блока `## Audit Pn` (§3) — та же единственная разрешённая
запись, тот же файл. Чат-only launch-block непроверяем машиной by design; на диске `plan-lint`
гейтит присутствие таблицы, code-block'а и всех четырёх строк (датовые планы от 2026.07.16 —
ERROR, старее/legacy — WARNING). Присутствие ≠ качество: содержательность `СКОУП:`/`НЕ ТРОГАТЬ:`
машина не меряет — это report-quality следующего аудита.

**Строка вердикта — литерал.** Аудит объявляет вердикт строкой `**Вердикт: <GREEN|ATTENTION|RED>**`
в своём блоке `## Audit Pn` и пишет её ДОСЛОВНО: значения латиницей, шапка `Вердикт:` — нет. По ней
гейт и находит вердикт. Вольная форма («Verdict: RED», «Итог: RED») гейт не срабатывает — молча, и
scope-payload перестаёт требоваться вовсе: это класс «гейт зеленеет на пустышке», ради которого
литерал и канонизирован (реестр `CANON_LITERALS`, директива `i18n-keep`). Блок `## Audit …` БЕЗ
строки `Вердикт:` — свободная заметка, а не отчёт аудита: не гейтится (иначе линтер требовал бы
payload от произвольного `## Audit`-заголовка). Вердикт `GREEN` находок не несёт и payload'а не
требует.

**Финальное сообщение сессии = launch-block.** Любая `task:plan-*` сессия (design / exec /
run / close / audit), у которой есть следующий шаг, ЗАКАНЧИВАЕТ своё последнее сообщение
владельцу полным launch-block'ом (semantic Next + таблица Model class/Effort/Capabilities/
Context/Суть + provider-rendered invocation
отдельным code-block'ом) — не «выполните такую-то команду» прозой: владелец не должен
переспрашивать route и настройки. Invocation без semantic Next/route в финале = дефект.

**Roadmap исполнения — `plans/<ID>/roadmap.md` (D-канон 2026-07-16).** После полной
детализации всех фаз (§5 дефолт) собирается исполнительская карта плана — ответ на
«какую команду дальше?» без анализа всего плана и без простоев владельца у монитора.
Собирает её `plan-design <ID> finish` ПОСЛЕДНИМ шагом (только на плане без дыр);
последующие пересборки (изменили/закрыли фазы) — лёгкий режим `plan-design <ID> roadmap`.
Скелет — `snippets/roadmap-template.md`. Содержание:

- таблица ВСЕХ items по порядку исполнения: `Item | Batch | Запуск | Model/Thinking | Гейт
  владельца | Примечание`;
- **Batch** — группа последовательных мелких items одной модели со сцепленным scope,
  исполняемая ОДНОЙ сессией одним carrier (`run-items: task:plan-run <ID> Pn.a-Pn.b` — серия);
  большой/сложный/рисковый item — `solo` (отдельная сессия); НЕЗАВИСИМЫЕ по scope items —
  `workflow` (скрипт в `plans/<ID>/workflows/`, один запуск). Обоснование «почему нельзя
  объединить» у solo-items обязательно (пустая ячейка = находка аудита);
- **Гейт владельца** — только там, где решение реально его (утверждение матрицы/ADR/спеки,
  высокорисковый шаг); остальное исполняется без остановок;
- на каждую batch/workflow-группу — готовый launch-block.

Потребители: сессии `plan-exec`/`plan-run`/`plan-close` сверяют свой финальный launch-block
с roadmap — если следующий шаг входит в батч, предлагается КОМАНДА БАТЧА, а не одиночный
item; вопрос владельца «что дальше?» = чтение roadmap.md + handoff.md. Расхождение
roadmap↔Routing§3 — дефект (roadmap не переопределяет модели, только группирует запуски).
Гейт: `plan-lint` — все фазы детализированы (нет скелет-маркеров), а `roadmap.md`
отсутствует → ERROR для датовых планов от 2026.07.16 (старее/legacy — WARNING);
`plan-audit design` проверяет полноту покрытия items и обоснованность батчей.
Живой документ: закрытие фазы/re-design обновляет roadmap (строка Update Log).

При мастер-плане общий session-handoff (скилл `session-handoff`) сворачивается
сюда — второй handoff-файл не заводить.

**Допустимые формы `Next`** (закрытый enum, m8/B1/N1/N2 + D8 — `plan-lint` принимает РОВНО эти
11 форм; иная форма = ERROR с перечислением допустимых):

```text
| Форма Next | Когда |
|:--|:--|
| exec-items: task:plan-exec <ID> Pn.m [Pn.k …] | следующий item детализирован, Exec = plan-exec (§9); список items = batch одной сессией |
| run-items: task:plan-run <ID> Pn.m[-Pn.k] | manual-item(ы) под проверенным inherited-plan route сессии |
| audit-design: task:plan-audit <ID> design | план детализирован — pre-exec ревью |
| design-phase: task:plan-design <ID> Pn | следующая фаза — скелет |
| design-item: task:plan-design <ID> Pn.m | item эскалирован (🔴) либо требует ре-дизайна |
| audit-phase: task:plan-audit <ID> Pn | фаза Pn терминальна — аудит перед следующей |
| close: task:plan-close <ID> Pn[.m] | закрыть фазу / сверить item |
| archive: task:plan-close archive <ID> | план терминален целиком |
| terminal: план закрыт | все items терминальны, следующий шаг вне протокола |
| manual: <model-class/effort> | Exec = manual (§9): invocation нет, launch-block несёт route и голый промпт item'а |
| waiting: <условие> → <целевая semantic форма> | шаг реален, но неисполним сейчас; не дефект и не терминал |
Иная форма = ERROR plan-lint.
```

Новые планы хранят semantic форму. Исторические `/task:…` строки остаются compatibility
input; литералы `ЗАПУСК ВРУЧНУЮ` и `ОЖИДАНИЕ:` также принимаются. Они не переписываются
blanket-миграцией. Renderer получает тот же carrier и выдаёт
Claude `/task:…` либо Codex `$ task:…`, не меняя PLAN-ID, item IDs, cold-start reads,
scope-payload или owner gate.

**Форма `Next` объявляется ПЕРВОЙ непустой строкой поля** (D40). Поле многострочное (тянется
до следующего `**Поле:**` и включает launch-block), поэтому резолвер читает форму по
строке-объявлению, и лишь при неудаче — грепом по всему полю (фолбэк, back-compat). Практический
смысл: launch-block ЦИТИРУЕТ команды и формы enum'а (у manual-item'а — целый голый промпт), и
цитата в ячейке «Суть» перехватывала бы резолвер, давая ложный ERROR. Объявляй форму строкой
`**Next:** …` — ниже гейт формы не смотрит.

**Порядок закрытия item'а** (канонизирует B1/F11/M2/A4 — рецидивы «нечестного» lint):

```text
ДВА коммита — единственная топология item'а. Сборка каждого (`git add` по явным путям,
запрет `-A`/`-a`) — §6 «Коммит-гигиена», здесь не дублируется.

1. Дифф Scope (код/артефакты) ТОЛЬКО по путям `Files` → validate.sh пакета зелёный →
   ITEM-КОММИТ. Файлы плана в него НЕ входят.
2. Bookkeeping плана: Status, Completion Notes, Pending Work, Known Deviations,
   Phase Status, Status Board, Update Log; в `plan.md` — `Last Updated` (дата закрытия
   item'а). Машинного гейта на `Last Updated` НЕТ (протухшее поле — бухгалтерия отстала,
   а не находка): сверяет чеклист `plan-audit`.
3. Перезапись handoff.md (Next — форма из enum выше). Хеш item-коммита handoff берёт ИЗ
   ШАГА 1 — коммит уже в истории (`git rev-parse --short HEAD`), поэтому хеш РЕАЛЬНЫЙ.
   Плейсхолдер вместо хеша (`<Pn.m>`, «TBD», пустая ячейка) — дефект, а не форма.
4. plan-lint — ПОСЛЕ шага 3, на итоговом дереве. Прогон ДО перезаписи handoff ЗАПРЕЩЁН:
   закрывающий item сам меняет handoff, и счёт «до» не описывает состояние коммита.
5. Счёт публикуется С АТРИБУЦИЕЙ: «N ERROR / M WARN — новых от диффа item'а: K»
   (K — детерминированно: plan-lint --baseline HEAD).
   • K > 0 — чинится ДО коммита bookkeeping'а;
   • N − K > 0 (остаточные ошибки плана вне Scope item'а) — НЕ замалчиваются: строка в
     Pending Work item'а + Open risks handoff'а.
6. BOOKKEEPING-КОММИТ: только файлы плана (`plans/<ID>/**`, `plans/ACTIVE.md`).

«Зелёный lint» гейта закрытия = K = 0 (нет НОВЫХ ошибок), а не N = 0.
Item без диффа кода (Scope = сам план) идёт той же топологией: шаг 1 коммитит `Files`
item'а, шаг 6 — остальную бухгалтерию.
Слить шаги 1 и 6 в один коммит (бандл) = process-отклонение §6: 🟢 + запись в Known
Deviations + чинящий коммит с реальным хешем в handoff.
```

**Якорь дерева для чисел в отчётах.** Любое ЧИСЛО в отчёте item'а (Completion Notes,
Validation, Known Deviations, Update Log) — счётчик `grep`, число ERROR/WARN, число
коммитов/файлов — приводится с явным **якорем дерева**, на котором оно воспроизводимо:
`<число> (на <git-ref>)`, и с командой, которой получено. Дефолтный якорь — **закоммиченное
дерево item'а**, а не дерево момента написания отчёта:

```text
Число о диффе Scope (код/артефакты) → якорь = ИТЕМ-КОММИТ (шаг 1): он уже в истории,
  bookkeeping его не меняет — команда воспроизводима как есть.
Число о файлах ПЛАНА (грепы по phases/Pn.md, счёт lint) → якорь = BOOKKEEPING-КОММИТ
  (шаг 6): его меняет сам отчёт. Считай на дереве, которое КОММИТИШЬ (после `git add`
  всех правок шага 2–3), а не на дереве до правки; разошлось после коммита — чини
  чинящим коммитом, а не оставляй.
```

Число без якоря либо не воспроизводимое своей же командой на закоммиченном дереве = **ложное
утверждение** (класс B1), даже если на момент написания оно было верным. Машинного гейта нет —
проверка в чеклисте `plan-audit`.

**Числа ВНЕ этого репо — только ДЕЛЬТА парного прогона** (D53). Чужой корень (`plans/` другого
репозитория, флот) живёт своей жизнью и мутирует между прогонами: якорь дерева на него не
распространяется — `git-ref` своего репо чужое дерево не фиксирует. Поэтому регресс/back-compat
по чужим корням доказывается ТОЛЬКО парой прогонов на ОДНОМ снимке чужого дерева
(`<ref-до>` → `<ref-после>` СВОЕГО репо, чужое не тронуто) и публикуется как **дельта**
множеств диагностик: `ERROR Δ 0 · WARN Δ −1 (снят ложный …)`. Абсолютный счётчик чужого корня
(«ERROR 116 → 116») доказательством НЕ является: он не отличает дрейф чужого репо от регресса
своей правки. Дельта ≠ 0 — либо истинная находка нового правила (назвать поимённо), либо блокер.

**Цикл «item/фаза → handoff → context boundary»:** следующий шаг читает plan.md →
phases/Pn.md → handoff.md, а не полагается на хвост чата. Конкретный provider может
проецировать `same-session` в очистку контекста, но это не semantic значение плана.

**Session-restart discipline (различение поля Context launch-block'а, D16 + D30).** Поле
Context launch-block'а несёт РОВНО одно из трёх значений — не статичное общее
«рекомендован /clear» независимо от типа следующего шага:

- **`same-session — item`** — следующий шаг обычный item-by-item exec; текущая сессия
  достаточна, provider сам выбирает native способ освежить контекст.
- **`cold-start — orchestration`** — следующий шаг оркестрованный кусок. Carrier хранит
  `kind`, `orchestration_id`, ordered inputs, required capabilities и provider projection
  reference. До запуска обязательны `command.subagents` и `command.workflow-carrier`;
  missing/unknown/unsupported support = `CMD_CAPABILITY_UNSUPPORTED`, silent solo fallback запрещён.
- **`cold-start — plan-step`** — следующий шаг не item-exec, а шаг протокола НАД планом
  (`plan-audit` / `plan-close` / `plan-design`): он читает план заново с диска (аудит —
  ещё и adversarial: наследовать контекст исполнителя ему запрещено).

**Item с `Exec = manual` (§9) — semantic форма `manual`.** Команды у такого item'а не
существует, поэтому launch-block:

- `Next` = `manual: <model-class/effort>`;
- `Model class`/`Effort` — **предписанные Routing** (§9);
- code-block несёт **ГОЛЫЙ ПРОМПТ item'а**, а НЕ provider invocation:
  `task:plan-exec` имеет минимум `implementation/medium` и обязан отклонить undershoot;
- `Context` — из того же enum'а ТРЁХ значений, по типу следующего шага. Manual-item — это
  обычный item-by-item exec под предписанным route ⇒ `same-session — item`.

Это ЕДИНСТВЕННОЕ место, где определяется `Context` manual-item'а; `snippets/` его цитируют,
собственных правил не заводят.

**Форма `Next` `waiting: <условие> → <целевая semantic форма>` (D8).** Следующий шаг РЕАЛЕН, но
неисполним ПРЯМО СЕЙЧАС — ЗДОРОВОЕ ожидание внешнего времени/состояния (time-gate,
накопление baseline/usage-trend, кросс-план-гейт ещё не терминален), а НЕ дефект плана.
Не путать: `🔴 Blocked`/эскалация §10 = ДЕФЕКТ (план разошёлся с кодом, нужен ре-дизайн);
«план закрыт» = ТЕРМИНАЛ (делать больше нечего); «ОЖИДАНИЕ» = пауза перед реальным шагом.

- `Next` = `waiting: <условие> → <целевая semantic форма>`, где **условие СТРУКТУРНО**: дата
  `≥ГГГГ-ММ-ДД`, либо гейт `<PLAN-ID> Pn терминальна`, либо `usage-trend ≥N недель` (не
  проза «когда-нибудь потом»); **целевая форма** — любая runnable-форма enum'а выше (обычно
  `exec-items: task:plan-exec <ID> Pn.m`);
- launch-block несёт **целевой carrier** и его provider projection, а ПЕРВОЙ
  строкой code-block'а — **guard `# НЕ раньше: <условие>`** (копипастабельно и честно про
  неисполнимость сейчас); `Model class`/`Effort`/`Context` — **целевого шага**;
- прозаическую оговорку в строке-объявлении (`exec-items: … — НО не раньше …`) НЕ писать:
  она не копипастится, и `plan-lint` метит её WARNING (C2), предлагая эту форму.

`plan-lint` резолвит форму как `waiting` и требует launch-block.

**Всплывшая ошибка → фикс-предложение (C3, D6).** Прогон обнажил material-проблему (Validation
осталась красной вне Scope · остаток lint'а N−K>0 · посторонний дифф · найденный дефект) —
отчёт/handoff СРАЗУ несёт конкретное remediation-предложение (что + launch-block под фикс + 1
строка «почему»), а НЕ пассивную заметку «готов к следующему, были ошибки»; дополняет запись в
Known Deviations/Pending Work, не заменяет её. Фикс — самое ценное следующее действие → `Next`
указывает на него (`design-item: task:plan-design <ID> Pn.m` либо follow-up fix-item), не на следующий item
молча. Launch-block такого `Next` несёт **scope-payload** (§8: `РЕЖИМ:`/`ВХОД:`/`СКОУП:`/
`НЕ ТРОГАТЬ:`) — предложение без него передаёт следующей сессии проблему, но не её границы.
Не путать с §10-эскалацией (🔴 = дефект план↔код, обязателен ре-дизайн): здесь item
закрывается (🟢/🟠) с явным предложением, а не блокируется. Report-quality — сверяет `plan-audit`.

## 9. Routing & Thinking Policy (SSOT-матрица)

Дефолтный роутинг ролей на neutral model class/effort. Секция `## 3. Routing` плана хранит
ТОЛЬКО отклонения от этой таблицы:

| Роль | Model class/effort | Где работает |
|:--|:--|:--|
| issue-planner | frontier/high | plan-design |
| invariant-auditor | frontier/xhigh | plan-audit |
| package-implementer | implementation/medium | plan-exec |
| small-implementer | economy/low | LOW-срезы dev-loop |
| repo-explorer | economy/low | разведка репо (grep/read/map) |
| docs-curator | implementation/low | plan-close |

Порядок классов: `economy < implementation < frontier`; effort независимо:
`low < medium < high < xhigh`. Provider selector выбирается только из проверенной mapping.
Гейт выполняется ДО status mutation/work/write/external call/subagent launch: exact и overshoot
по любой оси легальны (`CMD_ROUTE_OVERSHOOT` — info), undershoot блокирует
`CMD_ROUTE_UNDERSHOOT`; unknown/missing/ambiguous selector или effort блокирует без fallback.
Повышение effort не компенсирует недобор class и наоборот. Required capabilities принимают
только `native`/`adapted`; missing/unknown/unsupported = `CMD_CAPABILITY_UNSUPPORTED`.

**Thinking policy:**

- effort **high+ ОБЯЗАТЕЛЕН** для: декомпозиции, конфликтных требований, инвариантов,
  SemVer-public-API, финальной верификации.
- effort **low ОБЯЗАТЕЛЕН** (thinking вреден — жжёт токены без пользы) для:
  grep/read/map, механических правок, статус-апдейтов, docs sync,
  handoff-форматирования.

**Tier policy (критерий ТИРА МОДЕЛИ — ось, НЕЗАВИСИМАЯ от effort'а):**

- **frontier** — только где у item'а остаются ОТКРЫТЫЕ design-решения ЛИБО
  цена семантической ошибки необратима/замораживается (freeze-механизм, breaking-семантика
  дефолтов, канон флота, кросс-фазный синтез);
- **предписанная реализация** по уже запинённым канонам (RAG-вердикт, замороженная спека,
  готовое D#-решение) → implementation/high;
- **editorial/механика** с детерминированными гейтами → implementation/medium (по деривации ниже —
  `plan-exec`);
- «effort high+ ОБЯЗАТЕЛЕН» НЕ поднимает тир модели: SemVer-item по замороженной спеке =
  implementation/high, не frontier/high. Перебор тира, ПРЕДПИСАННЫЙ Routing'ом, — такой же дефект плана,
  как недобор исполнителя: жжёт frontier на работе implementation-класса (исторический Claude
  кейс azguard D28, 2026-07-18: блочная строка fable/high на 10 разнородных items, 7 из 10
  over-provisioned на 1–2 тира).

**Форма строки `## 3. Routing`** — канон для НОВЫХ планов (эмитит `plan-design`). Полная форма
несёт ДВЕ ОПЦИОНАЛЬНЫЕ колонки — `Batch` (id группы подфаз одной сессии, ниже «Батчинг подфаз»)
и `Review` (глубина ревью подфазы, enum `full`|`light`|`none`; дефолт `full`, сомнение → `full`):

```text
| Batch | Items | Model class/effort | Exec | Review | Почему |
|:--|:--|:--|:--|:--|:--|
| B1 | P2.7–P2.9 | frontier/high | manual | full | расфриз public-контракта: открытые design-решения → frontier; effort high+ MANDATORY |
| B1 | P2.10–P2.13 | implementation/low | plan-exec | light | doc-cleanup без новых решений |
```

Колонки `Batch`/`Review` — **ОПЦИОНАЛЬНЫЕ**: легаси-форма без них
(`| Items | Model class/effort | Exec | Почему |`) остаётся ВАЛИДНОЙ (back-compat ниже), их
отсутствие НЕ дефект. `Batch` пуст → подфаза исполняется одиночно (не в батче); `Review`
пуст → глубина по дефолту (`full`).

**Гранулярность.** Диапазон-строка (`P2.x–P2.y`) легальна только для ОДНОРОДНЫХ items:
один риск-класс по Tier policy, одна фраза «Почему» истинна для КАЖДОГО item'а диапазона.
При детализации фазы Routing её items ОБЯЗАН стать построчным, если однородность не
выполняется; блочная строка уровня фазы легальна лишь как черновик у НЕдетализированных
фаз. Гейт — DoR-чеклист `plan-design` (машинного линта на §3 нет — Back-compat ниже).

Колонка **Exec** — закрытый enum `plan-exec` | `manual` | `plan-design`: кто имеет право
исполнять item. Порядок: `economy < implementation < frontier`, effort
`low < medium < high < xhigh`. Минимум `task:plan-exec` — **implementation/medium**.

**Деривация Exec** (колонка пуста) и **консистентность** (колонка заполнена):

```text
Сравнение по тирам, обе оси: перебор безвреден, недобор запрещён.
- model class ≤ implementation И effort ≤ medium → plan-exec
- model class > implementation                    → manual
- effort > medium (high/xhigh/max)  → manual  (недобор thinking запрещён — policy выше)
- ячейка без модели / без effort    → недостающее берётся из матрицы ролей выше
Semantic capability IDs пишутся в отдельной ячейке/launch-block и ДОПОЛНЯЮТ route, не заменяют.

Заполненная Exec перебивает деривацию ТОЛЬКО в сторону строгости: `manual` законен при
любой паре model/effort. Обратное (`Exec = plan-exec` там, где деривация даёт `manual`) —
ДЕФЕКТ ПЛАНА, а не разрешение: иначе колонка = дыра в гейте, ровно F7.
```

**Routing-гейт** — исполняет `plan-exec` ДО работы (инцидент-основание — F7 плана
2026.07.13-PLAN-PROTOCOL-GAP: исторически contract-items ушли под Claude sonnet вопреки мандату fable/high):

```text
- Exec = manual (задан ИЛИ выведен) → item НЕ исполняется командой: СТОП, отчёт
  «ROUTING-BLOCKED: Pn.m — предписано <model-class/effort>, минимум task:plan-exec implementation/medium»,
  launch-block формы «ЗАПУСК ВРУЧНУЮ» (§8). Статус item'а НЕ меняется.
- Exec = plan-exec, Routing НИЖЕ минимума (economy и/или low) → исполнять (перебор безвреден),
  process-отклонение — в Known Deviations; статус остаётся 🟢 (§6).
- Exec = plan-exec ПРОТИВОРЕЧИТ model/effort → СТОП, отчёт «ROUTING-INCONSISTENT: Pn.m —
  Exec=plan-exec при <model/effort>»; правит `plan-design`. Статус НЕ меняется.
- Exec = plan-design → item не исполняется: СТОП, ре-дизайн (§10).
- Routing неоднозначен (строки на item нет, несколько классов/effort, проза без класса) И item —
  design/contract-класса (сработал бы любой триггер эскалации §10) → СТОП (fail-safe: цена
  ложного стопа — перезапуск, цена ложного прохода — RED-аудит).
```

**Чем исполняется `Exec = manual`.** Двумя равноправными путями, оба — под ПРЕДПИСАННОЙ
Routing route: (а) ГОЛЫМ ПРОМПТОМ item'а из launch-block'а (§8, форма `manual`);
(б) semantic command `task:plan-run <ID> Pn.m` (§13) с routing mode `inherited-plan`:
provider устанавливает selector/effort сессии, команда наследует их
и инвертирует routing-гейт — сверяет ФАКТИЧЕСКИЙ class/effort сессии с §3 Routing и на
недоборе даёт тот же `ROUTING-BLOCKED`. Граница честности названа явно: самоатрибуция
route агентом машинно НЕ проверяема, поэтому `plan-run` снимает provider-native ритуал переключения перед
серией manual-item'ов, но ЖЁСТКИЙ гейт остаётся за `plan-exec` (его пин делает недобор
структурно невозможным). Исполнитель `plan-run` ОБЯЗАН напечатать фактическую пару
class/effort в отчёте и в Update Log.

**Back-compat.** Легаси-формы §3 (проза, буллеты, таблица без колонки Exec/`Batch`/`Review`,
пустая секция) остаются ВАЛИДНЫМИ; `plan-lint` секцию §3 не парсит — гейт исполняет читающий
ИСПОЛНИТЕЛЬ, не regex. Exec легаси-строки выводится правилом деривации выше. Новые колонки
`Batch`/`Review` тоже не парсятся линтером (машинного гейта на них нет).

**Батчинг подфаз (опциональный «пульт» exec-плана).** Батч — группа подфаз, исполняемая в ОДНОЙ
сессии-исполнителе без ритуала подтверждения на каждой (мелкие подфазы не гоняют handoff→`/clear`
между собой). Носитель батча — колонка `Batch` секции §3 Routing (id группы, напр. `B1`), а НЕ
отдельный файл `exec-plan.md`: второй носитель routing/статуса дублировал бы §3/Status Board и
рассинхронизировался с ними («второй носитель факта» запрещён, §3). §3-как-полная-доска подфаз —
opt-in: план без батчинга держит легаси-форму §3.

- **Критерий слияния в батч** (все три): низкий coupling подфаз (Inputs одной НЕ ждут Deliverables
  другой ВНУТРИ батча) + совместимые `Model/effort` и `Exec` + совместимая глубина `Review`.
- **Каждая подфаза ВСЁ РАВНО несёт свою команду/модель** (свою строку §3 Routing): поток батча —
  удобство, не потеря гранулярности. Отвал от потока (ошибка, эскалация §10, смена модели) →
  оставшиеся подфазы запускаются поштучно руками (launch-block каждой валиден сам по себе).
- **Порядок внутри батча — последовательный** (механизм уже есть: `plan-exec` «Несколько item'ов
  в аргументах — исполняй последовательно, каждый по полному циклу»); закрытие КАЖДОЙ подфазы —
  полный протокол §8 (item-коммит + bookkeeping + handoff), батч закрытия НЕ сливает.
- **Инвариант «результат > экономии» (жёстко):** батчинг НИКОГДА не сливает `Review=full`-подфазу
  в поток, подавляющий её ревью. Батч наследует глубину ревью = **МАКСИМУМ риска участников**: один
  `full` в батче → весь батч ревьюится на его глубину. Классы, которые всегда `full` (напр.
  correctness-critical, public-contract/SemVer, tenant-isolation, фискалка/платежи,
  канон-которому-следует-флот), НЕ батчатся под «пропуск подтверждения» — экономия, роняющая
  результат, запрещена.

**Адаптивная глубина ревью (наполняет enum `Review`).** Классификация риска среза →
глубина ревью; ПРИНЦИП, не форс (канон не обязывает ревью на каждом срезе и не запрещает
его — даёт критерий). Дефолт `full`; `light`/`none` — только с явным обоснованием в
`Почему`; сомнение → `full` (fail-safe, как routing-гейт выше: цена ложного `full` —
лишнее ревью, цена ложного `none` — RED-баг в проде).

- **`full`** — correctness-critical, public-contract/SemVer, tenant-isolation,
  фискалка/платежи, канон-которому-следует-флот, миграции, security-sensitive.
- **`light`** — локализованная логика с зелёными детерминированными тестами, умеренный риск.
- **`none`** — косметика (доки, комментарии, форматирование, чисто-механические статус-апдейты).
- Срез не влезает ни в один класс однозначно → НЕ угадывать в сторону дешевле: `full`,
  неоднозначность назвать в Completion Notes.
- **D6-инвариант:** full-классы всегда `full` — не батчатся и не облегчаются под «пропуск
  подтверждения».
- Батч наследует глубину = МАКСИМУМ риска участников — см. «Батчинг подфаз» выше
  (связка, не переопределение: правило одно, носитель один).

## 10. Эскалация (протокол дешёвой модели)

Триггеры — закрытый enum:

- многопакетный рефакторинг
- неясная архитектура
- public contract/SemVer
- protected generated assets
- конфликт правил
- неясные acceptance

При срабатывании исполнитель оставляет ТРИ greppable-артефакта:

1. Blockquote в item:
   `> 🔴 ESCALATION Pn.m: <причина> | trigger: <из enum> | нужен: plan-design`
2. `**Status:** 🔴 Blocked` у item.
3. Финальная строка отчёта: `ESCALATION-REQUIRED: Pn.m — <причина>`.

План разошёлся с кодом → НЕ импровизировать, эскалировать: правит план plan-design,
а не исполнитель на ходу.

## 11. Межплановые паттерны

**Cross-plan gate** (прецедент AIRESTO ERP-GATE-01): зависимость плана от чужого
плана оформляется decision-доком с таблицей предусловий; каждая строка ссылается на
ТОЧНЫЙ ID строки Status Board донорского плана. Чтение однонаправленное: потребитель
читает донора, донор о потребителе не знает и не правится.

**Cross-plan notification (обратный канал).** Уведомление, которое «должен помнить
исполнитель», не исполняется (grep-прецедент: донор бампнул frozen-контракт до v2.0.2 —
у потребителей НОЛЬ упоминаний). Носитель — секция `## 7. Contracts` (§4), адресат —
конкретный item:

- Item, бампающий **замороженный** контракт (semver-bump), ОБЯЗАН нести в своих
  Deliverables: (а) обновление строки `Exported` донора (Версия + Уведомлены) и
  (б) обновление строки `Consumed` у КАЖДОГО плана-потребителя В ТОМ ЖЕ корне `plans/`
  (колонки `Замечено` + `Реакция` — item, который поднимет pin). Не «плана вообще» —
  ИМЕННО item'а: обязанность без адресата = заметка самому себе.
- Потребитель в ДРУГОМ репо линтером не проверяется — граница названа честно: запись в
  `open-questions.md` донора + строка в Open risks его handoff'а. Кросс-репо push —
  задача шины (mAInd), не plan-протокола.
- `plan-lint` в root-режиме сверяет `Consumed.Pinned` потребителя с `Exported.Версия`
  донора того же корня → **WARNING** при расхождении (механизм молод, ERROR сломал бы
  back-compat). Связь строится ОТ потребителя (его `Consumed.Донор-план`) — единственное
  детерминированное направление; колонка `Потребители` донора человекочитаемая.

**Программный план** (прецеденты FLEX-IMPL, ECOSYSTEM P4): координационный план над
делегатами — `Document Type: Program Master Plan (coordination)`; items =
milestone-делегаты (по плану-делегату на item); Validation item'а = GREEN-аудит
делегата; код в программном плане НЕ пишется. Execution Rules такого плана обязаны
запрещать `task:plan-exec` и указывать предписанный orchestration carrier.

## 12. Жизненный цикл: два дома, архив, документация

**Модель двух домов** (RAG:✅ P5.1 §2 docs-as-code: git=SSOT, hub=display/index;
внешнего канона именно для Obsidian↔repo two-way не найдено — механизм наш
`brain sync`). SSOT плана определяется стадией:

- **Home по умолчанию — репо проекта** (D31): план живёт там, где его deliverables
  (`plans/<ID>` репо, Meta `Home: repo:<путь>`); в Brain остаётся программный/
  межпроектный план, чьи deliverables размазаны по нескольким репо;
- **на старте exec** — repo-копия становится SSOT; Brain-зеркало синкается
  `brain sync`-каналом (frontmatter `repo:` — тот же механизм, что docs/);
- **во время exec** — SSOT = репо; правки базового плана в Brain молча ЗАПРЕЩЕНЫ —
  только через протокол конфликтов; направление синка по умолчанию repo→Brain
  (зеркалирование), не наоборот;
- **после завершения** — синк обратно → архив → миграция root/ в docs.

**Протокол конфликтов.** Базовый план изменился во время исполнения → исполнитель
НЕ мержит молча: фиксирует `temporary divergence` в Known Deviations текущего item →
эскалация по разделу 10; владелец решает — принять в working-копию новым D# или
отложить до конца фазы.

**Скиллы — тот же принцип:** SSOT скиллов — всегда swissknifeman; vendor-копии в
проектах обновляются только `skiller vendor/connect`; локальная правка vendor-копии =
дефект, путь — contribution в SSOT (см. `package-contribution-protocol`).

**Конвейер план→архив→docs** (RAG:✅ P5.1 §2 Diátaxis + Oxide «committed =
реализовано»). По терминальности плана — carrier `archive: task:plan-close archive <ID>`:

1. План перемещается в `plans/archive/<ID>` ОТДЕЛЬНЫМ коммитом
   `chore(plan): archive <ID>`.
2. Из `root/` собирается документация проекта по Diátaxis-типам:
   architecture/philosophy → explanation; data-model/contracts → reference;
   гайды фаз → how-to.
3. Чек-лист миграции (что перенесено в docs, что осталось в архиве) — в финальном
   handoff.

**Планы НЕ удаляются — никогда.** Терминальный план переезжает в `plans/archive/<ID>`
и хранится вечно (провенанс решений: D-лог, Completion Notes, Known Deviations —
единственный источник «почему так сделано» спустя месяцы). `rm`/`git rm` каталога
плана — дефект, а не операция протокола; superseded-предшественник тоже уходит в
архив, не в корзину. Единственное исключение — явное распоряжение владельца с
флагом `--force` в команде (агент по своей инициативе удаление не предлагает).

## 13. Командный протокол

| Semantic command ID | Model class/effort | Что делает |
|:--|:--|:--|
| `task:plan-design` | frontier/high | новый план / новая фаза / ТЗ item'ов; refine-цикл + DoR-гейт |
| `task:plan-exec` | implementation/medium | исполнить item; самозакрывающийся (обновляет статусы + handoff) |
| `task:plan-run` | minimum item route; observed route СЕССИИ | исполнить `Exec = manual`; inherited-plan гейт сверяет обе оси до работы |
| `task:plan-close` | implementation/low | реконсиляция статусов / закрытие фазы / режим `archive` |
| `task:plan-audit` | frontier/xhigh | adversarial-аудит фазы; вердикт GREEN/ATTENTION/RED |

Provider mapping проецирует эти minima в native selectors. `plan-run` не имеет fixed route:
его минимум приходит из item Routing, а observed route сессии проверяется тем же fail-closed
гейтом. Claude invocation — `/task:…`, Codex — `$ task:…`; UI prefix не semantic identity.

**Task Contract compiler (v2.14.0).** Pre-mutation/pre-final предикаты, precedence/conflict-
резолюция, content-hash и tiered-portability классификация — один модуль,
`packages/task/lib/task/task_contract.py` (`root/contracts/task-contract-v1.md` +
`plan-portability-v1.md` плана `2026.07.24-AGENT-RELIABILITY`, items P2.2/P2.6/P2.7/P2.10/P2.11).
Обе границы ЗОВУТСЯ исполняемо, не прозой, и на ОБОИХ путях закрытия item'а: `task:plan-exec`
собирает и проверяет контракт ДВАЖДЫ за один прогон — pre-mutation ПЕРЕД мутацией (шаг 2) и
pre-final при самозакрытии (шаг 7, штатный путь — item закрывает себя сам, реконсилирующий
`task:plan-close` на этом пути не вызывается); `task:plan-close`'s Pre-final (режим `Pn.m`, шаг 4)
— тот же вызов для item'ов, закрываемых реконсиляцией. Каждый вызов собирает Task Contract v1
(`task_contract.build`, живой actual route передаётся его же документированным kwarg'ом
`actual_route` — CLI-форма держит его неразрешённым ради байт-детерминированности между
процессами) и проверяет (`task_contract.evaluate`). **Гейт закрытия БИНАРЕН** (D76): зелёное —
РОВНО `pre_mutation == "allow"` И `pre_final == "allow"`; `n/a` — НЕ зелёное («сессия
заблокирована, объявлять сдачу нечего» — `task-contract-v1.md` §Pre-final predicate дословно),
любой `block:*` — тем более (таблица код→действие — в самих файлах команд, не здесь второй раз).
**Маршрут `actual_route` на pre-final — маршрут ИСПОЛНИТЕЛЯ item'а** (D75), не пин закрывающей
команды: у `task:plan-exec`/`task:plan-run` (самозакрытие) это own pin/observed route сессии; у
реконсилирующего `task:plan-close` — лестница разрешения из закоммиченной записи (routing-
adherence Completion Notes → терминальная запись `journal.jsonl` → неразрешимо/расхождение =
СТОП с названным ПРОХОДОМ). `task:plan-run` подставляет НАБЛЮДАЕМЫЙ route сессии в оба вызова
`plan-exec` вместо пина; `task:plan-audit` читает получившиеся `pre_mutation`/`pre_final` коды
ОБЕИХ границ из Completion Notes закрытого item'а как источник истины, вместо повторного счёта
вручную — item `🟢`/`🟠` с кодом ≠ `allow` на любой границе = находка. `plan_lint.py` зовёт тот же
строковый тест «внешности» пути для tiered-portability lint'а. **Что утверждает `pre_final`**
(D77): свойство ФОРМЫ спеки item'а — есть ли хотя бы один публично проверяемый acceptance-пункт
на детерминированном классе доказательства — а НЕ то, что item исполнен хорошо (он зелен и на
не стартовавшем `⬜`-item'е); вердикт material/process остаётся за status-rule §6, этот код его
не заменяет. Это утверждение защищено литеральным тестом (`test_canon_literals.py`), который
падает, если формулировка изменится без изменения тел команд (P2.7/P2.11, F1-репарация: до
2.13.0 канон утверждал «команды зовут», а звала только проза; до 2.14.0 звала только на одной
из двух границ закрытия, и `n/a` зеленел закрытие вслепую). **Тест защищает РАЗЛИЧАЮЩИЙ
предикат, не наличие идентификатора** (D79): каждый новый ассершен обязан быть проверен на
СТАРОМ тексте команды и там покраснеть — ассершен, зелёный и до правки, ничего не защищает
(ровно то, чем был литеральный тест до 2.14.0: он проверял подстроки и прошёл зелёным через
дефект `n/a`-гейта).

**Evidence bundle (v2.13.0).** Item тира `committed-bundle` (`plan-portability-v1.md`
§Classification rule, D26) обязан нести коммиченный evidence bundle с bundle-требованиями
(SSOT — `plan-portability-v1.md` §Bundle requirements, здесь только ЦИТАТА, не
переписывание): минимизация (только то, что фактически прочитано для execution input —
`privacy.minimized`/`excluded_classes` называет оставленное за бортом: сырые тела
транскриптов, chain-of-thought, tool-payloads, секреты), детерминированный manifest +
верификатор (хеши пересчитываются, никогда не доверяются как написанные), полное замыкание
зависимостей, один нейтральный semantic carrier с provider-рендерами, ни один public
acceptance-предикат не опирается на `pinned-not-recomputable`/`unknown` evidence. Исполнимая
форма — `snippets/source-evidence-template.md` (структура manifest'а, обязательные поля,
команда верификации, явный перечень запрещённых классов содержимого). Соответствие
ВЫЧИСЛЯЕТ, а не читает как декларацию, `task_contract.bundle_lint` (P2.6) — по фактическим
байтам bundle'а.

## 15. Per-project deployment

Планы живут В ПРОЕКТЕ, не в `~/.claude/plans/`: top-level ключ
`plansDirectory: "plans"` в `.claude/settings.json` проекта (шаримый, коммитится).
Раскатка — три слоя:

- `harness hooks --target <проект> --plans-dir plans` — точечная ручка (ключ, занятый
  другим значением, уважается — не перезаписывается);
- `maind sync --only plans-dir,plans-doc` — флот онбордженных проектов
  (opt-out: `project.plans_dir="off"`);
- `skiller integrate` — новые онбординги (блок plans-dir, дефолт «да»).

Конвенцию в проект приносит managed-блок `maind:plan-conventions` в CLAUDE.md
(провижионер `plans-doc`). Мост из встроенного plan mode: одобренный план сохраняется
плоским черновиком в `plans/` → `task:plan-design from-draft <файл>` разворачивает
его в `plans/<ID>/` по шаблонам этого скилла (черновик удаляется, история — в git).

## 16. Слои знаний плана: brief/ → findings/ → research/ → решения

Канон слоёв. Цепочка «вход → сырьё → синтез → решение» обязана восстанавливаться из файлов
плана БЕЗ доступа к чату авторской сессии — иначе доработка плана переплачивает за
восстановление «откуда что взялось», а мысли владельца/модели теряются.

0. **Слой 0 — вход владельца (`brief/`, ОБЯЗАТЕЛЕН, гейт plan-lint):**
   `brief/00-brief.md` — исходное сообщение владельца, переформулированное БЕЗ потери
   мыслей (не пересказ-выжимка: каждая мысль сохраняется, меняется только форма);
   всё, что выясняется в процессе (ответы на вопросы, закрытые развилки, смены скоупа), —
   ДОПИСЫВАЕТСЯ датированными блоками (`brief/01-refinements.md` или новые файлы).
   Задача слоя: из плана видно, «что было на входе → к чему пришли» — это же материал
   для улучшения самого процесса планирования. Без непустого `brief/*.md` план не
   проходит утверждение (датовые планы от 2026.07.16 — ERROR линтера).
1. **Слой 1 — сырьё извне (`findings/`):** всё полученное из внешних источников в ходе
   работы над планом — RAG-выжимки (источник-URL + дата верификации + вердикт),
   recon-отчёты субагентов, выжимки исходных документов (письма/спеки; бинарные вложения —
   рядом, напр. `findings/email-assets/`), диагнозы/репро.
   **Правило немедленной фиксации:** результат RAG-вызова или разведки, повлиявший на план,
   записывается в `findings/` в том же ходе работы, не «потом»; несущий факт, живущий
   только в чате, — дефект (находка plan-audit).
2. **Слой 2 — синтез автора (`research/`):** design-документы модели — анализы,
   целевые структуры, доменные модели, тест-стратегии, выжимка требований владельца
   (user-intent с трассировкой «мысль → куда ушла»). Каждый синтез ссылается на файлы
   слоя 1, на которых стоит; синтез без источника несёт `[UNVERIFIED]` или
   `RAG:— (repo-grounded: …)`.
3. **Слой 3 — решения (`## 5. Decision Log`, ADR, `root/`):** D-записи ссылаются на файлы
   слоёв 1–2 и несут RAG-маркеры (§7); долгоживущий канон — `root/` (судьба — docs, §3).

- **Путь и имя:** `findings/<Pn>-<slug>.md` (фазовые) либо `findings/<тема>-<дата>.md`
  (общеплановые, напр. `rag-2026-07-16.md`); `research/NN-<slug>.md` (NN — порядок чтения).
- **Как ссылаются:** item указывает файлы слоёв в `Inputs`/`Required Reads` — исполнитель
  читает файлы, а не чат; при детализации фазы (`plan-design Pn`) research-файлы фазы
  читаются ПЕРВЫМИ.
- **Опциональность:** каталоги опциональны, только пока пусты по факту: если RAG-вызовы,
  разведка или авторский синтез БЫЛИ — их фиксация в соответствующем слое обязательна.
  Схема 16 полей item'а не меняется, `plan_lint.py` каталоги не проверяет (не его слой).
