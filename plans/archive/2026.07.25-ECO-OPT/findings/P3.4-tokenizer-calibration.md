## 1. Модель листингового бюджета — дизайн и сверка с эмпирикой P3.1

First-party (`findings/P3-skill-desc-and-mcp-limits.md` §1, RAG:✅ 2026-07-25 `/docs/en/skills`):
бюджет = 1% контекстного окна модели; каждая запись (`description`+`when_to_use`) капается на
**1 536 символов**; при переполнении клиент дропает записи «starting with the skills you invoke
least» (порядок дропа зависит от истории вызовов конкретного проекта — этой величины у нас нет).

Реализация (`budget.py`):

```python
SKILL_LISTING_MAX_ENTRY_CHARS = 1_536
SKILL_LISTING_BUDGET_FRACTION = 0.01
SKILL_LISTING_CONTEXT_WINDOW = 1_000_000

def _listing_entry_tokens(skill_dir):
    # name без обрезки + description(+when_to_use), капнутые до 1536 симв,
    # оценены estimate_tokens (тот же измеритель, что и весь модуль).
    ...

def _measure_skills(env, target, *, listing_fraction=..., listing_context_window=...):
    raw = sum(_listing_entry_tokens(d) for ... in skills)   # Σ капнутых записей
    budget = int(listing_context_window * listing_fraction)  # потолок, В ТОКЕНАХ
    resident = min(raw, budget)                              # МОДЕЛЬ потолка, не порядок дропа
    ...
```

**Осознанное упрощение (Scope Included: только модель, не полная симуляция клиента).** Реализован
именно **потолок** (`resident = min(raw, budget)`), а не порядок «кто именно дропается» — точный
список зависит от частоты вызова скиллов в конкретном проекте, эта телеметрия недоступна `budget.py`
(тот же вывод, что и в `findings/P3.1-listing-diagnosis.md` §5: «точный список записей без описания
недоступен даже `/doctor`»). Отчёт `--first-turn` теперь показывает ОБА числа: `raw_tokens` (сумма
капнутых записей) и `tokens` (после потолка) — по Implementation Rules item'а «если фактический
резидент теперь меньше суммы описаний, показать оба числа».

**Единица бюджета — ТОКЕНЫ, не символы (сверено против живой эмпирики P3.1).**
`findings/P3.1-listing-diagnosis.md` §0/§5 (Pending Work п.2 адресован явно этому item'у) — живой
`claude --debug-file` на `flexcrm` дал `47021 chars > 30000 budget` (не 10 000 симв, как считал
первый заход слоя 1/2); `/context` на том же проекте показал пост-бюджетный размер листинга
**9,9k ТОКЕНОВ** — «почти точно совпадает с исправленным бюджетом (30 000 симв ⁄ ×3 симв/ток ≈
10 000 ток)». Иными словами: 30 000 символов — это КАК клиент хранит потолок внутри (символьный
кап), но при пересчёте через СВОЙ токенайзер он ложится ровно на `context_window × 1% = 10 000
ток` для 1M-модели. `budget.py` считает всё в ТОКЕНАХ через собственный `estimate_tokens` (тот же
измеритель, что весь модуль) — поэтому `SKILL_LISTING_CONTEXT_WINDOW × SKILL_LISTING_BUDGET_FRACTION
= 1 000 000 × 0.01 = 10 000 ток` **уже совпадает** с эмпирическим 9,9k (расхождение ~1%, в пределах
грубости `estimate_tokens`) — реализация НЕ требует правки под поправку P3.1, только явного
подтверждения записью здесь (что и делается этой секцией). Работать в символах (30 000) и
конвертировать код на char-based потолок было бы избыточным вторым путём к тому же числу и внесло
бы риск рассинхрона с `estimate_tokens`, которым уже посчитан весь остальной отчёт.

**Не проверено (нет `count_tokens`):** первоисточник называет 1 536 символов дефолтом cap на
запись — этот дефолт НЕ был предметом эмпирической проверки P3.1 (она проверяла только общий
потолок, не per-entry cap), поэтому взят как есть из first-party прозы, риск расхождения тот же,
что был у общего бюджета до поправки §0 P3.1 — если появится живая проверка (напр. скилл с
description близко к 1536 симв на реальном проекте и наблюдение `--debug`), это войдёт в
Pending Work следующего захода.

## 3. Pending Work — перекалибровка токенайзера (Scope Included «б», НЕ выполнено)

**Причина:** `count_tokens` (`POST /v1/messages/count_tokens`) недоступен в исполнительной
песочнице этого захода — нет `ANTHROPIC_API_KEY` в окружении, нет установленного `anthropic` SDK
(`ModuleNotFoundError`), нет `ant` CLI на `$PATH`. Сеть до `api.anthropic.com` технически отвечает
(`curl` → HTTP 405 на POST без тела, эндпоинт жив), но без креденшелов вызов невозможен —
Code Guidance item'а запрещает эмулировать результат «по ощущению».

**Что именно осталось невыполненным:**
- `CHARS_PER_TOKEN_CYR = 2.9` / `CHARS_PER_TOKEN_LAT = 3.4` (`budget.py:47-48`) — калиброваны RAG
  perplexity-оценкой 2026-07-02 (три источника), не прямым замером `count_tokens` на корпусе этого
  репо через `claude-opus-5`.
- `FIRST_TURN_TARGET_MAX = 7_000` / `FIRST_TURN_WARN = 10_000` (`budget.py:193-194`) — сохранены
  БЕЗ изменений (доля контекстного окна, которую они выражали на прежней шкале, не выведена заново
  через замер — правка «ради правки» без числового основания запрещена Code Guidance item'а).

**Точная команда для следующего захода** (оператор с сетевым доступом и `ANTHROPIC_API_KEY`,
или `ant auth login`):

```
ant messages count-tokens --model claude-opus-5 --message '{"role":"user","content":"@./CORPUS.md"}' \
  --transform input_tokens -r
```

где `CORPUS.md` — конкатенация реальных first-turn компонент (CLAUDE.md + skill listing + agents)
≥2 проектов (`flexcrm`, `swissknifeman`), как предписывает Scope Included item'а. Результат
сравнить с `estimate_tokens` на том же тексте, вывести новые `CHARS_PER_TOKEN_*` из расхождения
(если оно >10% — Code Guidance item'а: расхождение <10% значит «перекалибровка не нужна», это
тоже легальный результат, зафиксировать числом и не трогать константы). Пороги `FIRST_TURN_*`
пересчитать с сохранением доли контекстного окна (не абсолютного числа), как предписывают
Implementation Rules.
